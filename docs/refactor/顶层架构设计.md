## 0. 背景与设计目标

### 0.1 为什么要重构

Phase 1–10 完成的架构（下称"旧架构"）在 Python 调用场景下比 Python 原版慢约 5 倍。
根因经源码级对比确认，是**架构范式**而非局部优化不足：

- **Per-operation FFI 穿越模型**：construct 树是跨 FFI 边界的混合树，每个 Python 回调节点
  触发多次 FFI 往返。
- **Value enum 强制中转**：parse 先构建 `Value` 树再递归转 Python 对象；build 反向同理。
  这是贯穿数据流的 O(n) 系统性开销，是性能差距的**最大单一贡献因素**。
- **Context 全量转换**：每次表达式求值都重建整个 Context 的 Python 镜像。
- **`Box<dyn Construct>` 动态分发**：虚函数表跳转，无法内联。

对照 pydantic-core 的成功范式（build-once 编译 + 纯 Rust 执行树 + 直接操作 `Py<PyAny>` +
enum_dispatch），construct-rs 需要根本性重构。

### 0.2 重构的设计目标

| 目标 | 衡量标准 |
|------|---------|
| G1 Python 调用性能 | 几何平均 ≥1.0x（达到 Python 原版水平）；力争 ≥2x |
| G2 Rust 原生性能 | 不劣于旧架构（重构不得让纯 Rust 路径退化） |
| G3 API 兼容性 | 用户声明式 API（`Struct`/`/`/`this`）行为与 construct 原版一致 |
| G4 dataclass-first API | `ConstructMixin` + `cs_field` + `from_bytes`/`to_bytes`，Container 对用户消失 |
| G5 可维护性 | FFI 边界从 ~6 个文件（conversions/expr_bridge/py_adapter…）收敛到清晰边界 |
| G6 渐进性 | Rust 内核可分阶段重构，不要求一次性推翻重写 |

### 0.3 重构的核心范式转变

```
旧范式：per-operation bridging          新范式：build-once, run-pure-Rust
─────────────────────────────           ─────────────────────────────────
Python 声明树（混合）                    Python 声明（不变）
   ↓ 每次 parse/build                       ↓ 一次性编译（build-once）
跨 FFI 来回穿越                           编译为纯 Rust 执行树
每节点 Value↔Py 转换   ───────►          运行时：单次 FFI 进入
Context 全量转换                          整棵树 Rust 内遍历
                                         直接产出 Python 对象
```

### 0.4 设计约束（领域不可妥协项）

construct 与 pydantic 的领域差异决定了某些 pydantic 做法**不能照搬**：

1. **必须支持双向对称**（parse + build），pydantic 只需单向验证。
2. **必须有 Stream/seek/tell 能力**（Pointer/Anchor/Seek/Tell），pydantic 处理已结构化数据。
3. **表达式系统更复杂**：`this._._.field` 沿 parent 链向上查找，`obj_` 引用被构建对象，
   支持任意 Python 表达式。pydantic 只需访问当前字段值。
4. **parse 产出是全新数据**（从字节流构造），pydantic 输入本身就是 Python 对象。

> 这些约束在 §3 各决策中逐条体现，是该方案与"直接抄 pydantic"的关键区别。

## 1. 全局架构图

### 1.1 模块划分

重构后系统分为三大层：**Python 用户层 / 编译执行层 / Rust 内核层**。

```
┌─────────────────────────────────────────────────────────────────────┐
│  Python 用户层（construct-py + 纯 Python）                           │
│  ┌─────────────────────────┐  ┌──────────────────────────────────┐  │
│  │ 声明式 API（兼容）       │  │ dataclass-first API（新增）       │  │
│  │ Struct/"name"/Byte/this │  │ ConstructMixin + cs_field        │  │
│  │ + 运算符重载组合         │  │ from_bytes / to_bytes            │  │
│  └────────────┬────────────┘  └──────────────┬───────────────────┘  │
│               │ 构建时（一次性）               │                      │
│               ▼                                ▼                      │
│  ┌─────────────────────────────────────────────────────────────────┐ │
│  │ SchemaCompiler（编译层，FFI 边界 #1：per-tree 一次）             │ │
│  │  - 遍历 Python 声明树                                            │ │
│  │  - 提取每个节点的类型 + 参数                                       │ │
│  │  - 内联字段路径、预编译表达式（this.field → Rust 闭包）            │ │
│  │  - Python 回调封装为 PyCallback 节点（保留 Py<PyAny> 引用）       │ │
│  │  产出：CompiledSchema { tree: CompiledNode }（纯 Rust）         │ │
│  └─────────────────────────────────────────────────────────────────┘ │
└──────────────────────────────┬──────────────────────────────────────┘
                               │ 运行时（每次 parse/build）
                               │ FFI 边界 #2：顶层单次穿越
                               ▼
┌─────────────────────────────────────────────────────────────────────┐
│  Rust 内核层（construct-rs）                                          │
│  ┌─────────────────────────────────────────────────────────────────┐ │
│  │ 执行树（CompiledNode / enum_dispatch）                           │ │
│  │  parse_bytes(data, target) → 直接产出 target                     │ │
│  │    target = PyDict（声明式）或 dataclass（dataclass-first）       │ │
│  │  build_from(input) → bytes                                       │ │
│  │    input = 按 Input trait 惰性读取                                │ │
│  │  整棵树遍历在 Rust 内完成，PyCallback 节点才穿越 FFI               │ │
│  └─────────────────────────────────────────────────────────────────┘ │
│  ┌──────────────────┐  ┌───────────────┐  ┌──────────────────────┐  │
│  │ 旧内核构造器       │  │ Context        │  │ Stream               │  │
│  │ （Phase 1-9 复用） │  │ （惰性视图）   │  │ （字节流，领域必需）  │  │
│  └──────────────────┘  └───────────────┘  └──────────────────────┘  │
└─────────────────────────────────────────────────────────────────────┘
```

### 1.2 模块清单与职责

| 模块 | 位置 | 职责 | 复用/新增 |
|------|------|------|----------|
| **声明式 API** | `construct-py` | 用户组合 construct 树的 Pythonic 接口 | 复用旧 API，内部改造 |
| **ConstructMixin** | `construct-py/construct_rust/mixins.py` | dataclass-first API | **新增** |
| **SchemaCompiler** | `construct-py`（Rust） | Python 声明树 → 编译执行树 | **新增**（核心） |
| **CompiledSchema/执行树** | `construct-rs`（新模块） | 运行时遍历，direct-to-Python | **新增** |
| **PyCallback 节点** | `construct-rs` | 嵌入执行树的 Python 回调封装 | **新增**（替代旧 PyClosure/PyConstructAdapter） |
| **内核构造器** | `construct-rs/src/constructs` | 二进制 parse/build 实现 | **复用** Phase 1-9 |
| **Context** | `construct-rs/src/core` | 运行时上下文 | 复用结构，增惰性视图 |
| **Stream** | `construct-rs/src/core` | 字节流操作 | **复用**（领域必需） |
| **表达式编译** | `construct-rs` | `this.field` → Rust 求值；纯 Rust 表达式树 + PyCallback 回退 | **复用**（保留 expr.rs 语义，enum_dispatch 优化分发） |

### 1.3 模块间调用关系（调用方向）

```
Python 用户层
    │ 调用方向（向下）
    ▼
SchemaCompiler  ──编译──►  CompiledSchema（Rust 执行树）
                              │
                              │ 运行时：调用方向（向下，Rust 内部）
                              ▼
                          执行树遍历（CompiledNode）
                              │
                   ┌──────────┼──────────┐
                   ▼          ▼          ▼
              内核构造器    Context    Stream
            （parse/build）（惰性视图）（字节读写）
                   │
                   │ 遇到 PyCallback 节点时
                   ▼ （唯一的树内 FFI 穿越）
              Python 回调（表达式/Adapter）
```

**关键：调用方向是单向收敛的**——上层依赖下层，下层不回调上层（除显式的 PyCallback
节点）。这与旧架构"树在 FFI 边界来回穿梭"形成鲜明对比。

### 1.4 与 pydantic-core 架构的对比定位

| 维度 | pydantic-core | 本方案（construct-rs 重构后） | 差异原因 |
|------|--------------|---------------------------|---------|
| 编译产物 | `Arc<CombinedValidator>` 验证器树 | `CompiledSchema` 执行树 | 同范式（build-once） |
| 分发机制 | `enum_dispatch` | `enum_dispatch`（CombinedConstruct） | 完全借鉴 |
| 值表示 | 直接 `Py<PyAny>` | **双轨**：Python 路径直接 `Py<PyAny>`；Rust 路径用 Value | construct 需双向对称 + Rust 原生用户 |
| 输入抽象 | `Input` trait（按需读 int/str/dict） | `Input` trait（按需读字段） | 借鉴，用于 build 方向 |
| Stream | **无** | **有**（领域必需，Pointer/Seek/Tell） | construct 解析二进制流 |
| 表达式 | 无（只访问字段值） | **有**（this/obj_，编译为 Rust 求值） | construct 领域特有 |
| Context 转换 | 传引用，零转换 | 惰性视图，按需转换单字段 | construct context 更复杂 |

**定位总结**：本方案 = pydantic-core 的执行范式 + construct 的领域特征（双向对称、流操作、
表达式系统）。不是"翻译 pydantic"，而是"用 pydantic 的高性能范式解决 construct 的领域问题"。

## 2. 数据流向图

### 2.1 Parse 路径完整数据流（Python 声明式 API）

```
用户 Python 代码
│  schema = Struct("len"/Byte, "data"/Bytes(this.len))
│  result = schema.parse(b"\x03ABC")        # 调用点
│
▼  ┌─────────────────────────────────────────────────────────────────┐
   │ 步骤 A：构建阶段（build-once，仅在 schema 定义时执行一次）        │
   │                                                                 │
   │  1. Python 运算符组合出声明树（PyO3 wrapper 对象）                │
   │  2. 首次 parse/build 时，SchemaCompiler 介入（或显式 .compile()） │
   │  3. 遍历声明树：                                                 │
   │     - 提取节点类型 + 参数（Byte 的字节序、Bytes 的长度源…）       │
   │     - this.len → 编译为 Rust 原生路径求值闭包（无 Python 回调）   │
   │     - 产出 CompiledSchema { tree: StructNode[...] }             │
   │  4. 缓存 CompiledSchema（同一 schema 对象复用）                  │
   └─────────────────────────────────────────────────────────────────┘
   │
   │  ★ FFI 穿越 #1（构建时，一次性，与 parse 次数无关）
   │     穿越内容：声明树的结构信息（类型名 + 参数 dict）
   │     穿越次数：每 schema 1 次（缓存后为 0）
   │
▼  ┌─────────────────────────────────────────────────────────────────┐
   │ 步骤 B：运行时入口                                                │
   │                                                                 │
   │  result = cached_schema.parse_bytes(py, data, target=PyDict)    │
   │                                                                 │
   │  ★ FFI 穿越 #2（顶层单次，每次 parse 1 次）                       │
   │     穿越内容：data: &[u8]（字节切片引用，零拷贝）                 │
   │     进入 Rust，持有 GIL                                          │
   └─────────────────────────────────────────────────────────────────┘
   │
▼  ┌─────────────────────────────────────────────────────────────────┐
   │ 步骤 C：执行树遍历（纯 Rust，整棵树在 Rust 内完成）               │
   │                                                                 │
   │  output = PyDict::new(py)              # 直接构建 Python dict    │
   │  ctx = Context::new()                  # Rust 内部上下文          │
   │  stream = ByteStream::new_read(data)   # Rust 内部字节流          │
   │                                                                 │
   │  for field in &tree.fields:                                     │
   │      match field {                                              │
   │          ByteField => {                                          │
   │              bytes = stream.read_bytes(1)?                       │
   │              val = u8::from_be_bytes(...)                        │
   │              ctx.insert("len", val)    # 写入 Rust context       │
   │              output.set_item("len", val.into_py(py))?  # 直出   │
   │          }                                                       │
   │          BytesField(len_expr) => {                               │
   │              # this.len 已编译为 Rust 闭包，无 FFI               │
   │              len = len_expr.eval(&ctx)?                         │
   │              bytes = stream.read_bytes(len)?                    │
   │              output.set_item("data", PyBytes::new(py, bytes))?  │
   │          }                                                       │
   │      }                                                           │
   └─────────────────────────────────────────────────────────────────┘
   │
   │  ⚠ 仅当遇到 PyCallback 节点（用户自定义 Adapter/复杂表达式）时
   │     才发生树内 FFI 穿越 #3，按需触发（详见 §3.6）
   │
▼  ┌─────────────────────────────────────────────────────────────────┐
   │ 步骤 D：返回                                                     │
   │                                                                 │
   │  return output.unbind()    # Py<PyAny>，已经是最终 Python 对象   │
   │                                                                 │
   │  ★ FFI 穿越 #4（返回，每次 parse 1 次）                          │
   │     穿越内容：已构建好的 Py<PyAny>（dict / dataclass 实例）      │
   └─────────────────────────────────────────────────────────────────┘
   │
▼  用户拿到 result（dict 或 dataclass，无 Value enum 中间层）
```

**Parse 路径 FFI 穿越总计**：构建时 1 次（可缓存为 0）+ 运行时 2 次（进/出）+
可选的树内回调穿越。对比旧架构：顶层 1 次 + **每个 Python 回调节点 5+ 次**。

### 2.2 Build 路径完整数据流

```
用户 Python 代码
│  schema.build({"len": 3, "data": b"ABC"})   或   orm.to_bytes()
│
▼  ┌─────────────────────────────────────────────────────────────────┐
   │ 步骤 A：Input trait 惰性包装（按需读取，不预转换）                │
   │                                                                 │
   │  input = PyInput::new(py, obj)   # 持有 PyObject 引用           │
   │  # 不立即遍历整棵树，仅在访问 input.get("len") 时按需读取         │
   │                                                                 │
   │  ★ FFI 穿越 #1（进入，每次 build 1 次）                          │
   │     穿越内容：PyObject 引用 + data 目标                         │
   └─────────────────────────────────────────────────────────────────┘
   │
▼  ┌─────────────────────────────────────────────────────────────────┐
   │ 步骤 B：执行树遍历（按需从 Input 读取字段）                       │
   │                                                                 │
   │  stream = ByteStream::new_write()                               │
   │  ctx = Context::new()                                           │
   │  for field in &tree.fields:                                     │
   │      match field {                                              │
   │          ByteField => {                                          │
   │              val = input.get_int("len")?  # 按需读，FFI 局部     │
   │              ctx.insert("len", val)                             │
   │              stream.write_bytes(&[val as u8])?                  │
   │          }                                                       │
   │          BytesField(len_expr) => {                               │
   │              len = len_expr.eval(&ctx)?    # 已编译，无 FFI       │
   │              bytes = input.get_bytes("data")?  # 按需读         │
   │              stream.write_bytes(&bytes)?                        │
   │          }                                                       │
   │      }                                                           │
   └─────────────────────────────────────────────────────────────────┘
   │
   │  注意：Input trait 的 get_* 调用是细粒度 FFI，但只在需要该字段
   │  时发生，且只读单个标量（不递归）。对比旧架构 py_to_value 全量递归。
   │
▼  ┌─────────────────────────────────────────────────────────────────┐
   │ 步骤 C：返回                                                     │
   │                                                                 │
   │  bytes = stream.into_bytes()                                    │
   │  return PyBytes::new(py, &bytes)                                │
   │                                                                 │
   │  ★ FFI 穿越 #2（返回，每次 build 1 次）                          │
   │     穿越内容：构建好的 bytes                                      │
   └─────────────────────────────────────────────────────────────────┘
   │
▼  用户拿到 bytes
```

### 2.3 FFI 穿越点汇总表

| # | 时机 | 方向 | 内容 | 频率 | 与旧架构对比 |
|---|------|------|------|------|------------|
| 1 | 构建阶段 | Python→Rust | 声明树结构 | 每 schema 1 次（可缓存） | 旧架构无显式编译，每次都遍历混合树 |
| 2 | parse 运行时入口 | Python→Rust | data bytes + GIL | 每次 parse 1 次 | 同（顶层穿越不可避免） |
| 3 | parse 树内（可选） | Rust→Python | PyCallback 调用 | 仅 PyCallback 节点 | **旧架构每个 Python 节点 5+ 次**，新架构仅用户自定义回调 |
| 4 | parse 返回 | Rust→Python | Py<PyAny> 产出 | 每次 parse 1 次 | 同 |
| 5 | build 运行时入口 | Python→Rust | PyObject 引用 | 每次 build 1 次 | 同 |
| 6 | build 树内（细粒度） | Rust→Python | 单字段读取（Input） | 按需，每字段 1 次标量读 | **旧架构 py_to_value 全量递归**，新架构按需惰性 |
| 7 | build 返回 | Rust→Python | bytes | 每次 build 1 次 | 同 |

**核心收益**：树内 FFI 从"每个 Python 节点多次"降到"仅 PyCallback 节点"；Value 中转从
"贯穿全程"降到"Python 路径完全消除"。

## 3. 关键架构决策

每项决策给出：**选项 → 选择 → 理由**。所有理由基于 Python 源码事实与 pydantic 对比，
非理论推断。

### 3.1 决策 D1：分发机制

**问题**：执行树内部如何分发到具体构造器（Struct/Byte/Array…）？

| 选项 | 说明 | 评估 |
|------|------|------|
| A. `Box<dyn Construct>`（旧架构） | trait object，虚函数表跳转 | 无法内联；缓存局部性差；旧架构缺陷 §3.3 |
| B. `enum_dispatch`（pydantic 用法） | `CombinedConstruct` enum + 宏生成 match | 零开销；编译器可内联；分支预测友好 |
| C. 全泛型（编译期单态化） | 每棵树是具体类型 | 性能最优但破坏动态组合（construct 核心需求）；编译爆炸 |

**选择：B（enum_dispatch）**

**理由**：
1. pydantic-core 实测验证（`CombinedValidator` enum，`mod.rs:723-824`）：编译器对 match
   分支做内联优化，分支预测器对稳定类型预测良好。
2. construct 的异构集合需求（`Vec` 中存不同构造器）由 enum 天然满足，与 `Box<dyn>` 能力
   对等但零开销。
3. 旧架构的 `Box<dyn Construct>`（`core/mod.rs:50-66`）是缺陷 §3.3 的直接来源，机械替换
   风险低、收益明确。
4. 选项 C 虽性能最优，但 construct 树由用户在运行时组合（`"a"/Byte + "b"/Bytes(...)`），
   无法在编译期确定形状，泛型单态化不适用。

**实现方向**：定义 `CombinedConstruct` enum（含约 20-30 个 variant 覆盖所有构造器类别），
通过 `#[enum_dispatch]` 生成 `Construct` trait 的 match 分发。新增构造器只需加 variant。

**对 Rust 原生路径的影响**：纯 Rust 用户也受益（零开销分发），不退化。

### 3.2 决策 D2：Value 是否保留

**问题**：Rust 内核是否还需要自己的动态类型系统（Value enum）？

| 选项 | 说明 | 评估 |
|------|------|------|
| A. 完全消除 Value，所有路径直接操作 `Py<PyAny>` | pydantic 做法 | Rust 原生路径无 Python 对象，不可行；construct parse 产出是全新数据，需某种中间表示 |
| B. Value 仅作 Rust 内部中间表示，Python 路径不经它 | 双轨 | 兼顾两条用户路径；Python 路径 direct-to-Python |
| C. Value 仍是强制中转（旧架构） | parse→Value→Python；Python→Value→build | 缺陷 §3.2，性能最大杀手 |

**选择：B（Value 作为 Rust 内部中间表示，退出 Python 性能关键路径）**

**理由**：
1. **领域约束 0.4**：construct parse 从字节流产出全新数据，必须有中间表示。但这个表示
   **不必**先完整构建再转 Python——可在 parse 过程中**直接写入**目标 Python 对象
   （`PyDict::set_item`），跳过 Value::Container 临时树。这正是 pydantic TypedDictValidator
   的做法（`typed_dict.rs:155,225`：边验证边 `output_dict.set_item`）。
2. **Rust 原生路径仍需 Value**：纯 Rust 用户没有 Python 对象，parse 产出只能是 Value。
   保留 Value 让两条路径共享同一套二进制解析逻辑（解析字节→理解结构），只在"产出层"分叉。
3. 旧架构缺陷 §3.2 的本质是 Value 出现在 **Python FFI 的进出口**（`value_to_py`/`py_to_value`
   全量递归转换 + `import_bound` 每次查模块）。新架构让 Value 留在 Rust 内部，Python 路径
   的 parse 直接写 `PyDict`，build 直接用 `Input` trait 读 PyObject——Value 不再穿越 FFI。
4. 选项 A 不可行：纯 Rust 路径无 Python 运行时，`Py<PyAny>` 不存在。

**实现方向**：
- 内核构造器的 `parse` 在 Python 路径下，向一个 **output sink** 写入（sink 是 `PyDict` 或
  dataclass 实例），而非返回 Value。
- 纯 Rust 路径下，sink 是一个 Value 收集器（行为等价旧 Value 产出）。
- 通过泛型/trait 让同一套解析逻辑服务两种 sink（具体签名在模块设计阶段定）。

### 3.3 决策 D3：构建模型（build-once vs 即时构建）

**问题**：construct 树何时被"编译"成可执行形式？

| 选项 | 说明 | 评估 |
|------|------|------|
| A. 即时构建（旧架构） | 每次 parse/build 都遍历声明树，运行时重复解析配置 | 缺陷 §3.6；无法缓存优化 |
| B. Build-once（pydantic 用法） | schema 定义时一次性编译为执行树，运行时零构建开销 | 缓存字段路径、预编译表达式、分离构建/运行时 |

**选择：B（build-once）**

**理由**：
1. pydantic-core 在 `SchemaValidator::new()`（`mod.rs:147`）一次性调用
   `build_validator` 编译整棵树，运行时 `validate_python` 只遍历已编译的
   `Arc<CombinedValidator>`。这是其高性能的基石。
2. construct 的表达式系统（`this.field`、`this._.count + 1`）在旧架构中每次求值都要
   穿越 FFI（缺陷 §3.8）。build-once 时可将**常见模式**（单层/多层路径访问、常量算术）
   预编译为 Rust 原生闭包，运行时零 FFI。只有无法静态分析的复杂表达式才退化为 PyCallback。
3. 分离 `BuildConstruct`（构建 trait，schema→执行树）和运行时遍历，使同一 schema 可
   产出不同优化级别的执行器（类比 pydantic 的 strict/lax 模式）。
4. 缓存 `CompiledSchema` 后，同一 schema 反复 parse/build 零构建开销——这对解析大量
   同结构数据（如 Array of Struct）收益巨大。

**实现方向**：
- `SchemaCompiler`（FFI 边界 #1）遍历 Python 声明树，调用各构造器的 `build` 方法生成
  `CompiledNode`。
- `CompiledSchema` 持有 `tree: CompiledNode`（enum_dispatch），缓存于 schema 对象。
- 运行时 `parse_bytes`/`build_from` 只遍历 `CompiledNode` 树。

### 3.4 决策 D4：Context 设计

**问题**：表达式系统需要访问运行时上下文（`this.field`）。Context 如何表示并传给
Python 回调？

| 选项 | 说明 | 评估 |
|------|------|------|
| A. Rust Context → 每次全量转 Python Container（旧架构） | `context_to_py_container` 递归遍历 parent 链 | 缺陷 §3.4：O(深度) 全量转换 + `_root`/`_params` 注入，每次表达式求值都重建 |
| B. 惰性 Python 视图（lazy mapping） | Rust Context 包装成 Python Mapping，访问 `ctx["field"]` 时才转换单字段 | 按需转换，仅转访问到的字段；`_`/`_root`/`_params` 也是惰性视图 |
| C. 完全 Rust 内求值（无 Python Context） | 所有表达式编译为 Rust 闭包 | 最优但只覆盖可静态分析的表达式；复杂表达式（含任意 Python 调用）做不到 |

**选择：B（惰性视图）为主，C（Rust 内求值）为常见模式加速**

**理由**：
1. 旧架构 `context_to_py_container`（`conversions.rs:234-289`）是缺陷 §3.4 的直接来源：
   每次 `PyClosure::evaluate` 都递归遍历整条 parent 链构建 Python Container，并注入
   `_root`/`_params`（额外两次递归转换）。对于 100 元素 Array + `this.length` 表达式，
   就是 100 次完整 Context 重建。
2. pydantic 的 `FunctionBeforeValidator`（`function.rs:104-114`）只传 `ValidationInfo`
   引用（持有 context 的 `&Bound`），零转换。但 construct 的 context 更复杂（parent 链、
   `obj_`、任意 Python 表达式），不能直接传引用——需要惰性视图。
3. **双保险**：build-once 阶段已将 `this.field` 这类**可静态分析**的表达式编译为 Rust
   闭包（决策 C），运行时根本不进 Python。只有复杂表达式（含 lambda、动态属性）才退化为
   PyCallback，此时用惰性 Context 视图（B）按需转换单字段。两者叠加，绝大多数表达式零 FFI。
4. 惰性视图正确性更可靠：`_root`/`_params` 用视图而非递归构建，避免旧架构脆弱的近似注入
   （缺陷 §3.4 提到的正确性风险）。

**实现方向**：
- `PyContextView`：实现 Python `Mapping`/`Sequence` 协议的 Rust 支持对象，持有 `&Context`
  引用。`__getitem__` 时按需 `value_to_py` 单字段。
- Rust 闭包求值器：编译阶段为 `this.a.b` 生成 `move |ctx| ctx.get_path(&["a","b"])`，
  零 Python 参与。

### 3.5 决策 D5：Stream 抽象

**问题**：字节流是否还需要 trait 抽象？

| 选项 | 说明 | 评估 |
|------|------|------|
| A. 保留 Stream trait + `&mut dyn Stream`（旧架构） | 虚函数分发 | 缺陷 §3.7：轻微开销 + 三层抽象（Stream/ByteStream/PyStream）维护成本 |
| B. 简化为 `&mut [u8]` + position | 零开销内存操作 | 纯字节最快，但 Pointer/Seek/Tell 需 seek 能力，纯 slice 不够 |
| C. 保留 Stream 概念但用 enum_dispatch 替代 trait object | 零开销分发 + 保留 seek/tell | 兼顾性能与领域需求 |

**选择：C（保留 Stream 概念，enum_dispatch 替代 trait object）**

**理由**：
1. **领域约束 0.4 之二**：construct 必须支持 seek/tell（Pointer/Anchor/Seek/Tell 构造器），
   pydantic 无此需求故无 Stream。不能照搬 pydantic "无流"的做法。
2. Stream 本身**不是性能瓶颈**（缺陷 §3.7 评估为"轻微开销"），主开销在 Value 转换。但
   `&mut dyn Stream` 的虚分发仍可优化。
3. 选项 B 对纯内存场景最快，但 construct 需支持 Python 流对象（`io.BytesIO`、网络流），
   纯 slice 无法覆盖。保留 Stream 抽象统一处理多源。
4. 用 `enum_dispatch`（`ByteStream` / `PyStream` / `BitStream` 等 variant）替代
   `&mut dyn Stream`，消除虚分发开销，同时保留多态能力。

**实现方向**：`CombinedStream` enum（ByteStream/PyStream/BitStream…），`Stream` trait 用
`#[enum_dispatch]` 生成 match 分发。纯内存路径走 `ByteStream`（Cursor 包装），可被内联。

### 3.6 决策 D6：FFI 边界粒度

**问题**：FFI 在树的哪一层穿越？

| 选项 | 说明 | 评估 |
|------|------|------|
| A. Per-operation（旧架构） | 顶层 1 次 + 每个 Python 回调节点多次 | 缺陷 §3.1/§3.5：树深则 FFI 线性增长 |
| B. Per-module | 每个模块类型边界穿越 | 仍过多 |
| C. Per-tree（整棵树一次穿越） | 运行时仅顶层进/出 + PyCallback 节点 | pydantic 范式 |

**选择：C（per-tree，整棵树一次穿越）**

**理由**：
1. pydantic `validate_python`（`mod.rs:181-213`）一次进入 Rust，整棵 `CombinedValidator`
   树遍历完毕才返回。树内**无 FFI**（除显式 FunctionValidator 回调）。
2. 旧架构 `PyConstructAdapter`（`py_adapter.rs:195-259`）每次至少 5 次 FFI 穿越
   （GIL/BytesIO 创建/parse_stream/tell/py_to_value），树越深越糟。
3. construct 的特殊性：用户自定义 Adapter/Validator 是 Python 对象，无法在 Rust 内执行。
   这些节点封装为 **PyCallback**（持有 `Py<PyAny>` 引用），是执行树中**唯一**的树内 FFI 点。
   关键区别：PyCallback 是**显式可选**的（仅用户自定义时才有），而非架构固有开销——大多数
   construct 树由内置构造器组成，零 PyCallback，零树内 FFI。
4. 与决策 D3（build-once）协同：编译时识别哪些节点是 PyCallback（无法内联的 Python 回调），
   哪些可编译为 Rust 原生节点。

**实现方向**：
- 编译阶段：内置构造器 → `CompiledNode::Native(...)`；Python 回调 → `CompiledNode::PyCallback(...)`。
- 运行时遍历遇到 `PyCallback` 才穿越 FFI（用惰性 Context 视图传参）。
- 表达式同理：`this.field` → Rust 闭包（Native）；`lambda ctx: ...` → PyCallback。

### 3.7 决策 D7：表达式系统——保留 Rust 原生树，enum_dispatch 优化

**问题**：construct 表达式系统（`this.field + 1`、`abs_(this.delta)`、`lambda ctx: ...`）如何重构？
旧架构手写 `Box<dyn Evaluate>` 树 + 每节点虚分发，且 Python 表达式每次 FFI。

**选择：保留 expr.rs 手写表达式树 + enum_dispatch 优化分发**

**理由**：
1. **现有 expr.rs 功能完整**：已覆盖 construct 全部表达式类型（Path/BinExpr/UniExpr/FuncPath/Index），支持所有整数宽度（i8-i128, u8-u128）、浮点、布尔、字符串、字节、Container。无需引入外部依赖。
2. **exmex 评估结论：不引入**。exmex 的 `Val<I,F>` 类型系统存在硬性壁垒（u64 无 `Signed` trait、无 String/Bytes/Container variant），引入它反而缩减表达式覆盖范围。采用三方库的目的是**增加**能力而非加限制，exmex 不满足这一前提。
3. **enum_dispatch 零开销分发**：将 `Box<dyn Evaluate>` 改为 `enum_dispatch`（与 D1 一致），消除虚函数表开销，保持语义不变。
4. **与 D3（build-once）协同**：表达式在 SchemaCompiler 阶段编译为 `CompiledExpr`（enum_dispatch 枚举），缓存于 `CompiledNode`。运行时零分配求值。
5. **PyCallback 边界**：仅用户传入的任意 Python callable（lambda 等）走 PyCallback，其余全在 Rust。

**实现方向**：

```
CompiledExpr（enum_dispatch）
  ├── Native — Rust 表达式树（Path / BinOp / UniOp / Call / Index）
  │     零 FFI；支持全部 Value 类型
  │     enum_dispatch 替代 Box<dyn Evaluate>，零虚分发
  └── PyCallback — 用户自定义 Python callable
        唯一的 FFI 点；惰性 PyContextView 传参
```

> **与 D4（Context）的关系**：D4 的"表达式编译为 Rust 闭包"对应本决策的 Native 路径。PyCallback 仍用 D4 的惰性 `PyContextView`。

## 4. 与 construct 原版的映射表

下表说明 Python construct 的每个核心概念在新架构中的对应。

| Python construct 概念 | 旧架构对应 | 新架构对应 | 说明 |
|----------------------|-----------|-----------|------|
| **`Construct` 类**（声明式 API） | `Construct` trait + PyO3 wrapper | 声明式 API 保留；新增 `SchemaCompiler` 编译为 `CompiledNode` | 用户层 API 不变 |
| **`Container`（产出层）** | `Value::Container` → `value_to_py` → Python Container | Python 路径：parse 直出 `PyDict`/dataclass；Rust 路径：`Value::Container` | Container 退化为内部细节，用户不可见（见分析报告） |
| **`context`（运行时上下文）** | Rust `Context` → 每次全量转 Python Container | Rust `Context` + 惰性 `PyContextView`；常见表达式编译为 Rust 闭包 | 消除全量转换（D4） |
| **`Stream`** | `Stream` trait + `&mut dyn Stream` | `CombinedStream` enum（enum_dispatch） | 保留领域必需能力，消除虚分发（D5） |
| **表达式系统（`this`/`obj_`/`Path`/`BinExpr`）** | Python 对象 + `PyClosure` 桥接，每次 FFI | `this.field` 编译为 Rust 闭包（D3）；复杂表达式退化为 PyCallback + 惰性 Context | 常见模式零 FFI |
| **`Struct`/`Sequence`** | `Box<dyn Construct>` | `CompiledNode::Struct/Sequence`（enum_dispatch） | D1 |
| **`Array`/`GreedyRange`/`RepeatUntil`** | `Box<dyn Construct>` | `CompiledNode::Array`（含元素 schema 引用） | D1；元素 schema 已编译 |
| **`Adapter`/`SymmetricAdapter`/`Validator`** | Rust Adapter 或 `PyConstructAdapter`（Python 子类） | 内置 Adapter → `CompiledNode::Adapter`；用户 Python 子类 → `PyCallback` 节点 | D6：仅用户自定义才 FFI |
| **`Enum`/`Mapping`** | Rust Enum 构造器 | `CompiledNode::Enum`（映射表编译期固化） | 枚举映射表在编译期预计算 |
| **`Switch`/`IfThenElse`/`If`** | Rust 控制流 | `CompiledNode::Switch`（key 函数编译为闭包/PyCallback） | 条件表达式同表达式系统处理 |
| **`Bitwise`** | Rust Bitwise + BitStream | `CompiledNode::Bitwise`（包装 BitStream） | 领域必需，保留 |
| **`Pointer`/`Anchor`/`Tell`/`Seek`** | Rust 流操作 | `CompiledNode::Pointer` 等（操作 `CombinedStream`） | 领域必需，保留（D5） |
| **`Prefixed`/`Restreamed`/`Tunnel`/`RawCopy`** | Rust 隧道构造器 | `CompiledNode::Prefixed` 等 | 保留语义，编译期固化长度前缀 schema |
| **`Lazy`/`LazyStruct`/`LazyArray`/`LazyRange`** | Rust 惰性构造器 | `CompiledNode::Lazy*`（惰性求值节点） | 保留惰性语义 |
| **`Computed`/`Rebuild`/`Default`/`Const`** | Rust meta 构造器 | `CompiledNode::Computed` 等 | Computed 的函数编译为闭包/PyCallback |
| **`parse`/`build`/`sizeof` 用户调用** | `py_parse`/`py_build`（Value 中转） | `CompiledSchema::parse_bytes`/`build_from`（direct-to-Python） | 顶层单次 FFI（D6） |
| **`from_bytes`/`to_bytes`（dataclass-first）** | 不存在 | `ConstructMixin.from_bytes`（调 `parse_bytes` + dataclass 实例化） | **新增**（分析报告方案 2） |

**关键不变量**：construct 的领域语义（声明式、对称、字段间依赖、流操作、惰性）**全部保留**，
改变的是**执行模型**（从混合树即时执行到编译执行树）。

## 5. Python API 设计方向

### 5.1 两套并存的用户 API

| API 风格 | 面向 | 示例 | Container 可见性 |
|---------|------|------|----------------|
| **声明式 API（兼容）** | 现有 construct 用户、低层控制 | `s = Struct("len"/Byte, "data"/Bytes(this.len)); s.parse(data)` | parse 返回 dict/Container（可向后兼容） |
| **dataclass-first API（新增）** | 偏好类型安全、ORM 风格用户 | `@dataclass class A(ConstructMixin): ...; A.from_bytes(data)` | **对用户不可见** |

两套 API **共享同一编译执行树**（同一套 `SchemaCompiler` + `CompiledSchema`），区别仅在
产出目标（dict vs dataclass）。

### 5.2 用户如何定义 construct

**风格 1：声明式（保持不变）**

```python
from construct_rust import Struct, Byte, Bytes, this
s = Struct("len" / Byte, "data" / Bytes(this.len))
# 行为与 Python 原版 construct 完全一致
```

**风格 2：dataclass-first（ConstructMixin）**

```python
from dataclasses import dataclass
from construct_rust import Byte, Bytes, Prefixed, Int16ub, ConstructMixin, cs_field, this

@dataclass
class A(ConstructMixin):
    a: int = cs_field(Byte)
    b: int = cs_field(Byte)

@dataclass
class B(ConstructMixin):
    a: int = cs_field(Byte)
    b: A = cs_field(Prefixed(Int16ub, A))   # 嵌套 dataclass 自动解析

orm = B.from_bytes(data)      # 一步到位，返回 B 实例
binary = orm.to_bytes()       # 一步到位
```

两套风格可混用（声明式 Struct 中引用 ConstructMixin 子类，由 `extract_subcon`
duck-typing 兜底，见分析报告 §5.4）。

### 5.3 parse/build 的用户调用方式

| 操作 | 声明式 API | dataclass-first API |
|------|-----------|--------------------|
| parse 字节 | `s.parse(data)` → dict | `A.from_bytes(data)` → A 实例 |
| parse 流 | `s.parse_stream(stream)` → dict | `A.from_stream(stream)` → A 实例 |
| build | `s.build(dict_or_obj)` → bytes | `orm.to_bytes()` → bytes |
| sizeof | `s.sizeof(**kw)` → int | `A.sizeof(**kw)` → int |

**实现**：dataclass-first 的 `from_bytes`/`to_bytes` 内部调用 `CompiledSchema` 的
parse/build，只是把产出目标设为 dataclass 实例（parse 时 `target_cls` 传入，
direct-to-dataclass）。

### 5.4 Container 在用户 API 中的可见性

| 场景 | Container 是否暴露 |
|------|------------------|
| 声明式 API `s.parse(data)` | **可向后兼容地返回 dict/Container**（但内部已无 Value 中转） |
| dataclass-first `A.from_bytes(data)` | **完全不暴露**（Container 是 `from_bytes` 内部局部变量，或根本不构建） |
| 错误路径 | 错误信息可能含字段路径，但不暴露 Container 对象 |

**结论**：Container 在新架构中退化为"声明式 API 的可选产出格式"。dataclass-first 路径
彻底隐藏它（分析报告 §5.9 的最终结论）。

### 5.5 与 ConstructMixin 分析报告结论的衔接

分析报告（`docs/analysis/Container必要性与dataclass集成分析.md`）推荐**方案 2（纯 Python
ConstructMixin）作为 MVP**，理由是零 Rust 改动。但本顶层设计引入 build-once 架构后，
ConstructMixin 的实现可与编译执行树协同：

- **MVP 阶段**：ConstructMixin 仍可纯 Python 实现（`from_bytes` 调 `parse` 得 dict 再
  `cls(**dict)`），不阻塞架构重构。
- **优化阶段**：`CompiledSchema::parse_bytes` 支持 `target=dataclass`，直接实例化 dataclass，
  省去 dict 中转（分析报告方案 D，性能最优）。

两者不冲突——ConstructMixin 是**用户 API 层**，编译执行树是**执行层**，可独立演进。

| 模块 | 复用程度 | 说明 |
|------|---------|------|
| `construct-rs/src/constructs/*`（~100 构造器实现） | **高复用** | 二进制 parse/build 逻辑不变，只需从 `Box<dyn Construct>` 迁移到 `enum_dispatch` |
| `construct-rs/src/core/stream.rs` | **高复用** | Stream 语义不变，改 enum_dispatch |
| `construct-rs/src/core/context.rs` | **高复用** | Context 结构不变，新增惰性视图包装 |
| `construct-rs/src/core/error.rs` | **完全复用** | 错误体系不变 |
| `construct-rs/src/value.rs` | **保留** | Value 退化为 Rust 内部表示，仍服务于纯 Rust 路径 |
| `construct-rs/src/expr.rs` | **高复用** | 表达式 AST + 求值语义不变；`Box<dyn Evaluate>` → enum_dispatch（D7）；编译为 `CompiledExpr` 缓存于执行树（D3） |
| `construct-rs/src/binary.rs` | **完全复用** | 二进制工具不变 |
| `construct-py/src/conversions.rs`（788 行） | **大幅重写/废弃** | `value_to_py`/`py_to_value` 的全量转换被 direct-to-Python 取代；保留少量标量转换 |
| `construct-py/src/expr_bridge.rs`（909 行） | **大幅重写** | PyClosure 全量 Context 转换被惰性视图 + Rust 闭包取代 |
| `construct-py/src/py_adapter.rs` | **重写** | PyConstructAdapter 的 BytesIO 全量拷贝被 PyCallback 节点取代 |
| `construct-py/src/api.rs` | **重写** | `py_parse`/`py_build` 改为调用 `CompiledSchema` |

**结论**：Rust 内核（construct-rs）约 80% 可复用（主要是分发机制迁移）；FFI 层
（construct-py）约 70% 需重写（conversions/expr_bridge/py_adapter/api 是性能问题集中地）。

### 6.2 建议的子任务拆分方向（3-5 个大方向）

**方向 A：内核分发机制迁移（construct-rs）**
- 定义 `CombinedConstruct` enum + `#[enum_dispatch]`
- 将 ~100 个构造器从 `Box<dyn Construct>` 迁移到 enum 分发
- 定义 `CombinedStream` enum（Stream 的 enum_dispatch 版）
- 验证纯 Rust 路径性能不退化 + 所有现有测试通过
- *风险低（机械替换）、收益明确（消除虚分发）*

**方向 B：编译执行树模型（construct-rs 新模块）**
- 设计 `CompiledNode` enum + `CompiledSchema`
- 设计 `SchemaCompiler`：声明树 → 编译树
- 表达式编译：`this.field` → Rust 闭包；复杂表达式 → PyCallback
- 字段路径预计算、Enum 映射表固化
- *核心工作，决定整个重构成败*

**方向 C：FFI 执行层重写（construct-py）**
- `CompiledSchema::parse_bytes(py, data, target)` direct-to-Python（PyDict/dataclass）
- `Input` trait：build 方向按需读 PyObject 字段
- 惰性 `PyContextView`（Mapping 协议）
- PyCallback 节点统一封装（取代 PyClosure/PyConstructAdapter 分散逻辑）
- *性能收益最大处，也是改动最集中处*

**方向 D：dataclass-first API（construct-py 纯 Python + Rust 直构）**
- `ConstructMixin` + `cs_field`（纯 Python MVP，见分析报告）
- `CompiledSchema` 支持 `target=dataclass`（Rust 直构，性能优化）
- 嵌套类型自动解析（路径 A + 路径 B）
- 边界情况（前向引用、动态字段、Optional）
- *用户可见价值最大，可独立于 C 渐进*

**方向 E：性能验证与对照**
- 建立重构前/后基准对比（与 Python 原版 + 旧架构）
- 覆盖典型场景：纯内置构造器树、含 Python Adapter、表达式密集、大文件
- 验收标准：几何平均 ≥1.0x（目标 ≥2x）
- *贯穿全程，每个方向完成后回归*

### 6.3 建议的实施顺序

```
方向 A（内核分发迁移，低风险铺底）
   ↓
方向 B（编译执行树，核心）
   ↓
方向 C（FFI 执行层，性能主战场）
   ↓ （可与 D 并行）
方向 D（dataclass-first API，用户价值）
   ↓
方向 E（性能验证，贯穿）
```

方向 A 先行：它不改变语义，只改分发机制，风险最低，为后续提供零开销基础。
方向 B/C 是性能关键路径。方向 D 可在 B/C 完成后或并行（MVP 纯 Python 不依赖 B/C）。

## 8. 验收标准

> **目的**：为每个模块和整个系统定义可度量、可在开发前对照的验收标准，避免"开发完成后才发现
> 设计缺陷导致大批量返工"。每项标准必须可由测试/基准/静态检查自动验证。
>
> **使用方式**：DEV 编码时对照模块级标准；VET 审查时逐条核验；PM 验收时检查系统级标准全部通过。
> 任一标准未达标 → 驳回相应阶段，不得进入下一阶段。

### 8.1 系统级验收标准

系统级标准衡量整个架构重构完成后的整体质量，分四类。

#### 8.1.1 性能验收

| 编号 | 标准 | 度量方法 | 目标值 | 验证手段 |
|------|------|---------|--------|---------|
| S-PERF-1 | Python 调用场景几何平均加速比 | 对 Python 原版 construct 2.10.70 的相对性能 | **≥1.0x**（达标）/ ≥2.0x（目标） | `benches/python_compat_bench.rs`：20+ 典型 schema（Byte/Struct/Array/Bytes(this.len)/Adapter/Switch），各跑 1000 次 parse+build，取几何平均 |
| S-PERF-2 | Rust 原生场景不退化 | 对旧架构（Phase 1-10）的相对性能 | **≥1.0x**（不得退化） | `benches/rust_native_bench.rs`：同一套 schema 在纯 Rust 路径（无 PyO3）的 parse+build |
| S-PERF-3 | FFI 穿越次数 | per-tree 树内 FFI 调用计数 | 纯内置构造器树：**0**；含 1 个 PyCallback：**1** | 插桩计数器（`#[cfg(feature="ffi-instrument")]`），在 PyCallback::call 处递增 |
| S-PERF-4 | Context 转换开销 | 表达式求值时的 Context→Python 转换次数 | 常见模式（`this.field`）：**0**；惰性视图：仅访问字段数 | 同上插桩 |

**基准测试方案**：
- 基准集覆盖 6 类场景：(1) 纯标量 Struct、(2) 含 `this` 长度依赖、(3) 大 Array、(4) 嵌套 Struct 深度 5+、(5) Adapter/Validator、(6) Switch/Prefixed。
- 对比基准三方：(a) Python 原版 construct、(b) 旧架构 construct-rs、(c) 重构后 construct-rs。
- 统计：几何平均（主指标）+ p50/p99（尾部稳定性）。
- 环境：release 构建，`RUSTFLAGS="-C target-cpu=native"`，单线程，预热 100 次后测量 1000 次。

#### 8.1.2 功能验收

| 编号 | 标准 | 目标值 | 验证手段 |
|------|------|--------|---------|
| S-FUNC-1 | construct 原版测试通过率 | **≥85%**（与 Phase 10 一致），力争 ≥90% | 移植 construct 原版 `tests/` 目录的测试用例到 `construct-py/tests/`，统计通过数/总数 |
| S-FUNC-2 | 声明式 API 行为一致性 | parse/build 结果与 Python 原版**逐字段相等** | 黄金用例集（50+ schema × 数据对），`assert parse(py_data) == construct.parse(py_data)` |
| S-FUNC-3 | dataclass-first API 功能完整性 | from_bytes/to_bytes/sizeof 全覆盖，嵌套/可选/前向引用可用 | `construct-py/tests/test_dataclass_api.py` |
| S-FUNC-4 | parse/build 对称性 | `build(parse(data)) == data` 且 `parse(build(obj)) == obj` | 对所有基准 schema 往返测试 |

#### 8.1.3 架构验收

| 编号 | 标准 | 验证方法 |
|------|------|---------|
| S-ARCH-1 | FFI 穿越是 per-tree 而非 per-operation | 静态审查：`grep -r "Python::with_gil\|call_method\|extract" construct-rs/src/` 仅出现在 PyCallback 节点 + 顶层 parse_bytes/build_from 入口；树内无散落 FFI |

| S-ARCH-3 | enum_dispatch 替代 Box&lt;dyn&gt; | `grep -r "Box<dyn Construct>" construct-rs/src/` 返回 0（或仅出现在兼容层注释）；执行树用 `CombinedConstruct` enum |
| S-ARCH-4 | 编译执行树与运行时遍历分离 | `SchemaCompiler`（构建期）与 `CompiledSchema::parse_bytes`（运行期）是不同 trait/模块；构建产物 `CompiledSchema` 可序列化/缓存 |

### 8.2 模块级验收标准

为 §1.2 模块清单中的每个模块定义验收标准。每项标准标注 `[I]接口契约` `[D]依赖` `[T]测试` `[P]性能`。

#### 8.2.1 SchemaCompiler（编译层）

| 维度 | 验收标准 |
|------|---------|
| `[I]` 接口契约 | 输入：Python 声明树（`Py<PyAny>` 根 + 子节点引用）。输出：`CompiledSchema { tree: CompiledNode }`（纯 Rust，无 Python 引用，PyCallback 节点除外）。**不**在编译期执行任何 parse/build。**不**对外暴露声明树的内部结构。 |
| `[I]` 缓存契约 | 同一 schema 对象二次编译返回缓存的 `CompiledSchema`（`O(1)` 命中，零重复编译）。 |
| `[D]` 依赖 | 依赖：声明式 API（输入）、内核构造器的 `BuildConstruct` trait（编译各节点）。被依赖：CompiledSchema（产物）、声明式 API（调用方）。 |
| `[T]` 测试要求 | 单元测试：每个构造器类别有"声明树 → CompiledNode"的编译用例，断言节点类型/参数正确。集成测试：往返编译（声明→编译→序列化→反序列化→与原声明等价）。边界：空 Struct、深度 100 嵌套、循环引用检测（报错不 panic）。 |
| `[P]` 性能基线 | 编译单棵典型 schema（10 字段 Struct）< 100µs。缓存命中 < 1µs。编译开销摊销到 N 次 parse 后，N ≥ 10 时编译开销占比 < 5%。 |

#### 8.2.2 CompiledSchema / 执行树（CompiledNode）

| 维度 | 验收标准 |
|------|---------|
| `[I]` 接口契约 | `parse_bytes(&self, py, data: &[u8], target: OutputTarget) -> PyResult<Py<PyAny>>`；`build_from(&self, py, input: &dyn Input, sink: &mut dyn ByteSink) -> PyResult<()>`。`OutputTarget ∈ {PyDict, Dataclass(cls)}`。执行树内部用 `enum_dispatch`（`CombinedConstruct`），无 `Box<dyn>`。 |
| `[I]` 对称性契约 | parse 和 build 遍历**同一棵** CompiledNode 树（不同遍历方向），保证 `build(parse(x)) == x`。 |
| `[D]` 依赖 | 依赖：内核构造器（parse/build 逻辑）、Context（运行时状态）、Stream（字节读写）、PyCallback（树内 FFI）。被依赖：声明式 API、ConstructMixin。 |
| `[T]` 测试要求 | 单元测试：每个 `CompiledNode` variant 的 parse/build 用例（含 `this` 依赖）。集成测试：S-PERF 基准集全部 schema 的往返。边界：空输入、最大 u64、深度溢出检测。 |
| `[P]` 性能基线 | parse 10 字段 Struct（纯内置）: 单次 < 1µs（不含 FFI 进出）。树内无 FFI（S-ARCH-1）。 |

#### 8.2.3 内核构造器（迁移后的 constructs/*）

| 维度 | 验收标准 |
|------|---------|
| `[I]` 接口契约 | 每个构造器实现 `BuildConstruct`（编译期：声明参数 → CompiledNode）+ 运行时 parse/build 方法。**不再**实现 `Construct` trait 的 `parse_stream`/`build_stream`（旧接口废弃）。新增 variant 到 `CombinedConstruct` enum。 |
| `[I]` 迁移完整性 | 旧架构的 ~100 个构造器**全部**迁移，行为等价。迁移清单核对（PM 在总纲中维护）。 |
| `[D]` 依赖 | 依赖：Context、Stream、binary.rs、error.rs。被依赖：SchemaCompiler、CompiledSchema。 |
| `[T]` 测试要求 | 保留并迁移 Phase 1-9 的全部现有单元测试（每个构造器的 parse/build/sizeof），全部 PASS。新增：每个构造器的 CompiledNode 版本对照测试（旧 trait object 结果 == 新 enum_dispatch 结果）。 |
| `[P]` 性能基线 | 单构造器 parse/build 不劣于旧 `Box<dyn>` 版本（enum_dispatch 应更快或持平）。`cargo bench` 对比新旧，回归 < 5% 即通过。 |

#### 8.2.4 Context（惰性视图）

| 维度 | 验收标准 |
|------|---------|
| `[I]` 接口契约 | Rust 端：`Context` 保留现有 `get`/`get_path`/`insert`/`subcontext`（高复用）。Python 端：新增 `PyContextView`（实现 `Mapping` 协议），`__getitem__` 按需 `value_to_py` 单字段，**不**递归构建整个 Container。`_`/`_root`/`_params` 为惰性子视图。 |
| `[I]` 不可变性契约 | Context 在单次 parse/build 内是只读追加的（字段按序插入，不修改已插入字段）。PyContextView 持有 `&Context` 引用，生命周期不超出单次求值。 |
| `[D]` 依赖 | 依赖：Value（字段值表示）。被依赖：表达式编译系统、内核构造器、PyCallback。 |
| `[T]` 测试要求 | 单元测试：PyContextView 的 `__getitem__`/`__len__`/`__contains__`/`keys()`/`values()`。惰性验证：访问单字段不触发其他字段转换（插桩计数）。parent 链：`ctx["_"]["field"]` 正确向上查找。`_root`/`_params` 注入正确。 |
| `[P]` 性能基线 | PyContextView 单字段读取 < 500ns。对比旧架构 `context_to_py_container`（全量递归），100 字段 Context 访问 1 字段：新 < 1µs vs 旧 ~50µs。 |

#### 8.2.5 Stream（CombinedStream）

| 维度 | 验收标准 |
|------|---------|
| `[I]` 接口契约 | `CombinedStream` enum（ByteStream/PyStream/BitStream…），`#[enum_dispatch]` 生成 `Stream` trait。保留 `read_bytes`/`write_bytes`/`seek`/`tell`/`read_bits` 等。**领域必需**：seek/tell 不可省略（Pointer/Anchor 依赖）。 |
| `[D]` 依赖 | 依赖：error.rs。被依赖：内核构造器、CompiledSchema。 |
| `[T]` 测试要求 | 保留 Phase 1 的 Stream 测试。新增：ByteStream vs PyStream 行为等价（同一字节序列，两种流产生相同 parse 结果）。BitStream 位级读写对齐。seek 越界报错不 panic。 |
| `[P]` 性能基线 | ByteStream read_bytes(1) < 10ns（Cursor 包装，可内联）。PyStream（io.BytesIO）含 1 次 FFI，按需触发。 |

#### 8.2.6 表达式编译系统

| 维度 | 验收标准 |
|------|---------|
| `[I]` 接口契约 | 编译期：`compile_expr(ast: &ExprAst, ctx_schema) -> CompiledExpr`，返回 `Native(ExprTree)` 或 `PyCallback(Py<PyAny>)`。运行时：`CompiledExpr::eval(&Context, Option<&Value>) -> Result<Value>`。 |
| `[I]` 类型完整性 | Native 路径支持全部 Value 类型（i8-i128, u8-u128, f64, bool, String, Bytes, Container, ListContainer）。无类型截断风险。 |
| `[D]` 依赖 | 依赖：Context（路径求值）、PyO3（PyCallback 路径）。被依赖：SchemaCompiler、内核构造器（长度/条件表达式）。 |
| `[T]` 测试要求 | 单元测试：(1) 每种 BinOp/UniOp/Call/Index 的求值正确性；(2) 路径访问（`this.a.b`、parent 链 `this._._.field`、`obj_`）；(3) 类型边界（u64 高位、除零、类型不匹配）；(4) enum_dispatch 分发正确性。集成测试：所有 construct 原版 `this`/`obj_`/`len_`/`sum_`/`abs_` 表达式用例。 |
| `[P]` 性能基线 | Native 路径求值（5 运算符表达式）：< 200ns（enum_dispatch 零虚分发）。PyCallback：与旧架构持平。编译期 `compile_expr`：< 5µs/表达式。 |

#### 8.2.7 PyCallback 节点

| 维度 | 验收标准 |
|------|---------|
| `[I]` 接口契约 | `CompiledNode::PyCallback { callable: Py<PyAny>, kind: CallbackKind }`，是执行树中**唯一**的树内 FFI 点。`CallbackKind ∈ {Expr, Adapter, Validator, Predicate}`。调用时传入惰性 `PyContextView`（非全量 Container）。 |
| `[I]` 最小化契约 | PyCallback 仅在**用户显式提供 Python callable** 时出现（用户自定义 Adapter/Validator/lambda 表达式）。内置构造器树**零** PyCallback。 |
| `[D]` 依赖 | 依赖：PyO3、PyContextView、Context。被依赖：CompiledSchema（树内节点）。 |
| `[T]` 测试要求 | 单元测试：4 种 CallbackKind 各一例。FFI 计数：含 1 个 PyCallback 的树，单次 parse 树内 FFI == 1（S-ARCH-1）。惰性 Context 验证：回调内访问 `ctx["a"]` 仅转换 a 字段。GIL 安全：多线程场景不死锁。 |
| `[P]` 性能基线 | 单次 PyCallback 调用（含惰性 Context 传参）：< 10µs。对比旧架构 PyConstructAdapter（每次 5+ FFI + BytesIO 拷贝），单节点开销降 50%+。 |

#### 8.2.8 ConstructMixin（dataclass-first API）

| 维度 | 验收标准 |
|------|---------|
| `[I]` 接口契约 | `ConstructMixin` 提供：`from_bytes(cls, data) -> cls`、`from_stream(cls, stream) -> cls`、`to_bytes(self) -> bytes`、`sizeof(**kw) -> int`、`cs_field(subcon)` 字段声明。Container 对用户**完全不可见**（parse 直出 dataclass 实例）。 |
| `[I]` 嵌套契约 | dataclass 字段类型为另一 ConstructMixin 子类时，自动递归解析（`extract_subcon` duck-typing）。支持 Optional/前向引用（字符串注解）。 |
| `[I]` 与声明式 API 互操作 | ConstructMixin 子类可作为声明式 Struct 的子构造器（`Struct("inner"/MyMixinClass)`），反之亦然。 |
| `[D]` 依赖 | 依赖：CompiledSchema（parse_bytes target=Dataclass）、声明式 API（cs_field 复用构造器）。被依赖：用户 dataclass。 |
| `[T]` 测试要求 | 单元测试：(1) 扁平 dataclass；(2) 嵌套 dataclass（3 层）；(3) Optional 字段；(4) 前向引用（字符串注解）；(5) 与声明式 Struct 互操作；(6) 往返 `to_bytes(from_bytes(x)) == x`。边界：空 dataclass、全 Optional、循环引用报错。 |
| `[P]` 性能基线 | `from_bytes` 直构 dataclass（无 dict 中转）比"parse 得 dict 再 `cls(**dict)`"快 ≥30%。 |

#### 8.2.9 声明式 API（兼容层）

| 维度 | 验收标准 |
|------|---------|
| `[I]` 接口契约 | 用户 API 表面**不变**：`Struct("len"/Byte, "data"/Bytes(this.len))`、运算符重载（`/`/`+`）、`this`/`obj_` 全局对象。内部改造：首次 parse/build 时触发 SchemaCompiler，后续复用缓存。 |
| `[I]` 产出契约 | `s.parse(data)` 返回 dict/Container（向后兼容）。`s.build(obj)` 接受 dict 或 dataclass（duck-typing）。 |
| `[I]` 兼容性 | construct 原版用户代码**零修改**即可运行（除已知不兼容项）。S-FUNC-1 ≥85% 通过率。 |
| `[D]` 依赖 | 依赖：SchemaCompiler、CompiledSchema、ConstructMixin（互操作）。被依赖：用户代码。 |
| `[T]` 测试要求 | S-FUNC-1（原版测试通过率）。黄金用例集（S-FUNC-2）。运算符重载组合（`"a"/Byte + "b"/Byte`）。错误信息格式与原版一致（字段路径）。 |
| `[P]` 性能基线 | 满足 S-PERF-1（几何平均 ≥1.0x）。缓存命中后 parse 无编译开销。 |

### 8.3 验收流程

```
模块开发完成（DEV 自检通过）
    │
    ▼
模块级标准核验（VET 逐条对照 §8.2）
    │ 任一 [I] 契约不符 → 驳回 CODING
    │ 任一 [T] 测试缺失 → 驳回 CODING
    │ [P] 基线未达标 → 标注，PM 决定是否进入下一阶段
    │
    ▼ 全部模块级标准通过
系统集成（所有模块联调）
    │
    ▼
系统级标准核验（PM + VET 对照 §8.1）
    │ S-ARCH-* 静态审查不通过 → 驳回相应模块
    │ S-FUNC-* 功能不达标 → 驳回 CODING
    │ S-PERF-* 性能不达标 → 标注瓶颈模块，PM 决定优化或接受
    │ S-QUAL-* 代码质量 → 必须全绿
    │
    ▼ 全部系统级标准通过
阶段验收（PM 打 tag phase-11-complete）
```

**关键原则**：验收标准在**编码前**定义（本文档），DEV 对照编码，VET 对照审查。**禁止**开发完成后再补标准。每个 `[I]` 契约都应有对应的测试用例验证。
