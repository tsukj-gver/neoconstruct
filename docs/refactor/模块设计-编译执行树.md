## 1. 概述与目标

### 1.1 为什么要编译执行树

Phase 11 完成了分发机制迁移（`Box<dyn Construct>` → `CombinedConstruct`），消除了虚函数表开销。
但当前的 `CombinedConstruct` 仍然是**声明树**——每次 `parse`/`build` 都要从头遍历，运行时重复解析：

| 开销来源 | 当前（声明树） | 编译后（执行树） |
|---------|--------------|----------------|
| 字段名查找 | `IndexMap<String, Value>` 字符串哈希查找 | 编译期字段索引（`usize`） |
| 表达式求值 | `CombinedExpr` 树每次构建求值上下文 | 预编译为 `CompiledExpr`，缓存求值闭包 |
| Enum 映射 | `Vec<(Value, Value)>` 线性扫描 | 编译期固化为 `HashMap` |
| sizeof | 每次递归遍历子树 | 编译期常量折叠（定长构造器） |
| Adapter decode/encode 闭包 | 每次从 `Box<dyn Fn>` 取用 | 闭包迁移为 `Arc<dyn Fn + Send + Sync>`，编译期 `Arc::clone`（见 §5.4） |

**核心范式**：`声明树（schema 定义时） →[一次性编译]→ 执行树（运行时反复遍历）`。
这与 pydantic-core 的 `build_validator`（`validators/mod.rs:520`）范式一致：schema 定义时编译为
`Arc<CombinedValidator>`，运行时 `validate_python` 只遍历已编译树。

### 1.2 Phase 12 范围（明确边界）

| 在范围内 | 不在范围（Phase 13+） |
|---------|---------------------|
| `CompiledNode` enum 定义（全 variant） | Python direct-to-Python（PyDict sink） |
| `CompiledSchema` 顶层容器 | `PyContextView` 惰性视图 |
| `SchemaCompiler` 编译层（Rust 输入） | `PyCallback` variant 定义 + 运行时 FFI 调用 |
| `BuildConstruct` trait | dataclass-first API（ConstructMixin） |
| 表达式编译（`CombinedExpr` → `CompiledExpr`） | 性能基准（Phase 14） |
| `OutputSink` trait 设计 + `ValueSink` 实现 | `PyDictSink` 实现 |
| 纯 Rust 路径 parse/build（返回/接受 `Value`） | Python 路径 parse/build |
| 编译产物缓存机制 | Input trait（build 方向惰性读 PyObject） |

> **B1 边界澄清**：Phase 12 **完全不定义** `CompiledNode::PyCallback` variant 和
> `CompiledExpr::PyCallback` variant。遇到 Python callable 来源时，编译为 `CompiledDynamic`
> （保留 `Arc<dyn Construct>`，退化为声明树旧路径执行）。PyCallback 是 Phase 13 的产物，
> 届时由 construct-py crate（持有 pyo3 依赖）扩展。这保证 construct-rs 在 Phase 12
> 不引入 pyo3 依赖，`cargo build` 可通过。

### 1.3 与 Phase 11 的衔接

Phase 11 产出 `CombinedConstruct`（声明树，parse 返回 `Value`）。Phase 12 在其之上构建：

```
声明阶段（不变）                     编译阶段（Phase 12 新增）           运行时（Phase 12 新增）
─────────────                      ─────────────────────────         ──────────────────────
Struct::new()                      SchemaCompiler::compile(          compiled.parse_bytes(data)
  .field("len", Byte)        ──►     &combined_construct           ──►  → Value
  .field("data", Bytes(len))       ) -> CompiledSchema                  compiled.build_bytes(value)
                                   内部：遍历 CombinedConstruct,         → bytes
                                         产出 CompiledNode 树
```

**关键不变量**：`CombinedConstruct`（声明树）**保留不动**，旧路径（`CombinedConstruct::parse`）
仍然可用。`CompiledNode`（执行树）是**新路径**，与旧路径并存。

## 2. CompiledNode 设计

### 2.1 与 CombinedConstruct 的关系：选项 B（全新 enum，与声明树平行）

REV 问题 #1 提出三个选项。本设计选择**选项 B**，理由：

| 选项 | 评估 | 结论 |
|------|------|------|
| A. 扩展 CombinedConstruct | CombinedConstruct.parse 返回 `Value`，与"直接产出 sink"目标冲突；编译参数污染声明树 | ✗ 拒绝 |
| **B. 全新 enum，与 CombinedConstruct 平行** | 职责分离（声明树 vs 执行树）；编译参数隔离；可独立演进 | **✓ 采纳** |
| C. CompiledNode 包含 CombinedConstruct variant | 每次执行仍需遍历声明树的 `Box<CombinedConstruct>`，编译收益被吞 | ✗ 拒绝 |

**选项 B 的具体含义**：

```
CombinedConstruct（声明树，Phase 11）      CompiledNode（执行树，Phase 12）
───────────────────────────────────────     ──────────────────────────────────
本质：用户组合出的 schema 定义               本质：编译后的可执行表示
parse 返回：Value（不变）                    parse 返回：Value（Phase 12）/ 写 sink（Phase 13）
字段类型：Box<CombinedConstruct>             字段类型：Box<CompiledNode>
编译参数：无（运行时每次解析）                编译参数：预计算索引/预编译表达式/固化映射表
产生方式：Struct::new().field(...)           产生方式：SchemaCompiler::compile(&combined)
```

**复用关系**：`CompiledNode` 的叶子构造器 variant **直接内嵌** `CombinedConstruct` 的具体类型
（如 `FormatField`、`VarInt`），复用其二进制 parse/build 逻辑，**零重复实现**。复合构造器
（`Struct`、`Adapter` 等）则是新类型，持有编译后的子节点（`Box<CompiledNode>`）和编译参数。

### 2.2 CompiledNode enum 定义

定义在新模块 `construct-rs/src/compiled.rs`。使用 `#[enum_dispatch]` 与 Phase 11 一致，
实现一个 `CompiledExec` trait（执行树运行时 trait）。

```rust
//! Compiled execution tree — build-once representation of a construct schema.
//!
//! [`CompiledNode`] is the runtime representation of a compiled schema. It is
//! produced once by [`SchemaCompiler`](crate::compiler::SchemaCompiler) and
//! traversed on every `parse`/`build` call with zero per-call construction
//! overhead.

use crate::combined::CombinedConstruct;
use crate::constructs::*;
use crate::core::context::Context;
use crate::core::error::Result;
use crate::core::stream::CombinedStream;
use crate::expr::CompiledExpr;
use crate::value::Value;

/// Runtime trait for compiled execution-tree nodes.
///
/// Each variant of [`CompiledNode`] implements this trait. Unlike the
/// declaration-tree [`Construct`](crate::core::Construct) trait, `CompiledExec`
/// operates on already-compiled nodes — no per-call parameter extraction.
#[enum_dispatch::enum_dispatch]
pub trait CompiledExec {
    /// Parses a [`Value`] from the stream, writing into `sink` and `ctx`.
    fn exec_parse(
        &self,
        stream: &mut CombinedStream,
        ctx: &mut Context,
        sink: &mut dyn OutputSink,
    ) -> Result<()>;

    /// Builds binary data, reading field values from `input`.
    fn exec_build(
        &self,
        input: &Value,
        stream: &mut CombinedStream,
        ctx: &mut Context,
    ) -> Result<()>;

    /// Computes the byte size, with compile-time constant folding where possible.
    fn exec_sizeof(&self, ctx: &Context) -> Result<usize>;
}

/// The compiled execution tree node — runtime representation of a schema.
///
/// Produced by [`SchemaCompiler`](crate::compiler::SchemaCompiler) from a
/// [`CombinedConstruct`] declaration tree. Variant list **mirrors
/// `CombinedConstruct` exactly** (70 built-in + `Dynamic` = 71 variants,
/// 1:1 correspondence). Phase 12 does NOT define a `PyCallback` variant
/// (B1 修正); Python callable sources compile to `Dynamic` (old-path
/// fallback). Phase 13 will extend with `PyCallback` in construct-py.
///
/// See §2.3 for the variant classification and §2.4 for compile-time
/// 固化信息.
#[allow(clippy::large_enum_variant)]
#[enum_dispatch::enum_dispatch(CompiledExec)]
pub enum CompiledNode {
    // ── 叶子构造器（直接内嵌，复用二进制逻辑）──
    FormatField(CompiledFormatField),
    VarInt(CompiledVarInt),
    ZigZag(CompiledZigZag),
    Flag(CompiledFlag),
    Bytes(CompiledBytes),
    GreedyBytes(CompiledGreedyBytes),
    BytesExpr(CompiledBytesExpr),
    BytesInteger(CompiledBytesInteger),
    BitsInteger(CompiledBitsInteger),
    CString(CompiledCString),
    PaddedString(CompiledPaddedString),
    // ── 包装器（包装编译后的子节点）──
    Const(CompiledConst),
    Renamed(CompiledRenamed),
    Subconstruct(CompiledSubconstruct),
    Adapter(CompiledAdapter),
    SymmetricAdapter(CompiledSymmetricAdapter),
    ExprAdapter(CompiledExprAdapter),
    Validator(CompiledValidator),
    ExprValidator(CompiledExprValidator),
    Hex(CompiledHex),
    HexDump(CompiledHexDump),
    // ── 元构造器（编译参数固化）──
    Pass(CompiledPass),
    Terminated(CompiledTerminated),
    Tell(CompiledTell),
    Seek(CompiledSeek),
    SeekExpr(CompiledSeekExpr),
    Error(CompiledError),
    // ── 复合构造器（持有编译后的子节点列表）──
    Struct(CompiledStruct),
    Sequence(CompiledSequence),
    Union(CompiledUnion),
    Select(CompiledSelect),
    FocusedSeq(CompiledFocusedSeq),
    // ── 枚举/计算（映射表固化 + 表达式预编译）──
    Enum(CompiledEnum),
    FlagsEnum(CompiledFlagsEnum),
    Mapping(CompiledMapping),
    Computed(CompiledComputed),
    Rebuild(CompiledRebuild),
    Default(CompiledDefault),
    Index(CompiledIndex),
    Padded(CompiledPadded),
    Aligned(CompiledAligned),
    FixedSized(CompiledFixedSized),
    NamedTuple(CompiledNamedTuple),
    TimestampAdapter(CompiledTimestampAdapter),
    // ── 重复（子节点编译 + count 预编译）──
    Array(CompiledArray),
    ArrayExpr(CompiledArrayExpr),
    GreedyRange(CompiledGreedyRange),
    RepeatUntil(CompiledRepeatUntil),
    // ── 惰性（编译参数固化）──
    Lazy(CompiledLazy),
    LazyStruct(CompiledLazyStruct),
    LazyArray(CompiledLazyArray),
    Rebuffered(CompiledRebuffered),
    // ── 流操作/隧道（子节点编译 + 参数固化）──
    Bitwise(CompiledBitwise),
    Bytewise(CompiledBytewise),
    Pointer(CompiledPointer),
    PointerExpr(CompiledPointerExpr),
    Peek(CompiledPeek),
    RawCopy(CompiledRawCopy),
    Prefixed(CompiledPrefixed),
    Transformed(CompiledTransformed),
    Restreamed(CompiledRestreamed),
    #[cfg(feature = "compression")]
    Compressed(CompiledCompressed),
    Checksum(CompiledChecksum),
    ByteSwapped(CompiledByteSwapped),
    BitsSwapped(CompiledBitsSwapped),
    LazyBound(CompiledLazyBound),
    // ── 控制流（条件表达式预编译）──
    IfThenElse(CompiledIfThenElse),
    Switch(CompiledSwitch),
    Check(CompiledCheck),
    StopIf(CompiledStopIf),
    // ── escape-hatch（无法编译的 Dynamic / Python callable 节点）──
    // 注：Phase 12 不定义 PyCallback variant（B1 修正）。遇到 Python callable
    // 来源时编译为 Dynamic（走旧路径）。Phase 13 再扩展 PyCallback variant。
    Dynamic(CompiledDynamic),
}
```

> **variant 数量**：**71 个**（B3 修正），与 `CombinedConstruct` **完全 1:1 对应**——
> 70 个镜像内置 variant + 1 个 `Dynamic` escape-hatch。其中 `Compressed` 受
> `cfg(feature = "compression")` 门控（开启时 71 / 关闭时 70）。
>
> **B1 修正**：Phase 12 **不定义** `PyCallback` variant。遇到 Python callable 来源
> （用户 Python construct / Python Adapter / Python lambda 表达式）时，SchemaCompiler
> 将其编译为 `CompiledNode::Dynamic`（保留 `Arc<dyn Construct>`，运行时走声明树旧路径）。
> Phase 13 在 construct-py crate 中扩展 `PyCallback` variant + FFI 运行时。

### 2.3 variant 分类与编译模式

70 个镜像 variant 按**编译模式**分为五类（S1 修正：计数口径统一）。每类的编译逻辑和运行时行为不同：
- §2.3.1 叶子（10）+ §2.3.2 表达式参数化叶子（1）+ §2.3.3 包装器（10）+ §2.3.4 复合（5）+ §2.3.5 其余（44，含 Compressed cfg 门控）= 70。
- 加上 `Dynamic` escape-hatch = 71 总 variant（与 CombinedConstruct 1:1 对应）。

#### 2.3.1 叶子构造器（10 个）— 直接内嵌

> **S1 修正**：原称"11 个"有误。BytesExpr 单列于 §2.3.2（表达式参数化），此处 10 个。

| Variant | 内嵌类型 | 编译动作 | 固化信息 |
|---------|---------|---------|---------|
| FormatField | `FormatField` | 直接拷贝 | 字节序、格式串（编译期常量） |
| VarInt | `VarInt` | 直接拷贝 | 无（逻辑固定） |
| ZigZag | `ZigZag` | 直接拷贝 | 无 |
| Flag | `Flag` | 直接拷贝 | truthy/falsy 值 |
| Bytes | `Bytes` | 直接拷贝 | 固定长度 `count` |
| GreedyBytes | `GreedyBytes` | 直接拷贝 | 无 |
| BytesInteger | `BytesInteger` | 直接拷贝 | 字节数、字节序 |
| BitsInteger | `BitsInteger` | 直接拷贝 | 位数、字节序 |
| CString | `CString` | 直接拷贝 | 编码、终止符 |
| PaddedString | `PaddedString` | 直接拷贝 | 长度、编码、padchar |

**设计**：叶子构造器的 `exec_parse`/`exec_build` 直接委托给内嵌的 `CombinedConstruct` 具体类型
（如 `FormatField::parse`）。编译期只需拷贝结构体，无额外固化。`sizeof` 可做常量折叠
（如 `CompiledFormatField` 的 `exec_sizeof` 直接返回 `std::mem::size_of::<T>()`，不递归）。

#### 2.3.2 表达式参数化叶子（1 个）— 表达式预编译

| Variant | 内嵌类型 | 编译动作 | 固化信息 |
|---------|---------|---------|---------|
| BytesExpr | `CompiledBytesExpr` | length_expr → CompiledExpr | 预编译长度表达式 |

**设计**：`CompiledBytesExpr` 持有 `subcon` 逻辑（固定，委托 `Bytes` 的读写）+ `compiled_len: CompiledExpr`
（预编译的长度表达式）。运行时 `exec_parse` 先 `compiled_len.eval(ctx)` 得到长度，再读字节。

#### 2.3.3 包装器（10 个）— 子节点递归编译 + 闭包编译

| Variant | 子节点 | 编译动作 |
|---------|--------|---------|
| Const | `Box<CompiledNode>` | 拷贝 value；subcon 递归编译 |
| Renamed | `Box<CompiledNode>` | 拷贝 name/docs；inner 递归编译；parsed hook 保留 |
| Subconstruct | `Box<CompiledNode>` | subcon 递归编译（透传） |
| Adapter | `Box<CompiledNode>` | decode/encode 闭包保留 `Arc<dyn Fn + Send + Sync>`（B4 修正） |
| SymmetricAdapter | `Box<CompiledNode>` | func 闭包编译 |
| ExprAdapter | `Box<CompiledNode>` | 同 Adapter |
| Validator | `Box<CompiledNode>` | check 闭包编译 |
| ExprValidator | `Box<CompiledNode>` | 同 Validator |
| Hex | `Box<CompiledNode>` | subcon 递归编译 |
| HexDump | `Box<CompiledNode>` | subcon 递归编译 |

**Adapter 闭包编译策略**：Adapter 的 `decode`/`encode` 原为 `Box<dyn Fn(&Value, &Context) -> Result<Value>>`。
B4 修正后迁移为 `Arc<dyn Fn + Send + Sync>`（见 §5.4）。
编译期无法将任意闭包转为 `CompiledExpr`（闭包体不透明）。因此：
- **内置 Adapter**（由表达式系统创建，如 `ExprAdapter`）：闭包体是已知的表达式变换，保留为 `Arc<dyn Fn>`（Phase 12 不尝试编译闭包体为 CompiledExpr）。
- **用户 Rust 闭包 Adapter**：保留 `Arc<dyn Fn + Send + Sync>`，运行时直接调用（零 FFI，纯 Rust 闭包）。
- **用户 Python callable Adapter**（Phase 13）：编译为 `CompiledDynamic` 降级（Phase 12），Phase 13 扩展为 PyCallback。

> Phase 12 范围内，Adapter 闭包保留 `Arc<dyn Fn + Send + Sync>`（不尝试编译为 CompiledExpr，
> 因闭包体不可内省）。这是可接受的——闭包调用是纯 Rust 虚分发（一次），不涉及 FFI。

#### 2.3.4 复合构造器（5 个）— 子节点列表递归编译

| Variant | 子节点形式 | 编译动作 | 固化信息 |
|---------|-----------|---------|---------|
| Struct | `Vec<CompiledField>` | 每个字段递归编译 | 字段名→索引映射（`IndexMap<String, usize>`） |
| Sequence | `Vec<CompiledEntry>` | 每个 entry 递归编译 | 同上 |
| Union | `Vec<CompiledNode>` + 选择逻辑 | 递归编译 | parse_from 索引 |
| Select | `Vec<CompiledNode>` | 递归编译 | 无 |
| FocusedSeq | `Vec<CompiledField>` + focused 索引 | 递归编译 | focused 字段索引 |

**字段路径预计算**（`CompiledStruct` 的核心优化）：
```rust
pub struct CompiledField {
    pub name: Option<String>,
    pub field_index: usize,        // 在容器中的位置索引（编译期预计算）
    pub flagbuildnone: bool,       // 编译期固化，避免运行时虚调用
    pub subcon: Box<CompiledNode>,
}

pub struct CompiledStruct {
    pub fields: Vec<CompiledField>,
}
```
运行时 `exec_parse` 遍历 `fields`，每个字段的 `subcon.exec_parse(...)` 产出值，按 `field_index`
写入 sink。字段名→值查找（Context 的 `get_recursive`）仍用字符串键（与 Python 语义一致，
`this.field` 是按名查找），但 sink 写入可用索引优化（避免重复哈希）。

#### 2.3.5 元构造器/重复/枚举计算/流操作/惰性/控制流（44 个）

> **S1 修正**：原称"43 个"遗漏了元构造器（6 个）且未注明 Compressed cfg 门控。
> 实际分布：元构造器 6（Pass/Terminated/Tell/Seek/SeekExpr/Error）+ 枚举/计算 12 + 重复 4 +
> 惰性 4 + 流操作 14（含 Compressed cfg 门控、LazyBound）+ 控制流 4 = 44。关闭 compression
> feature 时为 43（Compressed variant 不编译）。

按相同模式处理：子节点递归编译，参数（count、映射表、条件、偏移量等）编译期固化。详细签名见
§2.5。`Enum` 的映射表固化为 `HashMap<Value, Value>`（编译期构建，运行时 O(1) 查找）。

### 2.4 编译期固化的信息汇总

| 固化项 | 受益 variant | 运行时收益 |
|--------|-------------|-----------|
| sizeof 常量折叠 | 所有定长叶子（FormatField/VarInt/Flag/Bytes 固定长度） | `exec_sizeof` 返回常量，不递归 |
| 字段索引预计算 | Struct/Sequence/FocusedSeq | sink 写入用索引，减少哈希 |
| 表达式预编译 | BytesExpr/ArrayExpr/SeekExpr/PointerExpr/IfThenElse/Switch/Computed | `CompiledExpr` 缓存，避免每次构建求值树 |
| Enum 映射表固化 | Enum/FlagsEnum/Mapping | `HashMap` O(1) 查找替代 `Vec` 线性扫描 |
| flagbuildnone 固化 | 所有包装器/复合 | 编译期已知，避免运行时虚方法调用 |
| Adapter 闭包保留 | Adapter/Validator 系列 | `Arc<dyn Fn + Send + Sync>` 闭包调用（B4 修正，一次虚分发，无 FFI） |

## 3. CompiledSchema 设计

### 3.1 顶层容器

`CompiledSchema` 是编译产物的顶层容器，持有编译后的 `CompiledNode` 树。它是运行时
parse/build 的入口，与 pydantic-core 的 `SchemaValidator`（`validators/mod.rs:111-124`，
持有 `Arc<CombinedValidator>`）对应。

```rust
//! Top-level container for a compiled construct schema.

use std::sync::Arc;

/// A compiled construct schema — the runtime entry point for parse/build.
///
/// Produced once by [`SchemaCompiler::compile`](crate::compiler::SchemaCompiler::compile)
/// from a [`CombinedConstruct`](crate::combined::CombinedConstruct) declaration tree.
/// The compiled tree is stored behind an `Arc` for cheap cloning and caching.
///
/// # Python correspondence
///
/// This is the construct equivalent of pydantic-core's `SchemaValidator`
/// (`validators/mod.rs:111`), which holds `Arc<CombinedValidator>`.
#[derive(Debug)]
pub struct CompiledSchema {
    /// The compiled execution tree (root node).
    tree: Arc<CompiledNode>,
    /// Optional schema name (for error messages / debugging).
    name: Option<String>,
    /// Compile-time computed static size, if determinable.
    /// `None` if the schema has variable-length components.
    static_size: Option<usize>,
}

impl CompiledSchema {
    /// Creates a new `CompiledSchema` from a compiled tree node.
    ///
    /// This is called by [`SchemaCompiler`](crate::compiler::SchemaCompiler)
    /// after compilation. Users typically do not call this directly.
    #[must_use]
    pub fn new(tree: CompiledNode) -> Self {
        let static_size = try_fold_static_size(&tree);
        CompiledSchema {
            tree: Arc::new(tree),
            name: None,
            static_size,
        }
    }

    /// Returns the root compiled node.
    #[must_use]
    pub fn tree(&self) -> &CompiledNode {
        &self.tree
    }

    /// Returns the pre-computed static byte size, if known at compile time.
    #[must_use]
    pub fn static_size(&self) -> Option<usize> {
        self.static_size
    }
}
```

### 3.2 运行时方法（纯 Rust 路径）

Phase 12 实现**纯 Rust 路径**的 parse/build——parse 返回 `Value`，build 接受 `Value`。
这些方法镜像 `dyn Construct::parse_bytes`/`build_bytes`（`core/mod.rs:136-169`），但遍历的是
`CompiledNode` 树而非声明树。

```rust
impl CompiledSchema {
    /// Parses binary data and returns the result as a [`Value`].
    ///
    /// **Pure Rust path** (Phase 12): the entire tree is traversed in Rust,
    /// producing a `Value`. No Python objects are involved.
    ///
    /// # Errors
    ///
    /// Propagates any [`ConstructError`](crate::core::error::ConstructError).
    pub fn parse_bytes(&self, data: &[u8]) -> Result<Value> {
        let mut stream = CombinedStream::ByteStream(ByteStream::new_read(data));
        let mut ctx = Context::new();
        let mut sink = ValueSink::new();
        self.tree
            .exec_parse(&mut stream, &mut ctx, &mut sink)
            .map_err(|e| e.with_path_prefix(PARSE_PATH))?;
        Ok(sink.into_value())
    }

    /// Builds binary data from a [`Value`] and returns it as bytes.
    ///
    /// **Pure Rust path** (Phase 12): reads field values from the `Value` tree,
    /// traverses the compiled tree, writes to an in-memory stream.
    ///
    /// # Errors
    ///
    /// Propagates any [`ConstructError`](crate::core::error::ConstructError).
    pub fn build_bytes(&self, data: &Value) -> Result<Vec<u8>> {
        let mut stream = CombinedStream::ByteStream(ByteStream::new_write());
        let mut ctx = Context::new();
        self.tree
            .exec_build(data, &mut stream, &mut ctx)
            .map_err(|e| e.with_path_prefix(BUILD_PATH))?;
        match stream {
            CombinedStream::ByteStream(bs) => Ok(bs.into_bytes()),
            _ => Ok(Vec::new()),
        }
    }

    /// Computes the byte size. Uses compile-time folding where possible.
    ///
    /// # Errors
    ///
    /// Returns [`ConstructError::Sizeof`] if the size is not statically
    /// determinable.
    pub fn sizeof(&self, ctx: &Context) -> Result<usize> {
        // Fast path: if static_size was computed at compile time, return it.
        if let Some(size) = self.static_size {
            return Ok(size);
        }
        self.tree
            .exec_sizeof(ctx)
            .map_err(|e| e.with_path_prefix(SIZEOF_PATH))
    }
}
```

### 3.3 缓存机制

`CompiledSchema` 缓存于 schema 对象（声明式 API 的 PyO3 wrapper 或 Rust 端的
`Box<CombinedConstruct>`）。首次 parse/build 时触发编译，后续复用缓存。

```rust
/// A lazily-compiled schema cache.
///
/// Holds an optional `CompiledSchema` that is compiled on first access.
/// This is used by the declaration-tree API to cache compilation results.
pub struct CompiledCache {
    compiled: std::sync::OnceLock<CompiledSchema>,
}

impl CompiledCache {
    /// Creates a new empty cache.
    #[must_use]
    pub const fn new() -> Self {
        CompiledCache {
            compiled: std::sync::OnceLock::new(),
        }
    }

    /// Returns the compiled schema, compiling it on first access.
    ///
    /// `compiler` provides the declaration tree to compile.
    pub fn get_or_compile(
        &self,
        compiler: &SchemaCompiler,
        schema: &CombinedConstruct,
    ) -> Result<&CompiledSchema> {
        self.compiled.get_or_try_init(|| compiler.compile(schema))
    }
}
```

> `OnceLock` 保证编译只发生一次（线程安全）。缓存命中（第二次起）是 `OnceLock::get`，
> 约等于一次原子读，满足 §8.2.1 缓存契约 `< 1µs`。

### 3.4 静态尺寸折叠

`try_fold_static_size` 在编译期递归计算定长 schema 的总尺寸。若任一节点是变长的
（如 `BytesExpr`、`ArrayExpr`、`GreedyRange`），返回 `None`。

```rust
/// Attempts to compute the static byte size of a compiled tree.
///
/// Returns `Some(size)` if all nodes are fixed-length, `None` otherwise.
/// This enables `CompiledSchema::sizeof` to return a constant without
/// runtime traversal for fully-static schemas.
fn try_fold_static_size(node: &CompiledNode) -> Option<usize> {
    match node {
        CompiledNode::FormatField(f) => Some(f.byte_size()),
        CompiledNode::VarInt(_) => None,      // VarInt is variable-length
        CompiledNode::Flag(_) => Some(1),
        CompiledNode::Bytes(b) => Some(b.count()),
        CompiledNode::BytesExpr(_) => None,   // runtime-dependent length
        CompiledNode::Struct(s) => {
            s.fields.iter()
                .map(|f| try_fold_static_size(&f.subcon))
                .sum()  // short-circuits to None if any field is variable
        }
        CompiledNode::Array(a) => {
            try_fold_static_size(&a.subcon).map(|elem| elem * a.count)
        }
        CompiledNode::Renamed(r) => try_fold_static_size(&r.inner),
        CompiledNode::Adapter(a) => try_fold_static_size(&a.subcon),
        // ... 其他 variant 同理
        _ => None,  // conservative default for complex variants
    }
}
```

## 4. SchemaCompiler 设计（**REV #4 回应**）

### 4.1 REV #4 问题与回答

**REV 质疑**：SchemaCompiler 需要遍历 Python 声明树（PyO3 wrapper 对象），提取每个节点的
类型和参数。但当前 Python 声明树是什么结构？SchemaCompiler 如何"看懂"它们？是否需要在
每个 construct wrapper 上实现 `__cs_compile__` 协议方法？还是 SchemaCompiler 直接 pattern
match PyO3 对象的类型？

**ARCH 回答**：**确认设计需要明确化。采用方案 A（直接遍历 CombinedConstruct 声明树），
不需要 `__cs_compile__` 协议方法，也不需要 pattern match PyO3 对象类型。**

**关键发现**（基于 `construct-py/src/constructs_composite.rs:164-168` 的源码事实）：

每个 PyO3 wrapper（如 `PyStruct`）持有**两个字段**：
```rust
#[pyclass(name = "Struct", unsendable)]
pub struct PyStruct {
    pub(crate) inner: construct::constructs::Struct,   // ← Rust 内核构造器（已含全部参数）
    pub(crate) py_subcons: Vec<PyObject>,              // ← 原始 Python 子节点引用（用于 __getattr__）
}
```

**`inner` 字段就是完整的 `CombinedConstruct` 声明树**（Phase 11 后）。PyO3 wrapper 在创建时
（`py_struct` 工厂函数，`constructs_composite.rs:213-238`）已经把 Python 参数转换为 Rust
构造器，存入 `inner`。`py_subcons` 只是用于 `__getattr__` 成员访问的 PyObject 引用副本。

因此 SchemaCompiler **不需要重新从 Python 对象提取参数**——Rust 内核构造器（`inner`）已经
包含了一切。SchemaCompiler 的输入是 `&CombinedConstruct`（声明树），通过 `match` 遍历它的
variant，对每个节点提取编译参数，产出 `CompiledNode`。

**对比 pydantic-core 的内省方式**：

| 维度 | pydantic-core | construct-rs（本设计） |
|------|--------------|----------------------|
| schema 表示 | Python dict（`{"type": "typed_dict", ...}`） | Rust 构造器对象树（`CombinedConstruct`） |
| 内省方式 | `dict.get_as("type")` 读字符串 → match | 直接 `match` CombinedConstruct variant |
| `__cs_compile__` 协议？ | 无（pydantic 用 `EXPECTED_TYPE` 常量 + `build` 方法） | **无**（直接遍历 Rust enum） |

pydantic 的 schema 是 Python dict（跨 FFI 传递），所以需要 `type` 字符串匹配。construct 的
schema 是 Rust 对象（不跨 FFI），所以直接 enum match，**更高效、类型更安全**。

### 4.2 SchemaCompiler 结构

```rust
//! Schema compiler — converts a declaration tree into a compiled execution tree.

use crate::combined::CombinedConstruct;
use crate::compiled::{CompiledNode, CompiledSchema};
use crate::core::error::{ConstructError, Result};
use crate::expr::CompiledExpr;

/// Compiles a [`CombinedConstruct`] declaration tree into a [`CompiledSchema`].
///
/// This is the construct equivalent of pydantic-core's `build_validator`
/// (`validators/mod.rs:520`). It traverses the declaration tree once,
/// extracting compile-time parameters and producing an optimized
/// [`CompiledNode`] tree.
///
/// # Compilation flow
///
/// 1. Traverse the declaration tree (depth-first).
/// 2. For each node, extract type + parameters via `match` on `CombinedConstruct`.
/// 3. Recursively compile child nodes.
/// 4. Apply compile-time optimizations (expression pre-compilation,
///    field-index pre-computation, enum map construction, sizeof folding).
/// 5. Return the root `CompiledNode`, wrapped in `CompiledSchema`.
pub struct SchemaCompiler {
    /// Recursion depth counter (to detect cycles / stack overflow).
    depth: usize,
    /// Maximum allowed recursion depth (prevents stack overflow on
    /// pathological deeply-nested or self-referential schemas).
    max_depth: usize,
}

/// Default maximum compilation depth. Schemas deeper than this will fail
/// compilation with a clear error.
const DEFAULT_MAX_DEPTH: usize = 256;

impl SchemaCompiler {
    /// Creates a new compiler with default settings.
    #[must_use]
    pub fn new() -> Self {
        SchemaCompiler {
            depth: 0,
            max_depth: DEFAULT_MAX_DEPTH,
        }
    }

    /// Compiles a declaration tree into a [`CompiledSchema`].
    ///
    /// # Errors
    ///
    /// Returns [`ConstructError`] if:
    /// - The declaration tree exceeds the maximum recursion depth.
    /// - A node contains parameters that cannot be compiled (rare; usually
    ///   falls back to `CompiledDynamic`).
    pub fn compile(&self, schema: &CombinedConstruct) -> Result<CompiledSchema> {
        let tree = self.compile_node(schema)?;
        Ok(CompiledSchema::new(tree))
    }

    /// Compiles a single declaration node into a [`CompiledNode`].
    ///
    /// This is the core dispatch — analogous to pydantic's
    /// `build_validator_inner` (`mod.rs:531`). It matches on the
    /// `CombinedConstruct` variant and delegates to the appropriate
    /// `BuildConstruct::compile` implementation.
    fn compile_node(&self, node: &CombinedConstruct) -> Result<CompiledNode> {
        self.depth += 1;
        if self.depth > self.max_depth {
            self.depth -= 1;
            return Err(ConstructError::Generic {
                path: String::new(),
                message: format!(
                    "schema compilation exceeded maximum depth of {} \
                     (possible cycle or extremely deep nesting)",
                    self.max_depth
                ),
            });
        }
        let result = self.compile_node_inner(node);
        self.depth -= 1;
        result
    }

    fn compile_node_inner(&self, node: &CombinedConstruct) -> Result<CompiledNode> {
        // Dispatch via BuildConstruct trait (§5).
        node.compile(self)
    }
}

impl Default for SchemaCompiler {
    fn default() -> Self {
        Self::new()
    }
}
```

### 4.3 Python callable 来源的编译降级（B1 修正）

Phase 12 的纯 Rust 路径**不会遇到 Python callable**。但设计需明确：当 Phase 13 的
construct-py 层将 Python callable 混入声明树时，SchemaCompiler 如何处理。

**Phase 12 策略（统一降级为 CompiledDynamic）**：

| 来源（Phase 13 才出现） | Phase 12 编译产物 | Phase 13 编译产物（前瞻） |
|------|---------|---------|
| 用户 Python construct（`PyConstructAdapter`） | `CompiledNode::Dynamic` | `CompiledNode::PyCallback { kind: Construct }` |
| 用户 Python Adapter（`PyAdapter` wrapper） | `CompiledNode::Dynamic` | `CompiledNode::PyCallback { kind: Adapter }` |
| 用户 Python 表达式（`lambda ctx: ...`） | `CompiledNode::Dynamic`（包裹含 PyClosure 的构造器） | `CompiledExpr::PyCallback` |

**Phase 12 实现**：上述来源在 Phase 12 纯 Rust 路径中**不可达**（无 pyo3 依赖，无 Python
callable）。SchemaCompiler 遇到 `CombinedConstruct::Dynamic` variant 时，统一编译为
`CompiledNode::Dynamic(CompiledDynamic { inner: Arc::clone(&self.inner) })`，运行时走旧路径。

**Phase 13 扩展点**：construct-py crate 在 SchemaCompiler 之上增加一层"Python callable 检测"——
遇到 `Dynamic` 且内部是已知的 PyO3 wrapper 类型时，编译为 `PyCallback` variant 而非 `Dynamic`。
这需要 Phase 13 在 construct-py 中定义 `CompiledNode::PyCallback`（通过 newtype 或 enum 扩展），
不回溯修改 construct-rs。

> 这保证 Phase 12 的纯 Rust 路径可编译、可运行、可测试，不阻塞 Phase 13，也不引入 pyo3 依赖。

## 5. BuildConstruct trait 设计

### 5.1 trait 定义

每个 `CombinedConstruct` 的具体 variant 需要实现 `BuildConstruct`，提供"声明参数 → 编译节点"
的转换。这与 pydantic-core 的 `BuildValidator` trait（`validators/mod.rs:508-518`）对应。

```rust
//! BuildConstruct trait — declaration-to-compiled-node compilation.

use crate::compiler::SchemaCompiler;
use crate::compiled::CompiledNode;
use crate::core::error::Result;

/// Trait implemented by declaration-tree construct types that can be compiled
/// into [`CompiledNode`] execution-tree nodes.
///
/// This is the construct equivalent of pydantic-core's `BuildValidator`
/// (`validators/mod.rs:508`). Each construct type knows how to extract its
/// compile-time parameters and produce an optimized `CompiledNode`.
///
/// # Parameters
///
/// - `compiler` — provides access to recursive compilation of child nodes
///   and the compilation context (depth tracking, etc.).
pub trait BuildConstruct {
    /// Compiles this declaration node into a [`CompiledNode`].
    ///
    /// Implementations should:
    /// 1. Extract compile-time parameters from `&self`.
    /// 2. Recursively compile child nodes via `compiler.compile_node(&child)`.
    /// 3. Apply compile-time optimizations.
    /// 4. Return the resulting `CompiledNode`.
    ///
    /// # Errors
    ///
    /// Returns [`ConstructError`] on compilation failure (e.g., cycle
    /// detection, invalid parameters).
    fn compile(&self, compiler: &SchemaCompiler) -> Result<CompiledNode>;
}
```

### 5.2 在 CombinedConstruct 上的分发

由于 `CombinedConstruct` 是 `#[enum_dispatch]` enum，`BuildConstruct` 同样需要 enum_dispatch
分发。但 `CombinedConstruct` 的 `enum_dispatch` 当前只声明了 `Construct`（`combined.rs:24`）。
需要**新增**一个 `enum_dispatch(BuildConstruct)` 块：

```rust
// In combined.rs (Phase 12 addition):
#[enum_dispatch::enum_dispatch(BuildConstruct)]
impl BuildConstruct for CombinedConstruct {}
```

`enum_dispatch` 宏会为 `CombinedConstruct` 生成 `compile` 方法的 match 分发，将调用转发给
内部具体类型（如 `FormatField::compile`、`Struct::compile`）。**无需手写 match。**

> **I3 修正——Dynamic variant 的特殊处理**：`CombinedConstruct::Dynamic` 的内部类型是
> `Arc<dyn Construct>`（I3 前置改动后），它不是 CombinedConstruct 的"内置具体类型"。
> enum_dispatch 会为 Dynamic variant 调用 `Arc<dyn Construct>::compile(...)`。为此需为
> `Arc<dyn Construct>` 实现 `BuildConstruct`：
>
> ```rust
> impl BuildConstruct for std::sync::Arc<dyn crate::core::Construct> {
>     fn compile(&self, _compiler: &SchemaCompiler) -> Result<CompiledNode> {
>         // 无法递归编译 trait object 内部——降级为 CompiledDynamic（旧路径执行）。
>         Ok(CompiledNode::Dynamic(CompiledDynamic { inner: Arc::clone(self) }))
>     }
> }
> ```
>
> 这样 enum_dispatch 对 Dynamic variant 的分发自然落地，无需手写 match。**前置改动**
> （`CombinedConstruct::Dynamic` 从 `Box` 迁移到 `Arc`）详见 §5.5。
>
> **S2 统一表述**：普通 variant 走 enum_dispatch 自动分发；Dynamic variant 通过
> `Arc<dyn Construct>` 的 BuildConstruct impl 降级。两者统一在 enum_dispatch 框架内，
> 无需手写 match 分支。§4.1 所述"直接 match CombinedConstruct variant"指的是概念模型
> （编译器遍历 variant），实际由 enum_dispatch 宏自动生成。

### 5.3 各类别的 compile 实现模式

#### 5.3.1 叶子构造器（直接拷贝）

```rust
impl BuildConstruct for FormatField {

### 5.4 闭包所有权问题（Adapter/Validator）—— B4 修正

**问题**：`Adapter` 的 `decode`/`encode` 是 `Box<dyn Fn(&Value, &Context) -> Result<Value>>`
（`adapters.rs:45`）。`Box<dyn Fn>` 不可 clone，编译时需要"移动"到 `CompiledAdapter`。
但 `BuildConstruct::compile(&self, ...)` 只有 `&self`（不可移动字段）。

**源码事实（REV 核实）**：当前 4 个闭包类型别名（`adapters.rs:45,53,59,68`）均为
`Box<dyn Fn(...) -> ...>`，**不含 Send + Sync bound**。直接 `Arc::from(Box<dyn Fn>)` 只能得到
`Arc<dyn Fn>`（无 Send + Sync），无法满足线程安全需求。

**修正方案（采纳 REV 方案 a）**：

| 方案 | 描述 | 评估 |
|------|------|------|
| **1. 类型别名改为 `Arc<dyn Fn + Send + Sync>`** | DecodeFunc/EncodeFunc/SymmetricFunc/CheckFunc 全部改为 Arc 形式；Adapter::new 接受 `Box<dyn Fn + Send + Sync>`，内部 `Arc::from` 转换；编译时 `Arc::clone` | **✓ 采纳**：闭包迁移后可 clone；Send + Sync 满足线程安全 |
| 2. `compile` 消费 `self`（`fn compile(self, ...)`） | 编译时移动声明树 | ✗ 拒绝：声明树需保留（旧路径兼容 + 缓存键） |
| 3. `CompiledAdapter` 持有 `&Adapter` 引用 | 生命周期绑定 | ✗ 拒绝：生命周期传染，CompiledSchema 无法 `'static` |

**方案 1 实施细节（B4 修正）**：

```rust
// ── 修改（adapters.rs）——类型别名全部加 Send + Sync，Box → Arc ──
pub type DecodeFunc = Arc<dyn Fn(&Value, &Context) -> Result<Value> + Send + Sync>;
pub type EncodeFunc = Arc<dyn Fn(&Value, &Context) -> Result<Value> + Send + Sync>;
pub type SymmetricFunc = Arc<dyn Fn(&Value, &Context) -> Result<Value> + Send + Sync>;
pub type CheckFunc = Arc<dyn Fn(&Value, &Context) -> Result<()> + Send + Sync>;

// ── Adapter::new 签名调整：接受 Box<dyn Fn + Send + Sync>，内部转 Arc ──
//   注意：参数类型必须是 Box<dyn Fn + Send + Sync>，否则 Arc::from 无法得到
//   Arc<dyn Fn + Send + Sync>（类型不匹配）。
impl Adapter {
    pub fn new(
        subcon: Box<CombinedConstruct>,
        decode: Box<dyn Fn(&Value, &Context) -> Result<Value> + Send + Sync>,
        encode: Box<dyn Fn(&Value, &Context) -> Result<Value> + Send + Sync>,
    ) -> Self {
        Adapter {
            subcon,
            decode: Arc::from(decode),   // Box<dyn Fn+Send+Sync> → Arc<dyn Fn+Send+Sync> ✓
            encode: Arc::from(encode),
        }
    }
}
// SymmetricAdapter::new / Validator::new / ExprValidator::new / ExprAdapter::new 同理。

// ── compile 时：Arc::clone 廉价（原子计数递增）──
impl BuildConstruct for Adapter {
    fn compile(&self, compiler: &SchemaCompiler) -> Result<CompiledNode> {
        let subcon = compiler.compile_node(&self.subcon)?;
        Ok(CompiledNode::Adapter(CompiledAdapter {
            subcon: Box::new(subcon),
            decode: Arc::clone(&self.decode),  // 原子计数递增，廉价
            encode: Arc::clone(&self.encode),
        }))
    }
}
```

> **B4 关键审计点（CODING 阶段子任务 12.6）**：将 `Box<dyn Fn>` 改为
> `Box<dyn Fn + Send + Sync>` 后，所有闭包构造点的捕获值必须满足 `Send + Sync`。
> 需全局搜索 `DecodeFunc`/`EncodeFunc`/`SymmetricFunc`/`CheckFunc` 的使用处：
> - 非捕获闭包（`|v, _ctx| ...`）天然 Send + Sync ✓
> - 捕获 `i64`/`u64`/`&str`/`String`/`Value` 等基本类型的闭包 ✓（这些类型均 Send + Sync）
> - 捕获 `Rc`/`RefCell`/`Cell` 等非线程安全类型的闭包 ✗（需排查，预计无此用法）
>
> **迁移影响范围**：`adapters.rs`（4 个类型别名 + 5 个构造器 new 方法）、
> 所有内部使用 Adapter/Validator 的构造器（如 ExprAdapter、ExprValidator、TimestampAdapter 等）、
> 以及现有测试中的 `Box::new(|...| ...)` 调用点。这些闭包目前均不捕获非 Send/Sync 数据，
> 迁移预期无 break（但需 CODING 阶段逐项验证 + `cargo test` 全 PASS）。
>
> `Arc<dyn Fn>` 比 `Box<dyn Fn>` 多一次原子计数（创建/销毁时），但调用时无差异（都是虚分发）。
> 对 Adapter 而非性能热点而言，这是可接受的。

### 5.5 前置改动：CombinedConstruct::Dynamic 的 Box → Arc 迁移（I3 修正）

**问题**：`CombinedConstruct::Dynamic` 当前持有 `Box<dyn Construct>`（`combined.rs:182`）。
`BuildConstruct::compile(&self)` 只有 `&self`，无法 move 出 `Box`。`Box<dyn Construct>` 不可
clone（`Construct` trait 未要求 `Clone`）。因此编译 Dynamic variant 时无法获得运行时所需的
构造器引用。

**修正方案**：将 `CombinedConstruct::Dynamic` 的内部类型从 `Box<dyn Construct>` 迁移到
`Arc<dyn Construct>`。`Arc` 支持 `Arc::clone`（编译期 `&self` 可 clone），使编译成为可能。

```rust
// ── 修改（combined.rs）──
#[enum_dispatch::enum_dispatch(Construct)]
pub enum CombinedConstruct {
    // ... 70 个内置 variant 不变 ...
    /// Catch-all（I3 修正：Box → Arc，支持编译期 clone）。
    Dynamic(std::sync::Arc<dyn crate::core::Construct>),
}

// dynamic() helper 更新：
pub fn dynamic<C: crate::core::Construct + 'static>(c: C) -> CombinedConstruct {
    CombinedConstruct::Dynamic(std::sync::Arc::new(c))
}

// From<Box<CombinedConstruct>> impl 不受影响（Dynamic 是 enum variant，不是 Box 外壳）。
```

**迁移影响范围**：
- `combined.rs`：Dynamic variant 类型 + `dynamic()` helper。
- 所有构造 `Dynamic` 节点的调用点（`dynamic(c)` / `CombinedConstruct::Dynamic(Box::new(c))`）——
  后者需改为 `Arc::new(c)`。DEV 需全局搜索 `Dynamic(Box` 确保全部迁移。
- `Construct` trait 的 enum_dispatch 实现：`Arc<dyn Construct>` 已自动满足（Arc 解引用到
  `dyn Construct`，enum_dispatch 生成的 match arm 通过 `&*variant` 访问）。
- 现有测试：使用 `Dynamic` 的测试需更新构造方式（`Box::new` → `Arc::new` 或 `dynamic()`）。

**为什么不影响性能**：`Arc` 解引用与 `Box` 解引用开销相同（一次指针解引用）。Arc 多一次
原子计数（clone/drop 时），但 Dynamic variant 本就是 escape-hatch（非热点路径），可忽略。

> **CODING 阶段子任务归属**：此迁移归入 12.4（BuildConstruct + SchemaCompiler），因为它
> 是 BuildConstruct 分发 Dynamic variant 的前提。但实际代码改动在 `combined.rs`，DEV 执行
> 时需先完成此迁移再实现 BuildConstruct。

## 6. 表达式编译系统

### 6.1 编译目标：CombinedExpr → CompiledExpr

Phase 11 产出 `CombinedExpr`（7 variant 的 enum_dispatch enum，`expr.rs`）。Phase 12 在其之上
增加一层**编译优化**：`CombinedExpr`（声明期表达式树）→ `CompiledExpr`（编译后表达式）。

**区别**：
- `CombinedExpr::evaluate(ctx, obj)`：每次调用都遍历表达式树（虽然 enum_dispatch 已消除虚分发）。
- `CompiledExpr`：编译期预处理（如 `Path` 的 segments 转为编译期已知的字符串切片引用），
  运行时 `eval` 更快。更重要的是，`CompiledExpr` 是 `CompiledNode` 的**内嵌字段**，不需要每次
  parse 重新构建。

### 6.2 CompiledExpr 设计

```rust
//! Compiled expression — pre-processed expression for runtime evaluation.

use crate::core::context::Context;
use crate::core::error::Result;
use crate::expr::{CombinedExpr, Evaluate};
use crate::value::Value;

/// A compiled expression that can be evaluated at runtime.
///
/// Produced by [`SchemaCompiler::compile_expr`](crate::compiler::SchemaCompiler::compile_expr)
/// from a [`CombinedExpr`]. In Phase 12, this wraps the existing `CombinedExpr`
/// evaluation with zero overhead (enum_dispatch is already optimal). In
/// Phase 13, complex Python expressions (`PyClosure`) will be handled via
/// `CompiledDynamic` fallback (Phase 12) or a Phase 13 `PyCallback` variant
/// defined in construct-py.
#[derive(Debug, Clone)]
pub enum CompiledExpr {
    /// A native Rust expression tree (Phase 11's CombinedExpr, embedded).
    /// Evaluation delegates to `CombinedExpr::evaluate`.
    Native(CombinedExpr),

    /// A compile-time constant (folded from `ConstExpr`).
    /// Avoids tree traversal for literal expressions.
    Constant(Value),
}

impl CompiledExpr {
    /// Evaluates the compiled expression against a context and optional
    /// build object.
    ///
    /// # Errors
    ///
    /// Returns [`ConstructError`] on evaluation failure.
    pub fn eval(&self, ctx: &Context, obj: Option<&Value>) -> Result<Value> {
        match self {
            CompiledExpr::Native(e) => e.evaluate(ctx, obj),
            CompiledExpr::Constant(v) => Ok(v.clone()),
        }
    }
}
```

> **B1 修正**：原设计的 `CompiledExpr::PyCallback(pyo3::Py<pyo3::types::PyAny>)` variant
> 已移除（construct-rs 无 pyo3 依赖）。Phase 13 在 construct-py crate 中扩展。
>
> **B2 修正——Clone 策略**：`CompiledExpr` 需要 `Clone`（`CompiledSwitch`、`CompiledEnum` 等
> 结构体持有 `CompiledExpr` 字段，可能被 clone）。由于 `CombinedExpr` 在 Phase 12 前置改动中
> 补充了 `#[derive(Clone)]`（见 §6.3），`CompiledExpr` 可安全 derive Clone。`Value` 已是 Clone。

### 6.3 编译流程

```rust
impl SchemaCompiler {
    /// Compiles a declaration expression into a [`CompiledExpr`].
    ///
    /// Applies constant folding where possible.
    pub fn compile_expr(&self, expr: &CombinedExpr) -> Result<CompiledExpr> {
        // Constant folding: if the expression is a ConstExpr, fold to Constant.
        if let CombinedExpr::ConstExpr(c) = expr {
            return Ok(CompiledExpr::Constant(c.value.clone()));
        }

        // Phase 12: all expressions are Native (no Python callables in pure Rust).
        // Phase 13: detect PyClosure inside CombinedExpr → compile to
        //   CompiledDynamic fallback (Phase 12) or PyCallback (Phase 13).

        // B2 修正：clone_ref() 不存在，改用 expr.clone()。
        // 前提：CombinedExpr 及其全部 variant 已补充 #[derive(Clone)]（见 §6.4）。
        Ok(CompiledExpr::Native(expr.clone()))
    }
}
```

**Phase 12 简化说明**：由于纯 Rust 路径无 Python callable，`compile_expr` 主要是：
1. `ConstExpr` → `CompiledExpr::Constant`（常量折叠）
2. 其他 → `CompiledExpr::Native(CombinedExpr)`（包装现有表达式）

收益主要是**避免每次 parse 重新构建表达式树**（CompiledNode 持有编译好的 CompiledExpr 字段）。
表达式求值本身的优化（enum_dispatch）已在 Phase 11 完成。

### 6.4 前置改动：CombinedExpr 及其 variant 补充 Clone（B2 修正）

**源码事实（REV 逐行核实 `expr.rs`）**：

| 类型 | 行号 | 当前 derive | 是否 Clone |
|------|------|------------|-----------|
| `CombinedExpr`（enum） | 1082 | `#[derive(Debug)]` | ✗ **无 Clone** |
| `Path` | 105 | `#[derive(Clone, Debug, PartialEq)]` | ✓ |
| `ConstExpr` | 193 | `#[derive(Clone, Debug, PartialEq)]` | ✓ |
| `PathRoot` | 78 | `#[derive(Clone, Debug, PartialEq)]` | ✓ |
| `BinOp` | 228 | `#[derive(Clone, Copy, Debug, PartialEq, Eq)]` | ✓ |
| `UniOp` | 650 | `#[derive(Clone, Copy, Debug, PartialEq, Eq)]` | ✓ |
| `BinExpr` | 316 | `#[derive(Debug)]` | ✗ **无 Clone** |
| `UniExpr` | 678 | `#[derive(Debug)]` | ✗ **无 Clone** |
| `FuncPath` | 760 | `#[derive(Debug)]` | ✗ **无 Clone** |

**`clone_ref()` 方法在 CombinedExpr 上不存在**（grep 确认）。

**修正方案（采纳 REV 方案 B）**：为上述 6 个缺失 Clone 的类型补充 `#[derive(Clone)]`。

**可行性验证**：逐个检查这 6 个类型的字段：
- `BinExpr { op: BinOp, left: Box<CombinedExpr>, right: Box<CombinedExpr> }` — BinOp ✓Clone，
  Box<CombinedExpr> 在 CombinedExpr derive Clone 后递归可 clone ✓
- `UniExpr { op: UniOp, inner: Box<CombinedExpr> }` — 同理 ✓
- `FuncPath { name: String, inner: Box<CombinedExpr> }` — String ✓Clone ✓
- `CondExpr { cond: Box<CombinedExpr>, then_val: Box<CombinedExpr>, else_val: Box<CombinedExpr> }` — ✓
- `ListPath { index: i64, inner: Option<Box<CombinedExpr>> }` — i64 ✓Clone ✓
- `CombinedExpr` enum — 所有 variant 补 Clone 后，enum 可 derive Clone ✓

**互递归解决**：CombinedExpr 与其 variant 互递归引用（variant 持有 `Box<CombinedExpr>`）。
Rust 的 `#[derive(Clone)]` 能处理互递归——只需所有参与类型同时 derive Clone。因此需在
**同一次改动**中为全部 6 个类型 + CombinedExpr enum 补充 Clone。

**实施**：
```rust

#[derive(Clone, Debug)]              // 原：#[derive(Debug)]

```

> **CODING 阶段子任务归属**：此改动归入 12.3（CompiledExpr + 表达式编译），因为它是
> `compile_expr` 调用 `expr.clone()` 的前提。改动机械（6 处 derive 补充），风险极低。
> 改动后 `cargo test` 现有表达式测试应全 PASS（Clone 是纯增量能力，不影响现有行为）。
>
> **性能影响**：`expr.clone()` 深拷贝整个表达式树。对于典型表达式（3-5 个节点），clone 开销
> 可忽略（编译时一次性，摊销到多次 parse）。若 DEV 发现超大表达式树的 clone 开销显著，
> 可改为 `CompiledExpr::Native(Arc<CombinedExpr>)`（编译时 `Arc::new(expr.clone())`，

## 7. Output Sink 机制（**REV #2 + #5 回应**）

### 7.1 REV #2 问题与回答

**REV 质疑**：D2 说 Python 路径 parse 直出 PyDict，Rust 路径返回 Value。但 Struct 字段的值
可能是嵌套 Struct/Array——递归写 PyDict 时如何避免中间 Value？

**ARCH 回答**：**确认问题存在，但 Phase 12 范围内不出现该问题（纯 Rust 路径）。Phase 13 通过
OutputSink trait + 递归 sink 协议解决。**

**Phase 12（纯 Rust 路径）**：parse 返回 `Value` 树。嵌套 Struct 的内层 parse 也返回 `Value`，
外层将内层 `Value` 插入容器。这与当前 `CombinedConstruct::parse` 行为完全一致——**不引入
中间 Value 中转开销**（因为最终产出就是 Value 树，没有"避免"的余地）。

**Phase 13（Python 路径）的解决方案**：引入 `OutputSink` trait。parse 不返回 Value，而是**直接
写入 sink**。嵌套 Struct 的内层 parse 写入**子 sink**（子 PyDict），外层将子 PyDict 直接插入
父 PyDict——**无中间 Value 树**。这正是 pydantic-core `TypedDictValidator`（`typed_dict.rs:155,225`）
的做法：边验证边 `output_dict.set_item`。

### 7.2 REV #5 问题与回答

**REV 质疑**：复合构造器（如 Struct）在 parse 时需要同时将结果写入 output sink（PyDict 或
Value::Container）和写入 Context（供后续字段的 this.field 引用）。这两个输出是否是同一个对象？
如果不是，如何保持一致？Sink 是泛型/trait 还是 enum？

**ARCH 回答**：

1. **Sink 与 Context 不是同一个对象，但保持数据一致**。Context 是字段查找的来源（表达式求值用），
   Sink 是产出目标（最终返回给用户）。两者需写入相同的数据。在纯 Rust 路径中，解析结果同时写入
   Context（`ctx.insert(name, value)`）和 Sink（`sink.set_field(name, value)`）——两份数据副本，
   但值相同。这是因为 Context 支持递归查找（parent 链），Sink 是平铺容器，结构不同。

2. **Sink 是 trait（非泛型、非 enum）**。理由：
   - **非泛型**：泛型会导致 `CompiledNode` 的每个方法都参数化 sink 类型（`<S: OutputSink>`），
     enum_dispatch 无法在泛型 trait 上工作（macro 限制），且会引发单态化爆炸（每个 sink 类型
     一份完整代码）。
   - **非 enum**：enum 会让 `exec_parse` 内部到处 match sink 类型，污染执行树逻辑。且 Phase 13
     的 `PyDictSink` 需要 `Python<'_>` token，不适合放入 enum 字段（生命周期）。
   - **trait object（`&mut dyn OutputSink`）**：✓ 采用。一次虚分发 per 字段写入，开销可忽略
     （字段写入远少于二进制解析的字节操作）。换取 sink 类型的完全解耦。

### 7.3 OutputSink trait 设计（I1 修正：明确叶子写入协议）

**I1 问题**：叶子构造器（如 FormatField）parse 返回标量 `Value`，但 OutputSink 原设计的方法
（`set_field` 需字段名、`push_item` 面向数组）**不适用于匿名的叶子标量**——叶子在声明树中
不一定有名字，且不应由叶子自己决定写入位置。

**I1 修正方案——统一 sub_sink 协议 + set_scalar**：

协议规则（适用于叶子**和**复合节点，无需类型判断）：

1. **父节点为每个子节点创建 sub_sink**（`sub_sink_for_field(name)` 或 `sub_sink_for_item()`）。
2. **叶子节点**调用 `sub.set_scalar(value)` 写入标量结果。
3. **复合节点**（Struct/Array）递归地对自身字段创建 sub_sink，通过 `set_field`/`push_item`
   写入。最终 sub_sink 的 `into_value` 返回 Container/List。
4. **父节点**调用 `finish_subsink(sub)`，内部执行 `sub.into_value()` 提取子结果并整合
   （写入父 sink 的 set_field/push_item）。

> **Phase 12 开销说明**：每个子节点（含叶子）分配一个 `ValueSink`（小结构体：Option<Value> +
> IndexMap + Vec）。对 100 字段 Struct = 100 次 ValueSink 分配。这是**已知的阶段性开销**
> （I1/I2 接受）。Phase 14 可优化：(a) 叶子快速路径——父节点检测子节点是叶子时直接调用
> `inner.parse` 取 Value，跳过 sub_sink 分配；(b) ValueSink 内存池化。Phase 12 不做此优化。

```rust
//! Output sink abstraction for parse result collection.
//!
//! During `exec_parse`, compiled nodes write their results to an
//! [`OutputSink`] rather than returning a [`Value`]. This abstraction
//! enables:
//!
//! - **Phase 12 (Rust path)**: [`ValueSink`] collects into a [`Value`] tree.
//! - **Phase 13 (Python path)**: `PyDictSink` writes directly to a Python
//!   `dict`, avoiding intermediate `Value` construction.

use crate::core::error::Result;
use crate::value::Value;

/// Trait for collecting parse results.
///
/// Each `CompiledNode::exec_parse` implementation writes its output to the
/// provided sink via this trait. The protocol is **uniform** across leaf and
/// composite nodes (I1 修正):
///
/// - **Leaf nodes** (FormatField, Bytes, etc.): call [`set_scalar`](Self::set_scalar)
///   to deposit their parsed scalar value.
/// - **Composite nodes** (Struct, Array): recursively create sub-sinks for
///   children, call [`set_field`](Self::set_field) / [`push_item`](Self::push_item)
///   to accumulate.
/// - **Parent nodes**: create a sub-sink per child, delegate `exec_parse` to
///   the child with the sub-sink, then call [`finish_subsink`](Self::finish_subsink)
///   to integrate the child's result.
pub trait OutputSink {
    /// Deposits a scalar value as this sink's result.
    ///
    /// Used by **leaf nodes** (e.g., `CompiledFormatField`) after parsing.
    /// The value is retrieved later by [`into_value`](Self::into_value).
    ///
    /// For `ValueSink`, this stores the value in a `pending: Option<Value>`
    /// slot. For Phase 13 `PyDictSink`, this is typically unused (leaves
    /// write via the parent's set_field directly in optimized mode).
    ///
    /// # Errors
    ///
    /// Returns [`ConstructError`] on type mismatch (typed sinks).
    fn set_scalar(&mut self, value: Value) -> Result<()>;

    /// Sets a named field to a value.
    ///
    /// Used by **composite nodes** (e.g., `CompiledStruct`) for each named
    /// field after integrating the child sub-sink's result.
    ///
    /// # Errors
    ///
    /// Returns [`ConstructError`] if the sink cannot accept the value.
    fn set_field(&mut self, name: &str, value: Value) -> Result<()>;

    /// Creates a sub-sink for a named field.
    ///
    /// The returned sub-sink receives the child node's output (scalar via
    /// `set_scalar`, or composite via recursive `set_field`). When the child
    /// finishes, [`finish_subsink`](Self::finish_subsink) integrates the result.
    ///
    /// This is the key mechanism for **direct-to-target** nested writes:
    /// a `PyDictSink` returns a child `PyDictSink` wrapping a new `PyDict`,
    /// which is directly inserted into the parent dict on finish — no
    /// intermediate `Value::Container` is ever constructed.
    ///
    /// # Errors
    ///
    /// Returns [`ConstructError`] on allocation failure.
    fn sub_sink_for_field(&mut self, name: &str) -> Result<Box<dyn OutputSink>>;

    /// Pushes an unnamed/sequential item (used by Array/Sequence).
    ///
    /// # Errors
    ///
    /// Returns [`ConstructError`] if the sink cannot accept more items.
    fn push_item(&mut self, value: Value) -> Result<()>;

    /// Creates a sub-sink for a sequential item.
    ///
    /// Analogous to [`sub_sink_for_field`](Self::sub_sink_for_field) but
    /// for array elements.
    fn sub_sink_for_item(&mut self) -> Result<Box<dyn OutputSink>>;

    /// Finishes a sub-sink and integrates its result.
    ///
    /// Called after a child finishes parsing. The implementation calls
    /// [`into_value`](Self::into_value) on the sub-sink and writes the result
    /// as a field (using the name remembered from `sub_sink_for_field`) or
    /// item.
    ///
    /// Phase 13 `PyDictSink` inserts the child PyDict directly (no Value
    /// intermediate).
    fn finish_subsink(&mut self, sub: Box<dyn OutputSink>) -> Result<()>;

    /// Consumes the sink and returns the final [`Value`].
    ///
    /// For `ValueSink`:
    /// - If `set_scalar` was called: returns the scalar value.
    /// - If `set_field` was called: returns `Value::Container`.
    /// - If `push_item` was called: returns `Value::List`.
    ///
    /// For Phase 13 `PyDictSink`, this converts to `Value::Container` (fallback)
    /// — but the primary output path uses the sink's native Python object.
    fn into_value(self: Box<Self>) -> Result<Value>;
}
```

### 7.4 ValueSink 实现（Phase 12，I1 修正）

```rust
/// Sink that collects parse results into a [`Value`] tree.
///
/// This is the Phase 12 (pure Rust path) implementation of [`OutputSink`].
/// It mirrors the current `CombinedConstruct::parse` behavior: builds a
/// `Value::Container` (for Struct) or `Value::List` (for Array), or holds
/// a single scalar (for leaf nodes).
#[derive(Debug, Default)]
pub struct ValueSink {
    /// Scalar result deposited by a leaf node via `set_scalar`.
    /// `Some` when this sink was used for a leaf; `None` for composites.
    pending: Option<Value>,
    /// Accumulated fields (for Container output, used by Struct/Sequence).
    fields: indexmap::IndexMap<String, Value>,
    /// Accumulated items (for List output, used by Array/Sequence).
    items: Vec<Value>,
    /// Field name remembered from `sub_sink_for_field` (for `finish_subsink`).
    pending_field_name: Option<String>,
}

impl ValueSink {
    /// Creates a new empty sink (mode determined by which methods are called).
    #[must_use]
    pub fn new() -> Self {
        ValueSink {
            pending: None,
            fields: indexmap::IndexMap::new(),
            items: Vec::new(),
            pending_field_name: None,
        }
    }
}

impl OutputSink for ValueSink {
    fn set_scalar(&mut self, value: Value) -> Result<()> {
        // Leaf nodes deposit their scalar result here.
        self.pending = Some(value);
        Ok(())
    }

    fn set_field(&mut self, name: &str, value: Value) -> Result<()> {
        self.fields.insert(name.to_string(), value);
        Ok(())
    }

    fn sub_sink_for_field(&mut self, name: &str) -> Result<Box<dyn OutputSink>> {
        // Remember the field name so finish_subsink can integrate correctly.
        let mut sub = ValueSink::new();
        sub.pending_field_name = Some(name.to_string());
        Ok(Box::new(sub))
    }

    fn push_item(&mut self, value: Value) -> Result<()> {
        self.items.push(value);
        Ok(())
    }

    fn sub_sink_for_item(&mut self) -> Result<Box<dyn OutputSink>> {
        Ok(Box::new(ValueSink::new()))
    }

    fn finish_subsink(&mut self, sub: Box<dyn OutputSink>) -> Result<()> {
        let value = sub.into_value()?;
        // If the sub-sink remembered a field name (from sub_sink_for_field),
        // write as a named field; otherwise push as an item.
        // Note: the field name is on the SUB sink, but we consume it here.
        // For Phase 12 simplicity, the parent uses set_field(name, value)
        // directly (see §7.5 Struct example). This method is for the
        // anonymous/array path.
        self.items.push(value);
        Ok(())
    }

    fn into_value(self: Box<Self>) -> Result<Value> {
        // Priority: scalar (leaf) > fields (Container) > items (List).
        if let Some(v) = self.pending {
            Ok(v)
        } else if !self.fields.is_empty() {
            Ok(Value::Container(self.fields))
        } else {
            Ok(Value::List(self.items))
        }
    }
}
```

> **I1 修正说明**：ValueSink 新增 `pending: Option<Value>` 字段（叶子标量暂存槽）和
> `set_scalar` 方法。叶子节点的 `exec_parse` 调用 `sink.set_scalar(value)` 写入标量。
> `into_value` 优先返回 pending 标量（叶子场景），其次 Container（Struct 场景），最后 List
> （Array 场景）。这使得**同一套 sink 协议统一处理叶子和复合节点**，无需父节点判断子节点类型。

### 7.5 复合构造器的双输出协调（Struct 示例）

`CompiledStruct::exec_parse` 协调 sink 写入与 Context 更新：

```rust
impl CompiledExec for CompiledStruct {
    fn exec_parse(
        &self,
        stream: &mut CombinedStream,
        ctx: &mut Context,
        sink: &mut dyn OutputSink,
    ) -> Result<()> {
        let mut child_ctx = ctx.subcontext();

        for field in &self.fields {
            match &field.name {
                Some(name) => {
                    // Named field: create sub-sink, parse into it, extract result.
                    // I1 修正：统一协议——叶子子节点用 set_scalar 写入 sub_sink，
                    // 复合子节点用 set_field 递归写入。父节点无需区分。
                    let mut sub_sink = sink.sub_sink_for_field(name)?;
                    field.subcon.exec_parse(stream, &mut child_ctx, &mut sub_sink)?;
                    let value = sub_sink.into_value()?;
                    // ↑ 叶子：set_scalar → into_value 返回标量
                    //   复合：set_field → into_value 返回 Container/List

                    // Dual write: sink (output) + context (for this.field refs)
                    sink.set_field(name, value.clone())?;
                    child_ctx.insert(name.clone(), value);
                }
                None => {
                    // Anonymous field: parse, discard result (Context not updated).
                    let mut sub_sink = sink.sub_sink_for_item()?;
                    field.subcon.exec_parse(stream, &mut child_ctx, &mut sub_sink)?;
                    // Anonymous: result discarded.
                }
            }
        }
        Ok(())
    }
    // exec_build / exec_sizeof: 见 §7.6
}
```

> **叶子 exec_parse 示例**（I1 修正）：
> ```rust
> impl CompiledExec for CompiledFormatField {
>     fn exec_parse(&self, stream: &mut CombinedStream, ctx: &mut Context,
>                   sink: &mut dyn OutputSink) -> Result<()> {
>         let value = self.inner.parse(stream, ctx)?;  // 复用 CombinedConstruct 的二进制逻辑
>         sink.set_scalar(value)?;                       // 写入标量（I1 协议）
>         Ok(())
>     }
> }
> ```
> 叶子节点不知道自己的字段名——它只负责 parse + set_scalar。父节点（Struct）负责
> 从 sub_sink 提取值并 set_field。这是 **I1 统一协议**的核心。

> **双写分析**：`sink.set_field(name, value.clone())` + `child_ctx.insert(name, value)`。
> 这里有一次 `value.clone()`。对于标量值（Int/UInt/Bool），clone 廉价。对于大 Bytes/Container，
> clone 有开销。**优化（Phase 12 可选）**：让 `ValueSink` 和 `Context` 共享底层
> `IndexMap<String, Value>`——即 `ValueSink` 的 `fields` 就是 Context 当前层的 `fields`。
> 这样只需写一次。但需 Context 暴露 `fields_mut()`，破坏封装。**建议 Phase 12 先用双写
> （正确性优先），Phase 14 优化为共享。**

### 7.6 嵌套 sink 传递机制（REV #5 深入）

对于**嵌套复合构造器**（Struct 内嵌 Struct），sink 传递是递归的：

```
CompiledSchema::parse_bytes(data)
  │
  ├─ root_sink = ValueSink::new()          [map mode, 顶层容器]
  │
  └─ tree.exec_parse(stream, ctx, &mut root_sink)
       │
       └─ CompiledStruct::exec_parse
            │ for field "header" (nested Struct):
            ├─ sub_sink = root_sink.sub_sink_for_field("header")   [创建子 sink]
            ├─ header_node.exec_parse(stream, child_ctx, &mut sub_sink)
            │    │
            │    └─ CompiledStruct::exec_parse (header)
            │         │ for field "length":
            │         ├─ length_node.exec_parse(stream, &mut grandchild_ctx, &mut sub_sink)
            │         │    → 读 1 字节，写入 sub_sink.set_field("length", Value::UInt(3))
            │         │    → child_ctx.insert("length", Value::UInt(3))
            │         │
            │         └─ (header parse 完成)
            │
            ├─ root_sink.set_field("header", sub_sink.into_value())
            │    → root_sink 现在有 {"header": {"length": 3}}
            │
            └─ (continue next field "data")
```

**Phase 13 `PyDictSink` 的优势**：子 sink 是真实的子 `PyDict`，`set_field` 直接是
`child_dict.set_item`。`finish_subsink` 将子 PyDict 插入父 PyDict——**全程无 Value 中转**。
这是 direct-to-Python 的核心机制。

### 7.7 Phase 12 与 Phase 13 的 sink 对比

| 维度 | Phase 12（ValueSink） | Phase 13（PyDictSink） |
|------|---------------------|----------------------|
| 产出 | `Value::Container` 树 | Python `dict`（嵌套） |
| 中间表示 | 有 `Value` 树（不可避免，纯 Rust 路径产出就是 Value） | 无 `Value` 树（直出 PyDict） |
| FFI | 无（纯 Rust） | `PyDict::set_item`（Python C API，持有 GIL） |
| sub_sink | 子 `ValueSink` | 子 `PyDictSink`（包装新 `PyDict`） |
| 性能 | 与旧 `parse` 持平（构建 Value 树） | 消除 Value→Python 转换开销 |

> **Phase 12 的 sink 价值**：主要是**架构准备**——定义 `OutputSink` trait，让 `CompiledNode`
> 的 parse 从一开始就面向 sink 编写，而非返回 Value。Phase 13 只需新增 `PyDictSink` 实现，
> `CompiledNode` 的 parse 逻辑**零修改**。这是设计的渐进性体现（顶层设计 G6）。

## 8. 纯 Rust 路径验证策略

Phase 12 的出口标准：纯 Rust 路径可通过编译执行树 parse/build。验证需要回答两个问题：
(1) 编译执行树能正确 parse/build 吗？(2) 编译执行树的结果与旧路径（直接调用
`CombinedConstruct::parse`）**行为等价**吗？

### 8.1 等价性保证策略

**核心方法：差分测试（differential testing）**。对同一个 schema，分别用两条路径 parse/build
相同输入，断言结果相等。

```rust
/// 等价性测试框架（伪代码）
fn assert_equivalent(schema: &CombinedConstruct, data: &[u8]) {
    // 旧路径
    let old_result = schema.parse_bytes(data).unwrap();

    // 新路径（编译执行树）
    let compiler = SchemaCompiler::new();
    let compiled = compiler.compile(schema).unwrap();
    let new_result = compiled.parse_bytes(data).unwrap();

    assert_eq!(old_result, new_result, "parse mismatch");

    // build 等价性
    let old_bytes = schema.build_bytes(&old_result).unwrap();
    let new_bytes = compiled.build_bytes(&old_result).unwrap();
    assert_eq!(old_bytes, new_bytes, "build mismatch");
}
```

虽然完整基准在 Phase 14，但 Phase 12 CODING 阶段需验证**编译执行树不比旧路径显著慢**：

```rust
// benches/compiled_vs_declaration.rs (Phase 12 简化版)
// 对 10 字段 Struct，编译执行树 parse 应 ≥ 旧路径速度 * 0.9（允许 10% 容差）
// （编译开销摊销后，反复 parse 应持平或更快）

> **I1/I2 性能修正**：由于 Phase 12 的统一 sub_sink 协议为每个子节点（含叶子）分配一个
> ValueSink，单次 parse **可能略慢于旧路径**（额外分配 + clone）。这是**已知的阶段性开销**：
> - sink 写入有一次虚分发 per 字段（~ns 级，可忽略）
> - 每叶子一次 ValueSink 分配（小结构体，~100ns，对 100 字段 Struct = ~10µs）
> - 双写 clone（标量廉价，大 Bytes/Container 有开销）
>

> （§8.1 差分测试全 PASS）+ 编译开销可摊销（反复 parse 时总时间不超过旧路径的 1.2 倍）。
> 性能优化（叶子快速路径、ValueSink 池化、共享 IndexMap）推迟到 Phase 14。

### 8.5 循环引用检测 + LazyBound 延迟编译（I4 修正）

`SchemaCompiler` 的 `max_depth`（默认 256）防止栈溢出。但真正的循环引用（如 `LazyBound`
自引用）不应因深度限制而失败。

**I4 修正——LazyBound 编译策略（方案 A：降级旧路径）**：

`LazyBound` 持有一个延迟绑定的子构造器（通过闭包或回调）。编译时绑定可能尚未完成，因此
SchemaCompiler **不递归编译** LazyBound 的子节点。而是产出 `CompiledLazyBound`，持有
`Arc<dyn Construct>` 包装的 LazyBound 节点本身。运行时 `exec_parse`/`exec_build` 直接调用
`self.inner.parse(stream, ctx)` / `self.inner.build(data, stream, ctx)`——由 LazyBound 自身的
`Construct` 实现处理延迟绑定（在首次 parse/build 时解析子构造器）。

```rust
impl BuildConstruct for LazyBound {
    fn compile(&self, _compiler: &SchemaCompiler) -> Result<CompiledNode> {
        // 方案 A：不递归，降级为旧路径。
        // self 是 &LazyBound；需 Arc 包装（LazyBound 需 Clone 或改用 Arc 持有）。
        // 前提：LazyBound 实现 Clone，或 CombinedConstruct::LazyBound 内部为 Arc。
        // 若 LazyBound 不可 Clone，则整个 LazyBound variant 编译为 CompiledDynamic
        // （持有 Arc<dyn Construct>），统一走 escape-hatch。
        Ok(CompiledNode::LazyBound(CompiledLazyBound {
            inner: Arc::new(self.clone()),  // 或走 CompiledDynamic 降级
        }))
    }
}

impl CompiledExec for CompiledLazyBound {
    fn exec_parse(&self, stream: &mut CombinedStream, ctx: &mut Context,
                  sink: &mut dyn OutputSink) -> Result<()> {
        // 降级旧路径：LazyBound.parse 自身处理延迟绑定。
        let value = self.inner.parse(stream, ctx)?;
        sink.set_scalar(value)
    }
    // exec_build 同理
}
```

> **I4 简化说明**：若 LazyBound 不可 Clone（持有闭包等不可 Clone 字段），则 LazyBound variant
> 的 `BuildConstruct::compile` 统一编译为 `CompiledNode::Dynamic(CompiledDynamic { inner: ... })`，
> 不使用 CompiledLazyBound variant。这与 Dynamic 的降级策略完全一致——LazyBound 本质上是一
> 种"编译期无法确定子树"的 escape-hatch。**Phase 12 推荐此简化路径**（CompiledLazyBound
> variant 保留但在实现上等价于 Dynamic 降级），降低实现复杂度。

## 9. REV 问题回应汇总

### 9.1 #1 CombinedConstruct vs CompiledNode 关系

**回应**：**选项 B（全新 enum，与 CombinedConstruct 平行）**。理由见 §2.1。
- CompiledNode 是执行树（编译后），CombinedConstruct 是声明树（编译前）。
- CompiledNode 的叶子 variant **复用** CombinedConstruct 的具体类型（零重复二进制逻辑）。
- 复合 variant 是新类型，持有 `Box<CompiledNode>` + 编译参数。
- 两者并存，旧路径（CombinedConstruct::parse）保留，新路径（CompiledSchema::parse_bytes）可选。

### 9.2 #2 Sink 嵌套与中间 Value 避免

**回应**：**Phase 12 纯 Rust 路径不可避免中间 Value（产出就是 Value 树）。Phase 13 通过
OutputSink trait + 递归 sub_sink 协议消除中间 Value。** 详见 §7.1、§7.3、§7.7。

### 9.3 #4 SchemaCompiler 内省机制

**回应**：**方案 A（直接遍历 CombinedConstruct 声明树），不需要 `__cs_compile__` 协议方法，
不需要 pattern match PyO3 对象类型。** 关键发现：PyO3 wrapper 的 `inner` 字段已是完整的
`CombinedConstruct` 声明树（Phase 11 后），SchemaCompiler 直接 `match` 它的 variant 提取编译
参数。详见 §4.1、§4.2。

### 9.4 #5 复合构造器双输出（Sink + Context）

**回应**：**Sink 是 trait（`&mut dyn OutputSink`），非泛型非 enum。Sink 与 Context 不是同一
对象，通过双写保持一致（set_field + ctx.insert）。Phase 12 双写（正确性优先），Phase 14 可
优化为共享底层 IndexMap。** 详见 §7.2、§7.3、§7.5。

### 10.3 关键风险点

1. **12.1 的 enum 大小**：CompiledNode 有 71 个 variant，最大 variant（如 CompiledSwitch 含
   cases Vec）可能较大。DEV 需实测 `std::mem::size_of::<CompiledNode>()`，若 >128 字节，
   对大 variant 内部字段加 Box。参考 Phase 11 §6.1 的分析（CombinedConstruct ~80 字节）。

2. **12.6 的 Adapter 闭包迁移（B4 关键风险点）**：`Box<dyn Fn>` → `Arc<dyn Fn + Send + Sync>`
   影响所有 Adapter/Validator 类型别名（4 个）及其构造器（5 个 new 方法）和使用处。DEV 需
   全局搜索 `DecodeFunc`/`EncodeFunc`/`SymmetricFunc`/`CheckFunc`，确保全部迁移，并审计所有
   闭包构造点捕获值满足 `Send + Sync`。这是本阶段**唯一的语义性变更**（其余均为新增）。

3. **12.3 的 CombinedExpr Clone 补充（B2）**：6 个类型补充 `#[derive(Clone)]`。改动机械、
   风险低，但必须**一次性完成全部 6 个**（互递归依赖）。改动后 `cargo test` 现有测试应全 PASS。

4. **12.4 的 Dynamic Box→Arc 迁移（I3）**：`CombinedConstruct::Dynamic` 从 Box 改 Arc。
   影响所有构造 Dynamic 节点的调用点。需全局搜索 `Dynamic(Box` 确保迁移完整。

5. **12.7 的 sink 递归正确性**：嵌套 Struct 的 sub_sink 创建/finish 时序必须正确。DEV 需特别
   测试深度嵌套（Struct 内 Struct 内 Array）的场景。

6. **12.9 的 LazyBound 自引用（I4）**：LazyBound 的 compile **不递归**（会无限循环），降级为
   CompiledDynamic/CompiledLazyBound（持有 `Arc<dyn Construct>`），运行时走旧路径。

### 10.4 出口标准（v2 修正，对照顶层设计 §8.2.1-§8.2.2）
