§16.2.3 表格（行 4333-4336）的 a_err_eof 预测"2342ns → 1100ns（节省 ~1240ns）"基于 INVEST §5.3（行 363-373）的三项优化建议。但精读 `error.rs:488-533` 后发现：

## §1 a_err_eof 优化设计

### 1.1 现状量化（数据来源标注）

数据源：`experiments/phase4_perf_investigation_report.md §3.3`（行 248-257）+ `§2.3`（行 146）。

| 场景 | Py ns/call | Rs ns/call | 当前加速比 | S-PERF 标准 |
|------|-----------:|-----------:|-----------:|------------|
| a_err_eof（Array(100, Int8ub) + 50B stream EOF）parse | 15,114 | 2,342 | **6.45x** | ≥10x（差 3.55x） |

**Rs 端开销分解**（INVEST §3.3 行 250-256，量级参考非精确值）：

| 成分 | 估算 ns | 占 Rs 总比 | 是否本设计优化目标 |
|------|--------:|----------:|------------------|
| 50 个 Int8ub 成功 parse（含 per-iter Array 开销） | ~850 | 36% | 否（4.7 lazy path 已优化） |
| 第 51 次 stream.read(1) 失败 → StreamError 构造 | ~150 | 6% | 否（必要工作） |
| ArrayNode + StructNode 错误传播（path 重建） | ~100 | 4% | 否（lazy path 已优化） |
| **ConstructError → PyErr 转换**（error.rs:655-679） | **~1,200-1,250** | **~53%** | **是（本设计核心目标）** |
| 合计 | ~2,300-2,350 | 100% | — |

**目标**：将 ConstructError → PyErr 转换从 ~1,250ns 降至 ~300-500ns（节省 ~750-950ns），使总 Rs ≤ 1,511ns（10x 加速比阈值）。

### 1.2 根因分析——错误抛出路径全部 FFI 来源（L-05 对策）

精读 `error.rs:655-679` 当前实现，错误抛出路径的 FFI / Python 调用来源如下：

| # | FFI 来源 | 代码位置 | 量级开销 | 当前是否已优化 |
|---|---------|---------|--------:|---------------|
| F1 | 字符串预格式化（`err.path().map(\|s\| s.to_string())` + `msg.to_string()`） | error.rs:658, 663 | ~100-200ns | 否（2-3 次 Rust String 分配） |
| F2 | `Python::with_gil(\|py\| ...)` 闭包构造 | error.rs:667 | ~10-30ns | 部分（已持 GIL 时 O(1)，仅栈帧） |
| F3 | `EXCEPTIONS.get(py)` OnceCell 读 | error.rs:668 | ~5-20ns | 是（GILOnceCell 已初始化后是原子读） |
| F4 | `select_exception_class`：match err 变体 | error.rs:585-619 | ~5ns | 是（Rust 内部 match，无 FFI） |
| F5 | `cls.bind(py).clone()`（Py<PyType>::clone = Py_INCREF） | error.rs:618 | ~10-20ns | 否（每次错误都 incref/decref 一次） |
| F6 | `cls.call1((message, path))` 构造 args 元组 | error.rs:635-637（`build_exception_instance`） | ~50-100ns | 否（每次新建 PyTuple + 2 个 item set） |
| F7 | `cls.call1(...)` 调用 Python 类构造 `tp_call → tp_new → tp_init` | error.rs:635-637 | ~600-900ns | **否（核心瓶颈，CPython 字节码循环 + tp_alloc + tp_init 执行 __init__）** |
| F8 | `PyErr::from_value_bound(instance)` 包装 + incref | error.rs:671 | ~50-100ns | 否 |

**合计估算**：100+20+10+5+15+75+750+75 = **~1,050ns**（与 INVEST 实测 ~1,200-1,500ns 吻合，差额来自 CPython 字节码循环额外开销）。

### 1.3 优化方案

按 F1-F8 逐项设计优化。**核心创新**：F7 改为"Rust 侧直接构造异常实例，绕过 Python `__init__` 字节码"。

#### 优化项 O1：lazy 字符串预格式化（针对 F1）

**现状**（error.rs:658-665）：
```rust
let path_owned: Option<String> = err.path().map(|s| s.to_string());
let (message, effective_path) = match err.message() {
    Some(msg) => (msg.to_string(), path_owned.as_deref()),
    None => (err.to_string(), None),
};
```

两次 `to_string()` + 一次 `path_owned` 分配，~100-200ns。

**优化方向**：传 `&str` 引用进入 `with_gil` 闭包，闭包内借用 `err`，不预格式化。需要重构 `From` 实现签名（借用 `&ConstructError` 而非消费 `ConstructError`）。

**预测节省**：~100ns。

#### 优化项 O2：避免 `Py<PyType>::clone` incref（针对 F5）

**现状**（error.rs:590-619）：
```rust
fn select_exception_class<'py>(...) -> Bound<'py, PyType> {
    let cls: &Py<PyType> = match err { ... };
    cls.bind(py).clone()  // Py<PyType>::clone = Py_INCREF
}
```

返回拥有的 `Bound`，触发一次 incref；调用方使用完后decref。

**优化方向**：返回借用 `&Bound<'py, PyType>`，避免 incref/decref。pyo3 0.22 API 支持。

**预测节省**：~20ns。

#### 优化项 O3：绕过 Python `__init__` 直接构造异常实例（针对 F6 + F7 + F8 核心）

**现状**（error.rs:627-638 + Python `_errors.py:46-53`）：

每次错误抛出都调 `cls.call1((message, p))`，触发 Python 类构造：
1. `tp_call` → `tp_new` → `tp_alloc`（~200ns，分配异常实例）
2. `tp_init` 执行 Python `__init__` 字节码：
   ```python
   def __init__(self, message="", path=None):
       self.message = message      # ~50ns
       self.path = path            # ~50ns
       if path is not None:
           full = "Error in path {}\n{}".format(path, message)  # ~150ns
       else:
           full = message
       super().__init__(full)      # ~100ns（设 args）
   ```
3. args tuple 构造（~50-100ns，`cls.call1((message, p))` 的 `(message, p)` 元组）

总开销 ~600-900ns（F6+F7+F8 部分）。

**关键洞察**：Python 侧 `ConstructError.__str__`（`_errors.py:55-58`）已经独立处理格式化：
```python
def __str__(self):
    if self.path is not None:
        return "Error in path {}\n{}".format(self.path, self.message)
    return self.message
```

`str(e)` 不依赖 `args`，而是依赖 `self.path` + `self.message`。这意味着 **`args` 的内容可以是 `(message,)` 而非预格式化的 `(full,)`**，不影响用户感知。

**优化方向**：在 Rust 侧用 CPython C API（pyo3::ffi）直接构造异常实例，绕过 `tp_init` 字节码执行：

1. `PyType_GenericAlloc(cls, 0)` 分配实例（~200ns，CPython 固有，无法优化）
2. `PyObject_Setattr(instance, "message", message)`（~30-50ns）
3. `PyObject_setattr(instance, "path", path_or_none)`（~30-50ns）
4. **不调用 format**：直接 `BaseException.args = (message,)`（~50ns，绕过 super().__init__(full)）
5. 包装为 `PyErr`（~30-50ns）

预估总开销：200+40+40+50+40 = **~370ns**。

**对比**：当前 F6+F7+F8 ≈ 750-900ns；优化后 ≈ 370ns。**节省 ~380-530ns**。

**实现风险**：
- 涉及 `unsafe` CPython C API（`PyType_GenericAlloc`），需 REV 严格审查安全边界
- 必须保证 Python 用户继承 `ConstructError` 并重写 `__init__` 时的兼容性——绕过 `__init__` 意味着子类 `__init__` 不被调用
- 必须保证 `pickle` / `repr` / `copy` 等标准协议不破坏（依赖 `args` 字段）

**风险缓解**：
- 仅对**已知的 13 个 construct 内置异常类**使用 fast-path（在 `ExceptionClasses` 缓存时标记）
- 用户子类化的异常走原有的 `call1` 慢路径（自动降级，保证兼容）
- 单元测试覆盖：`pickle.dumps(e)` / `repr(e)` / `str(e)` / `e.message` / `e.path` / `e.args`

#### O3 unsafe CPython C API 安全前置条件列表（按 4.x-REV OBS-3 修订，DEV 实施硬要求）

O3 fast-path 涉及 4 个 `unsafe` CPython C API 调用，每个都有明确的安全契约。DEV 实施 O3 时必须逐条满足前置条件、检查失败模式、并在失败时按 BC6 回退到 `call1` 慢路径。

| # | unsafe API | 安全前置条件 | 失败模式 | BC6 回退路径 |
|---|-----------|-------------|---------|-------------|
| U1 | `PyType_GenericAlloc(cls, 0)` | ① GIL 已持有（pyo3 `Python<'_>` token 在作用域内）② `cls` 是非空有效 `PyType` 指针（来自 `ExceptionClasses` 缓存的 `Py<PyType>`，模块初始化时已校验）③ `cls` 是确切内置异常类（经 `cls.as_ptr() == builtin_cls.as_ptr()` 指针比较确认，见 OBS-2 修订） | 返回 `NULL` + 设置 `PyErr_MemoryError`（仅 OOM 时） | 检查返回值 `is_null()` → 调 `PyErr_Clear()` + 回退到 `cls.call1((message, path))` 慢路径 |
| U2 | `PyObject_SetAttr(instance, "message", value)` | ① GIL 已持有 ② `instance` 是 U1 返回的非空 `PyObject*` ③ `value` 是非空 `PyObject*`（`&str` → `PyString::new` 构造，已在 pyo3 内部 incref）④ `instance` 类型未 monkey-patch `__setattr__` 拒绝写入（用户子类化已被 OBS-2 检测排除，但内置类仍可能被 monkey patch） | 返回 `-1` + 设置 `PyErr_AttributeError` / `PyErr_TypeError`（如 `__setattr__` 抛错） | 检查返回值 `< 0` → 调 `PyErr_Clear()` + `Py_DECREF(instance)` + 回退到 `call1` 慢路径 |
| U3 | `PyObject_SetAttr(instance, "path", value)` | 同 U2；`value` 为 `PyNone` 或 `PyString`（`err.path()` 为 `None` 时传 `PyNone`） | 同 U2 | 同 U2 |
| U4 | `BaseException.args` 直接设置（`PyObject_SetAttr(instance, "args", tuple)` 或直接操作 `PyBaseExceptionObject.fields.args`） | ① GIL 已持有 ② `instance` 是 `BaseException` 子类（13 个内置异常类全部满足）③ `tuple` 是非空 `PyTuple*`（构造 `(message,)` 单元素元组） | 返回 `-1`（罕见，仅 monkey patch `__setattr__` 拦截 `args` 时） | 同 U2 |

**统一的 unsafe 块结构**（DEV 实现参考）：

```rust
unsafe {
    // 前置条件断言（debug 模式）
    debug_assert!(Python::with_gil(|py| py.gil_is_owned()));
    debug_assert!(!cls.as_ptr().is_null());

    // U1: 分配实例
    let instance = PyType_GenericAlloc(cls.as_ptr(), 0);
    if instance.is_null() {
        PyErr_Clear();
        return fallback_to_call1_slow_path(py, cls, message, path);  // BC6
    }

    // U2: 设置 message 属性
    let msg_obj = PyString::new(py, message);
    if PyObject_SetAttr(instance, c_str!("message"), msg_obj.as_ptr()) < 0 {
        PyErr_Clear();
        Py_DECREF(instance);
        return fallback_to_call1_slow_path(py, cls, message, path);  // BC6
    }

    // U3 + U4 同款检查（略）
    // ...
}
```

**REV 审查重点**（REV 在 O3 实施后 CODE_REVIEW 阶段）：
1. 每个 `unsafe` 块是否都有完整的前置条件断言 + 失败模式检查 + BC6 回退
2. `instance` 在所有失败分支是否正确 `Py_DECREF`（避免引用泄漏）
3. `PyErr_Clear()` 是否在所有失败分支调用（避免污染 Python 错误状态）
4. `cargo miri test` 评估（Miri 对 FFI 支持有限，但本地逻辑如指针比较 / GC 引用追踪可被检查）

**反例声明（OBS-3 失效场景）**：
- 若 U1-U4 任一在 13 个内置异常类上发生失败（非 OOM），说明 Python 环境异常（如内置类被 monkey patch），fast-path 整体降级为关闭状态（R2 反例第 3 步"可配置开关"自动触发）

#### 优化项 O4：减少 PyErr 包装开销（针对 F8）

**现状**：`PyErr::from_value_bound(instance)` 内部 incref instance + 构造 PyErr 结构体。

**优化方向**：与 O3 合并——直接在 fast-path 中构造 PyErr（pyo3 提供 `PyErr::from_value`，避免中间层）。

**预测节省**：~30-50ns。

#### 优化方案汇总

| 优化项 | 目标 FFI 来源 | 预测节省（量级参考） |
|--------|--------------|-------------------:|
| O1 lazy 字符串 | F1 | ~100ns |
| O2 避免 incref | F5 | ~20ns |
| O3 绕过 __init__ | F6 + F7 + F8 | ~400-500ns |
| O4 PyErr 直接构造 | F8 | ~30-50ns |
| **合计** | — | **~550-670ns** |

加上 F2/F3/F4 已无优化空间（~35ns 不可压缩），优化后错误抛出总开销 ≈ **~480-580ns**（vs 当前 ~1,200-1,500ns，节省 ~62%）。

### 1.4 性能假设（performance-gate SKILL Checkpoint 1）

#### 1.4.1 瓶颈识别（量化数据 + 来源）

主瓶颈：**F7 Python `tp_init` 字节码执行**（~600-900ns / 次）。
- 数据来源：`experiments/phase4_perf_investigation_report.md §3.3 行 250-256`（实测 ~1,200-1,250ns 错误抛出总开销）
- Python `_errors.py:46-53`（`__init__` 实现含 format + super().__init__）
- 次瓶颈：F1 字符串预格式化（~100-200ns）、F6 args tuple 构造（~50-100ns）

#### 1.4.2 机制说明（因果链）

```
现状路径（~1,200-1,500ns）：
  ConstructError →
  with_gil 闭包 →
  OnceCell 查表（已优化） →
  select_exception_class + incref →
  cls.call1((message, path)) →
    构造 PyTuple (~75ns)
    tp_call → tp_new → tp_alloc (~200ns)
    tp_init 执行 Python __init__ 字节码：
      self.message = message (~50ns)
      self.path = path (~50ns)
      format "Error in path {}\n{}" (~150ns)   ← 不必要（__str__ 已重写）
      super().__init__(full) (~100ns)           ← 不必要（args 不影响 str(e)）
  PyErr::from_value_bound (~75ns)

优化后路径（~480-580ns）：
  ConstructError →
  with_gil 闭包 →
  OnceCell 查表（不变） →
  select_exception_class（借用，无 incref） →
  PyType_GenericAlloc (~200ns)                 ← 保留（CPython 固有）
  PyObject_SetAttr "message" (~40ns)
  PyObject_SetAttr "path" (~40ns)
  BaseException.args = (message,) (~50ns)      ← 跳过 format + super().__init__
  PyErr 直接构造 (~40ns)
```

#### 1.4.3 可证伪预测

**预测 P1（核心）**：实施 O1+O2+O3+O4 后，a_err_eof 场景的 Rs 端错误抛出开销从 ~1,250ns 降至 ~500ns（量级参考，节省 ~750ns），总 Rs 从 2,342ns 降至 ~1,592ns，加速比 **6.45x → ~9.5x**（保守）/ **~10.5x**（中位）/ **~12x**（理论上限，按 REV OBS-1 修订）。

> **乐观预测 ~12x 的属性说明（按 4.x-REV OBS-1 修订）**：
> - 乐观预测 ~12x 是**理论上限**——假设所有 O1-O4 优化叠加**无重叠损失**、CPython 字节码循环额外开销为零、`PyObject_SetAttr` 命中属性缓存最快路径。
> - O1-O4 合计预测节省 ~550-670ns（§1.3 优化方案汇总表）/ ~695ns（§1.4.3 FFI 来源对照表）仅支撑**中位预测 ~10.5x**（节省 ~850ns 含 CPython 字节码循环其他可压缩部分）。
> - 保守 ~9.5x 与中位 ~10.5x 是设计阶段可承诺的预测区间；若 VET 实测超出中位预测（达 ~12x），需在性能验证报告中重新分解开销，确认非 O1-O4 来源（如 crate 整体 inlining 收益，参考 4.6 O1 后 S03 Always 路径反例 3）贡献，避免归因错误（L-05 对策）。

**预测 P2（边界）**：a_err_eof 加速比达标（≥10x）的最低要求是 Rs ≤ 1,511ns，对应错误抛出开销 ≤ 411ns。若优化后实测错误抛出开销 > 600ns，预测 P1 不成立，需进入反例流程。

**FFI 来源对照**（L-05 对策：每个 FFI 来源在预测中均有对应声明）：

| FFI 来源 | 当前估算 | O1-O4 优化后估算 | 预测中对应声明 |
|---------|--------:|----------------:|---------------|
| F1 字符串预格式化 | ~150ns | ~0ns（lazy） | O1 节省 ~100ns，计入 P1 |
| F2 with_gil 闭包 | ~20ns | ~20ns（不变） | 不可压缩，计入 Rs 下界 |
| F3 OnceCell 读 | ~10ns | ~10ns（不变） | 不可压缩，计入 Rs 下界 |
| F4 match err 变体 | ~5ns | ~5ns（不变） | 不可压缩，计入 Rs 下界 |
| F5 incref/decref | ~15ns | ~0ns（借用） | O2 节省 ~20ns，计入 P1 |
| F6 args tuple 构造 | ~75ns | ~50ns（仅 `(message,)`） | O3 优化，计入 P1 |
| F7 tp_init 字节码 | ~750ns | ~280ns（仅 tp_alloc + setattr × 2） | O3 核心节省 ~470ns，计入 P1 |
| F8 PyErr 包装 | ~75ns | ~40ns（直接构造） | O4 节省 ~35ns，计入 P1 |
| **合计** | **~1,100ns** | **~405ns** | **节省 ~695ns，对应 P1 中位预测** |

**注**：F7 的 ~750ns 包含 `tp_alloc`（~200ns，CPython 固有，保留）+ `tp_init` 字节码（~550ns，O3 跳过）。优化后保留 `tp_alloc` + 用 `PyObject_SetAttr` 替代 `tp_init`。

#### 1.4.4 反例声明（如果预测为假，设计需要怎样修改）

**反例 R1**：实施 O1-O4 后实测 a_err_eof 加速比 < 10x（如 ~8-9x），且错误抛出开销 > 600ns。

**处置**：
1. 用 INVEST 同款方法重新分解 Rs 端开销，定位剩余瓶颈
2. 候选深层优化：
   - **R1a**：fast-path 完全跳过 `tp_alloc`，使用预分配的异常实例池（每次抛出复用并 set 新属性）—— 复杂度高，需评估线程安全
   - **R1b**：用 sentinel 返回值替代部分 PyErr（如 StreamError EOF 改为 Rust 内部 sentinel，在 FFI 入口才构造 PyErr）—— 影响所有节点签名，需新开 Phase
   - **R1c**：减少 50 个 Int8ub 的 per-iter 开销（如 4.7 lazy path 的更深优化，把 17ns/elem 降至 12ns/elem，节省 ~250ns）—— 但 4.7 已实施 lazy path，进一步优化空间有限
3. 若 R1a/R1b/R1c 仍无法达 10x，标记为"结构性边界"，按 §2 p_err_overflow 同款流程转呈用户决策

**反例 R2**：O3 绕过 `__init__` 导致 Python 用户子类化的异常行为破坏（如继承 ConstructError 重写 `__init__` 时 Rust 抛出的错误未走子类 `__init__`）。

**处置**：
1. O3 实施时仅在 `ExceptionClasses` 缓存的 13 个内置异常类启用 fast-path
2. 用户子类化的异常检测（**按 4.x-REV OBS-2 修订**：用指针相等比较 `cls.as_ptr() == builtin_cls.as_ptr()`，**确保是确切类型而非子类**；语义注：`PyType_IsSubtype(A, B)` 检查的是"A 是否 B 的子类"——任何子类都返回 true，不能用于"是否等于内置类"判定）走原有 `call1` 慢路径
3. 若仍有兼容性问题，O3 整体降级为可配置开关（默认开启 fast-path，用户报告问题可关闭）

#### 1.4.5 验证方法（实现后如何验证预测）

## §2 p_err_overflow 工程上限分析 + 推荐方案

### 2.1 现状量化与数据上不可行的论证

数据源：`experiments/phase4_perf_investigation_report.md §3.3`（行 232-246）+ §2.3（行 145）。

| 场景 | Py ns/call | Rs ns/call | 当前加速比 | S-PERF 标准 |
|------|-----------:|-----------:|-----------:|------------|
| p_err_overflow（PrefixedArray cf=300 build overflow）build | 4,864 | 2,471 | **1.97x** | ≥10x（差 8.03x） |

**Rs 端开销分解**（INVEST §3.3 行 234-244，量级参考）：

| 成分 | 估算 ns | 占比 |
|------|--------:|----:|
| 正常 build 路径至 countfield.build（FFI + StructNode 入口 + PrefixedArrayNode 收集 list + countfield 调度） | ~150 | 6% |
| FormatField.build(300) 失败（u8::try_from + FormatFieldError 构造 + path.to_string） | ~200 | 8% |
| PrefixedArrayNode push_path_segment | ~50 | 2% |
| **ConstructError → PyErr 转换** | **~1,500** | **61%** |
| 其他（Py_err 等待 + Python catch 开销计入 Rs） | ~570 | 23% |
| 合计 | ~2,470 | 100% |

**应用 §1 O1-O4 优化后的预测**（错误抛出从 ~1,500ns 降至 ~500ns，节省 ~1,000ns）：

| 项 | 当前 | 优化后（预测） |
|----|----:|---------------:|
| Rs 总耗时 | 2,471ns | ~1,471ns |
| 加速比（vs Py 4,864ns） | 1.97x | **~3.31x** |

**结论**：即使应用 §1 全部优化，p_err_overflow 加速比上限 **~3-4x**，远低于 10x。**数据上不可行**。

### 2.2 数据上不可行的根因（非"物理上限"豁免，而是数据特性）

p_err_overflow 难以达 10x 的结构性原因（§16.2.3 行 4340-4344 已论证，此处补全）：

1. **Python baseline 仅 4,864ns**：Python construct 的 PrefixedArray build 用 `FocusedSeq + Rebuild` 偷懒（`construct/core.py` PrefixedArray 实现），count 直接来自 `len(obj)`，正常路径就很短，错误路径占比相对小
2. **Rs 正常路径已 ~200ns**：到达 countfield.build 的正常 build 路径（FFI + StructNode + 收集 list + countfield 调度）已 ~150-200ns，无法进一步压缩（受 §0 一次 FFI 约束）
3. **错误抛出剩余成本**：即便 O3 把错误抛出压到 ~500ns，500 + 200 = 700ns vs Py 4,864ns = 6.95x（最乐观，仍未达 10x）
4. **若 Rs 错误抛出压到 0ns（理论极限）**：200 + 0 = 200ns vs 4,864ns = 24.32x（理论可达）—— 但错误抛出 0ns 不现实（至少需 PyErr 包装 ~50ns），实际极限 ~250ns vs 4,864ns = ~19x

**关键洞察**：p_err_overflow 的可达性**取决于 Python baseline**。当前 benchmark 的"PrefixedArray cf=300 build overflow"场景，Python baseline 仅 4,864ns（FocusedSeq+Rebuild 偷懒），导致 Rs 即便极致优化也仅 ~3-7x。

### 2.3 三方案对比

#### 方案 A：接受 p_err_overflow < 10x 作为"错误路径固有边界"

**描述**：在 4.x 范围内实施 O1-O4 优化（错误抛出从 ~1,500ns 降至 ~500ns），p_err_overflow 加速比提升至 ~3-4x；标注"错误路径 + Python baseline 短"双重结构性原因，转呈用户决策接受 < 10x。

**问题**：
- 直接违反用户硬约束 #5（禁止局部门禁）——用户决策事项 C（`总纲.md 行 147-151`）已明确"不豁免、不设局部门禁"
- 即便"4.x 整体承诺 ≥10x"（a_err_eof 达标），p_err_overflow 单点 < 10x 仍需用户显式决策，不能由 PM/ARCH 单方面接受
- 与 StopIf B1 类（`总纲.md §用户决策 事项 B`）的同档问题处理路径不一致——StopIf B1 选择了"路径 B（投资 Phase 5）"而非"接受下界"

**不推荐**：违反硬约束 #5，且与 StopIf B1 处理路径不一致。

#### 方案 B：更深重构（PrefixedArray 重构避免 FocusedSeq+Rebuild 路径）

**描述**：Python baseline 的 FocusedSeq+Rebuild 偷懒是 Python construct 2.10.70 自身的实现选择。如果重写 Rust 侧的 PrefixedArrayNode（不走 FocusedSeq+Rebuild 模拟路径），可能改变对照基准。

**问题**：
- **改变 Python baseline 等于改变 S-PERF 标准本身**——S-PERF 标准是"vs Python construct 2.10.70 原版"（`总纲.md §S-PERF 标准`），重写 PrefixedArray 改的是 Rust 侧，不改变 Python 原版
- 重构 PrefixedArrayNode 的 Rust 侧路径与 p_err_overflow 加速比无直接关系——Rs 端 build 路径已经 ~200ns，再优化空间有限
- PrefixedArrayNode 是 4.3 已 ACCEPTED 的子任务（`总纲.md 行 38`），重写需新开 Phase

**不推荐**：基于错误前提（"重构 Rust 侧能改变 Python baseline"），且属于 Phase 5+ 范围。

#### 方案 C：合并到 Phase 5（Struct + FFI 入口优化）

**描述**：
- 4.x 范围内对 p_err_overflow 实施 O1-O4 同款优化（与 a_err_eof 共用一套代码），实测后转呈用户决策
- p_err_overflow 的"达 10x"目标与 Phase 5（Struct + FFI 入口优化）合流：Phase 5 投资 StructNode + FFI 入口压缩（`总纲.md §用户决策 事项 B 路径 B`），同时收益：
  - Phase 1 B1（7.6x → ~12x）
  - Phase 4 StopIf B1（9.63x → ~15x）
  - **p_err_overflow 正常路径开销**（Rs 端 ~200ns → ~100ns，加速比从 ~3.31x → ~4.86x，仍 < 10x 但显著改善）

**优势**：
1. 不违反硬约束 #5（4.x 不豁免 p_err_overflow，只是承认单子任务范围内不可达 10x，需用户决策合流到 Phase 5）
2. 与 StopIf B1（路径 B 投资 Phase 5）处理路径一致
3. Phase 5 收益跨阶段，符合"通用规则"而非"局部豁免"

**问题**：
- Phase 5 完成后 p_err_overflow 可能仍 < 10x（最优估计 ~5x，受 Python baseline 4,864ns 限制）—— 需 Phase 5 完成时再转呈用户决策

### 2.4 推荐方案

**ARCH 推荐：方案 C（4.x 实施 O1-O4 + p_err_overflow 转 Phase 5 合流）**

**理由**（基于工程证据，避免 L-03 不对等证据）：

1. **方案 A 违反硬约束**：用户决策事项 C 已明确"不豁免、不设局部门禁"。PM/ARCH 无权在 4.x 内单方面接受 p_err_overflow < 10x。

2. **方案 B 基于错误前提**：S-PERF 标准对照 Python construct 2.10.70 原版，重构 Rust 侧 PrefixedArray 不改变 Python baseline。Python baseline 4,864ns 是 Python 自身实现特性（FocusedSeq+Rebuild 偷懒），不是 Rust 的问题。

3. **方案 C 与 StopIf B1 处理路径一致**：StopIf B1 类（9.63x）已选择"路径 B 投资 Phase 5"（`总纲.md §用户决策 事项 B`），p_err_overflow 同款处理保持一致性。Phase 5 的 Struct + FFI 入口优化对 p_err_overflow 正常路径有间接收益（Rs 200ns → ~100ns），虽不能让其单点达 10x，但显著改善。

4. **诚实承诺**：
   - 4.x 范围内：实施 O1-O4 优化，a_err_eof 达 10x，p_err_overflow 改善至 ~3-4x
   - p_err_overflow 达 10x：转 Phase 5，Phase 5 完成后重新评估；若 Phase 5 后仍 < 10x（受 Python baseline 限制），转呈用户最终决策

**PM 行动**：
- 4.x 子任务 VET 验证后，将 p_err_overflow 实测数据 + §2 工程上限分析转呈用户
- 用户决策点：是否接受"p_err_overflow 单点 < 10x 作为 Python baseline 短导致的固有边界，整体 4.x（含 a_err_eof）≥10x 视为达标"，或追加更深层重构（新开 Phase）

## §3 跨阶段模式沉淀建议（L-04 对策）

### 3.1 候选 ADR-019 评估

#### 3.1.1 候选模式

**模式名**：错误抛出 fast-path（绕过 Python `__init__` 直接构造异常实例）

**模式描述**：对于已知的内置 Python 异常类（在模块初始化时缓存 `Py<PyType>`），Rust 侧构造异常实例时用 CPython C API（`PyType_GenericAlloc` + `PyObject_SetAttr`）直接构造，绕过 `tp_init` 字节码执行；用户子类化的异常走原有 `call1` 慢路径。

#### 3.1.2 是否值得新 ADR（L-04 触发条件检查）

| 触发条件 | 是否满足 | 证据 |
|---------|---------|------|
| 该模式可能在 Phase 5+ 复用 | ✅ | Phase 5 Struct + FFI 入口优化可能涉及新错误路径；未来 Phase（如 Sequence / Union / Lazy）的错误抛出也会复用 |
| 该模式涉及架构层决策（非纯实现细节） | ✅ | 涉及 `unsafe` CPython C API 使用，需明确"何时使用 / 安全边界 / 兼容性策略"——超出 DEV 实现细节，属架构决策 |
| 该模式未被既有 ADR 覆盖 | ✅ | ADR-016（lazy path 错误传播）仅覆盖错误路径路径重建，不覆盖 PyErr 构造方式 |
| 该模式验证后可被未来 Phase 直接引用 | ✅ | 4.x 验证后，未来 Phase 任何错误抛出路径优化可直接引用此 ADR |

**评估结论**：**建议新 ADR-019**。

> **ADR 编号分配（PM 2026-07-28 决策）**：本 ADR 编号正式定为 **ADR-019 = 错误抛出 fast-path（绕过 Python `__init__` 直接构造异常实例）**，由 ARCH 在 4.x ACCEPTED 时起草。META-CI-1 设计文档的"CI 冒烟门禁方法学"另分配 ADR-020，互不冲突。

#### 3.1.3 ADR-019 草案要点（4.x ACCEPTED 时由 ARCH 落地）

```
id: ADR-019
status: proposed  → accepted（4.x ACCEPTED 时）
phase: 4
decides: "内置 Python 异常类的错误抛出走 fast-path（绕过 __init__），用户子类化异常走慢路径"
```

**Decision（决策内容）**：
1. `From<ConstructError> for PyErr` 实现中，对 `ExceptionClasses` 缓存的 13 个内置异常类启用 fast-path（O3）
2. fast-path 用 `pyo3::ffi::PyType_GenericAlloc` + `PyObject_SetAttr` 构造异常实例，跳过 `tp_init` 字节码
3. 用户子类化的异常（**按 4.x-REV OBS-2 修订**：用指针相等比较 `cls.as_ptr() == builtin_cls.as_ptr()` 检测"cls 是否确切等于内置类"；`PyType_IsSubtype` 是子类关系检查，任何子类都返回 true，不适用于"是否确切类型"判定）自动降级走 `call1` 慢路径
4. `args` 字段设为 `(message,)`（非预格式化 full string），依赖 Python 侧重写的 `__str__` 处理格式化

**Consequences（后果）**：
- 正面：错误抛出开销从 ~1,200-1,500ns 降至 ~480-580ns（节省 ~62%）；a_err_eof 等错误路径场景加速比显著提升
- 负面：用户子类化 ConstructError 重写 `__init__` 时不被调用（fast-path 跳过）—— 已通过"自动降级到慢路径"缓解
- 中性：`pickle` / `repr` 依赖 `args` 字段，行为与现状一致（`args = (message,)`）

**Relations（关系）**：
- 引用证据：本设计 §1.3 O3 + 4.x VET 性能验证报告
- 关联教训：`harness/experiences.md#L-04`（跨阶段模式未沉淀）
- 关联 ADR：ADR-016（lazy path 错误传播，与本 ADR 形成"错误路径优化系列"）
- 实施：4.x / CODING

### 3.2 与 ADR-016（lazy path 错误传播）的关联

ADR-016 决策："成功路径不维护 Path 栈，子节点 Err 时重建路径"。

ADR-019 与 ADR-016 形成**错误路径优化的两个互补维度**：

| 维度 | ADR-016（已 accepted） | ADR-019（候选） |
|------|----------------------|----------------|
| 优化阶段 | 错误抛出**之前**（Rust 内部 path 重建） | 错误抛出**之时**（Rust → Python PyErr 构造） |
| 优化对象 | `ConstructError::push_path_segment` / `push_path_index` | `From<ConstructError> for PyErr` |
| 收益场景 | 嵌套 Struct + Array 错误路径（4.7 已实施） | 所有错误抛出场景（4.x 实施） |
| 组合效果 | 单独使用：节省 path 维护开销 | 与 ADR-016 叠加：错误路径从 path 重建 + PyErr 构造双维度优化 |

**协同验证**：4.x 性能验证应同时测量"a_err_eof 在 ADR-016 + ADR-019 双重优化下的加速比"，验证两者无相互冲突。

## §4 子任务分解建议

### 4.1 拆分评估

**评估维度**：

| 维度 | 拆分（4.x.1 + 4.x.2） | 合并（单 4.x） |
|------|----------------------|---------------|
| 实现侧 | O1-O4 是单个文件（error.rs）的一组修改，无法物理拆分 | ✅ 一组 DEV 一次实施 |
| 验证侧 | a_err_eof / p_err_overflow 验证可并行，但共用同一份优化代码 | ✅ VET 同时验证，节省一轮 VET 周期 |
| 风险隔离 | O3 绕过 __init__ 风险高，可单独验证 | ⚠️ 单点失败可能导致整体回滚 |
| 用户决策点 | p_err_overflow 需转呈用户，与 a_err_eof 验证独立 | ✅ 合并但保留独立决策点 |

### 4.2 推荐方案

**ARCH 推荐：合并为单 4.x 子任务，内部分两个验证里程碑**

**理由**：
1. O1-O4 是 `error.rs` 单文件的一组协同修改，物理拆分无意义
2. a_err_eof 与 p_err_overflow 共用同一份优化代码（`From<ConstructError> for PyErr`），分开验证增加不必要周期
3. 合并后 VET 一次性验证两个场景，节省一轮 VET 时间
4. 风险通过 O3 的"自动降级到慢路径"机制缓解（§1.3 O3 风险缓解）

### 4.3 子任务内部里程碑

```
4.x [错误路径 D 类优化]
├─ M1: ARCH 设计完成（本文档 + DESIGN_REVIEW） → 转 CODING
├─ M2: DEV 实施 O1-O4（修改 error.rs） → 转 CODE_REVIEW
├─ M3: VET 性能验证（同会话 Controlled A/B Test）
│   ├─ M3.1: a_err_eof 达标验证（≥10x，阳/阴性对照）→ 转 ACCEPTED
│   └─ M3.2: p_err_overflow 实测 + §2 工程上限分析 → 转 PM 推送用户决策
└─ M4: PM ACCEPTED（a_err_eof 达标）+ p_err_overflow 用户决策点 → 转 AUDITED
```

### 4.4 出口判据

| 场景 | 出口判据 | 处置 |
|------|---------|------|
| a_err_eof | 加速比 ≥10x（同会话 Controlled A/B Test，≥5 次采样均值） | PM ACCEPTED |
| a_err_eof（反例 R1 触发） | 加速比 <10x 但 O3 已实施 | 进 §1.4.4 R1 反例流程；若 R1a/R1b/R1c 仍不达，转呈用户决策 |
| p_err_overflow | 实施优化后实测加速比（预期 ~3-4x） + §2 工程上限分析 | PM 转呈用户决策（方案 C 合流 Phase 5 或追加重构） |
| ADR-019 | O3 验证生效后 | ARCH 落地 ADR-019（status: accepted） |

## §5 测试策略

### 5.1 功能测试（错误抛出兼容性）

**目标**：验证 O3 绕过 `__init__` 不破坏 Python 用户的异常使用模式。

| 测试用例 | 期望行为 | 验证方法 |
|---------|---------|---------|
| T1：`except StreamError as e: e.path; e.message` | path 和 message 属性正确设置 | `pytest` 单元测试 |
| T2：`str(e)` | 返回 `"Error in path {}\n{}".format(path, message)` 或 `message` | `pytest` 单元测试，对照 Python construct 行为 |
| T3：`repr(e)` | 不破坏（如 `StreamError('Error in path root\n...')`） | `pytest` 单元测试 |
| T4：`e.args` | 等于 `(message,)`（fast-path）或 `(full,)`（慢路径） | `pytest` 单元测试，标注两种路径差异 |
| T5：`pickle.dumps(e); pickle.loads(...)` | 不破坏（依赖 args + message + path） | `pytest` 单元测试 |
| T6：用户子类化 `class MyError(StreamError): def __init__(self, ...): ...` | Rust 抛 MyError 时 `__init__` 被调用（走慢路径） | `pytest` 集成测试 |
| T7：13 个内置异常类的 fast-path 覆盖 | 全部走 fast-path（性能验证） | `pytest` 性能测试 |
| T8：StopField 哨兵（不走 PyErr 路径） | 行为不变（O3 不影响） | 回归测试 |

### 5.2 性能测试（performance-gate SKILL Checkpoint 4）

#### 5.2.1 测量场景

| 场景 | 类型 | 预期 |
|------|------|------|
| a_err_eof parse | 阳性对照（O3 主受益） | 加速比 ≥10x |
| p_err_overflow build | 阳性对照（O3 主受益） | 加速比 ~3-4x（结构性限制） |
| i02_idx_n100 parse | 阴性对照（与错误抛出无关） | 加速比不变（~10x），验证环境漂移幅度 |
| 正常路径全场景 | 阴性对照（无错误抛出） | 加速比不变，验证 O3 无副作用 |

#### 5.2.2 Controlled A/B Test 协议（L-09 对策）

```bash
# A. O3 off（fast-path 关闭）
git stash push -- construct-rs/src/error.rs  # 或 feature flag
cargo build --release && maturin develop --release
python experiments/phase4_perf_investigation.py a_err_eof  # 5 次

# B. O3 on（fast-path 开启）
git stash pop
cargo build --release && maturin develop --release
python experiments/phase4_perf_investigation.py a_err_eof  # 5 次

# C. 交替 A→B→A→B→A→B 至少 3 轮（共 6 次测量，每种条件 3 次）
# D. 阴性对照：i02 在 A 与 B 下各测 3 次，应无差异（差异 <0.3x 为环境漂移）
```

**统计判据**：
- a_err_eof A vs B 差异 >0.5x → O3 真实生效
- i02 A vs B 差异 <0.3x → 环境漂移幅度可接受
- a_err_eof B 加速比均值 ≥10x → 达标

#### 5.2.3 测量环境标注（强制）

报告必须包含：
- Python 版本（如 3.13.x）
- venv 重建状态
- 测量时段（如 2026-07-28 14:00-15:00）
- CPU 型号 + OS 版本
- crate 编译模式（`--release` + LTO 配置）

### 5.3 性能验证口径

| 项 | 要求 |
|----|------|
| 迭代次数 | ≥1000（per measurement） |
| 重复次数 | ≥5（取 min，统计 min/max/mean/stddev） |
| 对照基线 | Python construct 2.10.70 原版（不变） |
| 跨时段对比 | 必须做同会话 Controlled A/B Test，不可跨时段单次对比（L-09） |

## §6 边界条件清单

| 场景 | 输入 / 条件 | 预期行为 |
|------|------------|---------|
| BC1：单元测试无 GIL 初始化 | `EXCEPTIONS.get(py)` 返回 None | 回退到 `PyValueError::new_err(err.full_message())`（现状不变） |
| BC2：模块初始化失败 | `init_exception_classes` 失败 | 模块加载错误（现状不变） |
| BC3：用户子类化异常 | `cls` 不是 13 个内置类 | 自动降级到 `call1` 慢路径（O3 兼容性） |
| BC4：错误无 path（Compilation / UnresolvedReference） | `err.path()` 返回 None | O3 设 `path = None`，`args = (message,)` |
| BC5：错误无单一 message（ExprType / ExprFieldMissing / ExprStackUnderflow / StopField） | `err.message()` 返回 None | O3 用 `err.to_string()` 作为 message（现状不变） |
| BC6：fast-path 失败（`PyObject_SetAttr` 失败） | 极端情况（如 Python 端 monkey patch） | 回退到原有 `call1` 慢路径 |
| BC7：StopField 哨兵 | GreedyRangeNode / StructNode 捕获 | 不走 PyErr 路径，O3 不影响 |
| BC8：多线程抛错 | 多个 Python 线程同时触发错误 | fast-path 线程安全（无共享状态，每次 `tp_alloc` 新实例） |
