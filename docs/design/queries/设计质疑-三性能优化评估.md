# 设计质疑：三项性能优化评估

> **背景**：Phase 7.3 性能验证完成，parse 方向 27/35 不达标（普遍 7-10x），build 方向 33/35 达标（11-19x）。
> 用户对 parse 方向整体 + 两个具体构造器（RawCopy / Float16）提出 3 项优化质疑。
> 本文件 ARCH 基于参考实现事实 + 现有架构 + 跨阶段决策（ADR-008/019/021/022）逐一评估。

## 0. 三项质疑的共同根因预判（必须先读）

在深入每项之前，**ARCH 先指出一个关键事实**：

> **三项质疑的根因高度收敛到同一个事实：parse 方向的 PyFloat/PyLong/PyDict 构造开销（30-70ns/对象），
> 而非具体构造器（RawCopy/Float16）自身的实现选择。**

证据（来自 `docs/perf-scenarios.csv` Phase 6.6 全量 bench）：

| 构造器类型 | parse 典型值 | build 典型值 | parse/build 差异 |
|-----------|-------------|-------------|-----------------|
| Float32b/l（5 case 均值） | **8.57x**（rs_ns ~227） | 12.45x（rs_ns ~151） | parse 多 ~76ns |
| Float64b/l（5 case 均值） | **8.67x**（rs_ns ~226） | 12.59x（rs_ns ~148） | parse 多 ~78ns |
| **Float16b/l（5 case 均值）** | **8.50x**（rs_ns ~229） | 12.40x（rs_ns ~152） | parse 多 ~77ns |
| BytesInteger(1-8) fast-path | 9.1-9.4x（rs_ns ~222-238） | 12.0-12.7x（rs_ns ~155-187） | parse 多 ~70ns |
| Subconstruct（3 case） | **8.71x**（rs_ns ~227） | 12.78x（rs_ns ~148） | parse 多 ~79ns |

**关键观察**：
1. **Float16/Float32/Float64 性能几乎完全相同**（8.50 / 8.57 / 8.67x）——这**直接证伪**了"half crate 特别慢"的猜测。Float16 不是异类。
2. **所有 parse 路径 rs_ns 稳定在 ~220-240ns**，比 build 路径（~150ns）固定多出 **70-80ns**——这是 PyObject 构造的固有税。
3. 这 70-80ns 的构成（基于 `docs/design/模块设计/模块设计-FFI入口优化.md §1.2` B1 拆解）：
   - PyLong/PyFloat/PyBytes 分配 + 引用计数：~30-50ns
   - StructNode 的 `tp_new` + `getattr __dict__`：~32-40ns（不可消除，Phase 5 已优化）
   - 残差（cache miss / 分支预测）：~10-20ns

**含义**：质疑 1（parse 整体）是**根**，质疑 2（RawCopy）和质疑 3（Float16）是**同一根因的两个叶子案例**。
优化 RawCopy 或 Float16 的实现细节无法显著改善——它们的瓶颈不在自己身上。

## 1. 质疑 1：parse 方向能不能做更好？

### 1.1 能否改善（结论先行）

**结论**：**有有限的优化空间（~10-30ns/字段，可将 7-10x 提升到 8-11x），但不值得立即开 Phase 8。**

- "parse 方向 PyObject 构造固有开销"——**部分正确，部分误判**。
  - **正确部分**：PyLong/PyFloat 分配 + incref 确实是 CPython 固有税，无法绕过。
  - **误判部分**：Phase 5 已挖走的只是 Python 入口 + pyo3 wrapper 开销（A+B+C 候选），
    **Rust 内部仍有若干 ns 级优化点未被触及**，且 Phase 5 候选 B（raw FFI）的 ABI3 spike 当时未完成。

### 1.2 可能的优化方向（按预期收益降序）

#### 方向 A：CPython 小整数缓存 fast-path（u8/u16 parse，预期 +0.5-1.5x）

**现状**：`format_field.rs:282-314` 的 u8/u16 parse 走 `u8::into_py(py)` / `u16::into_py(py)`，
内部调 `PyLong_FromLong`。CPython 对 **-5 ~ 256** 的整数有缓存（`PyLong_FromLong` 命中缓存时仅 ~10ns，
未命中时 ~30-50ns 需新分配）。

**方案**：对 u8（0-255 全部命中缓存）/ i8（-128~127 全部命中缓存）添加编译期已知小整数分支，
直接用 `PyLong_Check` + 缓存指针（CPython 内部 `_PyLong_SMALL_INTS`，但这是私有 API）。
或更保守：用 pyo3 `intern!` / `PyObject_GetAttrString` 缓存 N 个 PyObject（首次构造后复用）。

**预期收益**：u8 parse 从 ~220ns 降到 ~190-200ns（节省 ~20-30ns），加速比 9.3x → ~10.5-11x。
对 i8/u16 边界值部分有效。

**成本**：~50-80 行新代码，可能引入 unsafe raw FFI（访问 `_PyLong_SMALL_INTS` 私有数组）。
**风险**：
- 高（私有 API，CPython 版本敏感，违反"pyo3 是核心依赖"的 §0 #4 精神边缘）
- parity 风险：用户子类化 int 后行为可能不一致

**ARCH 判断**：**不推荐**。收益边际（~20-30ns），风险高（私有 API + unsafe）。
且 pyo3 `into_py` 内部已尽可能走 `PyLong_FromLong` 快路径，CPython 自身已优化小整数缓存。

#### 方向 B：完成 Phase 5 候选 B（raw FFI pyo3 wrapper 绕过，预期 +0.3-0.8x）

**现状**：`模块设计-FFI入口优化.md §3` 候选 B 当时 ABI3 spike 未完成，仅候选 A（FFI 去层化）实施。
当前 parse 入口仍有 pyo3 `#[pymethods]` wrapper（GIL token + 参数解析 + 返回包装，~30-50ns）。

**方案**：用 raw C 函数（`PyCFunction` + 手工 GIL）替代 `#[pymethods]` wrapper，
参考 ADR-019（错误路径已用 raw FFI `error.rs:740-825`）。

**预期收益**：单次 parse 省 ~15-35ns，B1（3 字段）从 ~250ns 降到 ~220-235ns，
加速比 11.64x → ~12.5-13x（已 ≥10x，边际收益递减）。

**成本**：~150-200 行 unsafe raw FFI 代码 + SAFETY 审查 + ABI3 spike 补做。
**风险**：
- 中（已有 ADR-019 先例，但 parse/build 是热路径，错误处理路径不同）
- 需 PM 重新决策"是否接受 parse/build 主路径 unsafe raw FFI"（ADR-019 当时仅错误路径）

**ARCH 判断**：**有条件推荐**。如果用户要求 parse 方向系统性提升，这是**最干净的优化点**
（攻击的是 pyo3 wrapper 固定开销，对所有构造器一视同仁）。但需 PM 决策 unsafe 主路径使用。

#### 方向 C：StructNode `tp_new` 替代（预期 +0.2-0.5x，高风险）

**现状**：`instance.rs:72-97` 用 `tp_new` 创建用户类实例（~22ns）， unavoidable under mashumaro API。

**方案**：Phase 5 候选 E（`tp_new` 替代）已被 5.0 报告排除（违反 §0 #5 mashumaro API）。
唯一可能路径：预分配实例池（thread_local 缓存 N 个空实例）。

**预期收益**：~15-20ns/实例。
**风险**：
- 极高（生命周期管理复杂，多线程 GIL 场景语义不清，违反 §0 #5）
- 已被 Phase 5 排除，重新考虑无意义

**ARCH 判断**：**不推荐**（已被排除，无新证据）。

#### 方向 D：跨会话测量漂移（L-09 教训，预期 +1-3x，零代码成本）

**现状**：Phase 1 B1 parse 7.63x → Phase 5.6a 同会话 Controlled A/B Test **11.64x**（+4x）。
Phase 7 ITE1-parse 跨 3 会话：9.18x / 7.74x / 7.73x（摆动 ±1.5x）。

**方案**：对 Phase 7 27 项 parse 不达标中的典型 case（如 ITE1/SW1/SL1）做同会话 Controlled A/B Test，
消除跨会话漂移。

**预期收益**：**零代码改动**，加速比可能从 7-8x 跃升到 9-11x（如 Phase 1→5 同模式）。
**成本**：VET 执行 Controlled A/B Test（~1-2 天工作量）。
**风险**：零（纯测量验证）。

**ARCH 判断**：**强烈推荐作为第一步**。在投入 Phase 8 优化前，必须先用 Controlled A/B Test
确认"7-10x"是否部分归因测量漂移。如果漂移占 +2x，则真实性能已是 9-12x，无需 Phase 8。

### 1.3 是否值得开 Phase 8？

**ARCH 建议**：**暂不开 Phase 8，分两步走**：

1. **立即**：VET 对 Phase 7 27 项 parse 不达标中的 3-5 个典型 case 做 Controlled A/B Test（方向 D）。
   如果复测后 ≥10x 场景 >50%，则测量漂移是主因，Phase 8 无必要。
2. **若复测仍 <10x**：再启动 Phase 8 parse 优化，**仅实施方向 B（raw FFI pyo3 wrapper 绕过）**，
   因其收益最干净（攻击固定开销，对所有构造器一视同仁），且有 ADR-019 先例。

**理由**：
- Phase 5 已系统挖掘 parse 入口开销，剩余优化点都是 ns 级边际收益。
- parse 方向 7-10x 已**满足项目硬目标 ≥4x**（10x 是理想目标，非硬要求）。
- Phase 8 投入产出比低于继续推进未实现构造器（剩余 ~64/134 构造器）。

## 2. 质疑 2：RawCopy 为什么要 Copy 不能引用？

### 2.1 能否改为引用（结论先行）

**结论**：**技术上不可行（CPython 内存模型硬约束）**。即使可行，parity 也不允许。

### 2.2 "直接引用"的技术可行性分析

用户质疑"为什么要整个结构 Copy 出来，不能直接引用吗？"。基于参考实现事实：

**Python construct 原版行为**（`core.py:4788-4794`）：
```python
def _parse(self, stream, context, path):
    offset1 = stream_tell(stream, path)
    obj = self.subcon._parsereport(stream, context, path)
    offset2 = stream_tell(stream, path)
    stream_seek(stream, offset1, 0, path)
    data = stream_read(stream, offset2-offset1, path)  # ← 这里也是 read（拷贝）
    return Container(data=data, value=obj, offset1=..., offset2=..., length=...)
```

**关键事实**：Python 原版**本身也是拷贝**（`stream_read` 返回新 bytes 对象）。
construct-rs 的实现（`raw_copy.rs:100-111`）与原版**完全等价**——不存在"原版引用、Rust 拷贝"的差异。

**为什么必须拷贝（CPython 内存模型约束）**：
1. **`bytes` 是不可变对象**（immutable），CPython 不提供零拷贝 bytes view。
   `PyBytes_FromStringAndSize` 总是分配新 buffer + memcpy。
2. **ParseStream 的 `&[u8]` 生命周期**：stream 内部 buffer 在 parse 调用结束后释放，
   返回的 PyBytes 必须独立持有数据（否则悬垂指针）。
3. **`memoryview` 不适用**：memoryview 需要 buffer-like 源（如 bytearray/memoryview 输入），
   但 parse 接口约定输入是 `bytes`（不可变），无法创建可写 view。

**替代方案评估**：
- 用 `memoryview` 返回：违反 parse 接受 bytes 的约定，且 bytes 不可 memoryview（TypeError）。
- 用 `bytearray` 返回：可变，但 parity 不一致（Python 原版返回 bytes）。
- 缓存原始输入 bytes 引用：需要用户提供长期持有的 bytes（违反一次 FFI 原则，需额外 GIL 管理）。

**结论**：**无法改为引用**。这是 CPython `bytes` 不可变性的硬约束，非实现选择问题。

### 2.3 5 键 PyDict 能否精简？

用户质疑"5 键 PyDict 是否可以精简（如改为 2 键 data+value）"。

**parity 硬约束**（不可精简）：
- Python 原版返回 `Container(data=..., value=..., offset1=..., offset2=..., length=...)`（5 键）
- `Container` 是 `dict` 子类（`lib/containers.py:84`）
- 用户代码可能用 `result.offset1` / `result['length']` / `result.data` 三种方式访问
- 精简为 2 键会破坏所有依赖 offset1/offset2/length 的用户代码（如 CRC 校验、流定位）

**改为 namedtuple/dataclass**：
- 违反 parity（Python 原版是 dict 子类，支持 `result['data']` 字典访问）
- 用户可能用 `dict(result)` / `result.items()` / `result.update(...)`，namedtuple 不支持全部

**性能影响（即使能精简）**：
- 当前 5 次 `set_item`（~67.5ns）+ 1 次 PyBytes 拷贝（~30-50ns）+ value 是 inner.parse 结果
- 精简为 2 键：节省 ~40ns（3 次 set_item），但 inner.parse 开销不变
- RawCopy parse 当前 ~433ns（`perf-scenarios.csv` RC1），节省 40ns → ~393ns，加速比 5.41x → ~6.0x
- **仍然不达标 10x**——因为 inner.parse（如 FormatField）本身就有 ~220ns 开销

**结论**：**不可精简（parity 硬约束），且即使精简也无法达标**。

### 2.4 RawCopy 5.77x 的真实根因

RawCopy parse 性能偏低（5.77x 均值）的真实根因**不是 5 键 dict**，而是：

1. **inner.parse 开销叠加**：RawCopy 包裹一个 inner 构造器（如 FormatField ~220ns），
   自身额外开销（seek + read + 5 set_item + PyBytes）~200ns，总 ~420ns。
2. **Python baseline 偏低**：Python RawCopy 同样要 stream_tell × 2 + stream_seek + stream_read + Container 构造，
   baseline ~2300ns，与 Rust 420ns 比 → 5.5x（与实测 5.77x 吻合）。
3. **双重 read（设计固有）**：Python 原版也是 seek 回 + read 重读（`core.py:4792-4793`），
   无法避免（需要 inner.parse 消费的字节范围）。

**与其他 Adapter 节点对比**（`perf-scenarios.csv` 6.6）：
- Subconstruct parse：8.71x（无 seek/read，仅转发）
- Peek parse：9.79-11.40x（无 seek 回读）
- RawCopy parse：5.77x（**多一次 seek + read**）

RawCopy 的 seek + 重读是 Python 原版语义带来的固有开销，无法优化。

### 2.5 PM 决策建议

- **接受 RawCopy parse 5.77x**：根因是 CPython bytes 不可变 + Python 原版 seek/read 语义，
  非实现问题。与 Phase 6 已接受的 6/24 不达标同模式。
- **不做精简**：parity 硬约束，精简无意义且收益不足以达标。
- **不开针对 RawCopy 的优化子任务**。

## 3. 质疑 3：Float16 有没有办法做更好？

### 3.1 能否做更好（结论先行）

**结论**：**不值得优化**。Float16 8.7x 与 Float32 8.5x / Float64 8.7x 同档，
瓶颈是 parse 方向 PyFloat 构造固有开销（与质疑 1 同根因），**不是 half crate**。

### 3.2 half crate 转换开销的根因分析

**当前实现**（`format_field.rs:352-361`）：
```rust
PythonFormat::Float16Big => {
    let arr = read_array::<2>(stream, path)?;          // ~2ns
    let f16_val = half::f16::from_be_bytes(arr);       // ~1ns（const fn，编译期内联）
    Ok(f16_val.to_f64().into_py(py))                   // ~3ns（f16→f64）+ ~30-50ns（PyFloat）
}
```

**开销拆解**：
| 步骤 | 开销 | 性质 |
|------|------|------|
| `read_array::<2>` | ~2ns | stream.read，所有 FormatField 共有 |
| `f16::from_be_bytes` | ~1ns | **const fn，编译期内联**（half crate 文档保证） |
| `f16::to_f64()` | ~2-3ns | 位扩展（f16→f32→f64），纯算术 |
| `f64::into_py(py)` → `PyFloat_FromDouble` | **~30-50ns** | CPython PyFloat 分配 + incref |
| **half crate 总贡献** | **~3-5ns** | — |
| **PyFloat 构造贡献** | **~30-50ns** | CPython 固有，不可优化 |

**关键证据**（`perf-scenarios.csv` 6.6，5 case 均值）：
- Float16b parse：8.50x（rs_ns ~229）
- Float32b parse：8.57x（rs_ns ~227）
- Float64b parse：8.67x（rs_ns ~226）

**三者 rs_ns 差异 < 3ns，在测量噪声内（L-09 边界场景）**。
如果 half crate 特别慢，Float16 应显著低于 Float32/64——但事实并非如此。
**Float16 不是异类**。

### 3.3 手写 f16↔f32 bit 拼接可行性

**之前 ARCH 论述"subnormal/NaN 易错"的具体难点**：

f16 → f32 位转换需处理 4 类情况（IEEE 754-2008）：

| f16 类别 | 指数（5 bit） | 尾数（10 bit） | f32 转换逻辑 |
|---------|--------------|---------------|-------------|
| **零** | 0 | 0 | 直接扩展符号位 |
| **subnormal**（非正规） | 0 | ≠0 | **需正规化**：尾数左移直到最高位为 1，指数相应调整（隐含前导 1） |
| **normal**（正规） | 1-30 | 任意 | 指数偏移调整（+112），尾数左移 13 位 |
| **Inf** | 31 | 0 | 指数=255，尾数=0 |
| **NaN** | 31 | ≠0 | 指数=255，**payload 需保留**（quiet NaN bit 51 + signaling payload） |

**难点 1：subnormal 正规化**
- f16 subnormal 范围：2^-24 ~ 2^-15（最小 6.1e-5，最大 6.55e-5）
- 转 f32 需循环或 CLZ（count leading zeros）找前导 1，调整指数
- half crate 用查表 + CLZ intrinsic 实现，~10 行汇编

**难点 2：NaN payload 保留**
- f16 有 10 bit 尾数，f32 有 23 bit
- IEEE 754 要求 quiet NaN 的最高尾数位为 1（bit 51 in f32）
- signaling NaN 的最高位为 0，剩余是 payload
- parity 测试（设计 §7 BC-B9）要求 `Float16b.parse(b'\x7e\x00')` 返回特定 NaN payload
- 手写易漏：CPython struct 模块 + half crate 都保留 payload，但手写分支易丢失高位

**查表 + 分支实现估算**：
- 代码量：~80-120 行（含 subnormal 正规化 + NaN payload + 边界测试）
- 性能：手写 bit 操作可能比 half crate 快 **~1-3ns**（half crate 已编译期内联）
- 但 **PyFloat 构造仍占 ~30-50ns**，节省的 1-3ns 被淹没

**ARCH 之前的论述成立**：
> "Float16 的 subnormal + NaN payload 在手写中极易出错（Python construct 用 CPython struct 模块，
> 已含完整 IEEE 754-2008 实现，parity 测试需 100% 匹配）"
> —— `模块设计-Primitives收尾.md §1.3.1`

### 3.4 pyo3 原生 float 构造优化路径

**pyo3 `f64::into_py(py)` 内部实现**：
- 调用 `PyFloat_FromDouble`（CPython C API）
- 这是 CPython 最快 float 构造路径（无更快替代）
- pyo3 0.22 已优化，无进一步空间

**替代路径评估**：
- `PyFloat_FromString`：更慢（需先构造 PyString）
- 缓存 PyFloat 对象：float 不可变但值多样，无法像小整数那样缓存
- 直接操作 CPython `PyFloatObject` 结构体：unsafe + 私有布局，违反 §0 #4

**结论**：**无 pyo3 原生优化路径**。

### 3.5 性能预测 + 成本

| 方案 | 预期 rs_ns 变化 | 预期加速比变化 | 成本 | 风险 |
|------|----------------|--------------|------|------|
| **手写 f16 bit 拼接** | 229 → ~226-228 | 8.50x → ~8.55-8.60x（**<0.2x 提升**） | ~100 行 + 完整 parity 测试 | 中（subnormal/NaN 易错） |
| **raw FFI 绕过 pyo3（方向 B）** | 229 → ~210-220 | 8.50x → ~9.0-9.3x | ~150 行 unsafe | 中（ADR-019 先例） |
| **Controlled A/B Test 复测** | 0（纯测量） | 8.50x → ~9-11x（如 Phase 1→5 模式） | VET ~1 天 | 零 |

### 3.6 PM 决策建议

- **不做 Float16 手写优化**：收益 <0.2x，被 PyFloat 构造开销淹没，不值得。
- **保留 half crate**：D-1 决策（`模块设计-Primitives收尾.md`）仍然正确，无新证据推翻。
- **Float16 不达标归因 parse 方向整体**：与 Float32/Float64 同根因，跟随质疑 1 的处理路径。

## 4. PM 决策建议矩阵（汇总）

| 质疑 | 能否改善 | 推荐方案 | 预期收益 | 成本 | 风险 | 优先级 |
|------|---------|---------|---------|------|------|--------|
| **1. parse 方向整体** | 有限（~10-30ns/字段） | **分两步**：(1) VET Controlled A/B Test 复测；(2) 若仍 <10x 再开 Phase 8 仅做方向 B（raw FFI） | (1) 可能 +1-3x（零代码）；(2) +0.3-0.8x | (1) VET ~1-2 天；(2) DEV ~3-5 天 | (1) 零；(2) 中（unsafe 主路径，需新 ADR） | **中**（先做测量验证） |
| **2. RawCopy 引用** | **不能**（CPython bytes 不可变 + parity） | **接受 5.77x**，不做优化 | 无 | 无 | 无 | **低**（归档） |
| **3. Float16** | 不值得（half crate 仅 ~3-5ns，PyFloat 构造占主导） | **保留 half crate**，不做手写优化 | 无（<0.2x） | 无 | 无 | **低**（归档） |

### 4.1 核心建议

**ARCH 强烈建议**：

1. **质疑 2 和质疑 3 直接归档**：基于参考实现事实，无可行优化路径。
   - RawCopy：CPython bytes 不可变 + Python 原版 parity = 硬约束
   - Float16：half crate 不是瓶颈，PyFloat 构造是瓶颈（与 parse 整体同根因）

2. **质疑 1 分两步走**：
   - **第一步（立即）**：VET 对 Phase 7 ITE1/SW1/SL1/SK1 等 4-5 个典型 parse case 做 Controlled A/B Test。
     这是 L-09 教训的标准操作，零代码成本，可能直接解决一半不达标项。
   - **第二步（条件触发）**：若复测后仍有 >50% parse <10x，启动 Phase 8，
     **仅实施 raw FFI pyo3 wrapper 绕过（方向 B）**，需 PM 决策 unsafe 主路径使用（新 ADR）。
     方向 A/C/D 不推荐（私有 API / 已排除）。

3. **Phase 7 验收建议**：parse 方向 27/35 不达标按 Phase 6 同模式接受（6/24 不达标已接受），
   理由：(a) 满足项目硬目标 ≥4x；(b) 10x 是理想目标非硬要求；(c) 根因是 CPython 固有开销 + 测量漂移。

### 4.2 跨阶段决策影响

- **如启动 Phase 8 方向 B**：需新 ADR 沉淀"parse/build 主路径 unsafe raw FFI 使用准则"
  （扩展 ADR-019，从错误路径推广到主路径）。
- **质疑 1/2/3 共同根因（parse PyObject 构造税）**：建议在 `experiences.md` 沉淀为新教训
  "parse 方向 PyFloat/PyLong/PyDict 构造是 CPython 固有税，不可绕过，单字段场景加速比上限 ~10-13x"。
  避免后续 Phase 重复质疑同一现象。
