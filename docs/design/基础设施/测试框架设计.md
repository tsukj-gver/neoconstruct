### 0.3 §0 原则对照（基础设施类，L-01 对策）

本设计是测试基础设施，**不直接处理 parse/build 数据流**，但子进程隔离涉及 FFI 安全边界：

| §0 原则 | 本设计如何满足 |
|---------|--------------|
| #1 一次 FFI | N/A（测试代码不进入运行时数据流；子进程隔离是"测试视角"的 FFI 隔离） |
| #2 无中间表示层 | normalize helper 仅做"比较前规范化"，不引入运行时中间类型。**澄清（v2，REV 轻微-7）**：normalize 引入的 `{"__bytes__": hex}` / `"__NaN__"` 等中间形态**仅存在于测试子进程的 JSON 输出**（用于跨 rs/py 实现比对），**不进入 construct-rs 的 parse/build 运行时数据路径**，故不违反 §0 #2 |
| #3 输入输出侧无 trait 抽象层 | N/A |
| #4 pyo3 核心依赖 | N/A（测试不与 pyo3 直接交互） |
| #5 mashumaro 式 API | parity case 范例（§5.1）用 `@dataclass class P(StructMixin)` 用户面 |
| #6 enum_dispatch 静态分派 | N/A |
| #7 Result<T, ConstructError> | 子进程通过 returncode + stderr 上报错误，主进程包装为 RuntimeError |
| #8 Stream 抽象纯 Rust 内部 | N/A |

```python

import os
import sys
from pathlib import Path
import pytest

# ===== 保留：sys.path 操纵（现有 26 行） =====
_CRS_ROOT = os.path.abspath(os.path.join(os.path.dirname(__file__), "..", "python"))
if _CRS_ROOT not in sys.path or sys.path[0] != _CRS_ROOT:
    sys.path.insert(0, _CRS_ROOT)
for _key in list(sys.modules):
    if _key == "construct" or _key.startswith("construct."):
        del sys.modules[_key]

# ===== 新增：路径常量（供 fixture 与 helper 复用） =====
_TESTS_DIR = Path(__file__).resolve().parent
_PROJECT_ROOT = _TESTS_DIR.parent                  # construct-rs/
_CRS_PYTHON_DIR = _PROJECT_ROOT / "python"         # construct-rs/python/

# 子进程隔离用的 venv 解析（与 test_phase4_parity.py 一致）
_VENV_ROOT = Path(r"<opencode-temp>")
_DEFAULT_RS_PYTHON = _VENV_ROOT / "crs_venv" / "Scripts" / "python.exe"
_DEFAULT_PY_PYTHON = _VENV_ROOT / "crs_venv_py" / "Scripts" / "python.exe"


# ===== 新增：session 级 fixtures =====

@pytest.fixture(scope="session")
def crs_python_dir() -> str:
    """construct-rs/python/ 目录绝对路径（子进程 sys.path 注入用）。"""
    return str(_CRS_PYTHON_DIR)


@pytest.fixture(scope="session")
def rs_python() -> str:
    """CRS venv 的 python.exe（含 construct-rs wheel）。
    
    解析顺序：
      1. 环境变量 CRS_PYTHON（CI 覆盖用）
      2. 默认 venv 路径 _DEFAULT_RS_PYTHON
      3. fallback sys.executable（最后手段，可能两个 construct 冲突）
    """
    env = os.environ.get("CRS_PYTHON")
    if env and Path(env).exists():
        return env
    if _DEFAULT_RS_PYTHON.exists():
        return str(_DEFAULT_RS_PYTHON)
    return sys.executable


@pytest.fixture(scope="session")
def py_python() -> str:
    """PC venv 的 python.exe（含 Python construct 2.10.70）。
    
    解析顺序同 rs_python，环境变量名 PC_PYTHON。
    """
    env = os.environ.get("PC_PYTHON")
    if env and Path(env).exists():
        return env
    if _DEFAULT_PY_PYTHON.exists():
        return str(_DEFAULT_PY_PYTHON)
    return sys.executable


@pytest.fixture(scope="session")
def venv_pair(rs_python: str, py_python: str) -> dict:
    """聚合 fixture：返回 {"rs_python": ..., "py_python": ..., "crs_python_dir": ...}.

    **硬性契约（v2 修正硬性-1）**：dict 的 key 名与 ``run_parity_case`` / 
    ``BenchRunner.__init__`` 的形参名一一对齐，调用方可直接 
    ``run_parity_case(impl, case_id, case_definitions, **venv_pair)`` 解包。
    （v1 曾用 "rs"/"py" 简写 key，与 run_parity_case 形参 "rs_python"/"py_python"
    不匹配，导致 **venv_pair 解包抛 TypeError——v2 已修正。）
    """
    return {
        "rs_python": rs_python,
        "py_python": py_python,
```

```python
import sys

CASE = {case!r}
CRS_PYTHON_DIR = {crs_python_dir!r}

# ---- sys.path 操纵 ----

built = None
roundtrip_parsed = None

    parsed_obj = cls.parse(parse_data)
    parsed = extract(parsed_obj)
    built = build_factory().build()
    reparsed = cls.parse(built)
    roundtrip_parsed = extract(reparsed)
else:
    fmt, parse_data, build_input = _make_case_py(CASE)
    parsed_obj = fmt.parse(parse_data)
    parsed = dict(parsed_obj) if hasattr(parsed_obj, 'items') else parsed_obj
    built = fmt.build(build_input)
    reparsed = fmt.parse(built)
    roundtrip_parsed = dict(reparsed) if hasattr(reparsed, 'items') else reparsed

print(json.dumps({
    'impl': IMPL,
    'case': CASE,
    'parsed': normalize(parsed),
    'built': built.hex(),
    'roundtrip_parsed': normalize(roundtrip_parsed),
}))
```

#### 2.2.3 子进程隔离机制（DEV 实现硬要求）

1. **venv 解析顺序**：env var → 默认 venv 路径 → `sys.executable`（最后手段）。已在 §2.1 fixtures 实现。
2. **编码**：`subprocess.run` 必须用 `encoding="utf-8", errors="replace"`（Windows 控制台默认 GBK，stderr 含中文 traceback 会炸）。
3. **stdout 解析**：取**最后一行非空**（防 case 代码 print 调试信息污染输出）。JSON 解析失败 → RuntimeError 含 stdout 末尾 2000 字符。
4. **超时**：单个 case 子进程默认无超时（parity case 应 < 5s；超时视为 hang，由 L2 runner 上层 kill）。如需超时，DEV 可在 subprocess.run 加 `timeout=30`。

```python
# tests/_helpers/normalize.py

from typing import Any
from construct import Container, ListContainer  # type: ignore


def normalize(value: Any) -> Any:
    """规范化输出值，便于跨实现比较。
    
    规则（递归）：
        - dict / Container → 排序后的 dict，过滤以 "_" 开头的键（如 _io / _index）
        - list / tuple / ListContainer → list（递归）
        - bytes / bytearray → {"__bytes__": hex_str} 包装（dict 不能直接装 bytes）
        - float → 特殊值优先：NaN → "__NaN__"、+Inf → "__+Inf__"、-Inf → "__-Inf__"；
          普通 float → round 到 6 位小数（避免 IEEE754 精度差异）
        - 其他（int / bool / None / str）原样返回
    
    设计要点：
        1. 过滤 "_" 前缀键：Python construct Container 含 _io / _index 等内部状态，
           Rust construct-rs 不暴露这些，必须过滤才能比对
        2. bytes 包装为 dict：JSON 不能直接序列化 bytes，统一包装为 {"__bytes__": hex}
        3. float 精度：Rust f32/f64 与 Python float 在某些位模式有最后 1 位差异，
           round(6) 容忍协议场景的精度（6 位足够区分大多数协议字段）
        4. **NaN/Infinity 统一标记（v2 改进-3）**：JSON 标准不能直接序列化 NaN/Infinity，
           且 ``NaN != NaN`` 会导致 rs==py 比对永远 False。故在 normalize 统一标记为
           字符串哨兵值（"__NaN__" / "__+Inf__" / "__-Inf__"），两侧都转为同字符串后
           比对成立。**case 定义不再需要手动标记 NaN**（见 §5.1.2 范例修正）。
    
    边界条件：
        - 空容器：返回 {} / []
        - 嵌套 5 层以上：递归处理（Python 默认递归上限 1000，安全）
        - 含 None 值：原样保留（如 GreedyRange 空结果）
    """
```

**DEV 实现注意**：
- `Container` / `ListContainer` 是 Python construct 的内部类型，需在子进程内 import（子进程脚本注入 normalize_src 时，import 语句要在函数体内或顶部）
- **更稳妥**：normalize 不依赖 `Container` 类型，而是用 `isinstance(value, dict)` 检测（Python construct 的 Container 是 dict 子类，isinstance 成立）。这样 normalize 在 rs/py 两侧都能用，无需条件 import。

## §3 L2 门禁改造方案

### 3.1 双轨制设计（决策 4 配套）

**背景**：`run_l2_functional.ps1` 当前 `$MATRIX` 硬编码 12 项手工维护（OBS-1 已补 2 项）。每加一个 phase smoke 脚本要手工追加，遗漏风险高。

**双轨制定义**：

| 轨道 | 入口 | 用途 | 收集方式 |
|------|------|------|---------|
| **新轨（pytest）** | `run_l2_functional.ps1` 新增段 | 跑 `tests/parity/` + `tests/integration/` + `tests/errors/` 全部 test_*.py | pytest 自动递归发现 |
| **旧轨（smoke）** | `run_l2_functional.ps1` 现有 `$MATRIX` | 跑 `experiments/phase*_smoke.py` 端到端用户视角脚本 | glob 自动展开 |

**为何保留旧轨**：
- smoke 脚本是"端到端用户视角"（用户怎么写协议、怎么调 API），pytest 是"测试视角"（断言点 + parametrize），两者互补
- 部分 smoke 脚本依赖 Python construct 原版（PC venv），pytest 测试主要在 CRS venv，覆盖范围不同
- 已有 12 个脚本投入，不立即废弃（迁移成本 vs 收益不划算）

**何时废弃旧轨**：Phase 7+ 评估（详见 §3.3 兼容期管理）。

### 3.2 `run_l2_functional.ps1` 改造（+60 行）

#### 3.2.1 旧轨改造：`$MATRIX` glob 自动展开

**现状**（line 81-115）：12 项硬编码 `@{ Phase=...; Script=...; Target=...; Expected=...; Coverage=... }`。

**改造**：把硬编码脚本路径列表改为 glob 自动展开，但保留 expected/coverage 元数据（这些不能从文件名推断）。

**方案**：维护一个"元数据注册表"（轻量 JSON 或 PowerShell hashtable），脚本路径由 glob 展开。

```powershell
# testing/ci/run_l2_functional.ps1（改造后）

# ---- 旧轨：smoke 脚本元数据注册表（替代硬编码 $MATRIX） ----
# 注册表只记 Phase + Target + Expected + Coverage，不记 Script 路径
# Script 路径由下面的 glob 自动展开匹配
$SMOKE_METADATA = @{
    "phase1_smoke.py"                    = @{ Phase="1";   Target="CRS"; Expected="pass";           Coverage="FormatField(16) / Bytes / Struct B1-B2 / ModbusRTU" }
    "phase2_smoke.py"                    = @{ Phase="2";   Target="CRS"; Expected="pass";           Coverage="Bytes(const/expr) / Computed / Tell (E1-E3)" }
    "vet_phase3_binary.py"               = @{ Phase="3";   Target="PC";  Expected="pass";           Coverage="bits2integer / integer2bits / swapbytesinbits" }
    "vet_phase3_bits_integer.py"         = @{ Phase="3";   Target="PC";  Expected="known_broken";   Coverage="Bitwise(Bit/Nibble/Octet).parse/build 基线" }
    "vet_phase32_bitstruct.py"           = @{ Phase="3.2"; Target="CRS"; Expected="pass";           Coverage="Bitwise / BitStruct / BitsInteger 基本场景" }
    "vet_phase32_deep.py"                = @{ Phase="3.2"; Target="CRS"; Expected="pass";           Coverage="Bitwise / BitStruct 跨字节 / 嵌套 / swapped" }
    "test_phase33.py"                    = @{ Phase="3.3"; Target="CRS"; Expected="pass";           Coverage="BitStruct + Padding / Bytewise / BitsSwapped" }
    "phase4_smoke_greedy_range.py"       = @{ Phase="4";   Target="CRS"; Expected="pass";           Coverage="GreedyRange (parse/build/discard/fallback/empty)" }
    "phase4_smoke_prefixed_array.py"     = @{ Phase="4";   Target="CRS"; Expected="pass";           Coverage="PrefixedArray (含嵌套/Int16ub countfield)" }
    "phase4_smoke_repeat_until.py"       = @{ Phase="4";   Target="CRS"; Expected="deprecated";     Coverage="RepeatUntil v4 PyCallable（已弃用）" }
    "phase4_repeat_until_examples.py"    = @{ Phase="4";   Target="CRS"; Expected="pass";           Coverage="RepeatUntil v5 21 样例" }
    "v4_smoke_test.py"                   = @{ Phase="1-4"; Target="CRS"; Expected="deprecated";     Coverage="RepeatUntil v4 V-1~V-5 修正" }
}

# glob 自动展开 experiments/ 下所有 phase*/vet*/v4_smoke 脚本
$smokeScripts = Get-ChildItem -Path $experimentsDir -Filter "*.py" |
    Where-Object { $_.Name -in $SMOKE_METADATA.Keys }

# 构造 $MATRIX（动态）
$MATRIX = @()
foreach ($f in $smokeScripts) {
    $meta = $SMOKE_METADATA[$f.Name]
    $MATRIX += [pscustomobject]@{
        Phase    = $meta.Phase
        Script   = $f.Name
        Target   = $meta.Target
        Expected = $meta.Expected
        Coverage = $meta.Coverage
    }
}
```

**优势**：
- 新增 phase smoke 脚本：只需在 `$SMOKE_METADATA` 加一行元数据（不需写完整路径）
- 脚本被删/改名：glob 自然过滤掉，不会因路径失效导致 L2 FAIL
- 元数据与路径解耦：元数据稳定（Phase/Target/Expected），路径可变

**额外策略**：未来 phase smoke 脚本若遵循 `phase<N>_smoke_<name>.py` 命名约定，可让 glob 进一步自动化（无元数据时用默认 `Expected="pass"`）。

#### 3.2.2 新轨：pytest 自动发现段（追加到 `run_l2_functional.ps1`）

在现有 `$MATRIX` 执行段之后追加：

```powershell
# --------------------------------------------------------------------
# 新轨：pytest 自动发现（Phase 6.0 引入）
# --------------------------------------------------------------------
Write-CiLog "==== L2 pytest track start ====" -Level STEP

$pytestRoot = Join-Path $paths.CrsRoot "tests"
$pytestTargets = @(
    (Join-Path $pytestRoot "parity"),
    (Join-Path $pytestRoot "integration"),
    (Join-Path $pytestRoot "errors")
)

# 检查 pytest 是否在 CRS venv 可用
$pytestCheck = & $CrsPython -m pytest --version 2>&1 | Out-String
if ($LASTEXITCODE -ne 0) {
    Write-CiLog "pytest not available in CRS venv, skip pytest track" -Level WARN
} else {
    foreach ($target in $pytestTargets) {
        if (-not (Test-Path -LiteralPath $target)) {
            Write-CiLog "pytest target dir not exist, skip: $target" -Level WARN
            continue
        }
        Write-CiLog "pytest: $target" -Level STEP
        $sw = [System.Diagnostics.Stopwatch]::StartNew()
        $output = & $CrsPython -m pytest $target "-v" "--tb=short" 2>&1 | Out-String
        $code = $LASTEXITCODE
        $sw.Stop()
        $elapsedSec = [math]::Round($sw.Elapsed.TotalSeconds, 2)
        
        # pytest 失败也加入 scriptResults（统一报告）
        $scriptResults += [pscustomobject]@{
            phase        = "pytest"
            script       = "pytest:" + (Split-Path $target -Leaf)
            target_venv  = "CRS"
            expected     = "pass"
            passed       = ($code -eq 0)
            exit_code    = [int]$code
            elapsed_sec  = $elapsedSec
            coverage     = "pytest auto-discovery"
            note         = "Phase 6.0+ new track"
            output_tail  = ($output -split "`n" | Select-Object -Last 10) -join "`n"
            error        = $null
        }
        if ($code -ne 0) { $mustPassFailed = $true }
    }
}
```

**关键点**：
- pytest 失败（exit != 0）**阻断 L2**（与旧轨 `Expected="pass"` 同语义）
- pytest 必须在 CRS venv 可用（已确认 pyproject.toml 配置 + crs_venv 已装 pytest）
- 输出合并到 `scriptResults`，最终 JSON 报告统一

### 5.1 新 parity 测试的写法（统一模板）

#### 5.1.1 文件结构（DEV 照抄）

```python

"""Phase <N> <Category> 构造器 Python 行为一致性测试。

设计依据：
- docs/design/基础设施/测试框架设计.md §5.1（统一模板）
- docs/design/模块设计/模块设计-<XXX>.md §<边界条件章节>
- _helpers/parity.py（公共组件）

用法：
    pytest tests/parity/test_phase<N>_<category>_parity.py -v
    python tests/parity/test_phase<N>_<category>_parity.py
"""

from __future__ import annotations
import sys
from pathlib import Path

# 让 _helpers 可导入（tests/ 是 pytest 收集根）
_TESTS_DIR = Path(__file__).resolve().parent.parent
if str(_TESTS_DIR) not in sys.path:
    sys.path.insert(0, str(_TESTS_DIR))

from _helpers.parity import (
    make_parity_results_fixture,
    assert_parity,
    assert_fidelity,
    run_parity_case,
    PARITY_SCRIPT_TEMPLATE,
)
# v2：不再 import REGISTRY（CaseRegistry 已移除，见 §2.4）。case 清单直接用
# ALL_CASES 列表 + _CASE_DEFINITIONS 字符串（本文件下方定义）。

# ===== case 定义（子进程脚本片段，定义 _make_case_rs / _make_case_py） =====
_CASE_DEFINITIONS = '''
def _make_case_rs(case_id):
    from dataclasses import dataclass
    from construct import (StructMixin, field, ...)
    if case_id == 'F32-1':
        @dataclass
        class P(StructMixin):
            v: float = field(Float32b)
        return P, b"\\x42\\x28\\x00\\x00", lambda: P(v=42.0), lambda o: {'v': o.v}
    # ... 更多 case
    raise ValueError('unknown case (rs): ' + case_id)

def _make_case_py(case_id):
    import construct as pc
    if case_id == 'F32-1':
        return (pc.Struct("v"/pc.Float32b), b"\\x42\\x28\\x00\\x00", dict(v=42.0))
    # ... 更多 case
```

#### 5.1.2 范例：Float32b 的 parity 测试（Phase 6.1）

**旧方式（无 helper，~300 行模板重复）**：

每个 parity 文件都要复制 `_PARITY_SCRIPT` textwrap.dedent（~80 行）+ `_normalize`（~20 行）
+ `_run_parity_case`（~40 行）+ 5 个 test 函数（~80 行）+ standalone（~60 行）= 280 行模板 + case 定义。

**新方式（用 helper，仅 case 定义 + ~50 行调用）**：

```python
# tests/parity/test_phase6_primitives_parity.py（节选）
_CASE_DEFINITIONS = '''
def _make_case_rs(case_id):
    from dataclasses import dataclass
    from construct import StructMixin, field, Float32b, Float64b, VarInt, BytesInteger
    if case_id == 'F32-1':
        @dataclass
        class P(StructMixin):
            v: float = field(Float32b)
        # 42.0f = 0x42280000 (big-endian)
        return P, b"\\x42\\x28\\x00\\x00", lambda: P(v=42.0), lambda o: {'v': o.v}
    if case_id == 'F32-4':
        @dataclass
        class P(StructMixin):
            v: float = field(Float32b)
        # NaN: 0x7FC00000 (quiet NaN)
        # v2 改进-3：case 定义不再手动标记 NaN——直接返回 float('nan')，
        # 由 normalize 函数（§2.3 / §5.1.3）统一标记为 "__NaN__" 字符串。
        return P, b"\\x7f\\xc0\\x00\\x00", lambda: P(v=float('nan')), \\
            lambda o: {'v': o.v}
    # ... 其他 case
    raise ValueError('unknown case (rs): ' + case_id)

def _make_case_py(case_id):
    import construct as pc
    if case_id == 'F32-1':
        return (pc.Struct("v"/pc.Float32b), b"\\x42\\x28\\x00\\x00", dict(v=42.0))
    if case_id == 'F32-4':
        return (pc.Struct("v"/pc.Float32b), b"\\x7f\\xc0\\x00\\x00", dict(v=float('nan')))
    raise ValueError('unknown case (py): ' + case_id)
'''

ALL_CASES = [
    ("F32-1", "Float32b 正数（42.0）"),
    ("F32-2", "Float32b 负数（-42.0）"),
    ("F32-3", "Float32b ±0"),
    ("F32-4", "Float32b NaN（normalize 统一标记，case 无需特判）"),
    ("F32-5", "Float32b ±Infinity（normalize 统一标记）"),
    # Float64 / Float16 / VarInt / BytesInteger ...
]

parity_results = make_parity_results_fixture(ALL_CASES, _CASE_DEFINITIONS)
```

> **v2 改进-3 提示**：NaN / Infinity 的特殊值标记**统一由 normalize 函数处理**
> （见 §2.3 float 分支 + §5.1.3），**case 定义不要手动标记**（如旧版的
> `lambda o: {'v': 'NaN' if o.v != o.v else o.v}`）。混用会导致 rs 侧用 case 标记、
> py 侧用 normalize 标记，比对失败。统一路径：case 返回原始 float → normalize 统一标记。

**行数对比**：
- 旧方式：每个 parity 文件 ~300 行模板 + case 定义
- 新方式：每个 parity 文件 ~50 行调用 + case 定义
- **节省 ~250 行/文件**（Phase 6 三个 parity 文件共节省 ~750 行）

#### 5.1.3 NaN / Infinity 边界处理

Float 系列构造器涉及 NaN / Infinity 等特殊值，`normalize` 默认行为需扩展（DEV 实施时）。**这是 NaN/Inf 处理的统一路径**（v2 改进-3，case 定义不再手动标记）：

```python
# _helpers/normalize.py 的 float 分支（需扩展，与 §2.3 docstring 对齐）
if isinstance(value, float):
    if value != value:  # NaN
        return "__NaN__"
    if value == float('inf'):
        return "__+Inf__"
    if value == float('-inf'):
        return "__-Inf__"
    return round(value, 6)
```

**理由**：JSON 不能直接序列化 NaN/Infinity（标准 JSON），且 `NaN != NaN` 会导致 `rs == py` 比对永远 False。统一标记后两侧都为 `"__NaN__"` 字符串，比对成立。

> **DEV 实施顺序约束**：normalize 的 NaN/Inf 分支必须在步骤 1（写 normalize.py）就实现，
> 不能推迟。否则步骤 2（迁移 phase4 parity）若涉及 float case 会立即失败（phase4 无 float，
> 但 phase6.1 会用——提前实现避免 phase6.1 DEV 踩坑）。

### 5.2 新 benchmark 的写法（统一模板）

#### 5.2.1 文件结构（DEV 照抄）

```python
# bench/bench_<scope>.py
"""<scope> 性能基准测试。

设计依据：
- docs/design/基础设施/测试框架设计.md §5.2
- bench/_helpers/runner.py（BenchRunner）

    python bench/bench_<scope>.py

        paired = runner.run_paired(scenario, _MEASURE_SCRIPTS[scenario])
        results.append(paired)

    # 生成报告
```

### 5.3 DEV 实施 6.0 时的最关键 3 个注意点

> **REV 检查清单**（REV 检视设计时确认 DEV 是否在实施中遵守）：

#### 注意点 1：case_definitions 字符串的转义陷阱

**问题**：`_CASE_DEFINITIONS` 是多行字符串，内含 Python 代码（含 `\\` 反斜杠 bytes 字面量、`{{` JSON 转义等）。子进程通过 `subprocess.run([python, "-c", code])` 执行，`code` 由 `PARITY_SCRIPT_TEMPLATE.format(...)` 拼接。

**硬要求**：
- `_CASE_DEFINITIONS` 内若含 bytes 字面量（如 `b"\\x42"`），字符串内必须写 **4 个反斜杠** `\\\\x42`（外层 Python 字符串转义 + textwrap 不转义 + 内层 Python 子进程代码解析）
- 现有 `test_phase4_parity.py` 用 `textwrap.dedent` + `.format()` 已验证此模式，DEV 参考 line 69-558
- **替代方案**：用三引号 raw string `r"""..."""` 避免 \\ 转义，但需注意 raw string 不能含 `"""` 序列

**REV 验证点**：随机抽 3 个 case，手动跑子进程确认 bytes 字面量正确解析。

#### 注意点 2：normalize 函数的 "_前缀键过滤" 不能误删用户字段

**问题**：Python construct Container 的内部键（`_io` / `_index`）以 `_` 开头，但用户协议也可能用 `_private` 字段名。

**现状**：现有 `_normalize` 函数过滤所有 `_` 开头键（test_phase4_parity.py line 99: `if not k.startswith('_')`）。

**硬要求**：
- Phase 6.0 沿用现状（过滤所有 `_` 开头键）
- **但** construct-rs 用户面 dataclass 不允许 `_` 开头字段（PEP 8 + Python identifier 限制），故无风险
- 若未来 Phase 7+ 引入含 `_` 开头字段的需求，需重新设计过滤策略（白名单：仅过滤 `_io` / `_index` 等已知内部键）

**REV 验证点**：确认 normalize 单元测试覆盖"含 _io 键的 dict"和"不含 _io 的纯净 dict"两种场景。

#### 注意点 3：bench runner 子进程的 timeit number 必须与原 benchmark.py 一致

**问题**：`benchmark.py` 用 `NUMBER=30000, REPEAT=5`（取中位数），bench_stages.py 用 `NUMBER=10000, REPEAT=3`。新 BenchRunner 默认值若不同，会导致 speedup 数值漂移，与历史基线无法对比。

**硬要求**：
- `BenchConfig.number` 默认值 = `30_000`（与 benchmark.py 一致）
- `BenchConfig.iterations` 默认值 = `20`（比 REPEAT=5 多，统计更稳健）
- `BenchConfig.warmup` 默认值 = `5`
- 改造后的 `bench/bench_struct.py` 首次运行时，speedup 与原 `tests/benchmark.py` 历史值差异 < 10%（噪声范围）

**REV 验证点**：DEV 提交 6.0 时，附 bench_struct.py 与 benchmark.py 的 speedup 对照表（如 B1-parse: 旧 8.2x vs 新 8.4x），差异 > 10% 需 DEV 解释。
