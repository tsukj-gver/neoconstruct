# 单次 FFI 边界设计原则

> 本文档定义 construct-rs 项目中 Python ↔ Rust 跨语言调用的核心设计原则。
> 文档自包含——读者无需阅读任何参考项目源码即可完全理解全部内容。

---

## 1. 文档目的与适用范围

### 1.1 要解决的问题

construct-rs 的目标是将二进制数据的解析（parse）与构建（build）的**计算密集部分**用 Rust 实现，以获得远超纯 Python 实现的性能。但 Python 与 Rust 之间存在一道"语言边界"（FFI, Foreign Function Interface）。如何设计这道边界，直接决定了性能提升的成败。

本文档回答一个核心问题：

> **一次 parse 或 build 操作，Python 与 Rust 之间应该穿越 FFI 边界多少次？**

答案是：**各一次。不多不少。**

### 1.2 适用对象

- 架构设计阶段：定义 FFI 入口函数的签名与职责
- 实现阶段：约束执行树内部节点不得回调 Python
- 审查阶段：作为"是否存在 FFI 性能反模式"的检查清单

### 1.3 术语约定

| 术语 | 含义 |
|------|------|
| **FFI 穿越** | 一次从 Python 解释器进入 Rust 代码（或反向）的完整调用过程 |
| **执行树** | parse/build 操作在 Rust 侧展开的、由构造器节点组成的树形结构 |
| **编译产物** | 类定义时一次性构建的、可在运行时反复使用的执行树（不可变） |
| **构造器** | 执行树中的一个节点，对应一种二进制读写原语（如读取一个 int8） |
| **C API 调用** | Rust 代码通过 CPython 的 C ABI 直接操作 Python 对象（如创建字典、设置属性），这不是 FFI 穿越，而是进程内的普通 C 函数调用 |

## 2. 核心问题：FFI 穿越的开销本质

### 2.1 单次 FFI 穿越的固定开销量级

当 Python 代码调用一个用 Rust（经 pyo3）编写的函数时，实际发生的事情远不止"跳转到另一个地址执行"：

1. **CPython 参数封送**：Python 的调用约定（位置参数 + 关键字参数 + `*args` + `**kwargs`）必须被解包为 Rust 能理解的具体类型。这涉及类型检查、引用计数操作。
2. **C 栈帧建立**：CPython 为这次外部调用建立内部的调用追踪记录。
3. **GIL 状态确认**：确认全局解释器锁已被持有（pyo3 通过 `Python<'py>` 令牌在编译期保证这一点，但运行时仍有 token 校验开销）。
4. **返回值封送**：Rust 的返回值必须被包装为 `PyObject*` 并交还 Python，涉及引用计数转移。

综合下来，**一次 Python → Rust 的 FFI 穿越，固定开销约为 100–300 纳秒**（取决于参数数量和类型复杂度）。这在绝对值上看似很小，但关键在于它与操作本身的计算量之比。

一次"读取 1 字节并转为 int"的实际计算量约为 5–20 纳秒（内存拷贝 + 整数对象创建）。如果为这次读取单独做一次 FFI 穿越，FFI 开销是计算量的 **10–60 倍**。这完全抵消了用 Rust 实现带来的速度优势。

### 2.2 反面场景：执行树内部每个节点都回调 Python

考虑一种朴素的设计：执行树的根节点在 Rust 中，但每遇到一个子节点就回调 Python 层的方法来执行实际工作。

假设一个结构体有 20 个字段，parse 时每个字段需要：
- 1 次 Rust → Python 回调（执行该字段的解析逻辑）
- 1 次 Python → Rust 返回（传回解析结果）

这就是 **40 次 FFI 穿越**（20 次出 + 20 次回），每趟约 150–300 纳秒：

```
40 趟 × 200ns/趟 ≈ 8000ns = 8μs  （纯 FFI 开销）
```

而同样的 20 字段解析，如果全部在 Rust 内部用 C API 直接操作 Python 对象完成，实际计算量约为：

```
20 字段 × 15ns/字段 ≈ 300ns  （纯计算）
```

FFI 开销是计算量的 **~27 倍**。在这种设计下，即使用 Rust 重写，最终性能也可能与纯 Python 实现持平甚至更慢，因为 Python 解释器本身的字节码分派开销（约 30–50ns/条指令）在批量操作时反而比反复穿越 FFI 更高效。

### 2.3 正确做法：一次穿越，内部全在 Rust

正确的设计是：Python 调用一次 Rust 函数（1 次 FFI 穿越），传入输入数据，Rust 内部遍历整棵执行树，通过 CPython 的 C API **直接**创建 Python 对象、设置属性、构建嵌套结构，最终返回一个完整的 Python 对象。

```
Python 侧:  result = parse(data)        ← 唯一一次 FFI 穿越（入）
                                            Rust 侧完整执行整棵树
             ↑                           ← 唯一一次 FFI 穿越（出，返回结果）
```

此时 FFI 开销恒定为 1 趟（~200ns），与字段数量无关。当字段数为 20 时：

| 设计 | FFI 开销 | 计算开销 | 总计 |
|------|---------|---------|------|
| 每节点回调 Python | ~8000ns | ~300ns | ~8300ns |
| 一次穿越 + 内部 C API | ~200ns | ~300ns | ~500ns |

**差距约 16 倍。** 这就是"一次 FFI"原则的量化基础。

### 2.4 关键区分：C API 调用 ≠ FFI 穿越

这里必须澄清一个容易混淆的概念：

- **FFI 穿越**：Python 解释器的执行框架与 Rust 执行框架之间的切换。涉及 Python 调用约定的封送、C 栈帧切换。代价：~100–300ns/次。
- **C API 调用**：Rust 代码（已持有 GIL）调用 CPython 暴露的 C 函数（如创建字典、设置属性、创建整数对象）。这是**进程内的普通 C 函数调用**，代价：~20–80ns/次，且无框架切换开销。

"一次 FFI"原则禁止的是前者（FFI 穿越），**允许甚至鼓励**后者（C API 调用）。Rust 侧可以自由地、高频地调用 C API 来操作 Python 对象——这正是"直接操作 Python 对象"的含义。

> **设计原则（可证伪）**：如果将一次 parse/build 操作的所有 FFI 穿越次数从 1 增加到 N（N = 执行树节点数），性能将从 O(1) 的 FFI 开销退化为 O(N)。当 N > 10 时，FFI 开销将超过 Rust 计算本身的开销，使重写失去意义。

## 3. 设计原则一：编译期构建执行树

### 3.1 什么是"编译期构建执行树"

用户在 Python 中定义一个二进制结构（如一个协议帧的格式），本质上是声明了一棵"解析/构建规则树"。例如：

```
帧 = {
    地址:   1字节无符号整数
    功能码: 1字节无符号整数
    数据:   剩余全部字节
}
```

这棵规则树在**类定义的时刻**就已完全确定——字段名、字段类型、字段顺序、嵌套关系都不会在运行时改变。

"编译"指的是：在类定义时（而非每次 parse/build 时），将这棵声明式的规则树，**一次性转换为**一棵可直接执行的 Rust 数据结构（执行树）。此后每次 parse/build 只需遍历这棵已构建好的执行树，不再需要重新解析规则。

### 3.2 编译产物的形态

编译产物是一棵**不可变的 Rust 数据结构**，由枚举（enum）节点组成。每个节点对应一种构造器原语：

- **叶子节点**：原子操作，如"读取 N 字节并转为整数"、"读取剩余所有字节"。
- **复合节点**：容器操作，如"按顺序解析一组字段并组装为对象"、"重复解析 N 次"。复合节点持有其子节点的引用。

关键特征：
1. **不可变**：编译完成后，执行树的结构不再改变。运行时不允许增删节点或修改节点参数。
2. **自包含**：执行树持有所有运行时所需的信息（字段名、字节序、长度等），不依赖外部的 Python 对象来决定如何解析。
3. **可共享**：因为不可变，同一棵执行树可以被多次 parse/build 安全地并发使用（在 GIL 约束下）。

### 3.3 为什么编译只在类定义时做一次

执行树的结构由用户的类定义决定，而类定义在模块加载时执行一次。因此：

- 编译的输入（字段声明）在整个程序生命周期中不变。
- 编译的输出（执行树）可以安全地缓存，供所有后续 parse/build 调用复用。
- 将编译分摊到第一次使用时，后续每次调用的边际成本仅为"遍历执行树"，不包含"构建执行树"。

如果每次 parse 都重新编译执行树，则编译开销会被重复支付 N 次（N = parse 调用次数）。对于高频调用场景（如解析数百万个数据包），这是不可接受的开销。

### 3.4 违反此原则的后果

**反模式 A：运行时解释规则树**

每次 parse 调用时，都从 Python 侧的规则声明重新构建执行树。

- 后果：每次 parse 的开销 = 编译开销 + 执行开销。编译开销通常远大于执行开销（编译需要递归遍历 Python 字典、类型检查、分配 Rust 结构体），导致 parse 性能急剧下降。
- 典型表现：首次调用和后续调用耗时相同，没有"预热"效应。

**反模式 B：执行树可变**

允许运行时动态修改执行树（如添加/删除字段）。

- 后果：执行树无法被高效缓存和共享；每次使用前必须检查是否被修改；Rust 的借用规则难以保证安全。
- 替代方案：如果确实需要动态结构，应定义一个新的类（触发新的编译），而非修改已有执行树。

> **设计原则（可证伪）**：如果执行树在编译后可被修改，则无法保证同一棵树的多次 parse 调用行为一致，也无法安全缓存。不可变性是"编译一次、复用多次"模式的前提。

## 4. 设计原则二：运行时单次 FFI 穿越

### 4.1 parse 侧：bytes → Python 对象

parse 操作的 FFI 入口签名（概念性）：

```
fn parse(编译产物: &执行树, 输入数据: &[u8]) -> PyResult<Py<PyAny>>
```

**Python 侧**调用此函数（1 次穿越进入 Rust），**Rust 侧**执行以下全部工作后返回（1 次穿越回到 Python）：

1. 创建输入流的游标（纯 Rust 操作）
2. 遍历执行树，对每个节点：
   - 从游标读取相应字节
   - 通过 C API 将读取的字节转换为 Python 对象（如调用 `PyLong_FromLong` 创建整数）
   - 对于复合节点，通过 C API 创建容器对象（如 `PyDict_New`）并设置子项
3. 返回最终构建的 Python 对象

整个过程中，Rust 与 Python 之间的"穿越"只有进入和返回两次（算作 1 次完整调用）。所有中间步骤都是 Rust 进程内的 C 函数调用，不涉及框架切换。

### 4.2 build 侧：Python 对象 → bytes

build 操作的 FFI 入口签名（概念性）：

```
fn build(编译产物: &执行树, 输入对象: &Bound<PyAny>) -> PyResult<Vec<u8>>
```

**Python 侧**调用此函数并传入待构建的 Python 对象（1 次穿越进入 Rust），**Rust 侧**执行以下全部工作后返回字节数组（1 次穿越回到 Python）：

1. 创建输出缓冲区（纯 Rust 操作）
2. 遍历执行树，对每个节点：
   - 通过 C API 从 Python 对象读取属性值（如调用 `PyObject_GetAttr` 或字典查找）
   - 将 Python 值转换为字节并写入缓冲区
   - 对于复合节点，递归处理子对象
3. 返回最终的字节数组

### 4.3 "单次"的严格含义

"单次 FFI"指的是：**一次完整的 parse 或 build 操作中，Python 侧的调用栈只进入 Rust 一次**。具体来说：

- ✅ 允许：Rust 侧内部通过 C API 高频调用 CPython 函数（这是进程内调用，不是 FFI 穿越）
- ✅ 允许：一次 parse 调用内部，Rust 递归遍历数千个执行树节点
- ❌ 禁止：Rust 侧在遍历执行树时回调用户定义的 Python 函数来执行解析逻辑（这会在一次 parse 内产生 N 次额外的 FFI 穿越）
- ❌ 禁止：执行树的每个节点在 Python 侧有对应的"解析器对象"，Rust 逐个调用它们

### 4.4 例外情况：用户钩子函数

某些构造器需要调用用户提供的 Python 回调（如条件分支的判断函数、值变换函数）。这类回调**不可避免地**会产生 FFI 穿越。

处理原则：
1. **明确标注为"有 FFI 回调"的构造器**，让用户知晓性能影响。
2. **将回调次数最小化**：如果回调的结果在单次 parse 中不变，应缓存结果而非每次都回调。
3. **在文档中量化**：标注"每次回调增加约 200–500ns 开销"。
4. **作为可选特性**：默认路径（无回调）保持单次 FFI；有回调是用户主动选择的结果。

> **设计原则（可证伪）**：如果一次 parse 操作内部产生了 M 次 Python 回调，则该操作的总 FFI 开销为 O(M+1) 而非 O(1)。当 M > 5 时，性能优势将显著缩水。测试基准必须包含"有回调"和"无回调"两组数据，以暴露这一退化。

## 5. 设计原则三：Rust 侧直接操作 Python 对象

### 5.1 "直接操作"的含义

"直接操作 Python 对象"意味着：Rust 侧在 parse 时直接构造 Python 对象，在 build 时直接读取 Python 对象，**不经过任何 Rust 原生的中间数据类型**。

具体来说：

**parse 侧（bytes → Python 对象）**：

```
// 正确做法：直接构造 Python 对象
let int_obj = PyLong_FromLong(raw_bytes_to_i8(data)?);  // 字节 → C API → Python int
dict.set_item("address", int_obj)?;                       // 直接设置到 Python 字典

// 错误做法：先构造 Rust 中间类型，再转换为 Python 对象
let rust_value: i8 = raw_bytes_to_i8(data)?;              // 字节 → Rust i8
let rust_dict = RustDict::new();                           // Rust 中间字典
rust_dict.insert("address", rust_value);                   // 存入 Rust 中间类型
// ... 遍历完成后，再将 RustDict 逐项转换为 Python dict
let py_dict = PyDict::new(py);
for (k, v) in rust_dict {
    py_dict.set_item(k, convert_rust_to_py(v)?)?;          // 额外的转换遍历 + 额外的 FFI 操作
}
```

**build 侧（Python 对象 → bytes）**：

```
// 正确做法：直接从 Python 对象读取
let value = obj.get_attr("address")?;                     // C API 读取属性
let raw = extract_int_from_py(value)?;                     // 直接提取数值
output_buf.write_i8(raw)?;                                 // 写入字节

// 错误做法：先转为 Rust 中间类型，再序列化
let rust_obj = convert_py_to_rust(obj)?;                   // 整个对象转为 Rust 结构体
let raw = rust_obj.address;                                // 从 Rust 结构体读取
output_buf.write_i8(raw)?;                                 // 写入字节
// 转换过程本身涉及大量 C API 调用，且遍历了对象两次
```

### 5.2 为什么不引入 Rust 中间数据类型

引入 Rust 中间类型（如 `enum Value { Int(i64), Bytes(Vec<u8>), Struct(HashMap<String, Value>) }`）看似"类型安全"且"Rust 惯用"，但它带来三重开销：

1. **双重遍历**：parse 时先遍历执行树构建 Rust 中间类型，再遍历 Rust 中间类型转换为 Python 对象。构建侧同理。这使得工作量翻倍。
2. **额外内存分配**：Rust 中间类型需要分配自己的内存（HashMap、Vec、String），这些内存在转换为 Python 对象后立即被丢弃。纯粹的浪费。
3. **转换开销**：Rust 中间类型 → Python 对象的转换本身就是一系列 C API 调用（创建 dict、创建 int、set_item...），与"直接操作"的做法完全相同——只是多了一次"先填入 Rust 类型再取出"的无意义往返。

更深层的问题是：Python 的类型系统是动态的、开放的（用户可以定义任意类、使用任意嵌套的字典和列表），而 Rust 的 enum 是封闭的、有限的。任何 Rust 中间类型都无法完整表达 Python 对象的全部可能性，必然导致信息丢失或过度设计。

### 5.3 历史教训

本项目的前身实现采用了"Rust 中间类型"方案。其 parse 流程为：

1. Rust 从字节构建 `RustValue` 枚举
2. Rust 遍历 `RustValue`，逐项调用 C API 转换为 Python 对象

实测结果：Python 端性能仅为纯 Python 原版的 **0.3–1.8 倍**（即多数场景下反而更慢）。根因正是上述三重开销的叠加。

### 5.4 实践指导

- parse 的每个构造器节点的 `parse` 方法，返回类型应为 `PyResult<Py<PyAny>>`（即直接返回 Python 对象），而非 `Result<RustValue, Error>`。
- build 的每个构造器节点的 `build` 方法，参数应接收 `&Bound<PyAny>`（即直接接收 Python 对象），而非 `&RustValue`。
- 复合节点（如 Struct）在 parse 时应直接创建 Python dict / 用户类的实例，在 build 时应直接从 Python dict / 用户类实例读取属性。
- 不在 Rust 侧定义"通用值枚举"来表示解析结果。

> **设计原则（可证伪）**：如果在 parse 路径中引入了任何 Rust 中间数据类型（即 parse 的返回类型不是直接的 Python 对象引用），则每次 parse 必然产生额外的内存分配和额外的遍历。对于 N 个字段的 Struct，这意味着 N 次额外的中间值分配 + N 次额外的中间值到 Python 对象的转换，使总工作量从 O(N) 变为 O(2N) 并增加 N 次堆分配。

## 6. 设计原则四：静态分派（枚举 + match）

### 6.1 问题：执行树节点的分派方式

执行树由多种类型的构造器节点组成（整数读取器、字节读取器、结构体组装器等）。遍历执行树时，对每个节点需要根据其类型调用对应的 parse/build 逻辑。这就是"分派"（dispatch）。

有两种基本方式：

**动态分派（trait object / `Box<dyn Trait>`）**：

每个节点是一个指向堆上对象的指针，该对象的实际类型在运行时确定。调用方法时，通过虚表（vtable）查找实际类型的函数地址，然后间接跳转。

**静态分派（枚举 + match）**：

所有可能的节点类型被列举在一个枚举中。每个节点就是枚举的一个实例（存储在栈上或内联在 Vec 中）。调用方法时，通过 `match` 匹配枚举的变体（discriminant），直接调用对应类型的函数。

### 6.2 静态分派的优势

**优势一：消除间接跳转的不确定性**

动态分派的核心代价是**间接分支预测失败**。现代 CPU 的分支预测器对间接跳转（"跳转到 vtable 中记录的地址"）的预测准确率较低，因为同一个调用点在不同时刻可能跳转到不同目标。分支预测失败会导致 **15–20 个时钟周期的流水线冲刷**（约 5–7 纳秒 @ 3GHz）。

静态分派的 `match` 在变体较少时（通常 ≤ 20 个）会被编译器优化为**跳转表**（jump table），这是一次直接跳转，分支预测器可以完美预测。在变体较多时会被优化为比较链，同样比间接跳转更可预测。

**优势二：编译器内联**

静态分派时，编译器可以看到所有分支的具体实现，有机会进行**跨节点的内联优化**。例如，如果一个复合节点持有一个叶子节点，编译器可能将叶子节点的 parse 逻辑直接内联到复合节点的遍历循环中，消除函数调用开销。

动态分派时，编译器无法跨 vtable 边界进行内联（因为被调用函数在另一个编译单元，且通过指针调用）。

**优势三：内存局部性**

静态分派的枚举节点存储在连续的内存中（如 `Vec<Node>`），CPU 缓存行可以高效预取。动态分派的 `Box<dyn Trait>` 每个节点是独立的堆分配，内存分散，缓存命中率低。

**优势四：消除堆分配**

枚举节点的大小在编译期已知（取所有变体的最大大小），可以直接存储在父节点的 `Vec` 中，无需单独堆分配。动态分派的每个 `Box` 都是一次堆分配 + 一次堆释放。

### 6.3 量化对比

假设执行树有 100 个节点（parse 一个 100 字段的嵌套结构）：

| 维度 | 动态分派（Box<dyn>） | 静态分派（enum + match） |
|------|---------------------|------------------------|
| 堆分配次数 | 100 次（每节点一次） | 0 次（内联在 Vec 中） |
| 分派预测失败（假设 10% 失败率） | 10 次 × 6ns = 60ns | 接近 0 |
| 缓存未命中（分散的堆对象） | 约 20–50 次额外缓存行加载 | 接近 0（连续内存） |
| 函数调用开销 | 100 次（不可内联） | 可内联至 0 |

综合估算，对于 100 节点的执行树，静态分派相比动态分派可节省 **200–500 纳秒**。虽然这在绝对值上不如"减少 FFI 穿越"的节省（微秒级），但对于追求极致性能的场景，这是不可忽视的优化。

### 6.4 静态分派的实现要点

1. **定义一个封闭枚举**：列出所有构造器类型作为变体。
2. **为枚举实现统一接口**：每个接口方法内部用 `match self { Variant::Int8(v) => v.parse(...), ... }` 分派到具体类型。
3. **使用 `enum_dispatch` 宏**（或等效手段）：该宏自动生成上述 match 分派代码，使每个具体类型只需实现 trait，无需手写 match 臂。
4. **编译期类型集合封闭**：枚举的变体在编译期固定。新增构造器类型需要修改枚举定义并重新编译。

### 6.5 违反此原则的后果

**反模式：使用 `Box<dyn ConstructTrait>` 存储执行树节点**

- 后果：每个节点一次堆分配（100 字段 = 100 次堆分配），间接分支预测失败导致流水线冲刷，编译器无法内联。
- 典型表现：基准测试中，小结构（5 字段）的性能差距可能不明显，但大结构（50+ 字段）的性能显著退化。
- 额外问题：`Box<dyn Trait>` 不是 `Send` / `Sync` 的（除非 trait 对象本身是），限制了并发能力。

> **设计原则（可证伪）**：如果执行树的节点使用 trait object 存储，则每次节点遍历都产生一次间接调用 + 潜在的分支预测失败。对于 N 个节点的执行树，相比静态分派额外损失 O(N × 6ns) 的预测失败开销 + O(N) 次堆分配开销。当 N = 50 时，额外开销约 300ns + 堆分配开销，占纯计算开销的 ~50%+。

## 7. 设计原则五：错误在单次 FFI 内传播

### 7.1 问题：Rust 错误如何映射为 Python 异常

Rust 使用 `Result<T, E>` 和 `?` 运算符进行错误传播。Python 使用异常（exception）进行错误传播。两者的机制不同：

- Rust 的 `Result` 是普通值，`?` 运算符在当前函数内提前返回，开销极小（一次 match + 一次返回）。
- Python 的异常涉及栈展开（unwinding），开销较大（微秒级），但只在错误路径上产生。

在单次 FFI 模型中，错误传播的正确方式是：

1. **Rust 内部使用 `Result` 传播**：执行树的每个节点的 parse/build 方法返回 `PyResult<T>`（即 `Result<T, PyErr>`）。错误通过 `?` 运算符逐层向上传播，直到 FFI 入口函数。
2. **FFI 入口函数返回 `PyResult`**：pyo3 会自动将 `Err(PyErr)` 转换为 Python 异常抛出。这是 FFI 边界处的唯一一次异常转换。
3. **不在 Rust 内部抛出 Python 异常**：不使用 `panic!` 或 `unwrap()`，因为 Rust panic 跨越 FFI 边界是未定义行为（或被 pyo3 捕获为 `PanicException`，性能差且语义混乱）。

### 7.2 错误信息必须携带位置路径

当 parse 在某个嵌套字段处失败时，用户需要知道**具体是哪个字段**出了问题。因此，错误对象必须携带"路径"信息：

```
错误: 字段 "header" 的第 3 个元素 ("flags") 的值超出范围
路径: header[2].flags
```

实现方式：
- 执行树的每个节点在 parse/build 时，将其字段名/索引推入一个"路径栈"。
- 错误发生时，路径栈的内容被附加到错误信息中。
- 路径栈是 Rust 内部的数据结构（如 `Vec<PathSegment>`），不需要 FFI 穿越。

### 7.3 错误转换的成本控制

将 Rust 错误转换为 Python 异常的过程涉及：
1. 创建 Python 异常对象（C API 调用，~100ns）
2. 设置异常消息和属性（多次 C API 调用）
3. 栈展开（Python 侧，微秒级）

由于错误只在实际出错时产生（冷路径），上述开销是可接受的。关键约束是：

- **成功路径零成本**：在 parse/build 成功的情况下，不应产生任何与错误处理相关的开销（不预分配错误对象、不构建错误路径字符串）。
- **错误路径信息完整**：当错误发生时，必须提供足够的信息供用户定位问题。

> **设计原则（可证伪）**：如果错误路径信息不完整（如只报"parse 失败"而不说明是哪个字段），用户将无法调试嵌套结构的解析错误。如果错误处理在成功路径上产生开销（如每次 parse 都预分配错误对象），则违反"成功路径零成本"原则，影响基准性能。

## 8. 这一模式的限制与代价

上述五条设计原则构成了一个完整的设计模式，但它并非没有代价。以下是其固有限制：

### 8.1 执行树不可运行时修改

编译完成后，执行树的结构不可变。这意味着：

- **不能动态增删字段**：如果需要在运行时根据条件决定是否包含某个字段，必须通过"条件构造器"（在执行树中预设条件判断逻辑）实现，而非动态修改执行树。
- **不能动态替换构造器类型**：如果需要根据运行时类型决定使用不同的解析逻辑，必须通过"标签联合构造器"（在执行树中预设多种变体及选择逻辑）实现。
- **影响**：这限制了某些动态场景的灵活性，但换来了 O(1) 的 FFI 开销和编译期优化的可能性。

### 8.2 编译期必须知道所有类型

静态分派要求枚举的变体在编译期固定。这意味着：

- **无法支持用户在运行时定义全新的构造器类型**：所有构造器类型必须是 Rust 代码中已知的。用户可以组合已有的构造器（通过类定义），但不能发明新的原子构造器。
- **扩展需要重新编译 Rust 代码**：新增构造器类型需要修改 Rust 枚举定义并重新编译扩展模块。
- **影响**：对于 construct-rs 来说，这不是问题——二进制协议的构造器原语集合是有限的、稳定的（整数、浮点、字节、字符串等），不需要用户在运行时扩展。

### 8.3 用户回调不可避免地引入额外 FFI 穿越

某些高级功能（如基于上下文的条件分支、用户自定义的值变换）需要调用 Python 回调。这些回调无法在 Rust 中内联，必然产生 FFI 穿越。

- **缓解**：将这类功能标注为"有性能成本的可选特性"，在文档中量化其开销。
- **默认路径不受影响**：不使用回调的构造器仍然保持单次 FFI。

### 8.4 调试不如纯 Python 直观

当所有逻辑都在 Rust 内部执行时，Python 调试器无法逐步跟踪 parse/build 的内部过程。

- **缓解**：提供"调试模式"（可选启用），在 Rust 侧记录详细的解析日志，通过日志输出而非 Python 调试器来辅助调试。
- **权衡**：性能优先，调试性作为可选项。

### 8.5 编译失败的处理

类定义时的编译可能失败（如字段类型描述符无效、嵌套引用无法解析）。编译失败必须在类定义时即报错，而非延迟到首次 parse/build。

- **原则**：fail fast。编译错误应在 `__init_subclass__` 中立即抛出，提供清晰的错误信息（哪个字段、什么问题）。
- **影响**：用户在导入模块时就会看到编译错误，而非在运行 parse 时才发现。这是积极的行为——早失败比晚失败好。

## 9. 设计原则总览与适用性判断

### 9.1 五条原则速查表

| 编号 | 原则 | 一句话总结 | 违反后果 |
|------|------|-----------|---------|
| 一 | 编译期构建执行树 | 类定义时一次性编译，运行时只遍历 | 每次调用都重新编译，性能急剧下降 |
| 二 | 运行时单次 FFI 穿越 | 一次 parse/build 只穿越 FFI 边界一次 | O(N) 次 FFI 穿越，N > 10 时重写失去意义 |
| 三 | 直接操作 Python 对象 | parse 直接产 PyObject，build 直接读 PyObject | 双重遍历 + 额外内存分配，实测退化为 0.3–1.8x |
| 四 | 静态分派（枚举 + match） | 执行树节点用枚举存储，编译期分派 | 间接分支预测失败 + 堆分配，大结构退化 ~50% |
| 五 | 错误在 FFI 内传播 | Rust 用 Result 传播，入口处转 Python 异常 | panic 跨 FFI 是未定义行为；路径缺失导致无法调试 |

### 9.2 适用性判断

这一设计模式适用于以下场景：

- ✅ **计算密集的二进制数据处理**：parse/build 的核心工作是字节读写和数值转换，没有 I/O 等待。
- ✅ **结构在编译期确定**：二进制协议的格式在类定义时已知，运行时不变。
- ✅ **高频调用**：parse/build 被调用数百万次（如解析数据包流），FFI 开销的节省被放大。
- ✅ **构造器原语集合有限且稳定**：不需要用户在运行时发明新的原子构造器。

不适用于以下场景：

- ❌ **结构在运行时动态变化**：需要动态增删字段或替换构造器类型。
- ❌ **低频调用**：如果 parse 只调用几次，FFI 开销的绝对值（~200ns）可以忽略。
- ❌ **需要用户在运行时定义新构造器类型**：静态分派的枚举无法容纳运行时新增的类型。

### 9.3 与 construct-rs 的契合度

construct-rs 的典型使用场景（解析协议帧、文件格式等）完全满足上述适用条件：

1. 二进制协议格式在类定义时确定 ✅
2. parse/build 是纯计算，无 I/O ✅
3. 高频调用（流式处理大量数据包）✅
4. 构造器原语集合有限（整数、字节、结构体等）✅

因此，五条设计原则完全适用于 construct-rs，是架构设计的基石。
