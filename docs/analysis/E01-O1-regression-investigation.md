# E01 O1 回归根因调查（4.6-E01-INVEST）

## §1 调查背景

### 1.1 用户质疑

子任务 4.6 ACCEPTED 后，用户对 E01 `Array(0, Index()) parse` 性能提出质疑：

| 时点 | 测量者 | E01 加速比 | 状态 |
|------|--------|-----------|------|
| 2026-07-11 | 4.7 PM 验收复测 | **10.56x** | O1 实施前 |
| 2026-07-28 | 4.6 DEV 报告 | 9.44x | O1 实施后（commit c77c0ea） |
| 2026-07-28 | 4.6 VET 复测（3 轮） | 9.40-9.54x | O1 实施后 |

差异 -1.05x。用户核心逻辑：**4.7 PM 验收时 E01 合格（≥10x），4.6 O1 实施后 VET 复测 <10x，可能是 O1 引入的回归**。

### 1.2 VET 之前排查（H1-H4）的不充分性

VET 在 4.6 审查中用 4 个假设排查 E01 矛盾（详见 `plans/phase4-array/traces/4.6-集成测试.md §4.6-E01-INVEST`，原 offset 7386-7398）：

| 假设 | VET 论断 | 充分性 |
|------|---------|--------|
| H1: O1 引入真实回归 | "O1 仅改 stop_if.rs，E01 Array(0, Index) 不调用 StopIf；cargo 未重编译" | **不充分** |
| H2: 脚本口径差异 | 同脚本 perf_verify 跨时段仍 <10x | 充分（排除） |
| H3: 测量时段环境波动 | 系统性偏移 0.3-1.5x | 描述性，未受控验证 |
| H4: 噪声主导区间 | 3 轮 range 0.04x 极稳定 | 印证但非因果证明 |

**H1 论断的两个问题**（用户指出）：
1. **"cargo 未重编译"事实错误**：O1 实施后 cargo `build --release` 必然重编译 stop_if.rs 并重新链接整个 crate（本调查实测重编译耗时 ~8s，产物二进制 hash 改变——见 §4.1）。crate 整体重新链接时，LTO/inlining 决策可能全局变化，影响非 StopIf 调用路径。
2. **"E01 不调用 StopIf"不足以排除**：即使 E01 运行时不调用 `StopIfNode::eval_cond`，stop_if.rs 的代码变化改变了 crate 整体的 codegen（code layout、inlining budget、monomorphization），可能间接影响 IndexNode::parse 的指令缓存命中或 inlining 决策。

VET 的**结论**（"非 O1 真实回归"）可能是对的，但**论证路径**（H1 的"cargo 未重编译"）不成立。本次调查用 Controlled A/B Test 提供受控因果证据。

### 1.3 本调查的必要性

- 用户质疑的因果链（O1 实施 → crate 重编译 → inlining 变化 → E01 性能变化）在工程上是可能的，不能仅凭"不调用"排除。
- VET H3（测量环境波动）只有描述性证据（跨时段系统性偏低），没有受控实验区分"O1 因果"与"环境漂移"。
- 需要一次严格的 Controlled A/B Test：**同一会话、同一环境、交替测量 O1 off vs on**，直接隔离 O1 的因果效应。

### 1.4 git 历史确认（消除法成立）

`git log --since=2026-07-11 -- construct-rs/src/*.rs` 确认：**07-11（4.7 PM 验收）到 07-28（4.6 VET 复测）之间，唯一的源码改动是 c77c0ea（O1）**。用户的"消除法"逻辑成立——除 O1 外无其他源码变量。但消除法不能区分"O1 因果"与"环境漂移"（17 天跨度），这正是本调查要解决的。

### 2.3 关键观察（肉眼）

1. **E01 加速比**：A 组 9.55-9.71x，B 组 9.36-9.71x，两组**完全重叠**。B 组甚至出现 B3=9.71x（高于 A 组任一次）。

计算脚本：`experiments/E01_O1_ab_stats.py`。`mean ± sample_stdev [min, max]`，`|Δ|/noise` 为组间差绝对值与组内噪声（pooled stdev）的比。

### 3.2 E01 差异显著性判据对照

任务书判据：`>0.5x 回归 / <0.3x 波动 / 0.3-0.5x 加测`。

- **E01 speedup Δ(A-B) = +0.023x** → **远低于 0.3x 波动阈值**（仅为阈值的 7.7%）
- **E01 rs_ns Δ = -0.21 ns** → Rust 侧 O1 off 比 O1 on 还**慢** 0.21ns（方向与"O1 引入回归"相反），且 |Δ|/noise = 0.13（差值仅为组内噪声的 13%）
- **welch_t = +0.18（speedup）/ -0.16（rs_ns）** → |t| < 0.2，无任何统计显著性（n=3 时 even |t|>2 才有弱显著性）

**结论：O1 对 E01 无可观测的因果效应。** E01 的 Rust 侧执行时间在两种条件下统计上完全一致。

### 3.3 对照组数据自洽性（强化结论）

**阳性对照 S01**：O1 设计预期 Expr 路径 fast-path 节省 ~10ns（§16.1.4 预测 S01 rs 306→296ns）。实测 S01 rs_ns Δ(A-B)=+1.05ns（O1 off 略慢），|Δ|/noise=0.73，welch_t=+0.89——**方向正确但效应在噪声内**。说明 O1 fast-path 在当前 codegen 下节省的 ns 不足以穿透 ~1.4ns 的测量噪声（详见 §6.2 设计反思）。

**阴性对照 i01**：speedup Δ=-0.29x（接近 0.3x 波动阈值！），但 rs_ns Δ=+0.35ns（几乎为零）。**0.29x 加速比摆动完全来自 Python 侧 pc_ns 漂移（-93ns）**。这是本调查最有力的旁证：**仅凭 Python 侧环境漂移，就能在与 O1 完全无关的场景上制造 0.29x 加速比摆动**——而 4.7 PM 的 10.56x → 9.40x 差距（-1.16x）跨度 17 天，Python 侧漂移幅度完全可达。

### 3.4 对 4.7 PM 10.56x 的解释

E01 Rust 侧 ns：本调查稳态 204-205ns（6 次测量）。4.7 PM 测得 10.56x → 反推 Rust 侧约 186ns（pc_ns ~1963ns / 10.56）或 Python 侧更高。两种可能：
1. **Python 侧 07-11 偏快**：pc_ns 当时可能 ~1980ns，Rust 侧 ~187ns（比当前稳态快 ~18ns，~9%）。
2. **Rust 侧 07-11 偏快**：venv 刚重建、CPython 3.14 首次启动状态、CPU 温度等使当时的 ~187ns 处于测量低位。

无论哪种，都属于 17 天跨度的环境漂移，与 O1 无关。本调查在**同一会话内**测量 O1 off vs on，排除了跨时段漂移，证明 O1 本身对 E01 Rust 侧 ns 的效应为 0。

## §4 crate inlining 机制分析（Step 2）

> 按 Step 1 判据，E01 Δ=0.023x < 0.3x，Step 2 非必需。但用户明确质疑 crate 整体 inlining 机制，本节用 A/B 二进制差异 + 等性能直接证伪该机制假设。

### 4.1 A/B 二进制差异确认（toggle 真实生效）

| 维度 | A（O1 off） | B（O1 on） |
|------|------------|-----------|
| 源码含 `try_eval_simple_cmp` | 否（git show bdcbc91 确认） | 是（git show HEAD 确认） |
| `construct_rust.dll` 大小 | 516,608 bytes | 517,120 bytes（+512B） |
| `construct_rust.dll` SHA256（前 24 hex） | `B6B8CA037E4C8A11D3CE340B` | `01C2D1BD7D4220DC0F6A3573` |
| `cargo build --release` 耗时 | ~8s（重编译整个 crate） | ~8s（重编译整个 crate） |

**结论**：A/B toggle 产生**真实不同的编译产物**（不同二进制大小 + 不同 hash）。VET H1"cargo 未重编译"论断**被证伪**——cargo 确实重编译了整个 crate 并产生不同二进制。

### 4.2 crate inlining 假设的直接证伪

用户假设链：`O1 改 stop_if.rs → crate 重链接 → inlining/codegen 全局变化 → IndexNode::parse 性能变化`。

**A/B test 正是该假设的受控实验**：
- 自变量：stop_if.rs 是否含 O1 fast-path（已确认产生不同二进制，§4.1）
- 因变量：E01（`ArrayNode::parse` → `IndexNode::parse`，不调用 `StopIfNode::eval_cond`）的 Rust 侧 ns
- 结果：E01 rs_ns A=204.4±1.3 vs B=204.6±1.7，Δ=-0.21ns，|Δ|/noise=0.13

**证伪**：stop_if.rs 的代码变化 + crate 整体重链接（不同 codegen 产物）**未对 E01 产生任何超出噪声的 Rust 侧性能影响**。若 crate 整体 inlining 真的影响 IndexNode::parse，A/B 应出现可观测差异；实测差异 0.21ns < 组内噪声 1.3ns。

**机制解释**：Rust release profile（LTO=thin）下，stop_if.rs 的局部 fast-path 变化只改变 `StopIfNode::eval_cond` 自身的代码体积与 inlining。`IndexNode` / `ArrayNode` 是独立的 enum_dispatch 分派分支，其 parse 路径的 inlining 决策由各自调用点的 budget 决定，不受 stop_if.rs 的代码变化牵连。code layout 变化（DLL +512B）不影响 E01 热路径的指令缓存命中（IndexNode::parse 入口地址的 cache line 行为未变）。

### 4.3 未做的进一步检查（及为何不需要）

- `cargo asm` 汇编对比：Step 1 已用受控实验证明性能无差异，汇编差异（必然存在，因二进制 hash 不同）不会转化为性能差异，无需深入。
- `CARGO_PROFILE_RELEASE_CODEGEN_UNITS=1` 强制单 unit：默认 codegen units 下 A/B 已无性能差异，强制单 unit 不会改变结论。
- monomorphization 分析：O1 未新增泛型实例（`try_eval_simple_cmp` 是 `&self` 方法，非泛型），不触发新 monomorphization。

## §5 根因结论

### 5.1 明确结论

| 问题 | 结论 | 证据强度 |
|------|------|---------|
| O1 是否引入 E01 回归？ | **否**。O1 对 E01 Rust 侧性能的因果效应为 0（Δ=-0.21ns，|Δ|/noise=0.13） | **强**（受控 A/B，n=3×2，同会话交替） |
| 10.56x → 9.40x 的原因？ | **17 天跨度的测量环境漂移**（CPython 重启 / venv 重建 / CPU 状态 / 时段差异），非 O1 | **强**（阴性对照 i01 同会话内 0.29x 摆动完全由 Python 侧漂移驱动） |
| VET H1"cargo 未重编译"论断？ | **事实错误**（cargo 确实重编译，二进制不同），但 VET 的最终结论（非 O1）正确 | — |
| E01 <10x 是否为真实现象？ | **是**。E01 当前稳态 9.4-9.7x（Rust 侧 ~205ns，Python 侧 ~1963ns）。10.56x 是 07-11 测量高位 | 强（VET 3 轮 + 本次 A/B 6 次，共 9 次测量一致） |

### 5.2 对 ARCH §16 设计的自我审视

**§16.1.6 反例声明 #3（"测量噪声主导区间"）——已证实，设计无误**：
E01 Rust 侧 ~205ns，组内噪声 ±1.3-1.7ns（~0.7%）；Python 侧 ~1963ns，噪声 ±24-26ns（~1.3%）。加速比 = pc/rs，相对噪声 ~2%，对应 ±0.2-0.4x 加速比摆动。E01 处于"零工作量 + 入口开销主导"区，10x 阈值恰在其噪声带内——这是设计 §16.1.6 预言的反例，本次调查用受控数据确认。

**§16.1.4 O1 节省 ~10ns 预测——过于乐观（设计反思）**：
设计预测 S01 O1 后 rs 306→296ns（节省 10ns）。实测 S01 rs 两种条件均 ~256ns（基线已比 §16.1.1 数据低 50ns，因 07-28 测量环境整体偏低）；O1 的 fast-path 效应仅 ~1ns（|Δ|/noise=0.73，不显著）。原因推测：release LTO 下 `eval_expr_int` 的 3-op 比较路径已被编译器高度优化，`try_eval_simple_cmp` 内联后的机器码与 `eval_expr_int` 内联后差异很小。**这不影响 E01 结论**（E01 本就不调 Expr 路径），但说明 §16.1.4 的 ns 级估算精度有限——属 L-02（理论估算替代实证数据）的轻度体现，后续设计应标注"ns 估算为量级参考，需实测确认"。

**设计无缺陷性改动**：§16 的核心判断（E01 <10x 是 B1 类边界场景结构性特征，与 Phase 1 B1 同根因，需路径 B 长期投资）**不受本次调查影响，反而被强化**。

## §6 修复方案建议 + 防回归建议

### 6.1 是否需要修复 O1

**不需要。** O1 对 E01 无因果效应（§3/§4 已证），且 O1 实施后 StopIf 6 场景 VET 复测全部 ≥10x（10.72-15.69x）。O1 无需 revert、无需修改。

### 6.2 E01 <10x 的处置（沿用 §16.3 已有结论）

E01 当前稳态 9.4-9.7x，是 B1 类边界场景（零工作量 + 入口开销主导）。处置路径**不变**：
- **短期**：Phase 4 收尾按"待 Phase 5 复审"处理（与 StopIf B1 同档，OBS-V1 建议）。
- **长期**：Phase 5 投资 Struct + FFI 入口固定开销优化（§16.3 路径 B），目标将 Rs 入口开销从 ~150ns 降至 ~50ns，E01 预计可达 ~12x。

**本次调查无需修订任何已有决策**（用户决策事项 A/B/C + §16 设计 + 4.6 ACCEPTED 结论均成立）。

### 6.3 是否影响 S01/S03 的"O1 后 ≥10x"结论

**不影响。** S01/S03 的 ≥10x 结论基于 VET 复测（10.72x / 10.93x），与本次 A/B test 的 S01 数据（O1 on 11.46x）一致。本次调查只针对 E01，未发现 O1 对 S01/S03 有负面影响（S01 A vs B 差异在噪声内，且 B 不慢于 A）。

### 6.4 防止类似"伪回归"质疑的建议

本次质疑源于"消除法 + 单次跨时段测量对比"的局限性。建议沉淀以下测量规范（供 PM 决策是否写入 performance-gate SKILL 或新 ADR）：

1. **跨时段性能对比必须标注环境状态**：记录 venv 重建时间、CPython 重启次数、测量时段。仅当两次测量的环境状态一致时，加速比差异才可归因于代码变化。
2. **边界场景（Rust 侧 <300ns）默认处于噪声带**：加速比阈值判据（≥10x）在这些场景上需配合多次采样（≥3 轮）+ Rust 侧绝对 ns 趋势判断，不可仅凭单次加速比下定论。
3. **怀疑回归时优先做 Controlled A/B Test**：同会话交替测量（A→B→A→B→A→B）+ 阳性/阴性对照，是区分"代码因果"与"环境漂移"的唯一可靠方法。比"git 消除法 + 推理"更强。

## §8 L 教训对照

### 8.1 L-02（理论估算替代实证数据）

**本次触发（轻度）**：§16.1.4 对 O1 节省 ~10ns 的估算属于"理论推算"（基于 §16.1.2 开销拆解表的单项 ns 相加）。实测 O1 对 S01 的效应仅 ~1ns（|Δ|/noise=0.73，不显著），说明该估算精度有限。

**对策执行情况**：
- 设计阶段：§16.1.4 含"可证伪预测"（O1 后 S01 ~9.97x）+ 反例声明（§16.1.6）——形式上满足 performance-gate Checkpoint 1。
- 但 ns 级绝对值估算（306→296ns）偏差较大——这是 L-02 提醒的"理论估算容易给出吸引人数字"的体现。
- **改进建议**：后续性能设计的"节省 ns"估算应标注"量级参考，需实测确认"，避免被当作精确承诺。本次调查本身就是用实证数据（A/B test）替代理论推理（"O1 改了 crate 所以影响 E01"）的实践——符合 L-02 对策精神。

### 8.2 L-05（优化 A 路径忽略 B 路径）

**本次未触发**。O1 设计（§16.1.4）的 FFI 来源对照表覆盖了所有 7 项来源。本次调查反而验证了"未被优化的路径（E01 的 ArrayNode/IndexNode）确实不受 O1 影响"——O1 没有意外地拖累 B 路径。

### 8.3 候选新教训（建议 PM 评估是否沉淀）

**模式**：跨时段性能对比的"消除法归因"在边界场景（绝对 ns 小、噪声占比大）上不可靠，易将环境漂移误判为代码回归。

**事件**：4.6 收尾时 E01 从 10.56x（07-11）降到 9.40x（07-28），用户/VET 均尝试用消除法归因（唯一变量是 O1 → 推断 O1 引入）。Controlled A/B Test 证明非 O1，而是 17 天环境漂移。

**候选对策**（若 PM 决定沉淀）：
- 怀疑性能回归时，PM 优先分派 ARCH 做 Controlled A/B Test（同会话交替 + 对照组），而非依赖跨时段单次测量对比。
- performance-gate SKILL 可新增"边界场景回归判定"章节：Rust 侧 <300ns 的场景，加速比下降需用 Rust 侧绝对 ns 趋势确认（而非仅加速比），且需 ≥3 轮采样。

**此为建议，是否沉淀 L-09 由 PM 决策**（AGENTS.md §5：PM 是 harness/experiences.md 维护决策者）。
