## 1. 概述

### 1.1 设计决策：方案 A——接受即时解析（Eager Parse）实现

**ARCH 正式裁定：Phase 7 采用方案 A（即时解析 + 惰性类型接口），真正的按需延迟解析推迟至 Phase 9。**

以下是完整的论证过程。

### 1.2 核心矛盾

Python 原版的惰性解析依赖三个机制协同工作：

1. **`_actualsize` 跳过机制**：对定长字段（如 `Int*`, `Float*`, `Bytes(n)`），仅前移流游标、不读取字节。
2. **延迟容器**：`LazyContainer`（继承 `dict`）/`LazyListContainer`（继承 `list`）持有**流引用 + 偏移表 + 缓存字典**，在字段被访问时才 seek 回去解析。
3. **透明返回**：`_parse` 直接返回 `LazyContainer`，因 Python 的动态类型，调用方无感知。

在 Rust 中，`Construct::parse` 的签名是：

```rust
fn parse(&self, stream: &mut dyn Stream, ctx: &mut Context) -> Result<Value>;
```

`parse` **必须返回 `Value`**。`Value` 是一个具体枚举（`#[derive(Clone, Debug, PartialEq)]`），不存在"延迟变体"。这意味着：

- **即时物化是强制性的**：parse 返回时，所有字段的 `Value` 必须已经物化，无法表示"尚未解析"的状态。
- **延迟容器无法作为 `Value` 返回**：除非向 `Value` 添加 `Lazy` 变体，否则 `LazyContainer`/`LazyListContainer` 无法通过 `Construct::parse` 返回。

### 1.3 方案 B（真正惰性）的技术可行性分析

REV 正确指出：字节快照技术（`read_remaining` → owned `Vec<u8>` → 子 `ByteStream`）在 `Rebuffered` 中已被证明可行。因此，"真正的惰性解析在 Rust 中可行"这一结论成立。

**但方案 B 的实现需要修改 Phase 1 的核心架构决策**，具体如下：

#### 1.3.1 需要添加 `Value::Lazy` 变体

    offset: usize,                     // 数据起始偏移

#### 1.3.2 级联影响清单

| 影响范围 | 具体内容 | 风险等级 |
|---------|---------|---------|

#### 1.3.3 为什么不在 Phase 7 做方案 B

1. **架构变更范围超出 Phase 7 边界**：`Value` 枚举是 Phase 1 的核心架构决策（AGENTS.md §7："动态类型替代：Value 枚举 + 模式匹配"）。修改它影响 Phase 1-6 的所有已验收代码，违反"禁止在依赖阶段未完成验收时开始后续阶段的子任务"原则的逆向版本——不应让后续阶段破坏已验收的前置阶段。

2. **风险与收益不匹配**：Phase 7 有 5 个构造器已实现，37 项单元测试 + 5 项 doctest 全绿。为引入真正的惰性语义而冒 1090 项测试的回归风险，在缺乏迫切性能需求的情况下不合理。

3. **Python 的惰性本身就是部分的**：`_actualsize` 只能跳过**定长字段**（`Int*`/`Float*`/`Bytes(n)`/`Array(n,Byte)`）。变长字段（`VarInt`、`Prefixed`、`PrefixedArray`）在 parse 时仍被立即解析。真正的惰性收益仅限于"定长字段占多数且只需访问少数字段"的场景。

4. **Phase 9 正是为此而设**：阶段依赖关系（AGENTS.md §9）明确 Phase 9 为性能优化阶段。`Value::Lazy` 变体的引入应作为 Phase 9 的首要任务，有充分的规划与测试时间。

#### 回应 3："[设计质疑] 'Rust 所有权使惰性不可行'的技术理由不充分"

**ARCH 部分确认此质疑成立。** DEV 在代码注释中使用的措辞（"makes it impractical"）确实夸大了困难程度。

更准确的表述应为：

> Rust 的所有权模型使得**在不修改 `Value` 枚举的前提下**无法实现真正的惰性解析。`Construct::parse` 必须返回 `Value`，而 `Value` 是一个具体枚举，无法表示延迟物化状态。字节快照技术（如 `Rebuffered` 所用）本身可行，但要将其扩展到 Value 级别的惰性访问，需要添加 `Value::Lazy` 变体，这是一项影响全代码库的架构变更。

REV 关于"DEV 自己在 Rebuffered 中已实现字节快照"的观察是正确的。但需要指出一个关键区别：

- **Rebuffered 是流适配器**：它创建一个新的 owned `ByteStream`，传给 `subcon.parse()`，后者返回一个完全物化的 `Value`。这里没有延迟值参与。
- **LazyStruct/LazyArray 需要延迟值**：它们需要在 `Value::Container`/`Value::List` 中存储"尚未解析"的字段/元素。这要求 `Value` 支持 lazy 变体。

字节快照是必要技术，但非充分条件——还需要 `Value` 基础设施的支持。

## 3. 接口设计

### 3.1 parse 行为

| 构造器 | parse 策略 | 流推进 |
|--------|-----------|--------|
| `Lazy` | 记录偏移（诊断用），立即调用 `subcon.parse()` | 与 subcon 一致 |
| `LazyStruct` | 委托 `inner.parse()`，所有字段立即解析 | 与 Struct 一致 |
| `LazyArray` | 委托 `inner.parse()`，所有元素立即解析 | 与 Array 一致 |
| `LazyBound` | 调用 `subcon_func()` 获取构造器，立即 parse | 与绑定构造器一致 |
| `Rebuffered` | `read_remaining` 全量缓冲 → 在缓冲 ByteStream 上解析 subcon → 原流游标回正至 `start + consumed` | 精确推进 subcon 消费的字节数 |

### 3.2 build 行为

| 构造器 | build 策略 |
|--------|-----------|
| `Lazy` | 委托 `subcon.build()`（Python 版 callable 求值在 Rust 中不适用，Value 总是已物化） |
| `LazyStruct` | 委托 `inner.build()`，与 Struct 完全一致 |
| `LazyArray` | 委托 `inner.build()`，与 Array 完全一致（含 count 校验） |
| `LazyBound` | 调用 `subcon_func()` 获取构造器，立即 build |
| `Rebuffered` | 直接委托 `subcon.build()`（顺序写入无需缓冲） |

### 3.3 sizeof 行为

| 构造器 | sizeof 策略 |
|--------|------------|
| `Lazy` | 委托 `subcon.sizeof()` |
| `LazyStruct` | 委托 `inner.sizeof()`（= 各字段 sizeof 之和） |
| `LazyArray` | 委托 `inner.sizeof()`（= count × subcon.sizeof()） |
| `LazyBound` | 调用 `subcon_func()` 获取构造器后委托 sizeof（**有益扩展**：Python 版抛出 SizeofError） |
| `Rebuffered` | 委托 `subcon.sizeof()` |

## 4. 行为规格

### 4.1 内存模型

| 构造器 | parse 后的内存状态 |
|--------|-------------------|
| `Lazy` | 一个完全物化的 `Value`（与 subcon 的 parse 结果相同） |
| `LazyStruct` | 一个 `Value::Container(IndexMap)`，所有字段均已解析 |
| `LazyArray` | 一个 `Value::List(Vec<Value>)`，所有元素均已解析 |
| `LazyBound` | 绑定构造器的 parse 结果 |
| `Rebuffered` | subcon 的 parse 结果 + 临时缓冲区已释放 |

### 4.2 Rebuffered 的游标回正算法

```
1. start = stream.tell()           // 记录原流起始位置
2. data = stream.read_remaining()  // 全量读入缓冲（对应 Python tailcutoff=None）
3. buffered = ByteStream::new_read(&data)
4. result = subcon.parse(&mut buffered, ctx)
5. consumed = buffered.tell()      // subcon 实际消费的字节数
6. stream.seek(start + consumed)   // 原流精确回正
7. return result
```

**已知边角**（REV 次要建议 #1）：若 subcon 在 buffered 流上先前进读取再 seek 回退，`consumed = buffered.tell()` 会取最终游标位置（可能小于实际触及的最大偏移）。当前测试未覆盖此场景。与文档表述一致，标记为后续优化项。

### 4.3 边界条件清单

| 场景 | 预期行为 | 测试覆盖 |
|------|---------|---------|
| `Lazy` 包装的 subcon 字节不足 | 返回 `ConstructError::Stream` | `lazy_propagates_parse_error` |
| `LazyStruct` 空构造器（无字段） | 返回空 `Value::Container` | `lazystruct_default_is_empty` |
| `LazyStruct` build 缺字段 | 返回 `ConstructError::FieldMissing` | `lazystruct_build_missing_field_errors` |
| `LazyStruct` build 类型错误 | 返回 `ConstructError::TypeMismatch` | `lazystruct_build_wrong_type_errors` |
| `LazyStruct` 全 Pass 字段 | `flagbuildnone()` 返回 `true` | `lazystruct_flagbuildnone_all_pass` |
| `LazyArray` count=0 | 返回空 `Value::List` | 由 Array 委托保证 |
| `LazyArray` build 数量不符 | 返回 `ConstructError::Array` | `lazyarray_build_wrong_count_errors` |
| `LazyArray` build 类型错误 | 返回 `ConstructError::TypeMismatch` | `lazyarray_build_wrong_type_errors` |
| `Rebuffered` + GreedyBytes | 消费全部，游标在末尾 | `rebuffered_parse_consumes_everything_when_subcon_is_greedy` |
| `Rebuffered` + 依赖 seek 的子构造器 | 正常工作（Pointer 测试） | `rebuffered_provides_seekable_substream` |
| `Rebuffered` + tailcutoff 设置 | 接受参数但不截断缓冲 | `rebuffered_with_tailcutoff_still_parses` |
| `Rebuffered` 字节不足 | 返回 `ConstructError::Stream` | `rebuffered_parse_error_propagates` |
| `LazyBound` 重导出路径 | `lazy::LazyBound` 与 `stream_ops::LazyBound` 指向同一类型 | `lazybound_reexported_from_lazy_module` |

### 5.2 行为差异

| 行为 | Python | Rust（方案 A） | 差异性质 |
|------|--------|---------------|---------|
| Lazy parse 返回值 | 零参 callable（thunk） | 已解析 `Value` | ⚠️ 类型不同（round-trip 等价） |
| LazyStruct parse | 定长字段跳过+变长字段立即解析 | 所有字段立即解析 | ⚠️ 性能差异（语义等价） |
| LazyArray parse | 同上 | 所有元素立即解析 | ⚠️ 性能差异（语义等价） |
| LazyBound.sizeof | 抛出 `SizeofError` | 成功返回大小 | ✅ 有益扩展 |
| Rebuffered 缓冲策略 | `RebufferedBytesIO` 流式分块（128KB） | `read_remaining` 全量缓冲 | ✅ 功能等价（内存策略不同） |
| Rebuffered tailcutoff | 截断缓冲区大小 | 接受参数但不截断 | ⚠️ 参数忽略（文档化） |
| Rebuffered build | 经 stream2 写入（透传） | 直接委托 subcon | ✅ 结果一致 |

### 5.3 LazyRange 说明

总纲子任务 7.3 标题为"LazyArray / LazyRange"，但 Python 原版 `core.py` 中**不存在 `LazyRange` 类**。grep 确认仅有 `Lazy`、`LazyStruct`、`LazyArray`、`LazyBound` 四个惰性构造器。总纲此处为笔误。Rust 实现正确地仅实现了 `LazyArray`。

### 5.4 LazyBound 的特殊性

**LazyBound 在 Python 原版中本身就是 eager 解析**（line 6246-6248）。它不提供按需延迟语义——其"lazy"指的是"延迟绑定构造器"（runtime resolution of which construct to use），而非"延迟解析"。因此 Rust 的 LazyBound 实现与 Python 版本行为完全一致，无简化。

| 正确性 | ✅ round-trip 等价 | ✅ round-trip 等价 |

### 6.2 与总设计文档的一致性

### 6.3 Phase 9 演进计划（方案 B 的设计蓝图）

当 Phase 9 启动真正的惰性解析时，建议按以下路线实施：

#### 第一步：添加 `Value::Lazy` 变体

```rust
pub struct LazyValue {
    /// owned 字节快照（多个 LazyValue 可共享同一快照的不同区间）
    data: Rc<[u8]>,
    /// 本值在 data 中的起始偏移
    offset: usize,
    /// 解析此值所需的构造器
    construct: Rc<dyn Construct>,
    /// parse 时的上下文快照（Context 已实现 Clone）
    context: Context,
    /// 首次访问后的缓存（Rc 共享，RefCell 提供内部可变性）
    cache: Rc<RefCell<Option<Value>>>,
}
```

需手动实现 `Clone`（共享 Rc）、`Debug`（显示 `<lazy>` 不触发物化）、`PartialEq`（物化后比较，物化失败返回 `false`）。

#### 第二步：引入 `actualsize` 机制

在 `Construct` trait 中添加 `actualsize` 默认方法：

```rust
pub trait Construct {
    // ... 现有方法 ...

    /// 计算此构造器在当前流位置下占用的字节数。
    /// 默认实现委托 `sizeof`；变长构造器（如 Prefixed）可覆写
    /// 以部分读取流来确定大小。
    fn actualsize(&self, stream: &mut dyn Stream, ctx: &Context) -> Result<usize> {
        self.sizeof(ctx)
    }
}
```

对应 Python 的 `_actualsize`（core.py line 508-509）。

#### 第三步：实现 `LazyContainer` / `LazyListContainer`

在 `parse` 阶段：
1. 对每个字段/元素，尝试 `actualsize`
2. 成功 → 前移游标（不读取），在 Container 中存储 `Value::Lazy(LazyValue { data, offset, ... })`
3. 失败（SizeofError）→ 立即解析（与 Python 一致）

用户访问字段时，`LazyValue` 自动物化（首次 seek+parse，缓存结果）。

#### 第四步：回归测试

确保 1090+ 现有测试在 `Value::Lazy` 存在后仍全部通过。重点验证：
- `PartialEq` 行为（Lazy vs 非 Lazy 比较）
- `as_*` 方法对 Lazy 的自动物化
- 嵌套场景（Struct 内的 Lazy 字段）
