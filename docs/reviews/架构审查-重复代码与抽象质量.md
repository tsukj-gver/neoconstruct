# 架构审查：重复代码与抽象质量

> **审查范围**：construct-rs 全项目（Rust 侧 22,856 行 + Python 侧描述符层）
> **审查日期**：2026-07-11
> **审查人**：ARCH
> **触发事件**：4.7（Array per-iter 性能优化）过程中发现 P0-3 lazy path 模式在
> Phase 1 已由 StructNode 验证，但 Phase 4 Array 系列 4 个节点重新决策不用、
> 重复实现、直到性能不达标才补。用户严厉指出"ARCH 到底有没有做好抽象？"
>
> 本报告只审查不修改代码。整改清单（§4）供 DEV 后续执行。

---

## §1 执行摘要

### 1.1 量化结论

| 维度 | 数据 |
|------|------|
| Rust 总行数 | 22,856（非测试 ~7,343 + 测试 ~15,535） |
| 已识别重复代码（生产） | ~180-220 行（占非测试代码 ~2.5-3.0%） |
| 已识别重复代码（测试） | ~300-380 行（占测试代码 ~2%） |
| 已识别重复代码（合计） | ~480-600 行 |
| 完全相同函数体复制粘贴 | 4 处（`restore_index` ×4） |
| 近似相同代码块（差异仅错误消息/类型名） | 8 处（collect_iterable ×4 + lazy path ×4 命名族） |

### 1.2 抽象质量评级：**C（有改进空间）**

**评级理由**：

- **D（失职）的反例**：核心抽象（Construct trait、enum_dispatch 静态分派、Context Vec 化、
  Path lazy rebuild）设计本身是合理的，性能导向正确，没有出现"为抽象而抽象"的过度设计。
  P0-3 lazy path 模式在 StructNode 的实现是经过验证的优秀模式。
- **C（有改进空间）的依据**：
  1. **跨阶段模式未沉淀为规范**：P0-3 模式在 Phase 1 验证后，未写入设计决策记录，
     导致 Phase 4 Array 系列 4 个节点各自重新决策、重复实现。这是**过程性失职**，
     非抽象设计本身的缺陷。
  2. **机械复制粘贴明显**：`restore_index` 在 4 个文件中是完全相同的 6 行函数体，
     `collect_iterable` 在 4 个文件中是差异仅错误消息的 ~28 行块。这类重复无任何
     抽象成本，纯属于"复制粘贴便利"的惰性。
  3. **测试基础设施（`ensure_python`/`with_py`）在 21+ 文件中完全重复**：每文件
     ~12 行，合计 ~250 行。这是 Rust 测试组织问题，可用 `#[path]` 或 dev-dependency
     testutil 模块解决。
- **未达 B（合格）的依据**：合格要求"新模式一旦验证，即沉淀为可复用抽象"。本项目
  P0-3 模式验证后既未提取 helper 也未写入规范，导致 Phase 4 需要在性能不达标时
  回头补救（4.7 子任务），是可避免的返工。

### 1.3 关键发现（Top 5）

1. **`restore_index` 4 份完全相同副本**（array.rs / greedy_range.rs / prefixed_array.rs /
   repeat_until.rs）—— 纯机械复制，零抽象成本，**P0 立即整合**。
2. **`collect_iterable` 4 份近似副本**（list/tuple/iterable 三路 downcast + 错误包装）
   —— 差异仅类型名与错误消息字符串，**P1 提取 helper**。
3. **lazy path 错误传播模式（push_path_index + restore_index + return Err）** 在 4 个
   Array 节点中出现 ~8 处 —— 模式小（~5 行），**建议 macro 或 trait default method**。
4. **测试 helper（`ensure_python`/`with_py`/`byte_node`）21+ 文件重复** —— **P2 提取
   testutil 模块**。
5. **P0-3 lazy path 模式未写入设计决策记录** —— 导致 Phase 4 重新决策，**P0 流程改进**。

### 1.4 对 4.5 v5 实施的前置建议

设计决策记录已明确 v5 将删除 RepeatUntil 的 PyCallable 路径（决策 4'）。这意味着：

- repeat_until.rs 中 `parse_callable_path` / `build_context_proxy` /
  `call_repeat_predicate` / `container_cache` 依赖将整体删除（~400 行）。
- **建议 v5 实施时同步执行 §4 的 P0/P1 整改**（restore_index 提升、collect_iterable
  提升、lazy path macro），因为 v5 本就要大改 repeat_until.rs，整合的边际成本最低。
- **不建议**在 v5 之前单独做整合（会引起 repeat_until.rs 二次大改，浪费 DEV 工时）。

## §2 重复代码清单（按模式分类）

### 模式 A：lazy path 错误传播（push_path_index / push_path_segment）

**模式描述**：成功路径不维护 Path 栈（零 String 分配），子节点返回 Err 时通过
`ConstructError::push_path_*` 重建路径段。这是 P0-3 优化（Phase 1 验证）的核心模式。

#### A.1 StructNode 的 push_path_segment（Phase 1，已验证）

`struct_node.rs` 4 处，模式完全相同（仅字段名变量不同）：

```rust
// struct_node.rs L322-325（parse 表达式路径）
Err(mut e) => {
    e.push_path_segment(field.name.rust_name());
    return Err(e);
}
// 同模式重复于 L348-351（parse 无表达式路径）
//          L416-419（build RW/WO 路径）
//          L438-441（build RO 路径）
```

**共性**：4 处都是 `Err(mut e) => { e.push_path_segment(name); return Err(e); }`，
差异仅在 `field.name.rust_name()` 的上下文（全部相同）与是否在前面有 StopField
捕获分支。

**行数**：每处 ~4 行，合计 ~16 行。

#### A.2 Array 系列的 push_path_index（Phase 4，事后补救）

| 节点 | 文件:行 | 用途 | 备注 |
|------|---------|------|------|
| ArrayNode.parse | array.rs:171-175 | 索引重建 + restore_index | 含 restore |
| ArrayNode.build | array.rs:248-252 | 索引重建 + restore_index | 含 restore |
| GreedyRangeNode.build | greedy_range.rs:216-220 | 索引重建 + restore_index | parse 路径吞错误不重建 |
| PrefixedArrayNode.parse | prefixed_array.rs:146-150 | 索引重建 + restore_index | |
| PrefixedArrayNode.build | prefixed_array.rs:216-220 | 索引重建 + restore_index | |
| PrefixedArrayNode.build | prefixed_array.rs:204-207 | push_path_segment("countfield") | 字段名而非索引 |
| RepeatUntilNode.build (Expr) | repeat_until.rs:264-267 | 索引重建 + restore_index | |
| RepeatUntilNode.build (PyCallable) | repeat_until.rs:338-342 | 索引重建 + restore_index | v5 删除 |
| RepeatUntilNode.parse (Expr) | repeat_until.rs:419-423 | 索引重建（无 restore，函数级 restore） | |
| RepeatUntilNode.parse (PyCallable) | repeat_until.rs:491-495 | 索引重建（同上） | v5 删除 |

**共性**：所有 Array 系列节点的 lazy path 索引重建都是同一模式：
```rust
Err(mut e) => {
    e.push_path_index(i);
    restore_index(ctx, old_index);  // 部分场景在函数末尾统一 restore
    return Err(e);
}
```

**差异维度**：
- 是否在 match 臂内调 `restore_index`（ArrayNode/PrefixedArray 是；RepeatUntil
  parse 路径在函数末尾统一 restore）—— 实现风格不一致。
- 是否前面有 StopField 捕获分支（GreedyRange.build / RepeatUntil.build 有；
  ArrayNode.parse 无，因为 inner 不会返回 StopField 给 Array）。

**行数**：~8 处 × ~5 行 = ~40 行。

#### A.3 模式 A 总结

- **共性**：错误路径重建 + 向上传播，结构高度一致。
- **差异**：segment vs index（语义差异，正确）；是否含 restore（风格差异，应统一）；
  是否含 StopField 捕获（业务差异，正确）。
- **抽象难度**：中。segment 与 index 是两种语义，helper 需参数化；StopField 捕获
  是可选前置分支。建议用 macro 而非 trait default method（避免 trait 方法膨胀）。

### 模式 B：PyList Vec 中转 + collect_iterable

**模式描述**：4.7 优化——用 `Vec<Py<PyAny>>` 收集元素后一次性 `PyList::new_bound`，
避免 `PyList::append` 慢路径。

#### B.1 parse 路径的 Vec 中转

4 个 Array 节点 parse 都用 `Vec<Py<PyAny>>` 收集 + `PyList::new_bound(py, elems)`：

| 节点 | 文件:行 | Vec 初始化 | 终止条件 |
|------|---------|-----------|---------|
| ArrayNode | array.rs:160, 185 | `with_capacity(count)` | 固定 count 次 |
| GreedyRangeNode | greedy_range.rs:120, 161 | `new()`（未知容量） | EOF 或错误 |
| PrefixedArrayNode | prefixed_array.rs:136, 156 | `with_capacity(count)` | countfield 给的 count 次 |
| RepeatUntilNode (Expr) | repeat_until.rs:412, 218 | `new()` | 谓词为真 |
| RepeatUntilNode (PyCallable) | repeat_until.rs:222 | 直接用 PyList（谓词需实时 list） | v5 删除 |

**共性**：`Vec::new/with_capacity` → 循环 push → `PyList::new_bound`。
**差异**：容量策略（已知 count 用 with_capacity，未知用 new）；终止条件。
**抽象难度**：低。终态 `PyList::new_bound(py, elems)` 是单行，无需 helper；
循环逻辑因终止条件不同无法提取。**这部分重复是良性的**（差异 > 共性）。

#### B.2 build 路径的 collect_iterable（高重复）

4 个 Array 节点 build 都需要把 `obj`（list/tuple/iterable）收集到 `Vec<Py<PyAny>>`。
**这是最高重复度的模式**：

```rust
// array.rs L203-232（30 行）
let (obj_len, items): (usize, Vec<Py<PyAny>>) = if let Ok(list) = obj.downcast::<PyList>() {
    let len = list.len();
    let v: Vec<Py<PyAny>> = list.iter().map(|b| b.unbind()).collect();
    (len, v)
} else if let Ok(tuple) = obj.downcast::<PyTuple>() {
    let len = tuple.len();
    let v: Vec<Py<PyAny>> = tuple.iter().map(|b| b.unbind()).collect();
    (len, v)
} else {
    // 兜底：iter() 收集 + 错误包装（~15 行，差异仅在 "Array"/"GreedyRange"/...)
    ...
};
```

**4 份副本位置**：
- array.rs:203-232（30 行，额外返回 obj_len 用于长度校验）
- greedy_range.rs:177-200（24 行）
- prefixed_array.rs:171-194（24 行）
- repeat_until.rs:648-678（31 行，独立函数 `collect_iterable`）

**共性**：list → downcast PyList → iter collect；tuple → downcast PyTuple → iter collect；
兜底 → obj.iter() → 错误包装。

**差异**：
- 错误消息中的类型名（"Array" / "GreedyRange" / "PrefixedArray" / "RepeatUntil"）。
- ArrayNode 额外返回 `obj_len`（用于长度校验），其他 3 个仅返回 Vec。
- repeat_until.rs 已提取为独立函数 `collect_iterable`，但其他 3 个内联。

**行数**：4 × ~28 行 = ~112 行；提取为 1 个 helper（~30 行）可节省 ~82 行。

**抽象难度**：低。helper 签名：
```rust
fn collect_obj_to_vec(
    py: Python<'_>,
    obj: &Bound<'_, PyAny>,
    node_name: &str,  // 用于错误消息
    path: &mut Path,
) -> Result<Vec<Py<PyAny>>, ConstructError>
```
ArrayNode 的 `obj_len` 需求可通过 `vec.len()` 在调用方获取（Vec 已收集，len 是 O(1)）。

### 模式 C：ctx `_index` 操作（set_index + restore_index）

**模式描述**：嵌套数组支持——保存外层 `_index`，循环内 `set_index(i)`，循环后恢复。

#### C.1 `restore_index` 函数（完全相同，4 份副本）

**这是项目中最纯粹的复制粘贴**：

```rust
// array.rs:300-305 / greedy_range.rs:244-249 / prefixed_array.rs:243-248 / repeat_until.rs:685-690
#[inline]
fn restore_index(ctx: &mut Context<'_>, old: Option<usize>) {
    match old {
        Some(idx) => ctx.set_index(idx),
        None => ctx.clear_index(),
    }
}
```

**4 份完全逐字符相同**（含文档注释）。**行数**：4 × 6 行 = 24 行；提取为 1 个
`Context::restore_index` 方法可节省 18 行 + 消除"修一处需改四处"的维护风险。

**抽象难度**：极低。`Context` 已有 `set_index` / `clear_index` / `index`，
新增 `restore_index(old: Option<usize>)` 方法即可。

#### C.2 save + loop set + restore 骨架

4 个 Array 节点的循环骨架高度相似：
```rust
let old_index = ctx.index();          // 保存
for i in 0..count {                   // 或 loop / for (i, elem) in ...
    ctx.set_index(i);
    // ... inner.parse/build ...
}
restore_index(ctx, old_index);        // 恢复
```

**差异**：循环类型（for 0..count / loop / for enumerate）、错误处理（Array 传播 /
GreedyRange 吞错误回退 / RepeatUntil 传播）、discard 分支。**循环骨架本身无法提取**，
但 save/restore 这一对操作可封装为 RAII guard（见 §4 整改清单 P1-2）。

### 模式 F：错误变体构造 + PyErr 转换

**模式描述**：`ConstructError::set_path` 在 error.rs:452-470 用一个 `match` 列举
16 个变体的 `path` 字段写入。

**重复度**：error.rs 内部 1 处大 match，是 Rust enum 的固有权衡（无法用 macro
优雅消除，除非用 derive 宏）。各节点抛错时构造 `ConstructError::Generic/Range/Stream`
变体——这是正常的多态错误构造，非重复。

**已知问题**：`error.rs:452-470` 的 16 变体 match 在新增错误变体时需手动补 arm，
遗漏会导致 `set_path` 静默漏写 path。但这是 Rust 语言层面的限制，**非抽象失职**。

**结论**：**不整改**（语言固有），但建议在错误变体新增时 VET 检查 `set_path` 的
match 是否同步更新（见 §6 流程改进）。

### 模式 G：Python 描述符类 `_expr_params` 协议

**模式描述**：每个 Descriptor 类实现 `_expr_params` 协议，供 `_mixin._extract_and_compile_exprs`
识别哪些参数需要编译为 ExprOp 列表。

**实现方式不一致**（3 种风格）：

| 风格 | 使用者 | 行数 |
|------|--------|------|
| 类级别常量 `_expr_params = {}` | Bitwise, Bytewise, GreedyRange, PrefixedArray, Index, BitsSwapped, ByteSwapped（7 个） | 各 1 行 |
| `@property def _expr_params` | BitsInteger, Padding, Array, StopIf（4 个） | 各 ~6 行 |
| 实例属性 `self._expr_params = {...}` | RepeatUntil（1 个） | 在 `__init__` 内 |

**共性**：都返回 dict，key 是参数名，value 是待编译的表达式源。
**差异**：无表达式参数的描述符用类常量最简洁；有条件编译的用 @property；
RepeatUntil 因 v4 预编译逻辑用实例属性。

**重复度**：低。每个描述符的逻辑不同（BitsInteger 编译 "length"、Array 编译 "count"、
StopIf 编译 "cond"），非纯复制粘贴。

**问题**：风格不一致（3 种），影响新描述符的"该用哪种"决策。但这是**风格问题**，
非性能或正确性问题。

**结论**：**P3 整改**（后续阶段统一为 @property 风格，类常量作为"无参数"特例保留）。

### 模式 H：测试 setup（ensure_python / with_py / byte_node）

fn byte_node() -> Node {

**抽象难度**：中。需建 `tests/common/mod.rs` 并在每个测试模块 `#[path]` 引入，

### 模式 I：其他重复

#### I.1 compile.rs 的 build_*_node 函数

7 个 `build_*_node` 函数（build_bits_integer_node / build_padding_node /
build_array_node / build_greedy_range_node / build_prefixed_array_node /
build_stop_if_node / build_repeat_until_node）共享"getattr 属性 + 递归
build_node_from_descriptor + 错误包装"模式。

**共性**：每个函数开头都有 `desc.getattr("subcon").map_err(|e| Compilation { ... })`。
**差异**：属性名、编译逻辑因描述符而异。

**重复度**：低。错误包装是 Rust `?` 操作符的固有写法，每个属性的 map_err 消息
不同（含属性名定位）。提取 helper（如 `desc_getattr_or_compilation_error`）可减少
~3-4 行/函数，但收益有限。

**结论**：**P3 整改**（低优先级，可选）。

#### I.2 错误消息中的 `obj.get_type().name()` 类型名提取

collect_iterable 的兜底分支中，4 个 Array 节点都用：
```rust
obj.get_type().name().map(|n| n.to_string()).unwrap_or_else(|_| "<unknown>".to_string())
```

**重复度**：4 处 × 1 行。提取为 helper `obj_type_name(obj)` 可统一，但行数节省有限。

**结论**：随模式 B 的 collect_iterable helper 一并提取（P1）。

## §3 已有抽象评估

### 3.1 Construct trait（定义 + 默认方法）

**当前签名**（nodes/mod.rs:88-146）：
```rust
#[enum_dispatch]
pub trait Construct {
    fn parse<'py>(&self, py, stream, ctx, path) -> Result<Py<PyAny>, ConstructError>;
    fn build(&self, py, obj, stream, ctx, path) -> Result<(), ConstructError>;
    fn sizeof(&self, ctx) -> Result<usize, ConstructError>;
}
```

**扩展方法**（非 trait，定义在 `impl Node`）：
- `Node::has_expressions(&self) -> bool`：判断子树是否含表达式。
- `Node::compute_ro_value(&self, py, stream, ctx, path) -> Result<Py<PyAny>>`：
  RO 字段 build 方向计算值。

**评估**：
- ✅ **parse/build/sizeof 三方法是正确的最小接口**。不应把 `has_expressions` /
  `compute_ro_value` 放入 trait（前者是编译期元信息，后者仅 RO 节点需要）。
- ⚠️ **缺少 lazy path 的辅助方法**。当前 lazy path 错误传播散落在各节点的 match 臂，
  没有 trait 级 helper。建议**不**在 trait 加 default method（会污染所有节点的 impl），
  改用 free function 或 macro（见 §4）。
- ⚠️ **sizeof 签名不含 py 参数**。这导致 StructRefNode.sizeof 无法解析引用
  （struct_ref.rs:207-215 返回 Err），是**已知设计缺陷**（文档化为 [设计质疑]）。
  属于跨阶段决策，不在本次整改范围。

**覆盖度评级**：B（合格）。核心三方法覆盖完整，元信息方法（has_expressions）
通过 `impl Node` 提供。缺的是 lazy path helper，但 helper 不应在 trait 内。

### 3.2 Context API

**当前 API**（context.rs）：
- 构造：`new_root` / `placeholder` / `new_child` / `new_child_placeholder`
- 字段：`set_field` / `set_field_at` / `get_field` / `get_int_at` / `fields` / `inject_fields`
- 索引：`set_index` / `clear_index` / `index`
- 表达式：`init_expr_values` / `set_current_elem_ptr` / `clear_current_elem_ptr`

**评估**：
- ✅ **字段读写 API 完整**，Vec 化优化（expr_values_buf）设计优秀。
- ⚠️ **缺少 `restore_index` 方法**。当前 `restore_index` 是散落在 4 个 Array 节点的
  free function（模式 C.1），应提升为 `Context::restore_index(old: Option<usize>)`。
  这是最明确的整改项。
- ⚠️ **save/restore 配对无 RAII 保护**。`let old = ctx.index(); ... restore_index(ctx, old);`
  依赖开发者记得在所有退出路径（含错误返回）调 restore。ArrayNode/PrefixedArray 在
  错误臂调 restore，GreedyRange 在正常退出调，RepeatUntil 在函数末尾统一调——
  风格不一致。建议引入 RAII guard（见 §4 P1-2）。

**覆盖度评级**：B-（合格偏下）。核心 API 完整，但 `restore_index` 缺失 + RAII 缺位
导致模式 C 重复。

### 3.3 Helper 函数（散落在各 Node 文件）

| Helper | 定义位置 | 使用位置 | 评估 |
|--------|---------|---------|------|
| `restore_index` | 4 处（每 Array 节点一份） | 仅各自文件 | ❌ 应提升为 Context 方法 |
| `collect_iterable` | repeat_until.rs:648 | 仅 repeat_until | ⚠️ 应提升为公共 helper |
| `intern_pystring` | instance.rs | struct_node.rs / descriptors | ✅ 已正确集中 |
| `container_class` | container_cache.rs | repeat_until.rs | ✅ 已正确集中（v5 删除） |
| `eval_expr_int` | expr.rs | 多处 | ✅ 已正确集中 |
| `create_class` | instance.rs | struct_node.rs | ✅ 已正确集中 |

**评估**：集中化的 helper（intern_pystring / eval_expr_int / create_class）处理得当。
问题集中在 `restore_index`（应提升）和 `collect_iterable`（应共享）。

### 3.4 Macro / newtype

**当前项目几乎不用 macro**。仅 enum_dispatch（外部 crate）和标准 derive 宏。

**评估**：
- ⚠️ **lazy path 模式适合用 macro**。`e.push_path_index(i); restore_index(ctx, old); return Err(e);`
  是高频小模式，macro 可消除重复且不引入运行时开销。但 macro 会增加阅读复杂度，
  建议仅在 lazy path（模式 A）用，不过度使用。
- ✅ **newtype 未滥用**。`FieldName`（struct_node.rs:60）是合理的 newtype，
  封装 interned PyString + Rust String。无过度 newtype。

**结论**：macro 使用保守是正确的，但 lazy path 场景值得引入一个轻量 macro。

    /// 恢复 `_index` 到节点入口时的值（嵌套数组支持）。

| 影响范围 | 新文件（~35 行）、array.rs（-30 改调用）、greedy_range.rs（-24）、prefixed_array.rs（-24）、repeat_until.rs（删除 collect_iterable，-31） |

**草案签名**：
```rust
/// 从 list/tuple/任意 iterable 收集元素到 Vec。
///
/// 快路径：PyList / PyTuple 直接 iter collect（零额外开销）。
/// 兜底：obj.iter()，性能差（仅在用户传非 list/tuple 时触发）。
pub fn collect_obj_to_vec(
    py: Python<'_>,
    obj: &Bound<'_, PyAny>,
    node_name: &str,  // "Array" / "GreedyRange" / ...，用于错误消息
    path: &mut Path,
) -> Result<Vec<Py<PyAny>>, ConstructError> {
    if let Ok(list) = obj.downcast::<PyList>() {
        Ok(list.iter().map(|b| b.unbind()).collect())
    } else if let Ok(tuple) = obj.downcast::<PyTuple>() {
        Ok(tuple.iter().map(|b| b.unbind()).collect())
    } else {
        let type_name = obj_type_name(obj);
        let iter = obj.iter().map_err(|e| ConstructError::Generic {
            message: format!(
                "{} build expects list/tuple, got {} (iter error: {})",
                node_name, type_name, e
            ),
            path: path.to_string(),
        })?;
        iter.map(|b| b.map(|bound| bound.unbind())).collect().map_err(|e| {
            ConstructError::Generic {
                message: format!("{} build iterable error: {}", node_name, e),
                path: path.to_string(),
            }
        })
    }
}

#[inline]
fn obj_type_name(obj: &Bound<'_, PyAny>) -> String {
    obj.get_type()
        .name()
        .map(|n| n.to_string())
        .unwrap_or_else(|_| "<unknown>".to_string())
}
```

pub fn make_context_with_fields<'py>(

## §5 根本原因分析

### 5.1 为什么会有这些重复？

#### 根因 1：已验证模式未沉淀为规范（过程性失职）

**最严重的问题**。P0-3 lazy path 模式在 Phase 1 由 StructNode 验证（push_path_segment），
是经过性能基准确认的优秀模式。但：

- **未写入设计决策记录**：`docs/设计决策记录.md` 的 Phase 2.5 性能优化章节
  记录了"Context Vec 化"和"parse 借用实例 __dict__"，但**没有**记录 P0-3
  lazy path 模式。
- **未在 ARCH 设计阶段强制参考**：Phase 4 Array 系列的模块设计文档
  （`docs/模块设计-Array.md`）在 §4.1-§4.6 的 Array 节点设计中，最初的 v1/v2/v3
  版本**没有**采用 lazy path 模式（用 path.push_index/pop 维护成功路径）。
  直到 4.7 性能不达标才回头补救（设计文档 §6.2 "4.7 lazy path 嵌套组合测试"）。
- **REV 检视清单未覆盖"模式一致性"**：REV 在检视 Array 节点设计时，关注了
  Python 对齐、边界条件、错误处理，但**没有**检视"是否复用了 StructNode 已验证的
  P0-3 模式"。

**这是 ARCH 抽象层面的失职**：模式验证后既未提取 helper 也未写入规范，
导致后续节点重新决策。

#### 根因 2：复制粘贴的便利性（开发者惰性）

`restore_index` 的 4 份完全相同副本属于此类。该函数仅 6 行，复制粘贴比"想一下放哪里
共享"更快。`collect_iterable` 同理（repeat_until.rs 已提取为函数，但其他 3 个节点
仍内联）。

**这不是抽象设计问题，是工程纪律问题**。DEV 在实现新节点时倾向于"从相邻节点复制"，
而非"提取共享逻辑"。AGENTS.md §4 的角色隔离规则（DEV 只读 docs/ 不读其他节点的
实现细节？不——DEV 可读 construct-rs/src/）本应让 DEV 看到已有实现，但缺乏
"发现重复并提取"的激励。

#### 根因 3：测试基础设施的组织缺失（Rust 测试惯例问题）

`ensure_python` / `with_py` 的 21+ 份重复属于此类。Rust 的 `#[cfg(test)] mod tests`
惯例鼓励每个文件独立测试模块，但没有项目级的 testutil 约定。这与 Python 的
`conftest.py` / `tests/__init__.py` 共享 fixture 的惯例不同。

**这是项目基础设施缺失**，非抽象设计问题。解决方法是建立 `tests/common/` 约定。

### 5.2 ARCH 抽象层面的具体问题

#### 问题 1：跨节点模式识别滞后

P0-3 模式在 StructNode 验证时，ARCH 应当识别"这是一个适用于所有递归节点
（Struct/Array/Bitwise/Bytewise/Transform）的通用模式"，并：
- 在设计决策记录新增条目；
- 或在 Construct trait 加 default method（后被否决，因 trait 方法膨胀）；
- 或提取为 helper/macro。

实际上这些都没有做。P0-3 仅作为 StructNode 的实现细节记录在
`docs/设计修订-parse路径优化.md`，未被提升为项目级规范。

#### 问题 2：Phase 4 Array 设计未充分参考 Phase 1 已验证模式

`docs/模块设计-Array.md` 的 Array 节点设计（§4.1-§4.6）在最初的 v1 设计时，
ARCH 应当在"与其他模块的交互"章节明确引用 P0-3 模式。实际上 Array 节点设计
采用了"成功路径维护 path 栈"的方案，直到 4.7 才纠正。

#### 问题 3：Construct trait 设计的边界把握正确，但未提供 helper 层

Construct trait 仅含 parse/build/sizeof 三方法是**正确的**（接口最小化）。
但 trait 之外应当有一个"Node 共享工具层"（free function / macro），用于：
- lazy path 错误传播；
- list/tuple/iterable 收集；
- _index save/restore。

当前项目缺少这一层，导致工具散落在各节点。

### 5.3 是否触发 [设计质疑]？

**是的，部分触发**。

- **StructRefNode.sizeof 签名问题**（struct_ref.rs:207-215）：sizeof 签名不含 py 参数，
  导致 StructRefNode 无法解析引用。这已在 struct_ref.rs 文档化为 `[设计质疑]`，
  但**未在过程记录中正式提出**。建议 PM 将此作为 Phase 5+ 的待办，评估是否给
  sizeof 加 py 参数（会影响所有节点的 sizeof 实现）。
- **P0-3 模式未规范**：不算严格意义的设计质疑（不涉及接口冲突），但属于"已验收阶段
  （Phase 1）有架构性遗漏（未沉淀模式）"。建议 PM 在设计决策记录新增条目（§6.1）。

其余重复代码（restore_index / collect_iterable / 测试 helper）**不触发设计质疑**，
属于工程整改范畴，通过 §4 的 P0-P2 整改项处理。

|------|---------|------|---------|
| **P0-3 lazy path 错误传播** | Phase 1 (StructNode) | 成功路径不维护 Path 栈（零 String 分配）。子节点返回 Err 时，父节点通过 `ConstructError::push_path_segment(name)` 或 `push_path_index(i)` 重建路径段。所有含递归子节点的节点（Struct / Array / GreedyRange / PrefixedArray / RepeatUntil / Bitwise / Bytewise / Transform / StructRef）必须遵循。 | 所有递归节点 |

### 6.4 Construct trait 扩展的决策

**不建议扩展 Construct trait**（加 default method）。理由：
- parse/build/sizeof 是语义接口，lazy path 是实现模式，混入 trait 会污染所有节点。
- helper（free function / macro）是更合适的抽象层级。

**建议新增 `nodes/common.rs`**（或 `nodes/array_helpers.rs`）作为 Node 共享工具层：
- `collect_obj_to_vec`
- `obj_type_name`
- 未来可能的 lazy path macro（P1-2 若实施）

### 6.5 核心流程改进建议（给 PM 的 3 条）

1. **设计决策记录强制更新**：每个阶段验收时，ARCH 必须检查是否有"已验证模式"需
   沉淀到设计决策记录。PM 在阶段验收清单中加入此项。

2. **REV 检视清单加入"模式一致性"**：当前 REV 检视偏重 Python 对齐、边界条件、
   性能预测，缺少"是否复用已验证模式"维度。加入后可防止 P0-3 类型的重复决策。

3. **DEV 实现前强制查共享层**：DEV 在实现新节点前，必须在过程记录中声明"已查阅
   设计决策记录的跨阶段模式规范 + 已查阅 nodes/common.rs"。PM 在 CODING 阶段入口
   检查此项。
