# construct-rs 架构设计

> 本文档定义 construct-rs 的完整架构，覆盖 Python 接口、FFI 边界、Rust 执行模型、
> 模块分层、Schema 编译管线、Phase 1 范围六个维度。
>
> 本文档基于 `docs/FFI设计.md` 和 `docs/Mixin设计.md` 两份设计原则文档，是其原则在
> construct-rs 项目中的具体落地。读者应先阅读这两份文档以理解核心设计理念。
>
> 本文自包含——读者无需阅读任何参考项目源码即可理解全部设计。
> DEV 拿到本文档应能直接开始编码：所有接口签名、数据结构、模块划分均具体到可实现。

---

## 0. 文档定位与最高约束

### 0.1 适用对象

- **实现阶段（DEV）**：本文档是 Phase 1 编码的唯一架构依据。所有 Rust 类型签名、Python
  接口、模块层次以本文档为准。
- **审查阶段（VET/REV）**：本文档是"实现是否偏离架构"的检查基准。
- **后续阶段**：Phase 2+ 的扩展必须与本文档定义的分层和执行模型兼容。

### 0.2 最高约束（不可违反，违反即架构错误）

以下约束源自 `AGENTS.md §0` 与两份设计原则文档，本文档的所有设计均在其之下：

1. **一次 FFI**：编译、parse、build 各只有一次 Python↔Rust 边界穿越。Rust 内部通过
   CPython C API 直接操作 Python 对象（FFI 设计 §4）。
2. **无中间表示层**：parse 直接从 bytes 构造 PyObject，build 直接从 PyObject 读属性
   写字节，不在 Rust 侧引入独立的中值枚举再转换（FFI 设计 §5）。
3. **pyo3 是核心依赖**：单 crate，不存在独立的 Python 绑定层。
4. **静态分派**：执行树节点用封闭 `enum` + `match` 分派，禁止 `Box<dyn Trait>`（FFI 设计 §6）。
5. **mashumaro 式 API**：`@dataclass class X(StructMixin)`，编译在 `__init_subclass__`
   中完成，用户无感（Mixin 设计 §3）。
6. **Rust 编码红线**：禁止 `unwrap()`/`expect()`/`panic!` 在非测试代码；非法输入返回
   `Err`；所有 `pub` 项有文档注释；错误携带 path。

### 0.3 性能目标

- **硬目标**：≥ 4x vs Python construct 2.10.70（Phase 1 验收门槛）
- **理想目标**：10x
- 低于 4x 视为架构失败，须回退至设计阶段。

## 1. 术语表

| 术语 | 含义 |
|------|------|
| **FFI 穿越** | 一次 Python 解释器框架与 Rust 框架之间的完整切换调用，代价约 100–300ns |
| **C API 调用** | Rust 代码（已持有 GIL）调用 CPython 暴露的 C 函数，进程内调用，代价约 20–80ns，**不是** FFI 穿越 |
| **执行树** | parse/build 在 Rust 侧展开的、由构造器节点组成的不可变树形结构 |
| **构造器节点（Node）** | 执行树中的一个节点，对应一种二进制读写原语（如读取 int8、组装 Struct） |
| **编译产物（CompiledSchema）** | 类定义时一次性构建的、可在运行时反复使用的执行树，不可变 |
| **构造器（Construct）** | 执行树节点实现的统一 trait，定义 parse/build/sizeof 行为 |
| **类型描述符（Descriptor）** | 用户通过 `field()` 指定的二进制格式声明（如 `Int8ub`、`Bytes(4)`），Python 可见对象 |
| **Schema** | 用户类中字段信息的集合（字段名、顺序、描述符），编译的输入 |
| **字段（Field）** | StructMixin 子类中通过 `name: type = field(subcon)` 声明的一个二进制字段 |
| **Mixin 基类（StructMixin）** | 框架提供的、用户类需继承的基类，提供 parse/build 方法 |
| **类创建钩子** | Python 的 `__init_subclass__` 机制，在子类创建时自动调用 |
| **延迟桩（Stub）** | 前向引用未解析时安装在类上的占位 parse/build 方法，首次调用时触发真正的编译 |
| **前向引用** | 字段类型描述符引用了在同一类定义之后才定义的类 |
| **Context** | Rust 内部的上下文数据结构（持有 Python dict 引用），用于字段间引用与嵌套层传递 |
| **Stream** | Rust 内部的字节流游标抽象（parse 读、build 写），不跨 FFI |
| **Path** | 错误追踪路径（如 `header.flags[2]`），用于定位嵌套结构中的出错字段 |
| **用户钩子回调** | Rust 执行树内部不可避免地回调 Python 函数（如构造用户类实例），归类为 FFI 设计 §4.4 的例外 |

## A. Python 接口设计

### A.1 用户 API 总览

用户视角下的完整 API（与 `examples/example.py` 对齐）：

```python
from dataclasses import dataclass
from construct import StructMixin, field, Int8ub, GreedyBytes

@dataclass
class ModbusRTUMessage(StructMixin):
    address: int = field(Int8ub)
    function_code: int = field(Int8ub)
    data: bytes = field(GreedyBytes)

# build：从实例构造字节
msg = ModbusRTUMessage(address=1, function_code=3, data=b'\x00\x01')
built = msg.build()                       # → b'\x01\x03\x00\x01'

# parse：从字节构造实例
parsed = ModbusRTUMessage.parse(built)    # → ModbusRTUMessage(address=1, ...)
```

### A.2 StructMixin 基类

`StructMixin` 是纯 Python 实现的基类（不使用 pyclass），负责协调编译流程与 @dataclass。
Rust 仅承担编译/parse/build 三个计算入口。

```python
class StructMixin:
    """所有用户二进制结构类的基类。

    子类需配合 @dataclass 装饰器使用。类创建时自动触发 Schema 编译，
    编译产物存于类属性 _construct_compiled。
    """

    # 编译产物缓存槽（由 __init_subclass__ 设置），类属性
    _construct_compiled: "CompiledSchema | None" = None

    def __init_subclass__(cls, **kwargs):
        super().__init_subclass__(**kwargs)
        _compile_schema_for_class(cls)

    @classmethod
    def parse(cls, data: bytes) -> "StructMixin":
        """从字节解析为本类的实例。

        恰好一次 FFI 穿越：调用 CompiledSchema._parse_raw 返回字段 dict，
        随后在本类 __init__ 中构造实例（Python 解释器内部，无额外 FFI）。
        """
        schema = cls._construct_compiled
        if schema is None:
            raise ConstructError(
                f"{cls.__name__} 尚未完成编译（可能存在未解析的前向引用），"
                "请确保所有被引用的类型已定义后再调用 parse"
            )
        raw_fields = schema._parse_raw(data)   # ← 唯一一次 FFI 穿越（进入 Rust）
        return cls(**raw_fields)                # ← Python 内部构造实例

    def build(self) -> bytes:
        """从本实例构造字节。

        恰好一次 FFI 穿越：Rust 内部遍历执行树，通过 C API 读取本实例属性，
        直接写入输出缓冲区。
        """
        schema = type(self)._construct_compiled
        if schema is None:
            raise ConstructError(
                f"{type(self).__name__} 尚未完成编译"
            )
        return schema._build_raw(self)          # ← 唯一一次 FFI 穿越
```

**关键设计决策：parse 的实例构造在 Python 侧完成**

`_parse_raw` 返回字段 dict（Rust 通过 C API 构造的 `PyDict`），Python 侧用 `cls(**dict)`
构造实例。原因：
1. 严格保持"一次 FFI"：`_parse_raw` 进入 Rust 一次、返回一次，共两趟（算作一次完整穿越）。
   `cls(**dict)` 是 Python 解释器内部操作，不跨 FFI。
2. 正确触发 `@dataclass` 生成的 `__init__` 与用户的 `__post_init__`，保证验证逻辑生效。
3. 嵌套字段的构造（如 `Outer.inner: Inner`）由对应类的 `__init__` 递归完成，每层一次
   Python 内部调用，**不产生额外 FFI 穿越**（详见 §B.4 与性能假设 §G.2）。

### A.3 field() 函数

```python
def field(subcon):
    """声明一个二进制字段。

    参数:
        subcon: 类型描述符对象，决定该字段的二进制格式。
                必须是框架已知的描述符类型（Int8ub、Bytes(n)、GreedyBytes、
                或另一个 StructMixin 子类）。

    返回:
        一个 _FieldDescriptor 对象，同时满足:
        - 作为 @dataclass 的字段默认值（实现 dataclass 字段协议）
        - 携带 subcon 引用，供 __init_subclass__ 提取

    该函数在被调用时记录全局递增序号，保证字段顺序与声明顺序一致。
    """
```

`field()` 的返回值 `_FieldDescriptor` 必须同时满足两套协议：

| 协议 | 要求 | 用途 |
|------|------|------|
| `@dataclass` 字段协议 | 表现为合法的默认值或 dataclass Field 对象 | 让 `@dataclass` 能生成正确的 `__init__` |
| Mixin 编译协议 | 内部存储 `subcon` 引用，可被 `__init_subclass__` 提取 | 提供二进制格式信息给编译器 |

**字段顺序保证**：`field()` 利用 Python 3.7+ 类体命名空间（`__dict__`）的有序性，在
`__init_subclass__` 中按 `cls.__dict__` 的插入顺序提取字段。不依赖 `__annotations__`
的顺序（避免 PEP 526 与 `@dataclass` 重排的歧义）。

### A.4 类型描述符（Descriptor）

类型描述符是 Python 可见的对象，用户通过 `field()` 传入。三种形态：

#### A.4.1 预定义单例（无参数原子描述符）

```python
Int8ub    # 1 字节无符号大端整数（等价于 FormatField(">", "B")）
Int8sb    # 1 字节有符号大端整数
Int16ub   # 2 字节无符号大端整数
Int16sb, Int16ul, Int16sl
Int32ub, Int32sb, Int32ul, Int32sl
Int64ub, Int64sb, Int64ul, Int64sl
GreedyBytes   # 读取剩余全部字节
```

这些是 Rust pyclass 实例（在模块加载时创建一次，作为模块级常量）。每个实例内部存储
构建对应执行树节点所需的全部参数（如 `Int8ub` 内部存 `endianity='>', format='B'`）。

#### A.4.2 可实例化描述符（带参数）

```python
Bytes(length)            # 读取 length 字节（length 为正整数常量）
```

Phase 1 仅支持 `length` 为编译期常量整数。`length` 为上下文 lambda（如
`Bytes(this.length)`）的能力推迟到 Phase 2（需表达式系统支持）。

#### A.4.3 StructMixin 子类引用（嵌套结构）

```python
@dataclass
class Inner(StructMixin):
    x: int = field(Int8ub)

@dataclass
class Outer(StructMixin):
    inner: Inner = field(Inner)   # ← 直接传 StructMixin 子类作为描述符
```

`field(Inner)` 中 `Inner` 是一个 Python 类对象。编译器识别其为 `StructMixin` 子类后，
在执行树中创建一个递归引用节点（详见 §C.5 与 §E.5）。

### A.5 与标准 @dataclass 的集成

#### A.5.1 执行顺序（已由 REV 在 0.1 实测验证）

用户写 `@dataclass class X(StructMixin): ...` 时，Python 执行顺序：

1. 执行类体 → 收集 `address = field(Int8ub)` 到命名空间
2. `type.__new__` 创建类对象 `X`
3. **`StructMixin.__init_subclass__(X)` 触发**（此刻 `@dataclass` 尚未执行）
4. `@dataclass(X)` 装饰器执行 → 生成 `__init__`、`__dataclass_fields__`

**关键约束**：步骤 3 中编译器**不能**依赖 `__dataclass_fields__`（它还不存在），必须从
类体原始属性（`field()` 的返回值）提取字段信息。

#### A.5.2 字段信息来源协调

| 信息 | @dataclass 的用途 | StructMixin 的用途 |
|------|-------------------|-------------------|
| 字段名 | `__init__` 参数名 | 执行树节点标识；parse dict 的 key；build 时 getattr 的名字 |
| 类型注解（`address: int`） | `__init__` 类型提示（不影响运行时） | 不影响二进制格式（仅文档作用） |
| `field()` 返回值 | 作为字段默认值/描述符 | **从中提取 subcon，决定二进制格式** |

`field()` 返回值是两者的唯一桥梁，必须同时满足两套协议（见 §A.3）。

### A.6 空 StructMixin 子类的行为（落实 REV 建议 4）

无任何 `field()` 声明的子类是合法的边界情况：

```python
@dataclass
class Empty(StructMixin):
    pass
```

**定义行为**：编译成功，执行树为空 Struct 节点（零子节点）。

| 操作 | 行为 |
|------|------|
| `Empty.parse(b'')` | 返回 `Empty()`（无字段实例），不读任何字节 |
| `Empty.parse(b'abc')` | 返回 `Empty()`，**忽略**多余字节（与 Python construct 的 Struct 语义一致：Struct 不要求消费全部输入） |
| `Empty().build()` | 返回 `b''`（空字节） |
| `Empty().build()` 内部 | 不写任何字节，输出缓冲为空 |

此行为对协议头/尾的占位类型、纯标记类有意义。编译器不应对零字段报错。

## B. FFI 边界设计

本节定义 Python↔Rust 之间的三个 FFI 入口，以及 Schema 传递、编译产物结构、对象构造
与属性读取的精确机制。核心约束：每个入口恰好一次 FFI 穿越。

### B.1 三个 FFI 入口总览

| 入口 | 触发时机 | Python→Rust 输入 | Rust→Python 输出 | FFI 穿越次数 |
|------|---------|------------------|------------------|-------------|
| **编译** | `__init_subclass__` 中一次 | 类对象 + 描述符列表 | `CompiledSchema`（pyclass 实例） | 1 |
| **parse** | `cls.parse(data)` 中一次 | `CompiledSchema` + `bytes` | 字段 `dict`（PyDict） | 1 |
| **build** | `obj.build()` 中一次 | `CompiledSchema` + 用户实例 | `bytes` | 1 |

三个入口都在热路径之外或为单次穿越。编译在类定义时一次性发生；parse/build 每次调用
各一次穿越。Rust 内部遍历执行树的所有 C API 调用（创建 int、set_item、getattr 等）
**不计为 FFI 穿越**（FFI 设计 §2.4）。

### B.2 编译入口：compile_schema

```rust
/// Python 可见签名（概念性）：
///   compile_schema(cls: type, descriptors: list[Descriptor]) -> CompiledSchema
#[pyfunction]
fn compile_schema(
    py: Python<'_>,
    cls: &Bound<'_, PyType>,
    descriptors: &Bound<'_, PyList>,
) -> PyResult<CompiledSchema>;
```

**输入**：
- `cls`：用户类对象（`StructMixin` 子类）。用于：(a) 编译失败时在错误信息中报类名；
  (b) 作为执行树根 Struct 节点关联的类型引用（供 parse 时 `cls(**dict)` 构造实例）。
- `descriptors`：字段描述符列表，**按字段声明顺序排列**。每项是一个 pyclass 实例
  （Int8ub、Bytes 实例、GreedyBytes、或 StructMixin 子类）。

**Rust 内部流程**（一次 FFI 内完成，全为 C API 调用）：
1. 创建空的字段节点收集 `Vec<Node>`。
2. 遍历 `descriptors` 列表，对每个描述符：
   - 尝试 `extract::<FormatFieldDescriptor>` → 成功则构建 `Node::FormatField(...)`。
   - 尝试 `extract::<BytesDescriptor>` → 成功则构建 `Node::Bytes(...)`。
   - 尝试 `extract::<GreedyBytesDescriptor>` → 成功则构建 `Node::GreedyBytes`。
   - 尝试识别为 `StructMixin` 子类（检查 `issubclass`）→ 构建 `Node::StructRef(...)`。
   - 全部失败 → 返回 `ConstructError::UnknownDescriptor`，携带字段名与描述符 repr。
3. 将字段节点列表组装为 `Node::Struct { fields, cls_ref }` 作为根节点。
4. 返回 `CompiledSchema { root, cls_ref }`。

**描述符类型识别策略**：依赖 pyo3 的 `extract`（基于 `PyTypeInfo`）。每个描述符 pyclass
在 Rust 侧有对应的 Rust 结构体，`extract` 成功即匹配。这是类型安全的，无字符串标识。

**前向引用处理**：当描述符是 `StructMixin` 子类但该子类**尚未完成编译**（`_construct_compiled`
为 `None`，即对方类还在延迟桩阶段），编译器不为该字段报错，而是构建
`Node::StructRef { cls: Py<PyType>, lazy: true }`——存类引用，运行时动态解析（详见 §C.5）。
这保证互相引用的结构体（NodeA↔NodeB）可行（落实 REV 建议 1，关键）。

### B.3 parse 入口：CompiledSchema._parse_raw

```rust
#[pymethods]
impl CompiledSchema {
    /// Python 可见签名：
    ///   _parse_raw(self, data: bytes) -> dict[str, Any]
    #[pyo3(signature = (data))]
    fn _parse_raw<'py>(
        &self,
        py: Python<'py>,
        data: &Bound<'py, PyBytes>,
    ) -> PyResult<Bound<'py, PyDict>>;
}
```

**输入**：`data`（bytes 对象），用户传入的二进制数据。

**输出**：`PyDict`，键为字段名（str），值为字段解析结果（PyObject）。Python 侧用
`cls(**dict)` 构造实例。

**Rust 内部流程**（一次 FFI 内完成）：
1. 从 `PyBytes` 提取 `&[u8]`，创建 `ParseStream { data, pos: 0 }`（纯 Rust）。
2. 创建根 `Context`（持有空 `PyDict`，作为字段存储容器）。
3. 调用 `self.root.parse(stream, ctx, path)` —— 进入执行树遍历。
   - 每个节点通过 `match` 静态分派（FFI 设计 §6）。
   - 叶子节点（如 FormatField）读字节、通过 C API 创建 PyObject、返回。
   - Struct 节点创建子 `PyDict`，逐字段 set_item，最后返回该 dict。
   - 嵌套 StructRef 节点：获取对方 `CompiledSchema`，递归遍历其执行树（仍是 C API 操作）。
4. 返回根 Struct 节点产出的 `PyDict`。
5. 任何节点返回 `Err` → 通过 `?` 传播至入口，pyo3 自动转为 Python 异常（FFI 设计 §7）。

**为什么返回 dict 而非用户类实例**：见 §A.2。parse 严格保持一次 FFI（进入 Rust + 返回 dict），
实例构造在 Python 侧由 `cls(**dict)` 完成（解释器内部，无 FFI）。

### B.4 build 入口：CompiledSchema._build_raw

```rust
#[pymethods]
impl CompiledSchema {
    /// Python 可见签名：
    ///   _build_raw(self, obj: StructMixin) -> bytes
    fn _build_raw<'py>(
        &self,
        py: Python<'py>,
        obj: &Bound<'py, PyAny>,
    ) -> PyResult<Bound<'py, PyBytes>>;
}
```

**输入**：`obj`，用户类的实例（任意 StructMixin 子类实例）。Rust 通过 C API 读取其属性。

**输出**：`PyBytes`，构建的字节数据。

**Rust 内部流程**（一次 FFI 内完成）：
1. 创建 `BuildStream { buf: Vec<u8>::with_capacity(预估容量) }`（纯 Rust）。
2. 创建根 `Context`。
3. 调用 `self.root.build(obj, stream, ctx, path)` —— 进入执行树遍历。
   - Struct 节点：遍历字段，对每个字段 `getattr(obj, field_name)`（C API）取值，
     传递给子节点的 build。
   - 叶子节点（如 FormatField）：从 PyObject 提取数值（`extract::<i64>` 等），写入缓冲。
   - 嵌套 StructRef：`getattr(obj, field_name)` 取得子实例，递归 build。
4. 将 `Vec<u8>` 转为 `PyBytes` 返回。

**属性读取方式**：使用 `obj.getattr(name)`（对应 C API `PyObject_GetAttr`）。这兼容
普通 dataclass 实例（属性存在 `__dict__` 或为 slot）、`@dataclass(frozen=True)`、
以及任何实现了属性访问的对象。**不**假设对象内部是 dict 还是 slot。

**为什么不读 `__dict__` 直接访问**：`getattr` 是 Python 属性访问的标准语义，会触发
描述符协议、property、`__getattr__` 等。直接读 `__dict__` 会绕过这些，可能漏掉
`@property` 定义的字段。Phase 1 采用 `getattr` 保证语义正确。性能上 `getattr` 约
40–80ns（C API），可接受。

### B.5 Schema 从 Python 传到 Rust 的机制

```
┌─────────────────────────────────────────────────────────────────┐
│ Python 侧（__init_subclass__ 中）                                │
│                                                                 │
│  1. 遍历 cls.__dict__，按顺序收集 field() 返回值                 │
│  2. 从每个 field() 返回值提取 subcon（类型描述符）               │
│  3. 组装为 [(field_name, subcon), ...] 列表                     │
│  4. 调用 _native.compile_schema(cls, [subcon1, subcon2, ...])   │
│     （field_name 信息由描述符在列表中的位置隐式传递，             │
│      compile_schema 同时读取 cls 的 __annotations__ 获取字段名）  │
└─────────────────────────────────────────────────────────────────┘
                              │  1 次 FFI 穿越
                              ▼
┌─────────────────────────────────────────────────────────────────┐
│ Rust 侧（compile_schema 内）                                     │
│                                                                 │
│  1. 读取 cls.__annotations__，获取有序字段名列表                 │
│  2. 遍历 descriptors 列表，逐个 extract 为具体描述符类型          │
│  3. 根据描述符类型构建对应 Node                                   │
│  4. 组装为 Node::Struct { fields: Vec<(String, Node)>, cls }     │
│  5. 包装为 CompiledSchema 返回                                   │
└─────────────────────────────────────────────────────────────────┘
```

**字段名来源**：`cls.__annotations__`（类型注解字典，Python 3.7+ 保序）。`field()`
声明的字段必然有类型注解（`address: int = field(Int8ub)`），故 `__annotations__` 的
键集 ⊇ 字段集。编译器按 `__annotations__` 顺序取字段名，与 `descriptors` 列表位置对应。

**为什么不直接传字段名列表**：可以传。但利用 `__annotations__` 已有的有序信息更简洁，
且字段名与类型注解天然绑定（用户写 `address: int` 时，`address` 既是注解键又是字段名）。
实现上 Python 侧可显式传 `[(name, subcon), ...]` 元组列表，Rust 侧解包。两种等价，
DEV 实现时任选其一，本文档推荐传元组列表以减少 Rust 侧的 `__annotations__` 读取。

### B.6 编译产物 CompiledSchema 的结构与缓存

```rust
/// 编译产物：一棵不可变的执行树，关联到用户类。
#[pyclass(frozen, name = "CompiledSchema")]
pub struct CompiledSchema {
    /// 执行树根节点（通常是 Node::Struct）
    root: Node,
    /// 用户类的弱引用或引用，用于:
    /// - parse 时 Python 侧的 cls(**dict)（Python 侧已持有 cls，此处可选）
    /// - 调试与错误信息
    cls: Py<PyType>,
}
```

**不可变性**：`#[pyclass(frozen)]` 使 Python 侧无法修改其属性。Rust 侧 `root` 为
`Node` 枚举（不可变）。运行时不允许增删节点或修改参数（FFI 设计 §3.4）。

**缓存机制**（落实 Mixin 设计 §5.2 方案 A）：
- `CompiledSchema` 实例存为类属性 `cls._construct_compiled`。
- Python 属性查找是 O(1)（dict 查找）。
- `parse`/`build` 通过 `cls._construct_compiled` 访问，零编译开销。
- 重新定义类（重新执行 `class X(StructMixin): ...`）触发新的 `__init_subclass__`，
  覆盖旧的 `_construct_compiled`——这是预期行为（新类定义 = 新执行树）。

**线程安全**：`CompiledSchema` 是 `frozen` pyclass，内部 `Node` 不可变，可被多线程
安全共享（在 GIL 约束下）。parse/build 调用无副作用，可并发。

### B.7 dataclass 实例构造与属性读取（落实 FFI 设计 §5）

**parse 侧（构造实例）**：
- Rust 内部遍历执行树，对每个 Struct 节点构造 `PyDict`（C API `PyDict_New` +
  `PyDict_SetItem`），存入字段解析结果。
- 嵌套 Struct 字段：构造子 `PyDict`，作为父 dict 的一个值。
- parse 入口返回根 `PyDict`。Python 侧 `cls(**dict)` 构造实例。
- **嵌套字段的实例化**：Python 侧 `cls(**dict)` 中，dict 的嵌套 dict 值会被对应类的
  `__init__` 接收。但默认 dataclass `__init__` 不会递归转换嵌套 dict 为嵌套实例。

**嵌套实例化的处理**（关键设计点）：

对于 `Outer.inner: Inner`，parse 返回的根 dict 形如 `{'inner': {'x': 1}}`（inner 是
dict 而非 Inner 实例）。用户期望 `Outer(**dict).inner` 是 `Inner` 实例。

解决方案：**编译时记录每个字段的目标类型**。parse 时，Rust 遇到 StructRef 节点时，
调用对方类的构造（Rust→Python 回调，归类为必要用户钩子）：

```rust
// StructRef 节点的 parse（概念性）
fn parse(&self, stream, ctx, path) -> PyResult<Py<PyAny>> {
    let schema = self.resolve_schema(py)?;   // 通过 cls 引用获取对方 CompiledSchema
    let sub_dict = schema.root.parse(stream, ctx, path)?;  // 递归遍历，返回 PyDict
    // 调用对方类构造实例（Rust→Python 回调，归类为用户钩子）
    let instance = self.cls.call(py, (), Some(&sub_dict))?;
    Ok(instance)
}
```

此回调归类为 FFI 设计 §4.4 的"用户钩子"例外。开销：每 StructRef 节点一次回调，
约 200–400ns。对于扁平结构（Phase 1 主要用例），根 Struct 不回调（Python 侧构造），
仅嵌套层回调。N 层嵌套 = N-1 次回调。详见性能假设 §G.2。

**build 侧（读取属性）**：
- Rust 对每个字段 `obj.getattr(field_name)`（C API `PyObject_GetAttr`），取得值后传给
  子节点 build。
- 嵌套字段：`getattr(obj, "inner")` 返回 Inner 实例，递归 build。
- **无 Python 回调**——build 全程通过 C API 读取，严格一次 FFI。

### B.8 ConstructError 与 PyResult 的边界（落实 REV 建议 2）

**Rust 内部错误类型**：

```rust
/// construct-rs 内部统一错误类型，携带结构化信息。
#[derive(Debug, thiserror::Error)]
pub enum ConstructError {
    #[error("stream error: {message} at {path}")]
    Stream { message: String, path: String },

    #[error("format field error: {message} at {path}")]
    FormatField { message: String, path: String },

    #[error("field length error: {message} at {path}")]
    FieldLength { message: String, path: String },

    #[error("compilation error: {message}")]
    Compilation { message: String },

    #[error("unresolved type reference: {message}")]
    UnresolvedReference { message: String },

    #[error("{message} at {path}")]
    Generic { message: String, path: String },
}
```

**与 PyResult 的关系**：

```
节点方法签名:  fn parse(...) -> Result<T, ConstructError>     ← Rust 内部用结构化错误
                              ↓ impl From<ConstructError> for PyErr
FFI 入口签名:  fn _parse_raw(...) -> PyResult<PyDict>          ← 入口处转为 PyErr
                              ↓ pyo3 自动抛出
Python 侧:     except ConstructError as e: ...                 ← 用户捕获 Python 异常
```

- **Rust 内部**：所有节点方法返回 `Result<T, ConstructError>`。错误通过 `?` 传播。
  `ConstructError` 携带 `path`（出错位置）和结构化 `kind`（错误类别）。
- **FFI 入口**：三个入口函数返回 `PyResult<T>`。通过 `impl From<ConstructError> for PyErr`
  自动转换：`ConstructError::Stream` → Python `StreamError`，依此类推。
- **Python 侧**：异常层次与 Python construct 对齐（`ConstructError` 基类 → 各子类），
  携带 `path` 属性，`str(e)` 格式为 `"Error in path {path}\n{message}"`（与 Python construct 一致）。

**成功路径零成本**（FFI 设计 §7.3）：`Result` 是普通值，`?` 在成功时不分配错误对象。
错误对象（含 path 字符串）只在失败路径构造。

## C. Rust 执行模型

本节定义执行树的内部结构、Construct trait、enum_dispatch 静态分派、Stream 与 Context
抽象。这些都是 Rust 内部数据结构，**不跨 FFI**（FFI 设计 §4）。

### C.1 Construct trait

执行树的每个节点实现统一的 `Construct` trait。签名严格遵循"直接操作 Python 对象"原则
（FFI 设计 §5）：parse 返回 `Py<PyAny>`，build 接收 `&Bound<PyAny>`。

```rust
use pyo3::prelude::*;
use pyo3::types::{PyAny, PyDict};

/// 所有构造器节点实现的统一接口。
/// parse 直接产出 Python 对象，build 直接读取 Python 对象——不经过任何 Rust 中间类型。
pub trait Construct {
    /// 从流中解析，直接构造并返回 Python 对象。
    ///
    /// - `stream`: 字节流游标（纯 Rust，可读写位置）
    /// - `ctx`: 当前上下文（持有 Python dict 引用，供字段间引用）
    /// - `path`: 错误追踪路径栈（如 "header.flags"）
    fn parse(
        &self,
        py: Python<'_>,
        stream: &mut ParseStream<'_>,
        ctx: &mut Context<'_>,
        path: &mut Path,
    ) -> Result<Py<PyAny>, ConstructError>;

    /// 从 Python 对象构建，将字节写入流。
    ///
    /// - `obj`: 待构建的 Python 对象（用户实例或标量值）
    /// - `stream`: 输出缓冲
    fn build(
        &self,
        py: Python<'_>,
        obj: &Bound<'_, PyAny>,
        stream: &mut BuildStream,
        ctx: &mut Context<'_>,
        path: &mut Path,
    ) -> Result<(), ConstructError>;

    /// 静态大小（字节）。无法预知时返回 Err（对应 Python construct 的 SizeofError）。
    fn sizeof(&self, ctx: &Context<'_>) -> Result<usize, ConstructError>;
}
```

**签名设计要点**：
- `parse` 返回 `Py<PyAny>`：直接持有 Python 对象引用，无 Rust 中间枚举。
- `build` 接收 `&Bound<PyAny>`：直接读取任意 Python 对象，无 Rust 中间枚举。
- `Python<'_>` token 作为首参数：pyo3 要求持有 GIL 才能调用 C API，显式传递避免隐式获取。
- `ParseStream`/`BuildStream`/`Context`/`Path` 均为 Rust 内部类型，按引用传递（零拷贝）。

### C.2 Node 枚举与 enum_dispatch 静态分派

执行树的节点类型用封闭 `enum` 列举。使用 `enum_dispatch` 宏自动生成 `match` 分派代码，
使每个具体节点类型只需实现 `Construct` trait，无需手写 match 臂。

```rust
/// 执行树节点：封闭枚举，编译期类型集合固定。
/// 新增节点类型需在此枚举添加变体（Phase 2+ 扩展时修改）。
#[enum_dispatch(Construct)]
pub enum Node {
    // --- 叶子节点（原子构造器）---
    FormatField(FormatFieldNode),       // Int8ub / Int16ub / ... （struct 模块格式）
    Bytes(BytesNode),                   // Bytes(n)
    GreedyBytes(GreedyBytesNode),       // GreedyBytes

    // --- 复合节点 ---
    Struct(StructNode),                 // StructMixin 子类（字段序列）
    StructRef(StructRefNode),           // 嵌套引用其他 StructMixin 子类
}

// enum_dispatch 自动生成:
// impl Construct for Node {
//     fn parse(&self, ...) { match self {
//         Node::FormatField(n) => n.parse(...),
//         Node::Bytes(n) => n.parse(...),
//         ...
//     }}
//     fn build(&self, ...) { ... }
//     fn sizeof(&self, ...) { ... }
// }
```

**为什么用 enum_dispatch 而非手写 match**：
- 避免重复代码（每个方法都要 match 所有变体）。
- 每个节点类型只写一次 `impl Construct for XxxNode`。
- 宏展开后等价于手写 match，无运行时开销。
- 新增节点只需：在 enum 加变体 + 实现 Construct trait。

**禁止 Box<dyn Construct>**（FFI 设计 §6）：动态分派导致间接分支预测失败 + 堆分配，
对 50+ 字段结构退化约 50%。Node 枚举内联在 `Vec` 中，零堆分配，跳转表分派。

### C.3 节点类型定义（Phase 1 子集）

#### C.3.1 FormatFieldNode（整数读写）

```rust
/// 使用 struct 模块格式读写整数/浮点。
/// 对应 Python construct 的 FormatField。
pub struct FormatFieldNode {
    /// struct 格式字符串，如 ">B"（Int8ub）、"<h"（Int16sl）
    fmtstr: std::sync::OnceLock<PythonFormat>,
    /// 字节长度（编译期已知）
    length: usize,
}

/// 预编译的 struct 格式（避免每次 parse 重新解析 fmtstr）。
/// Phase 1 用 Rust 原生整数类型直接读写，不依赖 Python struct 模块。
pub enum PythonFormat {
    UnsignedInt8,    // >B, <B, =B
    SignedInt8,      // >b, <b, =b
    UnsignedInt16,   // >H, <H
    SignedInt16,     // >h, <h
    UnsignedInt32,   // >I, <I
    SignedInt32,     // >i, <i
    UnsignedInt64,   // >Q, <Q
    SignedInt64,     // >q, <q
    // Phase 2: Float32, Float64, Bool
}
```

**parse 行为**（对齐 Python construct `FormatField._parse`）：
1. `stream.read(self.length)` 读取 N 字节。
2. 根据 `fmtstr` 的字节序与符号性，用 Rust 原生方法解析为整数（如 `u8::from_be_bytes`）。
3. 通过 C API 创建 Python int 对象（`PyLong_FromLongLong` 等），返回 `Py<PyAny>`。
4. 失败（字节不足）→ `ConstructError::Stream`。

**build 行为**：
1. `obj.extract::<i64>()`（或对应类型）从 Python 对象提取数值。
2. 按字节序写入 stream（`to_be_bytes` / `to_le_bytes`）。
3. 类型不匹配 → `ConstructError::FormatField`。

#### C.3.2 BytesNode（固定长度字节）

```rust
/// 读取/写入固定长度的原始字节。
/// 对应 Python construct 的 Bytes(length)。
pub struct BytesNode {
    length: usize,   // Phase 1: 仅支持编译期常量
}
```

**parse**：`stream.read(length)` → 创建 `PyBytes`（C API）→ 返回。
**build**：`obj.extract::<&[u8]>()` 提取 bytes → 校验长度 == `length` → 写入 stream。
**sizeof**：返回 `length`。

#### C.3.3 GreedyBytesNode（剩余字节）

```rust
/// 读取流中剩余所有字节。
/// 对应 Python construct 的 GreedyBytes。
pub struct GreedyBytesNode;
```

**parse**：`stream.read_remaining()` → 创建 `PyBytes` → 返回。
**build**：提取 bytes → 写入（不校验长度）。
**sizeof**：返回 Err（大小未知，对应 SizeofError）。

#### C.3.4 StructNode（字段序列，根节点）

```rust
/// StructMixin 子类的根节点：按顺序解析/构建一组命名字段。
/// 对应 Python construct 的 Struct。
pub struct StructNode {
    /// 有序字段列表：(字段名, 子节点)
    fields: Vec<(String, Node)>,
}
```

**parse 行为**（对齐 Python construct `Struct._parse`）：
1. 创建 `PyDict`（C API `PyDict_New`）。
2. 对每个字段 `(name, node)`：
   - `let value = node.parse(stream, ctx, path)?;`（递归）
   - `path.push(name)`（进入字段路径）
   - `dict.set_item(name, value)?;`（C API）
   - `ctx.set_field(name, &value)?;`（存入上下文，供后续字段引用）
   - `path.pop()`（离开字段路径）
3. 返回 `PyDict`（Python 侧 `cls(**dict)` 构造实例）。

**build 行为**：
1. 对每个字段 `(name, node)`：
   - `let value = obj.getattr(name)?;`（C API `PyObject_GetAttr`）
   - `path.push(name)`
   - `ctx.set_field(name, &value)?;`
   - `node.build(py, &value, stream, ctx, path)?;`（递归）
   - `path.pop()`
2. 不返回值（字节已写入 stream）。

**sizeof**：累加所有字段的 sizeof（任一字段 SizeofError 则整体 SizeofError）。

#### C.3.5 StructRefNode（嵌套引用，落实 REV 建议 1 关键）

```rust
/// 引用另一个 StructMixin 子类的执行树，用于嵌套结构。
/// 存储类引用（Py<PyType>），运行时动态获取对方的 CompiledSchema——
/// 这保证互相引用（NodeA↔NodeB）可行。
pub struct StructRefNode {
    /// 对方类的 Python 引用
    cls: Py<PyType>,
    /// 缓存对方 CompiledSchema（首次 parse/build 时填充）
    /// 用 OnceCell 避免重复查找，但允许前向引用首次解析后更新
    schema_cache: std::sync::OnceLock<Py<CompiledSchema>>,
}
```

**resolve_schema 方法**（运行时动态解析，关键设计）：

```rust
impl StructRefNode {
    fn resolve_schema<'py>(
        &self,
        py: Python<'py>,
    ) -> Result<PyRef<'py, CompiledSchema>, ConstructError> {
        // 优先从缓存读取
        if let Some(schema) = self.schema_cache.get() {
            return Ok(schema.borrow(py));
        }
        // 缓存未命中：通过 C API 读取 cls._construct_compiled
        let cls_bound = self.cls.bind(py);
        let compiled = cls_bound
            .getattr("_construct_compiled")
            .map_err(|_| ConstructError::UnresolvedReference {
                message: format!(
                    "类 {} 尚未完成编译（可能存在未解析的前向引用）",
                    cls_bound.name()?
                ),
            })?;
        // compiled 为 None → 对方仍是延迟桩
        if compiled.is_none() {
            return Err(ConstructError::UnresolvedReference {
                message: format!("类 {} 仍是延迟桩，前向引用未解析", cls_bound.name()?),
            });
        }
        let schema: PyRef<CompiledSchema> = compiled.extract()?;
        // 填充缓存（OnceLock::set 失败说明并发已被填充，无碍）
        let _ = self.schema_cache.set(schema.into());
        Ok(schema)
    }
}
```

**为什么存类引用而非编译产物引用**（落实 REV 建议 1）：
- **互相引用场景**（NodeA.peer: NodeB，NodeB.peer: NodeA）：
  - NodeA 编译时，NodeB 尚未定义或未编译。
  - 若存编译产物引用，NodeA 编译时无法获取 NodeB 的产物。
  - 存类引用（`Py<PyType>`），NodeA 编译成功（只持有 NodeB 的类对象）。
  - 首次 `NodeA.parse(data)` 时，NodeB 已完成编译，`resolve_schema` 通过
    `cls._construct_compiled` 获取 NodeB 产物。
- **缓存机制**：`OnceLock` 首次解析后缓存，后续调用零查找开销。
- **延迟桩兼容**：若对方仍是延迟桩（`_construct_compiled` 为 None），返回
  `UnresolvedReference` 错误，Python 侧捕获后可触发对方的延迟编译并重试。

### C.4 Stream 抽象（落实 REV 建议 3）

Stream 是 Rust 内部的字节流游标，**不跨 FFI**。parse 和 build 各有一个 Stream 类型。

```rust
/// 解析流：包装输入字节切片，维护读取游标。
pub struct ParseStream<'a> {
    data: &'a [u8],
    pos: usize,
}

impl<'a> ParseStream<'a> {
    pub fn new(data: &'a [u8]) -> Self {
        Self { data, pos: 0 }
    }

    /// 读取 n 字节。不足时返回 StreamError（对齐 Python construct stream_read）。
    pub fn read(&mut self, n: usize, path: &Path) -> Result<&'a [u8], ConstructError> {
        if self.pos + n > self.data.len() {
            return Err(ConstructError::Stream {
                message: format!(
                    "stream read less than specified amount, expected {}, found {}",
                    n,
                    self.data.len() - self.pos
                ),
                path: path.to_string(),
            });
        }
        let result = &self.data[self.pos..self.pos + n];
        self.pos += n;
        Ok(result)
    }

    /// 读取剩余所有字节（GreedyBytes 用）。
    pub fn read_remaining(&mut self) -> &'a [u8] {
        let result = &self.data[self.pos..];
        self.pos = self.data.len();
        result
    }

    pub fn tell(&self) -> usize { self.pos }
    pub fn is_at_end(&self) -> bool { self.pos >= self.data.len() }
}

/// 构建流：输出缓冲区。
pub struct BuildStream {
    buf: Vec<u8>,
}

impl BuildStream {
    pub fn new() -> Self { Self { buf: Vec::new() } }

    pub fn write(&mut self, data: &[u8]) {
        self.buf.extend_from_slice(data);
    }

    pub fn into_bytes(self) -> Vec<u8> { self.buf }
}
```

**设计要点**：
- `ParseStream` 借用 `&[u8]`，零拷贝，读取返回切片引用（无需分配）。
- `BuildStream` 持有 `Vec<u8>`，预分配容量减少 reallocate。
- 所有方法纯 Rust，无 C API，无 FFI。
- read 失败时的错误信息与 Python construct `stream_read` 对齐（含 path、expected/found）。
- Phase 1 不支持 `seek`/`tell` 的复杂场景（如 Pointer、OnDemand），推迟到 Phase 3+。

### C.5 Context 抽象（落实 REV 建议 3）

Context 用于字段间引用（如 `Bytes(this.length)` 中 `this.length` 引用前序字段）和
嵌套层传递（Python construct 的 `_` 指向外层 context）。Phase 1 简化版仅存储已解析
字段，不支持 this 表达式（this 表达式推迟到 Phase 2）。

```rust
/// 解析/构建上下文。Rust 内部持有 Python dict 引用。
/// Phase 1: 仅存储字段值，不支持 this 引用（无表达式系统）。
/// Phase 2: 扩展支持 this.xxx 字段引用（通过 ctx.get_field 读取）。
pub struct Context<'py> {
    /// 当前层字段字典（PyDict 引用）
    /// parse 时存入已解析字段；build 时存入从对象读取的字段值
    fields: Bound<'py, PyDict>,
    /// 外层上下文（嵌套 Struct 时指向父 Context），对应 Python construct 的 _
    /// Phase 1 可为 None（顶层）
    parent: Option<&'py Context<'py>>,
}

impl<'py> Context<'py> {
    /// 创建顶层 context（parse/build 入口处）。
    pub fn new_root(py: Python<'py>) -> PyResult<Self> {
        Ok(Self {
            fields: PyDict::new(py),
            parent: None,
        })
    }

    /// 创建嵌套 context（Struct 节点进入时）。
    pub fn new_child(parent: &'py Context<'py>, py: Python<'py>) -> PyResult<Self> {
        Ok(Self {
            fields: PyDict::new(py),
            parent: Some(parent),
        })
    }

    /// 存入字段（parse/build 每个字段完成后调用）。
    pub fn set_field(&self, name: &str, value: &Bound<'_, PyAny>) -> PyResult<()> {
        self.fields.set_item(name, value)
    }

    /// 读取字段（Phase 2 的 this.xxx 引用使用）。
    /// Phase 1 不调用此方法（无 this 表达式）。
    pub fn get_field(&self, name: &str) -> PyResult<Option<Bound<'_, PyAny>>> {
        self.fields.get_item(name)
    }
}
```

**Phase 1 行为**：
- Struct 节点 parse 时 `new_child`，逐字段 `set_field`。
- 不调用 `get_field`（无 this 引用）。
- `Bytes(n)` 的 `n` 在编译期为常量，不从 context 读取。

**Phase 2 扩展点**：
- `get_field` 实现 this.xxx 引用。
- 表达式系统（this/obj_）在 Phase 2 设计，届时 Context 增加 `eval_expr` 方法。
- 完整的 `_root`、`_io`、`_index`、`_subcons` 等内部键（对齐 Python construct 的 Container）。

**为什么 Context 持有 PyDict 而非 Rust HashMap**：
- 字段值本身就是 Python 对象（`Py<PyAny>`），存入 PyDict 是 C API 调用（`PyDict_SetItem`），
  无需 Rust→Python 转换。
- this 引用读取时直接返回 Python 对象，无中间类型（FFI 设计 §5）。
- 与 Python construct 的 Container 语义一致。

### C.6 Path 错误追踪

```rust
/// 错误路径追踪栈。Struct 节点进入字段时 push，离开时 pop。
/// 错误发生时 to_string() 生成如 "header.flags[2]" 的路径。
pub struct Path {
    segments: Vec<PathSegment>,
}

pub enum PathSegment {
    Field(String),      // 结构体字段，如 "address"
    Index(usize),       // 数组元素，如 "[2]"（Phase 2 Array 支持）
}

impl Path {
    pub fn new() -> Self { Self { segments: vec![PathSegment::Field("(root)".into())] } }
    pub fn push_field(&mut self, name: &str) { self.segments.push(PathSegment::Field(name.into())); }
    pub fn push_index(&mut self, i: usize) { self.segments.push(PathSegment::Index(i)); }
    pub fn pop(&mut self) { self.segments.pop(); }
}

impl std::fmt::Display for Path {
    fn fmt(&self, f: &mut std::fmt::Formatter<'_>) -> std::fmt::Result {
        // 生成 "root.field1.field2[0]" 格式
        // 与 Python construct 的 path 格式对齐
        ...
    }
}
```

**性能保证**：`push`/`pop` 是 `Vec` 操作（~5ns），成功路径开销极小。`to_string` 只在
错误路径调用（FFI 设计 §7.3 成功路径零成本）。

## E. Schema 编译管线

本节定义从用户类定义到执行树构建的完整流程，覆盖 `__init_subclass__` 全过程、字段信息
收集、描述符传递、执行树构建、缓存与前向引用延迟桩。

### E.1 `__init_subclass__` 完整流程

```
┌─────────────────────────────────────────────────────────────────────┐
│ 用户代码执行: @dataclass class MyMsg(StructMixin): ...               │
└─────────────────────────────────────────────────────────────────────┘
                              │
                              ▼  Python 解释器创建类对象
┌─────────────────────────────────────────────────────────────────────┐
│ StructMixin.__init_subclass__(cls=MyMsg) 被调用                      │
│                                                                      │
│  1. 调用 _collect_field_descriptors(cls)                             │
│     → 遍历 cls.__dict__，提取所有 field() 返回值                      │
│     → 从每个 field() 返回值提取 subcon                                │
│     → 返回 [(field_name, subcon), ...] 有序列表                       │
│                                                                      │
│  2. 判断是否为空类（无字段）                                           │
│     → 是: 创建空 CompiledSchema（空 Struct 节点），存入 cls 属性       │
│           cls._construct_compiled = schema                            │

│                                                                      │
│  3. 尝试调用 _native.compile_schema(cls, descriptors)                │
│     ← 1 次 FFI 穿越（进入 Rust）                                      │
│     → Rust 构建执行树，返回 CompiledSchema                            │
│     ← 1 次 FFI 穿越（返回）                                           │
│                                                                      │
│  4a. 编译成功:                                                        │
│      cls._construct_compiled = schema                                 │
│      （parse/build 方法继承自 StructMixin，可直接使用）                │
│                                                                      │
│  4b. 编译抛出 UnresolvedReference（前向引用未解析）:                   │
│      → 安装延迟桩（详见 §E.6）                                        │
│      cls.parse = classmethod(_lazy_parse_stub)                        │
│      cls.build = _lazy_build_stub  (实例方法)                         │
│                                                                      │
│  4c. 编译抛出其他错误（描述符无效等）:                                 │
│      → 立即重新抛出（fail fast，编译错误在导入时报出）                 │
└─────────────────────────────────────────────────────────────────────┘
                              │
                              ▼  __init_subclass__ 返回
┌─────────────────────────────────────────────────────────────────────┐
│ @dataclass(MyMsg) 装饰器执行                                          │
│   → 生成 __init__, __repr__, __eq__, __dataclass_fields__            │
│ （StructMixin 不依赖这些，已用原始类体属性完成编译）                    │
└─────────────────────────────────────────────────────────────────────┘
```

### E.2 Python 端字段信息收集

```python
def _collect_field_descriptors(cls):
    """从类体收集字段信息，返回 [(field_name, subcon), ...] 有序列表。

    利用 Python 3.7+ __annotations__ 的有序性保证字段顺序。
    不依赖 __dataclass_fields__（此刻尚未生成）。
    """
    import_annotations = getattr(cls, '__annotations__', {})

    fields = []
    for field_name, _annotation in import_annotations.items():
        # field() 的返回值存为类属性的默认值
        default_value = cls.__dict__.get(field_name)
        if isinstance(default_value, _FieldDescriptor):
            # 提取 subcon（类型描述符）
            subcon = default_value.subcon
            fields.append((field_name, subcon))
        # 非 field() 声明的属性（普通方法、类变量等）跳过

    return fields
```

**字段顺序保证**（Mixin 设计 §4.3）：
- `__annotations__` 在 Python 3.7+ 保序（PEP 526）。
- 用户写 `address: int = field(Int8ub)` 时，`address` 同时进入 `__annotations__`
  和 `cls.__dict__`，顺序一致。
- `@dataclass` 的字段重排（如有默认值字段在无默认值之后）发生在 `__init_subclass__`
  之后，不影响编译收集的字段顺序。

**类型注解的作用**：仅用于 IDE 提示，不影响二进制格式。用户写 `address: int` 或
`address: Any` 都不影响 `field(Int8ub)` 的二进制语义。

### E.3 字段信息传递给 Rust 编译器

```python
# StructMixin.__init_subclass__ 中
descriptors = [subcon for (_name, subcon) in fields]
field_names = [name for (name, _subcon) in fields]

# 调用 Rust 编译入口（1 次 FFI）
cls._construct_compiled = _native.compile_schema(
    cls=cls,
    field_names=field_names,        # list[str]
    descriptors=descriptors,        # list[Descriptor pyclass]
)
```

**传递方式**：两个并行列表（字段名 + 描述符）。Rust 侧按下标配对，构建
`Vec<(String, Node)>`。这种传递方式比传元组列表更符合 pyo3 的类型提取约定
（`Vec<String>` + `Vec<Py<PyAny>>`）。

### E.4 编译器构建执行树

Rust 侧 `compile_schema` 流程：

```rust
#[pyfunction]
fn compile_schema(
    py: Python<'_>,
    cls: &Bound<'_, PyType>,
    field_names: Vec<String>,
    descriptors: Vec<Py<PyAny>>,
) -> PyResult<CompiledSchema> {
    // 1. 校验：field_names 与 descriptors 长度一致
    if field_names.len() != descriptors.len() {
        return Err(ConstructError::Compilation {
            message: format!("field_names ({}) 与 descriptors ({}) 长度不一致",
                field_names.len(), descriptors.len()),
        }.into());
    }

    // 2. 逐字段构建节点
    let mut fields: Vec<(String, Node)> = Vec::with_capacity(field_names.len());
    for (name, desc) in field_names.iter().zip(descriptors.iter()) {
        let desc_bound = desc.bind(py);
        let node = build_node_from_descriptor(py, desc_bound)
            .map_err(|e| e.with_field_context(name))?;
        fields.push((name.clone(), node));
    }

    // 3. 组装根 Struct 节点
    let root = Node::Struct(StructNode { fields });

    // 4. 包装为 CompiledSchema
    Ok(CompiledSchema {
        root,
        cls: cls.into_py(py),
    })
}

fn build_node_from_descriptor(
    py: Python<'_>,
    desc: &Bound<'_, PyAny>,
) -> Result<Node, ConstructError> {
    // 按优先级尝试 extract 为具体描述符类型
    // 顺序：先具体 pyclass，最后 StructMixin 子类引用

    if let Ok(fmt) = desc.extract::<FormatFieldDescriptor>() {
        return Ok(Node::FormatField(FormatFieldNode::from_descriptor(&fmt)));
    }
    if let Ok(b) = desc.extract::<BytesDescriptor>() {
        return Ok(Node::Bytes(BytesNode { length: b.length }));
    }
    if desc.extract::<GreedyBytesDescriptor>().is_ok() {
        return Ok(Node::GreedyBytes(GreedyBytesNode));
    }
    // StructMixin 子类引用：检查 isinstance(desc, type) 且 issubclass
    if let Ok(cls) = desc.extract::<Py<PyType>>() {
        let cls_bound = cls.bind(py);
        if is_structmixin_subclass(cls_bound)? {
            // 检查对方是否已编译
            let compiled = cls_bound.getattr("_construct_compiled")?;
            if compiled.is_none() {
                // 前向引用：对方仍是延迟桩
                return Ok(Node::StructRef(StructRefNode {
                    cls,
                    schema_cache: OnceLock::new(),
                }));
            }
            // 对方已编译：仍用 StructRef（运行时 resolve_schema 会命中缓存）
            return Ok(Node::StructRef(StructRefNode {
                cls,
                schema_cache: OnceLock::new(),
            }));
        }
    }

    Err(ConstructError::Compilation {
        message: format!("未知的字段描述符类型: {}", desc.repr()?),
    })
}
```

**描述符识别策略**：
- 用 pyo3 `extract::<T>` 按优先级匹配。
- 每个描述符 pyclass 在 Rust 侧有对应结构体（如 `FormatFieldDescriptor`）。
- 最后检查是否为 StructMixin 子类（`issubclass`）。
- 匹配失败 → 编译错误（fail fast，导入时报出）。

### E.5 编译产物缓存与递归引用解析

编译产物存为 `cls._construct_compiled`（Mixin 设计 §5.2 方案 A）。

**递归引用的解析时机**（落实 REV 建议 1，核心）：

| 场景 | 编译时 | 首次 parse 时 |
|------|--------|---------------|
| 简单引用（Inner 已编译） | StructRef 存 Inner 类引用 | `resolve_schema` 读取 `Inner._construct_compiled`，缓存 |
| 前向引用（Inner 未编译，延迟桩） | StructRef 存 Inner 类引用（编译成功） | `resolve_schema` 读取 `_construct_compiled`，若为 None 报错；否则缓存 |
| 互相引用（NodeA↔NodeB） | 两方都存对方类引用，都编译成功（延迟桩在另一类上） | parse NodeA 时，NodeB 已完成延迟编译，`resolve_schema` 成功 |

**关键洞察**：StructRef 存**类引用**（`Py<PyType>`）而非编译产物引用。这切断编译时
的循环依赖——互相引用的两方都能在 `__init_subclass__` 中编译成功（因为不立即获取对方
产物，只存类引用）。运行时通过 `_construct_compiled` 类属性动态获取。

### E.6 延迟桩机制（落实 Mixin 设计 §6）

当 `compile_schema` 抛出 `UnresolvedReference`（某字段的 StructRef 指向的类连延迟桩都
没有，即类完全未定义），编译器无法构建该字段节点。此时安装延迟桩：

```python
def _install_lazy_stubs(cls):
    """安装延迟桩：首次 parse/build 时重试编译。"""
    cls._construct_compiled = None  # 标记未编译

    @classmethod
    def _lazy_parse(cls_, data):
        _retry_compile(cls_)              # 首次调用重试编译
        return _StructMixin_parse(cls_, data)  # 调用真正的 parse

    def _lazy_build(self):
        _retry_compile(type(self))        # 首次调用重试编译
        return _StructMixin_build(self)   # 调用真正的 build

    cls_.parse = _lazy_parse
    cls_.build = _lazy_build
```

```python
import threading
_lazy_compile_lock = threading.Lock()

def _retry_compile(cls):
    """首次调用时重试编译。线程安全。"""
    if cls._construct_compiled is not None:
        return  # 已编译（可能是其他线程已完成）
    with _lazy_compile_lock:
        if cls._construct_compiled is not None:
            return  # 双重检查
        descriptors = _collect_field_descriptors(cls)
        field_names = [n for (n, _) in descriptors]
        subcons = [s for (_, s) in descriptors]
        # 重试编译：此时前向引用的类可能已完成编译
        schema = _native.compile_schema(cls, field_names, subcons)
        cls._construct_compiled = schema
        # 替换桩为真正方法
        cls.parse = _StructMixin_parse
        cls.build = _StructMixin_build
```

**线程安全**（Mixin 设计 §6.4）：`threading.Lock` + 双重检查确保编译只发生一次。
首次调用后，桩被替换为真正方法，后续调用零开销。

**延迟桩的适用边界**：
- 仅当 `compile_schema` 抛出 `UnresolvedReference` 时安装。
- 其他编译错误（无效描述符等）立即抛出，不延迟。
- 一旦编译成功，桩被永久替换，不再触发重试。

**注意**：StructRef 指向"已定义但未编译"的类（对方有延迟桩）时，`compile_schema` **不**
抛 `UnresolvedReference`——它成功构建 StructRef 节点（存类引用）。只有在描述符既不是
已知 pyclass 也不是 StructMixin 子类时，才抛编译错误。

### F.4 Phase 1 的语义对齐保证

Phase 1 实现的格式类型必须与 Python construct 2.10.70 的语义**完全一致**：

| 检查项 | Python construct 行为 | Phase 1 对齐 |
|--------|----------------------|--------------|
| Int8ub.parse 读取 1 字节大端无符号 | `struct.unpack(">B", data)[0]` | Rust `u8::from_be_bytes`，结果一致 |
| Bytes(n).parse 读取 n 字节 | `stream.read(n)`，返回 bytes | Rust 切片，转 PyBytes |
| Bytes(n).build 校验长度 | `len(data) != length` → StreamError | Rust 校验，同错误 |
| GreedyBytes.parse 读取剩余 | `stream.read()` | Rust `read_remaining` |

| Struct.build 缺字段 | `obj[name]` → KeyError | Rust `getattr` 失败 → ConstructError |
| 错误携带 path | `"Error in path {}\n".format(path) + message` | Rust Path::to_string，同格式 |

DEV 实现时须对照 `construct/construct/core.py` 的 `FormatField._parse/_build`、
`Bytes._parse/_build`、`GreedyBytes._parse/_build`、`Struct._parse/_build` 的逐行语义。

## G. 性能假设（性能门禁 §1 落实）

本节列出 Phase 1 路径上的所有性能瓶颈来源、可证伪预测、验证方法。这是性能门禁要求的
"性能假设"段落。

### G.1 瓶颈识别与可证伪预测

#### 瓶颈 1：FFI 穿越次数

- **来源**：parse/build 入口的 Python→Rust 穿越。
- **设计目标**：parse 严格 1 次（进入 + 返回），build 严格 1 次。
- **可证伪预测**：若 parse 的 FFI 穿越次数从 1 增加到 N（N = 字段数），性能退化为 O(N)
  FFI 开销。10 字段 × 200ns/穿越 = 2000ns 纯 FFI 开销，占总开销 > 50%。
- **量级预期**：parse FFI 开销恒定 ~400ns（进入 + 返回），与字段数无关。10 字段结构中
  FFI 开销占比 < 10%。

#### 瓶颈 2：节点分派开销

- **来源**：执行树遍历时每个节点的 match 分派。
- **设计目标**：静态分派（enum + match），编译器优化为跳转表。
- **可证伪预测**：若改用 `Box<dyn Construct>`（动态分派），每节点额外 6ns 间接分支预测
  失败 + 堆分配。50 字段 = 300ns + 堆分配开销，占纯计算 ~50%。
- **量级预期**：静态分派每节点 ~2-5ns（跳转表 + 内联）。10 字段 = ~30-50ns。

#### 瓶颈 3：C API 调用（PyObject 构造与属性操作）

- **来源**：parse 时创建 int 对象（`PyLong_FromLongLong`）、dict set_item；
  build 时 getattr、extract 数值。
- **不可避免**：这是"直接操作 Python 对象"的必要成本（FFI 设计 §5）。
- **可证伪预测**：若改用 Rust 中间类型再转换，每字段双重遍历 + 额外内存分配，
  实测退化为 0.3-1.8x（FFI 设计 §5.3 历史教训）。
- **量级预期**：每字段 C API 开销 ~80-150ns（创建 int ~40ns + set_item ~40ns +
  其他 ~40ns）。10 字段 = ~1000-1500ns。

#### 瓶颈 4：用户类实例构造（parse 侧用户钩子回调）

- **来源**：Python 侧 `cls(**dict)` 构造实例；嵌套 StructRef 的 Rust→Python 回调。
- **归类**：FFI 设计 §4.4 的用户钩子例外，不可避免。
- **可证伪预测**：若每次字段解析都构造实例（而非只在 Struct 边界），N 字段 = N 次回调，
  10 字段 = 2000-4000ns，与 C API 开销相当，性能优势消失。
- **量级预期**：
  - 扁平结构（Phase 1 主要用例）：根 Struct 实例化在 Python 侧 `cls(**dict)`，
    无 Rust→Python 回调。FFI 穿越 = 1（_parse_raw）。
  - 嵌套结构（K 层）：K-1 次 StructRef 回调（每层 ~200-400ns）。
    3 层嵌套 = 2 次回调 = ~400-800ns。

#### 瓶颈 5：Context 操作（字段存入上下文）

- **来源**：每字段 `ctx.set_field(name, value)`（PyDict_SetItem）。
- **量级预期**：每字段 ~40ns。10 字段 = ~400ns。Phase 2 的 this 引用会额外增加 get_item
  开销，但 Phase 1 无此开销。

#### 瓶颈 6：内存分配

- **来源**：执行树节点（编译期，非热路径）；parse 输出 PyDict；build 输出 Vec<u8>。
- **设计目标**：执行树节点内联在 Vec（零堆分配）；PyDict 由 Python 内存管理；
  BuildStream 预分配容量。
- **量级预期**：热路径仅 PyDict 创建（~50ns）+ Vec 预分配（一次性）。可忽略。

### G.2 性能加速比预测

以 10 字段扁平 Struct 为基准（Phase 1 典型用例）：

| 组件 | construct-rs 预期 | Python construct 预期 | 加速来源 |
|------|-------------------|----------------------|---------|
| FFI 穿越（parse） | ~400ns | 0（纯 Python） | — |
| 节点分派 | ~40ns | ~3000ns（解释器分派 30-50ns × 60 指令） | enum_dispatch |
| C API 调用 | ~1200ns | ~3000ns（dict 操作 + int 创建） | C API vs Python 字节码 |
| Context 操作 | ~400ns | ~2000ns（Container 操作） | PyDict 直接操作 |
| 实例构造 | ~300ns（Python 侧 cls(**dict)） | ~2000ns | dataclass __init__ |
| **总计** | **~2340ns** | **~10000ns** | **~4.3x** |

**预测加速比：约 4-5x**（满足 ≥4x 硬目标，接近理想 10x 需进一步优化）。

对于大结构（100 字段），Python construct 的解释器开销线性增长，construct-rs 的 C API
开销也线性增长但系数更小，加速比预期提升至 6-8x。

### G.3 性能退化场景（须在基准测试中暴露）

| 场景 | 退化原因 | 预期退化 | 验证方式 |
|------|---------|---------|---------|
| 深度嵌套（10 层） | 每层 StructRef 回调 | 加速比降至 2-3x | 嵌套基准测试 |
| 小结构（1-2 字段） | FFI 固定开销占比高 | 加速比降至 1.5-2x | 小结构基准测试 |
| 用户回调（Phase 2） | 每回调 1 次 FFI 穿越 | 视回调密度 | Phase 2 基准测试 |

这些退化是设计权衡的已知代价（FFI 设计 §8.3），基准测试必须包含对应场景以暴露。

### G.4 验证方法（基准测试设计，落实性能门禁 §1）

#### G.4.3 测量方法

```python
import timeit

t_rs = timeit.timeit(lambda: ModbusRTUMessage.parse(data), number=100000)

assert speedup >= 4.0, f"性能未达标: {speedup}x < 4x"
```

- **number**：足够大（≥ 100000）以消除计时误差。
- **首次调用排除**：timeit 自动预热（取最小值）。
- **重复测量**：5 次取中位数。
- **parse 与 build 分别测量**。

## 附录 A：与 Python construct 的 API 差异说明

construct-rs 的用户 API 与 Python construct 2.10.70 有意不同（mashumaro 式 vs 命令式）：

| 维度 | Python construct | construct-rs | 差异原因 |
|------|-----------------|--------------|---------|
| 结构定义 | `Struct("a"/Int8ub, "b"/Bytes(4))` 命令式 | `@dataclass class X(StructMixin): a=field(Int8ub)` 声明式 | 用户无感、类型提示、IDE 友好 |
| parse 调用 | `Struct.parse(data)` 返回 Container | `X.parse(data)` 返回 X 实例 | 与 @dataclass 集成 |
| build 调用 | `Struct.build(dict)` 传 dict | `instance.build()` 传实例 | 实例方法更自然 |
| 结果类型 | Container（dict 子类） | 用户类实例 | 类型安全、属性访问 |
| 字段引用 | `this.length`（运行时表达式） | Phase 1 无，Phase 2 支持 | 渐进实现 |

Python construct 的 `Struct("a"/Int8ub)` 命令式 API **不在** construct-rs 的 Phase 1
范围（推迟到 Phase 2+ 评估）。Phase 1 仅支持 StructMixin 声明式 API。

## 附录 B：设计决策溯源

| 决策 | 备选方案 | 选择理由 |
|------|---------|---------|
| StructMixin 用纯 Python | Rust pyclass | 元编程逻辑（__init_subclass__、延迟桩）Python 更灵活 |
| 类型描述符用 pyclass | 纯 Python 对象 | 类型安全（extract）、Rust 直接读取参数 |
| Node 用 enum_dispatch | Box<dyn Construct> | 静态分派，消除堆分配与间接跳转（FFI 设计 §6） |
| parse 返回 dict | Rust 内部构造实例 | 严格一次 FFI，实例构造在 Python 侧无 FFI |
| StructRef 存类引用 | 存编译产物引用 | 解决互相引用的循环依赖（REV 建议 1） |
| Context 持有 PyDict | Rust HashMap | 字段值本就是 PyObject，直接操作无中间类型 |
| 错误用 ConstructError + From | 直接用 PyErr | 结构化 path/kind，成功路径零成本 |
