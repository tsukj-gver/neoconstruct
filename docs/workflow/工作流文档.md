# 工作流文档

## 1. 概述

本文档定义 construct-rs 项目的开发工作流。工作流围绕**阶段（Phase）**组织，每个阶段内的每个**子任务**必须经过完整的流程管道，通过多层角色校验后方可标记完成。

工作流的核心设计目标：防止**设计缺陷、漏开发、漏测、接口不一致、实现逻辑错误**五类问题。

## 2. 角色总览

| 角色 | 简称 | agent 名 | 核心职责 |
|------|------|---------|---------|
| 项目经理 | PM | `pm` | 任务分派、进度追踪、阶段验收 |
| 架构师 | ARCH | `architect` | 设计文档编写与维护、接口一致性把关 |
| 开发者 | DEV | `developer` | 代码实现、单元测试编写 |
| 审查员 | REV | `reviewer` | **设计检视**：延续性、性能、整体性、可行性、完备性 |
| 检验员 | VET | `vetter` | **代码审查**：逻辑正确性、错误处理、行为一致性、资源安全、边界条件 |

> 角色是"帽子"概念，同一人可戴不同帽子，但同一子任务中**禁止一人同时担任 DEV + REV/VET**。

> **已移除**：对照验证员（REF）角色。其 Python 行为对比职责已并入 VET 的代码审查清单。

## 3. 子任务生命周期

每个子任务从总纲中取出后，经历以下状态流转：

```
┌──────────┐  ┌───────────┐  ┌──────────────┐  ┌──────────┐  ┌───────────┐  ┌───────────┐
│  PENDING │─>│ DESIGNING │─>│ DESIGN_REVIEW│─>│  CODING  │─>│ CODE_REVIEW│─>│  ACCEPTED │
│  (待设计) │  │  (设计中)  │  │  (设计检视)   │  │ (开发中)  │  │ (代码审查) │  │  (已通过)  │
└──────────┘  └───────────┘  └──────────────┘  └──────────┘  └───────────┘  └───────────┘
    PM            ARCH             REV            DEV            VET            PM
   分派任务      编写设计        检视设计         编码+自测      审查代码        确认完成
                 ARCH → REV      REV → DEV      DEV → VET      VET → PM
                                 通过/驳回                      通过/驳回
```

### 3.1 PENDING → DESIGNING

**触发**：PM 从总纲中选取下一个子任务，分配给 ARCH。

**产出**：
- 子任务对应的模块设计文档（或确认已有设计文档覆盖）
- 设计文档中必须包含：接口签名、数据流向、调用方向、边界条件清单

**入口条件**：上一阶段已完成验收（或 PM 授权并行）

**出口条件**：ARCH 确认设计文档就绪，提交给 REV 检视

### 3.2 DESIGNING → DESIGN_REVIEW

**触发**：ARCH 完成设计文档，PM 分配给 REV 进行设计检视。

**目的**：在开发开始前，确保设计在**延续性、性能、整体性**上没有问题。
避免"设计错误到代码审查阶段才发现"的返工浪费。

**REV 设计检视清单**：
- [ ] **延续性**：设计与已有架构一致，不破坏已有接口契约
- [ ] **性能**：设计不会引入已知的性能瓶颈（FFI 边界、不必要的拷贝、反复转换等）
- [ ] **整体性**：设计与全局架构图一致，模块边界清晰，调用方向正确
- [ ] **可行性**：设计在 Rust + PyO3 技术栈下可实现，无已知技术障碍
- [ ] **完备性**：设计覆盖了所有边界条件，没有遗漏的行为

**入口条件**：ARCH 确认设计文档就绪

**出口条件**：
- 全部清单项通过 → 进入 CODING
- 有不通过项 → 驳回至 DESIGNING，ARCH 修改设计后重新提交检视

### 3.3 DESIGN_REVIEW → CODING

**触发**：REV 设计检视通过，PM 将开发任务分配给 DEV。

**产出**：
- Rust 源代码实现
- 单元测试代码
- 过程记录更新（操作日志）

**DEV 自检清单**（开发完成前必须逐项确认）：
- [ ] 编译通过：`cargo build` 零 error
- [ ] 规范通过：`cargo clippy` 零 warning，`cargo fmt --check` 通过
- [ ] 单元测试通过：`cargo test` 全部 PASS
- [ ] 接口对照：公开 API 与设计文档中的签名一致
- [ ] 无 panic：非法输入返回 `Err` 而非 panic / unwrap

**入口条件**：REV 设计检视通过

**出口条件**：DEV 自检清单全部勾选

### 3.4 CODING → CODE_REVIEW

**触发**：DEV 自检通过，PM 分配给 VET 进行代码审查。

**VET 代码审查清单**：
- [ ] **逻辑正确性**：核心算法与设计文档描述一致，无逻辑漏洞
- [ ] **行为一致性**：针对相同输入，Rust 版本的 parse/build 输出与 Python 版本一致
- [ ] **错误处理完整**：所有可能失败的操作都有错误处理，无遗漏
- [ ] **错误行为**：相同错误输入，抛出的错误类型与 Python 版本对应
- [ ] **资源安全**：无内存泄漏、无未初始化数据、无 unsafe 不当使用
- [ ] **API 一致性**：与已实现的其他模块的 API 风格统一
- [ ] **性能**：无明显的性能反模式（不必要的拷贝、反复 FFI 穿越等）
- [ ] **边界条件**：空输入、最大值、零值、溢出等场景行为正确

**入口条件**：DEV 自检通过

**出口条件**：
- 全部清单项通过 → 进入 ACCEPTED
- 有不通过项 → 驳回至 CODING，附具体审查意见

### 3.5 CODE_REVIEW → ACCEPTED

**触发**：VET 审查通过。

**PM 确认**：
- [ ] 过程记录完整（所有操作已记录）
- [ ] 子任务所有产出物已就位（代码、测试、文档更新）
- [ ] 该子任务的总纲清单项可标记为 `[x]`
- [ ] 执行 `git add` + `git commit`（commit message: `feat(phaseN): X.Y 描述`）

## 4. 驳回与返工

当 REV 或 VET 驳回子任务时：

1. 驳回人在过程记录中记录具体问题
2. **设计检视驳回**（REV → DESIGNING）：ARCH 修改设计 → 重新提交 REV 检视
3. **代码审查驳回**（VET → CODING）：DEV 修复 → 重新提交 VET 审查
4. 修复后须重新走该阶段的完整检视/审查流程
5. 修复版本可仅审查被驳回相关的部分，但须确认修复未引入新问题

## 4.5 简化流程与合并设计

**简化流程（trivial）**：对于 `trivial` 性质的子任务（如项目初始化、纯文档更新），PM 可标注为 trivial。trivial 子任务跳过 DESIGNING 和 DESIGN_REVIEW 阶段，仅走 CODING → CODE_REVIEW。

**合并设计**：关联紧密的多个子任务，PM 可合并为一次 ARCH 分派，产出一份合并的模块设计文档。

**子任务粒度调整**：任何角色发现子任务粒度不当时（过大需拆分、过小需合并），可向 PM 提议。

## 4.6 设计质疑（Argue 机制）

任何角色在执行任务过程中发现设计文档存在不合理、冲突或遗漏时，可向 PM 提出质疑。PM 将质疑转发给 ARCH，ARCH 必须回应。

### 流程

```
DEV/VET/REV 发现设计问题
  │
  ├─ 小问题（参数类型微调、方法签名调整）
  │   → 执行者按自认为合理的方式实现，在返回报告中标注 [设计质疑]
  │   → PM 转发 ARCH 确认
  │
  └─ 大问题（架构冲突、核心逻辑矛盾）
      → 执行者暂停，立即向 PM 报告 [设计质疑]
      → PM 分派 ARCH 回应
      → ARCH 回复后，执行者继续
```

### ARCH 回应方式（三选一）

1. **确认设计正确**：附解释，说明质疑方遗漏的上下文
2. **修改设计文档**：确认质疑成立，修改设计文档并说明变更
3. **标记后续处理**：确认问题存在但不影响当前阶段，标记为已知问题

## 5. 阶段验收流程

一个阶段内所有子任务均 ACCEPTED 后，执行阶段验收：

**阶段验收检查清单**：
- [ ] 总纲中所有子任务 `[x]` 已完成
- [ ] `cargo build` 零 error，`cargo clippy` 零 warning
- [ ] `cargo test` 全部 PASS
- [ ] `cargo fmt --check` 通过
- [ ] 所有模块间接口调用正常（无编译/链接错误）
- [ ] 过程记录完整
- [ ] 阶段出口标准全部满足
- [ ] `plans/00-项目进度.md` 已更新
- [ ] `git tag phase-N-complete` 已打标签

## 6. 文件更新规范

| 步骤 | 更新文件 | 更新内容 |
|------|---------|---------|
| 任务分派 | `plans/phaseN/过程记录.md` | 填写子任务的负责人、开始时间、状态 |
| 任务分派 | `plans/00-项目进度.md` | 更新当前焦点 |
| 设计完成 | `docs/` 下设计文档 | 编写或更新设计文档 |
| 设计检视 | `plans/phaseN/过程记录.md` | REV 记录检视意见 |
| 开发完成 | `plans/phaseN/过程记录.md` | DEV 记录操作日志、自检结果 |
| 代码审查 | `plans/phaseN/过程记录.md` | VET 记录审查意见 |
| 子任务完成 | `plans/phaseN/总纲.md` | 标记 `[x]` |
| 子任务完成 | `plans/00-项目进度.md` | 更新计数 |
| 子任务完成 | git | PM 执行 commit |
| 阶段验收 | git | PM 执行 tag |

## 7. 跨阶段接口一致性保障

1. **设计先行**：每个阶段的设计文档必须明确与已有模块的交互接口
2. **设计检视**：REV 在开发前检视设计的延续性和整体性
3. **API 变更审批**：修改已验收模块的公开 API 须经 ARCH 审批
4. **总设计文档同步**：接口变更须同步更新总设计文档

## 8. 缺陷追踪

| 问题类型 | 处理方式 | 记录位置 |
|---------|---------|---------|
| 设计缺陷 | 驳回至 DESIGNING | 过程记录 + 设计文档 |
| 实现遗漏 | 驳回至 CODING | 过程记录 |
| 测试遗漏 | 驳回至 CODING | 过程记录 |
| 接口不一致 | 驳回至 CODING 或 DESIGNING | 过程记录 + 设计文档 |
| 逻辑错误 | 驳回至 CODING | 过程记录 |
| 代码质量 | 驳回至 CODING | 过程记录 |

## 9. 工作流简明视图

```
子任务工作流:

  PM ──> ARCH ──> REV ──> DEV ──> VET ──> PM ──> DONE
         设计     检视     编码     审查     确认
                    ^                 |
                    |                驳回
                    +────────────────+
```
