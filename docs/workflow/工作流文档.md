# 工作流文档

## 1. 概述

本文档定义 construct-rs 项目的开发工作流。工作流围绕**阶段（Phase）**组织，每个阶段内的每个**子任务**必须经过完整的流程管道，通过多层角色校验后方可标记完成。

工作流的核心设计目标：防止**漏开发、漏测、接口不一致、实现逻辑错误**四类问题。

## 2. 角色总览

| 角色 | 简称 | 核心职责 |
|------|------|---------|
| 项目经理 | PM | 任务分派、进度追踪、阶段验收 |
| 架构师 | ARCH | 设计文档编写与维护、接口一致性把关 |
| 开发者 | DEV | 代码实现、单元测试编写 |
| 对照验证员 | REF | 与 Python 版本的行为对比验证 |
| 代码审查员 | REV | 代码质量、逻辑正确性、安全性审查 |

> 角色是"帽子"概念，同一人可戴不同帽子，但同一子任务中**禁止一人同时担任 DEV + REV/REF**。

## 3. 子任务生命周期

每个子任务从总纲中取出后，经历以下状态流转：

```
┌──────────┐    ┌───────────┐    ┌──────────┐    ┌───────────┐    ┌──────────┐    ┌───────────┐
│  PENDING │───>│ DESIGNING │───>│ CODING   │───>│ VERIFYING │───>│ REVIEWING│───>│  ACCEPTED │
│  (待设计) │    │  (设计中)  │    │ (开发中)  │    │ (对照验证) │    │ (代码审查)│    │  (已通过)  │
└──────────┘    └───────────┘    └──────────┘    └───────────┘    └──────────┘    └───────────┘
     PM              ARCH             DEV              REF              REV             PM
   分派任务        编写/确认         编码+自测       Python行为对比     逻辑+质量审查     确认完成
                   模块设计文档                                         通过/驳回
```

### 3.1 PENDING → DESIGNING

**触发**：PM 从总纲中选取下一个子任务，分配给 ARCH。

**产出**：
- 子任务对应的模块设计文档（或确认已有设计文档覆盖）
- 设计文档中必须包含：接口签名、与 Python 版本的 API 映射表、边界条件清单

**入口条件**：上一阶段已完成验收

**出口条件**：ARCH 确认设计文档就绪

### 3.2 DESIGNING → CODING

**触发**：ARCH 完成设计文档，PM 将开发任务分配给 DEV。

**产出**：
- Rust 源代码实现
- 单元测试代码
- 过程记录更新（操作日志）

**DEV 自检清单**（开发完成前必须逐项确认）：
- [ ] 编译通过：`cargo build` 零 error
- [ ] 规范通过：`cargo clippy` 零 warning，`cargo fmt --check` 通过
- [ ] 单元测试通过：`cargo test` 全部 PASS
- [ ] 接口对照：公开 API 与设计文档中的签名一致
- [ ] 无 panic：非法输入返回 `Err` 而非 panic / unwrap

**入口条件**：设计文档已就绪

**出口条件**：DEV 自检清单全部勾选

### 3.3 CODING → VERIFYING

**触发**：DEV 自检通过，PM 分配给 REF 进行对照验证。

**产出**：
- 对照验证报告（记录在过程记录文件中）
- 发现的问题清单（如有）

**REF 验证清单**：
- [ ] **功能覆盖**：Python 版本该模块的所有公开方法/类，Rust 版本均有对应实现
- [ ] **行为一致性**：针对相同的输入数据，Rust 版本的 parse/build 输出与 Python 版本一致
- [ ] **错误行为**：相同错误输入，Rust 版本抛出的错误类型与 Python 版本对应
- [ ] **边界条件**：空输入、最大值、零值、溢出等场景行为一致
- [ ] **sizeof 一致性**：sizeof 返回值与 Python 版本一致

**入口条件**：DEV 自检通过

**出口条件**：
- 全部清单项通过 → 进入 REVIEWING
- 有不通过项 → 驳回至 CODING，附具体问题描述

### 3.4 VERIFYING → REVIEWING

**触发**：REF 验证通过，PM 分配给 REV 进行代码审查。

**产出**：
- 代码审查意见（记录在过程记录文件中）
- 通过 / 驳回决定

**REV 审查清单**：
- [ ] **逻辑正确性**：核心算法与设计文档描述一致，无逻辑漏洞
- [ ] **错误处理完整**：所有可能失败的操作都有错误处理，无遗漏
- [ ] **资源安全**：无内存泄漏、无未初始化数据、无 unsafe 不当使用
- [ ] **API 一致性**：与已实现的其他模块的 API 风格统一
- [ ] **上下文传递**：Context 在子构造器间正确传递，无丢失或错位
- [ ] **路径追踪**：错误路径（path）正确拼接，能精确定位出错位置

**入口条件**：REF 验证通过

**出口条件**：
- 全部清单项通过 → 进入 ACCEPTED
- 有不通过项 → 驳回至 CODING，附具体审查意见

### 3.5 REVIEWING → ACCEPTED

**触发**：REV 审查通过。

**PM 确认**：
- [ ] 过程记录完整（所有操作已记录）
- [ ] 子任务所有产出物已就位（代码、测试、文档更新）
- [ ] 该子任务的总纲清单项可标记为 `[x]`
- [ ] 执行 `git add` + `git commit`（commit message: `feat(phaseN): X.Y 描述`）

## 4. 驳回与返工

当 REF 或 REV 驳回子任务时：

1. 驳回人在过程记录中记录具体问题
2. 任务状态回退至 CODING
3. DEV 修复后重新执行自检 → 重新提交 REF → REV
4. 修复版本 REV 可仅审查被驳回相关的部分，但须确认修复未引入新问题；REF 须重新跑完整验证清单

## 4.5 简化流程与合并设计

**简化流程（trivial）**：对于 `trivial` 性质的子任务（如项目初始化、纯文档更新），PM 可在总纲中标注为 trivial。trivial 子任务跳过 DESIGNING 和 VERIFYING 阶段，仅走 CODING → REVIEWING。ARCH 设计和 REF 对照验证在 trivial 任务中不强制。

**合并设计**：关联紧密的多个子任务（如 Value 类型 + Context 容器），PM 可合并为一次 ARCH 分派，产出一份合并的模块设计文档覆盖所有关联子任务。

**子任务粒度调整**：任何角色发现子任务粒度不当时（过大需拆分、过小需合并），可向 PM 提议。PM 审批后在总纲中更新子任务清单，并在过程记录中记录调整原因。

## 4.6 设计质疑（Argue 机制）

任何角色在执行任务过程中发现设计文档存在不合理、冲突或遗漏时，可向 PM 提出质疑。PM 将质疑转发给 ARCH，ARCH 必须回应。

### 触发条件

- 设计签名与 Python 源码逻辑冲突
- 设计中遗漏了 Python 源码的重要行为
- 设计中存在 Rust 无法实现或严重不惯用的模式
- 多个设计文档之间存在接口矛盾

### 流程

```
DEV/REF/REV 发现设计问题
  │
  ├─ 小问题（参数类型微调、方法签名调整）
  │   → 执行者按自认为合理的方式实现，在返回报告中标注 [设计质疑]
  │   → PM 转发 ARCH 确认
  │   → ARCH 在 REVIEWING 阶段前回复
  │
  └─ 大问题（架构冲突、核心逻辑矛盾）
      → 执行者暂停，立即向 PM 报告 [设计质疑]
      → PM 分派 ARCH 回应
      → ARCH 回复后，执行者继续
```

### ARCH 回应方式（三选一）

1. **确认设计正确**：附解释，说明质疑方遗漏的上下文
2. **修改设计文档**：确认质疑成立，修改设计文档并说明变更
3. **标记后续处理**：确认问题存在但不影响当前阶段，标记为已知问题

### 记录要求

质疑和回复必须在过程记录的对应子任务段落中完整记录，包括：
- 质疑的具体设计点（引用文档位置）
- Python 源码依据
- ARCH 的回应和理由
- 最终决定（维持/修改/延后）

## 5. 阶段验收流程

一个阶段内所有子任务均 ACCEPTED 后，执行阶段验收：

```
┌─────────────────────────────────────────────────────────┐
│                    阶段验收（Phase Acceptance）           │
├─────────────────────────────────────────────────────────┤
│ 1. PM 检查：总纲中所有子任务均已 ACCEPTED                │
│ 2. ARCH 检查：模块间接口一致性、无冲突、无遗漏           │
│ 3. 集成测试：cargo test（含跨模块集成用例）全部通过      │
│ 4. ARCH 确认：设计文档与实现一致，无偏离                 │
│ 5. PM 签署：阶段验收通过，更新总纲状态                   │
└─────────────────────────────────────────────────────────┘
```

**阶段验收检查清单**：
- [ ] 总纲中所有子任务 `[x]` 已完成
- [ ] `cargo build` 零 error，`cargo clippy` 零 warning
- [ ] `cargo test` 全部 PASS
- [ ] `cargo fmt --check` 通过
- [ ] 所有模块间接口调用正常（无编译/链接错误）
- [ ] 无遗漏的 Python 版本功能（ARCH 确认）
- [ ] 过程记录完整，所有子任务有完整的操作日志
- [ ] 阶段出口标准（总纲中定义）全部满足
- [ ] `plans/00-项目进度.md` 已更新（阶段状态改为 ✅）
- [ ] `git tag phase-N-complete` 已打标签

## 6. 文件更新规范

工作流中的每个步骤都必须更新对应的文件：

| 步骤 | 更新文件 | 更新内容 |
|------|---------|---------|
| 任务分派 | `plans/phaseN/过程记录.md` | 填写子任务的负责人、开始时间、状态 → 进行中 |
| 任务分派 | `plans/00-项目进度.md` | 更新当前焦点、活跃子任务 |
| 设计完成 | `docs/模块设计-*.md` | 编写或更新设计文档 |
| 开发完成 | `plans/phaseN/过程记录.md` | 记录开发操作、自检结果 |
| 验证完成 | `plans/phaseN/过程记录.md` | 记录验证结果、问题清单 |
| 审查完成 | `plans/phaseN/过程记录.md` | 记录审查意见 |
| 子任务完成 | `plans/phaseN/总纲.md` | 子任务清单项标记 `[x]` |
| 子任务完成 | `plans/00-项目进度.md` | 更新完成计数、下一步、活跃子任务 |
| 子任务完成 | git | PM 执行 `git add` + `git commit`（`feat(phaseN): X.Y 描述`） |
| 阶段验收 | `plans/phaseN/过程记录.md` | 填写阶段验收记录 |
| 阶段验收 | `plans/00-项目进度.md` | 阶段状态改为 ✅，当前焦点移至下一阶段 |
| 阶段验收 | git | PM 执行 `git tag phase-N-complete` |
| 设计质疑 | `plans/00-项目进度.md` | 更新活跃质疑列表 |
| 质疑关闭 | `plans/00-项目进度.md` | 从活跃质疑列表移除 |

### PM 恢复工作流程

PM 每次启动（包括工作中断后恢复）时：

1. 读取 `plans/00-项目进度.md` — 获取全局状态
2. 根据总进度中的"当前焦点"，读取对应阶段的 `总纲.md` 和 `过程记录.md`
3. 从上次中断处继续执行

只需读 1 个总进度文件 + 当前阶段的 2 个文件，即可掌握完整上下文。

## 7. 跨阶段接口一致性保障

为防止阶段间接口不一致，执行以下机制：

1. **设计先行**：每个阶段的设计文档必须明确与已有模块的交互接口
2. **集成测试点**：每个阶段结束时，ARCH 检查新模块与已实现模块的接口兼容性
3. **API 变更审批**：如需修改已验收模块的公开 API，须经 ARCH 审批并同步更新设计文档
4. **总设计文档同步**：接口变更须同步更新 `docs/总设计文档.md`

## 8. 缺陷追踪

验证或审查中发现的问题按以下规则处理：

| 问题类型 | 处理方式 | 记录位置 |
|---------|---------|---------|
| 实现遗漏（漏开发） | 驳回至 CODING，补充实现 | 过程记录 |
| 测试遗漏（漏测） | 驳回至 CODING，补充测试用例 | 过程记录 |
| 接口不一致 | 驳回至 CODING，修正接口或更新设计文档 | 过程记录 + 设计文档 |
| 逻辑错误 | 驳回至 CODING，修正逻辑 | 过程记录 |
| 设计缺陷 | 驳回至 DESIGNING，修正设计 | 过程记录 + 设计文档 |

## 9. 工作流简明视图

```
子任务工作流（单任务视角）:

  PM ──分派──> ARCH ──设计──> DEV ──实现+自测──> REF ──对照验证──> REV ──代码审查──> PM ──确认──> DONE
                                      ^               |                  |
                                      |               驳回               驳回
                                      +───────────────+──────────────────+
```

```
阶段工作流（阶段视角）:

  总纲子任务1 ──> [完整子任务流程] ──> ACCEPTED
  总纲子任务2 ──> [完整子任务流程] ──> ACCEPTED
  ...
  总纲子任务N ──> [完整子任务流程] ──> ACCEPTED
                                          │
                                          v
                                  [阶段验收] ──> 阶段完成
```

## 10. opencode 工具接口

本项目的角色分派通过 opencode 的 agent 系统实现。PM 是默认主 agent，通过 Task 工具分派任务。

### 10.1 agent 配置

项目根目录的 `opencode.json` 定义了 5 个 agent：

| agent 名 | 角色 | mode | 用途 |
|----------|------|------|------|
| `pm` | PM | primary | 默认主 agent，用户直接对话 |
| `architect` | ARCH | subagent | PM 通过 Task 分派设计任务 |
| `developer` | DEV | subagent | PM 通过 Task 分派开发任务 |
| `validator` | REF | subagent | PM 通过 Task 分派验证任务 |
| `reviewer` | REV | subagent | PM 通过 Task 分派审查任务 |

每个 agent 的完整指令见 `.opencode/agents/<name>.md`。

### 10.2 PM 分派操作

PM 使用 Task 工具分派任务时，按以下格式：

```
Task 工具调用：
  subagent_type: 对应的 agent 名
  description: "3-5词任务描述"
  prompt: |
    包含以下内容：
    1. 任务信息（阶段、子任务、状态流转）
    2. 任务要求（从总纲提取）
    3. 必读文件列表
    4. 输出要求（返回格式）
    5. 文件操作权限提醒
```

### 10.3 分派示例

**设计阶段分派**：
```
Task(
  subagent_type: "architect",
  description: "设计错误体系模块",
  prompt: "你现在是 ARCH，负责执行 Phase 1 子任务 1.2 错误体系设计..."
)
```

**开发阶段分派**：
```
Task(
  subagent_type: "developer",
  description: "实现 Value 枚举类型",
  prompt: "你现在是 DEV，负责执行 Phase 1 子任务 1.3 值类型系统实现..."
)
```

**验证阶段分派**：
```
Task(
  subagent_type: "validator",
  description: "验证 Bytes 构造器",
  prompt: "你现在是 REF，负责验证 Phase 2 子任务 2.1 Bytes 构造器..."
)
```

**审查阶段分派**：
```
Task(
  subagent_type: "reviewer",
  description: "审查 Struct 实现",
  prompt: "你现在是 REV，负责审查 Phase 3 子任务 3.1 Struct 构造器..."
)
```

### 10.4 agent 切换

用户可在 opencode 中直接切换到任意 agent（如直接使用 developer agent 编码），无需经过 PM 分派。切换后，该 agent 的指令（`.opencode/agents/<name>.md`）自动生效。

### 10.5 并行分派

PM 可在同一消息中发起多个 Task 调用，将无依赖的子任务并行分派。例如 Phase 1 中 1.2（错误体系）、1.3（值类型）、1.5（流抽象）可同时分派给 3 个 developer subagent。
