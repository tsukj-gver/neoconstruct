### 2.2 子任务 9.2：零拷贝优化——**推迟（post-project）**

**总纲要求**：对 `Value::Bytes` 使用 `Cow<[u8]>` 或 `&[u8]` 切片，对只读场景（parse）尽量使用引用而非 `Vec<u8>` 克隆。

**可行性分析**：

当前 `Value` 定义（`value.rs` line 39-67）：
```rust
#[derive(Clone, Debug, PartialEq)]
pub enum Value {
    Bytes(Vec<u8>),
    // ... 其他 9 个变体
}
```

要将 `Bytes(Vec<u8>)` 改为借用形式，有两种路径：

#### 路径 A：`Value<'a>`（生命周期参数）

```rust
pub enum Value<'a> {
    Bytes(Cow<'a, [u8]>),
    // ...
}
```

**级联影响**：
- `Construct::parse` 返回 `Result<Value<'a>>`，但 `'a` 来自 `stream` 参数的生命周期——`stream` 是 `&mut dyn Stream`（trait 对象引用），其底层数据不一定是 `'static` 的。这要求 `parse` 的生命周期约束变成 `fn parse<'a>(&'a self, stream: &'a mut dyn Stream, ...) -> Result<Value<'a>>`。
- `Context` 持有 `IndexMap<String, Value>` → 需变为 `IndexMap<String, Value<'a>>`，Context 的生命周期也被感染。
- `Context: Clone`（`subcontext()` 依赖 clone）——`Cow::Borrowed` 的 clone 是引用拷贝，但 Context clone 会复制整个 map，此时借用数据的生命周期必须统一。
- 所有 `match value { Value::Bytes(b) => ... }` 的 `b` 类型从 `&Vec<u8>` 变为 `&Cow<[u8]>`，需要适配。
- 所有 `From<Vec<u8>> for Value` → 需要同时保留 `From<Vec<u8>>`（owned）和 `From<&'a [u8]>`（borrowed）。
- 用户代码（gallery、tests）中所有 `Value::Bytes(...)` 构造都需要标注生命周期或调整。

**结论**：路径 A 等同于重新设计 Phase 1 的核心类型系统。影响面与 Value::Lazy（§2.5）同级，但收益（避免一次 memcpy）远低于惰性解析（跳过整个 parse）。

#### 路径 B：使用 `bytes::Bytes`（引用计数共享）

`bytes::Bytes` 是一个原子引用计价的字节容器，`clone` 是廉价的（仅增加引用计数），且可以 `slice` 出子视图而不复制。

**优点**：不引入生命周期参数，`Value` 仍是 `'static`。
**缺点**：
- 引入 `bytes` crate 作为**必需依赖**，违反总设计文档 §1.2 "零运行时依赖"原则（AGENTS.md §7："可选依赖：feature gate 控制"）。
- `Bytes` 的 `PartialEq`/`Debug` 行为与 `Vec<u8>` 一致，但 API 习惯不同（`&[u8]` vs `Bytes`），需要适配所有 `as_bytes()` 调用点。
- 收益主要在 `Rebuffered`（`read_remaining` 全量缓冲）和 `GreedyBytes` 等大块字节场景，但这些场景中字节本身就需要 owned（因为流数据随后会被释放）。

**裁定**：**推迟**。理由如下：

1. **收益有限**：parse 路径的字节拷贝主要集中在 `Bytes(n)` / `GreedyBytes` / `Rebuffered`，这些场景中字节必须 owned（流是临时资源）。真正能受益于零拷贝的场景（如从一个大 buffer 中切片多个 `Value::Bytes`）在当前 API 模式下很少见。

2. **成本过高**：路径 A 影响全代码库（与 Value::Lazy 同量级），路径 B 违反零依赖原则。

3. **基准驱动原则**：Phase 9 的核心原则是"基于基准测试数据驱动"（总纲 line 107）。在缺乏基线数据时进行全库重构违反此原则。应先用 9.1 的基准测试识别真正的热点，再决定是否值得零拷贝重构。

**替代措施**（在 9.4 中实施）：
- 在已知大小的 `Array`/`Struct` parse 中使用 `Vec::with_capacity` 减少 realloc。
- 在 `Rebuffered` 中评估是否可以避免 `read_remaining` 的二次拷贝（Phase 7 §4.2 已记录）。

### 2.3 子任务 9.3：trait 对象优化——**简化**

**总纲要求**：对 `Box<dyn Construct>` 的虚函数调用开销进行分析，对热点路径考虑泛型单态化或 `enum_dispatch`。

**可行性分析**：

#### 全局泛型化的不可行性

Phase 1 核心决策（AGENTS.md §7："构造器抽象：`Box<dyn Construct>`"）是整个库的架构基石。所有复合构造器（Struct、Sequence、Array、Union、Select、Switch 等）都持有 `Vec<(String, Box<dyn Construct>)>` 或 `Box<dyn Construct>`。

改为泛型（如 `Struct<T1, T2, ...>`）的问题：
- **字段数量不固定**：Struct 可以有任意数量的字段，无法用固定泛型参数表达。需要 HList（异构列表）或 `macro_rules!` 生成定长泛型 Struct——极其复杂。
- **运行时组合能力丧失**：Python construct 的核心价值是运行时动态组装构造器树（如根据配置文件构建解析器）。泛型化要求编译期已知所有类型组合，完全丧失这一能力。
- **API 破坏**：所有用户代码的 `Box::new(...)` 构造方式都需要重写。

#### enum_dispatch 的不可行性

`enum_dispatch` 要求所有参与分发的类型在编译期已知且封闭（closed set）。但 `Construct` 是一个**开放 trait**——用户可以（且应该能）实现自己的 `Construct` 类型。enum_dispatch 无法容纳用户自定义类型。

#### 裁定：简化为编译期优化 + 局部优化

不进行 trait→泛型/enum_dispatch 的全局重构。改为以下低风险措施：

1. **LTO（Link-Time Optimization）**：在 `Cargo.toml` 的 `[profile.release]` 和 `[profile.bench]` 中启用 `lto = true`。LTO 可以跨 crate 边界内联虚函数调用（当编译器能看到具体类型时），在不修改源码的情况下获得部分单态化收益。

2. **`codegen-units = 1`**：减少代码生成单元，允许编译器做更激进的优化。

3. **基准驱动评估**：用 9.1 的基准测试测量 `dyn Construct` 调用的实际开销。现代 CPU 的间接分支预测器对重复模式的虚函数调用预测准确率很高，实际开销可能仅 1-3ns——如果基准测试证明开销可忽略，则无需进一步优化。

4. **局部热点优化**（数据驱动，非现在实施）：如果基准测试发现特定路径是瓶颈，可以对**该路径单独**引入泛型版本（如为 `Array<Byte>` 提供特化 fast path），而非全局重构。

**具体配置详见** §4.2。

### 2.4 子任务 9.4：内存分配优化——**部分实施**

**总纲要求**：`Vec::with_capacity`、`SmallVec`/`TinyVec`、`FxHashMap`/`AHashMap`。

**逐项裁定**：

#### (a) `Vec::with_capacity`——**实施**

安全、低风险。在已知元素数量的 parse 路径中预分配容量，避免多次 realloc。

具体优化点（详见 §4.1）：
- `Array::parse`：count 已知 → `Vec::with_capacity(count)`
- `Struct::parse`：字段数已知 → `IndexMap::with_capacity(n)`
- `Sequence::parse`：字段数已知 → `Vec::with_capacity(n)`
- `LazyArray::parse`、`LazyStruct::parse`（委托 Array/Struct，间接受益）

#### (b) SmallVec / TinyVec——**推迟**

`SmallVec` 将少量元素内联存储在栈上，避免堆分配。

**不实施的理由**：
1. **新增必需依赖**：`smallvec` 不是 Rust 标准库，添加它违反"核心库无必需外部依赖"原则（除非放在可选 feature 后，但 SmallVec 的收益场景太窄，不值得 feature gate 的复杂度）。
2. **Value 枚举不适合 SmallVec**：`Value` 有 10 个变体，`Value::List(Vec<Value>)` 中的 `Vec` 如果换成 `SmallVec<[Value; N]>`，需要选择内联容量 N。Value 每个变体大小不同（最大的 `Container(IndexMap)` 可能占 100+ 字节），SmallVec 的内联数组会显著增大 Value 的总体积，反而增加所有 Value 的内存开销。
3. **收益不确定**：典型 parse 场景中，List 的元素数通常 > 4（SmallVec 的典型内联容量），SmallVec 退化为普通 Vec + 额外判断开销。

#### (c) FxHashMap / AHashMap 替代 IndexMap——**不适用**

总纲（line 47）说"对 `Context` 使用 `FxHashMap` 或 `AHashMap` 替代 `BTreeMap`"。

**实际情况**：总设计文档（line 65）写的是 `BTreeMap`，但**实际实现**（`context.rs` line 37）已经使用了 `IndexMap<String, Value>`：

```rust
pub struct Context {
    fields: IndexMap<String, Value>,  // 已经是 IndexMap，不是 BTreeMap
    parent: Option<Box<Context>>,
}
```

`IndexMap` 提供 O(1) 查找 + 插入顺序保持，性能特性与 `FxHashMap` 接近（FxHashMap 仅在哈希函数上更快，但 IndexMap 的默认哈希器已经足够快）。Context 的字段数量通常 < 20，哈希性能不是瓶颈。

**裁定**：无需替换。Context 已使用 IndexMap，这是 Phase 1 就做出的合理选择。总纲此条基于过时的总设计文档描述。

### 2.5 子任务 9.5：真正惰性解析（Value::Lazy）——**推迟（post-project）**

**总纲要求**：实现 `Value::Lazy` 变体、`actualsize` 机制、`LazyContainer`/`LazyListContainer`。

**可行性分析**：

Phase 7 设计文档（`docs/模块设计-惰性解析.md` §6.3）已提供了完整的 Value::Lazy 设计蓝图。ARCH 在 Phase 7 明确裁定"推迟至 Phase 9"。现在在 Phase 9 的设计阶段，ARCH 做出**最终裁定：继续推迟，标记为 post-project**。

理由如下（Phase 7 §1.3.3 论证的复现与强化）：

#### 1. 架构变更范围超出合理边界

`Value` 枚举是 Phase 1 的核心架构决策（AGENTS.md §7）。添加 `Lazy` 变体影响：

| 影响范围 | 具体内容 | 风险 |
|---------|---------|------|
| `Value` 的 derive | `#[derive(Clone, Debug, PartialEq)]` 必须改为手动实现（`Rc<RefCell<Option<Value>>>` 不支持 derive PartialEq） | 高 |
| 全代码库 match 分支 | 约 50+ 处 `match value { Value::... }` 需添加 Lazy 分支 | 中 |
| `as_*` 方法 | 需决定是否自动物化（物化可失败，`as_bytes()` 的签名要从 `Result<&[u8], _>` 变为可能触发 parse 的操作） | 中 |
| `PartialEq` 语义 | 比较两个 LazyValue 需物化（副作用）或按指针比较（语义错误） | 高 |
| 现有 1090+ 测试 | match 分支变化可能导致编译错误或行为偏差 | 高 |

#### 2. 收益有限

Python 的惰性解析依赖 `_actualsize` 跳过**定长字段**（Int*/Float*/Bytes(n)）。变长字段（VarInt、Prefixed、PrefixedArray）仍需立即解析。真正能受益的场景是"定长字段占多数且只需访问少数字段"——这在实际使用中是少数情况。

#### 3. Phase 9 的核心原则是数据驱动

在 9.1 的基准测试建立之前，无法证明惰性解析的收益。如果基准测试显示 parse 已经足够快（如 Rust 版本是 Python 的 50x+），则惰性解析的边际收益不值得其架构成本。

#### 4. 风险与收益不匹配

Phase 7 已有 5 个 Lazy 构造器实现（Lazy/LazyStruct/LazyArray/LazyBound/Rebuffered），37 项单元测试全绿。引入 Value::Lazy 冒 1090+ 测试的回归风险，在缺乏迫切性能需求（需基准数据证明）的情况下不合理。

**裁定**：**推迟至 post-project**。

**建议 PM 修订总纲 9.5 的出口标准**为：
- 9.5 标记为 "推迟（post-project）"
- 在本文档 §6 保留 Phase 7 §6.3 的完整设计蓝图供未来参考
- Phase 9 的惰性解析收益评估改为：在 9.1 基准测试完成后，如果数据显示 parse 是瓶颈且惰性解析能带来 > 2x 提升，则创建独立的 post-project 任务实施

### 2.7 子任务 9.7：编译优化（高级，可选）——**跳过（post-project）**

**总纲要求**：设计编译期优化方案（对应 Python `compile()` 方法），评估 proc-macro 可行性。

**可行性分析**：

Python construct 的 `compile()` 方法（`core.py` 中的 `Construct.compile()`）将声明式构造器树编译为 Python 源代码字符串，然后 `exec()` 执行。编译后的代码省去了虚函数分发和 Context 字典查找，性能提升约 2-5x。

**在 Rust 中无直接等价物**：
1. Rust 没有运行时代码生成能力（无 `eval`/`exec`）。
2. `proc-macro` 在编译期运行，但 construct 的构造器树是**运行时构建**的——用户在运行时用 `Struct::new().field("a", ...).field("b", ...)` 组装解析器。proc-macro 无法捕获运行时结构。
3. 声明式 DSL 宏（如 `construct_struct! { a: Int32ub, b: Bytes(4) }`）可以在编译期生成特化代码，但：
   - 无法表达 Python construct 的全部动态能力（运行时条件分支、动态字段名等）
   - 需要重新设计整个 API 层（与现有 builder-style API 并行）
   - 工作量等于一个小型项目

**裁定**：**跳过**，标记为 post-project。Phase 9 的性能优化应聚焦于安全、低风险的改进（LTO + with_capacity + 遗留修复），编译优化作为独立研究方向留给未来。

## 3. 基准测试框架设计

### 3.1 criterion 配置

在 `Cargo.toml` 中添加：

```toml
[dev-dependencies]
criterion = { version = "0.5", features = ["html_reports"] }

[[bench]]
name = "atomic"
harness = false

[[bench]]
name = "composites"
harness = false

[[bench]]
name = "adapters"
harness = false

[[bench]]
name = "stream_ops"
harness = false

[[bench]]
name = "gallery"
harness = false
```

> **注意**：`harness = false` 是 criterion 的要求——criterion 自带测试 main 函数，不需要标准 libtest harness。

### 3.2 bench 文件组织

```
construct-rs/
├── benches/
│   ├── atomic.rs          # 原子构造器基准
│   ├── composites.rs      # 复合构造器基准
│   ├── adapters.rs        # 适配器/控制流基准
│   ├── stream_ops.rs      # 流操作基准
│   ├── gallery.rs         # gallery 格式端到端基准
│   └── common.rs          # 共享辅助函数（基准数据生成）
```

### 3.3 基准测试矩阵

## 4. 内存分配优化设计

### 4.1 Vec::with_capacity 预分配

以下是在 parse 路径中已知元素数量、可以预分配容量的优化点：

#### (1) `Array::parse`

当前实现（推测）先创建空 Vec，然后 push count 次。优化为：

```rust
fn parse(&self, stream: &mut dyn Stream, ctx: &mut Context) -> Result<Value> {
    let mut list = Vec::with_capacity(self.count);  // 预分配
    for _ in 0..self.count {
        list.push(self.subcon.parse(stream, ctx)?);
    }
    Ok(Value::List(list))
}
```

**预期收益**：对于 `Array(1000, Byte)`，避免约 10 次 realloc（Vec 增长策略：1→2→4→8→...→1024）。

#### (2) `Struct::parse`

Struct 知道字段数量，可以预分配 IndexMap：

```rust
fn parse(&self, stream: &mut dyn Stream, ctx: &mut Context) -> Result<Value> {
    let mut container = IndexMap::with_capacity(self.fields.len());
    // ... 逐字段 parse 并 insert
}
```

**预期收益**：IndexMap 内部使用哈希表 + 顺序数组，预分配避免两次 realloc。

#### (3) `Sequence::parse`

```rust
let mut list = Vec::with_capacity(self.fields.len());
```

#### (4) build 路径

build 路径通常不需要预分配（数据已在 Value 中），但 `Struct::build` 创建子 Context 时可考虑 `Context::with_capacity`——但这需要给 Context 添加 `with_capacity` 方法，属于低优先级增强。

> **实施约束**：以上优化均为**单行修改**，不改变任何接口签名或行为。DEV 在实施时需逐一确认对应代码位置，添加预分配，并确保 `cargo test` 全部通过。如果某个构造器的 parse 实现中 count 不是编译期常量（如 GreedyRange），则不适用此优化。

### 4.2 编译期优化（LTO + codegen-units）

在 `Cargo.toml` 中添加 release/bench profile 优化：

```toml
[profile.release]
lto = true
codegen-units = 1

[profile.bench]
lto = true
codegen-units = 1
```

**原理**：
- `lto = true`：启用跨 crate（及跨模块）的链接时优化。编译器在链接阶段能看到完整代码，对 `dyn Construct` 的虚函数调用，如果调用点的具体类型可推导，则自动内联。
- `codegen-units = 1`：将整个 crate 作为一个代码生成单元，允许编译器做最大范围的内联和死代码消除。

**代价**：编译时间增加（可能 2-3x），但 release/bench 构建不频繁，可接受。

**零风险**：不修改任何源码，不改变任何行为，仅影响编译器优化策略。

### 4.3 Rebuffered 缓冲优化（评估项）

Phase 7 §4.2 记录了 Rebuffered 的 `read_remaining` 全量缓冲策略。当前实现：

```rust
let data = stream.read_remaining();      // 全量读入 owned Vec<u8>
let buffered = ByteStream::new_read(&data);
```

**评估**：`read_remaining` 必须返回 owned `Vec<u8>`，因为底层流（如文件流）的数据在 read 后不再可用。这与 9.2 零拷贝优化的限制一致——无法避免这次拷贝，除非引入 `bytes::Bytes` 的引用计数共享（见 §2.2 路径 B，推迟）。

**裁定**：当前实现合理，不修改。仅在基准测试中测量 Rebuffered 的开销，如果成为瓶颈再评估。

## 5. 遗留项修复清单

### 5.1 [高优先级] expr.rs `UniOp::Neg` 对 `i64::MIN` panic

**当前代码**（`expr.rs` line 700-704）：
```rust
UniOp::Neg => match val {
    Value::Int(i) => Ok(Value::Int(-i)),        // -i64::MIN → panic!
    Value::UInt(u) => Ok(Value::Int(-(u as i64))),
    Value::BigInt(i) => Ok(Value::BigInt(-i)),   // -i128::MIN → panic!
    Value::Float(f) => Ok(Value::Float(-f)),
    // ...
}
```

**问题**：`-i64::MIN` 等于 `9223372036854775808`，超出 `i64::MAX`（`9223372036854775807`），在 debug 模式下 panic，在 release 模式下 wraps。这违反 AGENTS.md §8 红线 #2（禁止 panic）。

注意：二元运算（BinExpr）已经使用了 `wrapping_add`/`wrapping_sub`/`wrapping_mul`（expr.rs line 357-375），所以 BinExpr 的溢出测试（line 2614-2683）能正确通过。但一元 Neg 漏掉了。

**修复方案**：
```rust
UniOp::Neg => match val {
    Value::Int(i) => Ok(Value::Int(i.wrapping_neg())),
    Value::UInt(u) => Ok(Value::Int((u as i64).wrapping_neg())),
    Value::BigInt(i) => Ok(Value::BigInt(i.wrapping_neg())),
    Value::Float(f) => Ok(Value::Float(-f)),     // f64 取反不溢出
    // ...
}
```

**新增测试**：验证 `Neg(Int(i64::MIN))` 返回 `Int(i64::MIN)`（wrapping），不 panic。

### 5.2 [高优先级] expr.rs `FuncPath::abs` 对 `i64::MIN` panic

**当前代码**（`expr.rs` line 870-874）：
```rust
"abs" => match &val {
    Value::Int(i) => Ok(Value::Int(i.abs())),     // i64::MIN.abs() → panic!
    Value::UInt(u) => Ok(Value::UInt(*u)),
    Value::BigInt(i) => Ok(Value::BigInt(i.abs())), // i128::MIN.abs() → panic!
    Value::Float(f) => Ok(Value::Float(f.abs())),
    // ...
}
```

**修复方案**：
```rust
"abs" => match &val {
    Value::Int(i) => Ok(Value::Int(i.wrapping_abs())),
    Value::UInt(u) => Ok(Value::UInt(*u)),
    Value::BigInt(i) => Ok(Value::BigInt(i.wrapping_abs())),
    Value::Float(f) => Ok(Value::Float(f.abs())),  // f64 abs 不溢出
    // ...
}
```

**新增测试**：验证 `abs(Int(i64::MIN))` 返回 `Int(i64::MIN)`（wrapping），不 panic。

### 5.3 [低优先级] Union sizeof 行为裁定

**当前代码**（`union.rs` line 292-327）：返回所有 subcon 中的最大 size。

**Python 行为**：`Union._sizeof` 抛出 `SizeofError`（因为实际 size 取决于 build 时选择哪个成员）。

**裁定**：**保持当前行为（返回 max）**，理由：
1. 这是 Phase 3 实现时做出的**有益扩展**——返回 max 比 抛出 SizeofError 更实用（用户可以预分配最大缓冲区）。
2. 改为 SizeofError 会破坏现有依赖 Union.sizeof() 的代码和测试。
3. 代码注释（line 294-307）中的不确定表述（"Actually, re-reading more carefully..."）应清除，替换为明确的设计说明。

**修复**：清除 `union.rs` sizeof 方法中的冗长注释，替换为：
```rust
fn sizeof(&self, ctx: &Context) -> Result<usize> {
    // 返回所有 subcon 中的最大 size。
    // Python 版本在此抛出 SizeofError，但返回 max 是有益扩展：
    // 允许调用方预分配足够大的缓冲区。如果任何 subcon 的 size
    // 无法计算，则传播该错误。
    let child_ctx = ctx.subcontext();
    // ...（保持现有逻辑）
}
```

### 5.4 [低优先级] RepeatUntil build 错误信息改善

**当前代码**（`repetition.rs` line 587-592）：当没有元素匹配谓词时：
```rust
Err(ConstructError::Array {
    path: String::new(),
    expected: 0,
    actual: 0,
})
```

**问题**：`expected: 0, actual: 0` 语义不清晰——显示为 "expected 0 elements but got 0"，无法传达"没有元素满足停止条件"的含义。

**裁定**：不新增错误变体（避免膨胀 ConstructError 枚举），改为使用 `Generic` 变体并提供清晰的错误信息：

```rust
Err(ConstructError::Generic {
    path: String::new(),
    message: "RepeatUntil build: no element satisfied the stop predicate".to_string(),
})
```

> **注意**：总纲提到"评估是否新增 `ConstructError::Repeat` 变体"。ARCH 裁定不新增——现有 21 个变体已覆盖主要场景，新增变体需要同步更新 `path()` 和 `with_path_prefix()` 中的 match 分支（各 21 处），成本不匹配。`Generic` 变体配合描述性 message 足够。

### 5.5 [低优先级] RawCopy build 错误信息改善

**当前代码**（`stream_ops.rs` line 478-481）：当 Container 中既无 "data" 也无 "value" 时：
```rust
Err(ConstructError::Generic {
    path: String::new(),
    message: "RawCopy cannot build: both data and value keys are missing".to_string(),
})
```

**裁定**：当前错误信息已经足够清晰。不新增专用变体。保持现状。

### 5.6 [低优先级] Rebuffered 游标低估边角

**Phase 7 §4.2 已记录**：若 subcon 在 buffered 流上先前进读取再 seek 回退，`consumed = buffered.tell()` 取最终游标位置（可能小于实际触及的最大偏移）。

**裁定**：**不修复**，标记为已知限制。理由：
1. 当前测试未覆盖此场景，说明在实际使用中极少触发。
2. 修复需要追踪 buffered 流的 "high water mark"（最大触及偏移），增加复杂度。
3. 此行为不影响正确性（只是 subcon 可能少消费几个字节），且与 Python 的 `tailcutoff` 语义不完全对齐是已文档化的差异。

在 `lazy.rs` 的 Rebuffered 文档注释中追加此已知限制的说明即可。

## 6. Value::Lazy 最终裁定

### 6.1 裁定：推迟至 post-project

ARCH 在 Phase 7 §6.3 提供了 Value::Lazy 的完整设计蓝图。在 Phase 9 设计阶段，ARCH 做出**最终裁定：继续推迟**。

### 6.2 决策矩阵

| 评估维度 | 实施 Value::Lazy | 推迟 |
|---------|-----------------|------|
| 惰性收益 | ✅ 定长字段跳过 parse | ❌ 无 |
| 架构风险 | ❌ 修改 Value 枚举，影响 50+ match 分支 | ✅ 零风险 |

| 实施工期 | ❌ 2-3 周（Value 重构 + 回归测试） | ✅ 0 |
| 数据支撑 | ❌ 尚无基准证明 parse 是瓶颈 | ✅ 先建立基线 |
| 替代方案 | — | ✅ eager parse 可能已足够快 |

### 6.3 推迟条件（未来重启的触发条件）

Value::Lazy 应在未来满足以下**全部**条件时重启实施：
1. 基准测试数据显示 parse 是性能瓶颈（占端到端时间 > 50%）
2. 用户反馈惰性解析是实际需求（而非理论需求）
3. 有 2-3 周的专属开发窗口（不与其他功能竞争）
4. 愿意接受 1090+ 测试的回归验证工作量

### 6.4 设计蓝图保留

Phase 7 §6.3 的完整设计蓝图（LazyValue 结构、actualsize 机制、LazyContainer/LazyListContainer、四步实施路线）仍然有效，作为 post-project 实施的参考。本文档不再重复，避免文档冗余。

## 8. 设计决策记录

### 8.1 决策 D9-01：零拷贝优化推迟

**决策**：不实施 `Value::Bytes` 的 `Cow`/借用重构。

**理由**：生命周期参数 `Value<'a>` 感染全代码库（Context、Construct trait、所有 match 分支），影响面与 Value::Lazy 同级，但收益（避免一次 memcpy）远低于惰性解析。违反"基于基准数据驱动"原则。

**替代**：在已知大小的 parse 路径使用 `Vec::with_capacity`（§4.1）。

### 8.2 决策 D9-02：trait 对象优化简化为 LTO

**决策**：不进行 `Box<dyn Construct>` → 泛型/enum_dispatch 的全局重构。

**理由**：泛型化破坏运行时动态组合能力（Python construct 的核心价值）；enum_dispatch 要求封闭类型集，与开放 trait 冲突。LTO（`lto = true` + `codegen-units = 1`）可在零源码修改下获得部分内联收益。

### 8.3 决策 D9-03：SmallVec 推迟

**决策**：不引入 SmallVec/TinyVec。

**理由**：新增必需依赖违反零依赖原则；Value 枚举变体多，SmallVec 内联数组会增大所有 Value 的体积。收益不确定（典型 List 元素数 > SmallVec 内联容量）。

### 8.4 决策 D9-04：Context 不替换为 FxHashMap

**决策**：保持 Context 使用 IndexMap。

**理由**：实际实现已用 IndexMap（非总设计文档中的 BTreeMap）。IndexMap 提供 O(1) 查找 + 插入序保持，Context 字段数通常 < 20，哈希性能非瓶颈。总纲此条基于过时的设计文档描述。

### 8.5 决策 D9-05：Value::Lazy 推迟至 post-project

**决策**：不实施 Value::Lazy，标记为 post-project。

**理由**：50+ match 分支变更，1090+ 测试回归风险，收益有限（仅定长字段跳过 parse）。缺乏基准数据证明 parse 是瓶颈。Phase 7 §6.3 设计蓝图保留供未来参考。

### 8.6 决策 D9-06：编译优化跳过

**决策**：不实施 compile() 等价物 / proc-macro DSL。

**理由**：Rust 无运行时代码生成；proc-macro 无法捕获运行时构建的构造器树。工作量等同于独立项目。LTO 已提供编译期内联的收益。

### 8.7 决策 D9-07：不新增 ConstructError 变体

**决策**：RepeatUntil/RawCopy 的错误信息改善使用现有 Generic 变体，不新增 Repeat/Transformed 等变体。

**理由**：ConstructError 已有 21 个变体，新增需同步更新 `path()` 和 `with_path_prefix()` 各 21 处 match 分支。Generic + 描述性 message 足够。

### 8.8 决策 D9-08：Union sizeof 保持返回 max

**决策**：保持 Union.sizeof() 返回所有 subcon 的最大 size（有益扩展），不改为 SizeofError。

**理由**：返回 max 比 SizeofError 更实用（允许预分配最大缓冲区）。改为 SizeofError 会破坏现有代码。仅清除代码中的不确定注释。
