## 1. 协议选择

### 选定协议：**SCTP (Stream Control Transmission Protocol)** — RFC 4960

### 选择理由

| 要求 | SCTP 满足情况 |
|------|--------------|
| **bitfield (BitStruct)** | ✅ DATA chunk 的 flags 字段是真实 bitfield：`Reserved(5) \| U \| B \| E` = 8 bit |
| **条件分支 (Switch/If)** | ✅ chunk_type 决定 chunk value 结构（DATA/INIT/SACK/ABORT/...），天然 Switch 场景 |
| **CRC/校验** | ✅ Common Header offset 8-11 是 CRC32c（Castagnoli）checksum |
| **复杂度足够** | ✅ Common Header + GreedyRange(Chunks)；每个 chunk = Prefixed(ChunkInner)；ChunkInner 内嵌 Switch；DATA 内含变长 user_data；SACK 内含 Array(count_field) |
| **非 SKILL 样例** | ✅ SKILL 样例是 Modbus RTU / CAN / IEC104 / IPv4，SCTP 不在其中 |
| **真实协议** | ✅ IETF 标准（RFC 4960），用于 WebRTC、SIGTRAN、Diameter 等真实场景 |

### 实现范围（简化）

- Common Header（12 B 全实现）
- 4 种 chunk type：**DATA(0)**, **INIT(1)**, **SACK(3)**, **ABORT(6)**
- GreedyRange 支持单包多 chunk
- CRC32c 外部校验（compute + verify）

## 2. 实现要点（用了哪些构造器 + 模式）

### 协议结构总览

```
SCTPPacket (StructMixin)
├── src_port: Int16ub
├── dst_port: Int16ub
├── verify_tag: Int32ub
├── checksum: Bytes(4)              ← CRC32c，外部函数校验（SKILL 4.4.4 中间位置 gap）
└── chunks: GreedyRange(
        Prefixed(Int16ub,           ← chunk_length（含 lengthfield 自身 2B，includelength=True）
            ChunkInner,             ← 在子流中：type + flags + value
            includelength=True))
    └── ChunkInner (StructMixin)
        ├── chunk_type: Int8ub
        ├── flags_raw: Int8ub
        └── value: Switch(chunk_type, {0: Data, 1: Init, 3: Sack, 6: Abort})
```

### 用到的构造器（按 SKILL 章节）

| 构造器 / 模式 | SKILL 章节 | 用途 |
|--------------|----------|------|
| `@dataclass StructMixin` | §2, §3.4 | SCTPPacket / ChunkInner / DataChunkValue 等 7 个 Struct |
| `@dataclass BitStructMixin` | §4.2 | `DataChunkFlags`：5 reserved + U + B + E |
| `field(subcon)` | §3.1 | 所有 RW 字段（src_port、value、user_data 等） |
| `Bit()` / `BitsInteger(N)` | §3.3, §4.2 | BitStruct 内的位字段 |
| `Int8ub / Int16ub / Int32ub` | §3.3 | 整数字段 |
| `Bytes(N)` | §3.3 | checksum 字段、user_data 等 |
| `GreedyBytes` | §3.3 | DATA.user_data / INIT.params（读到子流末尾） |
| `Switch(key, cases)` | §4.3.1 | chunk_type 分派 4 种 chunk value |
| `Prefixed(lengthfield, subcon, includelength=True)` | §3.3 | chunk_length 前缀的子流（关键技巧） |
| `GreedyRange(subcon)` | §4.5.4 | 一个 packet 内多个 chunks |
| `Array(count_field, subcon)` | §4.5.1 | SACK.gap_blocks / SACK.dup_tsns（count 引用字段） |

### 关键设计技巧

1. **`Prefixed(includelength=True)` 包装 chunk**：
   SCTP 的 chunk_length = 整个 chunk 字节数（含 type+flags+length+value）。
   `Prefixed(Int16ub, ChunkInner, includelength=True)` 让 substream =
   `chunk_length - 2` 字节，正好是 type+flags+value 的字节数。Switch 在
   子流中查找 chunk_type 完成分派。这种"length 含 lengthfield 自身"的
   语义完美匹配 SCTP 的 wire 格式。

2. **GreedyRange + Prefixed 组合**：
   GreedyRange 反复执行 Prefixed，直到 EOF 或 subcon 失败。每次迭代
   自动消费一个完整 chunk（包括其 length 字段）。

3. **变长 user_data（GreedyBytes 读到子流末尾）**：
   `DataChunkValue.user_data = GreedyBytes` 读到 Prefixed substream 末尾，
   自动等价于 `chunk_length - 16` 字节，无需跨层引用 chunk_length。

4. **BitStruct 独立定义 + 事后解析**：
   由于 chunk flags 字段的语义依赖 chunk_type（动态），无法让 ChunkInner.flags
   字段静态绑定 BitStruct 类型。变通：flags 字段保持 Int8ub，DATA chunk 的
   flags 通过 `DataChunkFlags.parse(bytes([flags_raw]))` 事后解码为 bit 字段。

5. **CRC32c 外部校验**：
   SCTP checksum 在 common header 中间（offset 8-11），按 SKILL 4.4.4 必须
   用 `Bytes(4) + 外部函数`，不能用 `Checksum` 构造器（StreamRange 模式
   要求 checksum 在 body 末尾）。

## 4. SKILL 质量反馈

### 4.1 SKILL 是否够用单轮实现？

**结论：基本够用，但有几处明显不足需要在 SKILL 中补充。**

仅靠读 SKILL，我完整实现了 SCTP（一个真实、复杂、含三大特征的协议），
通过 53 项 round-trip 测试 + 8 项 parity 测试。SKILL 的核心 API
（StructMixin / BitStructMixin / Switch / Prefixed / GreedyRange / Array）
文档齐全，cookbook 模式直接可用。

### 4.2 SKILL 的强项（继续保持）

1. **§4 关键模式 Cookbook**：每个模式有完整可运行代码，复制即用。
   §4.4.1 StreamRange CRC 模式、§4.3.1 Switch 模式、§4.2 BitStruct 模式
   都很完整。

2. **§5 易错点 + API gap 替代方案**：极有价值。§5.1/5.2（Checksum/Peek
   必须 field）、§5.4（Computed 不能跨层引用）、§5.5（Switch keyfunc
   必须简单字段）、§5.6（Const 参数顺序）等直接救了我好几次。

3. **§3.3 构造器清单**：分类清晰、覆盖完整，从 §3.3 找构造器很快。

4. **§9 实现协议的步骤**：8 步推荐流程（画字段图 → 识别 bitfield →
   识别条件分支 → ...）确实指导我按部就班实现 SCTP。

### 4.3 SKILL 的不足（建议补充）

#### Gap 1（重要）：`Prefixed` 的 `includelength` 参数完全没文档

SKILL §3.3 只写：
> `Prefixed(lengthfield, subcon, includelength=False)`：长度前缀子流（lengthfield 是字节计数）

**问题**：没说 `includelength=True` 的语义。我必须自己写探针测试
（`_probe_api.py` Probe1）才能确认 `includelength=True` 时 substream =
`length_value - len(lengthfield)` 字节。

**对实现 SCTP 的影响（关键）**：SCTP 的 chunk_length = 整个 chunk 字节数
（含 type+flags+length+value = 4B header + value）。我必须用
`includelength=True` 才能让 substream = `chunk_length - 2` 字节（去掉
lengthfield 自身 2B），正好是 type+flags+value 字节数。如果 SKILL 不
说明 includelength，我会用默认 `False`，substream = `chunk_length` 字节
（多读 2B），wire 格式错误。

**建议补充**：
```
Prefixed(lengthfield, subcon, includelength=False)
  - includelength=False（默认）：substream 长度 = length 值
  - includelength=True：substream 长度 = length 值 - len(lengthfield)
    （length 值包含 lengthfield 自身字节数，常见于协议头 length 字段
     "含自身"的场景，如 SCTP chunk_length / TLS record Length）
```

#### Gap 2（重要）：`Prefixed` + `GreedyRange` 组合未给示例

SKILL §4.5.4 GreedyRange 只给简单示例（`GreedyRange(Int8ub)`），§3.3
Prefixed 也只单独讲。两者组合（`GreedyRange(Prefixed(...))`）是处理
"长度前缀变长记录序列"的核心模式（如 SCTP chunks / TLS records /
PNG chunks），但 SKILL 没有任何示例。

**对实现的影响**：我必须写探针（`_probe_api.py` Probe2/Probe5）确认
GreedyRange + Prefixed 的组合工作正常（包括 build 方向）。

**建议补充**：在 §4.5 加一节 "GreedyRange + Prefixed：变长记录序列"。

#### Gap 3（中等）：BitStruct 字段类型依赖上下文（动态 bitfield）未讨论

DATA chunk 的 flags 字段在不同 chunk_type 下语义不同（DATA 是 U/B/E，
ABORT 是 T bit + 7 reserved）。我无法让 `ChunkInner.flags` 字段在
chunk_type=0 时是 `DataChunkFlags`、其他类型时是 raw byte。

SKILL §4.2 BitStruct 只讲"静态 bitfield"，没讨论"同一字节在不同上下文
下不同 bit 解读"。变通是 flags 保留为 Int8ub + 事后用 BitStruct.parse()
解码，但这是我自己想的，SKILL 没教。

**建议补充**：在 §4.2 加一句"BitStruct 适合静态位域分解；动态位域
（同一字节在不同上下文下含义不同）请保留 raw byte 并事后解析"。

#### Gap 4（已知，§4.4.4 提到但无替代方案）：中间位置 checksum 无内置支持

SCTP checksum 在 common header 中间（offset 8-11），不在 packet 末尾。
SKILL §4.4.4 提到这个 gap 并建议"用 Bytes(2) + 外部 Python 函数校验"，
但没有更优雅的方案（如 Pointer + Checksum 组合，或"任意位置 checksum"
API）。

**对实现的影响**：我用 `Bytes(4)` + 外部 `verify_sctp_checksum()` 函数
+ `attach_checksum()` helper。可行，但失去了 construct-rs Checksum 构造
器的 parse-time 自动校验能力（必须显式调用 verify 函数）。

**建议补充**：探索是否可用 `Pointer(offset, Checksum(...))` 实现中间
位置 checksum 自动校验；或明确文档说明这是设计限制。

#### Gap 5（次要）：`Switch default=Pass` 在 Prefixed substream 中的行为未文档化

当 Switch 默认 Pass（keyfunc 未命中）且 substream 还有未消费字节时，
Prefixed 子流未完全消费会让外层 GreedyRange 终止。SKILL 只说
"default=Pass 表示未命中时不解析"，没说在 Prefixed + GreedyRange 组合
中的副作用。

**对实现的影响**：我最初写了一个 unknown chunk_type=99 的测试，包含
3 字节 value。Switch default=Pass 不消费 value 字节，Prefixed substream
未完全消费导致 GreedyRange 终止，最终 `parsed.chunks == []`（与预期
不符）。改为 chunk_length=4（无 value 字节）后才正常。

**建议补充**：在 §4.3.1 Switch 加一句"default=Pass 不消费 substream
字节；在 Prefixed 内使用时若 substream 有剩余字节，会让 Prefixed 报
substream 未消费错误"。

#### Gap 6（很小）：编码后缀约束文档有点散

§5.10 和 §3.3 Strings 都提到编码必须用显式后缀（utf8 不能写 utf16）。
但我没用到字符串，所以无影响。

## 5. SKILL 质量评分

### 综合评分：**8 / 10**

### 评分分解

| 维度 | 评分 | 说明 |
|------|------|------|
| **覆盖完整度** | 8 / 10 | 核心 API 都有；缺 Prefixed.includelength 语义、GreedyRange+Prefixed 组合 |
| **示例质量** | 9 / 10 | Cookbook 章节示例完整可运行；4 个真实协议（Modbus/CAN/IEC104/IPv4）递进合理 |
| **易错点覆盖** | 10 / 10 | §5 易错点救了我多次（Checksum/Peek 必须 field、Const 参数顺序等） |
| **自包含性** | 8 / 10 | 基本"读完即可上手"；但 Prefixed includelength 需自写探针 |
| **API gap 透明度** | 9 / 10 | §4.4.4 / §4.7 / §5.x 明确标出已知限制 + 变通方案 |
| **新手上手难度** | 7 / 10 | 中等。`@dataclass + field(subcon)` 简洁但与 Python construct 差异大，需要适应 |

### 总评

SKILL 是一份**质量很高、自包含度很高**的 construct-rs 使用文档。仅靠读
SKILL（+ 写 5 个小探针），我成功实现了 SCTP 这种真实复杂协议，并通过
了 53 项 round-trip 测试 + 8 项与 Python 原版 construct 的字节级 parity
测试。

主要改进方向：补充 `Prefixed.includelength=True` 语义、`GreedyRange +
Prefixed` 组合示例。这两个 gap 是实现"长度前缀变长记录序列"协议
（SCTP / TLS / PNG / HTTP2 / ...）的关键，补齐后 SKILL 对这类协议的
覆盖会更完整。
