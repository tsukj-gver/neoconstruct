# 8.ENV 环境切换 — Python 3.13 非 abi3 + PERF 基线重建

## 任务背景

REV 检视 8.OPT-SHARED 设计时发现：项目此前编译在 abi3 模式（为了让 pyo3 0.22.6
支持 Python 3.14，构建时设置 `PYO3_USE_ABI3_FORWARD_COMPATIBILITY=1`）。abi3 模式
下 `Py_LIMITED_API` cfg 开启，pyo3-ffi 的 `cpython/` 子模块不编译（`#[cfg(not(Py_LIMITED_API))]`），
导致 8.OPT-SHARED 计划使用的三个 cpython 内部符号全部不可访问：

- `pyo3::ffi::PyTypeObject.tp_dictoffset`（dict 偏移直读）
- `pyo3::ffi::_PyDict_SetItem_KnownHash`（KnownHash 插入）
- `pyo3::ffi::PyBytesObject.ob_sval`（bytes 零拷贝）

用户决策（2026-08-06）：放弃 abi3，目标 Python 3.13（立项未要求支持 3.14）。
pyo3 0.22.6 原生支持 Python 3.13，无需 abi3 forward compat。

本任务建立 Python 3.13 非 abi3 的新基线，为 8.OPT-SHARED 铺路。

### 4.3 加速比提升归因（L-09 谨慎归因）

加速比普遍提升（48/48 点均 ≥ 旧值），但归因需谨慎（L-09）。两个竞争假设：

1. **非 abi3 使 Rust 侧更快**（部分成立）：`Py_LIMITED_API` 关闭后，pyo3 内部从
   `PyType_GetSlot` 间接槽位读取改为直接 struct 字段访问，类型操作/对象构造路径
   变快。这能解释 rs 侧 parse 普遍从 ~240-640ns 降至 ~195-602ns。
2. **Python 3.13 vs 3.14 基线侧变化**（混合变量）：py 侧从 3.14 换到 3.13，
   CPython 3.13 在某些路径（Struct 调度/Adapter）可能略慢或相当，拉高加速比。
   本对比未隔离此变量（L-09 要求控制变量）。

**判定（L-09 对策）**：本任务目的是建立新基线（非 abi3 + 3.13），而非归因加速比变化。
加速比普遍且单调提升（无反向项），与"非 abi3 让 pyo3 路径更直接"的预期一致，可作为
**定性佐证**，但不可当作"非 abi3 带来 +Nx"的精确量化（ns 级效应常在测量噪声内）。
后续 8.OPT-SHARED 优化效果**以本 3.13 基线为对照**，不再回比 3.14。

**仍不达标的 7 项**（CN1/HX1/HX2/HD1/FE1×2/NT1）与 3.14 基线根因一致（Hex/HexDump
显示对象构造、FlagsEnum dict→int、NamedTuple 创建、parse 方向 PyObject 构造固有税），
正是 8.OPT-SHARED 的优化目标。

## 5. cpython 子模块可访问性验证（8.OPT-SHARED 前提）

### 5.1 符号定位（pyo3-ffi 0.22.6 源码确认）

三个符号均在 pyo3-ffi 的 `cpython/` 子模块（仅 `#[cfg(not(Py_LIMITED_API))]` 编译，
经 `pub use self::cpython::*` 重导出到 `pyo3::ffi::` 顶层）：

| 符号 | 源码位置 | 门控 |
|------|----------|------|
| `PyTypeObject.tp_dictoffset: Py_ssize_t` | `cpython/object.rs:258`（`object.rs:10` 重导出覆盖 opaque 定义） | `#[cfg(not(Py_LIMITED_API))]` |
| `_PyDict_SetItem_KnownHash` 函数 | `cpython/dictobject.rs:29` | `#[cfg(not(Py_LIMITED_API))]` |
| `PyBytesObject.ob_sval: [c_char; 1]` | `cpython/bytesobject.rs:13` | `#[cfg(not(Py_LIMITED_API))]` |

abi3 模式下 `cpython/` 不编译、`PyTypeObject`/`PyBytesObject` 为 opaque → 三符号全部不可访问。

### 5.2 编译链接验证（临时测试，已删除）

临时测试 `tests/abi3_symbol_check.rs`（pyo3 临时加入 `[dev-dependencies]` 供集成测试引用
`pyo3::ffi`），用 `core::mem::offset_of!` 验证字段存在 + 函数指针赋值验证函数链接：

```rust
let _ = core::mem::offset_of!(ffi::PyTypeObject, tp_dictoffset);   // 字段 1
let _: unsafe extern "C" fn(...) -> c_int = ffi::_PyDict_SetItem_KnownHash;  // 函数 2
let _ = core::mem::offset_of!(ffi::PyBytesObject, ob_sval);        // 字段 3
```

`cargo test --test abi3_symbol_check --release`（PYO3_PYTHON=3.13 venv）结果：

```
test cpython_symbols_accessible_non_abi3 ... ok
test result: ok. 1 passed; 0 failed
```

**结论：三个 cpython 内部符号在非 abi3 模式下均可编译链接**。8.OPT-SHARED 实施前提满足。
验证完成后已删除临时测试文件并还原 Cargo.toml（无 `[dev-dependencies]` 残留）。

## 7. 风险与后续（需 PM 注意）

### R1（中）：bench_stages.py / bench_breakdown.py 误导性 abi3 残留

`bench/bench_stages.py`（L230/L252）与 `bench/bench_breakdown.py`（L198/L219）在子进程
env 中硬编码 `PYO3_USE_ABI3_FORWARD_COMPATIBILITY=1`。该 env var 仅构建期生效，对已编译
的非 abi3 模块运行无影响（功能不受影响），但属误导性残留，且若未来以这些脚本子进程
触发任何 pyo3 build-time 探测会产生错误。建议后续清理（不在本任务范围）。

### R2（低）：cargo 命令需显式 PYO3_PYTHON=3.13 venv

非 abi3 模式下，`cargo build/test/clippy` 不再能直接用 PATH 上的 3.14（pyo3 0.22 拒绝 3.14）。
所有 cargo 命令需 `PYO3_PYTHON=<crs_venv_313>\Scripts\python.exe`。CI / 后续 DEV 自检清单
应纳入此约束。`maturin develop` 额外需 `VIRTUAL_ENV` 引导 + `--uv`（uv venv 无 pip）。

### R3（低）：DF1/TM1/Default rfield 既有设计质疑沿用

PERF-bench.md 中的 3 项 [设计质疑]（DF1 常量编译、TM1/DF2 rfield build）在本次 3.13 基线
测量中表现一致（workaround 仍生效），状态不变，待 PM 决策。
