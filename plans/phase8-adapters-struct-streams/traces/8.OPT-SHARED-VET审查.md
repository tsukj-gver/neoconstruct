## 1. 5 个 unsafe 块逐块审查（核心）

### 块 1：instance.rs L224 `PyObject_GenericGetDict` 调用（O1-A）

**源码**：
```rust
let dict_ptr = unsafe {
    ffi::PyObject_GenericGetDict(instance.as_ptr(), std::ptr::null_mut())
};
```

**SAFETY 注释完整性**（L217-223）：
- ✅ 指针来源：`instance.as_ptr()` 由 pyo3 `Bound<'py, PyAny>` 守护，是有效 PyObject 指针
- ✅ ABI 依赖：`PyObject_GenericGetDict` 是 CPython 公开 Stable ABI（自 3.10 起，Added 3.3）
- ✅ GIL 持有：由 `py: Python<'py>` 参数保证
- ✅ context 参数 NULL：CPython 文档约定（__dict__ getset descriptor 调用时传 NULL）
- ✅ 返回值语义：owned reference（new ref），由调用方负责 decref

**UB 风险审查**：
- ✅ managed dict 正确性：委托 CPython 内部 `_PyObject_GenericGetDictWithDict` 处理
  `Py_TPFLAGS_MANAGED_DICT` flag + lazy materialize（首次访问触发 dict 创建）
- ✅ NULL 返回处理：L225 `if dict_ptr.is_null()` 检查 + `PyErr::take(py)`
  （**比 PyErr::fetch 更安全**——fetch 在无异常时行为未定义，take 返回 Option）
- ✅ 无 &mut 别名：CPython GIL 单线程，instance 期间无并发修改

**退化路径**：返回 NULL → 返回 `PyErr`，调用方（struct_node.rs L340）fallback 到原
R4 getattr 路径，保留 slots class / `__dict__` override 错误信息。

**结论**：✅ **安全**。SAFETY 注释完整，无 UB 风险，退化路径完备。论证深度与
ADR-019（错误抛出 fast-path）/ ADR-021（Strings UTF-16/32 raw FFI）先例一致。

### 块 2：instance.rs L239 `Bound::from_owned_ptr`（O1-A）

**源码**：
```rust
unsafe { Bound::from_owned_ptr(py, dict_ptr) }
    .downcast_into::<PyDict>()
    .map_err(|_| { ... })
```

**SAFETY 注释完整性**（L235-238）：
- ✅ 所有权链：dict_ptr 是 owned reference（GenericGetDict 返回 new ref）
- ✅ from_owned_ptr 接管 ownership，pyo3 在 Bound drop 时自动 decref（无内存泄漏）
- ✅ downcast_into::<PyDict> 做运行期 type check

**UB 风险审查**：
- ✅ NULL 已在 L225 提前检查，到 L239 时 dict_ptr 必非 NULL
- ✅ owned ptr 转 Bound：refcount 平衡（GenericGetDict incref 一次 + Bound drop
  decref 一次）
- ✅ downcast 失败时（用户 override `__dict__` 描述符）返回 PyTypeError，调用方
  fallback 到 getattr

**结论**：✅ **安全**。所有权链清晰，refcount 平衡，退化路径完整。

### 块 3：instance.rs L292-294 `_PyDict_SetItem_KnownHash` 调用（O1-B）

**源码**：
```rust
let result = unsafe {
    ffi::_PyDict_SetItem_KnownHash(dict.as_ptr(), key.as_ptr(), value.as_ptr(), hash)
};
if result == -1 {
    Err(PyErr::fetch(py))
} else {
    Ok(())
}
```

**SAFETY 注释完整性**（L286-291）：
- ✅ 指针来源：dict / key / value 由 pyo3 Bound 守护，均为有效 PyObject 指针
- ✅ dict 类型保证：`Bound<PyDict>` 类型签名守护是 PyDictObject
- ✅ GIL 持有：保证单线程访问
- ✅ hash 来源：FieldName 编译期一次性 `PyObject_Hash` 计算并缓存
- ✅ ABI 依赖：`[CPython Internal Function]`，pyo3 0.22 cpython 子模块暴露，
  `#[cfg(not(Py_LIMITED_API))]` 守护（项目非 abi3 可用）

**UB 风险审查**：
- ✅ hash 正确性：interned PyString hash 在其生命周期内不变（CPython 强约束：
  interned 不可变 + hash 字段 once-cached），FieldName 持有 `Py<PyString>` 引用
  保证 hash 有效
- ✅ dict 有效性前提：dict 由 `dict_via_generic_getdict` 返回，已 materialize 为
  PyDictObject（GenericGetDict 内部强制 materialize）
- ✅ 返回值处理：`-1` 时 `PyErr::fetch`（KnownHash 返回 -1 必然有异常设置，
  fetch 安全）
- ✅ key hashable：interned PyString 自动满足

**退化路径**：返回 -1 → 返回 `Err(PyErr)`，与 `PyDict_SetItem` 同行为，调用方可
fallback。

**结论**：✅ **安全**。hash 缓存正确性论证充分，dict 有效性前提满足。

### 块 4：struct_node.rs L100 `PyObject_Hash` 调用（FieldName::new NB-4）

**源码**：
```rust
// SAFETY: py_name 是有效的 PyString 指针，PyObject_Hash 是 CPython Stable ABI。
// interned PyString hash 在其生命周期内不变（CPython 强约束）。
let cached_hash = unsafe { ffi::PyObject_Hash(py_name.as_ptr()) };
// NB-4 修复：PyObject_Hash 返回 -1 表示失败（异常已挂起）。interned PyString
// 理论不会失败，但若发生则 panic（构造期错误）。
if cached_hash == -1 {
    let err = PyErr::fetch(py);
    panic!(
        "FieldName::new: PyObject_Hash failed for interned string {:?}: {:?}",
        rust_name, err
    );
}
```

**SAFETY 注释完整性**（L98-99）：
- ✅ 指针来源：py_name 由 `intern_pystring` 创建，`Py<PyString>` 守护
- ✅ ABI 依赖：`PyObject_Hash` 是 CPython Stable ABI
- ✅ 不变量：interned PyString hash 在其生命周期内不变

**UB 风险审查**：
- ✅ hash 稳定性：CPython 强约束（interned 字符串不可变 + hash 字段 once-cached）
- ✅ panic 合理性：返回 -1 时 panic（构造期错误，比运行期退化更明确）。
  AGENTS.md §3 红线"禁止 panic 在非测试代码"——此处是**设计允许的例外**：
  - ADR-023 决策 2 + 设计 §1.2.2 + §7 #8 明确允许
  - 注释说明"仅在 OOM 等极端场景触发"
  - 替代方案（缓存 -1）会触发 dict 内部 hash 冲突路径性能退化（NB-4 修复的核心动机）
- ✅ panic 后状态：`PyErr::fetch` 取出异常（避免异常悬挂），构造期失败不影响
  已存在的 FieldName 实例

**结论**：✅ **安全**。NB-4 panic 是设计允许的例外（有 ADR + 设计文档双重背书），
注释充分论证了为何 panic 优于缓存 -1。

### 块 5：schema.rs L173-181 `PyBytesObject.ob_sval` 直读（O2-A）

**源码**：
```rust
let bytes: &[u8] = unsafe {
    use pyo3::ffi::PyBytesObject;
    let bytes_ptr = data.as_ptr() as *const PyBytesObject;
    let bytes_obj = &*bytes_ptr;
    let len = bytes_obj.ob_base.ob_size as usize;
    std::slice::from_raw_parts(bytes_obj.ob_sval.as_ptr() as *const u8, len)
};
```

**SAFETY 注释完整性**（L160-172）：
- ✅ 指针来源：data 是 `&Bound<'py, PyBytes>`，pyo3 参数类型签名在入口处 type check
- ✅ ABI 依赖：`[CPython Internal Struct]` PyBytesObject.ob_sval + ob_base.ob_size，
  pyo3 0.22 cpython 子模块暴露，`#[cfg(not(any(PyPy, GraalPy, Py_LIMITED_API)))]` 守护
- ✅ ob_sval 长度不变量：声明为 `[c_char; 1]` 是占位，实际长度 `ob_base.ob_size + 1`
  （含终止 NUL），from_raw_parts len 取 ob_size（不含 NUL）
- ✅ 借用：返回的 `&[u8]` 生命周期受 `data` 借用约束（Rust borrow checker 保证）
- ✅ GIL 持有

**UB 风险审查**：
- ✅ 指针偏移正确性：`data.as_ptr()` 返回 `*mut ffi::PyObject`，cast 为
  `*const PyBytesObject` 后 deref——CPython 内部约定（PyBytes 是 PyVarObject 子类，
  布局兼容，PyBytes_Check 通过则 cast 安全）
- ✅ ob_size 长度：`ob_base.ob_size` 是 PyVarObject 的 Py_ssize_t 字段，cast usize
  在 64-bit 系统安全（项目锁定 AMD64）
- ✅ NUL 终止：CPython 不变量 `ob_sval[ob_size] == '\0'`，from_raw_parts len 取
  ob_size 不含 NUL（slice 不会越界）
- ✅ 别名规则：CPython GIL 单线程 + parse 期间不修改 data，无 &mut 别名。返回的
  `&[u8]` 与 data 共享内存，但 parse 流程是只读的

**注释精度小问题**（非阻塞）：
- 注释 L162-163 说 "PyBytes_CheckExact 通过才进入此函数"，实际 pyo3 0.22 参数
  类型转换走的是 PyBytes_Check（不是 CheckExact）。但 **CPython 不允许 bytes 被
  子类化**（Py_TPFLAGS_BASETYPE 未设置），所以 Check 与 CheckExact 等价。注释
  表述略有偏差但不影响安全性。

**退化路径**：cpython 子模块缺失时编译失败（编译期发现）；无 abi3 fallback
（非 abi3 是项目约束，详 ADR-023 §abi3 处理策略）。

**结论**：✅ **安全**。指针偏移、长度、NUL 终止、别名规则均正确。

## 2. §0 合规审查（L-01 对策）

| §0 原则 | 审查结论 | 证据 |

| **#6 enum_dispatch 静态分派** | ✅ 合规 | StructNode 仍是 Node enum 变体，分派路径不变。FieldName 字段变化不影响 enum_dispatch |
| **#7 Result + thiserror** | ✅ 合规 | 错误处理不变。退化路径返回 `ConstructError::Generic`（struct_node.rs L347-361） |
| **#8 Stream 抽象纯 Rust** | ✅ 合规 | Stream 抽象不涉及 |

**L-01 触发检查**：三条优化都**不引入中间表示层**——GenericGetDict 返回 Python 对象
本身（不是 Rust HashMap 再转回），KnownHash 直接操作 Python dict，ob_sval 返回
Rust slice 但这是输入侧（已有 ParseStream 的纯 Rust 抽象）。**未触发 L-01**。

| **失败判据**（TM1 rs_ns > 200ns）| 200ns | **189ns** | 190ns | ✅ **未触发**（共享税优化成功）|
| 目标判据（TM1 rs_ns ≤ 180ns）| 180ns | 189ns | 190ns | ⚠ 未达 target（超 9-10ns，L-09 噪声带）|

**TM1 共享税压缩复现**：基线 237ns → VET 复测 189ns（**节省 48ns**），与 DEV 报告
的 47ns **实质一致**（差异 1ns 在测量噪声内）。**失败判据未触发**。

#### 6.3.2 CN1 LOW→OK 转化

VET 复测 CN1 parse **mean 10.42x**（≥10x 达标），但 **min 9.93x / std 0.34**
表明 CN1 parse 对环境敏感（5 轮中有 2 轮 <10x：9.93x / 10.23x）。

DEV 报告 CN1 parse 10.65x（mean）/ 10.46x（min）/ std 0.13——DEV 会话更稳定。

**判定**：CN1 LOW→OK 在 VET 复测中 **mean 达标但稳定性较差**。不阻塞（设计 §3.2
预测 LOW→OK 已验证，mean 达标是判据），但建议 PM 关注 std。

#### 6.3.3 阳性对照不回退

TM1/EN1/MP1 全部 ≥ 10x（11.31-11.58x），与 3.13 基线（10.28-10.88x）相比**提升
而非回退**（共享税压缩带来额外加速）。

#### 6.3.4 阴性对照不回退（build 方向）

CN1 build 15.92x / TM1 build 18.83x，与 3.13 基线（15.07x / 17.26x）一致或提升。
build 路径不经 O1-A/O1-B（仅 O2-A 影响 _parse_raw），所以 build 的稳定性证明
**环境漂移在可控范围内**（L-09 阴性对照有效）。

### 6.4 VET ↔ DEV 数据一致性（L-09 谨慎归因）

**高度一致项**（差异 ≤5ns）：
- TM1 parse（189 vs 190，差 1ns）
- EN1 parse（193 vs 193，差 0ns）
- MP1 parse（191 vs 191，差 0ns）
- CN1 build（127 vs 127，差 0ns）
- TM1 build（118 vs 117，差 1ns）
- FE1 build（430 vs 428，差 2ns）

**噪声带内项**（差异 6-33ns）：
- HX1/HX2/HD1 parse：VET 比 DEV 高 22-33ns（Hex 显示对象构造对环境敏感，VET 会话
  略慢，但 Δns vs 基线仍为负，优化生效）
- FE1 parse：VET 328 vs DEV 310，差 18ns

**需关注项**（差异 >25ns）：
- **CN1 parse**：VET 211 vs DEV 195，差 16ns。VET 单轮 std 0.34（DEV 0.13），
  说明 CN1 parse 路径对环境敏感。**L-09 归因**：CN1 是单字节 Const parse，共享税
  占比极高（~90%），任何环境波动（CPU 频率 / 缓存状态）都会显著影响绝对 ns。
- **NT1 parse**：VET 600 vs DEV 571，差 29ns。NamedTuple 构造路径重（~600ns），
  VET 会话整体略慢，但 Δns vs 基线仍 -2ns（未回退）。

**归因判定（L-09）**：VET 与 DEV 数据**实质一致**。差异集中在重 case（HX/NT）和
共享税占比极高的 CN1，均可由环境波动（CPU 频率 / 缓存 / 后台进程）解释。**关键
判据（TM1 失败判据 / 阳性对照不回退）VET 与 DEV 完全一致**。

   ADR-019/ADR-021 先例（共享路径，影响所有 parse，论证更严）。

### 7.2 风险点（不阻塞）

1. **NB-4 panic**（struct_node.rs L105）：FieldName::new 在 PyObject_Hash 返回 -1
   时 panic。这是设计允许的例外（ADR-023 + 设计 §1.2.2 + §7 #8 三重背书），仅
   OOM 等极端场景触发。**接受**。
2. **CN1 parse 稳定性**：VET 复测 std 0.34（DEV 0.13），min 9.93x。CN1 共享税
   占比 ~90%，对环境敏感。**建议 PM 在后续 perf 跟踪中关注 CN1 std 趋势**。
3. **FE1-parse 未稳定达标 10x**：VET 9.59x / DEV 9.78x，mean 均 <10x。设计 §3.2
   已声明 "FE1-parse min/max 跨 10x 边界"，PM 决策是否计入 LOW→OK。

### 7.3 非阻塞建议

1. **O2-A SAFETY 注释精度**（schema.rs L162-163）：注释说 "PyBytes_CheckExact
   通过才进入此函数"，实际 pyo3 走的是 PyBytes_Check。CPython 不允许 bytes 子类化
   （Py_TPFLAGS_BASETYPE 未设置），两者等价，但注释可改为 "PyBytes_Check 通过
   （CPython 不允许 bytes 子类化，与 CheckExact 等价）" 更精确。**非阻塞，后续
   文档迭代时修正**。
2. **CN1 LOW→OK 的 std 跟踪**：建议 PM 在 8.OPT-CASE-B 后或 perf 监控中持续跟踪
   CN1 parse 的 std，若长期 >0.3 需考虑环境归因或加测轮次。
3. **FE1-parse 决策**：设计 §3.2 预测 FE1-parse ~10.9-11.5x，实测 VET 9.59x /
   DEV 9.78x，**未达预测下限**。建议 PM 关注是否需 OPT-CASE-B 进一步优化（或
   接受为"接近 10x"）。
