# Phase 0: 架构设计

## 阶段目标

为新 construct-rs 项目奠定架构地基。Phase 0 产出的文档必须自包含——任何读者无需了解 pydantic-core、mashumaro、Python construct 三个参考项目的任何一行代码，即可理解核心设计理念。

## 前置依赖

- 无（项目起始）

## 子任务清单

### 0.1 设计原则文档：FFI 边界 + Dataclass Mixin 编译（ARCH → REV）✅ 已通过

ARCH 阅读三个参考项目的源码，提取关键设计理念，产出两份**去业务化的设计原则文档**。

#### 文档一：`docs/FFI设计.md` — 单次 FFI 边界设计原则

研究目标：理解"编译期构建执行树，运行时单次 FFI 穿越，Rust 内部直接操作 Python 对象"这一模式。

文档需回答：
- 为什么每次操作（parse/build）只应有一次 FFI 穿越？
- 如果执行树内部每个节点都回调 Python，性能开销从何而来？
- "编译期构建执行树"是什么意思？编译产物是什么形态？
- "直接操作 Python 对象"具体指什么？parse 的产出和 build 的输入在 Rust 侧如何表达？
- 静态分派（编译期已知所有分支）相比动态分派的优势是什么？
- 这一模式有哪些限制/代价？（如：执行树不可运行时修改）

#### 文档二：`docs/Mixin设计.md` — Dataclass Mixin 自动编译设计原则

研究目标：理解"用户定义 dataclass 子类时，在类创建钩子中自动完成编译，用户无感"这一模式。

文档需回答：
- "类创建钩子"在 Python 中是什么机制？何时触发？
- 编译需要收集哪些信息？（字段名、字段类型描述符、顺序等）
- 编译产物如何与类关联？后续 parse/build 如何找到它？
- 前向引用（字段类型引用尚未定义的类）如何处理？
- 这一模式对用户 API 有什么约束？用户能做什么、不能做什么？

#### 输出要求（两份文档共同遵守）

1. **去业务化**：不得出现任何参考项目的内部代码、类名、文件路径、函数名。不得出现"pydantic-core 中的 XXX 类"或"mashumaro 的 YYY 函数"这类表述。
2. **自包含**：读者无需阅读任何参考项目源码即可完全理解。
3. **设计导向**：描述的是"应该怎么做"和"为什么这样做"，不是"某个项目是怎么做的"。
4. **可证伪**：每个设计原则应包含"如果违反这条原则会发生什么"的反面论证。
5. 分批写入，每次不超过 300 行。

## 关键约束

- **直接操作 Python 对象**：parse 直接产 PyObject，build 直接读 PyObject，不在 Rust 侧引入中间数据类型
- **输出/输入侧无抽象 trait**：不在输入/输出侧引入 trait 抽象层
- **单 crate**：pyo3 是核心依赖
- **一次 FFI**：编译/parse/build 各一次
- **不常用的功能先不做**：Phase 1 只做最小集
