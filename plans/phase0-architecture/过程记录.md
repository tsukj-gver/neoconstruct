### ARCH 设计说明

**FFI设计.md 核心论点**：
1. FFI 穿越开销（100-300ns）远大于节点计算量（5-20ns），N 字段 = 2N 次穿越会抵消 Rust 优势
2. 编译期构建不可变执行树，运行时只遍历不重建
3. 直接操作 Python 对象，无 Rust 中间类型（中间类型带来三重开销）
4. 静态分派（enum + match）优于动态分派（Box<dyn>）
5. 错误在单次 FFI 内用 PyResult 传播

**Mixin设计.md 核心论点**：
1. `__init_subclass__` 是编译的正确触发点（比元类简单、无冲突）
2. 字段描述符应为 Python 对象（携带参数、支持编译期检查、可组合）
3. 编译产物作为类属性存储，O(1) 查找且不可变
4. 前向引用通过延迟桩（stub）处理
5. `__init_subclass__` 先于 `@dataclass` 执行，编译管线不能依赖 `__dataclass_fields__`

**4. 可行性：✅ 通过（含 1 项需 0.2 明确的关键点）**

- **`__init_subclass__` 先于 `@dataclass` 论断——已实测验证正确**：
  REV 用 Python 实测确认：`__init_subclass__` 触发时类对象确实**没有** `__dataclass_fields__` 属性，`@dataclass` 装饰器之后才有。Mixin §7.2 的论断和推导（编译不能依赖 `__dataclass_fields__`，须从原始类体属性收集字段）完全成立。
- **延迟桩（stub）方案基本可行**：§6.3 的"安装桩→首次调用编译→替换桩"逻辑成立。§6.4 已识别多线程竞态并给出加锁/OnceLock 方向。
- **编译产物作类属性存储可行**：`frozen=True` dataclass 不阻止类属性设置（frozen 约束实例属性），方案 A 无技术障碍。
- **字段描述符为 Python 对象——与 examples/ 一致**：`field(Int8ub)` 形式、预定义单例 + 可实例化类 + 类引用三种形态，与 examples/construct.py 和 example.py 完全兼容。
- ⚠️ **需 0.2 明确的关键点——循环引用处理**：
  Mixin §6.2 第 3 步称"首次调用时对方类已定义，可成功解析引用"。但对于**互相引用**（NodeA↔NodeB），NodeB 编译时 NodeA 虽存在但**尚未编译**（只有延迟桩）。此时编译器能否获取 NodeA 的字段结构？
  执行树中"递归引用节点"的存储策略（存"类引用"运行时动态解析 vs 存"编译产物引用"）未明确，这直接决定循环引用是否可行。建议 0.2 明确：递归节点应存储类引用（`Py<Type>`），运行时 parse 通过 `cls._construct_compiled` 动态获取对方执行树——此策略下循环引用可行。
