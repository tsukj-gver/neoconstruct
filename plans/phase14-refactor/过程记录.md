**检视文档**：`docs/refactor/模块设计-dataclass-API.md`

### 总体结论

**驳回至 DESIGNING** — 存在 3 个阻塞级可行性问题（B-FEAS），涉及编译流程核心路径与
Phase 13 接口暴露状态的事实性错误。ARCH 需修正设计后重新提交。

核心问题：设计文档假设 Python 端可以通过 `Struct().field(name, subcon)` 构建器模式
增量构建 Rust Struct，但**实际代码确认 `PyStruct` 未暴露 `.field()` 方法**。此外，
`_resolve_subcon` 调用的 `extract_subcon` 返回 Rust 类型（`Box<CombinedConstruct>`），
无法从 Python 端调用。这两点导致 `_compile` 核心流程不可实现（需 Rust 改动）。

##### B-FEAS-1（阻塞）：PyStruct 未暴露 `.field()` 方法

**文档位置**：§5.2 步骤 2、§2.2 `_compile`、§8.2.2 `_build_struct_decl`、§9.4 表格

**问题描述**：
设计文档的核心编译流程 `_compile` 假设 Python 端可通过构建器模式增量构建 Struct：
```python
builder = Struct()                        # PyStruct
builder = builder.field(f.name, subcon)   # 增量添加字段
```
§9.4 表格声称 `Struct` builder 的 `.field(name, subcon)` 已暴露（"已暴露 Phase 10 py_struct"）。

**代码事实（已确认）**：
- `PyStruct`（`constructs_composite.rs:166-267`）的 `#[pymethods]` 仅暴露 `__getattr__`、`__repr__`
- `impl_api_methods!` 宏注入的 7 个方法（parse/build/sizeof 等）不包含 `.field()`
- `impl_construct_operators!` 宏注入的 6 个运算符也不包含 `.field()`
- **`.field()` 仅存在于 Rust 内部的 `construct::constructs::Struct` builder，未通过 pymethod 暴露给 Python**

§9.4 表格中 "`.field(name, subcon)`" 标注为"已暴露"是**事实性错误**。

**影响**：整个 `_compile` / `_build_struct_decl` 流程无法按设计实现。

**建议修改方向**：
两种可行方案（ARCH 任选其一并在设计文档中明确）：

- **方案 1（推荐，零 Rust 改动）**：改用 `Struct(**subconskw)` 关键字参数形式。`py_struct` 已支持 `(*subcons, **subconskw)`（`constructs_composite.rs:216`），Python 端直接：
  ```python
  fields = {f.name: _get_field_subcon(f) for f in dataclasses.fields(cls)}
  struct_obj = Struct(**fields)  # py_struct 的 **subconskw 路径
  holder = compile_schema(struct_obj)
  ```
- **方案 2（需 Rust 改动）**：为 `PyStruct` 新增 `.field(name, subcon) -> PyStruct` pymethod。在 §9.4 改动清单中新增此项。

##### B-FEAS-2（阻塞）：`_resolve_subcon` 调用 `extract_subcon` 返回 Rust 类型，Python 不可调用

**文档位置**：§8.2.1 `_resolve_subcon`

**问题描述**：
```python
def _resolve_subcon(subcon):
    # ...
    from construct_rust._core import extract_subcon
    return extract_subcon(subcon)  # 返回 Box<CombinedConstruct>（Rust 类型）
```
`extract_subcon`（`py_adapter.rs:417`）签名为 `fn extract_subcon(obj: &Bound<PyAny>) -> PyResult<Box<CombinedConstruct>>`。返回值 `Box<CombinedConstruct>` 是 Rust 类型，不是 PyObject。即使暴露为 pyfunction，Python 端无法持有或传递此返回值。

**影响**：嵌套 dataclass 编译路径（§8.2）依赖 `_resolve_subcon`，无法按设计实现。

**建议修改方向**：
消除 `_resolve_subcon` 函数。Python 端直接传递 PyObject（PyO3 wrapper 或 PyStruct）给 `compile_schema` 或 `Struct(**kwargs)`，由 Rust 端的 `extract_subcon` 在 FFI 边界内部完成转换。具体：
```python
# Python 端只收集 (name, PyObject) 对，不做 extract
fields = {}
for f in dataclasses.fields(cls):
    subcon = _get_field_subcon(f)
    if isinstance(subcon, type) and issubclass(subcon, ConstructMixin):
        subcon = subcon._build_struct_decl()  # 返回 PyStruct（PyObject）
    fields[f.name] = subcon   # subcon 是 PyObject（PyO3 wrapper 或 PyStruct）
struct_obj = Struct(**fields)  # Rust 端 add_struct_subcon → extract_subcon
```
注意：此方案下 `_resolve_subcon` 的 case (a) 普通 wrapper 不需要显式 extract，`Struct(**kwargs)` 内部的 `add_struct_subcon` 会自动调用 `extract_subcon`。

##### I-COMP-1（重要）：`from __future__ import annotations` 下类型解析失败

**文档位置**：§8.4.2 `_dict_to_instance`

**问题描述**：
`_dict_to_instance` 调用 `typing.get_type_hints(cls)` 解析类型注解以识别嵌套 dataclass 字段。当项目使用 `from __future__ import annotations`（PEP 563，Python 3.10-3.13 中常见模式）时，所有注解变为字符串。

设计在 §8.3.2 有 fallback：`except Exception: hints = getattr(cls, '__annotations__', {})`。但 fallback 后 `hints` 的值是字符串（如 `"FileHeader"`），`isinstance(ftype, type)` 返回 False，**嵌套 dict 不会被转换为嵌套 dataclass 实例**。

`typing.get_type_hints` 本身能正确处理 `from __future__ import annotations`（它评估字符串注解），所以正常路径没问题。但如果 `get_type_hints` 因任何原因失败（如模块未正确加载、循环导入等），fallback 路径会静默丢失嵌套转换。

**影响**：使用 `from __future__ import annotations` 的项目，或存在复杂导入依赖的项目，嵌套 dataclass parse 结果中嵌套字段为 dict 而非 dataclass 实例。

**建议修改方向**：
1. `_dict_to_instance` 的 fallback 不应静默使用原始 `__annotations__`。若 `get_type_hints` 失败，应抛出清晰的错误消息
2. 或在 `_compile` 时调用 `get_type_hints` 并缓存结果（`get_type_hints` 成功时缓存；失败时报错而非 fallback）

##### I-COMP-2（重要）：多余键过滤策略过于简单

**文档位置**：§6.4 边界条件表

**问题描述**：
设计建议"过滤掉下划线开头的键"来处理 PyDict 多余键。但 construct 中匿名字段产出的键不一定以下划线开头（如 Padding 产出匿名、Const 可能产出值）。更精确的做法是基于 `dataclasses.fields(cls)` 的字段名白名单过滤。

**建议修改方向**：
```python
valid_names = {f.name for f in dataclasses.fields(cls)}
filtered = {k: v for k, v in result.items() if k in valid_names}
return cls(**filtered)
```
这确保只传递 dataclass 声明的字段，其余键（construct 内部键如 `_io`、`_`，或匿名字段产出）全部过滤。

##### I-COMP-3（重要）：`construct_dataclass` 装饰器修改 `__bases__` 有风险

**文档位置**：§4.3 方案 B

**问题描述**：
```python
cls.__bases__ = (ConstructMixin,) + cls.__bases__
```
运行时修改 `__bases__` 存在已知风险：
1. 若 `cls` 有非 `object` 基类且涉及 `__slots__` 或 layout conflict，Python 会抛 `TypeError`
2. 修改 `__bases__` 后 MRO 重算可能失败
3. 已被其他代码引用的类对象身份不变但行为突变

**建议修改方向**：
方案 B（语法糖）是可选项（§10.4），非 MVP 必需。建议在设计文档中标注此风险，或改为更安全的 `type()` 重建方案（接受类身份变化的权衡）。至少在 MVP（14.1）中不包含方案 B。

##### I-FEAS-1（重要）：嵌套 dataclass 的编译路径与设计描述不符

**文档位置**：§8.2.3

**问题描述**：
设计声称嵌套 dataclass 编译后"嵌套 Struct 的编译结果内联在父 schema 的执行树中（CompiledNode::Struct 嵌套），无独立缓存"。

**代码事实**：当 PyStruct 作为子构造器传入 `Struct(**kwargs)` 时，`add_struct_subcon` 调用 `extract_subcon(pystruct_obj)`。`try_extract_registered`（`constructs_adapter.rs:1315-1456`）**不包含 PyStruct**（仅注册了 atomic/adapter/stream/string 类型）。因此 PyStruct 走 duck-typing fallback → 被 `PyConstructAdapter` 包装为 `CombinedConstruct::Dynamic`。

**影响**：嵌套 dataclass 不会作为 `CompiledNode::Struct` 内联编译，而是作为 `CompiledNode::External`（PyCallback/Dynamic）执行。功能上可行（parse 仍返回嵌套 dict），但：
1. 性能：每次嵌套 parse 走 Python 回调（PyConstructAdapter → PyStruct.parse），不走 Rust 编译路径
2. 与 §8.2.3 描述不符（不是 CompiledNode::Struct 嵌套）
3. build 方向同理（Dynamic path 而非直接 Rust exec_build）

**建议修改方向**：
两种可行方案：
- **方案 1（推荐，零 Rust 改动）**：在设计文档中修正 §8.2.3 的描述，承认嵌套 dataclass 走 Dynamic 路径（MVP 可接受，14.5 优化时考虑直构）
- **方案 2（需 Rust 改动）**：将 `PyStruct` 加入 `try_extract_registered`（调用 `PyStruct::make_owned()`），使嵌套 PyStruct 获得直接 Rust 提取。但这可能影响现有的 Struct 扁平化语义（`+` 运算符），需谨慎。

##### S-COMP-1（建议）：Sequence-like dataclass 未覆盖

**文档位置**：全文

**问题描述**：
设计仅覆盖 Struct-like dataclass（命名字段）。Python 原版 construct 也支持 Sequence（位置字段）。dataclass 的位置字段（无默认值、有类型注解）也可映射到 Sequence。设计未提及这一场景。

**建议**：在设计文档中明确 Phase 14 范围（仅 Struct-like），Sequence-like dataclass 留待后续阶段。

### 新发现问题

#### N-1（重要，影响 14.2）：§8.2.3 嵌套编译描述与代码事实不符

**文档位置**：§8.2.1 `_resolve_nested_subcon` + §8.2.3 编译流程图（906-934 行）

**问题描述**：
v2 §8.2.3 声称嵌套 PyStruct 传入 `Struct(**kwargs)` 后：
> `extract_subcon(PyStruct)` → 识别为 PyStruct → 提取 inner Rust Struct → 内联编译为 CompiledNode::Struct

并给出了内联编译流程图（928-933 行）：
```
CompiledNode::Struct { fields: [
    ("header", CompiledNode::Struct { ... }),  ← 声称内联
]}
```

**代码事实（已逐行确认）**：

1. `py_struct` kw 路径（`constructs_composite.rs:227-233`）对每个 kw value 执行：
   ```rust
   let renamed = apply_rename(py, &val, &name)?;  // → make_renamed → extract_subcon(val)
   let inner = extract_subcon(renamed.bind(py))?;  // → extract_subcon(PyRenamed)
   ```
2. `apply_rename` → `make_renamed`（`py_renamed.rs:93`）调用 `extract_subcon(subcon_obj)`
3. `extract_subcon`（`py_adapter.rs:417-441`）的逻辑：
   - 先 `try_extract_registered(obj)` — **`try_extract_registered`（`constructs_adapter.rs:1315-1452`）不包含 PyStruct**（也不含 PySequence / PyArray）
   - 再检查 duck-typing（`hasattr("parse_stream") and hasattr("build_stream")`）
   - `PyStruct` 通过 `impl_api_methods!` 宏（`construct_macros.rs:54/108`）注入了 `parse_stream` / `build_stream`
   - **因此 PyStruct 走 duck-typing → `PyConstructAdapter` 包装 → `CombinedConstruct::Dynamic`**
4. kw 路径第二次 `extract_subcon(PyRenamed)`：PyRenamed 也未注册（`constructs_adapter.rs:1451` 注释明确说明），
   PyRenamed 通过 `__getattr__`（`py_renamed.rs:233`）代理了 parse_stream/build_stream → 同样走 Dynamic
5. 最终 `builder.field(name, Dynamic(PyConstructAdapter(PyRenamed(PyStruct))))`

**编译结果**：编译器看到 `Dynamic`，编译为 Dynamic/External 节点（持有 `Arc<dyn Construct>`），
**不是** `CompiledNode::Struct` 嵌套。

**运行时行为**（功能上可行，但有开销）：
- `PyConstructAdapter.parse`（`py_adapter.rs:196-261`）对 PyStruct 有 fast path（202 行），
  但此处 py_obj 是 PyRenamed（不是 PyStruct），**fast path 不触发**
- 走 Python 回调路径：PyRenamed.parse_stream → `__getattr__` → PyStruct.parse_stream →
  `api::py_parse_stream` → 编译 + parse → 返回 dict
- 嵌套字段最终得到 dict，`_dict_to_instance` 递归转换为 dataclass 实例

**影响**：
1. **设计描述不准确**：§8.2.3 编译流程图与实际不符，会误导 DEV 实现
2. **性能**：嵌套字段每次 parse 走 Python 回调（PyConstructAdapter → PyRenamed → PyStruct），
   非 Rust 编译内联路径。PyConstructAdapter 回调涉及 BytesIO 流转换（额外开销）
3. **不影响功能**：Dynamic 路径正确代理 parse/build，最终结果正确

**建议修改方向（ARCH 在 14.2 DESIGNING 阶段选择其一）**：

- **方案 1（推荐，零 Rust 改动，修正文档描述）**：承认嵌套 dataclass 走 Dynamic 路径。
  修正 §8.2.3 的编译流程图，将 `CompiledNode::Struct` 嵌套改为 `CompiledNode::External/Dynamic`。
  性能在 MVP 可接受（14.5 优化阶段可考虑直构）。
- **方案 2（需 Rust 改动，实现真正内联）**：将 PyStruct 加入 `try_extract_registered`
  （调用 `PyConstructWrapper::as_construct(self).make_owned()`），使 `extract_subcon(PyStruct)`
  直接提取内部 Rust Struct。但需评估对现有 `+` 运算符扁平化语义的影响。

**是否阻塞**：
- **不阻塞 14.1**（扁平 dataclass 无嵌套，不受影响）
- **阻塞 14.2**（嵌套 dataclass 的设计描述需先修正）

#### N-2（小问题）：_collect_field_subcons 存在两个不一致版本

**文档位置**：§3.2（`_collect_field_subcons`）vs §8.3.2（`_compile` 内联版本）

§3.2 版本不处理 `subcon=None`（前向引用），直接传给 `_resolve_nested_subcon` → 抛 TypeError。
§8.3.2 内联版本检查 `if subcon is None` → 调用 `_resolve_forward_ref`。

两者逻辑不一致。`_build_struct_decl`（§8.2.2）调用 §3.2 版本，遇到前向引用会失败。

**建议**：统一为一个函数（带前向引用参数），或在 §3.2 中明确标注"不含前向引用处理，仅用于 14.1/14.2"。

#### N-3（小问题）：pymethod 签名适配方案未明确

**文档位置**：§9.4 末尾注释 + §10.1 Rust 改动清单

现有 `parse_bytes_py` / `build_from_py` 签名参数 `kw: IndexMap<String, Value>` 不能直接作为
PyO3 `**kwargs`（需 `Option<&Bound<PyDict>>`）。§9.4 注释提到了两种方案（新增包装 vs 修改签名），
但未明确选择。

考虑到约束 C1（现有签名不变），实际只能新增 pymethod 包装（如 `#[pyo3(name = "parse_bytes_py")]`）。
建议在设计文档中明确。

#### N-4（小问题）：CompiledSchemaHolder pyclass 需 unsendable

`CompiledSchema` 内部不是 Send+Sync（`compiled_ext.rs:88` 注释），注册 pyclass 时需要
`#[pyclass(name = "CompiledSchemaHolder", unsendable)]`。文档未提及 `unsendable`。

#### N-5（小问题）：_dict_to_instance 每次 parse 重复解析类型提示

`_dict_to_instance`（§8.4.2）在 parse 路径上，每次 parse 都调用
`typing.get_type_hints(cls, globalns=...)`。应在 `_compile` 时缓存 hints 到 ClassVar，
`_dict_to_instance` 直接读取缓存。（v1 S-PERF-1 的延续，MVP 可接受但应标注。）

#### N-6（小问题）：List[Dataclass] 嵌套场景未覆盖

`_dict_to_instance`（§8.4.2）只处理 `dict → 嵌套 dataclass`，不处理 `list[dict] → list[dataclass]`。
若 dataclass 字段类型为 `List[SomeDataclass]`（Array 嵌套 dataclass），parse 后嵌套字段为 list of dict，
不会递归转换。建议在 §8.4.2 补充 list 递归处理，或在 §10 范围说明中标注此限制。

[设计质疑] PyInput::as_value() 新增 `__dict__` fallback

设计文档（§7.3）声称 build 方向"PyInput 已支持 attribute 访问，零改动"。但实际测试发现
`CompiledStruct::exec_build` 在 line 1764 调用 `input.as_value()` 将整个输入转为 `Value::Container`。
对于 dict 输入，`py_to_value` 正确转换为 Container；但对于 dataclass 实例，
`py_to_value` 不识别该类型，返回 TypeError。

**修复方案**：在 `PyInput::as_value()` 中增加 fallback 路径——当 `py_to_value` 失败时，
尝试读取 Python 对象的 `__dict__` 属性，将其转换为 `Value::Container`。
这是 construct-py 侧的修复，**零 construct-rs 改动**，不影响现有行为。

**设计文档 §3.3 (FFI 执行层) 的 Pattern C（lazy field access）**描述了复合节点应使用
`get_field`/`sub_input_field` 而非 `as_value`。但实际 `CompiledStruct::exec_build` 仍使用
eager `as_value()` 方式（Pattern A/B 混用）。尝试将其改为 Pattern C 导致 30 个测试回归
（Rebuild/Checksum 等依赖"所有字段在 context 中"的语义）。Pattern C 的正确实现需要更深入的
context 传播重构，留作后续优化。

1. `sizeof()` 对 `make_combined` 编译的 schema 返回 `None`（Dynamic 节点无法计算静态大小）
