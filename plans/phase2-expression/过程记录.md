## 设计共识完整记录

### 决策 1：废弃 `this` 机制，改用编译期字段引用

**问题**：Python construct 的 `this.count` 是运行时 `Path` 对象——无类型信息、无 IDE 补全、
拼写错误到 parse 时才报、`len_()` 会静默错算、`_`/`_root` 是隐式魔法。

**方案**：字段名本身就是引用对象。`Bytes(count)` 而非 `Bytes(this.count)`。
`count` 是 `FieldRef[int]` 类型对象，在 `__init_subclass__` 中编译解析。
`count + flag` → `ExprRef[int]`，类型传播。拼写错误在编译期 `CompilationError`。

### 决策 2：表达式编译为 Rust 栈式 VM，零 FFI 求值

编译期将表达式翻译为 `ExprOp` 指令序列：
```rust
enum ExprOp {
    GetField(usize),    // interned field name index
    Const(i64),
    Add, Sub, Mul, Div,
    // ...
}
```
运行时 `eval_expr(ops, ctx)` 在 Rust 内部栈式执行，全程不跨 FFI。

### 决策 3：不提供 `len_()`，用显式 `Tell()` + `Computed()`

```python
start: int = rfield(Tell())
# ... 其他字段 ...
end: int = rfield(Tell())
actual_length: int = rfield(Computed(end - start))
```

### 决策 4：嵌套 Struct 跨层引用用显式 `context=` 参数传递

```python
sections: list = field(
    Array(section_count, Section),
    context={"machine": machine}  # 显式注入，类型检查
)
```
Section 内部用 `ContextRef[int]("machine")` 声明依赖。不靠魔法 `this._._`。

### 决策 5：三种 field 函数替代 FieldRole——RW/RO/WO 数学完备分类

从用户视角定义两个布尔属性：
- **R**：parse 后用户能读到（出现在实例属性中）
- **W**：build 时用户需要提供（出现在 `__init__` 参数中）

非空子集 `{RW, RO, WO}`——数学完备，可证明穷尽（{R,W} 的非空子集）。

| 函数 | 含义 | dataclass 配置 | 用户视角 |
|------|------|---------------|---------|
| `field(subcon)` | RW | 正常 field，在 `__init__` 中 | build 要填，parse 能读 |
| `rfield(subcon)` | RO | `init=False` | build 不用填，parse 能读 |
| `wfield(subcon)` | WO | 正常 field，在 `__init__` 中 | build 要填，parse 读不到 |

用户需要知道的就一句话：**`r` = 读得到，`w` = 要填，`field` = 两者都要**。

### 决策 6：default 处理——`field(subcon, default=value)` 自动 kw_only

可填可不填的字段（原 Python construct 的 `Default` 语义）：
```python
version: int = field(Int8ub, default=1)    # 有 default → 自动 kw_only=True
data: bytes = field(Bytes(4))               # 无 default → positional
```
有 default → `kw_only=True` → 可以出现在任何位置，不受 dataclass 字段顺序约束。

### 决策 7：`Default` 构造器不再需要

`field(subcon, default=value)` 完全覆盖 `Default(subcon, value)` 的语义。
**分层原则**：field 函数管用户语义（谁填值、默认值是什么）；构造器只管字节语义
（怎么读、怎么写、怎么校验）。

| Python construct | 我们的处理 | 理由 |
|-----------------|-----------|------|
| `Default(subcon, value)` | `field(subcon, default=value)` | 纯用户语义，归 field 层 |
| `Const(value, subcon)` | `rfield(Const(subcon, value))` | 字节层仍有用——parse 时校验 |
| `Computed(expr)` | `rfield(Computed(expr))` | 字节层仍有用——parse 时从 context 计算 |
| `Rebuild(subcon, expr)` | `rfield(subcon)` + 表达式系统 | build 时自动算，parse 时正常读 |

### 决策 8：字节顺序与 init 顺序解耦

**核心原则**：字节布局顺序 = 声明顺序；`__init__` 参数顺序 = 按字段性质自动排列。
两者独立。`rfield` 的 `init=False` 不参与 dataclass 参数排序约束。

#### 性能预测核心结论

使用 P0 后修正基线（Python construct 固定 ~1816ns + per-field ~413ns；
construct-rs 固定 ~229ns + per-field ~33ns），表达式场景加速比公式：

```
ratio = (1816 + 413*N + 200*K) / (229 + 33*N + 30*K)
```

| 场景 | 预测加速比 | 达标(≥8x) |
|------|----------|----------|
| 最小表达式(N=2,K=1) | 8.1x | ✅ |
| 典型小结构(N=3,K=1) | 9.1x | ✅ |
| 中等结构(N=10,K=3) | 10.1x | ✅ |
| 大结构(N=50,K=5) | 11.6x | ✅ |
| build 方向(N=3,K=1) | 7.2x | 接近（build set_field 开销） |

**主要风险**：GetInt 开销（PyDict get_item + extract i64 ≈ 25-35ns）。
如高于 50ns，备选 i64 并行缓存方案。

**失败门槛**：<4x 设计失败；4-8x 需调查。

#### Phase 2 最小验证集

建议 Phase 2 包含：field/rfield/wfield + FieldRef/ExprRef + Bytes(expr) +
Context 恢复 + default + Tell + Computed。

4 个 benchmark 场景：
1. `Bytes(count)` — 简单字段引用
2. `Bytes(count + flag)` — 算术表达式
3. `Tell + Computed` — 流位置与计算字段
4. 三种 mode 混合（Const/field/wfield/default）

#### 需 PM 注意的事项

1. **ContextParam 命名**：建议确认 `ContextParam("name")` 作为跨层引用的 API 名称
2. **Rebuild 映射**：Phase 2 不实现 Rebuild，Phase 3 单独设计 RebuildNode
3. **RO + Bytes(expr) 限制**：编译期拒绝 RO 字段使用 Bytes(expr)（逻辑矛盾），
   详见 §5.6
4. **build 方向小结构**：N=3 时 build 加速比约 7.2x，略低于 8x 目标，
   但 parse 方向达标（9.1x）。需确认是否可接受

- **编译期错误信息**：拼写错误、前向引用、不支持运算符的错误信息格式清晰。✅

**必须修改的问题 [MUST-FIX-1]**：

**WO 字段在 parse 方向与 dict 复用优化存在逻辑矛盾**。

设计在两个地方做出了相互冲突的声明：

1. §5.5.2："有表达式时，StructNode.parse 复用 ctx 的 PyDict 作为 instance dict"
   - 代码：`let dict = ctx.fields().expect(...).clone_ref(py)` → dict 和 ctx.fields 指向**同一个底层 PyDict 对象**

2. §5.3：WO 字段 parse 时"不存入 dict（不成为实例属性），但仍需写入 context（供后续表达式引用）"
   - 代码：WO 分支调用 `ctx.set_field_interned(field.name.py_name(), &value.bind(py))?` → 对 ctx.fields（= 同一个 dict）做 set_item

**矛盾**：如果 dict = ctx.fields（同一 PyDict），那么：
- WO 字段通过 `ctx.set_field_interned` 写入 ctx.fields = 写入 dict
- force_setattr(dict) 后，WO 字段成为实例属性
- 这与"WO 不存入实例"的核心语义（§2.1 定义）直接矛盾

**影响**：WO 字段（padding/reserved）会错误地出现在 parse 返回的实例中，违反 API 契约。

**建议修改方向**（ARCH 选择其一）：
- **方案 A（推荐）**：WO 字段**不写入 context**。如果任何表达式引用了 WO 字段，编译期报 CompilationError。理由：WO 字段是 padding/reserved，被表达式引用的场景极少。这同时保持 dict 复用优化和 WO 语义正确性。
- **方案 B**：parse 结束后、force_setattr 前，从 dict 中 pop 所有 WO 字段。代价：每 WO 字段一次 PyDict DelItem（~10-15ns）。
- **方案 C**：parse 方向不复用 dict（回退到 Phase 1 的独立 dict 创建）。代价：PyDict::new 80-150ns 固定开销。

**必须修改的问题 [MUST-FIX-2]**（同 D4）：Python 侧描述符扩展设计缺失。

**需 PM 确认项 [CONFIRM-2]**：

**Rebuild 场景（长度字段在前、数据字段在后、长度=len(数据)）在 Phase 2 无法实现**。

§3.4.2 的前向引用限制（编译期统一拒绝 `getint idx >= current_field_index`）使得经典的 Rebuild 模式不可用：
```python
# 这在 Phase 2 无法工作（data 在 count 之后，表达式引用了后序字段）
count: int = rfield(Computed(len(data)))  # 前向引用 → CompilationError
data: bytes = field(Bytes(count))
```

设计在 §10.2 标注了 Phase 3 处理 RebuildNode，但这个限制影响实际可用性。需 PM 确认：
1. Phase 2 用户是否需要 Rebuild 场景？
2. 如果需要，是否在 §1.2 范围或 §11 边界条件中明确标注为"Phase 2 已知限制"？

**完备性遗漏补充**：
- §11.3 缺少"WO 字段被表达式引用"的边界条件（无论采用 MUST-FIX-1 的哪个方案）
- §11.3 缺少"嵌套 Struct 内的表达式引用"场景（内层 Struct 的表达式只能引用内层前序字段，不能跨层引用——跨层用 context= 参数）

### 特别关注点分析结论

#### 关注点 1：FieldRef 的 Python 类型系统实现 — **可行，但有设计缺口**

`count: int = field(Int8ub)` 中 `field(Int8ub)` 返回 `_FieldDescriptor`。类体执行时 `count` 绑定到这个对象。`Bytes(count)` 中 `count` 取的是 `_FieldDescriptor` 对象（不是 int 值）。这一机制在 Python 类创建机制中是可行的。✅

但当前 Phase 1 的 `BytesDescriptor` `#[new] fn new(length: usize)` 只接受 usize。`Bytes(count)` 传入 `_FieldDescriptor` 会在 Python 侧报 TypeError。**必须扩展 Bytes() 的 Python 侧构造**（见 MUST-FIX-2）。

类型系统自洽性：`_FieldDescriptor` 通过 `__class_getitem__` 支持 `FieldRef[int]` 语法（T 被忽略）。算术重载返回 `_ExprRef`。`_ExprRef` 也支持 `__class_getitem__` 和继续运算。无循环依赖。✅

#### 关注点 2：后序字段引用限制与 Rebuild — **已知限制，需 PM 确认**

前向引用限制（§3.4.2）在编译期统一拒绝引用后序字段。这使得 Rebuild 的经典模式（length 在前、data 在后、length=len(data)）在 Phase 2 不可用。

设计在 §10.2 明确 Phase 3 设计 RebuildNode。这是合理的设计分期，但：
- 前向引用检查**不区分 parse/build 方向**（统一在编译期拒绝）
- build 方向理论上可以引用后续字段（因为 build 时所有字段值已在实例中）
- 但统一拒绝简化了设计，代价是 Rebuild 场景需特殊节点处理

**结论**：这是设计权衡而非设计缺陷。需 PM 确认 Phase 2 不支持 Rebuild 是否可接受。

#### 关注点 3：compute_ro_value 求值顺序 — **正确**

build 方向按字段声明顺序逐个处理。每个字段处理完后值写入 context。后续字段的表达式（包括 Computed）从 context 取已写入的前序字段值。

追踪 `start=rfield(Tell()), header=field(Bytes(4)), end=rfield(Tell()), actual=rfield(Computed(end-start))`：
1. start：stream.tell()=0 → context[start]=0
2. header：写 4 字节 → context[header]=...
3. end：stream.tell()=4 → context[end]=4
4. actual：eval_expr([GetInt(end), GetInt(start), Sub]) → 4-0=4 ✅

求值顺序由字段声明顺序保证，前向引用限制确保表达式只引用已处理的前序字段。**设计正确**。✅

#### 关注点 4：WO 字段 parse 行为 — **设计矛盾，必须修改**

如上文 MUST-FIX-1 所述，WO 字段 parse 时"不存入 dict 但写 context"的声明在 dict 复用（dict = ctx.fields 同一对象）的前提下是**逻辑不可能**的。

这是**必须在开发前解决的设计级逻辑矛盾**，不是实现细节。不解决会导致 DEV 在实现时发现语义与性能优化冲突，需要回退至设计阶段重新决策。

#### SF-1 修复：FloorDiv/Mod 负数取整方向

**问题**：`wrapping_div`/`wrapping_rem`（向零取整）与 Python `//`/`%`（向负无穷取整）在负数操作数时结果不一致。

**实现方案**（偏离任务指示，详见下方设计质疑）：

添加了两个私有辅助函数 `floor_div` 和 `floor_rem`，使用 `wrapping_*` 算术实现真正的 Python floor division/modulo 语义：

- `floor_div(a, b)`：先取 truncating 商/余数，若余数非零且余数与除数符号不同，则商减 1
- `floor_rem(a, b)`：先取 truncating 余数，若余数非零且余数与除数符号不同，则余数加除数

验证（与 Python 逐一对照）：
| 表达式 | Python 结果 | floor_div/floor_rem 结果 |
|--------|------------|-------------------------|
| `-7 // 2` | -4 | -4 ✓ |
| `-7 % 2` | 1 | 1 ✓ |
| `7 // -2` | -4 | -4 ✓ |
| `7 % -2` | -1 | -1 ✓ |
| `-7 // -1` | 7 | 7 ✓ |
| `i64::MIN / -1` | (overflow, 任意精度) | i64::MIN (wrapping) ✓ |
| `i64::MIN % -1` | 0 | 0 ✓ |

**[设计质疑] 偏离任务指示**：任务指示使用 `i64::div_euclid`/`i64::rem_euclid`，但实测发现
`div_euclid`/`rem_euclid`（欧几里得除法：余数恒非负）与 Python floor division（余数符号同除数）
**在负数除数时不一致**。例如 `7 // -2`：Python = -4，`div_euclid(7, -2)` = -3。
`rem_euclid(7, -2)` = 1（非负），但 Python `7 % -2` = -1（符号同除数）。
因此改用显式 floor division 公式（`wrapping_*` 实现），数学上精确匹配 Python 语义，且永不 panic。

错误信息包含越界索引值和 names 列表实际长度。
