### S-PERF 性能分析

**优化后实测数据**（NUMBER=100000, REPEAT=5, release build fat LTO）：

| 场景 | 方向 | construct-rs (ns) | Python (ns) | 加速比 | 判定 |
|------|------|------------------|-------------|--------|------|
| E1 (N=2,K=1) | parse | 382 | 2717 | **7.11x** | ⚠️ |
| E1 (N=2,K=1) | build | 276 | 2634 | **9.54x** | ✅ |
| E2 (N=3,K=1) | parse | 423 | 3604 | **8.51x** | ✅ |
| E2 (N=3,K=1) | build | 312 | 3453 | **11.07x** | ✅ |
| E3 (N=6,K=2) | parse | 573 | 4721 | **8.24x** | ✅ |
| E3 (N=6,K=2) | build | 494 | 4273 | **8.65x** | ✅ |

**E1 parse 7.11x 未达 8x 分析**：

表达式系统优化后额外开销仅 ~10ns（一次 `PyDict_GetItem` + `PyLong_AsLongLong`），与 Phase 1 的 `PyDict_SetItem` 同量级。E1 (N=2) 的 382ns 中：
- 减去表达式开销 ~10ns → ~372ns
- Phase 1 B1 (N=3) 为 406ns，减去一个字段 ~33ns → ~373ns
- **两者几乎一致**，证明表达式系统已无额外开销

E1 未达 8x 是小 struct 固有特征（PyDict 创建 + create_class + force_setattr 等固定开销 ~200ns 在 N=2 时占比高），与表达式系统无关。Phase 1 B1 (N=3 无表达式) 同样仅 7.6x。N≥3 的场景 (E2/E3) 均达 8x。

**性能优化历史**：
- 初始实现：E1-E3 parse 5.6-6.2x（VM 栈堆分配 + to_str() UTF-8 校验 + 临时 str 创建 + field_names 每次 clone）
- 四处优化后：E1-E3 parse 7.1-8.5x（VM 栈改栈分配 + PyDict_GetItem C API + field_names 零拷贝引用）
- 净提升：每 parse 节省 124-367ns（24-42%）
