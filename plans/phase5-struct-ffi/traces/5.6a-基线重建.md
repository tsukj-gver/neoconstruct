## 二、测量方法

### 2.1 Controlled A/B Test 协议（L-09 对策）

- **A 组**：Python construct 2.10.70 baseline（`crs_venv_py_new` venv）
- **B 组**：当前 construct-rs 实现（`crs_venv_new` venv，HEAD 版本）
- **同会话交替**：每场景内 A→B→A→B→A→B 共 3 轮（每轮 A 和 B 紧邻测量，<3s 间隔）
- **轮间 sleep**：20 秒（防 CPU 热节流）
- **子进程隔离**：A 和 B 在独立子进程跑（同名 `construct` 包冲突，必须隔离）
- **S-PERF 口径**：`min(repeat=5) × number=100000`（performance-gate SKILL Checkpoint 2）
- **统计**：3 轮 speedup 样本 → mean ± 样本标准差（n-1 分母）

### 5.1 对比表

| 场景 | Phase 1（CSV，跨时段） | 5.6a（同会话） | B(crs) Δ | speedup Δ |
|------|----------------------|--------------|----------|-----------|
| B1-modbus | rs=386ns, pc=3123ns, 8.09x | rs=251ns, pc=2923ns, 11.64x | **-135ns** | **+3.55x** |
| B1-int3 | （无 CSV 数据，micro-bench 265ns） | rs=241ns, pc=2926ns, 12.12x | -24ns vs micro-bench | — |

| B4-int100 | rs=3656ns, pc=44097ns, 12.06x | rs=3016ns, pc=40103ns, 13.30x | **-640ns** | **+1.24x** |

### 5.2 差异归因分析

**B(crs) 端（construct-rs）**：所有场景 B 端 ns 都显著降低（-135 ~ -640ns）
- **真实代码改进主导**：Phase 1 → 当前，construct-rs 经历了 Phase 2.5（Context-Vec 优化）+ Phase 3（BitStream）+ Phase 4（Array 系列 + per-iter 优化 + 错误路径 O1-O4）+ crate 整体 inlining 副作用
- **每字段边际成本下降**：B1（3 字段）降 135ns ≈ 45ns/field；B4（100 字段）降 640ns ≈ 6.4ns/field——大字段数场景每字段改进较小（固定项占比下降），符合"FFI 入口开销稀释"模型

**A(pc) 端（Python construct 2.10.70）**：所有场景 A 端也降低（-180 ~ -4000ns）
- **L-09 跨时段环境漂移**：Phase 1 测量于早期 Python 3.14 版本/不同 venv 状态，当前 Python 3.14.2 baseline 略快
- **B1-modbus A 端降 200ns**（3123→2923）：纯环境漂移（Python construct 代码未变）
- **大字段场景 A 端降更多**（B4 降 4000ns）：Python 端 per-field 开销也随环境略降

**speedup 提升分解**（以 B1-modbus 为例，+3.55x）：
- B 端改进贡献：3123/251 - 3123/386 = 12.43 - 8.09 = **+4.34x**（B 端真实改进使 speedup 提升 4.34x）
- A 端漂移贡献：2923/251 - 3123/251 = -0.79x（A 端变快使 speedup 降低 0.79x）
- 净提升：+4.34 - 0.79 = **+3.55x**（与实测一致）

**关键结论**：B1 speedup 提升的主因是 **construct-rs 真实代码改进**（Phase 2.5-4 累积），次因是 Python 端 baseline 漂移（反向，部分抵消）。L-09 跨时段对比归因失效的风险已被同会话 Controlled A/B Test 排除——3 轮 stddev <0.15x（除 B2/B4 在 0.30x 边缘），数据稳定可信。

### 5.3 REV P2-1 的两个数据源冲突解决

| 数据源 | 原值 | 5.6a 复测 | 解释 |
|--------|------|----------|------|
| perf-scenarios.csv 行 2 | rs=386ns, 8.09x | rs=251ns（B1-modbus 同口径） | CSV 是 Phase 1 时期值，B 端真实改进 135ns + A 端漂移 -200ns 共同拉高 speedup 至 11.64x |

**REV P2-1 预言成真**：B1 当前确实已 ≥10x（11.64x modbus / 12.12x int3），且 stddev 极小（0.07x / 0.13x），不在阈值边缘。Phase 5 的硬目标"B1 ≥10x"在 5.2 实施前已经达成。

## 八、PM 决策建议

基于 5.6a 基线重建结果（B1 已 ≥10x + 全场景 ≥10x），向 PM 提供以下决策建议：

### 8.1 主决策：Phase 5 范围缩小

**建议**：Phase 5 范围从"5.2 + 5.3 + 5.4 + 5.5 + 5.6b（全量 FFI 入口优化）"缩小为"零优化收尾 + 5.6b 验证 + 可选锦上添花"。

**理由**：
1. **硬目标已达成**：Phase 5 总纲 §S-PERF 要求的 B1-B4 ≥10x 在 5.2 实施前已经达成
2. **StopIf S01/S03 不再需要豁免**：用户决策事项 B 的预案（"即使 <10x 也视为达标"）不再需要触发
3. **L-02 教训**：性能预测必须基于实测。当前实测 B1=11.64x 已达标，5.2-5.4 的边际收益（设计 §7.2 估算 B1 → ~10.2x 是基于旧基线 386ns，新基线下 5.2-5.4 的边际收益需重新评估）可能不达成本
4. **REV v2 P2-1 预言验证**：REV 明确指出"若当前基线已 <312ns（即 >10x），PM 可考虑重排优先级"——5.6a 实测 B1=251ns < 312ns，触发此条件
