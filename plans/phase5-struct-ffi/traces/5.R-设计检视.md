### 2.2 L-09 教训执行：良好

### 2.3 L-02 教训违反：P0-2（候选 C 收益预估缺乏 profiling 支撑）

**问题 P0-2**：候选 C 的 fast-path 收益预估（6-15ns）缺乏 profiling 数据支撑，违反 L-02 教训"瓶颈识别有量化数据支撑"。

**具体分析**：

设计文档 §4.1 / §4.3 / §7.5 声称候选 C 的优化点是"消除 Vec 迭代器（边界检查 + 指针递增）+ match field.mode 分支预测"，预估"每字段省 2-5ns，3 字段共省 6-15ns"。

但是：

1. **Rust 编译器对 `for field in &self.fields` 的优化已经很好**：迭代器会被编译为指针递增，边界检查在 `iter()` 模式下通常被消除（Rust 编译器能证明索引在范围内）。设计文档未提供 `cargo asm` 或 `perf record` 数据证明当前实现存在可优化的边界检查。

2. **候选 C 的 fast-path 实现本质**（§4.3 步骤 3 伪代码）：`for i in 0..self.fields.len() { self.fields[i] }` 与通用路径的 `for field in &self.fields` **生成的机器码几乎一致**（两者都会被 Rust 编译器优化为指针递增）。设计文档未说明 fast-path 与通用路径的**实际机器码差异**。

3. **`match field.mode` 分支预测**：3 字段场景下，CPU 分支预测器命中率极高（历史模式简单），实际分支预测惩罚可能 <1ns/字段，而非设计预估的 1-3ns/字段。

4. **唯一明确的优化**是 `#[inline]` 标注（§4.3），但 `#[inline]` 仅影响跨函数内联，而 `parse_small` 本身已是 `StructNode` 的方法，调用链 `StructNode.parse -> parse_small` 的内联由编译器自动决定，`#[inline]` 提示的边际收益不确定。

**L-02 违反判定**：候选 C 的收益预估基于"消除迭代器 + 分支开销"的**理论推算**，未提供 profiling 数据证明当前实现存在这些开销。这符合 experiences.md §L-02 模式描述："设计阶段用'预计 Nx 加速'等理论推算代替实测数据"。

**影响评估**：
- 若候选 C 实际收益 <3ns（而非预估的 6-15ns），B1 加速比上界从 10.6x 降至 ~10.3x，中位估算从 9.88x 降至 ~9.7x
- B1 ≥10x 达标概率进一步降低（原本已临界）

**修改方向**：
- ARCH 应补充 profiling 数据（如 `cargo asm --release --rust` 查看 `StructNode::parse` 生成的汇编，确认是否存在可优化的边界检查 / 分支；或用 `perf record` 测量 `for field in &self.fields` 循环的实际 CPU 周期）
- 或者，承认候选 C 的收益预估是**理论估算的上界**，并相应调整 B1 达标概率评估（§7.2 应增加"候选 C 收益为 0-15ns"的下界场景）

### 2.4 L-02 灰色地带：候选 A 收益预估（P2-1，标注不驳回）

**观察**：候选 A 的"Python 入口 60-90ns"基于 bench_asymmetry C 值（41-49ns，实测）+ 属性查找扩充估算（20-30ns，估算）。属性查找贡献是**未直接测量的估算**，使候选 A 的净节省预估（30-50ns）有 ~20ns 的不确定性。

**判定**：这是 L-02 的**灰色地带**——C 值本身是实测的，属性查找估算是合理的工程推断。设计文档 §7.2 已通过"保守估算"（实际叠加 45-90ns vs 理论 51-100ns）部分缓解。**不构成驳回理由**，但建议 ARCH 在 §7.1 标注"属性查找贡献为估算值，实际收益可能在 20-50ns 区间"。

### 3.2 集成方案交互点：P1-4（候选 A+B 挂载方式未具体分析）

**问题 P1-4**：设计文档 §5.2 交互点 1 描述：
> 候选 A 挂载 `schema._parse_raw`（pyo3 方法）到 `cls.parse`
> 候选 B 实施后，候选 A 可改为挂载 `parse_raw_fast`（raw C 函数）到 `cls.parse`

但是：
1. raw C 函数的注册方式（类型方法 vs 模块级函数）未确定（见 P0-1）
2. 若 raw C 函数是**模块级函数**，则挂载方式需 `functools.partial(parse_raw_fast, schema)`，而 `functools.partial` 的调用开销（~10-15ns）会**抵消候选 B 的部分收益**（候选 B 预估节省 15-35ns，partial 开销 10-15ns，净节省仅 5-20ns）
3. 若 raw C 函数是**类型方法**（CompiledSchema._parse_raw_fast），则挂载方式与候选 A 一致（`cls.parse = schema._parse_raw_fast`），但 ABI3 兼容性存疑（见 P0-1）

**影响**：候选 A+B 的集成收益预估（§7.2 "A+B 40-75ns"）可能因 partial 开销而高估。

**修改方向**：ARCH 应在 §5.2 明确 raw C 函数的注册方式选择，并分析对应的挂载开销。

## 四、可行性检查（问题）

### 4.1 候选 B ABI3 兼容性：P0-1（关键可行性未验证）

**问题 P0-1**：候选 B 的核心技术路径（raw C 函数注册到 CompiledSchema 类型方法表）在 ABI3（Py_LIMITED_API）下的可行性**未验证**，且设计文档承认这一点但未提供验证方案或回退详细设计。

**具体分析**：

设计文档 §3.2.3 明确承认：
> 实施难点：raw C 函数作为类型方法（而非模块级函数）注册，需修改 CompiledSchema 的 PyTypeObject 方法表。ABI3（Py_LIMITED_API）下 PyTypeObject 为 opaque，需用 PyType_Spec + PyType_FromSpec 重新定义类型，或用 PyObject_SetAttrString 动态挂载方法。

设计文档 §12.2 第 2 项诚实声明：
> 候选 B ABI3 兼容性未验证：raw C 函数注册到类型方法表在 ABI3 下是否可行，需 DEV 实施时首先验证。

但是：

1. **`PyType_FromSpec` 重新定义类型与 pyo3 `#[pyclass]` 注册冲突**：CompiledSchema 已由 pyo3 `#[pyclass]` 宏注册为 PyTypeObject。用 `PyType_FromSpec` 重新定义会创建**新的类型对象**，而非修改现有 CompiledSchema 类型。设计文档未提供解决此冲突的方案。

2. **`PyObject_SetAttrString` 动态挂载方法**：将 PyCFunction 包装后 setattr 到类型对象。但是 PyCFunction（METH_VARARGS）作为类型属性时，Python 描述符协议会将其视为**未绑定方法**（unbound method），调用 `schema._parse_raw_fast(data)` 时 self 不会自动绑定——这与候选 A 的 `cls.parse = schema._parse_raw`（已绑定 self）语义不一致。设计文档未分析此差异。

3. **B-conservative 详细设计缺失**：§3.2.1 提到"方案 B-conservative（保留 #[pymethods] 入口，内部用 raw C API）"作为回退，但仅一句话描述，无接口签名 / 收益重新评估 / 实施步骤。若 B-aggressive 因 ABI3 不可行而回退，DEV 没有可执行的设计依据。

4. **ABI3 是项目硬约束**：pyo3 默认在 Python 3.7+ 使用 `Py_LIMITED_API`（ABI3）以支持多版本 Python wheel。禁用 ABI3（`PYO3_USE_ABI3_FORWARD_COMPATIBILITY=0`）会破坏项目的 Python 版本兼容性（设计文档 §8.3 BC-B3 已正确识别此约束）。

**可行性违反判定**：reviewer.md §可行性检查明确要求"无已知的技术障碍"。候选 B 的 ABI3 兼容性是**已知的技术障碍**，设计未提供解决方案，仅说"DEV 实施时验证"。这违反可行性检查要求。

**影响评估**：
- 若 ABI3 不可行，候选 B 可能完全放弃（B1 加速比上界从 10.6x 降至 ~9.5x，不达标）
- 或降级为 B-conservative（收益从 15-35ns 降至 5-10ns，B1 加速比上界 ~9.8x，临界）

**修改方向**：
- ARCH 应补充 **ABI3 验证 spike 计划**：具体的 minimal 验证步骤（如"实施第一步是写一个 20 行的 spike：定义一个 raw C 函数，尝试注册到现有 pyclass 类型的方法表，验证 ABI3 下 cargo build + maturin develop + 简单调用是否成功"）
- 或者，提供 **B-conservative 详细设计**（接口签名 / 收益重新评估 / 实施步骤 / 与候选 A 的集成方式）
- 在 ABI3 验证完成前，候选 B 的收益预估应在 §7.1 / §7.2 标注"取决于 ABI3 验证结果，若不可行则收益为 0 或降至 5-10ns"

### 4.2 候选 A pyo3 bound method 行为：P1-3（核心假设未验证）

**问题 P1-3**：候选 A 的核心假设"`cls.parse = schema._parse_raw` 等价于 `schema._parse_raw(data)`"未经验证。

**具体分析**：

设计文档 §2.3.2 / §2.4.1 声称：
- `schema._parse_raw` 是 pyo3 `#[pymethods]` 生成的实例方法
- 访问 `schema._parse_raw` 返回 bound method（self 已绑定为 schema）
- `cls.parse = schema._parse_raw` 后，`MyClass.parse(data)` 等价于 `schema._parse_raw(data)`

但是：

1. **pyo3 bound method 作为类属性的行为未验证**：pyo3 生成的 PyCFunction 在 Python 端是 `PyCFunctionObject`（非 Python function）。将其作为类属性存储时，Python 描述符协议的行为可能与普通 Python function 不同。普通 Python function 作为类属性会触发描述符 `__get__` 绑定 self；pyo3 bound method 已绑定 self，其 `__get__` 行为取决于 pyo3 实现。

2. **实例调用 vs 类调用**：
   - `MyClass.parse(data)`：LOAD_ATTR 命中类属性 -> 返回 bound method -> CALL(data) -> 应该等价 `schema._parse_raw(data)`（理论上）
   - `instance.parse(data)`：LOAD_ATTR 命中类属性（经 MRO）-> 返回 bound method -> CALL(data) -> 应该等价 `schema._parse_raw(data)`（self 不会再次绑定到 instance）（理论上）

   但这是**理论推断**，未实际验证。pyo3 的 PyCFunction 在某些版本可能有不同的描述符行为。

3. **设计文档 §2.6 BC-A1 已正确识别 build 路径的 self 冲突**，但**未验证 parse 路径真的没有 self 冲突**。设计文档仅说"parse 路径：cls.parse(data) 等价 schema._parse_raw(data)，self 自动绑定为 schema [OK]"——这个 OK 是断言，不是验证。

**可行性风险**：若 pyo3 bound method 作为类属性时行为与设计假设不符（如 self 被错误绑定），候选 A 的 parse 路径会崩溃或行为异常。

**修改方向**：
- ARCH 应在 §2.3.2 或 §2.6 补充 **pyo3 bound method 行为验证方案**（如"DEV 实施第一步是写一个 5 行 spike：`cls.parse = schema._parse_raw; assert MyClass.parse(b'...') 返回正确实例`"）
- 或者，提供**替代方案**（如用 pyo3 pyclass 实现 `ParseDescriptor`，在 `__get__` 中返回 bound method，避免依赖 pyo3 bound method 的类属性行为）

### 4.3 候选 C 可行性：高

候选 C 是纯 Rust 内部优化，无 ABI3 / unsafe 风险。StructNode 新增 `is_small_struct` 字段 + parse/build 入口分支，技术成熟，无已知障碍。

### 5.1 §0 原则对照表：完整（L-01 教训硬要求满足）

设计文档 §6 对照表覆盖 AGENTS.md §0 全部 8 条原则，三候选逐条说明。候选 B 的两处边缘（§0 第 4 / 第 7 条）标注为"⚠️ 边缘"并附理由（ADR-019 先例 + 语义等价）。

- 候选 B：两处边缘，符合原则精神（pyo3::ffi 仍是 pyo3 crate 的一部分，非"独立的 Python 绑定层"；错误转换语义等价）
- 候选 C：零 §0 风险

### 5.2 文档内部矛盾：P1-6（§2.3.2 与 §2.6 BC-A1 冲突）

**问题 P1-6**：设计文档 §2.3.2 的 `_install_fast_call_bindings` 函数同时挂载 `cls.parse` 和 `cls.build`：
```python
cls.parse = schema._parse_raw       # bound method，self 绑定为 schema
cls.build = schema._build_raw       # bound method，self 绑定为 schema
```

但 §2.6 BC-A1 的设计决策明确说：
> build 路径保守保留 StructMixin.build（当前 build 11.71x 已远超 10x，无需优化）

这两处**直接矛盾**：§2.3.2 的代码会触发 BC-A1 描述的 build 路径 self 冲突崩溃（`my_instance.build()` 调用时，self 错绑为 my_instance 而非 schema），但 §2.6 决策又说 build 路径保留 StructMixin.build。

**影响**：DEV 实施时会产生困惑——到底挂不挂载 `cls.build`？若按 §2.3.2 挂载，build 崩溃；若按 §2.6 不挂载，则 §2.3.2 的代码是错误的。

**修改方向**：ARCH 应修正 §2.3.2 的 `_install_fast_call_bindings`，仅挂载 `cls.parse`，明确注释 `cls.build` 保留继承的 `StructMixin.build`。

### 5.3 候选 C fast-path 核心实现缺失：P1-5（完备性）

**问题 P1-5**：候选 C 的 fast-path 核心逻辑（字段处理）是完全注释的伪代码，具体实现方式未确定。

**具体分析**：

设计文档 §4.3 `parse_small` 方法的步骤 3（字段处理）是**完全注释掉的伪代码**。候选 C 的**核心优化逻辑**（如何"手动展开"以消除迭代器/分支开销）没有具体设计，仅给出三种可能方式（macro / 显式展开 / 循环+inline）让 DEV 选择。

**问题**：
1. **macro 展开** vs **显式展开** vs **循环+inline** 三种方式的收益差异很大：
   - macro / 显式展开：编译期完全消除循环，但需处理 1/2/3 三种字段数的分支
   - 循环+inline：与通用路径几乎无差异（见 P0-2 分析），收益可能 <3ns
2. 设计文档未推荐任何一种方式，也未分析各方式的收益/复杂度权衡
3. 这是 fast-path 的**核心实现**，不是"实施细节"——它直接决定候选 C 是否能达到预估收益（6-15ns）

**完备性违反判定**：reviewer.md §完备性检查要求"覆盖了所有边界条件"和"错误路径设计完整"。候选 C 的 fast-path 核心实现缺失，使完备性检查无法确认 fast-path 是否正确处理所有边界（如 StopField 捕获 / push_path_segment / WO 字段 drop）。

**修改方向**：ARCH 应在 §4.3 提供**推荐的 fast-path 实现方式**（至少伪代码级别，而非完全注释），并分析该方式的预期收益。

### 5.4 边界条件覆盖：基本完整，2 项轻微遗漏（P2）

设计文档 §8 列出 13 个全局边界条件 + 候选专属边界（BC-A1~A4, BC-B1~B3, BC-C1~C3），覆盖大部分场景。

**遗漏 1（P2-2）**：嵌套 Struct + fast binding 的边界条件未明确。§8.1 提及"嵌套 Struct"但仅一句话描述，未说明：
- 外层 Struct 的 fast binding 是否影响内层 Struct 的 parse 性能（分析：不影响，因为 StructRefNode 直接调 `inner_schema._parse_raw`，不经过 `Inner.parse`）
- 内层 Struct 的 fast binding 挂载时序（分析：Inner.__init_subclass__ 独立编译 + 挂载）

**遗漏 2（P2-3）**：`@dataclass` 时序验证未明确。`_install_fast_call_bindings` 在 `__init_subclass__` 中调用，而 `__init_subclass__` 在 `@dataclass` **之前**执行。设计未验证 `@dataclass` 不会覆盖 `cls.parse` / `cls.build`（分析：`@dataclass` 仅生成 `__init__`/`__repr__` 等，不动 parse/build，安全）。

这两项是**轻微遗漏**，不影响正确性（经源码分析确认安全），但建议 ARCH 在 §8 补充说明。
