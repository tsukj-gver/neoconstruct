## DEV 3 项设计质疑评估

### [设计质疑] 1：SwitchKey / IfThenElseNode 删除 Clone derive

**DEV 主张**：设计 §2.2/§3.3 标注 `#[derive(Debug, Clone)]`，但 Node enum 整体未实现 Clone。删除 Clone derive。

**VET 评估**：✅ **接受**

**理由**：
1. **代码库约定一致性**：现有 Node 变体中 `BitwiseNode` / `TransformNode` / `StructNode` 等持有 `Box<Node>` 的节点均未 derive Clone。DEV 删除 Clone 与既有约定一致。
2. **无功能影响**：grep `\.clone()` 在 src/ 中无对 IfThenElseNode/SwitchNode/SelectNode/FocusedSeqNode 的 clone 调用（这些节点仅在 compile.rs 构造一次，存入 Node enum 后只读访问）。
3. **技术准确性**：DEV 称 "FieldName 未实现 Clone" 实际上 FieldName 字段（`Py<PyString>` + `String`）都可 Clone，但 Node enum 含 `StructRefNode { cls: Py<PyType> }` 等——而 `Py<T>` 是 Clone（incref）。所以严格说 Node 可以实现 Clone，但**当前代码库约定就是不实现**，DEV 选择与约定一致是正确的。
4. **未来如需 Clone**：应统一为 Node 全变体实现 Clone，而非局部 derive。

**严重度**：Trivial（不影响功能、不影响 API、不影响性能）。

### [设计质疑] 2：Switch FieldRef 路径在 Python 用户面不可达

**DEV 主张**：设计 §3.2 规划 FieldRef（路线 B）支持 `this.tag`（str/bytes 字段），但 Python 侧无法在编译期区分 int 字段 vs str/bytes 字段。实际实现：所有 `_FieldDescriptor`/`_ExprRef` keyfunc 走 IntExpr 路径（`_expr_params = {"key": keyfunc}`）；FieldRef 仅通过 Rust API 直接构造（单元测试 SW-5/SW-6/SW-12 验证）。

**VET 评估**：⚠️ **接受，但记为观察项 O-1**

**理由**：
1. **真实差异**：这是与设计 §3.2 表格的实质偏离。设计 §3.2 明确列出 FieldRef 路径对应"this.tag（单字段引用，tag 是 str/bytes 字段）"。但 Python 用户面无法触发此路径。
2. **DEV 文档化透明**：在 7.1-DEV实施.md §[设计质疑] 2 + switch.rs L48-50 docstring + _conditional.py docstring 中均明确记录此限制。
3. **功能正确性不受影响**：
   - int key 用户：完整 parity（路线 A 工作）
   - str/bytes key 用户：会得到清晰错误（`eval_expr_int` 中 `PyLong_AsLongLong` 失败 → ExprType 错误），非静默错误
   - FieldRef 路径在 Rust API 层完整实现并测试通过
4. **PM 决策 1 措辞**：原决策为"接受 ARCH 推荐 A+B"——A（int）+ B（str/bytes）。B 路径的 Python 用户面缺失确实降低了决策 1 的覆盖度，但 PM 决策文本未承诺"Python 用户面立即可达 B 路径"。
5. **未来解锁条件**：需在描述符系统引入字段类型元数据（当前 _FieldDescriptor 不携带类型信息）。属于 Phase 8+ 范围。

**严重度**：Minor（功能范围小幅缩减，已文档化，无静默错误）。

**观察项 O-1**：建议 PM 在 Phase 8+ 规划时考虑为描述符系统引入字段类型元数据，以解锁 Switch FieldRef 路径从 Python 用户面的可达性。当前不阻塞 7.1 验收。

### [设计质疑] 3：FocusedSeq Python 用户面用 Renamed 包装器（非 `"/"`运算符）

**DEV 主张**：设计 §11.4 暗示 `"num"/Byte` 语法，但 construct-rs 描述符不共享基类，无法添加 `__rtruediv__`。实际实现：定义 `Renamed(name, subcon)` 类，用户用 `Renamed("num", Byte)` 显式构造。

**VET 评估**：✅ **接受**

**理由**：
1. **既有约定**：construct-rs 从 Phase 1 起就用 Descriptor 系统（不共享 Python construct 的 Construct 基类），所有用户面都通过 Descriptor 类。`"/"` 运算符是 Python construct 的特殊语法糖，不属于核心 API 契约。
2. **功能等价**：`Renamed("num", Byte)` 与 `"num" / Byte` 在 FocusedSeq 场景下功能完全等价（都是给 subcon 加名字）。
3. **parity 验证通过**：parity 测试 F1 用 `Renamed("num", Int8ub)` 与 Python `"num" / Int8ub` 对照，结果一致（27p 全 PASS）。
4. **DEV 文档化**：_conditional.py L260-285 Renamed docstring 明确说明此差异。
5. **未来扩展**：如需 `"/"` 语法，可统一为所有 Descriptor 添加 `__rtruediv__`（需重构描述符基类），属于未来 API 增强范围。

**严重度**：Trivial（语法糖差异，功能等价，parity 通过）。
