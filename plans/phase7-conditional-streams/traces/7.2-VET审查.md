## PM 要求的审查重点

### 1. BuildStream 向后兼容性（pos 字段引入后现有调用方零变更？）✅

**审查结论：完全向后兼容，现有调用方零变更。**

**核心不变量**：所有现有 build 调用方（StructNode/BitwiseNode/BytesNode/FormatFieldNode/PrefixedArrayNode/PascalString/NullTerminated/NullStripped 等）不调 seek，`pos == buf.len()` 始终成立。

**逐方法验证**：
- `write(data)`：pos == buf.len() 时，`end = pos + data.len() > buf.len()` → `resize(end, 0)` + `copy_from_slice`，等价于原 `extend_from_slice`。结果：buf 末尾追加，pos 推进到末尾。
- `tell()`：返回 pos。pos == buf.len() 时，与旧 `buf.len()` 返回值一致。
- `into_bytes()`：返回 buf（不变）。
- `write_bits`/`write_padding_bits`：bit API 内部 `buf.push`，与 pos 无关。DEV 偏离 2 在 push 后同步 `self.pos = self.buf.len()` 保持不变量（详见下文 §6）。

**回归测试验证**（DEV 报告 §向后兼容性回归）：
- StructNode build（write + tell）：✅ Phase 1-6 round-trip 全过
- BitwiseNode build（write_bits/write_padding_bits）：✅ Phase 3 parity 全过
- PrefixedArrayNode build：✅ Phase 4 parity 全过
- PascalString/NullTerminated/NullStripped build：✅ Phase 6.2 parity 全过
- cargo test --lib：✅ 1191 passed（含全部历史 Phase 测试）

**关键代码守卫**：
- 空 write 显式 no-op（stream.rs L570-572）：避免 pos > buf.len() 时被 resize 误扩展。
- bit API 入口 `debug_assert!(self.pos == self.buf.len())`（L720-725/L774-779）：debug build 捕获"先 seek 再 bit 写"契约违反。

### 2. Stream 扩展安全性（seek_whence + BuildStream.seek 零填充）✅

**ParseStream.seek_whence**：
- 现有 `seek(pos, path)`（whence=0 专用）保留不变，Phase 4 GreedyRange/Peek 调用方零影响（stream.rs L205-219）。
- 新方法 `seek_whence` 供 Pointer/Seek 使用，三分支完整。
- 重置 `bit_pos = 0`（与现有 seek 一致，S8 测试验证）。

**BuildStream.seek 零填充**：
- seek 仅移动 `pos`，**不扩展 buf**（零填充延迟到下次 write，避免无 write 的空 seek 浪费内存）。
- write 时 `end > buf.len()` → `resize(end, 0u8)`（Python BytesIO 行为，0x00 填充）。
- S10 测试验证：seek(10) + write(b"X")，buf.len()=3 → buf=[a,b,c,0,0,0,0,0,0,0,X]（len=11）。

### 3. PointerNode save/restore（Tell 模式 + 错误强制 seek 回）✅

**模式复用**：复用 PeekNode 已验证的 save/restore 模式（设计 §1.2 / §3.3）。
- parse：`fallback = stream.tell()` → `seek_whence(offset, whence)` → `subcon.parse` → `seek(fallback)` → 返回 result。
- build：对称（`seek(offset, whence)` → `subcon.build` → `seek(fallback, Start)`）。

**错误路径强制 seek 回**（关键）：
```rust
let result = self.subcon.parse(py, stream, ctx, path);
let seek_back = stream.seek(fallback, path);
seek_back?;  // seek 失败优先（破坏主流位置，比 subcon 错误更严重）
result
```
（pointer.rs L164-169）

- subcon.parse/build 失败时，**仍执行 seek_back**（result 是 `Err` 但不提前返回）。
- `seek_back?` 优先：若 seek_back 失败（极端，fallback 越界），即使 subcon 成功也报错；若 subcon 失败但 seek_back 成功，返回 subcon 错误（携带 subcon 的 path）。
- 对齐 Python `finally: stream_seek(fallback, 0)`（core.py Pointer._parse/_build）。

**P6 测试验证**：subcon EOF（Bytes(10) on 5 字节）→ seek 回 fallback 后返回 Stream Err（pointer.rs L394-416）。

### 6. bit API 同步 pos 的偏离（设计说"不感知"，实际"内部同步"——可接受？）✅ 可接受

**偏离描述**：
- 设计 §3.1.3 说 "bit API 不感知 pos"（bit 级 API 保持末尾追加语义）。
- 实际实现：bit API（write_bits/write_padding_bits/write_bits_slow）在每次 `buf.push` / `buf.resize` 后同步 `self.pos = self.buf.len()`（stream.rs L747/L791/L801/L813/L834）。

**偏离必要性论证**：
- 入口 `debug_assert!(self.pos == self.buf.len())` 守卫要求 bit API 调用时 pos == buf.len()（末尾追加模式）。
- 若不同步 pos：第一次 write_bits 批量 push 后 buf.len() 增长但 pos 不变（pos < buf.len()），第二次 write_bits 入口 debug_assert 失败（panic in debug）。
- 同步 pos 是**保持入口守卫不变量的必要修正**，否则连续 bit 写入（批量 + 慢路径混合，常见场景）会触发 debug_assert panic。

**实际语义对齐**：
- "bit API 不感知 pos" 的设计意图是"bit API 假设末尾追加模型，不与 seek 交互"。
- 实现通过"同步 pos 保持 pos == buf.len() 不变量"实现了该意图——bit API 仍只在末尾追加模式工作，仅"先 seek 再 bit 写"会触发入口 debug_assert（设计意图）。
- 设计文档描述不准确，但实现行为符合设计意图。DEV 在偏离说明 §2 中明确记录并解释了原因（7.2-DEV实施.md L80-84）。

**结论**：偏离可接受。建议设计文档在后续修订中将"bit API 不感知 pos"更正为"bit API 假设末尾追加模式（pos == buf.len()），通过同步 pos 保持该不变量"（minor 文档修正，非阻断）。
