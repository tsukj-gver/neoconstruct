**附录 A 审计表专项核查**（PM 关注点）：

附录 A 列出 8 个调用方，逐一推演 pos 字段引入后的行为：
- StructNode.build / BytesNode.build / PrefixedArrayNode.build：用 `write` + `tell`。新 write 在 pos==buf.len() 时退化为 extend_from_slice（end > buf.len() → resize + copy，pos 推进到 end == 新 buf.len()）。tell 返回 pos == buf.len()。**零行为变更**。
- BitwiseNode.build / FormatFieldNode.build（bit 域）：用 `write_bits`/`write_padding_bits`，操作 `self.buf.push`（末尾追加），**不感知 pos**。设计决策：bit API 入口加 `debug_assert!(self.pos == self.buf.len())` 守卫，将"Bitwise 域内 seek"定性为契约违反（debug 触发 panic / release 静默）。已文档化为已知限制（§3.1.3 + 附录 B + §9.3）。
- TellNode.build / PeekNode.build：no-op，无 stream 调用。零变更。

**结论**：除 bit API 加 debug_assert 守卫外，现有代码零修改。审计表完整且准确。

**Minor 提示**（不阻塞，DEV 实施时注意）：

1. **[完备性-1] PrefixedNode sizeof/parse 的 subcon 错误路径未加 push_path_segment**
   - 位置：§3.4 PrefixedNode parse（L716）+ sizeof（L757）
   - 现状：lengthfield 错误用 `push_path_segment("lengthfield")`，subcon 错误直接 `?`（无 path 段）
   - 评估：与 PointerNode parse（subcon 错误也无 path 段）+ PrefixedArray parse（inner 错误用 `push_path_index(i)` 因为是数组元素）一致。Prefixed 的 subcon 是"主内容"，其 path 段隐含为父字段名，沿用 lazy path（ADR-016）由 StructNode 重建。**属风格选择，非缺陷**。
   - 建议：DEV 实现时保持与 Pointer 一致即可（不加 push_path_segment）。

2. **[完备性-2] Prefixed includelength 减成负数：错误类型差异**
   - 位置：§3.4 PrefixedNode parse L700-708
   - 现状：design 返回 `ConstructError::Range`（"Prefixed length N shorter than lengthfield size M"）
   - Python 行为：`length -= self.lengthfield._sizeof(...)` 后 `stream_read(stream, negative_length, path)` 触发 `StreamError`（"stream read less than specified amount, expected -N, found 0"）
   - 评估：design 提前校验更友好（错误信息明确），但错误类型与 Python 不一致。PF-4 场景未明确指定错误类型。
   - 建议：DEV 实施时**保持 design 决策（Range 错误 + 明确信息）**，理由：(a) 比 Python 模糊的负数 stream_read 错误更清晰；(b) parity 测试用 `except (StreamError, RangeError, ConstructError)` 兜底即可；(c) 不影响成功路径。若 VET 在 Phase 7.3 parity 验证时发现用户代码精确 `except StreamError` 受影响，再调整。

3. **[可行性] BuildStream::new / with_capacity 构造器需更新**
   - 位置：§3.1.3 BuildStream 扩展（设计未显式展示新构造器）
   - 现状：设计展示 struct 定义加 `pos: usize` 字段，但 `new()` / `with_capacity()` 构造器实现未显式更新
   - 评估：DEV 实施时需在两个构造器中初始化 `pos: 0`（`new()` 走 `#[derive(Default)]` 自动处理；`with_capacity()` 需手工加 `pos: 0`）。属于实现细节，非设计缺陷。
   - 建议：DEV 实施时直接处理，无需 ARCH 补设计。
