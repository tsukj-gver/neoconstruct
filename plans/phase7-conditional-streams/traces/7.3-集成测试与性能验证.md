### 不达标根因分析（L-09 对照）

按 `harness/experiences.md §L-09`（跨时段性能对比消除法归因失效 / 边界场景）+ `performance-gate/SKILL.md Checkpoint 4` 分析：

#### 根因 1：parse 方向结构性边界（25 项，占不达标 86%）

**现象**：
- parse 方向 Rust 侧耗时 ~220-450ns（接近 L-09 边界场景阈值 <300ns 上限）
- build 方向 Rust 侧耗时 ~150-560ns（普遍高于 parse，但 Python baseline 也较高）
- parse 加速比普遍 7-10x，build 加速比普遍 11-19x

**根因**：parse 方向需要从字节构造 PyObject（PyLong/PyBytes/PyDict 等），涉及 GIL + 引用计数 + 类型分配开销；
build 方向是从 PyObject 读值写字节，相对简单。这与 Phase 1 B1 parse 7.63x → Phase 5.6a Controlled A/B Test 复测 11.64x
是同性质现象（parse 方向 Rust 侧固有开销 + 跨时段测量漂移）。

**证据**：
- Phase 1 B1 parse PM 验收 7.63x（plans/00-项目进度.md）→ Phase 5.6a 同会话 Controlled A/B Test 复测 11.64x（差异 +4.01x 来自测量环境漂移）
- 本 phase ITE1-parse 跨 3 次会话跑：9.18x / 7.74x / 7.73x（摆动 ±1.5x，符合 L-09 边界场景特征）

**判定**：边界场景 + 跨会话漂移。不自行优化（按 PM 任务书要求）。建议 PM 在 Phase 7 验收时
对 1-2 个典型 parse case 做 Controlled A/B Test 复测确认稳态（参考 Phase 5.6a 模式）。

#### 根因 2：FocusedSeq 完全达标（对比基准）

**现象**：FocusedSeq parse 10.89-12.49x / build 15.27-17.30x，全场景 ≥10x。

**根因**：Python construct FocusedSeq 实现较重（context nesting + finalret 字段覆盖语义），
baseline ~3500ns 比 IfThenElse/Switch/Select 的 ~2000ns 高 ~75%。Rust 侧开销 ~300ns
与同类节点持平，加速比因此拉高到 11-12x。

**判定**：FocusedSeq 的 Python baseline 偏重，自然达标。其他 Conditional 节点的 Python baseline
较轻（~2000ns），Rust 侧 ~250ns → 加速比落在 8x 边缘。

#### 根因 3：PF4-build 数据密集型边界（1 项）

**现象**：PF4-build = Prefixed(VarInt, GreedyRange(Int32ul)) build 8.19x，唯一一项 build <10x
（除 PF2-build 9.97x 边缘外）。

**根因**：GreedyRange(Int32ul) build 在 Python 端走 cycled PathSequence 优化路径，
baseline ~2925ns 比 Prefixed(Byte, Bytes(N)) 的 ~2300ns 高 ~27%。Rust 侧 build temp BuildStream
+ GreedyRange 循环 + lengthfield.build 三步开销 ~357ns，加速比因此落到 8x。

**判定**：数据密集型场景的 Python baseline 相对快，是已知的"Python 在特定循环场景下不慢"现象
（与 Phase 4 Array 大规模场景同性质）。

### Switch str-key 不可达说明

PM 任务书要求"Switch（int key + str key）"，但：

- **7.1 DEV 设计质疑 2 + VET 观察 O-1 确认**：Python 用户面 str-key 路径不可达
  （_FieldDescriptor 不携带类型元数据，所有 field 引用走 IntExpr 路径）
- **str-key FieldRef 路径**仅通过 Rust API 直接构造，switch.rs 单元测试 SW-5/SW-6/SW-12 覆盖
- **bench 测量**：Python 端可达的 const int key 场景（≥10x 预期），str-key 不独立 bench

**PM 决策点**：是否在 Phase 8+ 引入字段类型元数据以解锁 Switch FieldRef Python 用户面可达性。

**建议**：接受。根因是边界场景（Rust 侧 <300ns）+ parse 方向 PyObject 构造固有开销 + 跨会话测量漂移。

- (B) 对 1-2 个典型 case（如 ITE1-parse）做 Controlled A/B Test 复测确认稳态（参考 Phase 5.6a 模式）
- (C) 触发性能优化子任务（Phase 8+ 范围）

### 决策点 2：Switch str-key Python 用户面不可达是否解锁？

**建议**：Phase 8+ 引入字段类型元数据。当前 str-key 路径在 Rust API 完整实现（switch.rs SW-5/6/12），
仅 Python 用户面不可达。属于已知限制（设计质疑 2 / VET O-1）。

### 决策点 3：PF4-build 数据密集型边界（8.19x）是否接受？

**建议**：接受。与 Phase 4 Array 大规模场景同性质（Python 在循环密集场景下相对快）。
不属于回归或实现 bug，是数据密集型场景的固有边界。
