## PM 检视重点逐项回应

### 重点 1：§0 合规（L-01）—— Switch A+B 是否引入中间表示层？

**判定：✅ 不引入中间表示层，§0 合规**

逐条核对 §7 对照表：

| §0 原则 | Switch A+B 合规性判定 |
|---------|---------------------|
| #1 一次 FFI | ✅ Switch.parse 的数据流：eval_key（路线 A：GetInt 走 expr_values_buf 指针读 ~1ns；路线 B：1 次 PyDict_GetItem + N 次 PyObject_RichCompare）→ match_sub（Rust 内 i64== 或 PyObject 比较）→ subcon.parse（直接产 PyObject）。无"Python→Rust→Python"的边界穿越往返，Rust 内部 CPython C API 调用属 §0 #1 后半句"Rust 内部通过 CPython C API 直接操作 Python 对象"允许范围（与 ADR-022 §0 #1 合规论证同脉络）|
| #2 无中间表示层 | ✅ **关键**：matched subcon.parse 的结果**直接返回**给调用者，不经过任何 Rust 中间数据类型再转换。SwitchKey/SwitchCase 是**执行树的编译期内部状态**（key 分类 + 缓存），不是"parse 结果的中间表示"。与 L-01 禁止的"先构造 Rust enum/dict 再转 PyObject"模式有本质区别 |
| #3 输入输出无 trait 抽象层 | ✅ SwitchNode 持 `Vec<SwitchCase>` + `Box<Node>`，subcon 调用走 enum_dispatch 静态分派，无 `dyn Construct` |

**与历史教训对照**：L-01 事件 2（Phase 1 R3）是"dict 跨 FFI 返回"——Switch 不存在此模式（subcon.parse 在 Rust 内调用，结果 PyObject 在 Rust 栈上传递）。

**唯一需注意的措辞**：§7 验证点写"受控 FFI（路线 B，cases 数决定）"。严格说 PyObject_RichCompare 是"Rust 调 C API"（持有 GIL），不是"Python↔Rust 边界穿越"。但从性能开销量级看（~50-100ns/op），把它列入 §8 性能假设的"FFI 来源"是合理的工程化处理。此措辞精度不影响 §0 合规实质。

### 重点 2：Switch keyfunc A+B 方案可行性（编译期分类 + 运行时匹配 + py_eq 容错）

**判定：✅ 技术可行，设计完整**

- **编译期分类**（§3.2）：4 类 keyfunc（ConstInt / IntExpr / FieldRef / 复杂表达式拒绝），分类逻辑清晰。复杂表达式编译期拒绝 + 引导用户用 Computed 预计算，与 ADR-014 脉络一致（构造器内部决策不背 PyCallable 包袱）。
- **运行时匹配**（§3.4 match_sub）：先 i64 快速路径（零 C API），再 PyObject __eq__ 慢路径，最后 default 兜底。算法正确，边界覆盖（SW-1~SW-12）。
- **py_eq 容错**（§3.4）：`PyObject_RichCompare` 返回 null 时 `PyErr_Clear` + 返回 false（视为不匹配），对齐 Python `dict.get` 的 `__hash__+__eq__` 语义（异常→不匹配）。unsafe raw FFI 模式与 ADR-019/021 已验证模式一致。

**路线 A+B 覆盖度**：路线 A 覆盖 int key（最常见用法），路线 B 覆盖 str/bytes key（cases ≤5 时 FFI 开销可控）。路线 C（PyCallable）拒绝合理（与 ADR-014 脉络）。

**已知限制文档化**：D2（default=Error 不支持）/ D3（复杂表达式编译期拒绝）已在 §12 诚实记录。

### 重点 4：FocusedSeq 不复用 StructNode 的决策

**判定：✅ 决策合理，4 点理由充分**

§5.1 路线 B（独立 Node）的理由覆盖：
1. **返回值类型不兼容**：StructNode.parse 返回用户类实例，FocusedSeq.parse 需返回单字段值。若复用需外层 getattr（跨 FFI）+ FocusedSeq 无"用户类"语义。✅
2. **build 输入语义不同**：StructNode.build 逐字段 getattr；FocusedSeq.build 接收单值 obj，只赋 focus 字段，其余传 None。✅
3. **context nesting 来源不同**：StructNode 由 StructRefNode 委托时隐式注入；FocusedSeq 需主动 new_child。✅
4. **耦合代价**：复用需在 StructNode 加"focus 提取钩子"，破坏单一职责。✅

独立实现成本（~100 行 context nesting）远小于复用引入的耦合复杂度。决策符合"职责单一"原则。

### 重点 5：IfThenElse 复用 StopIfCondition

**判定：✅ L-04 对策落实，复用合理**

1. **同构类型**：StopIfCondition 三变体（Always/Never/Expr）与 IfThenElse 条件分类完全同构。✅（核对 stop_if.rs L48-59）
2. **L-04 对策**：避免重新决策同构类型，StopIf 已验证 Condition 模式（4 个 Node 用、性能达标）。✅

**eval_condition 提取**（§2.3）：将 `StopIfNode::eval_cond`（stop_if.rs L129 私有方法）提取为 `pub(crate) fn eval_condition`，行为不变。StopIf 既有测试全 PASS（回归保证）。此重构是内部改进，不影响公开 API，符合 L-04 模式沉淀。

**未来 ADR 触发点**：§2.1 标注"若 Phase 8+ 出现第 3 个使用 Condition 模式的构造器，应沉淀 ADR 重命名为 Condition"。此前瞻性标注符合 L-04 对策的"避免重新决策"精神。

### 重点 6：性能假设（≥4x 必需 / ≥10x 理想）

### P4【完备性 - 表述精度】ExplicitError 变体 Phase 7 内 dormant，措辞易误解

**文档位置**：§1.5 边界条件 + D1 差异 + §11.5 parity 模板

**问题描述**：
- §1.5 明确：`ConstructError::Explicit` 仅由用户路径产生（AdapterCallback 回调抛 Python `ExplicitError` → pyo3 转 PyErr → `From<PyErr>` 转 Generic）。
- §1.5 同时明确：Select / Peek 自身不主动构造 Explicit。
- D1 差异：`From<PyErr> for ConstructError`（error.rs L942）统一转 Generic，丢失 Python 侧 ExplicitError 类型信息。
- **推论**：Phase 7 内**没有任何代码路径会构造 `ConstructError::Explicit` 变体**——Python 用户路径经 From<PyErr> 转 Generic，Rust 内部不主动构造。
- 因此 Select 的 `if matches!(e, ConstructError::Explicit { .. })` 和 Peek 的 `is_explicit_error` 在 Phase 7 内**永远不会触发**（dormant 状态）。
- PM 决策 2 理由"Select 必须 parity（Python `except ExplicitError`）"容易让读者误解为 Phase 7 已完全达成 parity。实际上 §11.5 诚实承认"Python parity 在'Rust 内部主动构造 Explicit'场景下成立（Phase 7 范围内 Rust 不主动构造 Explicit）"。

**影响**：不构成功能缺陷（设计诚实承认差异 + 标注未来修复计划"Phase 8+ 修复 From<PyErr> 保留 Python 异常类映射"）。但措辞精度不足易导致 PM/DEV/VET 误判 parity 达成度。

**建议修改方向**：
1. §1.5 或 §1.2 显式标注："**Phase 7 内 `Explicit` 变体处于 dormant 状态**——无 Rust 内部构造路径，Python 用户路径经 From<PyErr> 转 Generic。变体引入是为 Phase 8+ Error 构造器 + From<PyErr> 修复做前置基础设施（ADR-022 PE-3 收尾）。Select/Peek 的 Explicit 识别逻辑在 Phase 7 内无用户可达触发路径，但代码正确性已就位。"
2. PM 决策 2 的"Select 必须 parity"措辞可在设计文档中补充限定"（Rust 内部构造场景达成；Python 用户抛 ExplicitError 场景待 Phase 8+ From<PyErr> 修复后达成）"。

**严重度**：低（设计已诚实承认差异，仅表述精度建议加强；不影响功能正确性）。
