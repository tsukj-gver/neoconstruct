## 偏离设计文档

### [设计质疑] 1：SwitchKey / IfThenElseNode 删除 Clone derive

设计文档 §2.2 / §3.3 标注 `#[derive(Debug, Clone)]`，但 `Node` enum 整体未实现 `Clone`
（含 `Py<PyType>` / `FieldName` 等非 Clone 字段）。删除 Clone derive，与 `BitwiseNode` /
`TransformNode` 等持有 `Box<Node>` 的节点保持一致。

**判定**：小问题。删除 Clone 不影响功能（无调用点需要 Clone）。如未来需 Clone 能力，
应统一为 Node 实现 Clone（涉及全 Node 变体 + FieldName + Py 字段）。

### [设计质疑] 2：Switch FieldRef 路径在 Python 用户面不可达

设计 §3.2 规划 FieldRef（路线 B）支持 `this.tag`（str/bytes 字段）作为 keyfunc。
但 Python 侧无法在编译期区分 "int 字段" vs "str/bytes 字段"（无字段类型元数据）。

**实际实现**：
- Python 用户面 SwitchDescriptor 对所有 _FieldDescriptor keyfunc 走 IntExpr 路径
  （`_expr_params = {"key": keyfunc}`）
- Rust SwitchKey::FieldRef 仅通过 Rust API 直接构造（单元测试覆盖），不从 Python 用户面触发
- 用户用 str/bytes 字段作 keyfunc 时，运行时 eval_expr_int 会因 PyLong_AsLongLong
  失败抛 ExprType 错误（清晰失败，非静默错误）

**判定**：小问题。FieldRef 路径在 Rust API 层完整实现（单元测试 SW-5/SW-6/SW-12 验证），
Python 用户面暂不可达，文档化为已知限制。未来若引入字段类型元数据可解锁。

### [设计质疑] 3：FocusedSeq Python 用户面用 Renamed 包装器（非 `"/"`运算符）

设计 §11.4 暗示 `"num"/Byte` 语法（Python construct 原版），但 construct-rs 描述符不共享
基类，无法添加 `__rtruediv__`。

**实际实现**：定义 `Renamed(name, subcon)` 类，用户用 `Renamed("num", Byte)` 显式构造。
Python 用户面文档已说明此差异。

**判定**：小问题。语法小幅变化，功能等价。未来若需 `"/"` 语法，可统一为描述符添加
`__rtruediv__`（需重构描述符基类）。
