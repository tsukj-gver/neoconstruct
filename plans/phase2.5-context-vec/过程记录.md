### ARCH 设计说明

**优化方案两层结构：**

- **Layer 1（必做）**：P0 Context Vec 化 + P1 移除 field_names 体系
  - Context 新增 `expr_values: Option<Vec<*mut ffi::PyObject>>`（borrowed 指针，零额外 incref）
  - GetInt 从 PyDict hash 查找(~36ns) 改为 Vec 索引 + PyLong_AsLongLong(~6ns)，节省 ~30ns/GetInt
  - 移除 names 参数连带省 ~10ns/eval 调用（field_names() 调用 + 参数传递）
  - 预估 5/6 项达标，E1 parse 预估 8.7x（⚠️ 风险项）

- **Layer 2（视实测）**：P2 dict take + P3 interned "__dict__" + P4 force_setattr 内联
  - 固定开销微优化，预估节省 ~15-25ns
  - 叠加后 E1 parse 预估 9.3x（⚠️ 仍可能不达标）

**关键设计决策：**

1. raw pointer（`Vec<*mut PyObject>`）而非 `Option<Py<PyAny>>`：零额外引用计数操作，
   净收益优于 owned 方案（附录 A 对比）。安全性由 5 条不变量保证（§2.1）。
2. raw pointer 优于 i64 提前缓存：i64 缓存的 set_field extract 对不被 GetInt 引用的
   字段是纯浪费，净收益更低。
3. 借用安全：set_field_at(&mut self) 与 parse/build 中的其他 ctx 借用均为顺序借用，
   无冲突（§2.5 分析）。
4. 分阶段实施：先 Layer 1 实测，再决定 Layer 2（避免过早优化）。

**移除的 API**：set_field_names / set_field_names_ref / field_names / get_int_by_name /
get_obj_by_name / set_field_interned / StructNode.field_names_cache。

**需要 PM 决策的 3 个点**（见设计文档末尾）：
1. E1 parse 达标门槛（≥10x 硬要求 vs ≥9.5x 可接受）
2. Layer 2 分阶段实施策略确认
3. field_names_cache 移除确认

- **接口风格统一**：raw pointer 借用 dict 值的模式与现有 get_int_by_name 中的 `PyDict_GetItem` 返回 borrowed pointer 一致（context.rs:203），不引入新的抽象范式。
- **向后兼容**：`get_obj_by_name` 移除不影响当前功能（附录 B 说明 Phase 3 Switch 实现时重新设计），当前无生产调用方（grep 确认仅 context.rs 定义 + expr.rs 测试引用）。

## 性能退化排查与修复（2026-06-24）

### 问题描述

Vec 化优化实现后（commit 2570254），所有 416 测试通过，但 benchmark 显示**全面性能退化**：

| 场景 | 方向 | 退化后 ns | 基线 ns | 退化 |
|------|------|------:|------:|------:|
| E1 | parse | ~537 | 353 | **+52%** |
| E1 | build | ~326 | 271 | +20% |
| E2 | parse | ~535 | 391 | **+37%** |
| E2 | build | ~473 | 317 | **+49%** |
| E3 | parse | ~677 | 572 | +18% |
| E3 | build | ~637 | 541 | +18% |

退化集中在 has_expressions=true 路径，每场景退化 50-200ns。

### 根因分析

**通过 Rust 级 micro-benchmark 定位（`tests/bench_context_ops.rs`）：**

#### 根因 1（主要）：`get_int_at` 中 `ok_or` 的 eager 求值

```rust
// BUG: ok_or 每次调用都构造错误值（含 .to_string() 堆分配）
let vals = self.expr_values.as_ref()
    .ok_or(ConstructError::ExprContext {
        message: "...".to_string(),  // ← 每次调用都堆分配 ~60 字节 String！
        path: String::new(),
    })?;
```

`ok_or(value)` 是**eager 求值**——即使在成功路径（`Some` 分支），也会构造错误值。
`.to_string()` 分配 ~60 字节 String 堆内存，随后立即释放。

micro-benchmark 实测：

| 操作 | 成本 |
|------|-----:|
| `eager: .to_string() + String::new()` [旧路径] | **31.1 ns/op** |
| `lazy: len != 0 check` [新路径] | 0.3 ns/op |

每次 GetInt 调用浪费 **31ns** 堆分配。E1 有 1 次 GetInt（+31ns），E3 有 3 次（+93ns）。

#### 根因 2（次要）：`init_expr_values` 的 Vec 堆分配

`vec![ptr::null_mut(); n]` 每次 parse/build 分配 + 释放堆内存。
Windows Heap Allocator 对小对象（16-48 字节）的 malloc+free 开销 ~30-50ns。

### 修复方案

#### 修复 1：`ok_or` → 直接长度检查

```rust
// FIX: 直接检查 len，错误构造仅在错误路径触发（惰性）
if self.expr_values_len == 0 {
    return Err(ConstructError::ExprContext { ... });  // 仅此分支构造 String
}
```

#### 修复 2：Vec → 栈分配内联数组

```rust
const MAX_INLINE_FIELDS: usize = 16;

pub struct Context<'py> {
    fields: Option<Bound<'py, PyDict>>,
    parent: Option<&'py Context<'py>>,
    // 旧: expr_values: Option<Vec<*mut ffi::PyObject>>,  // 堆分配
    // 新: 栈分配内联数组，零堆开销
    expr_values_buf: [*mut ffi::PyObject; MAX_INLINE_FIELDS],
    expr_values_len: usize,
}
```

- `init_expr_values(n)`: 仅填充前 n 个槽位为 null（~2ns），零堆分配
- `set_field_at`: 直接数组索引写入（无 Vec 指针间接）
- `get_int_at`: 直接数组索引读取

#### 修复 3：添加 `#[inline]` 提示

对 `init_expr_values`、`set_field_at`、`get_int_at`、`take_fields` 添加 `#[inline]`。

    lazy len check          0.3 ns/op  (新路径)

### SHOULD-FIX（改进建议，不阻塞通过）

**SF-1 [context.rs:33,158] MAX_INLINE_FIELDS=16 静默截断——建议 Phase 3 前增加编译期检查**

当前实现：`init_expr_values(n)` 将 n 截断到 16，`get_int_at(idx>=16)` 返回
ExprFieldMissing。`compile.rs` 中**无编译期检查**阻止 GetInt(idx>=16) 的生成。

风险：用户定义 >16 字段的 Struct 且表达式引用第 17+ 字段时，运行时收到
`ExprFieldMissing { field: "<index 17>" }` 错误——值实际存在于 dict 中
（set_field_at 写入 dict），但快速路径 buf 无法访问。

评估：非数据损坏（产生明确错误而非静默错误结果），Phase 2.5 范围内（E1-E3 均
<=6 字段）不触发。但 Phase 3 可能遇到 PE/COFF 等 >16 字段格式。

建议（三选一，PM 决策）：
- (a) compile.rs 增加 `assert!(getint_idx < MAX_INLINE_FIELDS)` 编译期检查
- (b) 将 MAX_INLINE_FIELDS 增大到 32 或 64（栈开销 256/512 字节，可接受）
- (c) 保持现状但在设计文档追加正式 amendment 记录此限制

**SF-2 [context.rs:180-181] set_field_at 文档措辞不精确**

当前文档："对占位 context（fields = None）或未初始化 expr_values（len == 0）
为无操作"。

为无操作。未初始化 expr_values 时仅写 PyDict，不同步 buf。"

影响：仅文档精确性，不影响正确性（生产路径 has_expressions=true 时 len > 0）。

**SF-3 [设计偏离] 设计文档未追加正式 amendment**

设计文档 `docs/design/模块设计/模块设计-Context-Vec优化.md` §2.1 仍描述 `Option<Vec<*mut PyObject>>`，

### ARCH 设计说明

**优化核心**：parse 路径先创建实例（tp_new），借用实例自带的 `__dict__`，parse 循环
直接填充该 dict，无需新建独立 dict + force_setattr 整体替换。

**与 R3 方案 B' 的关系**：R4 是 R3 的增量优化，不改变语义（parse 返回用户类实例、
兼容 frozen dataclass、绕过自定义 `__setattr__`），仅改变实例 dict 的来源。

**关键设计决策**：

1. **dict 来源**：从 `PyDict::new_bound`（新建）改为 `instance.getattr("__dict__")`
   （借用 tp_new 附带的空 dict）。PyObject_GetAttr 是 ABI3 稳定 API，CPython 对
   `__dict__` 有内部 fast path，开销 ~15-25ns（比新建 dict ~30-50ns 便宜）。

2. **frozen dataclass 兼容**：直接 `dict.set_item` 不经过 `tp_setattro`（即不触发
   `__setattr__`），天然绕过 frozen dataclass 的拦截。与 R3 force_setattr 绕过
   机制不同但结果等价。

3. **Context API 新增**：
   - `inject_fields(dict)` — 注入外部 dict 替代 new_root 创建
   - `new_child_placeholder(parent)` — 有 parent 无 dict 的嵌套 context（替代 new_child）
   - 保留 new_root/placeholder/new_child/take_fields（兼容性，build 方向仍需要 new_root）

4. **schema.rs 简化**：_parse_raw 统一用 placeholder（移除 has_expressions 分支），
   StructNode.parse 内部自行管理 dict。

5. **不采用 tp_dictoffset 直接访问**：`Py_tp_dictoffset` 不在 PyType_GetSlot 文档化
   slot 列表，ABI3 模式不可靠。用 PyObject_GetAttr + interned 缓存替代。

**性能预估**：
- 净节省 ~66-102ns/parse（保守 70ns，乐观 100ns）
- E1 parse：Vec化后 350ns → R4 预估 250-280ns → 比率 9.7-10.9x（⚠️→✅）
- E2 parse：410ns → 310-340ns → 10.6-11.6x ✅
- E3 parse：650ns → 550-580ns → 8.1-8.5x ❌（固定开销占比小，仍不达标）
- build 方向：不受影响（无实例创建）

**影响面**：context.rs(~40行) + struct_node.rs(~50行) + struct_ref.rs(~5行) +
schema.rs(~5行) + 测试(~80行) = ~180 行。instance.rs 无改动（保留 force_setattr
函数，仅 parse 不再调用）。

**需要 PM 决策的 3 个点**（见设计文档 §设计完成状态）：
1. E3 parse 仍不达标（8.1-8.5x），是否接受阶段性 ≥8x？
2. build 方向不受益，是否需另立优化设计？
3. take_fields 是否标记 deprecated 或移除？

- **frozen dataclass 绕过论证正确**（§2.2）：`PyDict_SetItem` 直接操作 dict 对象的内部哈希表，**不触发** `tp_setattro`（不调用 `__setattr__`）。frozen dataclass 生成的 `__setattr__` 会 raise `FrozenInstanceError`，但因 dict.set_item 不经过该路径，写入安全。这与 R3 force_setattr 绕过机制不同（R3 用 `PyObject_GenericSetAttr` 绕过），但结果等价。论证准确——CPython 中 `PyDict_SetItem` 确实不调用实例的 `tp_setattro`。

- **Rust 借用安全**（§4.2-4.3）：`instance: Bound<PyAny>` 与 `dict_bound: Bound<PyDict>` 是独立的 GIL-bound handle（同为 `'py` 生命周期），无 Rust 可变借用冲突。`inject_fields(dict_bound)` 通过 move 语义消耗 dict_bound，ctx.fields 接管所有权——与现有 `take_fields` 的 move 模式对称，不引入新的借用风险。

**SF-2 [观察项] dict_attr_name 每 StructNode 创建一份——可考虑全局缓存**

当前每个 StructNode 在 `new()` 中调用 `intern_pystring(py, "__dict__")` 缓存一份
`Py<PyString>`。由于 "__dict__" 是 CPython 全局 interned 字符串，实际开销接近零
（仅一次指针比较返回已有对象）。设计 §3.2 已论证此选择合理（StructNode 生命周期 =
类生命周期，开销可忽略）。

若未来有大量 StructMixin 子类（>100），可考虑改用全局 `OnceLock<Py<PyString>>`
单例缓存。当前 Phase 2.5 范围内非必要优化。列为观察项，不要求修改。
