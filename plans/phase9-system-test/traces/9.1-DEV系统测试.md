# TRACE 9.1 DEV 系统测试：真实二进制协议解包拆包

## 1. 协议选型

选了 4 个真实工业/网络协议，覆盖任务要求的**条件分支 + bitfield + CRC/校验**三大能力：

| 协议 | 来源 | 覆盖能力 | 复杂度 |
|------|------|---------|--------|
| **Modbus RTU** | Modbus Application Protocol V1.1b3 | Switch (功能码) + Checksum (CRC16) + Array + 嵌套 Struct | 中 |
| **CAN 2.0A/B** | ISO 11898-1 / SocketCAN | BitStruct (32-bit ID + 标志) + Bytes(dlc) 变长 + 条件分支（标准/扩展帧） | 中 |
| **IEC 60870-5-104** | IEC 60870-5-104 spec | Switch (帧类型 I/S/U) + Peek + Computed + 嵌套 + Const | 高 |
| **IPv4 报文头** | RFC 791 | BitStruct (3 个子结构) + Checksum (外部校验) | 中 |

## 2. 每个协议的实现要点

### 2.1 Modbus RTU (`test_modbus_rtu.py`)

**协议结构**：Address(1B) + FC(1B) + Data(variable) + CRC16(2B, LE)

**关键设计**：
- **Switch on function_code**：cases 字典映射 `{0x01: ReadReq, 0x03: ReadReq, 0x06: WriteSingle, 0x10: WriteMulti, ...}`
- **Checksum 自动校验/计算**：
  - 用 `field(Checksum(Bytes(2), modbus_crc16, start=body_start, end=body_end))`（**注意是 `field()` 不是 `rfield()`**）
  - `body_start / body_end` 用 `rfield(Tell())` 标记流位置
  - parse 时读 2 字节 → 用 Python callable `modbus_crc16` 算 [body_start, body_end) 的 CRC → 比较，不等抛 ChecksumError
  - build 时算 [body_start, body_end) 的 CRC → 写入
- **Array with FieldRef count**：FC=0x10 的 `values = Array(quantity, Int16ub)`，count 引用同 Struct 的 quantity 字段

**测试用例**：
- Round-trip：4 种功能码 (0x01/0x03/0x06/0x10) parse → build 一致
- CRC 校验：正确 CRC pass / 错误 CRC 抛 ChecksumError
- Switch 覆盖：6 种 FC 各自分派正确
- parity：parse + build 两端字节一致（含 CRC）

### 2.2 CAN 2.0A/B (`test_can_frame.py`)

**协议结构（SocketCAN 字节级表示）**：can_id(4B, 含标志) + DLC(1B) + data(0-8B)

**关键设计**：
- **BitStruct 32-bit ID 分解**（Linux `can_id_t` 布局）：
  ```python
  @dataclass
  class CANIdentifier(BitStructMixin):
      err: int = field(Bit())              # bit 31
      rtr: int = field(Bit())              # bit 30
      eff: int = field(Bit())              # bit 29
      ext_id_low: int = field(BitsInteger(18))   # bits 28-11
      std_id: int = field(BitsInteger(11))       # bits 10-0
  ```
- **变长 data**：`data: bytes = field(Bytes(dlc))`，dlc 引用同 Struct 字段
- **标识符重建**（标准 vs 扩展）：在测试代码中根据 `eff` 标志重建，不在 construct-rs 内做（Computed 不能跨层引用子 BitStruct 字段）

**测试用例**：
- 5 种帧类型：标准/扩展/远程/错误/minimal
- bitfield 边界：11-bit ID 边界 (0/0x7FF) + 29-bit ID 边界 (0/0x1FFFFFFF) + DLC 0-8
- parity：parse + build 一致

### 2.3 IEC 60870-5-104 (`test_iec104.py`)

**协议结构**：Start(0x68) + Length(1B) + Control Field(4B) [+ ASDU for I-frame]

**关键设计**：
- **Peek + Computed + Switch** 实现 I/S/U 三种帧类型分派：
  ```python
  cf1_peek: int = field(Peek(Int8ub))  # RW, not rfield（Peek 不在 RO 允许列表）
  frame_type: int = rfield(Computed(
      (cf1_peek & 1) * (1 + 2 * ((cf1_peek >> 1) & 1))
  ))
  control_field: object = field(Switch(frame_type, {0: IFormat, 1: SFormat, 3: UFormat}))
  ```
- **关键公式**：`cf1 & 3` **不能**直接区分 I-frame（因 send_seq 的 bit 0 会出现在 cf1 bit 1 上）。
  正确公式 `(cf1 & 1) * (1 + 2 * ((cf1 >> 1) & 1))`：I→0, S→1, U→3
- **嵌套 Struct + Computed**：I-format 内 `send_seq = (cf2 << 7) | (cf1 >> 1)`
- **Const 校验**：S-format CF1=0x01, CF2=0x00；U-format CF2=CF3=CF4=0x00；起始字节 0x68

**测试用例**：
- Round-trip：I/S/U 三种帧类型
- 序列号边界：15-bit (0, 32767, wrap 组合)
- Const 字段校验：错误 CF1/CF2 → ConstError
- parity：5 种帧 parse 字段一致

### 2.4 IPv4 报文头 (`test_ipv4.py`)

**协议结构**：20 字节（最小），含 3 个 BitStruct 子结构

**关键设计**：
- **3 个 BitStruct 子字段**：
  - VersionIHL: BitsInteger(4) + BitsInteger(4) = 1 byte
  - DSCPECN: BitsInteger(6) + BitsInteger(2) = 1 byte
  - FlagsFragment: Bit + Bit + Bit + BitsInteger(13) = 2 byte
- **Checksum 当作普通 Bytes(2)**：协议中间位置（offset 10-11），无法用 Tell(start, end) 包裹（详见 §4 API gap）
- **外部校验**：`ipv4_checksum()` 函数在测试代码中验证

**测试用例**：
- Round-trip：minimal + typical TCP + DSCP/ECN + max fragment offset
- bitfield 边界：Version/IHL/DSCP/ECN/Flags/Fragment 各字段边界值
- Checksum：RFC 1071 真实报文（b1f1）+ 自校验（含 checksum 重新计算应为 0）
- parity：parse + build 一致

## 4. API gap 发现

### 4.1 Checksum + RawCopy dict 不工作 [中等优先级]

**问题**：Checksum 构造器的 `bytesfunc='field_name'` 模式（路径 A2/ContextBytes）
不能引用 RawCopy 包装的字段（dict 类型），只能引用直接的 bytes 字段。

**复现**：
```python
@dataclass
class P(StructMixin):
    body: dict = field(RawCopy(SomeStruct))  # dict 类型
    checksum: bytes = field(Checksum(
        Bytes(2), hash_fn, bytesfunc='body'  # 期望取 body['data']
    ))
```

实际：抛 `ChecksumError: bytes field 'body' is not bytes-like`。

**Rust 端实现**（`src/nodes/checksum.rs` L211-216, L249-254）：直接 `extract::<&[u8]>()`
从 ctx 取的字段，对 dict 类型失败。

**文档**（`_descriptors.py` ChecksumDescriptor docstring L2917-2924）说：
> bytesfunc: 引用 RawCopy dict 的 "data" 字段

但实际未实现 dict.data 提取。文档与实现不一致。

**临时变通**：用 StreamRange（start/end + Tell）模式替代，bytes 数据通过 stream slice 取。
本任务的 Modbus RTU 即用此方案。

**建议修复**：在 `ContextBytes` 路径中加一层 dict.data 提取逻辑（type check 是 dict 且
含 'data' key → 取 data 字段）。

### 4.2 Checksum / Peek 不能作为 rfield（RO 模式）[低优先级]

**问题**：`rfield(Checksum(...))` 与 `rfield(Peek(...))` 在 build 时报错：
```
compute_ro_value: node type Checksum(...) is not a valid RO node.
RO fields must be Tell, Computed, Index, StopIf, Check, Terminated, Default,
Rebuild, Element, or Const/ContextParam (future).
```

**变通**：用 `field()`（RW 模式）：
- Checksum：build 时 instance 的 crc 值被忽略，由 StreamRange 重算
- Peek：build 时是 no-op（不写字节），instance 上的值仅用于 Computed 计算

**建议**：要么扩展 `build_ro_value` 允许列表，要么文档明确"Checksum/Peek 必须用 field() 而非 rfield()"。

### 4.3 Computed 不能跨层引用子 BitStruct 字段 [已知限制]

**问题**：Computed 表达式只能引用同 Struct 内的兄弟字段（siblings），不能引用
嵌套子 Struct（包括 BitStruct）的字段。

**例子**：CAN frame 想要：
```python
@dataclass
class CANFrame(StructMixin):
    can_id: CANIdentifier = field(CANIdentifier)
    # 不能引用 can_id.eff：
    is_extended: int = rfield(Computed(can_id.eff))  # 编译错误
```

**变通**：标识符重建在测试代码中完成（Python 层运算）。construct-rs 协议定义层面
保持扁平化的子 Struct。

**建议**：Phase 10 SKILL 中作为"已知限制"说明，引导用户在 Python 层做跨层计算。

### 4.4 Switch keyfunc 复杂表达式需通过 Computed 预计算 [设计约束]

**问题**：Switch 的 keyfunc 直接用复杂表达式（如 `byte1 & 3`）能编译通过
（_ExprRef 被接受），但语义可能错误（如 IEC 104 cf1 & 3 因 send_seq 位污染）。

**学习要点**：复杂表达式应先用 Computed 预计算到一个新字段，再 Switch 字段名引用。
本任务 IEC 104 即如此实现。

## 6. 对 Phase 10 SKILL 的建议

### 6.1 construct-rs API 关键用法要点

1. **Switch 的 keyfunc**：
   - 简单字段引用直接用字段名：`Switch(my_field, {1: A, 2: B})`
   - 复杂表达式用 Computed 预计算：先 `frame_type = rfield(Computed(...))` 再 Switch(frame_type, ...)

2. **BitStruct 字段总 bit 数必须是 8 的倍数**（否则 parse/build 报 BitFieldError）
   - 用 `Padding(n)` 补齐（在 wfield 中）

3. **Checksum 用 StreamRange 模式**（推荐）：
   ```python
   body_start: int = rfield(Tell())
   # ... body fields ...
   body_end: int = rfield(Tell())
   crc: bytes = field(Checksum(Bytes(2), hash_fn, start=body_start, end=body_end))
   ```
   - **必须用 `field()` 而非 `rfield()`**（Checksum 不在 build_ro_value 允许列表）

4. **Peek（预读不消费）**：用于在不破坏后续字段解析的前提下偷看字节
   - 同样**必须用 `field()`**（与 Checksum 同理）

5. **Const 用法**：
   - bytes 值：`Const(b"\x68")` 自动推断为 Bytes(len)
   - int 值：`Const(0x01, Int8ub)`（**注意**：参数顺序是 `(value, subcon)`，与 Python construct 一致）

6. **变长字段引用**：`Bytes(my_count_field)` / `Array(my_count, Int16ub)` 直接引用同 Struct 内 int 字段

### 6.2 易错点（基于本任务踩过的坑）

1. **Python construct parity 时**：`pc.Const(0x01, pc.Int8ub)` 是 `(value, subcon)` 顺序，
   不是 `(subcon, value)`。这与 construct-rs 一致但容易写反。

2. **Python construct Container 含 `_io` 等内部状态字段**，JSON 比对前必须过滤 `_*` 开头键。

3. **IEC 104 帧类型识别**：`cf1 & 3` 因 send_seq 位污染，必须用乘法 + 移位公式
   `(cf1 & 1) * (1 + 2 * ((cf1 >> 1) & 1))`

4. **CAN ID BitStruct 字节序**：BitStruct 默认大端 bit 序（MSB first），与 SocketCAN
   can_id_t 一致；不要用 BitsSwapped 反转。

5. **subprocess parity 测试**：每个用例都要重新声明协议类（子进程无父进程的 import context）；
   venv 路径要从 `tests/conftest.py` 复制（避免 stale cache）。
