### ARCH 设计说明

**核心技术决策**：
1. **pyo3 作为 construct-rs 的 optional feature**（方案 A，非合并 crate）：PySink/exec_parse_py 全在 construct-rs 内，可访问编译树内部字段，与 CompiledExtension 无缝集成。纯 Rust 测试（1515 个）通过 `cargo test`（无 python feature）零影响保留。
2. **新增 PyCompiledExec trait + 宏生成 dispatch**（非修改 CompiledExec、非泛型化 OutputSink）：Value 路径 trait 零修改；Py 路径独立 trait + 71-arm 宏 match。
3. **PySink 双产物设计**（Value for ctx + PyObject for output）：leaf 一次解码同时产出标量 Value（供 context 表达式）和 PyObject（供输出），彻底消除 B1 round-trip。
4. **build 方向 per-field 类型已知 extract + schema-guided batch extract**：消除 B2（双重全量转换）和 B3（类型检查链）。100 元素 int array build 从 638 FFI 降至 ~5 FFI。

**性能假设摘要**（满足 performance-gate Checkpoint 1）：
- 识别 8 个瓶颈来源（B1-B8，含旧设计的 B1-B4 + 新增 B5-B8）
- 可证伪预测：simple parse ~10x / simple build ~7.7x / array parse ~3-5x / array build ~11x (batch)；geomean(6 场景) ≥2.0x（保守）
- 反例声明：6 条，每条有明确应对方案
- 验证方法：test_perf_comparison.py 分阶段验证 + 烟雾测试检查点（16.3 后 simple parse ≥1.0x）

**对现有代码的影响**：
- construct-rs：新增 3 文件（~800-1200 行），Cargo.toml + mod.rs 小改，现有代码零修改
- construct-py：compiled_ext.rs 重写入口，conversions.rs 从 788 行缩减至 ~250 行，py_sink.rs/py_input.rs 删除/deprecated
- 公共 Python API 不变；1515 纯 Rust 测试不变；61 dataclass 测试行为等价

##### 2.2 🔴 关键问题 P-CRIT-1：extract_batch_int_py "单次 C 调用" 声明事实错误

**文档位置**：§4.5 + §6.3 P4

**设计声明**：
> "items extract_batch_int_py | **1** extract(Vec\<i64\>) | 1 | ~500ns"
> "pyo3 对 Vec\<i64\> 的批量 extract 是单次 C 调用遍历 CPython list 内部数组，~5ns/元素"

**实际行为**（pyo3 0.22.6 源码 `types/sequence.rs:494-529` 已验证）：
```rust
fn extract_sequence<'py, T>(obj: &Bound<'py, PyAny>) -> PyResult<Vec<T>> {
    let seq = ...; // PySequence_Check
    let mut v = Vec::with_capacity(seq.len().unwrap_or(0));
    for item in seq.iter()? {       // per-element: PySequence_GetItem × N
        v.push(item?.extract::<T>()?);  // per-element: PyLong_AsLongLong × N
    }
    Ok(v)
}
```

**实际 FFI 计数（100 元素）**：~202 次 C 调用（1 PySequence_Check + 1 PySequence_Length + 100 PySequence_GetItem + 100 PyLong_AsLongLong），而非 1 次。实际耗时 ~3-5µs 而非 ~500ns。

**对 P4 预测的影响**：
| | 设计声明 | 修正估算 |
|---|---------|---------|
| batch extract FFI | 1 | ~202 |
| batch extract 耗时 | ~500ns | ~3-5µs |
| array build 总计 | ~2.6µs | ~5-6µs |
| vs Python ~30µs | ~11.5x | ~5-6x |

**判定**：P4 ≥4.0x 目标仍可能达标（5-6x > 4x），但余量大幅缩窄。设计声称的 batch extract 相对 per-index 的 "~100x FFI 优势" 实际为 "~0-1.2x"（两者都是 per-element）。batch 的真实优势仅在于避免 per-element trait object dispatch 和更好的缓存局部性。

**要求**：ARCH 必须修正 §4.5 和 §6.3 P4 的 batch extract 分析。选项：
(a) 更正为 per-element 估算，承认 batch 优势主要来自避免 `dyn PyInput` dispatch；或
(b) 将 batch extract 改为裸 CPython API 手动循环（`PyList_GET_ITEM` 宏 + `PyLong_AsLongLong`），明确这是绕过 pyo3 抽象的方案；或
(c) 将 array build 优化降级为 Phase 17 候选（如 numpy frombuffer）。

##### 2.3 🟡 重要问题 P-IMP-1：B7 (Box\<dyn PySink\>) 对大数组的影响被低估

**文档位置**：§6.2 B7 + §6.6

**设计声明**："B7 影响 ~20ns/字段，非主导"

##### 5.1 🔴 关键问题 C-CRIT-1：Container/ListContainer 包装机制未指定（BC-5）

**文档位置**：§3.3 PyDictSink2 + BC-5

**问题**：Python 原版 construct 的 parse 结果必须包装在 `Container`（dict 子类，支持 `result.field` 属性访问 + `search()` 方法）和 `ListContainer`（list 子类）中。当前 `conversions.rs:58-95` 的 `value_to_py` 对 List/Container 分支显式 import 并构造这些子类。

新设计的 `PyDictSink2::new_root_struct` 创建的是 **plain PyDict**，`into_root_py` 返回 **raw PyDict/PyList**，无 Container/ListContainer 包装。这将导致：
- `result.field_name` 属性访问失效（61 个 dataclass 测试可能失败）
- `result.search()` / `result.search_all()` 不可用
- Container 特有的 repr 格式丢失

设计在 P3 估算中提到了"ListContainer 包装 | call1 (root 时一次) | 2 | 200ns"，说明 ARCH 意识到了这个需求，但**未在接口设计中给出实现机制**。

**要求**：ARCH 必须在设计文档中补充 Container/ListContainer 包装的具体方案（建议：root sink 完成后一次性包装；或在 `new_root_struct` 时创建 Container 实例而非 plain PyDict）。

##### 5.2 🔴 关键问题 C-CRIT-2：build 方向 context._ 设置未指定（BC-3）

**文档位置**：§4 CompiledStruct::exec_build_py + BC-3

**问题**：当前 `compiled_ext.rs:190` 的 `build_from_raw` 执行：
```rust
if let Ok(embed) = input.as_value() {
    ctx.insert("_", embed);  // 供 IfThenElse(this._ == ...) 等条件构造使用
}
```

新设计的 `PyInput` trait **没有 `as_value()` 方法**（它有 `extract_scalar_py` / `sub_field_py` / `extract_batch_int_py`）。因此新 `build_from_raw` 如何设置 `ctx["_"]` 未定义。

选项：
(a) 在入口处对 root input 做一次缩减版 `py_to_value`（仅用于 `ctx["_"]`）——但这部分恢复了 B2；
(b) 跳过 `ctx["_"]` 设置——破坏 IfThenElse(this._ == ...) 等条件构造的正确性；
(c) 在 PyInput trait 增加 `as_value_for_ctx()` 方法——但这需要对 root dict 做全量转换。

**要求**：ARCH 必须明确指定新 `build_from_raw` 中 `ctx["_"]` 的处理方案。建议方案 (a)：仅在 root 入口做一次 `py_to_value` 用于 `ctx["_"]`，不传入 exec_build_py 链路（即 B2 的第一次 as_value 保留但只用于 ctx 初始化，不传入 Struct 的 per-field 读取）。

##### 5.3 🟡 重要问题 C-IMP-1：PyInput sub_field_py 需 getattr 回退（BC-7）

**文档位置**：§4.2 PyInput trait

**问题**：当前旧 `PyInput::get_field_bound`（py_input.rs:62-75）先试 `__getitem__`（dict），失败后试 `getattr`（dataclass/attribute）。新设计的 `PyInput::sub_field_py` 未指定是否保留此回退。

dataclass 实例的 build 输入依赖 getattr 访问。若 `sub_field_py` 仅用 `PyDict_GetItem`，dataclass build 会 FieldMissing。

**要求**：DEV 实现时 `sub_field_py` 必须保留 `get_item → getattr` 回退链（与旧 PyInput 一致）。

##### 5.4 🟡 重要问题 C-IMP-2：Adapter/Validator Py 路径模式未细化（BC-11）

**文档位置**：§3.7

**问题**：Adapter 的 decode 闭包对 Value → Value 变换。Py 路径中，wrapper 需要：(1) 通过 sub-PySink 获取 inner 的 (Value, PyObject)，(2) 对 Value 应用 decode，(3) 对 decode 后的 Value 重新 `value_to_py_scalar` 生成新 PyObject，(4) deposit 新 pair。步骤 (3) 的开销未在任何估算中计入。

**要求**：DEV 实现时注意 Adapter/Validator wrapper 的 exec_parse_py 需要"sub-sink → 取 Value → transform → 重新转 PyObject → deposit"模式。对非标量 decode 结果（如 Container），需走 `value_to_py_composite_fallback`。

2. **[设计质疑] PySink trait 新增 `into_pair()` 方法**
   - 设计文档的 7 方法 trait（deposit_leaf + sub_py_field/sub_py_item + finish_field_py/finish_item_py/finish_named_item_py + into_root_py）缺少 `into_pair()`

   - 影响：trait 增加一个方法，不破坏设计意图

   - 实现：finish_* 在 sink 为 Empty 时隐式创建 Container/ListContainer（ensure_struct/ensure_array 私有方法）
   - 影响：调用方无需显式 begin_struct/begin_array，简化 exec 层逻辑

#### 设计偏离评估

| 编号 | 偏离 | VET 意见 | 理由 |
|------|------|---------|------|
| 1 | sub_py_field/sub_py_item 增加 `py: Python<'_>` 参数 | **接受** | 创建 Container/ListContainer 子类实例需 GIL token。当前实现用 `_py`（实际未使用，因 sub-sink 创建为 Empty，Container 在 ensure_struct/ensure_array 延迟创建），但作为面向未来的 trait 设计无害。建议未来若 classes.clone 改用 clone_ref(py) 即可激活此参数。 |
| 2 | PySink trait 新增 `into_pair() -> (Value, PyObject)` 方法 | **接受** | 设计文档 §3.3 示例 `sub.into_value_obj_pair(py)?` 已暗示需要此方法（仅未在 trait 定义中显式列出）。`into_root_py` 通过默认实现委托给 into_pair，不破坏设计意图。零 round-trip 机制的核心。 |
| 3 | finish_field_py / finish_item_py 在 Empty 状态隐式创建 Struct/Array（ensure_struct/ensure_array） | **接受** | 简化 exec 层（调用方无需显式 begin_struct）。文档表 "Mode transitions" 已列出 Empty → Struct/Array 转换。`pydictsink2_nested_struct_zero_round_trip` 测试验证此行为。替代方案（显式 begin_struct）会增加 exec 层复杂度，当前方案更优。 |

#### 建议改进项（不阻塞 16.2 通过，转 16.4/16.5 处理）

1. **🟡 extract_scalar_short_circuit 补 BigInt 分支**（行为一致性）
   - 位置：py_input.rs:197-225
   - 现状：仅探测 i64/u64，>u64::MAX 的 Python int 返回 None → TypeMismatch
   - 对照：旧 conversions.rs:122-124 用 extract::<BigInt> 统一处理
   - 建议：在 u64 分支后补 `if let Ok(b) = obj.extract::<num_bigint::BigInt>() { ... narrow to BigInt(i128) ... }`，或在 16.4 leaf exec_build_py 中对 BigInt leaf 直接用类型化方法绕过此函数
   - 阻塞性：否（build 方向 BigInt 罕见，16.2 未端到端集成）

2. **🟢 ContainerClasses::clone 改用 clone_ref(py)**（性能微优化）
   - 位置：py_sink.rs:87-97
   - 现状：`Python::with_gil(|py| ... clone_ref(py) ...)`，虽然 GIL 已持有时为 no-op，但仍有一次线程局部 GIL 状态检查
   - 建议：增加 `pub fn clone_ref(&self, py: Python<'_>) -> Self` 方法，sub_py_field/sub_py_item 用传入的 py 参数调用
   - 阻塞性：否（影响 ~5-10ns/字段）

3. **🟢 finish_item_py / finish_named_item_py 用 PyList_Append 替代 call_method1("append")**（性能微优化）
   - 位置：py_sink.rs:527-529, 549-551
   - 现状：通过 Python 方法解析调用 list.append，~25ns/调用
   - 建议：用 `pyo3::ffi::PyList_Append` 直接 C API（对 ListContainer 子类等价），~10ns/调用
   - 阻塞性：否（影响 ~15ns/元素，对 100 元素 array ~1.5µs）
