## 补充验证：用户层级性能对比基准（S-PERF 用户视角）

> 本节为 Phase 15 验收遗漏项的紧急补测。S-PERF 要求 ≥1.0x 对比，
> 但 15.1 仅测量了 Rust 端 cargo bench 绝对性能，从未在 Python 用户
> 层级测量新旧路径与 Python 原版的对比。本节填补该空白。

| 项目 | 内容 |
|------|------|
| 状态 | 已完成（数据已采集） |
| 负责人 | DEV |
| 完成时间 | 2026-06-19 |
| 基准文件 | `construct-py/tests/test_perf_comparison.py`（新建） |

### 测试设计

三路对比（5000 次迭代，time.perf_counter 计时，GC 禁用）：

- **Path A — python_original**：上游 Python `construct` 包（参考基准）
- **Path B — old_ffi**：`Struct(...).parse(data)` / `.build(obj)` 走
  `impl_api_methods!` → `api::py_parse`（per-op FFI + Value 树转换）
- **Path C — new_compiled**：`compile_schema(fmt)` →
  `holder.parse_bytes_py(data)` / `build_from_py(obj)` 走 direct-to-Python
  编译树（无 Value::Container 中间树）

三种复杂度格式：
- `simple`：3 字段扁平 Struct（10 字节）
- `nested`：2 级嵌套 Struct（14 字节）
- `array_heavy`：100 元素 Array<Int32ub>（404 字节）

### 完整数据（5000 iterations）

```
[simple]
  python_original   parse 0.0150s  build 0.0139s   (reference)
  old_ffi           parse 0.0403s  build 0.0818s   0.37x parse   0.17x build
  new_compiled      parse 0.0326s  build 0.1034s   0.46x parse   0.13x build
  new vs old speedup                              1.24x parse   0.79x build

[nested]
  python_original   parse 0.0306s  build 0.0288s   (reference)
  old_ffi           parse 0.0938s  build 0.2191s   0.33x parse   0.13x build
  new_compiled      parse 0.0844s  build 0.2558s   0.36x parse   0.11x build
  new vs old speedup                              1.11x parse   0.86x build

[array_heavy]
  python_original   parse 0.1384s  build 0.1416s   (reference)
  old_ffi           parse 1.1736s  build 3.5537s   0.12x parse   0.04x build
  new_compiled      parse 1.1608s  build 4.0393s   0.12x parse   0.04x build
  new vs old speedup                              1.01x parse   0.88x build

Geomean new vs py: parse 0.260x  FAIL | build 0.079x  FAIL
```

### 关键结论

1. **S-PERF ≥1.0x 标准：❌ 未达到**。new_compiled 相对 Python 原版
   几何平均 parse 仅 0.260x、build 仅 0.079x（即仍比 Python 慢约 4x / 13x）。

2. **新路径 vs 旧路径**：parse 有微弱加速（1.01–1.24x），build 反而
   **更慢**（0.79–0.88x）。Phase 11–15 的 direct-to-Python 重构**未能
   解决 per-operation FFI 瓶颈**。

3. **根因分析**：new_compiled 虽避免了 `Value::Container` 中间树，
   但仍对每个字段做一次 Python C API 调用（PyDictSink 逐字段写入 /
   PyInput 逐字段惰性读取）。对于 array_heavy（100 元素），FFI 调用
   数量与旧路径相当，故几乎无收益（1.01x）。build 路径的惰性读取
   开销（属性查找 + 类型转换）反而拖慢了整体。

4. **与 15.1 结论的关系**：15.1 的 cargo bench 测量的是 Rust 内核
   `Construct` trait 绝对性能（µs 级），未含 PyO3 FFI 开销。本基准
   在 Python 用户层级测量，揭示了 FFI 开销主导了端到端耗时——这正是
   15.1 遗漏的部分。
