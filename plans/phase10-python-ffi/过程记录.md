### ARCH 设计说明

- **PyConstruct API**：共享 helper 函数方案（py_parse/py_build 等 7 个），各 #[pyclass] 构造器委托
- **PyStream**：持有 `Py<PyAny>`，Stream 方法内用 `Python::with_gil` 获取 GIL 调用 Python read/write/seek/tell
- **Context→Container**：递归转换，parent 链写入 `["_"]` 键

### ARCH 设计说明

- **核心决策：纯 Python 方案替代 PyO3**。原版 Container 使用 `self.__dict__ = self` trick 使属性-下标完全等价并支持 method shadowing（`c['update'] = 42` 后 `c.update == 42`）。PyO3 `extends=PyDict` 模式下实例 `__dict__` 与 dict 数据分离，无法原生实现此 trick；需覆盖 `__getattribute__` 并手动实现描述符 fallback，复杂度高且有递归风险。纯 Python 逐行移植原版代码可零差异复刻全部行为
- **Container 类**：继承 dict，`__init__` 中 `self.__dict__ = self`。属性-下标双访问由 trick 自动实现。method shadowing 天然支持（实例字典优先于类型方法）。`__repr__`/`__str__` 受 `@recursion_lock` 保护。`__eq__` 顺序无关、跳过 `_` 前缀键、与普通 dict 可互比。search/search_all 正则搜索（`re.match` 匹配键名）

- **全局打印标志**：3 个模块级变量 + 3 个 setter 函数。只影响 `__str__`，不影响 `__repr__`
- **辅助函数**：`recursion_lock` 装饰器（防 `__repr__`/`__str__` 无限递归，finally 清理确保不残留）、`value_to_string`（bytes 16 字节/str 32 字符截断，EnumInteger/HexDisplayedBytes 类名识别）

**2. [应修复 — 逻辑问题] `collect_subcons_for_merge` 运算符展开逻辑与 Python 不一致**

`constructs_composite.rs:23-56` 的 `collect_subcons_for_merge` 函数同时展开 PyStruct 和 PySequence，但 Python 原版的运算符语义不同：
- `__add__`（core.py:764）：`lhs = self.subcons if isinstance(self, Struct) else [self]` — **仅展开 Struct**
- `__rshift__`（core.py:772）：`lhs = self.subcons if isinstance(self, Sequence) else [self]` — **仅展开 Sequence**

**影响**：
- `seq + byte`：Python → `Struct(seq, byte)`（2 个匿名条目）；当前实现 → `Struct(seq_field1, seq_field2, ..., byte)`（seq 被错误展开）
- `struct >> byte`：Python → `Sequence(struct, byte)`（2 个条目）；当前实现 → `Sequence(struct_field1, ..., byte)`（struct 被错误展开）

**不影响的场景**（常见用法，工作正确）：
- `struct + struct` → 正确合并（两侧都是 Struct，展开正确）
- `byte + byte` → 正确（两侧都不是 Struct/Sequence，作为单个条目）
- `seq >> seq` → 正确合并（两侧都是 Sequence，展开正确）

**建议修复**：将 `collect_subcons_for_merge` 拆分为两个函数，或在调用时传入期望类型参数：
```rust
// make_struct_from_add 中只展开 PyStruct
// make_sequence_from_rshift 中只展开 PySequence
```
此问题不导致崩溃或数据损坏，但产生与 Python 结构不同的结果。**非阻塞 10.5/10.6 验收**，但应在 10.10 测试套件运行前修复（可能影响 `test_from_issue_244` 等跨类型运算符测试）。

**3. [不阻塞 — 性能观察] extract_subcon 纯 duck typing 导致多层 PyConstructAdapter 嵌套**

当前 extract_subcon 对所有含 parse_stream+build_stream 的对象（包括 PyO3 包装类）都包装为 PyConstructAdapter。例如 `Struct("a" / Byte)` 中：
- field "a" 的 Rust construct 为 `PyConstructAdapter → PyRenamed → Renamed(PyConstructAdapter → PyFormatField)`

每次 field parse 需穿越多层 GIL 边界 + BytesIO 创建。对于 N 个 field 的 Struct，每个 field parse 都执行 read_remaining（读取全部剩余字节）+ BytesIO + tell + seek，总流读取量为 O(N × D)。

功能正确，但性能不理想。设计文档 §1.5 预留了"PyO3 类型快速路径"方案。**Phase 10 优先正确性，性能优化可推迟**。建议在 10.10 测试套件验证通过后，评估是否需要优化（如果测试通过率受性能影响）。

#### ❌ 逻辑正确性 — 发现 1 个严重逻辑错误

**问题 1（严重 — 驳回项）：py_mapping 键值对交换方向错误**

- **文件**：`construct-py/src/constructs_adapter.rs:537-543`
- **现象**：Python dict 的 key/value 被错误交换后传入 Rust `Mapping::new`
- **根因分析**：
  - 代码注释（line 539）声称 "Python dict: {raw_value: decoded_value}"
  - **此注释事实错误**。Python 原版 `Mapping(subcon, mapping)` 中 mapping 是**编码（build）映射**，即 `{user_value: raw_value}`。证据：
    - Python core.py:2117 docstring：`":param mapping: dict, for encoding (building) mapping"`
    - Python core.py:2131-2134：`self.encmapping = mapping`（dict 直接作为编码映射）
    - Python core.py:2124 示例：`Mapping(Byte, {x:0})` → `build(x)` 写 0，`parse(0)` 返回 x
  - Rust `Mapping::new(subcon, mapping)` 的 mapping 参数是 `(build_key, build_value)` 对，其中 build_key = 用户值，build_value = 原始值（见 enum_.rs:334 docstring）
  - **正确实现应直接 `pairs.push((k, v))` 不交换**，与设计文档 §4.1（line 881-885）一致
- **影响**：所有 Mapping 操作方向反转。以 `Mapping(Byte, {"on": 1})` 为例：
  - 预期：`parse(b"\x01")` → "on"；`build("on")` → `b'\x01'`
  - 实际：`parse(b"\x01")` → **MappingError**（decmapping 中找不到 key=1）；`build("on")` → **MappingError**（mapping 中找不到 key="on"）
- **修复建议**：删除交换逻辑，直接传递 `(key, val)`：
  ```rust
  for (key, val) in mapping.iter() {
      let k = py_to_value(py, &key)?;  // build key (user-facing value)
      let v = py_to_value(py, &val)?;  // build value (raw value)
      pairs.push((k, v));
  }
  ```
- **DEV 设计质疑 #6 判定**：DEV 声称 "Python dict `{raw: decoded}`" 的前提错误，导致引入了本不需要的交换。设计文档 §4.1 的原始实现是正确的，DEV 的"修正"反而引入了 bug。

### ARCH 设计说明

**核心决策 — 字符串构造器混合策略**：
- `PaddedString`/`CString` → PyO3 包装 Rust 内核（已实现，性能优先）
- `PascalString`/`GreedyString` → 纯 Python macro（`StringEncoded(Prefixed/GreedyBytes, enc)`，与原版 macro 风格一致，不修改 Rust 内核）
- `StringEncoded` Adapter 逐行移植原版 `core.py:1711-1744`

**核心决策 — 编码名映射**：Rust `StringEncoding`(8标准名) ↔ Python `possiblestringencodings`(13别名)，PyO3 层 `encoding_name_to_enum()` 做归一化（lowercase + `-`→`_`）

**核心决策 — Gallery 暴露**：通用 `PyGalleryParser`(Box<dyn Construct> 包装) + 3 个 pyfunction 工厂；Python 侧 `gallery/` 子包对齐原版导入路径

**核心决策 — lib 子模块**：4 个纯 Python 子模块逐行移植（binary/py3compat/hex/bitstream），循环依赖规避（binary 显式 import py3compat 子模块）

**核心决策 — debug.py**：stub 实现（Probe/Debugger 继承 _adapter 基类，printout/handle_exc 逐行移植，测试跳过）

**边界条件**：36 个边界条件（字符串16 + Gallery5 + lib15），详见设计文档 §6

**API 映射覆盖**：
- 字符串构造器：4/4 全部映射（PaddedString/CString PyO3，PascalString/GreedyString 纯Python）
- Gallery：3/3 全部映射（elf/pe32file/UTIndex）
- lib/binary：11 函数 + 3 缓存，全部映射
- lib/py3compat：3 常量 + 1 缓存 + 5 函数 + 8 弃用常量，全部映射
- lib/hex：5 类 + 2 常量 + 2 函数，全部映射
- lib/bitstream：2 类，全部映射
- debug：2 类（Probe/Debugger），全部映射

#### 严重问题（驳回 — 必须修复）

**问题 1：_stream.py 双路径缺失（6 个纯 Python 类全受影响）**

- **位置**：`construct-py/construct_rust/_stream.py` line 66, 108, 140, 147, 184, 199, 209, 278, 291, 317, 320
- **现象**：NullTerminated / NullStripped / RestreamData / ProcessXor / ProcessRotateLeft / OffsettedEnd 的 `_parse` / `_build` 方法直接调用 `self.subcon._parsereport(BytesIO(data), context, path)`，但 Rust PyO3 包装类（通过 `impl_api_methods!` 宏）只有 `parse` / `parse_stream` / `build` / `build_stream` / `sizeof` 这 7 个方法，**没有 `_parsereport`**。当 subcon 为 Rust 包装（最常见用法：`NullTerminated(GreedyBytes)`、`ProcessXor(0xf0, Byte)` 等）时抛出 `AttributeError`。
- **根因**：`_adapter.py` 的 `Subconstruct` 基类已实现双路径机制（`_adapter.py` line 141-146：`hasattr(self.subcon, "_parsereport")` 检查 + `parse_stream` fallback），但 `_stream.py` 的 6 个类**覆盖了 `_parse` / `_build` 且未使用双路径**，直接硬编码调用 `_parsereport`。
- **影响**：6 个纯 Python 构造器在最常见的用法下（subcon 为 Rust 包装）完全不可用。
- **建议修复**：在 `_stream.py` 中添加双路径辅助函数，或将 `self.subcon._parsereport(BytesIO(data), context, path)` 替换为双路径调用：
  ```python
  def _sub_parse(self, data, context, path):
      from io import BytesIO
      stream = BytesIO(data)
      if hasattr(self.subcon, "_parsereport"):
          return self.subcon._parsereport(stream, context, path)
      else:
          from ._adapter import _filter_context
          contextkw = _filter_context(context)
          return self.subcon.parse_stream(stream, **contextkw)
  ```
  同理为 `_build` 添加双路径。所有 6 个类的 `_parse` / `_build` 方法都需更新。

**问题 2：Lazy callable 包装完全不可用**

- **位置**：`construct-py/src/constructs_stream.rs` line 828-839（`wrap_as_zero_arg_callable`）
- **现象**：`Lazy(Byte).parse(b"\x41")` 返回一个 Python lambda（`callable=True`），但调用该 lambda 时抛出 `NameError: name '_v' is not defined`。
- **根因**：`py.eval_bound("lambda *a, **k: _v", None, Some(&locals))` 中，`locals` dict 里的 `_v` **不会成为 lambda 的闭包变量**。Python 的 `eval` 中 locals 参数仅在 eval 表达式本身求值时可见，但 lambda 内部的名字查找发生在**调用时**，且 lambda 的作用域是定义时的 globals + enclosing 函数作用域，**不包含 eval 的 locals dict**。因此 `_v` 在调用时找不到。
- **影响**：`Lazy(subcon).parse(data)` 返回的 callable 调用时必定失败。Python 原版 `Lazy` 的核心语义（`x = d.parse(data); x()`）完全不可用。
- **建议修复**：将 `_v` 放入 globals dict（而非 locals），或用默认参数捕获，或用 `functools.partial`：
  ```rust
  // 方案 A：用 globals
  let globals = PyDict::new_bound(py);
  globals.set_item("_v", value)?;
  py.eval_bound("lambda *a, **k: _v", Some(&globals), None)

  // 方案 B：默认参数捕获（_v 在 lambda 创建时从 locals 求值）
  py.eval_bound("lambda *a, _v=_v, **k: _v", None, Some(&locals))
  ```

**问题 3：BitStruct 嵌套失败（subcon_obj 存储类型对象而非实例）**

- **位置**：`construct-py/src/constructs_stream.rs` line 1248-1254（`py_bit_struct`）
- **现象**：`Struct("x" / BitStruct("a" / Byte)).parse(b"\x41")` 抛出 `TypeError: descriptor 'parse_stream' for 'Struct' objects doesn't apply to a '_io.BytesIO' object`。
- **根因**：`py_bit_struct` 的 `subcon_obj` 字段存储的是 `PyStruct` 的**类型对象**（`py.get_type_bound::<PyStruct>()`，即类本身），而非创建的 `py_struct` 实例。当 `BitStruct` 的结果被嵌套到需要 `make_owned` 的构造器（如 `Struct` / `Sequence`）时，`PyBitwise.make_owned()` 调用 `extract_subcon(self.subcon_obj)`，传入类型对象，`extract_subcon` 尝试在类型对象上调用 `parse_stream`，但 Python 描述符协议要求 `parse_stream` 通过实例调用，类型对象上调用导致 `TypeError`。
- **影响**：`BitStruct` 结果无法嵌套使用（`Struct("x" / BitStruct(...))`、`Sequence(BitStruct(...))`、`Array(3, BitStruct(...))` 等全部失败）。非嵌套直接使用正常（Test 7 PASS）。
- **建议修复**：将 `py_struct` 实例（而非类型对象）存入 `subcon_obj`。需重构 `py_bit_struct`，先用 `Py::new(py, py_struct)` 创建 Python 对象再提取 inner：
  ```rust
  let py_struct_obj = Py::new(py, py_struct)?;  // 先创建 Python 对象
  // 从 py_struct_obj 借用 inner 构造 Bitwise
  let sc = py_struct_obj.borrow(py).as_construct_owned();  // 需要某种方式获取 owned
  Ok(PyBitwise {
      inner: Bitwise::new(sc),
      subcon_obj: py_struct_obj.into_any(),  // 存实例
  })
  ```
  或者在 `make_owned` 中特殊处理类型对象场景。

### `[设计质疑]` BitStruct 场景 5/7 的 Byte vs BitsInteger(8)

经独立运行 Python 原版 construct 验证：
- `BitStruct("a" / Byte).parse(b"\x41")` 在 Python 原版中 **ERROR**（`stream read less than specified amount, expected 1, found 0`）
- `BitStruct("a" / BitsInteger(8)).parse(b"\x41")` 在 Python 原版中 → `Container(a=65)` ✅
- 原因：`Byte`（FormatField ">B"）在 Bitwise 位流中读取 1 个"字节"= 1 个位值（0 或 1），而非 8 位整数值。`BitsInteger(8)` 才是读取 8 位并组装为整数的正确构造器
- Rust FFI 行为与 Python 原版一致：`BitStruct("a"/Byte)` 不崩溃（返回首位值），比 Python 原版更 graceful
- **修复后的 7 个场景全部通过**（场景 5/7 使用 `BitsInteger(8)` 替代 `Byte` 验证 BitStruct 嵌套/非嵌套正确性）
