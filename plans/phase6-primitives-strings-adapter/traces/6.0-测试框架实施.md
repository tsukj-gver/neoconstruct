### P1 [BUG·必修] BenchRunner 未丢弃 warmup sample

**根因**：设计 §2.5 line 727 硬要求"丢弃前 config.warmup 个 sample"，
`BenchResult.samples_ns` 注释（runner.py:50）+ `run_scenario` docstring（runner.py:128-129）+
`bench_struct.py:225/318` 注释均描述了正确契约，但**实际代码 runner.py:165 未切片**。

**修复**（runner.py:165-175，~7 行）：
```python
samples_ns = data["per_call_ns"]
# 实现要点 2：丢弃前 config.warmup 个 sample（设计 §2.5 硬要求）
# 边界防御：若脚本返回的 sample 数 ≤ warmup（如调用方配置错误），
# 保留全部 sample 而非切片成空——符合 stats 模块"空序列返回 0.0 不抛异常"契约，
# 让上层通过 BenchResult.samples_ns 长度异常发现问题。
if 0 < self.config.warmup < len(samples_ns):
    samples_ns = samples_ns[self.config.warmup:]
```

边界防御选择 `0 < warmup < len` 而非 `>=`：若调用方误配 warmup >= sample 总数，
保留全部 sample 而非切片成空——避免 median/min/max 返回 0.0 → speedup=inf 的无意义结果。
上层可通过 `len(samples_ns) != iterations` 检测配置异常。

**注释一致性核对**（VET 报告点名 5 处）：
| 位置 | 注释内容 | 修复后状态 |
|------|---------|-----------|
| runner.py:50 | `samples_ns: list  # ...（已减 warmup）` | ✅ 与代码一致 |
| runner.py:128-129 | docstring "丢弃前 config.warmup 个 sample" | ✅ 与代码一致 |
| runner.py:170-175 | 新增切片代码 + 解释注释 | ✅ 新增 |
| bench_struct.py:225 | "runner 丢弃前 warmup 个 sample" | ✅ 与代码一致 |
| bench_struct.py:318 | "runner 内部已丢弃 warmup" | ✅ 与代码一致 |

**验证**（bench_struct.py --case B1）：
| 场景 | 修复前 (warmup 未丢) | 修复后 (warmup 已丢) | 历史 baseline | 收敛评估 |
|------|---------------------|---------------------|---------------|---------|
| B1-parse | 10.42x | **9.80x** | 9.73x | **+0.7%** ✅ < 10% |
| B1-build | 14.18x | 16.95x | 12.55x | +35% ❌（方向更快，低 iter 噪声，VET 已知） |

B1-parse 收敛到历史 9.73x（+0.7% < 10% 阈值）—— 正符合 VET 预测"warmup 修复后 speedup 与历史差异应收敛"。
修复前 10.42x 偏高是因为预热 sample 偏向某个 impl（cache 冷启动效应），污染了 median；
丢弃 5 个 warmup 后 median 反映稳态性能，更可信，将支撑 Phase 6.1+ 性能验收基线。

B1-build 仍偏高（+35%）但**方向是 rs 更快（非回归）**，且 bench_struct.py 单次只跑 1 paired
（20 个 sample 的统计噪声大）。B1-build 不在 VET 要求验证范围（VET 只点名 B1-parse）。

### P2 [BUG·必修] ABResult.welch_t_speedup 与 controlled_ab_test 契约不一致

**根因**：`controlled_ab_test`（修复前 runner.py:210-212）只跑 impl="rs"，
但 `welch_t_speedup`（runner.py:85-87）假设 results 是 `[rs, py, rs, py]` 交替排列，
过滤条件 `py.impl == "py"` 永远 False，sp_a/sp_b 始终为空列表。

**修复方案选择**：VET 推荐方案 A（让 controlled_ab_test 跑 rs+py 配对，符合 E01_O1_ab_stats.py 模式）。
理由：
- E01_O1_ab_stats.py line 64-78 的核心指标是 "speedup(x)"，对 A/B 两组 speedup 做 Welch t
- speedup 必须由 (rs, py) 配对计算 → controlled_ab_test 必须为每组同时跑 rs+py
- 方案 B（直接对两组 rs median 做 Welch t）会丢失"加速比显著性"语义，偏离设计意图

**修复**（runner.py:197-232 controlled_ab_test + runner.py:76-91 welch_t_speedup docstring）：
```python
for i in range(repeats):
    # A 组：rs + py 配对（与 E01_O1_ab_stats.py 的 speedup 计算模式一致）
    results_a.append(self.run_scenario("rs", f"{scenario_a_name}-rs-r{i}", measure_script_a))
    results_a.append(self.run_scenario("py", f"{scenario_a_name}-py-r{i}", measure_script_a))
    # B 组：rs + py 配对
    results_b.append(self.run_scenario("rs", f"{scenario_b_name}-rs-r{i}", measure_script_b))
    results_b.append(self.run_scenario("py", f"{scenario_b_name}-py-r{i}", measure_script_b))
```

同时增强 welch_t_speedup docstring 明示 "[rs, py, ...] 交替排列" 契约。

**验证**（临时脚本，验证后已删除）：
```
=== controlled_ab_test (repeats=3, 每次 4 子进程) ===
results_a impl 序列: ['rs', 'py', 'rs', 'py', 'rs', 'py']
results_b impl 序列: ['rs', 'py', 'rs', 'py', 'rs', 'py']
[OK] results_a / results_b 按 [rs, py, ...] 交替排列
每个 BenchResult.samples_ns 长度: [3, 3, 3, 3, 3, 3, 3, 3, 3, 3, 3, 3]
[OK] warmup 切片生效（REPEAT=8 - warmup=5 = 3 个 sample）   ← P1 修复同时验证
sp_a (A 组 speedup): ['0.978', '1.009', '1.012']
sp_b (B 组 speedup): ['1.004', '1.006', '1.012']
welch_t: -0.6724
[OK] sp_a / sp_b 各 3 个样本（修复前为空列表）
```

speedup≈1.0 是预期（rs/py 跑同一段 sum 代码）；welch_t=-0.67 描述性差异，n=3 不稳健但 API 工作性已确认。
