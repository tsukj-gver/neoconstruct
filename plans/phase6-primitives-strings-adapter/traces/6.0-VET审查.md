### P1 [BUG·必须修复] BenchRunner 未丢弃 warmup sample（契约违反 + 注释撒谎）

**涉及文件**：
- `bench/_helpers/runner.py:165`（实际代码）
- `bench/_helpers/runner.py:50`（BenchResult 字段注释："samples_ns: list # 每次 iteration 的 per-call ns（**已减 warmup**）"）
- `bench/_helpers/runner.py:125`（run_scenario docstring："2. 丢弃前 config.warmup 个 sample"）
- `bench/bench_struct.py:225`（注释："runner 丢弃前 warmup 个 sample"）
- `bench/bench_struct.py:318`（注释："runner 内部已丢弃 warmup，这里再确认"）

**问题**：
设计文档 §2.5 run_scenario 实现要点 2 硬要求"丢弃前 config.warmup 个 sample"。BenchRunner.run_scenario 的 docstring（runner.py:124-127）和 BenchResult.samples_ns 字段注释（runner.py:50）都声称已经做了丢弃。

但实际代码（runner.py:165）：
```python
samples_ns = data["per_call_ns"]   # 直接使用全部 25 个 sample，未切片
return BenchResult(
    ...
    samples_ns=samples_ns,
    median_ns=median(samples_ns),  # 对全部 25 个求统计
    ...
)
```

bench_struct.py 的 `_MEASURE_SCRIPT` 子进程返回 `iterations + warmup = 25` 个 sample（line 227 `timer.repeat(repeat=REPEAT, number=NUMBER)`，REPEAT=25），bench_struct.py 主循环 line 318 注释说"runner 内部已丢弃 warmup"——**实际 runner 没做**。

**影响**：
1. bench 统计包含 5 个预热 sample，median/mean/stdev/min/max 全部受污染
2. 多处注释撒谎，下游 DEV 读注释会被误导（误以为 samples_ns 只有 20 个）
3. 当前 bench_struct.py 报告 speedup +7%/+13% 可能在容忍范围，但 warmup 概念失效使 bench 数据可信度受损，无法支撑 Phase 6.1+ 性能验收

**修复建议**（DEV 返工）：
```python
# runner.py run_scenario 内，line 165 改为：
samples_ns = data["per_call_ns"]
if self.config.warmup > 0 and len(samples_ns) > self.config.warmup:
    samples_ns = samples_ns[self.config.warmup:]
# 同时修正 BenchResult.samples_ns 注释保持一致
```

并删除/修正 bench_struct.py:318 的错误注释。

### P2 [BUG·必须修复] ABResult.welch_t_speedup 与 controlled_ab_test 契约不一致

**涉及文件**：`bench/_helpers/runner.py:85-91`（welch_t_speedup）vs `runner.py:208-218`（controlled_ab_test）

**问题**：
`controlled_ab_test`（line 211-212）只跑 impl="rs"：
```python
results_a.append(self.run_scenario("rs", f"{scenario_a_name}-r{i}", measure_script_a))
results_b.append(self.run_scenario("rs", f"{scenario_b_name}-r{i}", measure_script_b))
```

但 `ABResult.welch_t_speedup`（line 85-87）假设 results_a 是 `[rs, py, rs, py, ...]` 交替排列：
```python
sp_a = [speedup_ratio(r.median_ns, py.median_ns)
        for r, py in zip(self.results_a[::2], self.results_a[1::2])
        if r.impl == "rs" and py.impl == "py"]
```

由于 results_a 全是 rs（无 py），过滤条件 `py.impl == "py"` 永远 False，sp_a/sp_b 始终为空列表。调用 `welch_t([], [])` 返回 0.0（无意义）。

**影响**：
- 当前 6.0 未调用 controlled_ab_test（bench_struct.py 只用 run_paired），不影响 6.0 验收
- 但这是为 Phase 6.1+ 性能优化对比（O1 on/off）预留的 API，契约不一致会使下游 DEV 踩坑

**修复建议**（DEV 返工）：
方案 A（改 controlled_ab_test 同时跑 rs+py，符合 E01_O1_ab_stats.py 的配对模式）：
```python
for i in range(repeats):
    results_a.append(self.run_scenario("rs", f"{scenario_a_name}-rs-r{i}", measure_script_a))
    results_a.append(self.run_scenario("py", f"{scenario_a_name}-py-r{i}", measure_script_a))
    # 同理 results_b
```
方案 B（改 welch_t_speedup 直接对两组 rs median 做 Welch t 检验，不计算 speedup）：
```python
def welch_t_speedup(self):
    medians_a = [r.median_ns for r in self.results_a if r.impl == "rs"]
    medians_b = [r.median_ns for r in self.results_b if r.impl == "rs"]
    return welch_t(medians_a, medians_b), medians_a, medians_b
```
推荐方案 A（与 E01 经验一致，能算 speedup 显著性）。

### P4 [建议·不阻断] 容错 fixture 缺 skip 数量断言

**涉及文件**：`tests/parity/test_phase4_array_parity.py:528-548` + `test_phase3_bitstream_parity.py:264-284`

**问题**：
当前容错 fixture（偏离 2）的设计是"broken case 记录 error，test 函数 skip"。但 `test_parity_all_cases_collected` 只断言 case_id 存在 dict 中，**未断言 error 数量上限**。

风险场景：假设 A1 case 在 construct-rs 升级后意外 broken，fixture 会静默记录 error，所有 A1 测试 skip，**问题被隐藏**，无任何信号告警。

**建议**（DEV 返工）：
在 `test_parity_all_cases_collected` 加断言：
```python
def test_parity_all_cases_collected(parity_results):
    for case_id, _ in ALL_CASES:
        assert case_id in parity_results
        assert "rs" in parity_results[case_id]
        assert "py" in parity_results[case_id]
    # 新增：已知 broken case 白名单（防止静默 skip 扩散）
    KNOWN_BROKEN = {"R1", "R2", "R3"}  # phase4 ADR-014
    actual_errors = {cid for cid, e in parity_results.items()
                     if "error" in e.get("rs", {}) or "error" in e.get("py", {})}
    unexpected = actual_errors - KNOWN_BROKEN
    assert not unexpected, f"意外 broken case（非已知白名单）: {unexpected}"
```

### P6 [信息·不阻断] 设计文档 §5.3 注意点 1 转义规则错误

**涉及文件**：`docs/design/基础设施/测试框架设计.md:1477`（设计文档自身）+ DEV 实现 `test_phase3_bitstream_parity.py:79` 等

**问题**：
设计 §5.3 注意点 1 硬要求："`_CASE_DEFINITIONS` 内若含 bytes 字面量（如 `b"\\x42"`），字符串内必须写 **4 个反斜杠** `\\\\x42`"。

实际转义链分析（已验证）：
1. 父进程 Python 解析三引号字符串 `'''...b"\\xA5"...'''` → 字符串值含 `b"\xA5"`（**2 个反斜杠足够**）
2. `PARITY_SCRIPT_TEMPLATE.format(case_definitions=...)` 注入，子进程脚本含 `b"\xA5"`
3. `subprocess.run([python, "-c", code], text=True)` 把字符串原样传给子进程（**text=True 不做二次转义**）
4. 子进程 `-c` 执行 `b"\xA5"` → 字节 0xA5 ✅

DEV 在 phase3 用 2 反斜杠（如 line 79 `b"\\xA5"`），phase3 全部 13 case PASS 验证正确。设计文档的"4 反斜杠"规则是错的（高估了转义层数）。

**建议**：PM 协调 ARCH 修正设计文档 §5.3 注意点 1 为"2 个反斜杠"。DEV 实现正确，不需返工。
