## 2. PM 决策 2 双层分离严格落实审查（§0 合规硬要求）

### 约束 1：类型层面分离（不共享内部实现）

| 层 | Rust Node 变体 | Python 类型 |
|----|--------------|-------------|
| 内置 Adapter（5 个） | SubstructNode / PeekNode / RawCopyNode / RebuildNode / PassNode（**各自独立 struct**，不共享内部实现） | SubconstructDescriptor / PeekDescriptor / RawCopyDescriptor / RebuildDescriptor / PassDescriptor（独立描述符） |
| 用户面 Adapter | AdapterCallbackNode（独立 struct） | Adapter / SymmetricAdapter / AdapterDescriptor（Python 基类） |

✅ **严格落实**：内置与用户面从 Rust 类型上就是不同 Node 变体，不共享内部实现。

### 约束 2：用户面 Adapter 在 Python 层

- ✅ Adapter / SymmetricAdapter / AdapterDescriptor 在 `_adapters.py` Python 层定义（用户继承写 _decode/_encode）
- ✅ Rust 仅提供 AdapterCallbackNode 最小钩子（PM 决策 6.3-D1 接受范围）
- ✅ Rust 不背"通用用户回调"包袱：AdapterCallbackNode 仅识别 Adapter 子类实例（type name + duck typing），不接收任意 callable（与 RepeatUntil v5 同硬约束，设计 §4.5 论证）

### §0 原则对照（设计 §7 表 + VET 独立审）

| §0 原则 | 内置 5 Node | AdapterCallbackNode | VET 验证 |
|---------|------------|---------------------|---------|
| #1 一次 FFI | ✅ 严格 1 次（Rust Node 内部完成） | ⚠️ 2 次（parse 入口 + _decode 回调）。**不违反**——用户主动继承 Adapter = 显式接受折衷（PM 决策 2 + 设计 §4.4 论证） | ✅ 论证成立 |
| #2 无中间表示层 | ✅ Substruct 透传；RawCopy PyDict；Peek 纯 Rust；Rebuild ExprProgram；Pass 无数据 | ✅ _decode/_encode 操作用户域 Python 对象，非 Rust 中间类型 | ✅ |
| #3 输入输出无 trait 抽象层 | ✅ 仅 Box<Node>（与 Bitwise/Bytewise/Transform 同模式） | ✅ Box<Node> + Py<PyAny>，无新 trait | ✅ |
| #4 pyo3 核心依赖 | ✅ 全部用 pyo3 直接操作 PyObject | ✅ Py<PyAny> 引用 _decode/_encode | ✅ |
| #5 mashumaro API | ✅ 不破坏 StructMixin 用户面 | ✅ 用户继承 Adapter 写 _decode/_encode（Python 原生） | ✅ |
| #6 enum_dispatch 静态分派 | ✅ 5 个新 Node 加入 enum | ✅ AdapterCallbackNode 加入 enum | ✅ |
| #7 Result+ConstructError | ✅ 所有方法返回 Result，错误带 path | ✅ _decode/_encode 异常跨 FFI 转 Generic 带 path | ✅ |
| #8 Stream 纯 Rust 内部 | ✅ Peek 用 ParseStream::seek；RawCopy 用 tell+read+seek | ✅ AdapterCallback 不直接操作 Stream（subcon 在 Rust 内） | ✅ |

**L-01 对策**：本设计无中间表示层违反（RawCopy 用 PyDict 直接构造，与 StructNode 用 __dict__ 同脉络，ADR-008 验证）；无双向 trait 抽象层（仅 Box<Node> 单向递归）。

**结论**：§0 合规 ✅，PM 决策 2 双层分离严格落实 ✅。

## 3. DEV 3 项偏离评估

### 偏离 4.1：duck typing 识别策略 — **可接受**（建议同步修正文档）

**设计 §6.3**：compile.rs 通过 `type_name == "AdapterDescriptor"` 识别用户面 Adapter。
**实施**（compile.rs L705-727, L1700-1724）：双重识别策略：
1. type name == "AdapterDescriptor"（直接分支，设计原始方案）
2. `is_adapter_like(desc)` duck typing：hasattr + callable 检查 _decode 和 _encode

**VET 评估**：
- ✅ **鲁棒性提升**：用户继承 `class HexAdapter(Adapter)` 子类，type name 是 "HexAdapter" 而非 "AdapterDescriptor"，duck typing 自动识别，符合 Python 习惯。
- ✅ **误判风险已论证**（设计 §4.1 + is_adapter_like docstring L1686-1699）：
  - StructMixin 子类（含 `_construct_compiled`）已在 compile.rs 前序分支返回，不会进入 is_adapter_like
  - FormatFieldDescriptor / BytesDescriptor / RebuildDescriptor 等无 `_decode`/`_encode` callable 属性，不会误判
  - 残留风险：用户自定义非 Adapter 类恰好有 callable `_decode`/`_encode` → 误判。但这种场景极少见，且用户主动定义这两个方法大概率就是 Adapter 模式。
- ❌ **文档不一致问题**（**非阻断，建议 ARCH 在 ADR-022 落地时同步修正**）：
  - `_adapters.py` L318-323 AdapterDescriptor docstring 说："compile.rs 当前的实现是按 type name 匹配（"AdapterDescriptor"），**不含 isinstance 检查**" → **错误**（实际是 type name + duck typing）
  - `_adapters.py` L328-339 "**当前实现策略**：compile.rs 同时识别以下两个 type name：AdapterDescriptor / Adapter" → **错误**（实际不识别 "Adapter" type name，而是 is_adapter_like duck typing）
  - `_adapters.py` L339 "或者更优雅的方式：用户子类继承 AdapterDescriptor 而非 Adapter" → **过时建议**（duck typing 已让继承 Adapter 自动工作）
  - 这三处 docstring 描述互相矛盾且与 compile.rs 实际实现不符，会误导用户。建议 ARCH 在沉淀 ADR-022 时一并修正 _adapters.py docstring。

**结论**：duck typing 实施本身可接受（更鲁棒、误判风险已论证），但 _adapters.py docstring 与实际实现严重不一致，**作为 ADR-022 沉淀的 followup**（非阻断本子任务验收）。

### 偏离 4.2：Adapter 单独使用限制 — **可接受**（设计主用例不受影响）

**设计 §4.1**：`adapter.parse(b"...")` / `adapter.build(value)` 顶层入口。
**实施**（`_adapters.py` L188-249）：仅当 subcon 自身有 .parse/.build 方法时工作（嵌套 Adapter 或 StructMixin 子类）。原子描述符（Int8ub）无 .parse 方法。

**VET 评估**：
- ✅ **原因合理**：construct-rs 的原子描述符（Int8ub 是 FormatFieldDescriptor 实例）是无状态"编译期标记"，与 Python construct 的 Construct 对象不同（Python Construct 有 .parse/.build 顶层方法）。这是 §0 双层架构的固有差异，非 DEV 实现错误。
- ✅ **错误信息已优化引导**（`_adapters.py` L211-217）：明确提示"embed Adapter in a Struct: @dataclass class P(StructMixin): v = field(HexAdapter(Int8ub))"，引导用户用推荐用法。
- ✅ **设计主用例不受影响**：设计 §4.2 主要场景就是嵌入 Struct（`field(HexAdapter(Int8ub))`），此场景经 AdapterCallbackNode + compile.rs duck typing 完整工作（parity AC1 验证）。
- ✅ **Phase 7+ 补全路径明确**：DEV §4.2 建议在 `Adapter.parse` 中自动包装 subcon 为匿名 Struct，恢复 Python 兼容性。这是后续优化空间，非本子任务范围。

**结论**：可接受。建议在 ADR-022 中明确此 API 限制 + Phase 7+ 补全计划。

### 偏离 4.3：Rebuild int 常量表达式不支持 — **可接受**（与 Computed 同行为，非偏离）

**设计 §1.4**：func 必须是 Phase 2 表达式（FieldRef/ExprRef/int 组合）。
**实施**：仅 FieldRef/ExprRef 路径工作。int 常量因 Python 侧 `_extract_and_compile_exprs`（`_mixin.py` L609-618）不编译 int 常量（仅 _FieldDescriptor / _ExprRef / 预编译 list 进入 result），导致 Rust 侧 `expr_programs[field_index]` 为空，`build_rebuild_node` 取 "func" 失败 → Compilation error。

**VET 评估**：
- ✅ **与 Computed 同行为一致**：`Computed(42)` 也会失败（int 不被 _extract_and_compile_exprs 编译），需 `Computed(items_count * 2)`。这是 Phase 2 表达式系统的统一行为，非 Rebuild 特有 bug。
- ✅ **设计主用例不受影响**：Rebuild 引用前序字段（`Rebuild(Int8ub, this.items.length)`）是设计 §1.4 唯一主用例（Python L2993-2997 示例同），int 常量场景应用 Const 替代（无业务意义）。
- ✅ **REV 问题 2 已记录**（设计 §5.3 RB-callable）：Rebuild func 收窄为 Phase 2 表达式。
- ❌ **小文档不一致**（**非阻断**）：`_descriptors.py` L1276 RebuildDescriptor._expr_params docstring 说"int 常量也走表达式路径（ExprProgram 包装 Const）" → **错误**（实际不编译 int 常量）。建议同步修正为"int 常量不被编译，应使用 FieldRef/ExprRef"。

**结论**：可接受（与 Computed 一致行为，非偏离）。建议修正 _descriptors.py L1276 docstring。

```rust
        message: format!("Adapter _decode callback failed: {} (path: {})", e, path_str),
        path: path_str,
    })?;
```

**VET 验证**：
- ✅ **subcon.parse 错误正确传播**（L105 `?`）：StreamError / ExprContext 等通过 `?` 向上传播，不进入 _decode 回调
- ✅ **_decode 回调异常跨 FFI 转 Generic**（L123-128）：`call_bound` 返回 Err 时 map_err 转 ConstructError::Generic，message 含原始 Python 异常 + path 字段
- ✅ **测试覆盖 AC-3**（adapter_callback.rs L329-370 `parse_decode_raises_python_exception_returns_generic_error`）：FailingAdapter._decode 抛 ValueError → 转为 Generic 错误，message 含 "decode failed"

**build 路径**（L133-163）：对称设计，_encode 异常同样转 Generic 带 path。

**安全性结论**：✅ 错误处理路径完整，无 panic 风险，所有 Python 异常正确跨 FFI 转换为 ConstructError::Generic 并携带 path 字段（项目硬要求达标）。

### 4.2 duck typing 识别策略误判风险 — ✅（详见 §3 偏离 4.1）

**VET 独立验证误判场景**：

### 4.3 compute_ro_value Rebuild 分支双重求值性能影响 — ✅（可接受，非 bug）

**审查位置**：`rebuild.rs` L102-120（build）+ `mod.rs` L359-364（compute_ro_value）

**RO 字段 build 流程**：
```
StructNode → compute_ro_value(Rebuild) → eval_expr_int(func) [第 1 次] → 写入 context
           → RebuildNode.build(obj=eval_result) → eval_expr_int(func) [第 2 次] → inner.build
```

**VET 评估**：
- ✅ **正确性无问题**：两次求值结果一致（表达式纯函数，无副作用），最终写入字节正确。
- ✅ **与 Python 语义一致**：Python Rebuild._build L3005-3007 `obj = evaluate(self.func, context); return self.subcon._build(obj, ...)`，"build value is ignored"——construct-rs build 忽略 obj 重算，行为对齐。
- ✅ **性能开销可忽略**（设计 §1.4.3 论证）：ExprProgram::eval ~10ns × 2 = ~20ns，vs FormatField build ~30ns，占比 <40%。在 Rebuild 作为 RO 字段的典型场景（如 count 字段），整体开销远小于 FFI 节省。
- ⚠️ **优化空间**（非阻断）：设计 §1.4.3 提到"优化：RebuildNode.build 直接用 obj（不再求值）"，但当前实现仍双重求值。这是性能优化空间，不是 bug。建议作为 Phase 6 性能子任务的 followup（若 benchmark 显示 Rebuild 路径未达 ≥10x）。

**结论**：✅ 双重求值性能影响在设计可接受范围内。优化空间记录为 followup。
