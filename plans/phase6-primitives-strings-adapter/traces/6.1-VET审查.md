## 详细审查清单

### 逻辑正确性 ✅

**VarInt LEB128 编解码**（varint.rs:60-78 / 147-156）：
- parse 循环 `result |= (b & 0x7F) << shift`，shift 从 0 开始每字节 +7，与 Python `core.py:1608-1618` 等价（Python `acc + reversed` 与 Rust `shift += 7` 在小端字节序下数学等价）
- 手工验证 case：`b'\x01'`→1、`b'\x80\x01'`→128、`b'\xff\xff\xff\xff\x0f'`→4294967295，全部与 Python 一致
- 防御：`shift >= 64` 返回 IntegerError（Python 无限精度，Rust u64 限 10 字节）—— 与 Python 行为差异在 i64/u64 边界外，6.1 范围可接受
- build fast-path `varint_encode_u64` 与 Python `_build` 算法逐行等价

**ZigZag 正反变换**（zigzag.rs:64-68 / 92）：
- 反变换 `((zz >> 1) as i64) ^ -((zz & 1) as i64)`：手工验证 zz=5→-3、zz=6→3、zz=0→0、zz=1→-1，全部正确
- 正变换 `((val << 1) ^ (val >> 63)) as u64`：i64 算术右移（负数填充全 1）+ XOR 实现符号位翻转，等价 Python `2*abs(n)-1 if n<0 else 2*n`
- 复用 VarIntNode 字节编解码（`zz_node.parse` / `zz_node.build`），零重复代码

**BytesInteger fast/slow path**（bytes_integer.rs:103-141 / 160-202）：
- fast-path endian/signed 矩阵正确：
  - little endian：data 放 buf 低位（前段），signed 负数时高位填充 0xFF（符号扩展），`u64::from_le_bytes` 还原
  - big endian：data 放 buf 高位（后段），signed 负数时低位填充 0xFF，`u64::from_be_bytes` 还原
- 手工验证 Int24ub/ul/sb 全部边界（含 `\xFF\xFF\xFF`→-1 符号扩展、`\x80\x00\x00`→-8388608 最小负数），全部正确
- slow-path 调用 Python `int.from_bytes`/`int.to_bytes`（kwargs 传 signed，对齐 Python 3.11+ keyword-only API）
- `check_range` 用 i128/u128 中间值避免 bits=64 溢出，signed 范围 `[-2^(8n-1), 2^(8n-1)-1]`、unsigned `[0, 2^(8n)-1]` 正确

**Float half crate**（format_field.rs:352-377）：
- Float16 parse：`half::f16::from_be_bytes(arr).to_f64().into_py(py)`，f16→f64→PyFloat，与 CPython struct 'e' 格式一致
- Float16 build BC-B12 修正：`val.is_finite() && val.abs() > F16_MAX_ABS (65504.0)` 时手动返回 FormatFieldError，对齐 `struct.pack('>e', 70000)` OverflowError
- Float32 build BC-B8：`extract::<f32>` 对 1e40 触发 pyo3 OverflowError→FormatFieldError
- int→float fallback（P2 v2）：extract f32/f64 → i64 as f32/f64 → u64 as f32/f64，对齐 Python `struct.pack('>f', 42)` 接受 int

## DEV 偏离评估

### 偏离 1：sizeof 返回 Generic 而非 Sizeof（设计 §1.4.1 D-5 / §1.4.2）— **可接受**

**设计要求**：VarInt / ZigZag sizeof 返回 `Err(SizeofError)`
**实际实现**：`Err(ConstructError::Generic { ... })`（varint.rs:132 / zigzag.rs:101）

**原因（DEV 标注 [设计质疑]）**：`error.rs` 无 `ConstructError::Sizeof` 变体。设计文档 §1.4.1 line 446-450 代码示例用 `ConstructError::Sizeof { ... }`，但 error.rs 实际无此变体——**设计文档与实现不一致**。

**VET 评估**：
- 项目惯例一致（`GreedyRangeNode` / `PrefixedArrayNode` 变长字段 sizeof 也用 Generic）
- Python 端 `SizeofError` 是 `ConstructError` 子类；Rust Generic 经 `select_exception_class` 映射到 `GenericConstructError`（同为 ConstructError 子类）
- Python 用户面 `except ConstructError` 仍可捕获；仅 `except SizeofError` 不能精确捕获
- **parity 缺陷**：用户无法用 `except SizeofError` 精确区分变长字段错误
- **建议**：后续给 error.rs 加 `Sizeof` 变体并在 `select_exception_class` 加映射（不阻塞 6.1，可与 6.2/6.3 一起做）

### 偏离 2：Python 3.11+ int.to_bytes/from_bytes signed 用 kwargs（设计 §1.5.3-1.5.4）— **必要**

**设计要求**：位置传 3 参数（`from_bytes(bytes, byteorder, signed)`）
**实际实现**：kwargs 传递（bytes_integer.rs:310-318 / 342-350）

**VET 评估**：Python 3.11+ 中 `signed` 是 keyword-only 参数（`*, signed=False`），位置传 3 参数触发 TypeError。这是 Python API 事实，非设计意图偏离。✅ 必要修正。

### 偏离 3：format_field 测试 'f' → 'F' 更新（trace §3.3）— **必要**

Phase 6.1 后 `'f'` 是有效的（Float32Big）。改用 `'F'/'E'/'D'` 验证 None 分支。✅ 必要更新。

## 潜在改进（非阻塞，提示 PM）

### 改进 1：BytesInteger(8, signed=True).build(2^63) fast-path 限制

**问题**：`extract::<i64>` 对 `2^63` 失败（超出 i64::MAX），但 Python `int.to_bytes(8, 'big', signed=True)` 接受（= -2^63 的 two's complement）。
**影响范围**：仅 length=8 + signed=true + 值=2^63 单一边界值
**VET 评估**：用户极少传 2^63 这种边界值，6.1 fast-path 范围限制可接受。设计 §1.5 已明确"fast-path 覆盖主场景"。若未来需要，可对 length=8 + signed + 值超 i64 范围自动 fallback 到 slow-path。

### 改进 2：ZigZag > i64 范围失败

**问题**：ZigZag.build 对超出 i64 的整数返回 IntegerError，Python ZigZag 接受任意大整数
**影响范围**：仅 ZigZag 用于 > i64 整数（罕见，protobuf 通常 int32/int64）
**VET 评估**：设计 §1.4.2 明确"Rust 限 i64"。可接受。

### 改进 3：parity 错误路径 case 覆盖

**问题**：设计 §5 列出的错误 case（BC-B8/B12/D6/D8/F9 等）未进 parity 文件
**现状**：unit test 覆盖 Rust 自身行为，但未对比 Python 错误类型
**VET 评估**：通过代码逻辑分析（实测 `struct.pack` / `int.to_bytes` 行为），Rust 错误行为对齐 Python。但建议 PM 在测试框架设计中加错误路径 parity 模板（`assert_raises` 模式），后续 phase 落地。

### 改进 4：except ImportError: pass 模式

**问题**：`__init__.py:166` 的静默吞 ImportError 模式仍存在
**VET 评估**：trace §7.2 教训已建议加 Python 导入冒烟到 CI。**建议 PM 落地**。
