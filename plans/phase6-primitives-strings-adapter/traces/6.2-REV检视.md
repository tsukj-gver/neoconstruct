## 具体问题详述

### P1：encode 路径引入 Rust String 中转层（§0 #2 违反）— 驳回项

**文档位置**：§2.2.2 `Encoding::encode` + `encode_utf16_32_raw` 签名（设计 L314-394）

**问题**：encode 函数当前对所有编码统一 `obj.downcast::<PyString>()?.to_cow()` 转 Rust `Cow<str>`，utf16/32 分支再传 `&Cow<str>` 给 `encode_utf16_32_raw`。但该函数注释说"使用 `PyUnicode_AsUTF16String`"——该 CPython API 需要的是 PyObject 指针，不是 Rust str。

**§0 #2 违反分析**：
- §0 #2："build 直接从 PyObject 读属性写字节，不在 Rust 侧引入独立的中间数据类型再转换"
- `to_cow()` 对**非 ASCII** PyString（内部 UCS-2/UCS-4 表示）返回 `Cow::Owned(String)`——一次完整的 Rust String 分配 + UTF-8 编码转换（中间数据类型）
- utf16/32 场景几乎都是非 ASCII 内容（否则用 utf8），故 `to_cow()` 在 utf16/32 路径**必定**触发 `Owned` 分配
- 若 DEV 按 `encode_utf16_32_raw` 注释实现（`PyUnicode_AsUTF16String`），需先把 `&Cow<str>` 重新构造成 PyString——`PyString → Cow<str> → PyString → PyBytes` 的荒谬往返（中间表示层再转换的典型）

**对照证据**（现有合规模式，`greedy_bytes.rs:78-87`）：
```rust
let py_bytes = obj.downcast::<PyBytes>()?;  // 直接 downcast
let data = py_bytes.as_bytes();              // 零拷贝借用内部缓冲区
stream.write(data);
```
GreedyBytes 直接操作 PyObject，无 Rust 中间类型——是 §0 #2 的标准实现模式。Strings encode 应参照此模式。

**正确实现方向**：encode 函数应按编码分支处理，utf16/32 直接持有原始 PyObject：
```rust
pub fn encode<'py>(&self, py, obj: &Bound<'py, PyAny>, path) -> Result<Vec<u8>, _> {
    match self {
        Encoding::Utf8 | Encoding::Ascii => {
            // 安全路径：需 &str，to_cow 可接受（ASCII 主导，Borrowed 居多）
            let s = obj.downcast::<PyString>()?.to_cow()?;
            /* utf8/ascii 编码逻辑 */
        }
        Encoding::Utf16Le | Utf16Be | Utf32Le | Utf32Be => {
            // raw FFI 路径：直接用原始 PyString，不经 Cow<str>
            let py_str = obj.downcast::<PyString>()?;  // 仅类型校验，不转换
            self.encode_utf16_32_raw(py, py_str, path)  // 传 &Bound<PyString>
        }
    }
}
```

**建议修改**：ARCH 修订 §2.2.2，将 encode 函数重构为"按编码分支决定是否经 Cow<str>"；`encode_utf16_32_raw` 签名改为接收 `&Bound<PyString>`。同步更新 §6 §0 对照表 #2 行措辞（当前"utf16/32 用 raw FFI 直接产 PyUnicode"只对 decode 成立，encode 方向需补正）。

### P2：utf16/32 raw FFI 实现指引多处错误 — 驳回项

#### P2a：decode byteorder 参数值错误

**文档位置**：§2.2.2 `decode_utf16_32_raw` 注释（设计 L373-376）

**问题**：注释写 `byteorder: i32 = match self { Le => 0, Be => 1 }`。

CPython `PyUnicode_DecodeUTF16(s, size, errors, &byteorder)` 的 byteorder 语义：

| 值 | 含义 |
|----|------|
| `0` | **自动检测 BOM**（开头有 BOM 则消费并按 BOM 序；无 BOM 按本机字节序） |
| `-1` | 强制 Little Endian（不检测 BOM） |
| `+1` | 强制 Big Endian（不检测 BOM） |

用户传 `utf_16_le` 期望"纯 LE 无 BOM"，应 `byteorder = -1`。设计 `Le => 0` 会导致：数据流开头恰好是 `\xff\xfe`（LE BOM）时被误判为 BOM 并消费掉 2 字节，破坏 parity（Python `bytes.decode("utf_16_le")` 不消费 BOM）。

**建议修改**：注释改为 `Le => -1, Be => 1`。同步在 SAFETY 注释中说明"byteorder 非 0 时 CPython 不扫描 BOM，与 Python `utf_16_le`/`utf_16_be` 语义一致"。

#### P2b：from_user_str 丢失 utf16/utf32 无后缀编码的 BOM 语义

**文档位置**：§2.1.2 `from_user_str`（设计 L192-209）

**问题**：Python `possiblestringencodings`（core.py:1695）列出 `utf16`/`utf_16`/`u16`（无后缀）与 `utf_16_le`/`utf_16_be`（有后缀）同为合法编码，但 Python 运行时行为不同：
- `str.encode("utf16")` → 加**本机字节序 BOM**（`b'\xff\xfe...'` 或 `b'\xfe\xff...'`）
- `str.encode("utf_16_le")` → 纯 LE，**无 BOM**
- `bytes.decode("utf16")` → 自动检测 BOM
- `bytes.decode("utf_16_le")` → 强制 LE，不检测 BOM

设计 `from_user_str` 将 `utf16`/`utf_16`/`u16` 全部映射到 `Encoding::Utf16Le`（无 BOM 纯 LE），丢失 BOM 语义。后果：
- `CString("utf16").build("h")`：Python 产出 `b'\xff\xfeh\x00\x00\x00'`（BOM + LE + term），设计产出 `b'h\x00\x00\x00'`（无 BOM）→ **parity 测试 CS-utf16-1 会失败**
- `CString("utf16").parse(b'\xff\xfeh\x00\x00\x00')`：Python 自动检测 BOM 返回 `"h"`，设计（若按 P2a 修正后 byteorder=-1）会把 `\xff\xfe` 当数据解码 → 返回乱码

**两种可行修改方向**（ARCH 选一）：
1. **显式不支持无后缀编码**：`from_user_str` 对 `"utf16"`/`"utf_16"`/`"u16"`/`"utf32"`/`"utf_32"`/`"u32"` 返回 `Err(Compilation)`，错误信息提示"construct-rs 要求显式字节序，请用 utf_16_le/utf_16_be"。同步更新 §5.1 对齐度表（标注 API 表面差异）。
2. **新增 BOM 变体**：Encoding enum 增加 `Utf16Bom`/`Utf32Bom` 变体，实现 BOM 检测/添加逻辑（参考 CPython `PyUnicode_DecodeUTF16` byteorder=0 + `PyUnicode_AsUTF16String` 本机序行为）。

**ARCH 需决策**：方向 1 更简单（6 变体 enum 不变），但破坏 API 兼容（Python `CString("utf16")` 可用，construct-rs 报错）；方向 2 完全兼容但增加 2 变体 + BOM 逻辑复杂度。无论选哪个，当前"静默映射到 Utf16Le 且不文档化"是不可接受的。

## 驳回项逐项复核

### P1 复核：encode 是否真正不经 `Cow<str>` — ✅ 解决

**v1 要求**：encode 按编码分支，utf16/32 直接持有 `&Bound<PyString>` 调 raw FFI，不经 `Cow<str>` 中转。

**v2 证据**（§2.2.2 encode，L392-452）：

1. **encode 顶层分支**（L398-451）按 `match self` 分编码族：
   - `Utf8 | Ascii`（L399-432）：走 `to_cow()`（v1 已认可此路径——ASCII 主导多为 Borrowed，utf8 编码本身要求 Rust str，非 §0 #2 违反）
   - `Utf16Le | Utf16Be | Utf32Le | Utf32Be`（L433-451）：**不调 `to_cow()`**，仅 `obj.downcast::<PyString>()?` 做类型校验得到 `py_str: &Bound<PyString>`，直接传给 `encode_utf16_32_raw`

2. **`encode_utf16_32_raw` 签名修订**（L522-527）：参数从 v1 的 `s: &Cow<'py, str>` 改为 `obj: &Bound<'py, PyString>`。doc（L506-507）明确标注"P1 修订（v2）：签名从 `s: &Cow<'py, str>` 改为 `obj: &Bound<'py, PyString>`"

3. **实现要点**（L529）：`ffi::PyUnicode_AsUTF16String(obj.as_ptr())`——直接消费 PyObject 指针，输入是 PyObject 不是 Rust str。本机序 byte-swap 在返回的 PyBytes 上做（对输出字节的处理，非中间表示层）

4. **§6 §0 对照表 #2 行措辞修正**（L1682）："utf16/32 直接 downcast 后持有 `&Bound<PyString>` 调 `AsUTF16/32String` raw FFI，不经 `Cow<str>` 中转（v2 修订 P1）"

**§0 #2 合规判定**：utf16/32 encode 路径现与 `greedy_bytes.rs` build 零拷贝模式一致（直接操作 PyObject，无 Rust 中间类型）。**P1 解决**。

---

### P2a 复核：byteorder 值是否 LE=-1 — ✅ 解决

**v1 要求**：`Le => -1, Be => 1`（0 是自动检测 BOM，会误消费 `\xff\xfe`）。

**v2 证据**（§2.2.2 `decode_utf16_32_raw`，L454-502）：

1. **SAFETY 段 byteorder 语义表**（L463-472）：完整列出 CPython `PyUnicode_DecodeUTF16` byteorder 三值含义——`0`=自动检测 BOM / `-1`=强制 LE 不检测 BOM / `+1`=强制 BE 不检测 BOM。并明确解释"若用 0（v1 错误值），数据流开头恰好是 `\xff\xfe`（LE BOM）会被误判消费，破坏 parity"

2. **实现注释**（L491-494）：
   ```
   byteorder: i32 = match self {
       Utf16Le | Utf32Le => -1,   // 强制 LE，不扫描 BOM
       Utf16Be | Utf32Be => 1,    // 强制 BE，不扫描 BOM
   }
   ```
   **Le => -1, Be => 1**，与 CPython `utf_16_le`/`utf_16_be` 语义一致

3. **parity case 覆盖**（§11.2，L1955）：新增 `CS-utf16-le-fffe-data`——"CString utf16-le 解码含 `\xff\xfe` 字节流，验证 byteorder=-1 不误判 BOM"。此 case 直接验证修正正确性，若 byteorder 误用 0 会在该 case 失败

**CPython 语义独立验证**：`PyUnicode_DecodeUTF16(s, size, errors, &byteorder)` 文档明确 byteorder=0 时消费 BOM、±1 时不扫描。v2 取值正确。**P2a 解决**。

---

### P2b 复核：无后缀编码是否编译期报错 + parity 覆盖 — ✅ 解决

**v1 要求**：ARCH 在两种方案中选一。ARCH 选**方案 1（显式不支持无后缀编码，编译期报错）**。

**v2 证据**：

1. **`from_user_str` 显式拒绝分支**（§2.1.2，L218-237）：`"utf16" | "utf_16" | "u16" | "utf32" | "utf_32" | "u32"` 六个别名统一返回 `Err(ConstructError::Compilation { message })`，message 含引导文本（提示用 `utf_16_le`/`utf_16_be`/`utf_32_le`/`utf_32_be`）

2. **决策记录完整**（§2.1.3，L267-296）：方案 1 vs 方案 2 对照表 + ARCH 选方案 1 的 4 条理由（Python 行为本身不可移植 / 用户主流习惯 / 错误时机友好 / parity 影响可控）+ breaking change 用户面影响 + 备选方案 2 保留为后续选项

3. **parity case 覆盖**（§11.2，L1959-1960）：
   - `CS-reject-utf16-bare`：`CString("utf16")` 编译期拒绝（应 StringError，含引导文本）
   - `CS-reject-utf32-bare`：`CString("utf32")` 编译期拒绝
   - 注：v1 原有 `CS-utf16-1` 已用 `utf_16_le`（L1953），符合 P2b 决策，无需调整

4. **错误类型链路**（§3.8.5，L1502-1508）：`from_user_str` 返回 `Err(Compilation)`（编译期），Descriptor 转 `StringError` 抛给用户（保持用户面异常类型一致）。链路清晰

5. **breaking change 文档化**（§3.7.3，L1424-1427）：明确标注"无后缀 utf16/utf32/u16/u32 编码被拒绝"为 breaking change + 迁移指引（改字符串字面量）+ §5.1 对齐表（L1640-1647）标注 API 表面差异

**parity 一致性判定**：方案 1 虽是 breaking change（Python `CString("utf16")` 可用，construct-rs 报错），但消除了"静默映射到 Utf16Le 丢失 BOM 语义"的 v1 缺陷。报错时机在编译期（`__init_subclass__`），错误信息明确，迁移成本仅改一个字符串字面量。**P2b 解决**。

## 新发现（非阻断）

### P8：`from_user_str` 引导文本逻辑 bug（低，标注）

**文档位置**：§2.1.2 `from_user_str`（L225-234）

**问题**：引导文本的条件判断 `normalized.starts_with("utf16") || normalized.starts_with("u16")` 对别名 `"utf_16"`（带下划线）**失效**：

| 用户输入 | normalized | starts_with("utf16")? | starts_with("u16")? | 引导建议 | 正确？ |
|---------|-----------|----------------------|---------------------|---------|-------|
| `"utf16"` | `utf16` | true | false | utf_16_le/utf_16_be | ✅ |
| `"utf_16"` | `utf_16` | **false**（是 `utf_`） | **false**（是 `utf`） | **utf_32_le/utf_32_be** | ❌ 误导 |
| `"u16"` | `u16` | false | true | utf_16_le/utf_16_be | ✅ |
| `"utf32"` | `utf32` | false | false | utf_32_le/utf_32_be | ✅ |
| `"utf_32"` | `utf_32` | false | false | utf_32_le/utf_32_be | ✅ |
| `"u32"` | `u32` | false | false | utf_32_le/utf_32_be | ✅ |

用户传 `CString("utf_16")`（Python 合法别名）会被正确拒绝，但错误信息建议"用 utf_32_le"——**主动误导**。

**严重度评估**：低。仅影响错误信息文本质量，**不影响行为**（拒绝仍正确发生，仍是 `Err(Compilation)`）。parity case `CS-reject-utf16-bare` 用 `"utf16"`（不带下划线）不会触发此 bug，故测试矩阵不覆盖。

**建议修改**（DEV 实施时修正，不需 ARCH 重出设计）：将条件改为按 unit_size 判断，如：
```rust
let is_utf16_family = normalized.contains("16");
let (le, be) = if is_utf16_family { ("utf_16_le", "utf_16_be") } else { ("utf_32_le", "utf_32_be") };
```
或直接在 match 分支内用 `s` 的原始值（用户输入）做判断更直观。DEV 修正后建议补一个 parity case `CS-reject-utf16-underscore` 覆盖 `"utf_16"` 输入的引导文本。

**为何不阻断**：P2b 的核心要求（编译期报错 + parity 覆盖）已满足；此 bug 是引导文本质量问题，属"小问题可在报告中标注但不驳回"范畴，DEV 实施时易修正。
