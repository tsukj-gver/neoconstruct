## 分项检视

### 延续性：❌ 问题（1 项硬性）

#### [硬性-1] `venv_pair` 与 `run_parity_case` 接口契约不匹配（dict 解包必失败）

**文档位置**：
- §2.1 `venv_pair` fixture（line 252-262）返回 dict：`{"rs": ..., "py": ..., "crs_python_dir": ...}`
- §2.2.2 `run_parity_case` 签名（line 366-375）：`(impl, case_id, case_definitions, rs_python, py_python, crs_python_dir, *, extra_imports="")`
- §2.2.2 `make_parity_results_fixture` DEV 实现要点（line 489-490）：
  ```python
  "rs": run_parity_case("rs", case_id, case_definitions, **venv_pair),
  "py": run_parity_case("py", case_id, case_definitions, **venv_pair),
  ```

**问题**：`**venv_pair` 展开为 `rs=..., py=..., crs_python_dir=...`，但 `run_parity_case` 没有 `rs` / `py` 形参（只有 `rs_python` / `py_python`），调用必抛 `TypeError: run_parity_case() got an unexpected keyword argument 'rs'`。

**严重性**：DEV 照抄实现要点 → 所有 parity 测试 fixture 初始化即崩溃，6.0 步骤 2 验证必失败。

**建议修改方向**（ARCH 任选其一，并同步修订 §2.1/§2.2.2/§2.5）：
- **方案 A（推荐）**：统一 `venv_pair` 的 key 为 `rs_python` / `py_python` / `crs_python_dir`，与 `run_parity_case` 形参名一一对齐，`**venv_pair` 即可工作。
- **方案 B**：把 `run_parity_case` 第一参数改为接收 `venv_pair: dict`（聚合入参），签名简化为 `(impl, case_id, case_definitions, venv_pair, *, extra_imports="")`。BenchRunner 同步调整。
- 方案 C（不推荐）：保留现状但在 `make_parity_results_fixture` 内部手工映射 key，违反"减少参数数量"设计初衷。

### 完备性：❌ 问题（1 项硬性 + 1 项改进）

#### [硬性-2] CaseRegistry 缺少 `by_phase` 方法 + 与 §5.1 模板脱节（过度设计）

**文档位置**：
- §2.4.1 CaseRegistry 类定义（line 553-600）：仅声明 `register` / `all_cases` / `by_category` 三个方法，**无 `by_phase`**。
- §2.4.1 使用示例（line 615）：`PARITY_DEFINITIONS = "\n".join(c.builder() for c in REGISTRY.by_phase("6.1"))` —— 调用了**不存在**的 `by_phase` 方法，且 `c.builder()` 中 `c` 的类型/结构未定义（`all_cases` 返回 `list[tuple[str, str]]`，tuple 没有 `.builder()` 属性）。
- §5.1.1 DEV 照抄模板（line 1205-1294）：**完全未使用 REGISTRY**，直接用 `ALL_CASES = [("F32-1", "..."), ...]` 列表 + `_CASE_DEFINITIONS = '''...'''` 字符串，再调 `make_parity_results_fixture(ALL_CASES, _CASE_DEFINITIONS)`。

**问题**：
1. CaseRegistry API 不完备（`by_phase` 缺失，`c.builder()` 类型不一致）。
2. CaseRegistry 与 §5.1 模板**双轨并存但互不引用**——DEV 实施时不知该用哪个，且 §5.1 模板已证明"列表 + 字符串"足够，CaseRegistry 是**过度设计**。
3. 设计文档 §0.2 交付物清单（line 40）声称 fixtures.py 行数 ~120，但 CaseRegistry 占了大半，而其实际价值未在 §5.1 体现。

**严重性**：DEV 照抄 §2.4.1 示例 → `AttributeError: 'CaseRegistry' object has no attribute 'by_phase'`；照抄 §5.1 模板 → CaseRegistry 成为死代码。

**建议修改方向**（ARCH 任选其一）：
- **方案 A（推荐，做减法）**：移除 CaseRegistry，§2.4 fixtures.py 仅保留共享 fixtures（test_data_dir / tmp_binary_file / encoding）。§5.1 模板的 `ALL_CASES = [...]` + `_CASE_DEFINITIONS = '''...'''` 已足够简单且显式。理由：phase 内 case 数量有限（27/13/<30），无需注册中心；parametrize 直接用列表是 pytest 惯用法。
- **方案 B（保留但补全）**：补全 `by_phase` 方法（按 phase 字段过滤），修正使用示例的 `c.builder()` 为 `case.builder` 属性访问（统一 case 项的结构），并在 §5.1 模板改用 REGISTRY 注册 + 查询，使两节一致。代价：增加 DEV 学习成本，且 REGISTRY 的"phase × category 过滤"价值在当前 case 规模下不显著。

#### [改进-1] PARITY_SCRIPT_TEMPLATE 未列入公开 API，但 §5.1 范例导入它

**文档位置**：
- §2.2.2 章节标题"公开 API（3 个函数 + 1 个 fixture 工厂）"（line 351）—— 仅列 `run_parity_case` / `assert_parity` / `assert_fidelity` / `make_parity_results_fixture`。
- §5.1.1 范例（line 1228-1234）：`from _helpers.parity import (... PARITY_SCRIPT_TEMPLATE)`。

**问题**：PARITY_SCRIPT_TEMPLATE 是模块顶部常量（§2.2.1 line 293），DEV 可直接 from import，但**未在公开 API 清单声明**，DEV 不确定是否稳定 API。

**建议**：§2.2.2 标题改为"公开 API（3 个函数 + 1 个 fixture 工厂 + 1 个模板常量）"，并把 PARITY_SCRIPT_TEMPLATE 列入清单说明"DEV 可直接 import 用于自定义 case 定义注入"。

#### [改进-2] `_make_case_rs` 参数化变更未提示

**文档位置**：
- §2.2.1 约定（line 347-349）：要求 case 定义代码定义 `_make_case_rs(case_id: str) -> tuple` / `_make_case_py(case_id: str) -> tuple`（**带参数**）。
- 现有 `test_phase4_parity.py` line 113 / line 409：`def _make_case_rs():` / `def _make_case_py():`（**无参数**，通过模块级 `C = CASE` 读取）。

**问题**：设计将 case 函数从"无参数 + 闭包读 CASE"改为"带 case_id 参数"，是合理的显式化重构，但**未在迁移步骤 2/3（§4）明确提示"DEV 重写时必须把 `_make_case_rs()` 改为 `_make_case_rs(CASE)` 并在每个 if 分支用 case_id 替代闭包 C"**。DEV 可能照抄旧 case 定义导致子进程 `NameError: CASE`。

**建议**：§4 步骤 2/3 加一行硬要求："重写时 `_make_case_rs` / `_make_case_py` 必须参数化为 `(case_id)`，函数体内 `C = case_id`（替代旧 `C = CASE` 闭包）"。

#### [改进-3] NaN/Infinity 处理存在两条路径，无明确推荐

**文档位置**：
- §2.3 normalize 函数（line 515-536）：float 分支仅 `round(value, 6)`，**未处理 NaN/Infinity**。
- §5.1.2 范例（line 1322-1323）：在 case 定义内 extract 函数手动标记 NaN：`lambda o: {'v': 'NaN' if o.v != o.v else o.v}`。
- §5.1.3（line 1354-1367）：提出 normalize 函数扩展（NaN → `"__NaN__"` 字符串）。

**问题**：NaN 处理有两条路径并存——(a) case 内手动标记（§5.1.2）、(b) normalize 扩展（§5.1.3）。DEV 不知该用哪个，混用会导致 rs 侧用 (a) py 侧用 (b) 比对失败。

**建议**：明确推荐 **(b) normalize 扩展**（统一在 normalize 函数处理，case 定义无需特判），并把 §5.1.2 范例改为不手动标记、依赖 normalize。同步修正 §2.3 normalize docstring 加 NaN/Inf 分支说明（与 §5.1.3 对齐）。

**影响**：附录 A 步骤 1（line 1588）已正确列出 8 个 fixture 完整名字（含 case_template），DEV 照清单实现不会出错。仅文档描述层笔误。

### 新-改进-5：§5.2.1 bench 模板 venv 解析与 conftest.py 不完全一致

**位置**：§5.2.1 line 1445-1447
```python
# 从环境变量解析 venv（与 conftest.py 一致）   ← 注释声称一致
rs_python = os.environ.get("CRS_PYTHON", sys.executable)
py_python = os.environ.get("PC_PYTHON", sys.executable)
crs_python_dir = str(_BENCH_DIR.parent / "python")
```

**问题**：conftest.py fixture（§2.1 line 256-261, 270-275）是**三级解析**（env var → 默认 venv 路径 `_DEFAULT_RS_PYTHON` → sys.executable），bench 模板是**两级解析**（env var → sys.executable，**跳过了默认 venv 路径检查**）。本地未设 CRS_PYTHON/PC_PYTHON 环境变量时，pytest parity 测试用默认 venv（crs_venv/crs_venv_py），bench 测试用 sys.executable，可能用不同 Python 解释器，导致 bench 结果不可比。

**影响**：bench 是手动执行（不在 CI 自动跑），且 CI 环境通常已设环境变量。严重性低，但注释"与 conftest.py 一致"不准确。

**建议**：DEV 实施 bench 模板时，把三级解析逻辑补全（或抽公共函数 `_resolve_venv(env_var, default_path)` 供 conftest.py 与 bench 共用），使注释名副其实。不阻塞 6.0（bench 模板是 §5.2 范例，DEV 实施时可修正）。
