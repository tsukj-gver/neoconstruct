## 具体问题（按严重度）

### 问题 1（P1，高严重度，必须修正）：错误类型映射与 Python `IntegerError` 不一致

**文档位置**：
- §1.4.1 `VarIntNode::build`（行 383-399）：负数分支用 `ConstructError::FormatField`
- §1.4.2 `ZigZagNode::build`（行 575-579）：非 int 分支用 `ConstructError::FormatField`
- §1.5.3 `BytesIntegerNode::parse`（行 686-691）：length==0 分支用 `ConstructError::FormatField`

**问题**：Python construct 原版对这三类错误全部抛 `IntegerError`：
- `core.py:1634` `IntegerError(f"value {obj} is not an integer")`（VarInt 非 int）
- `core.py:1636` `IntegerError(f"VarInt cannot build from negative number {obj}")`（VarInt 负数）
- `core.py:1249` `IntegerError(f"length {length} must be positive")`（BytesInteger length<=0）
- `core.py:1260` `IntegerError(f"value {obj} is not an integer")`（BytesInteger 非 int）
- `core.py:1680` `IntegerError(f"value {obj} is not an integer")`（ZigZag 非 int）

**设计文档内部矛盾**：
- §3 §0 #7 对照表（行 972）**正确**写："VarInt 负数返回 IntegerError；ZigZag 非 int 返回 IntegerError；BytesInteger length=0 / 值超范围 / 非 int 返回 IntegerError（与 Python 对齐）"
- 但 §1.4.1 / §1.4.2 / §1.5.3 的**代码示例**用 `ConstructError::FormatField`，与对照表自相矛盾

**影响**：现有 `error.rs:191-196` 已有 `ConstructError::Integer` 变体（Phase 3.3 新增），`init_exception_classes`（error.rs:614）已缓存 `integer_error: get("IntegerError")?`，`select_exception_class`（error.rs:663）已映射 `Integer → integer_error`。若按 §1.4.1 代码示例实现，Python 侧 `except IntegerError` **捕获不到** VarInt 负数错误（实际抛 `FormatFieldError`），直接破坏用户面 API 兼容性。

**建议修改方向**：
1. §1.4.1 / §1.4.2 / §1.5.3 所有整数相关错误改用 `ConstructError::Integer { message, path }`
2. 错误信息格式与 Python 对齐（如 `f"value {obj} is not an integer"` / `f"VarInt cannot build from negative number {obj}"`）
3. 修正后与 §3 对照表一致，消除文档内部矛盾

### 问题 2（P2，高严重度，必须修正）：Float build 未处理整数输入

**文档位置**：§1.3.3 Float build 路径（行 250-269）

**问题**：Python `struct.pack(">f", 42)` 接受整数（CPython struct 模块自动 int→float 转换），这是 Python construct `Float32b.build(42)` 的既定行为。设计文档 §1.3.3 用 `obj.extract::<f32>()`：

- pyo3 的 `extract::<f32>()` / `extract::<f64>()` 对 Python **int 类型**返回 `Err`（pyo3 不自动 int→float，Python int 与 float 是不同 PyType）
- 这会导致 `Float32b.build(42)` 在 construct-rs 失败（FormatFieldError），但在 Python construct 成功
- mashumaro 式 API 中 `v: float = field(Float32b)` 类型注解是 `float`，但 Python 运行时不强制，用户传 int 常见（如 `P(v=42)`）

**遗漏边界条件**：§5.2 Float 边界条件（BC-B1~B14）未覆盖 "Float32b.build(42)"（整数输入）case。

**建议修改方向**：
1. Float build 路径先 `extract::<f64>()`（pyo3 对 Python float 成功），失败时尝试 `extract::<i64>()` 后 `as f64`（处理 int 输入），两者皆失败才报 FormatFieldError
2. 或更简洁：`let val = obj.extract::<f64>().or_else(|_| obj.extract::<i64>().map(|i| i as f64()))`
3. §5.2 补充 BC-B15 "Float32b.build(42) 写入 b'\x42\x28\x00\x00'（int→float 转换）"

### 问题 3（P3，中严重度，合并 P1 修正）：VarInt slow-path 实现方式

**文档位置**：§1.4.1 `build_varint_bigint`（行 428-467）+ §9.3 预案（行 1527）

**问题**：
1. `py.run_bound(code, ...)` 每次调用重新编译执行 Python 代码定义函数（slow-path 罕见，性能可接受，但实现粗糙）
2. §9.3 预案提出"改为 `obj.call_method('to_bytes', ...)`（与 BytesInteger slow-path 统一）"**有技术错误**：VarInt 需 LEB128 编码（每 7 位 + MSB 续位），`int.to_bytes(length, 'big')` 是直接转 N 字节大端，两者编码逻辑完全不同，不能统一
3. 设计文档主体（§1.4.1）与预案（§9.3）方案不一致

**建议修改方向**（任选其一，ARCH 决策）：
- 方案 A：保留 `run_bound` 但在文档中说明"slow-path 罕见，每次定义函数的开销可接受"，并修正 §9.3 预案的改进方向（承认 VarInt LEB128 不能用 to_bytes 简单替代，改为"如需优化可在模块初始化时缓存编译后的函数"）
- 方案 B：在 Rust 侧用 `obj.call_method("__rshift__", (7,))` / `obj.call_method("__and__", (0x7F,))` 逐位运算（每字节 2 次 call_method，FFI 次数多于 run_bound，但语义清晰）
- 无论选哪个，需消除 §1.4.1 主体与 §9.3 预案的不一致

### 问题 4（P4，低严重度，标注不驳回）：§1.1 Node 变体数描述

**文档位置**：§1.1（行 73-80）多处"现有 24 个 Node 变体" / §1.4.1 行 481"现有 24 个变体"

**问题**：`construct-rs/src/nodes/mod.rs` 中 Node enum 实际 20 个变体（FormatField/Bytes/GreedyBytes/Struct/StructRef/Tell/Computed/BitsInteger/Bitwise/Bytewise/Transform/BitPadding/Padding/Array/GreedyRange/PrefixedArray/RepeatUntil/Index/StopIf/Element）。

**建议**：文档润色，统一为"现有 20 个变体"（不影响设计，DEV 实施时按 mod.rs 实际状态注册）。
