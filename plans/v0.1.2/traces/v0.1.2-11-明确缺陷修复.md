## 1. 修复 #1：不可信 count 预分配 abort（Critical）

- 根因：`ArrayNode::parse` / `PrefixedArrayNode::parse` 以 `Vec::with_capacity(count)`
  按不可信 count 预分配结果 Vec——`Array(0xFFFFFFFF)` → 34GB 分配失败 → Rust
  侧 abort（rc=0xC0000409），Python 层无法 catch。对照组（Bytes/Prefixed
  大长度、负 count）因不预分配而天然安全。
- 修复（`nodes/common.rs` 新增 `capped_result_capacity`，两处 parse 采用）：
  - 元素静态尺寸 `size ≥ 1`：`cap = min(count, remaining / size)`
    （remaining = `ParseStream::remaining()`）。顺序流中当前位置起最多解析
    `remaining/size` 个该尺寸元素，预分配永不超过实际可解析量；count 超出
    部分由逐元素 parse 的自然 Stream 错误拒绝。
  - 尺寸未知（sizeof 失败，如 GreedyBytes）或为 0（如 Pass）：退化为
    `min(count, 16)` 小常量起步，push 摊还增长。
  - 单位混用安全性：bit 域元素 sizeof 单位是 bit、remaining 是字节——混合
    除法只会**低估** cap（bit 域实际可解析量为 8×remaining/size bits），
    低估仅触发 push 增长，无过度分配风险。
  - 分配量由此以输入规模为上界（O(remaining)），不再以不可信 count 为上界。
- 合法路径零影响：count ≤ remaining/size 时 cap == count（与旧行为完全一致）；
  仅 count 超出时才降为封顶值。
- 测试：
  - Rust 单测：array.rs × 2（字面 0xFFFFFFFF / 表达式 0xFFFFFFFF →
    StreamError 非 abort）、prefixed_array.rs × 1（流内 0xFFFFFFFF）、
    common.rs × 5（封顶函数各分支）。
  - Python 子进程崩溃隔离矩阵（`tests/errors/test_untrusted_count_hardening.py`，
    探针转正、语义命名）：字面巨 count / 流内 count / PrefixedArray 大 count /
    负 count（对照）/ Bytes 大长度（对照）/ GreedyBytes 常规（对照）——全部
    断言子进程 rc==0 且输出 CATCHABLE（即 ConstructError 被 catch，进程存活）；
    另含 5 个进程内合法路径回归（正常 Array/PrefixedArray/1000 元素大数组/
    元素级 path 定位）。

## 2. 修复 #3B：继承显式拒绝（用户裁决：字节排布有位置语义）

- 根因：Schema 编译只收集子类自身类体的 field() 声明（`_collect_field_descriptors`
  仅查 `cls.__dict__`），继承已编译结构类会静默丢基类字段（REPORT #3 实测：
  3 字节协议 build 出 1 字节、parse 抛裸 AttributeError）。
- 修复（`_mixin.py` 新增 `_reject_struct_subclassing`，`__init_subclass__` 在
  编译前调用）：
  - 直接基类是 StructMixin 后代且非框架入口基类（`StructMixin` 本体判等 +
    `_FRAMEWORK_STRUCT_BASES = (BitStructMixin,)` 白名单）→ CompilationError。
  - 消息含三要素：不支持继承 + 理由（字节排布具有空间位置语义，继承体系
    无法表达基类字段的占位，继承会导致基类字段静默丢失）+ 引导（用组合：
    字段嵌套该结构类）。
  - 加载期次序处理：检查函数定义于 `BitStructMixin` 之前（模块创建
    BitStructMixin 时 `__init_subclass__` 即触发）；`StructMixin` 本体单独
    判等使其在白名单元组填充前也可安全通过。
- 测试（`tests/unit/test_compile_rejections.py`，11 例）：单继承/空子类/
  多基类形态/make_dataclass 动态创建/已编译且使用过的基类各 1 例拒绝 +
  消息三要素断言；框架路径回归 3 例（BitStructMixin 子类、普通 mixin 组合、
  组合模式 build/parse 往返）。

## 4. 修复 #4：build 接受 bytes-like

- 根因：`BytesNode::build` / `GreedyBytesNode::build` 仅 `downcast::<PyBytes>()`，
  bytearray/memoryview 被拒（`GenericConstructError`）。
- 修复（`nodes/common.rs` 新增 `extract_bytes_like`，两节点采用）：
  - bytes：`as_bytes` 零拷贝借用（Cow::Borrowed，快路径不变）；
  - bytearray：`to_vec` 一次拷贝（pyo3 0.22 无安全借用切片 API；build 侧
    写入 BuildStream 本需一次拷贝，无额外净开销）；
  - memoryview 等 buffer 协议对象：`PyBuffer::<u8>::get_bound` + `to_vec`
    （非 u8 格式/非连续缓冲由 PyBuffer 拒绝，落入明确错误）。
  - 其余类型（int/str/None/list）仍拒绝，错误消息保留实际类型名。
  - 旧名不符实测试 `test_bytes_build_accepts_bytearray`（test_roundtrip.py:192，
  从未传入 bytearray）修正为真传入 bytearray；新增 memoryview、bytes-like
  长度校验、GreedyBytes bytes-like 用例；Rust 侧同步（bytearray/memoryview/
  长度不匹配 ×Bytes + GreedyBytes ×2 + 拒绝非 bytes-like）。
- parse 侧契约不变（parse(bytearray) → TypeError 是有测试的有意行为）。

## 5. 修复 #5：dataclasses.field 遮蔽检测

- 根因：误 import dataclasses 的 field 后，`magic: int = dataclasses.field(...)`
  被当作非二进制属性静默跳过——parse 零字节消费、返回默认值、无任何报错。
- 修复（`_mixin.py` 新增 `_reject_dataclasses_field_shadowing`，编译前调用）。
  检测两种**可判定**误用形态：
  1. `dataclasses.field(default=<协议描述符>)`——描述符被误当实例默认值
     （`_is_protocol_descriptor`：StructMixin 子类 / Rust pyclass——其
     `__module__` 历史设为 `"construct"`，repr 兼容用 / `neoconstruct.*`
     模块实例）；
  2. 类体只有 dataclasses.field 字段、无任何本库 field() 声明——整类遮蔽
     （REPORT #5 复现场景：单字段 `dc_field(default=5)`）。
- **设计说明（粒度取舍）**：与二进制字段**并存**的普通
  `dc_field(default=标量)` 是既有受支持混合字段模式（test_edge_cases 3 例
  用例锁定），与"部分字段遮蔽误用"在结构上不可区分——故并存形态不拒绝，
  仅拒绝上述两种无歧义形态。若 PM/ARCH 认为应彻底禁止类体出现
  dataclasses.field（收缩混合模式契约），需另行裁决并改 3 个既有用例。
- 测试：包装描述符 / 整类遮蔽各 1 例编译期拒绝（消息含正确 import 引导）+
  混合模式回归 1 例（确认不误伤）。
