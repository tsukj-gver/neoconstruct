## 2. 快照可疑点裁决清单（13 例 → 6 个行为点）

### S1 [高] 表达式 VM i64 回绕 / 移位量掩码（6 例锁定）
- 锁定行为：`(2**63-1)+1` 回绕负；`-(i64::MIN)` 回绕自身；`n*n` 回绕 1；
  `1<<63` = -2^63；`1<<64` == 1（移位量按 64 掩码）；`0xff>>64` == 255。
- 自然语义：Python 用户心智 = 任意精度整数（Python 无溢出）。`Computed(n*n)`
  **静默错值**；长度面有负值防御（FieldLengthError），但 Computed/普通算术面
  无任何防御。与项目自身原则"显式失败优于静默错值"（矩阵 docstring 原话）冲突。
- 裁决建议：**需 PM/用户裁决**。选项：(a) 溢出/大移位显式报错（checked）；
  (b) 保持回绕但 build/parse 前提下文档高亮；(c) 边界提升 Python bigint
  （性能代价）。理由：这是"性能 vs 最小惊讶"的产品决策，不是实现细节。
- 用户影响：协议字段缩放/校验和计算在极端值下静默错，且无告警。

### S2 [中] 用户 raise ExplicitError 被 Select 吞掉（1 例）
- 锁定行为：Adapter._decode 内 `raise ExplicitError` → `From<PyErr>` 统一转
  Generic（error.rs L1284，仅特判 CancelParsing）→ Select 视为普通失败尝试
  下一候选，**不传播**。
- 自然语义：`_errors.py` ExplicitError docstring 明文承诺"Select / Peek 不吞掉，
  直接向上传播"——**文档契约与实现矛盾**（文档承诺的是应有语义，实现未达）。
  Select/Peek 的 Rust 内部 `ConstructError::Explicit` 穿透逻辑已写好
  （select.rs/peek.rs），仅差 From<PyErr> 识别用户侧类型（指针比较，与
  CancelParsing 同模式，改动面小）。
- 裁决建议：**疑似缺陷，建议修复**（From<PyErr> 加 ExplicitError 识别）。
  修复后 test_user_explicit_error_wrapped_as_generic_currently 按 DOC 注释
  预告"转断言传播"。

### S3 [中] FlagsEnum parse 值携带 `_flagsenum` 内部标记键（1 例）
- 锁定行为：parse b'\x03' → `{"_flagsenum": True, "READ": True, "WRITE": True,
  "EXEC": False}`（flags_enum.rs L93 set_item）。
- 自然语义：下划线前缀标记是**内核为 build 侧识别 dict 形态而设的实现细节
  泄漏到用户值**；parse 产出全键 dict + 标记 vs build 接受部分键 dict——
  形态不对称；用户 `parsed.flags == {"READ": True}` 永假，`dict(**flags)`
  会带出垃圾键。
- 裁决建议：**疑似缺陷（API 污染），需 PM/ARCH 裁决**替代方案：专用
  FlagsContainer 类型 / build 侧按 dict 值域判定（无需标记）/ 保留但文档化。
  注意：这是 Phase 8 已知显示对象税家族（L-14 关联），非本轮回归。

### S4 [低中] RepeatUntil parse 全流无哨兵 → StreamError（3 例同一点）
- 锁定行为：EOF 时 inner.parse 失败直接上抛 StreamError（repeat_until.rs
  L253-261 "失败直接上抛，不像 GreedyRange 回退"），path=元素索引。
- **正面回答"哪个正确"**：**报错是对的，"EOF 优雅停"（设计骨架猜测）是错的**。
  理由：RepeatUntil 的哨兵是组帧契约（build 侧同样强制"某元素必须满足"）；
  "读到 EOF 停"是 GreedyRange 的语义，两者不可混。DEV 按 [基线] 锁定报错
  行为方向正确。
- 但存在**错误类型不对称**：build 无满足元素 → RepeatError；parse 哨兵从未
  出现 → StreamError（真实根因被流错误掩盖）。裁决建议：**EOF 且无哨兵时
  转 RepeatError（"no item matched terminator before EOF"）更对称**，属低风险
  改进项；现 StreamError + 元素级 path 也可接受（需文档化）。
- 附带发现：RepeatUntil docstring（_descriptors.py L946-974）**完全未写 EOF
  行为**——该 [基线] 锁定无文档契约背书。

### S5 [低] NamedTuple 非容器 inner → 运行期 NamedTupleError（1 例）
- 锁定行为：`NamedTuple("coord","x y", Int8ub)` 编译通过，parse 时才报错。
- 自然语义：inner 非容器在描述符创建时即可静态判定，按项目 fail-fast 一贯
  策略（Array(-1)/Aligned modulus<2/callable terminator 均编译期拒）应编译期
  CompilationError。
- 裁决建议：**疑似缺陷（一致性），低优先修复**或文档说明为何延迟。

### S6 [低] Hex(Bytes) str() 形态 `unhexlify('00000102')`（1 例）
- 锁定行为：bytes 显示形态为可 eval 的 `unhexlify('...')`。
- 自然语义：纯显示场景下用户预期 `00000102` 或 `00 00 01 02`；
  `unhexlify(...)` 是"repr 可回粘贴执行"的设计取舍（construct 血统）。
- 裁决建议：**需裁决（设计取舍）**——eval-ability 是真实特性，但应在文档
  明示"str() 为代码形态，display 用 X"。SKILL 现只写"Hex 显示包装"，
  形态契约缺失（见 §4-8）。

## 3. 四个嫌疑实例的正面回答

1. **RepeatUntil EOF**：见 S4——报错正确、骨架猜错；遗留错误类型不对称
   （RepeatError 更对称，需裁决）。
2. **5 个无触发路径异常类**——两个都是问题，具体拆解：
   - ExplicitError：**不是死代码，是真缺陷**（S2：用户路径存在但类型被吞）；
   - IndexFieldError：**覆盖缺口 + 死类**——Index 缺 _index 返回静默 None，
     与 Peek"哑值 None 流入消费者显式报错"的处理不一致（None 会下游远处
     炸成 GenericConstructError，归因更难）；保留"供严格模式"无时间表；
   - SizeofError：**死类 + 功能缺口**——用户面无 sizeof API
     （`hasattr(P,"sizeof")==False` 实测）；且 RepeatUntil.sizeof 内部返回
     **Generic 变体而非 Sizeof**（repeat_until.rs L352-357，注释却声称
     SizeofError）——内部不一致，说明该变体从未被真正接线；
   - StopFieldError：**合理**——Result 哨兵变体被外层捕获属设计（真特性），
     唯一可议是暴露在 public API（可降为内部）；
   - UnresolvedReferenceError：半合理——struct_ref 延迟编译机制保留变体，
     用户面无自然触发路径，测试只能靠手动置空模拟。建议 docstring 标注
     "内部机制变体"。
   - 综合裁决：建议 PM 立项"异常面清理"小任务（sizeof API 取舍 / Index
     严格模式 / Explicit 识别），层次断言用例已预留转正路径。
3. **Timestamp unit 语义**：**语义本身自洽，非缺陷**——独立验证：
   0x5A497A00 = 1514764800s = 2018-01-01T00:00Z ✓；3_600_000 × 0.001s =
   1h ✓。"每 tick 秒数"数学上就是 `value × unit = 秒`，与文档示例一致。
   DEV 未质疑是对的。真正可议的是**命名 ergonomics**（unit=0.001 vs
   unit="ms"）→ 归入 API 设计裁决（低）。**审计新发现**：unit/epoch 传
   非 "msdos" 的任意 str 时 isinstance 检查放行（_macros.py L91-94），
   到 parse 期才 TypeError 而非构造期 TimestampError——值校验缺口（低，
   未测路径，建议补例+修复）。
4. **SKILL/README 契约**：见 §4——主流声明与实现一致（5/10），但存在
   1 处**文档承诺超实现**（ExplicitError，反向固化）、4 处**文档缺口**
   （行为被测试锁定但文档未契约化——这才是"文档照实现写"的真实形态：
   不是写错，是没写，让测试成了唯一契约源）。
