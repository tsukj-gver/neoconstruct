### 4. O3 raw FFI 安全性专项结论

**结论：通过，但 DEV 实施时必须补全以下三项**（不阻塞设计通过）：

1. **安全前置条件列表**：设计 §1.3 O3 提及 `PyType_GenericAlloc` + `PyObject_SetAttr`，但未展开 CPython C API 的契约（如 `PyType_GenericAlloc(cls, 0)` 要求 cls 是有效 type 对象；`PyObject_SetAttr` 可能失败需检查返回值并走 BC6 回退）。DEV 实施时必须列出每个 unsafe 调用的前置条件 + 失败模式 + 回退路径。

2. **用户子类化检测方法表述精确化**：设计 §1.4.4 R2 + §3.1.3 ADR-019 草案中"`PyType_IsSubtype` 检查 cls 是否等于内置类"语义不精确——`PyType_IsSubtype(A, B)` 是"A 是否 B 的子类"，不是"A 是否等于 B"。准确的检测应在 ExceptionClasses 缓存时记录每个内置类的指针，运行时用 `cls.as_ptr() == builtin_cls.as_ptr()` 指针相等比较。设计方向正确但表述需精确化。

3. **兼容性测试 T6 设计具体化**：§5.1 T6（用户子类化）必须在 DEV 实施时设计具体子类化用例（如 `class MyError(StreamError): def __init__(self, msg, path=None): super().__init__(msg, path); self.extra = "custom"`），验证子类 __init__ 在 Rust 抛 MyError 时被调用（走慢路径）。

**反例 R2 可执行性**：三步处置（fast-path 仅 13 内置类 / 子类走慢路径 / 整体降级为可配置开关）都具体可执行——已有 `call1` 慢路径作为后备。BC3（用户子类化）+ BC6（fast-path 失败回退）覆盖关键边界。

**`cargo miri test` 缓解**：Miri 对 FFI 支持有限（CPython C API 调用会被 Miri 拒绝），但本地逻辑（指针比较 / GC 引用追踪）可被 Miri 检查。DEV 实施时需评估哪些部分能被 Miri 覆盖。

### 3. unsafe 块安全论证（按 §1.3.1 U1-U4 + 失败模式 + BC6 回退）

#### 3.1 `try_fast_path_alloc` 函数签名与前置条件

`
ust
fn try_fast_path_alloc<'py>(
    py: Python<'py>,
    cls: &Bound<'py, PyType>,
    classes: &ExceptionClasses,
    message: &str,
    path: Option<&str>,
) -> Option<PyErr>
`

函数本身是 **safe**（所有 unsafe 操作均被前置条件检查包裹）。内部单一 `unsafe { ... }` 块含 4 个 unsafe CPython C API 调用，每个对应 U1-U4 之一。

#### 3.2 U1-U4 前置条件 + 失败模式逐项论证

| # | unsafe API | 前置条件（实施时验证） | 失败模式 | BC6 回退 |
|---|-----------|---------------------|---------|---------|
| **U0** | `classes.is_builtin_class(cls.as_ptr())` | 入口检查：`cls.as_ptr()` 与 13 个内置类指针逐个比较（`contains`） | 用户子类化 → false | 返回 `None`，调用方走慢路径 |
| **U1** | `ffi::PyType_GenericAlloc(cls.as_type_ptr(), 0)` | ① GIL 持有（`py` token 在作用域内）② `cls` 有效 PyTypeObject（pyo3 类型保证）③ `cls` 确切为内置类（U0 已验证）| 返回 NULL + PyErr_MemoryError（仅 OOM）| `PyErr_Clear()` + 返回 `None` |
| **U2** | `ffi::PyObject_SetAttrString(instance, c_str!("message"), msg_ptr)` | ① GIL 持有 ② `instance` 是 U1 返回的非空对象（已 is_null 检查）③ `msg_ptr` 是有效 PyString（`PyString::new_bound` 返回 owned Bound）④ `instance` 是内置类（无 monkey patch `__setattr__`）| 返回 -1 + PyErr（极端：monkey patch）| `PyErr_Clear()` + `Py_DecRef(instance)` + 返回 `None` |
| **U3** | `ffi::PyObject_SetAttrString(instance, c_str!("path"), path_ptr)` | 同 U2；`path_ptr` 为 PyString 或借用 Py_None（`ffi::Py_None()`）| 同 U2 | 同 U2 |
| **U4** | `ffi::PyObject_SetAttrString(instance, c_str!("args"), args_tuple_ptr)` | ① GIL 持有 ② `instance` 是 BaseException 子类（13 个内置类全满足）③ `args_tuple` 是 `(message,)` PyTuple | 返回 -1（罕见：monkey patch `__setattr__` 拦截 args）| 同 U2 |

**关键 CPython 行为依赖**（`BaseException_setattro` 对 `args` 的特殊处理）：CPython `Objects/exceptions.c` 中 `BaseException_setattro` 检查 `name == &_Py_ID(args)` 时调 `Py_XSETREF(self->args, value)`，绕过 `args` member 的 READONLY 限制。本设计依赖此行为；UAT 测试 `try_fast_path_alloc_builtin_stream_with_path` 验证 `args == ('boom',)` 实际生效。

#### 3.3 引用计数追踪（按 §1.3.1 注释要求）

| 步骤 | 对象 | refcount 变化 | 净持有 |
|------|------|--------------|--------|
| 入口 | instance (PyType_GenericAlloc) | +1（新分配） | instance=1 |
| U2 后 | msg PyString | +1（msg_bound 持有）+ 1（instance.message） = 2 | msg_bound=1, instance.message=1 |
| U3 后 | path PyString 或 Py_None | +1（path_owned 持有，仅 Some 分支）+ 1（instance.path）；None 分支仅 Py_None 全局 +1 | path_owned=1, instance.path=1 |
| U4 前 | args PyTuple | +1（args_tuple 持有）+ msg.clone() 临时 +1 = msg 现 3；PyTuple::new_bound incref msg → 4；clone drop → 3 | args_tuple=1, msg 总计 3（msg_bound + instance.message + tuple element） |
| U4 后 | args_tuple | +1（instance.args） = 2 | args_tuple=1, instance.args=1 |
| 末段 | Bound::from_owned_ptr_or_opt 消费 instance | 不 incref，所有权转移 | instance 由 Bound 持有 |
| 末段 | Bound drop（msg_bound, path_owned, args_tuple 离开作用域）| 各 -1 | instance.message/path/args 由 instance 独占持有 |

最终 instance 持有：`message` + `path` + `args` 三个属性的独占引用，`PyErr` 持有 instance。无泄漏。

#### 3.4 BC6 回退路径完整性

所有 4 个 unsafe API 的失败分支均执行：
1. `ffi::PyErr_Clear()` — 清除挂起的 Python 异常（避免污染后续 `with_gil`）
2. `ffi::Py_DecRef(instance)` — 释放已分配的部分实例（避免内存泄漏）
3. `return None` — 信号调用方走 `build_exception_instance` 慢路径

调用方 `From::from` 在 `try_fast_path_alloc` 返回 `None` 时落到：
`
ust
match build_exception_instance(py, cls, message, path) {
    Ok(instance) => PyErr::from_value_bound(instance),
    Err(_) => PyValueError::new_err(err.full_message()),  // BC1 final fallback
}
`

BC3（用户子类化）+ BC6（fast-path 失败）+ BC1（慢路径也失败）三层降级完整。

#### 3.5 SAFETY 注释覆盖度

### 4. T6 子类化兼容性测试设计 + 结果

#### 4.1 测试用例（按 ARCH §1.3.1 + REV OBS-3）

新增 8 个测试（`error.rs:1556-1981`），关键测试逐项说明：

| 测试名 | 目的 | 关键断言 |
|--------|------|---------|
| `is_builtin_class_matches_cached_ptrs_only` | O3 U0 指针比较仅匹配确切内置类 | 13 个内置类 true；`type('MyError', (StreamError,), {})` false |
| `try_fast_path_alloc_builtin_stream_with_path` | O3 fast-path 内置 StreamError + path | `message='boom'` / `path='root.x'` / `args=('boom',)` / 类型名 StreamError |

| **`slow_path_invokes_user_subclass_init`** | **T6 关键**：慢路径调用用户 __init__ | `MyStreamError.__init__` 设置 `self.extra='custom_marker'` → 通过 `build_exception_instance` 慢路径构造后 `extra` 必须被设置 |
| `fast_path_str_matches_slow_path_when_path_set` | O3 + Python `__str__` 重写依赖 | fast-path 与慢路径的 `str(e)` 一致（都包含 `Error in path root.x\nboom`）|
| `fast_path_args_differs_from_slow_path_by_design` | ADR-019 决策 4 行为差异 | fast-path `args=('boom',)` vs 慢路径 `args=('Error in path root.x\nboom',)` — 设计显式批准 |

#### 4.2 T6 子类化兼容性论证（按 ARCH §1.4.4 R2）

**R2 风险**：O3 绕过 Python `__init__` 导致用户子类化的异常 `__init__` 不被调用（破坏用户自定义行为）。

**R2 缓解实施**：
1. `ExceptionClasses::is_builtin_class(cls_ptr)` 用裸指针相等比较（**非** `PyType_IsSubtype`，按 REV OBS-2 修订）。13 个内置类的指针在 `init_exception_classes` 时缓存。
2. `try_fast_path_alloc` 入口检查：`if !classes.is_builtin_class(cls.as_ptr()) { return None; }` —— 用户子类化返回 `None`，调用方走 `build_exception_instance` 慢路径。
3. 慢路径 `cls.call1((message, path))` 调用 Python 类的 `tp_call → tp_new → tp_init`，用户的 `__init__` 被正常调用。

**T6 验证证据**：
- `try_fast_path_alloc_user_subclass_returns_none` 测试 `MyStreamError(StreamError)` 含 `__init__` → fast-path 返回 `None` ✅
- `slow_path_invokes_user_subclass_init` 测试 `MyStreamError.__init__` 设置 `self.extra='custom_marker'` → 慢路径构造后 `extra == 'custom_marker'` ✅

**结论**：T6 兼容性测试通过。R2 风险已被指针比较 + 慢路径回退两层缓解。

### 5. i02_idx_n100 改善归因（DEV OBS-DEV-2 处置）

DEV 报告 OBS-DEV-2：i02_idx_n100 在 4.x 后从 INVEST 基线 ~10x 升至 17.3x，怀疑 crate LTO 重新内联（O3 副作用）。

- A 状态（O1-O4 off）：i02_idx speedup = 18.060 ± 0.427x（17.59-18.43）
- B 状态（O1-O4 on）：i02_idx speedup = 17.768 ± 0.424x（17.30-18.14）
- Δ = -0.29x（<0.3x 波动阈值），welch_t=1.05（不显著）

**归因结论**：i02_idx_n100 的"10x（INVEST 07-11）→ 17.3x（4.x DEV 07-28）"改善**不是 O1-O4 引入**（A/B 内无显著差异），是**跨时段测量环境漂移**（17 天跨度）。

这正好对应 **L-09 教训**——跨时段性能对比的消除法归因在边界场景失效，必须用 Controlled A/B Test。本次调查复用 L-09 对策（同会话交替测量 + 阳性对照 + 阴性对照）成功归因。
