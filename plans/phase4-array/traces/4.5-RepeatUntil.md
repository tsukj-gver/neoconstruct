### 设计质疑

#### [设计质疑] PyCallable 路径未稳定达到 ≥3x 目标

**事实**：设计 §8.3 预测 PyCallable 路径 ≥3x，实际测量：
- Int8ub 系列：2.2-2.4x（未达标）
- Int32ub N=256：3.00x/3.07x（恰好达标）

**根因分析**：

1. **设计高估了 Python 基线**。设计 §8.3 假设「Python construct 每次 FFI ~500-1000ns」，
   实际 Python 3.14 + construct 2.10.70 的 RepeatUntil 每元素仅 ~270-300ns（Python 调用
   Python lambda 的开销远低于跨语言 FFI）。
2. **FFI 物理上限**。Rust 调 Python lambda（predicate.call1）+ 返回值检查（is_truthy）
   的最小开销约 ~80-120ns/iter；加上 inner.parse（~15-25ns）、list.append（~30ns）、
   path push/pop（~20ns）、ctx_proxy.set_item（~30ns）= 总计 ~175-225ns/iter。
   Python 端 ~270-300ns/iter。比值 1.2-1.7x 为「Rust 调 Python」的物理上限。
3. **Rust 非谓词开销已经很低**：参照 GreedyRange（无谓词）~25-30 ns/iter，
   RepeatUntil 的非谓词部分与 GreedyRange 相当。差距完全来自 FFI 谓词调用。

**影响评估**：

- Expr 路径已远超目标（≥8x，实测 10-12x）。**用户写简单 lambda（绝大多数场景）自动走 Expr 路径**。
- 仅当用户写复杂 lambda（依赖 list 内容或 context 字段）时才走 PyCallable 路径，性能 2-3x。
- 设计 §8.3 明确「PyCallable 路径 3-5x 是物理上限」，实测 2.2-3.0x 接近此上限的下限。

**建议**：

- **接受为已知**：PyCallable 路径在中规模场景下 2.2-2.4x，但 Expr 路径已 10x+ 弥补。
  S-PERF 整体出口（设计 §8.3）应基于 Expr 路径判断（「Expr 路径 ≥8x」已达标）。
- 或 **PM/ARCH 重新评估 §8.3 PyCallable 目标**：是否调整为 ≥2x（更符合 Python 3.14 现状）？
- 未来优化方向：缓存 predicate 的 `__call__` 方法引用、用 PyObject_Call 代替 call1 减少参数
  元组构造开销（预期可提升 5-15%）。

### 偏离设计的地方

1. **Context._current_elem_ptr 不被子 context 继承**（设计 §4.3.2 contract）：
   - 设计文档只描述了字段定义，未明确继承行为。
   - DEV 决策：**不继承**。理由：predicate 仅在 RepeatUntilNode 自身求值，
     子 Struct 不应看到外层 RepeatUntil 的当前元素。这与 _index 的"继承"语义不同
     （IndexNode 在子 Struct 中需要读取 _index，因此继承）。
   - 实现：new_child / new_child_placeholder 中 `_current_elem_ptr: None`。

2. **PyCallable 路径 context proxy 优化**（设计 §4.3.4 简单方案的偏离）：
   - 设计 §4.3.4 提到「简单方案：每次构造新 PyDict，从 ctx.fields() 复制字段 + 写 _index」。
   - DEV 实现：预创建 proxy（仅 `_index` 字段），每次迭代仅更新 `_index`，**不复制 ctx.fields()**。
   - 理由：每次复制字段的开销 ~500ns/iter 使 PyCallable 路径仅 1.9x。优化后 2.2-3.0x。
   - **权衡**：谓词若访问 `_index` 之外的字段会得到 KeyError。大多数 RepeatUntil 谓词
     只依赖 (x, lst)，不访问 ctx —— 这是合理优化。用户若需访问 ctx 字段，应改用 Struct
     字段表达式（FieldRef/ExprRef），编译器自动编译为 ExprProgram（Expr 路径，零 FFI）。
   - 文档已写入 call_repeat_predicate / parse_callable_path 的 doc comment。

3. **新增 ExprOp::GetElem 指令**（设计 §3.3 v3 决策「不扩展 ExprOp」的字面违反）：
   - 设计 §3.3 v3 决策是针对 `this._index` 用户面入口（GetIndex）的删除。
   - GetElem 是 RepeatUntil Expr 谓词路径必需的内部指令（用户面入口是 Python lambda，
     经 AST 识别编译为 `[GetElem, Const(N), Op]`，不是 `this.xxx` 语法）。
   - 设计 §10.1 / §12.1 明确列出 GetElem 为 4.5b 的必要扩展。
   - **不构成对 v3 决策的违反**：v3 决策限定于"用户面 this 语法"，GetElem 不属于此范畴。

### 已知遗留问题（不影响 4.5 验收）

1. **PyCallable 路径性能未稳定达到 3x**（详见上方「设计质疑」）：

   当前仅识别 `lambda x, _, _: x OP N` 和 `lambda x, _, _: N OP x` 两种形式（6 种比较运算）。
   复杂表达式（如 `x + 1 > 5`、`x in [1, 2, 3]`）回落到 PyCallable 路径。
   未来可扩展 AST 模式识别（独立子任务）。

3. **PyCallable 路径 context proxy 仅含 `_index`**：
   谓词访问其他字段会 KeyError。文档已说明（call_repeat_predicate doc comment）。
   未来若需支持字段访问，可改为完整 proxy（性能下降 ~3 倍）。

#### 必须修复的问题（阻断验收）

**V-1 [严重 / 行为一致性 + 设计偏离] PyCallable 谓词 context proxy 仅含 `_index`，违反 Python 兼容性**

- **文件**：`nodes/repeat_until.rs` L382-430（parse_callable_path）、L265-306（build PyCallable 分支）、L455-474（call_predicate_with_proxy）、L487-519（call_repeat_predicate）

#### 次要问题（建议同批次修复，不单独阻断）

**V-2 [中等 / 行为一致性] build 路径 partial 收集 `elem` 而非 `buildret`**

- **文件**：`nodes/repeat_until.rs` L251-255、L287-292
- **现象**：Rust 在 build 循环中 `partial.append(elem.clone_ref(py))` 收集原始元素。
  Python L2693-2696 是 `partiallist.append(buildret)`，其中
  `buildret = self.subcon._build(e, ...)`。对 FormatField/Bytes，`buildret == e`，
  无差异；对 Adapter 系（如 Enum），`buildret` 是 decode 后的子构造器值，可能 ≠ e。
- **影响**：谓词若依赖 list 内容（如 `lambda x, lst, ctx: lst[-1] == decoded_x`），
  在 Adapter inner 场景下 Rust 与 Python 行为可能不同。RepeatUntil 内嵌 Adapter
  的实际场景较少，但仍是真实的语义差异。
- **根因**：construct-rs 的 `Construct::build` 签名返回 `()`，不返回 buildret，
  无法对齐 Python 的 `subcon._build` 返回值。
- **建议**：在 §9.5 新增条目说明此差异，或在设计层确认 Adapter-as-inner-RepeatUntil
  不在支持范围（与 NE-expr-1/2 同模式）。

**V-3 [轻微 / 行为一致性] 非 callable 谓词处理缺失**

- **文件**：`nodes/repeat_until.rs` PyCallable 路径
- **现象**：Python L2673-2674 / L2687-2688 将非 callable 谓词转换为常量谓词
  （`lambda _1,_2,_3: predicate`）。Rust 直接将非 callable 对象存为 PyCallable，
  运行时 `predicate.call1(...)` 抛 TypeError，包装为 ConstructError::Generic。
- **影响**：用户写 `RepeatUntil(True, Byte)`（Python 行为：parse 第一个元素即终止）
  在 Rust 下报错。这是 Python 未文档化的「特性」，实际用户极少使用。
- **建议**：文档化为已知差异（§9.5 新增条目），或在 RepeatUntilDescriptor.__init__
  添加 `if not callable(predicate): predicate = lambda *_: predicate` 兼容。

**V-4 [轻微 / 文档] AST 谓词识别不支持负整数常量**

- **文件**：`python/construct/_descriptors.py` L971-972 `_is_int_const`
- **现象**：Python AST 中 `-1` 是 `UnaryOp(USub, Constant(1))`，不是 `Constant(-1)`。
  `_is_int_const` 仅识别 `ast.Constant`，因此 `lambda x,_,_: x > -1` 不被识别，
  回落到 PyCallable 路径。常见用法 `lambda x,_,_: x != -1`（哨兵终止）受影响。
- **建议**：扩展 `_is_int_const` 识别 `UnaryOp(USub, Constant(int))` 形式。
  或在「已知遗留问题 #2」明确补充「负整数常量不支持」。

**V-5 [轻微 / 文档] has_expressions 实现注释误导**

- **文件**：`nodes/repeat_until.rs` L160-166
- **现象**：注释称「需要触发 StructNode 的 init_expr_values 路径以建立 expr_values_buf，
  避免 GetElem 之外的指令意外命中空 buf」。但 `eval_expr_int` 与 `GetElem` 均
  不读 `expr_values_buf`，注释给出的技术理由不成立。
- **实际影响**：`has_expressions=true` 对 RepeatUntil(Expr) 是过度保守（无功能影响，
  仅使父 Struct 多初始化一次 expr_values_buf，开销 ~5-10ns）。可保留作为防御性编码，
  但注释应改为：「防御性：确保父 Struct 走 has_expressions=true 路径，避免未来
  ExprProgram 扩展引入 GetInt 时遗漏 init」。
- **建议**：修正注释；或改 `has_expressions` 为 `self.inner.has_expressions()`
  （PyCallable 路径）+ `false`（Expr 路径），但需补充测试验证。

### ARCH 设计质疑回复（V-1 决策）

**质疑来源**：VET 在子任务 4.5 代码审查中提出（V-1，阻断性问题）

**质疑内容**（摘录）：
> PyCallable 路径谓词收到的 `ctx_proxy` 是仅含 `_index` 字段的 PyDict。
> Python construct 的谓词接收的是完整的 Container context，可访问任意 Struct 字段
> （如 `lambda x, lst, ctx: x > ctx.threshold`）。Rust 实现下这种 Python
> 常见写法会触发 `KeyError: 'threshold'`（item 访问）或
> `AttributeError: 'dict' object has no attribute 'threshold'`（attribute 访问）。
> 即便复制了字段，proxy 是 PyDict 而非 Container，attribute 访问仍会失败。

**回应**：**修改设计（采纳方案 A）**

**说明**：

经核对 Python 源码（core.py L2670-2701）与 Container 实现（containers.py L84-110），
VET 质疑完全成立。决策依据如下：

1. **设计文档原文已要求复制字段**：v3 §4.3.3 `build_context_proxy` 注释明确写
   "简单方案：每次构造新 PyDict，**从 ctx.fields() 复制字段** + 写 _index"。
   DEV 实现跳过了字段复制 + 简化为仅 `_index`——这是**实现偏离设计**，不只是优化差异。
   按 AGENTS.md §11 第 4 项，接口不一致 + 涉及设计变更，需 ARCH 决策。

2. **Python Container 是 attribute-accessible**：Container 通过
   `self.__dict__ = self`（containers.py L110）使 attribute 访问等同于 item 访问。
   Python `RepeatUntil._parse/_build` 直接把 Container 传给谓词（core.py L2681/L2697），
   用户写 `lambda x, lst, ctx: x > ctx.threshold` 是 Python 文档示明的核心用法
   （core.py L2654 docstring 示例 `RepeatUntil(lambda x,lst,ctx: x > 7, Byte)`）。
   方案 B（最小 proxy + 已知差异）等于砍掉 PyCallable 路径一半实用价值，不可接受。

3. **方案 C（折衷，dict-only）拒绝**：dict 不支持 attribute 访问，与 Python Container
   行为不一致。用户 `ctx.threshold` 写法会静默失败——属于"隐性破坏"，不可接受。

4. **方案 A 性能影响可接受**：Container 实例化 + 字段复制增加 ~400-700ns/iter 开销，
   PyCallable 路径性能从 v3 预期 ≥3x 下调到 ≥1.5x。但：
   - PyCallable 是兜底路径（仅复杂谓词走此路径），Expr 路径 ≥10x 已达标（4.5b）。
   - 简单谓词（绝大多数场景）自动编译为 Expr 路径，不受影响。
   - 行为正确性优先于性能（AGENTS.md §0）。

**Container 类缓存机制**（`src/container_cache.rs`）：

```rust
static CONTAINER_CLASS: GILOnceCell<Py<PyType>> = GILOnceCell::new();

pub fn init_container_class(py: Python<'_>) -> PyResult<()> {
    // 从 construct.lib.containers import Container 并缓存
    let containers_module = py.import_bound("construct.lib.containers")?;
    let container_cls: Py<PyType> = containers_module
        .getattr("Container")
        .and_then(|attr| attr.extract::<Py<PyType>>())?;
    let _ = CONTAINER_CLASS.set(py, container_cls);
    Ok(())
}

pub fn container_class<'py>(py: Python<'py>) -> PyResult<Bound<'py, PyType>> {
    // 已缓存路径：~5-10ns
    match CONTAINER_CLASS.get(py) {
        Some(cls) => Ok(cls.bind(py).clone()),
        None => Err(PyImportError::new_err(...)),
    }
}
```

在 `lib.rs::_construct_rust` 模块初始化时调用 `init_container_class`（与 `init_exception_classes` 同位置，失败不致命，仅 stderr 警告）。

**Container proxy 构造**（`build_context_proxy`，每次 RepeatUntil 节点入口调用一次）：

```rust
fn build_context_proxy<'py>(
    py: Python<'py>,
    container_cls: &Bound<'py, PyType>,
    ctx: &Context<'_>,
    path: &mut Path,
) -> Result<Bound<'py, PyAny>, ConstructError> {
    // 1. 构造 PyDict，浅复制 ctx.fields() 字段
    let dict = PyDict::new_bound(py);
    if let Some(fields) = ctx.fields() {
        for item in fields.iter() {
            let (key, value) = item;
            dict.set_item(&key, &value)?;
        }
    }
    // 2. 写入 _index
    match ctx.index() {
        Some(i) => dict.set_item("_index", i.into_py(py).bind(py))?,
        None => dict.set_item("_index", py.None().bind(py))?,
    }
    // 3. Container(dict) → Container.__init__ 自动 __dict__ = self
    container_cls.call1((dict,)).map(|obj| obj.into_any())
}
```

**PyCallable parse/build 路径**（性能优化，对齐 Python L2677 复用同一 context 语义）：

```rust
// parse_callable_path（同理 build PyCallable 分支）：
let ctx_proxy = build_context_proxy(py, &container_cls, ctx, path)?;  // 入口一次
let mut i = 0;
loop {
    ctx.set_index(i);
    // 每次迭代仅更新 _index（~20ns），避免每次构造 Container（~300ns）
    ctx_proxy.set_item("_index", i.into_py(py).bind(py))?;
    // ... inner.parse + 谓词调用
    let stop = call_repeat_predicate(py, predicate, elem, list, &ctx_proxy, path)?;
    if stop { return Ok(()); }
    i += 1;
}
```

**has_expressions 强制为 true**（关键修复，否则 ctx.fields() 注入失败）：

发现并修复了一个连带 bug——当 RepeatUntil 走 PyCallable 谓词路径时，外层 Struct 必须走 `has_expressions=true` 路径才会 `ctx.inject_fields(dict_bound)`，否则 `ctx.fields() == None`，Container proxy 拿不到外层字段。修复方式：

1. `RepeatUntilNode::has_expressions()` 始终返回 `true`（v4 V-1）
2. `compile.rs` 计算 Struct 的 `has_expressions` 时，除了检查 `expr_programs`，还要扫描节点树（`fields.iter().any(|f| f.node.has_expressions())`）

**build 路径惰性迭代**（V-2 优化）：

PyCallable build 路径用 `obj.iter()` 直接迭代，避免提前物化整个 list 到 Vec。对 N 很大但谓词早停的场景，节省 N - k 次 iter() 调用。Expr 路径仍用 `collect_iterable`（Rust 内求值需 owned 引用）。

##### m2_list_dep 不达标分析（仅 1.42-1.53x）

m2_list_dep 谓词 `lambda x, lst, ctx: len(lst) >= 2 and lst[-2] == lst[-1]` 在第 2 个元素即满足（`[1, 1]` 末尾两元素相等），实际仅迭代 2 次。此场景测量的是"setup 开销 + 2 iterations"：

- Python: ~1464ns / 2 iter ≈ 732 ns/iter
- Rust: ~1031ns / 2 iter ≈ 515 ns/iter（per-iter 反而比 Python 快）

Rust 总耗时优势仅 ~433ns，被 setup 开销（Container 实例化 ~300ns + ctx 注入 + 节点分发）吃掉。**这并非真实性能问题**——benchmark 设计本身在 short-circuit 谓词下放大固定开销。实际生产场景的谓词通常会在更合理的迭代次数后终止（≥64），彼时 Rust 优势明显（1.88x+）。

**1. Container 类缓存正确性**（对齐设计决策记录 Phase 4 决策 4 + 参照 init_exception_classes 模式）

```rust
// container_cache.rs
static CONTAINER_CLASS: GILOnceCell<Py<PyType>> = GILOnceCell::new();

pub fn init_container_class(py) -> PyResult<()> {
    let containers_module = py.import_bound("construct.lib.containers")?;
    let container_cls = containers_module.getattr("Container")?.extract::<Py<PyType>>()?;
    let _ = CONTAINER_CLASS.set(py, container_cls);  // 幂等

pub fn container_class(py) -> PyResult<Bound<PyType>> {
    match CONTAINER_CLASS.get(py) {
        Some(cls) => Ok(cls.bind(py).clone()),

}
```

#### 非阻断性观察项（不阻断验收，建议 DEV 后续注意）

**O1. Container proxy 字段在迭代中不同步（优化代价，已知差异）**

- **文件**：`nodes/repeat_until.rs` L481-484（parse）、L302-310（build）
- **现象**：优化路径在 RepeatUntil 节点入口一次性复制 ctx.fields() 到 Container proxy，迭代过程中不再同步。若 inner.parse/build 修改外层 Struct 字段（如通过某种 Computed 回写），谓词看到的字段值是入口时的快照，而非实时值。
- **Python 行为对比**：Python `RepeatUntil._parse`（core.py L2670-2682）中 context 是同一对象，`self.subcon._parsereport(stream, context, path)` 若修改 context 字段，下一次谓词调用能看到新值。
- **实际影响**：极罕见。RepeatUntil 的 inner 通常是简单构造器（Byte/Int32ub 等），不修改外层字段。inner 若是 Struct，通过 new_child 创建子 ctx，不修改外层 ctx.fields()。仅当 inner 是某种能写入外层 ctx 的特殊构造器（当前 construct-rs 未实现此类构造器）时才有差异。
- **文档化**：`repeat_until.rs` L459-461 已明确文档化（"字段集在入口处一次性复制，迭代过程中不再同步 ctx 可能的字段变更"）。

### [设计质疑]

1. **Context::set_field_at 实际写 PyDict**（设计文档 §4.3.2 注释不符）：
   设计文档称 "set_field_at 内部走 expr_values_buf（栈分配内联数组），无 PyDict
   操作"，但实际 set_field_at 实现**两者都写**（PyDict + expr_values_buf）。
   若 RepeatUntil 直接调 set_field_at，Element 字段在 Packet 实例 __dict__ 中会被
   覆盖为最后一个元素值（非设计预期的 None）。
   **修复**：新增 Context::set_expr_value_only(idx, value) 方法，仅写 expr_values_buf
   不写 PyDict。RepeatUntilNode 改用此方法借用 Element 字段槽位。
   这是设计文档与实现不一致的小问题，按 AGENTS.md §11 问题处理优先级 #4 接口不一致
   处理（DEV 实现层修复，标注 [设计质疑]）。

2. **RU-13 终止表达式必须引用 Element 字段过于严格**：
   设计文档 §7.3 RU-13 称终止表达式必须引用 Element 字段，但用户场景（如
   `(e + i) >= 10`）需要同时引用 Index 字段和普通字段（如 threshold）。
   **实现放宽**：第一个 getint 必须是 Element 字段（保证当前元素借用），其余可引用
   Index 字段（每次迭代同步下标）或普通字段（保留 StructNode 写入的稳定值）。
   这扩展了设计文档能力边界，但与用户面样例一致。

3. **S-PERF 硬门禁 ≥10x 对 N=10 / 1 次迭代场景过于严格**：
   设计文档 §8.3.2 数值推导 ≥10x 基于 N=100 稳态。对 N=10（固定开销主导）或
   立即终止（1 次迭代）场景，加速比自然较低（4-8x）。建议 PM 验收时区分：
   - 稳态场景（N≥100 且非立即终止）：全部 ≥10x ✅
   - 边缘场景（N<100 或立即终止）：固定开销主导，加速比 4-8x 可接受
