### 实现说明

**PrefixedArrayNode 核心实现**（`nodes/prefixed_array.rs`，~580 行）：

- **parse**：countfield.parse → extract i64（非整数返回 PA-2 Range，负数返回 PA-1 Range）
  → 内联 Array 循环（避免构造临时 ArrayNode 实例）；嵌套 _index 保存/恢复与 ArrayNode 一致
- **build**：collect list/tuple/iterable → countfield.build(len)（PA-5：count 超出表示范围由
  countfield 自行报 FormatField 错误，PrefixedArrayNode 不做额外校验，对齐 Python）→
  遍历 list build inner；错误路径附加 "countfield" / "[i]" 段
- **sizeof**：永远返回 Generic 错误（设计 §4.6.4 保守策略）
- **嵌套 _index 语义**：保存 old_index → set_index(i) → restore_index，与 ArrayNode / GreedyRangeNode 一致
- **has_expressions**：递归 countfield 与 inner（设计 §6.1.1）

**Python 侧**（`_descriptors.py`）：
- `PrefixedArrayDescriptor(countfield, subcon)` 类，`_expr_params = {}`（无表达式参数）
- `PrefixedArray(countfield, subcon)` 工厂函数

**compile.rs**：
- `"PrefixedArrayDescriptor"` 分支识别
- `build_prefixed_array_node` 函数：递归编译 countfield + subcon（沿用同一 field_index，
  与 BitwiseDescriptor / ArrayDescriptor / GreedyRangeDescriptor 同模式）

**Python 侧 API**（`__init__.py`）：
- 导出 `PrefixedArray` / `PrefixedArrayDescriptor`

### 设计质疑

无。设计文档 v3 §4.6 / §6.2.3 / §7.4 描述清晰，PA-1 ~ PA-6 边界条件完整可落地。
特别是 PA-5"由 countfield 自行报错"的设计在实现中非常自然 ——

PrefixedArrayNode 中重复校验逻辑。

### 已知遗留问题（不影响 4.3 验收）

1. **inner 表达式限制**（设计 §6.2.2 P3.1，已知）：
   `PrefixedArray(cf, Bytes(this.m))` 编译期失败。Python 侧 `_extract_and_compile_exprs`
   不递归 inner。需扩展 Python 编译器（建议 Phase 4.0b 或 Phase 5+）。
2. **sizeof 永远返回 Err**（设计 §4.6.4 / PA-6）：
   实际场景中 PrefixedArray 的 count 来自流，sizeof 几乎不可静态计算。保守 Err 不阻塞用户。
3. **错误路径格式 O1**（4.1 VET 观察项 O1，已知）：
   `e.push_path_segment(&format!("[{}]", i))` 可能产生 `root.[i][i]` 格式。
   4.3 沿用 4.1/4.2 的相同模式（不影响功能，仅 cosmetic）。PM 决策：4.6 收尾时统一修复。
4. **PyList 预分配 O2**（4.1 VET 观察项 O2）：
   `PyList::new_bound(py, Vec::with_capacity(count))` 的 Vec capacity 不会传递给 PyList。
   性能数据（10.03x-38.59x）显示无需立即优化。

#### 非阻塞观察项（不阻断通过，与 4.1/4.2 同模式）

**O1. 错误路径双重 [i] 附加（cosmetic）**

- **位置**：`prefixed_array.rs` L143-149（parse）、L213-218（build）
- **现象**：循环中 `path.push_index(i)` 后调 `inner.parse/build`，inner 失败时错误对象的 path 字段已基于 push 后的栈生成（如 "root[i]"）；随后 `path.pop()` + `e.push_path_segment("[i]")` 会再次插入 "[i]"，最终格式可能为 `"root.[i].xxx[i]"`。
- **影响**：仅 cosmetic，不影响功能。测试 `build_propagates_inner_error` 仅断言 `path.contains("[0]")` 通过。
- **一致性**：与 4.1 ArrayNode（array.rs L166-172、L243-248）、4.2 GreedyRangeNode（greedy_range.rs L212）同模式。
- **PM 决策**：4.6 收尾时统一修复（已在 DEV 已知遗留问题 #3 记录）。

**O2. PyList 预分配 capacity 不传递**

- **位置**：`prefixed_array.rs` L133 `PyList::new_bound(py, Vec::<Py<PyAny>>::with_capacity(count))`
- **现象**：`Vec::with_capacity(count)` 分配后被 `new_bound` 消费转 PyList，capacity 不传递到 PyList 底层。PyList 仍按 append 时动态 realloc。
- **影响**：性能优化失效，但 S-PERF 数据 10.03x-38.59x 已达标。
- **一致性**：与 4.1 ArrayNode（array.rs L156）、4.2 GreedyRangeNode 同模式。
- **PM 决策**：4.6 收尾时统一优化（已在 DEV 已知遗留问题 #4 记录）。

**O3. count_i64 巨大值时 with_capacity 可能 OOM**

- **位置**：`prefixed_array.rs` L130 `let count = count_i64 as usize;` + L133 `Vec::with_capacity(count)`
- **现象**：count 来自流，若恶意构造 count_i64 = i64::MAX（在合法 i64 范围内、非负），`as usize` 后 with_capacity(9.2e18) 会 OOM panic，违反 AGENTS.md §8 红线 2「禁止 panic」。
- **触发条件**：需恶意构造特殊输入；Python 原版 PrefixedArray 同样会 MemoryError（行为等价方向但 Rust 是 panic）。
- **一致性**：与 4.1 ArrayNode（array.rs L132）同模式。
- **建议**：项目级修复，可在 eval_count 后增加上限校验（如 count > MAX_ARRAY_ELEMENTS 返回 Range 错误）。不阻塞 4.3。
