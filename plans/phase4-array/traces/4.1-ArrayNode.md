### S-PERF 性能数据

测试环境：Python 3.14.2 / Windows / release build (lto=fat, codegen-units=1)
测量口径：`maturin develop --release` 安装后 Python timeit（子进程隔离），
取 min(repeat=5) × number=1000

| 场景 | Python ns/call | Rust ns/call | 加速比 | S-PERF 出口 (≥10x) |
|------|---------------:|-------------:|-------:|:------------------:|
| Array(100, Int8ub) parse | 23,875 | 2,087 | **11.44x** | PASS |
| Array(100, Int8ub) build | 24,421 | 1,138 | **21.46x** | PASS |
| Array(10, Struct{2字段}) parse | 20,628 | 1,665 | **12.39x** | PASS |
| Array(10, Struct{2字段}) build | 18,580 | 865 | **21.48x** | PASS |

派生指标：
- 加速比按场景排序（由高到低）：build(2 个) > parse(2 个)，符合预期（build 无 PyLong 分配开销）
- 低于 4x 的场景：无
- parse/build 比率（py）：0.98x（parse ≈ build，Python 两端都被解释器开销主导）
- parse/build 比率（rs）：1.83x（parse > build，因 parse 需分配 PyLong + PyList，build 仅迭代已有对象）

parse/build 方向差异说明：construct-rs 中 build 比 parse 快（1.83x），
而 Python 中两者相近（0.98x）。**这是性能优势的体现而非异常**：
construct-rs 的 build 路径不分配 Python 对象（仅迭代已有 list + 写字节），
parse 路径需为每个元素分配 PyLong 并 append 到 PyList。
Python 两侧均受解释器循环开销主导，差异不明显。
benchmark 脚本（experiments/phase4_bench_array.py）的 [WARN] 标记是机械的方向一致性
检查，此场景下属于预期的"方向不一致"。

#### 非阻断性观察项（不阻断验收，建议 DEV 后续优化或注意）

**O1. 错误路径重建在 Array 索引段上产生不理想格式**（cosmetic）

`nodes/array.rs` parse/build 错误路径：
```rust
Err(mut e) => {
    path.pop();
    e.push_path_segment(&format!("[{}]", i));   // 用 push_path_segment 拼接 "[i]"
    ...
}
```

`push_path_segment` 设计用于 StructNode 字段名插入（`root.field.suffix` 模式）。当 e.path 已含 `[i]` 后缀（来自 FormatFieldNode 在 path 栈含 Index(i) 时生成的 `path.to_string()="root[i]"`），调用 `push_path_segment("[i]")` 会通过 `strip_prefix("root")` → `format!("root.{}{}", "[i]", "[i]")` 生成 `"root.[i][i]"`，而非理想的 `"root[i]"`。

**影响**：仅错误消息中的 path 字段格式不理想（如 `"root.[1][1]"`）。错误本身正确传播，message 字段正确，仅 path 字段格式异常。`parse_const_insufficient_returns_stream_error` 测试只校验 message 不校验 path，故未暴露此问题。

**建议修复**（非阻断）：直接移除 `e.push_path_segment(&format!("[{}]", i))` 一行——错误来自 inner.parse 时 path 栈已含 Index(i)，inner 已经把 path 写成 "root[i]"，无需 ArrayNode 再补充。或改用专门处理索引段的辅助方法。

**O2. PyList 预分配实际未生效**（performance note）

`nodes/array.rs` parse：
```rust
let list = PyList::new_bound(py, Vec::<Py<PyAny>>::with_capacity(count));
```

`Vec::with_capacity(count)` 分配 Vec 的容量，但 `PyList::new_bound(py, iter)` 通过迭代器构造 PyList，Vec 的 capacity 不会传递给 PyList 内部分配。实际行为等价于 `PyList::empty_bound(py)` + N 次 `append`（amortized O(1)，可能 realloc）。

**影响**：性能仍达 12.97x（parse），满足 S-PERF ≥10x。设计 §4.1.2 注释提到的"一次性预分配"在此实现中未真正生效。

**建议优化**（非阻断，性能已达目标，可延后）：用 `PyList::new_bound(py, std::iter::repeat(py.None()).take(count))` 真正预分配 N 个槽位，然后 `list.set_item(i, elem)` 替代 `append`。

**O3. array.rs doc comment 残留 `this.length` 未标注"Python 语法"**（doc style）

`nodes/array.rs` L12 与 L41 的 doc comment 使用 `Array(this.length, Byte)` 作为 CountSource::Expr 的示例，未按 Phase 2 决策 1 标注"**Python 语法**"。性质与 REV v3 复审中的 D4 同级（doc comment 内部一致性）。

**建议**：与 D1/D2/D3/D4 一并在 Phase 4 收尾时统一清理。
