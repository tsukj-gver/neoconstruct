### ARCH 设计说明

**核心决策摘要**（详见设计文档 §2）：

1. **A1**：Array 系列 Node 的 inner 用 `Box<Node>`（沿用 BitwiseNode 模式）
2. **A2**：count 来源编译期分类为 `CountSource::{Const, Expr}`，复用 ExprProgram
3. **A3**：`_index` 通过 Context 的栈分配字段 `Option<usize>` 传递（不走 PyDict）
   —— 嵌套数组语义：内层覆盖外层，循环结束后恢复
4. **A4**：`StopFieldError` 用 `ConstructError::StopField` 哨兵变体（不引入 panic）
   —— StructNode/GreedyRangeNode 捕获视为正常终止
5. **A5**：RepeatUntil 谓词两条路径（ExprProgram 快路径 + PyCallable 兜底）；
   **首版建议仅实现 PyCallable**（功能完整，性能延后）
6. **A6**：PrefixedArray 用独立 Node（不依赖未实现的 FocusedSeq/Rebuild）
7. **A7**：ListContainer 直接返回原生 `list`（不引入新 Python 子类）
8. **A8**：`discard` 用编译期 bool 标志（运行时分支预测 100% 命中）

**基础设施扩展**：
- `ParseStream::seek(pos, path)` —— GreedyRange 硬依赖（失败回退）
- `Context._index: Option<usize>` + set_index/clear_index/index 方法
  （嵌套语义通过 new_child 继承父 _index）
- `ExprOp::GetIndex` 指令 + 编译期翻译 `this._index` → `("getindex",)`
- 4 个错误变体：`Range` / `Repeat` / `StopField` / `IndexField`
- Python 异常类映射扩展（init_exception_classes 缓存 4 个新类）

**关键修改点**（DEV 实现时注意）：
- `StructNode::parse/build` 增加 StopField 捕获分支（struct_node.rs 唯一修改点）
- `Context::new_child` / `new_child_placeholder` 需继承父 `_index`
- `Context` 所有构造函数初始化 `_index = None`
- `error.rs::build_test_classes` 测试辅助同步增加 4 个测试类

**遗留问题（6 个 PM 决策点）**：

1. **PM 决策 1**：RepeatUntil Expr 谓词路径是否在 Phase 4 实现？（建议延后）
2. **PM 决策 2**：Array count 表达式支持范围（建议与 Bytes 表达式长度同路径，一并实现）
3. **PM 决策 3**：PrefixedArray sizeof 是否支持静态计算？（建议保守 Err）
4. **PM 决策 4**：ListContainer 子类是否引入？（建议不引入）
5. **PM 决策 5**：path.push_index 是否首版用 P0-3 风格优化？（建议首版保留 push/pop）
6. **PM 决策 6**：sizeof 签名是否增加 py 参数？（建议用 with_gil，不改签名）

**建议的子任务拆分**（PM 参考）：

#### 严重问题（必须修复，阻断通过）

**P1. `Node::has_expressions()` 对 `StopIf(Expr)` 返回 false —— 设计理由错误（§6.1.1）**

设计文档 §6.1.1 写道：
> `Node::Index(_) | Node::StopIf(_) => false`
> StopIf(Expr) 节点自身持有表达式程序，但其表达式不引用 Struct 字段

**这是错误的判断**。`StopIf(this.x == 0)` 中的 `this.x` 明显引用 Struct 字段 x。
经由 `struct_ref.rs` L171/L194 的 `root.has_expressions()` 路径可知：
当 StructRef 引用一个含 `Array(5, StopIf(this.x > 10))` 字段的 Struct 时，
`root.has_expressions()` 会递归到 StopIf，若返回 false 则整个子树返回 false
（假设 Array count 是常量），导致 StructRef **不创建 child context**、
**不调用 init_expr_values**，StopIf 的 `eval_expr_int` 求值时 GetInt 会命中
`ExprContext`/`ExprFieldMissing` 错误。

设计 §6.1.1 最后一段虽提到"DEV 实现时验证此路径"，但作为设计文档应明确：
`Node::StopIf(s)` 的 `has_expressions()` 必须返回
`matches!(s.cond, StopIfCondition::Expr(_))`，而非无条件 false。

→ **建议修改方向**：StopIf(Expr) 返回 true；StopIf(Always/Never) 返回 false；
Index 返回 false（确实不引用字段）。

---

**P2. RepeatUntil build 方向的 discard 语义与 Python 不一致（§4.3.4）**

Python `RepeatUntil._build`（core.py L2684-2701）：
```python
for i,e in enumerate(obj):
    buildret = self.subcon._build(e, stream, context, path)
    if not discard:
        retlist.append(buildret)
        partiallist.append(buildret)   # ← 仅在非 discard 时 append
    if predicate(e, partiallist, context):  # partiallist 在 discard 时为空
        break
```

设计 §4.3.4 的 build 伪代码：
```rust
partial.append(elem.clone_ref(py)).map_err(...)?;  // ← 无条件 append，不看 discard
let stop = call_repeat_predicate(py, predicate, elem_bound, partial.as_any(), ctx)?;
```

**行为差异**：discard=True 时，Python 谓词收到空 list，设计收到累积 list。
对于依赖 list 内容的谓词（如 `lambda x,lst,c: lst[-2:] == [0,0]`），
discard=True 与 discard=False 会产生**不同的终止时机**。

边界清单 §7.3 RU-7 仅覆盖 parse 方向的 discard，**未覆盖 build 方向 discard**。

→ **建议修改方向**：build 循环内 `if !self.discard { partial.append(...) }`，
对齐 Python 语义；补充 RU-7-build 边界条目。

---

**P3. Array 表达式 count 的编译路径未设计（§6.2.2）**

设计 §6.2.2 的 `build_array_node` 对表达式 count 明确返回错误：
```rust
return Err(ConstructError::Compilation {
    message: "Array expression count not yet supported in build_array_node".to_string(),
});
```

但 PM 决策点 2（§12.2）建议"应一并实现"，且 CountSource::Expr 变体已设计、
ExprProgram 基础设施已具备（Bytes 表达式长度已实现相同模式）。
设计把核心编译路径留作 placeholder，是**设计未完成**。

更关键的是：**嵌套 Array（Array 内 Array）的表达式索引映射**未明确——
内层 Array 的 count 表达式如何存入 expr_programs？Python 侧 `_compile_expr_tree`
如何为非直接字段的 subcon 分配 field_index？这些编译期问题需要在设计中回答，
不能推给 DEV。

→ **建议修改方向**：参照 compile.rs L273-281（BytesDescriptor 表达式长度编译路径），
给出 ArrayDescriptor 的 count 表达式编译完整路径；明确嵌套 subcon 的
expr_programs 键名空间（如 "count"、"cond" 共存于同一字段的 dict）。

#### 中等问题（建议修复，不强制阻断）

**M1. GreedyRange 吞掉所有非 StopField 错误（§4.2.2）—— 行为差异未充分告知**

Python GreedyRange 区分三类异常（core.py L2609-2614）：
- `StopFieldError` → 正常终止
- `ExplicitError` → 向上抛出
- 其他 `Exception` → seek 回退 + 正常终止

设计 §4.2.2 把"其他错误"全部 seek 回退 + 终止。construct-rs 无 ExplicitError
等价物，意味着 **inner Struct 字段类型错误（如 FormatField 解析失败）也会被
静默吞掉**，用户得不到任何错误反馈，只是 GreedyRange 提前终止。

这在功能上可能"接近"Python（Python 的 Exception 也包括 FormatFieldError），
但 Python 用户至少能通过 `construct.ExplicitError` 标记不可恢复错误。
construct-rs 没有这个逃生舱。

→ **建议**：要么在设计文档中明确这是已知行为差异（写入 §9.5 已知差异表），
要么引入 ConstructError::Explicit 等价变体（影响较大，建议前者）。

---

**M2. PrefixedArray build 时 count 溢出 countfield 表示范围的行为含糊（§7.4 PA-5）**

边界 PA-5 写道："build 时 list 长度 > countfield 容量 → 取决于 countfield 实现
（如 Byte 溢出回绕）"。

**"回绕"说法不准确**。Python 中 countfield 是 `FormatField`（如 Byte=Int8ub），
当 count=256 试图 `struct.pack(">B", 256)` 时会抛 `struct.error`，
被 construct 包装为 `FormatFieldError`/`StreamError`，**不是回绕**。

construct-rs 的 PrefixedArrayNode.build 直接调 `self.countfield.build(count, ...)`，
若 countfield 是 FormatFieldNode 且 count 超出表示范围，FormatFieldNode 应自行
报错（这是 FormatFieldNode 的责任）。但设计应明确这一行为契约，而非含糊地说"回绕"。

→ **建议修改方向**：PA-5 改为"count 超出 countfield 表示范围时，由 countfield
节点自行报错（如 FormatFieldError）；PrefixedArrayNode 不做额外校验"。

---

**M3. sizeof 表达式 count 的 GIL 获取路径不明确（§4.1.4）**

设计 §4.1.4 的 sizeof 伪代码：
```rust
CountSource::Expr(prog) => {
    crate::expr::eval_expr_int(prog, ctx, Python::with_gil(|py| py))? as usize
}
```

问题：
1. `Python::with_gil(|py| py)` 的生命周期：返回的 `Python<'_>` 与 with_gil 闭包
   的 GIL scope 绑定，在闭包外使用可能存在生命周期问题（需要 DEV 验证）。
2. sizeof 签名 `fn sizeof(&self, ctx: &Context<'_>)` 没有 py 参数，若 sizeof 在
   非 GIL 持有线程调用会 panic 或死锁——虽然实际 sizeof 总在 parse/build 内调用
   （已持 GIL），但设计未明确这一前置条件。

PM 决策点 6 把这归为"选项 A vs B"，但没给出明确推荐。设计应明确：
- sizeof 的调用契约（必须在 GIL 持有线程调用）
- 或修改 Construct trait 签名（影响全部节点，需 PM 决策）

→ **建议修改方向**：在设计文档中明确 sizeof 的 GIL 前置条件；
或推动 PM 决策修改 trait 签名。

---

**M4. S-PERF 出口标准对 RepeatUntil PyCallable 路径的适用性歧义（§8.2 vs 总纲）**

总纲 §S-PERF："Array parse/build ≥10x vs Python construct"。
设计 §8.2 预测 RepeatUntil(PyCallable) 仅 ≥3x，低于出口标准。

设计 §12.1（PM 决策点 1）建议首版仅 PyCallable、Expr 路径延后。
但若 RepeatUntil 首版仅 3x，是否满足 S-PERF 出口？

总纲的"Array parse/build"是否涵盖 RepeatUntil？还是仅指狭义 Array？
这是**出口标准的歧义**，会导致验收阶段争议。

→ **建议修改方向**：在设计或总纲中明确：
- 要么 RepeatUntil 的 Expr 路径必须在 Phase 4 实现（满足 ≥10x）
- 要么总纲明确"RepeatUntil 性能延后，不纳入 Phase 4 S-PERF 出口"

#### 小问题（不阻断，建议 DEV 实现时参考）

**S1. StopIfCondition::Always/Never 变体冗余（§4.5.1）**

`Always`/`Never` 可用 `Expr(Const(1))`/`Expr(Const(0))` 复用 Expr 路径，
减少枚举变体。Python `StopIf(True)` 中 True 是常量，编译为 Const(1) 自然。
当前设计增加两个变体是不必要的复杂度。

**S2. Context 添加 _index 字段污染通用性（§3.2）**

Context 之前是"字段无关"的通用容器。_index 是 Array 特定的状态，
直接作为 Context 字段破坏了纯净性。
替代方案：用 `expr_values_buf[MAX_INLINE_FIELDS - 1]` 作为 _index 保留槽位，
或在 Array 节点局部维护（但嵌套数组需要栈传递，复杂度更高）。
当前设计的字段方案更简单，但应在设计文档中讨论为何不选替代方案。

**S3. `this._._index` 表达式的处理未明确（§3.3）**

Python docstring（core.py L2956）展示 `this._._index+1` 用法——
显式访问父 context 的 _index。设计选项 A（new_child 复制 _index）使
`this._index` 在子 Struct 中直接可用，但 `this._._index`（显式父引用）
在 construct-rs 表达式系统中如何编译未明确。
若现有 ExprOp 无 parent 链访问指令，这是覆盖盲点。

**S4. build 方向 collect 到 Vec 的开销未列入性能假设（§8）**

ArrayNode/GreedyRangeNode/RepeatUntilNode/PrefixedArrayNode 的 build 均调用
`collect_iterable` 消费所有元素到 `Vec<Py<PyAny>>`，对 N=100 数组是
~800 字节堆分配 + 100 次 incref。性能假设 §8.1 未列出此开销。
可直接遍历 list.iter() 避免 collect（设计 §4.1.3 注释提到，但未纳入瓶颈分析）。

**S5. IndexField 错误变体"保留但不触发"（§3.4.4）**

设计明确说 IndexField "首版不触发"，IndexNode 在 _index=None 时返回 Py_None。
既然不触发，引入此变体是死代码。建议直接删除，未来需要时再加。

#### 独立架构判断（不被 Python 实现胁迫）

**A1. Node 变体数量评估：6 个变体合理**

考虑过合并方案：单一 `RepeatNode { inner, policy: RepeatPolicy }`，
其中 `RepeatPolicy = Fixed(count) | Greedy | UntilPred(pred) | Prefixed(countfield)`。
但 Prefixed 变体需 `countfield: Box<Node>`，使 RepeatPolicy 变得复杂
（enum 变体含 Box，大小不均），且 parse/build 流程差异大（Prefixed 需先解析
countfield），合并后 match 分支反而更混乱。
**当前 4 变体（Array/GreedyRange/RepeatUntil/PrefixedArray）+ 2 辅助（Index/StopIf）
是合理的边界**。

**A2. 不对齐 Python 的优化决策正确**

- ListContainer → 原生 list：✅ 正确（避免子类实例化慢路径）
- StopField 哨兵（非 panic）：✅ 正确（符合 Rust 错误处理习惯）
- _index 走栈字段（非 PyDict）：✅ 正确（性能分析 50x 加速有说服力）
- PrefixedArray 独立 Node（非 FocusedSeq+Rebuild 组合）：✅ 正确（避免依赖未实现模块）

**A3. 可优化但非缺陷的设计点**

- RepeatUntil Expr 谓词路径的 `_current_elem: Option<*mut ffi::PyObject>` 
  borrowed ptr 设计——设计 §4.3.2 承认复杂度，首版不实现是合理妥协。
  但 §10.1 提到 Expr 路径"仅支持整数元素"（PyLong_AsLongLong），
  这对 Struct 元素的 RepeatUntil 不适用——此限制应在设计文档中明确。

**A4. 整体设计成熟度**

设计的核心决策（A1-A8）方向正确，性能假设结构完整（瓶颈识别+可证伪预测+
验证方法），边界条件覆盖面广（54 条）。主要缺陷集中在**几个具体实现路径
未完成设计**（has_expressions 判断、Array 表达式 count 编译、RepeatUntil
build discard），以及**若干 Python 行为覆盖的细节遗漏**。这些都是可修复的，
不需要架构级重做。

### ARCH 修正说明（v2）

#### P1 修正（§6.1.1）

**根因**：v1 把 `has_expressions` 用于"决定 StructNode 是否创建带 PyDict 的 context"，
认为编译期 expr_programs 已能判断，所以 StopIf(Expr).has_expressions() 返回 false 无影响。

**REV 暴露的盲点**：`StructRefNode`（struct_ref.rs L171/L194）在**运行时**重新解析
schema 并通过 `root.has_expressions()` 决定是否创建 child context——这是运行时路径，
与编译期 expr_programs 完全独立。StopIf(this.x == 0) 的 this.x 引用 Struct 字段 x，
必须返回 true 触发 StructRef 创建 child ctx 并调用 init_expr_values。

**修正**：
```rust
Node::StopIf(s) => s.has_expressions(),    // 改为 false → 真实判断
// StopIfNode::has_expressions: matches!(self.cond, StopIfCondition::Expr(_))
```
并附完整说明（编译期 vs 运行时两套机制）。

#### P2 修正（§4.3.4）

**根因**：v1 伪代码 `partial.append(elem.clone_ref(py))?` 无条件 append，
未对齐 Python L2694-2696 的 `if not discard: ... partiallist.append(buildret)`。

**修正**：加 `if !self.discard` 守卫。补充 RU-8 边界条目说明对依赖 list 内容
的谓词（如 `lst[-2:] == [0,0]`）会产生不同终止时机（这是 Python 的语义）。

#### P3 修正（§6.2.2）

**根因**：v1 对表达式 count 直接返回错误（placeholder），未给出完整编译路径。

**修正**：参照 compile.rs L266-308 的 BytesDescriptor 表达式长度路径，给出完整设计：
1. Python 侧 ArrayDescriptor._expr_params 返回 {"count": self.count}
2. Rust 侧 build_array_node 从 expr_programs[field_index]["count"] 取 ExprOp 列表
3. 编译为 ExprProgram，构造 CountSource::Expr

**关键发现**：Python 侧 `_extract_and_compile_exprs`（_mixin.py L583-615）不递归 inner
subcon——这意味着 `Array(N, Bytes(this.m))` 与 `Bitwise(Bytes(this.m))` 一样在编译期失败。
v1 隐含假设可递归，v2 明确为已知限制（P3.1）+ 扩展方案（P3.2）。

#### M1 修正（§9.5 GE-1）

**修正**：新增 §9.5 已知差异表，集中管理所有 LC/IX/GE/RU-build/PA/NE-expr 条目。
GE-1 详述 ExplicitError 等价物缺失的决策（不引入，因当前无用户场景触发）+ 后续处理计划。

#### M2 修正（§7.4 PA-5）

**修正**：删除"回绕"误述，改为"由 countfield 节点自行报错"。
Python `struct.pack(">B", 256)` 抛 struct.error 被 construct 包装为 FormatFieldError，
construct-rs 的 FormatFieldNode 同样在超出表示范围时报错。

#### M3 修正（§4.1.4）

**修正**：明确 sizeof 的 GIL 前置条件（必须在已持 GIL 线程调用）+
Python::with_gil 闭包的正确写法（避免借用逃逸）。

#### M4 修正（§8.2/§8.3/§12.1）

**修正**：明确 S-PERF 出口对 RepeatUntil 的判定规则：
- "Array" 指狭义 Array（PM/ARCH 共识）
- PyCallable 路径 ≥3x 可接受（物理上限）
- Expr 路径 ≥8x，**必须在 Phase 4 验收前完成**（4.5b）

子任务拆分：4.5a（PyCallable，S-FUNC）+ 4.5b（Expr，S-PERF），4.5b 不可延后。

**V1（设计问题）：§3.3 ExprOp::GetIndex 的用户面入口设计缺失且违反决策 1**

**事实链**：

1. 设计文档 §3.3 标题："支持 `this._index` 表达式（如 `Array(3, Computed(this._index + 1))`）"
2. §3.3.3 描述："Python 侧编译器（`_compile_expr_tree`）识别 `this._index` 表达式节点，翻译为 `ExprOp::GetIndex` 元组 `("getindex",)`"
3. §3.3.2 把 `Computed(this._index + 1)` 作为 construct-rs 用户代码示例讨论行为差异

**违反点**：

- **决策 1 明确**："用户写 `Bytes(count)` 而非 `Bytes(this.count)`。字段名本身就是引用对象，编译期通过 `id()` 绑定到字段索引。**禁止在 construct-rs 设计和文档中使用 `this.xxx` 语法**"
- **表达式系统 §2.3** 已建立 FieldRef/ExprRef 类型系统：用户面表达式输入是 `_FieldDescriptor` / `_ExprRef` 对象，**不是 `this.xxx` 语法**
- **表达式系统 §3.3 `_compile_expr_tree`** 输入节点类型为 `_FieldDescriptor | _ExprRef | int | float`（表达式系统 L715），**不存在 `this._index` 这种节点类型**——设计文档 §3.3.3 描述的"识别 `this._index` 表达式节点"在 construct-rs 表达式系统中**永远不会发生**

**实证（已实现代码状态）**：

- `construct-rs/src/expr.rs` L282-283：ExprOp::GetIndex 已在 eval_expr_int 中实现
- `construct-rs/src/compile.rs`：parse_expr_ops_from_py 已增加 "getindex" 分支
- **Python 侧 `*.py` 文件 grep `getindex|GetIndex`：无结果**
- 即：**用户面没有任何语法能产生 `("getindex",)` 指令**，ExprOp::GetIndex 在当前实现中是**事实上的死代码**

这进一步证实设计缺陷：设计了 VM 指令，但用户面入口未设计（设计文档假设的 `this._index` 入口违反决策 1，且实际未实现）。

**为什么是设计问题而非文档表述问题**：

- 不是改几个字就能解决——需要决定 construct-rs 中用户**如何**在表达式中引用当前数组下标
- 影响已实现代码：4.1 子任务已落地 ExprOp::GetIndex 与 "getindex" 编译分支，但用户面入口缺失

- **选项 A**：让 `Index()` 构造器返回 FieldRef-like 对象（如 `_IndexRef`），可在表达式中使用：

  @dataclass
  class P(StructMixin):
      idx: int = rfield(Computed(Index() + 1))   # Index() 返回 _IndexRef
  ```

- **选项 B**：仅通过 IndexNode 暴露 _index（作为独立字段），**删除 ExprOp::GetIndex**：

  ```
  用户不能写 `Computed(Index() + 1)`。需同步删除 §3.3 全节、§9.4 `this._index` 行、compile.rs "getindex" 分支、expr.rs GetIndex 变体。

### ARCH 修正说明（v3）

#### V1 决策：删除 ExprOp::GetIndex（选项 B）

**根因**：v1/v2 设计的 `ExprOp::GetIndex` 指令声称支持 `this._index` 表达式，
但 Phase 2 表达式系统的输入节点类型只有 `_FieldDescriptor` / `_ExprRef` / `int` / `float`
（表达式系统 §2.3 / §3.3），**不存在 `this._index` 节点类型**。
Python 侧 `_compile_expr_tree`（`_mixin.py` L475-533）也没有产生 `("getindex",)` 元组的
分支。GetIndex 是事实上的死代码。

**决策（选项 B）**：删除 `ExprOp::GetIndex`，不扩展表达式系统。用户访问数组下标的机制：

| 用户需求 | construct-rs 写法 | 编译结果 |
|---------|------------------|---------|
| 取当前下标值（作为字段） | `i: int = rfield(Index())` | IndexNode.parse 读 `ctx.index()` |
| 在表达式中引用下标 | 先声明 Index 字段，再用字段名引用：`v: bytes = field(Bytes(i + 1))` | `[GetInt(idx_of_i), Const(1), Add]` |

**选项对比**：
- 选项 A（扩展表达式系统支持 `Index()` 在表达式中使用）：保留已实现的 Rust 代码，
  需补充 Python 侧 `_IndexRef` 类与编译逻辑。但 `Index` 在 Python construct 中本身
  是构造器（subcon），让它同时充当表达式引用会使语义混乱。
- **选项 B（删除 GetIndex，仅 IndexNode）**：需要回退已实现的代码（expr.rs GetIndex
  变体 + 8 个测试 + compile.rs "getindex" 分支），但保持表达式系统输入类型纯粹，
  与 Phase 2 "字段名即引用" 哲学一致。IndexNode + 字段引用已完整覆盖功能需求。
- 选项 C（新增内置函数 `current_index()`）：与 Python construct 的 `this._index`
  没有直接对应关系，引入新 API 表面。

选择 B 的理由：(1) YAGNI——表达式内引用下标是罕见场景；(2) IndexNode + 字段引用
已能覆盖功能需求；(3) 保持表达式系统纯粹；(4) 符合 Phase 2 "字段名即引用" 哲学；
(5) 用户心智模型清晰。

**对已实现代码的影响**（DEV 在新子任务中执行回退）：
