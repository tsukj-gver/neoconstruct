## PM 决策

1. RepeatUntil Expr 谓词路径：Phase 4 内完成，不延后
2. ListContainer：直接返回原生 list
3. PrefixedArray：独立 Node，不依赖 FocusedSeq/Rebuild
4. inner 表达式限制（如 Array(N, Bytes(this.m))）：编译期失败，与 Bitwise(Bytes(this.m)) 一致，后续阶段扩展

## S-PERF 出口标准（用户 2026-06-30 重审硬约束，不可逆）

### 用户面设计四原则（不可违反，违反即打回）

1. **禁止用户不可见的开销 + 隐藏决策路径**：用户面 API 表面必须能预测性能表现。不允许"白名单 + 兜底"二分设计、不允许"简单/复杂"分叉、不允许性能悬崖隐藏在 API 内部。

2. **Adapter 是用户主动选择的较慢路径，不是任何构造器的内部兜底**：用户主动选 Adapter = 显式接受性能折衷；想 ≥10x 就别用 Adapter。Adapter 不允许出现在 RepeatUntil / 其他构造器的实现路径中作为 fallback。

3. **禁用"谓词"术语**：RepeatUntil 的终止条件就是 Phase 2 表达式，与 `Bytes(count)` 中的 `count` 是表达式无本质区别。不允许用"谓词"暗示"接收 callable"。设计文档、代码、注释中统一改用"终止表达式"或直接"表达式"。

4. **只认 Phase 2 表达式语法**：RepeatUntil 终止表达式必须复用 Phase 2 已有的表达式系统（ExprProgram / ExprOp VM），不允许 RepeatUntil 自建表达式机制。重新造轮子一律打回。Phase 2 表达式无法描述的终止逻辑，用户面 API 不支持——用户须改用 Adapter（显式慢路径）。

### 推论

- RepeatUntil 用户面 API 不接收 Python lambda / callable
- RepeatUntil 终止表达式 100% 编译期翻译为 ExprProgram，运行期 Rust 内求值，零 FFI
- 不存在"AST 识别覆盖率"问题——用户根本不传 AST
- 不存在"复杂模式回落 PyCallable"问题——没有 PyCallable
- RepeatUntil 与 Adapter 是用户面 API 的两条独立路径，不在 RepeatUntil 内部交汇

### S-PERF 标准

| 标准 | 要求 |
|------|------|
| S-FUNC | 全部 Rust + Python 测试通过；Array 相关构造器行为与 Python construct 一致 |
| S-QUAL | clippy 零 warning + fmt 通过 |
| S-PERF | **全部 6 个构造器（Array / GreedyRange / PrefixedArray / RepeatUntil / Index / StopIf）× parse/build 双向 × 全场景，加速比 ≥10x**。无任何局部门禁豁免、无"兜底路径"豁免、无"特殊用例排除"。 |

### 场景矩阵硬要求（不允许"一个构造器一个 parse + 一个 build"）

每个构造器至少覆盖以下维度，**最少 10 个测量点（5 场景 × parse/build）**：

| 维度 | 要求 |
|------|------|
| 元素类型 | Int8ub / Int32ub / Struct{2} / Struct{N} / 嵌套构造器 至少 3 种 |
| 规模 | 小（N≤10）/ 中（N≈100）/ 大（N≥1000）至少 3 档，验证 O(n) 扩展性 |
| 字节序 | 大端 + 小端 + 有符号/无符号 至少 2 种 |
| 分支 | discard / count 类型 / countfield 类型 等该构造器的所有可配置分支 |
| 错误路径 | inner parse 错误、countfield 错误、流不完整 至少 2 种 |
| 嵌套组合 | 与其他构造器组合至少 2 种 |

RepeatUntil 额外要求：谓词路径全覆盖（不允许"简单 lambda / 复杂 lambda"二分），具体由 ARCH 重设计决定。

### 禁止事项（PM 验收硬规则）

1. 禁止用"物理上限"作为门禁豁免理由
2. 禁止用"兜底路径"作为门禁豁免理由
3. 禁止在 benchmark 中标记 "N=1024" 但实际只迭代 6/3 次（场景标签必须与实际工作量一致）
4. 禁止"特殊用例不计入硬门禁"——所有场景必须达标
5. 禁止局部门禁（不允许某构造器/某路径单独设低于 10x 的门禁）
6. 性能数据必须有逐项开销分析（Python 端 + Rust 端），不允许拍脑袋估算

## 重审状态（2026-06-30）

Phase 4 从 ✅ 全部通过 → 🔴 重审中。原因：

1. **4.5 框架级设计缺陷**：PyCallable 兜底路径违反 AGENTS.md §0 "一次 FFI" 核心原则（每迭代跨 FFI），AST 白名单无法穷尽用户面，"简单/复杂谓词"二分设计错误。需要 ARCH 重新设计谓词处理框架。
2. **门禁设定无物理推导**：3x（首版 §8.4 粗糙估算 500-1000ns/Python 调用 × 100 = 3-5x，取下限）和 1.5x（v4 借 V-1 下调）都没有逐项开销分析。Python 3.14 实测仅 270-300ns/调用，估算高估 2-3 倍。
3. **场景覆盖严重不足**：4.6 集成测试仅 27 场景（平均每构造器 ~4 个），4.6 性能 benchmark 仅 22 数据点（平均每构造器 ~4 个），远低于"每构造器 ≥10 测量点"硬要求。
4. **4.6 性能数据失真**：场景 19-22（ru_expr/ru_call）标 "N=1024" 但实际只迭代 6/3 次，谓词与数据不匹配。同份报告中 GreedyRange N=1024 是 448μs（真 1024 次），RepeatUntil "N=1024" 仅 4.8μs，差 92 倍——本应触发的内部关系异常未被 PM 验收核查。
5. **PM 验收失职**：未独立核查门禁合理性、场景规模标签与实际工作量一致性、benchmark 数据的内部关系。门禁下调由 ARCH 单方决策，PM 未独立判断。
