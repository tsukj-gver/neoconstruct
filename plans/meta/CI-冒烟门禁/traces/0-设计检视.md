### 3. L3 性能回归检测框架专项结论（核心）

**架构合理性**：§5.1 框架架构图清晰（读 baseline → 采集环境 → 逐点 bench → diff 判定 → FAIL 触发 A/B Test → 生成报告 → 退出码 0/1/2）。退出码语义明确（0=PASS / 1=WARN / 2=FAIL）。

**Baseline 管理（§5.2）**：
- ✅ 单一事实源 `docs/perf-scenarios.csv` 对齐 `pm-extension.md`
- ✅ "禁止自动更新"对齐 L-03 对策（PM 不接受不对等证据，回归不被洗白）
- ✅ 更新流程（L3 报告→PM 审查→PM 手动编辑 CSV）严谨
- ✅ "新场景"标记 `NEW` 不触发回归判据，提示 PM 是否纳入

**测量口径（§5.3）**：5 项硬要求严格执行，对齐 performance-gate SKILL + phase4_47_perf_verify.py 实现。无可降级空间 ✅

**测量环境标注（§5.4）**：9 项环境字段，thermal_state 标"unknown 或人工备注"合理（自动采集困难）✅

**回归判据三档（§5.6）对齐分析**：

| ARCH §5.6 判据 | performance-gate Checkpoint 4 判据 | 对齐分析 |
|----------------|------------------------------------|---------|
| 边界场景：WARN `abs(delta_x)>0.5`, FAIL `>1.0` | （L3 主跑层不直接对应） | L3 主跑容忍环境漂移（L-09 教训 0.29x 摆动）；FAIL 1.0x 阈值给漂移留余地 ✅ |
| 普通场景：WARN `abs(delta_pct)>10%`, FAIL `>20%` | （同上） | 用百分比而非绝对值，避免高速场景（如 30x→33x）误判 ✅ |
| 特殊场景：直接 FAIL `baseline ≥10x → new <10x` | （同上） | **完全对齐用户硬约束 #5**（禁止局部门禁）✅ |
| A/B Test 升级判据：`abs(delta_x)>0.5` 回归 / `<0.3` 波动 / `0.3-0.5` 加测 | Checkpoint 4 同表 | **逐字对齐** ✅ |

**分层合理性**：L3 主跑用宽阈值（容忍漂移），A/B Test 升级用严格阈值（Checkpoint 4）——两层不混淆 ✅

**Controlled A/B Test 升级路径（§5.7）对齐 L-09**：
- ✅ 触发条件：L3 主跑 FAIL
- ✅ 6 步流程：识别 → 定位 commit → 构造对照 → 交替测量 A→B→A→B→A→B（3 轮 6 次）→ 统计分析（welch_t）→ 结论判据
- ✅ 阳性对照 + 阴性对照（必做）—— 对齐 Checkpoint 4 "没有对照组的 A/B Test 不构成因果证据"
- ✅ 复用 `E01_O1_ab_*` 工具链（bench + harness + stats），参数化通用化
- ✅ 每场景独立 A/B Test 报告 + 退出码（确认回归→2 / 波动→1）

**专项结论**：**L3 性能回归检测框架设计严密，完全对齐 L-09 + Checkpoint 4 + 用户硬约束 #5。无架构缺陷**。唯一风险点在 §6.4 known_exemptions.json 初始内容（见 §5 详述）。
