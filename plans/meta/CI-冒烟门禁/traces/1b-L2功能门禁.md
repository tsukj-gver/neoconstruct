### E. phase1_smoke.py + phase2_smoke.py 设计亮点

#### E.1 phase1_smoke.py：subprocess 子进程隔离行为对照

**核心机制**：主进程跑 construct-rs（crs_venv_new），通过 `subprocess.run([pc_python, "-c", script], input=json)` 在 crs_venv_py_new 子进程中跑 Python construct 2.10.70，传 JSON scenario 进去，回 JSON 结果出来。

**对照覆盖**：
- FormatField 16 单例 × 5 个极值/中间值（0/1/-1/0x7F/极值）= 80 个对照点
- 每 scenario 比对 (a) construct-rs build 字节 vs PC build 字节；(b) construct-rs parse round-trip
- Struct B1 (3 字段) / B2 (10 字段)：所有字段值与 PC parse 结果逐字段对照
- Bytes(count) / GreedyBytes：parse 字节与 PC parse 字节对照

**关键技巧**：
- construct-rs 的 FormatFieldDescriptor 是单例（无 parse/build 方法），不能直接调用 → 包到 1-字段 Struct 通过 `Single.parse(built) / Single(v=v).build()` 用户面 API 调用
- Python construct Container 返回值含 `_io` (BytesIO) 内部键不可 JSON 序列化 → 子进程 runner 剔除 `_*` 键 + bytes 转 list
- 子进程 runner 用 inline `-c` 脚本（不依赖临时文件）+ stdin/stdout JSON 协议（无文件 IO 副作用）

**对照完整性**：
- phase1_smoke.py 共 176 个 assert（含 PC 对照），全 PASS
- 与 Python construct 2.10.70 字节级与值级双重对照（build bytes identical + parse value identical）

#### E.2 phase2_smoke.py：表达式系统用户面验证

**核心机制**：同 phase1_smoke.py（subprocess 隔离）。

**对照覆盖**：
- Bytes(const N)：定长字段（impl_phase=2 的 Bytes 表达式路径）
- Bytes(this.len_)：字段引用长度（construct-rs `Bytes(len_)` 直接传 `_FieldDescriptor`，编译期翻译为 ExprProgram）
- Bytes(a+b)：字段引用 + 算术（E2 场景 `Bytes(count+flag)` 简化版；编译为 `[getint(a), getint(b), add]`）
- Computed(a+b)：表达式求和（编译为 `[getint(a), getint(b), add]`）
- Tell + Computed（E3 场景）：Tell 记流位置 + Computed(end - start) 计算段长度

**关键技巧**：
- construct-rs 表达式语法不需要 `this.` 前缀：`Bytes(len_)` 直接把字段 descriptor 传入；Python construct 用 `Bytes(this.len_)`。子进程 runner 用 `this.len_` 表达，主进程用 `Bytes(len_)`
- Tell 是 RO 字段（rfield）：build 时由 StructNode 自动取流位置；对照 PC construct 的 Tell（也是 RO）
- Computed(end - start) 编译为 ExprProgram，两端行为一致

**对照完整性**：
- phase2_smoke.py 共 28 个 assert（含 PC 对照），全 PASS
- 覆盖 E1/E2/E3 三个 Phase 2 表达式核心场景
