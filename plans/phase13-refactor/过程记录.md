#### 一、延续性

**结论：✅ 基本通过（1 个建议级问题）**

- ✅ 设计明确声明 Phase 12 纯 Rust 路径（`parse_bytes` 返回 Value）完全不受影响，Phase 13 新路径（`parse_bytes_py` 返回 PyObject）是 construct-py 的增量。这与 Phase 12 设计 §1.2 的 B1 边界一致。
- ✅ `CompiledNode::External` variant 新增为第 72 variant，不影响现有 71 variant。纯 Rust 路径中 External 不可达（SchemaCompiler 不产出 External），零影响。
- ✅ `CompiledExpr::External` variant 新增（Arc<dyn ExprExtension>），不影响 Native/Constant。
- ✅ OutputSink 扩展采用**默认实现**策略（finish_field/finish_item 的默认实现 = Phase 12 行为），ValueSink 无需改动逻辑，向后兼容。
- ✅ SchemaCompiler 不修改（construct-rs 编译核心保持纯 Rust），construct-py 只做预处理/后处理。
- ⚠️ **S-CONT-1（建议）**：§7.1 从 PyO3 wrapper 提取 CompiledSchema 的代码引用 `wrapper.getattr("_compiled")`，但当前 PyO3 wrapper（`constructs_composite.rs`）的结构体字段是 `inner: construct::constructs::Struct`，没有 `_compiled` 字段。设计文档 §7.3 提到"每个 PyO3 wrapper 新增 `_compiled: OnceLock<Py<CompiledSchemaHolder>>` 字段"，这是一个涉及**所有 wrapper 类型**的结构体变更（PyStruct/PySequence/PyArray/...），但设计文档没有明确列出受影响的 wrapper 清单和迁移方式。建议 ARCH 补充 wrapper 变更清单。

#### 二、性能

**结论：✅ 通过**

- ✅ **PyDictSink direct-to-PyDict**：打破 Value::Container 中转，叶子字段单次 Value→PyObject 转换（§2.2 set_scalar 暂存 + finish_field 转换），比旧架构全量递归 value_to_py 大幅优化。
- ✅ **PyContextView 惰性映射**：常见表达式（this.field，~95%）编译为 Rust 闭包，0 次 FFI；退化模式（lambda，~5%）按需转换 + 字段缓存，200-400x 加速。§4.4 量化数据合理。
- ✅ **PyInput 按需读 PyObject**：build 方向只读被访问的字段，未访问字段零开销。对比旧架构 py_to_value 全量递归是改进。
- ✅ **CompiledExtension trait object 虚分发**：仅 External variant 一次虚分发，纯内置节点零额外开销。
- ✅ **Input trait 的 get_field 每次 FFI**：对 100 字段 Struct 约 100 次 FFI（~10-20µs），对比旧架构全量转换不是瓶颈。
- ⚠️ **S-PERF-1（建议）**：§2.4 提到 context.insert 优化推迟到 Phase 14。复合子节点的 PyObject→Value 反转（finish_field 的 Object 分支 py_to_value）在 Phase 13 总是发生，即使字段不被表达式引用。设计文档已标注这是可接受的（旧架构开销远大于此），且不影响正确性。建议在 CODING 阶段添加一个性能标记（comment），便于 Phase 14 定位优化点。

#### 三、整体性

**结论：❌ 1 个重要级问题**

- ✅ 模块边界清晰：construct-rs 定义扩展点（CompiledExtension trait + External variant + Input trait），construct-py 提供实现（PyCallback/PyDictSink/PyInput/PyContextView）。
- ✅ 调用方向正确：construct-rs →（trait object）→ construct-py，无循环依赖。construct-rs 不依赖 pyo3。
- ✅ ProducedOutput enum 使用 `Box<dyn Any + Send + Sync>` 保持 construct-rs 对 pyo3 零依赖。
- ❌ **I-INT-1（重要）**：**finish_field/finish_item 未覆盖 Sequence 的 named entry 场景**。
  - **问题**：设计文档 §2.1.4 声称影响 9 个复合 variant，但只给出了 CompiledStruct 的改动示例。当前源码（`mod.rs:1736-1768`）显示 **CompiledSequence 的 named entry** 使用 `exec_parse_named_child`（得到 value）+ `sink.push_item(value.clone())`（不是 set_field）+ `child_ctx.insert`。Sequence 的输出是 List/PyList，named entry 也走 push_item。
  - **冲突**：`finish_field` 的默认实现和 PyDictSink override 都用 `set_field`/`set_item`（写入 dict 字段），但 Sequence named entry 需要 `push_item`/`append`（写入 list）。如果 Sequence 用 finish_field，会写入错误位置（dict 而非 list），破坏 Sequence 语义。
  - **finish_item 的局限**：`finish_item` 默认实现是 `finish_subsink`（push value as item），但它不接收 name 参数、不返回 Value。Sequence named entry 需要同时 push_item **和**返回 Value 给 context。finish_item 的签名 `fn finish_item(&mut self, sub: Box<dyn OutputSink>) -> Result<()>` 无法满足。
  - **建议修改方向**：引入一个新方法 `fn finish_item_named(&mut self, name: &str, sub: Box<dyn OutputSink>) -> Result<Value>`（默认：into_value + push_item + 返回 value），或让 ARCH 明确 Sequence 的 exec_parse 如何在 PyDictSink 场景下整合 named entry。同理需检查 FocusedSeq 的 named field（当前 `mod.rs:2415-2426` 也是 set_field + context.insert，但 FocusedSeq 最终用 set_scalar 返回 focused value，可能有额外复杂性）。

#### 四、可行性

**结论：❌ 2 个阻塞级 + 1 个重要级问题**

- ❌ **B-FEAS-1（阻塞）**：**Input trait 缺少标量值获取方法，叶子节点 exec_build 无法实现**。
  - **问题**：§3.3 将 `CompiledExec::exec_build` 签名从 `input: &Value` 改为 `input: &dyn Input`，"所有 71 variant 的 exec_build 签名变更"。但 §3.2 的 Input trait 只定义了 `get_field`/`has_field`/`get_index`/`len`/`sub_input_field`/`sub_input_index` 六个方法，**没有**获取"自身代表的标量/整体值"的方法。
  - **源码事实**：叶子节点（CompiledFormatField/VarInt/Bytes 等 17 个，`mod.rs:1136-1175` 的 `impl_leaf_exec!`）的 exec_build 是 `self.inner.build(input, stream, ctx)`，其中 `inner.build` 接受 `&Value`。如果 exec_build 接受 `&dyn Input`，叶子节点无法从 Input 中提取标量 Value 传给 `inner.build`。同理 CompiledDynamic（`mod.rs:3959-3967`）也是 `self.inner.build(input, ...)`。
  - **遗漏范围**：设计文档 §3.3 只描述了 CompiledStruct 的适配（"从 input.as_container() 改为 input.get_field(name)"），完全遗漏了 ~20 个叶子/包装器节点的适配方案。
  - **建议修改方向**：Input trait 新增 `fn as_value(&self) -> Result<Value>` 方法（ValueInput 实现：`Ok(self.value.clone())`；PyInput 实现：`py_to_value(py, self.obj)`）。叶子节点 exec_build 改为 `let value = input.as_value()?; self.inner.build(&value, stream, ctx)`。设计文档应明确所有"内部构造临时 Value 传给子节点"的模式（如 `mod.rs:1272 self.inner.exec_build(&self.value, ...)`、`mod.rs:1306 self.inner.exec_build(&encoded, ...)` 等共 ~15 处）改为 `self.inner.exec_build(&ValueInput::new(&value), ...)`。

- ❌ **B-FEAS-2（阻塞）**：**CompiledExtension::ext_build 签名与 exec_build 新签名不一致**。
  - **问题**：§3.3 将 exec_build 签名改为 `&dyn Input`。但 §5.2 的 `CompiledExtension::ext_build` 签名仍是 `fn ext_build(&self, input: &Value, ...)`，§5.3 的 `CompiledExternal::exec_build` 实现也写的是 `fn exec_build(&self, input: &Value, ...)` 并直接转发到 `ext_build`。这是直接矛盾——如果 CompiledExec trait 的 exec_build 改为 `&dyn Input`，所有 impl（含 CompiledExternal）都必须接受 `&dyn Input`。
  - **根因**：ext_build 接受 `&Value`，但 CompiledExternal::exec_build 接受 `&dyn Input`，需要从 Input 提取 Value。回到 B-FEAS-1 的 Input::as_value 缺失。
  - **建议修改方向**：ext_build 签名也改为 `&dyn Input`（CompiledExtension 是 construct-rs 的 trait，Input 也在 construct-rs，可引用）。或 CompiledExternal::exec_build 内部用 `input.as_value()` 提取 Value 传给 ext_build（但需先解决 B-FEAS-1）。

- ❌ **I-FEAS-1（重要）**：**parse_bytes_py / build_from_py 不能作为 CompiledSchema 的 inherent impl 放在 construct-py**（孤儿规则）。
  - **问题**：§2.3 代码示例 `impl CompiledSchema { pub fn parse_bytes_py(...) }` 位于 `construct-py/src/compiled_ext.rs`。但 CompiledSchema 定义在 construct-rs，Rust 孤儿规则禁止在外部 crate 为外部类型添加 inherent impl。这段代码无法编译。
  - **设计文档内部不一致**：§2.3 注释说"新 trait 或 inherent impl wrapper"，§7.3 定义了 `CompiledSchemaHolder { schema: CompiledSchema }` 但 §2.3 没有用它。
  - **建议修改方向**：统一为 CompiledSchemaHolder wrapper 方案。parse_bytes_py/build_from_py 定义为 CompiledSchemaHolder 的方法（`impl CompiledSchemaHolder { fn parse_bytes_py(...) }`），内部委托 `self.schema.tree().exec_parse(...)`。

- ✅ **OutputSink 协议扩展（finish_field/finish_item）安全性**：默认实现等价于 Phase 12 行为（into_value + set_field）。ValueSink 路径所有 Phase 12 测试保持 PASS。9 个复合 variant 的 exec_parse 改动是机械化的（`into_value + set_field` → `finish_field`），设计文档 §2.1.4 的改动示例（针对 Struct）正确。
- ✅ **PyDictSink 嵌套**：sub_sink_for_field 返回新 PyDictSink（Empty 模式），子节点写入后 finish_field 提取 ProducedOutput。Py<PyDict>/Py<PyList> 引用计数管理，GIL 持有期间安全。with_gil 可重入（pyo3 0.22），嵌套获取无死锁风险。
- ✅ **CompiledExtension 三个方法签名**（ext_parse/ext_build/ext_sizeof）方向正确，镜像 CompiledExec。除 B-FEAS-2 的 ext_build input 类型外，签名合理。
- ✅ **CompiledExpr::External**：`Arc<dyn ExprExtension + Send + Sync>` 可 Clone（CompiledExpr derives Clone）。Py<PyAny> 是 Send + Sync（pyo3 保证），PyExprCallback 可实现 ExprExtension。

#### 五、完备性

**结论：❌ 1 个重要级 + 2 个建议级问题**

- ❌ **I-COMP-1（重要）**：**PyContextView 的 raw pointer 安全性论证不完整（use-after-free 风险）**。
  - **问题**：§4.3 PyContextView 持有 `ctx_ptr: *const Context`，注释说"safe because PyContextView only exists during a single PyCallback invocation"。但 PyContextView 是 `#[pyclass]`，Python 代码可以**持有引用**（存到全局变量、闭包捕获等）。PyCallback 返回后，exec_parse 的栈帧释放，Context 被销毁，ctx_ptr 变为悬垂指针。后续 Python 代码访问该 PyContextView 触发 `unsafe { &*self.ctx_ptr }` → use-after-free。
  - **unsendable 的局限**：`#[pyclass(unsendable)]` 只防止跨线程传递（防止 Send/Sync），**不防止同一线程内跨调用持有**。
  - **建议修改方向**：
    1. 引入 epoch/generation 机制：Context 持有 generation 计数器，PyContextView 创建时记录 generation，访问时校验。不匹配则返回错误（而非 UB）。
    2. 或明确文档化为"PyContextView 仅供单次调用内使用，Python 侧禁止持有"，并在 PyContextView drop 时将 ctx_ptr 置 null（但 clone 后无法保证）。
    3. 最低限度：在设计文档中明确标注此为**已知的安全约束**，并在 CODING 阶段由 DEV 实现防护（如 Drop 时 abort 检测）。
  - **严重性说明**：这是 unsafe Rust 的内存安全问题，不能简单标注为"已知约束"了事。use-after-free 可能导致不可预测的行为（非 panic，而是 UB）。ARCH 必须给出安全的替代方案或防护机制。

- ⚠️ **S-COMP-1（建议）**：**PyDictSink 的 sub_sink_for_field / sub_sink_for_item / finish_subsink 行为未描述**。
  - §2.2 的 PySinkMode 行为表格只列了 set_scalar/set_field/push_item/into_produced/finish_field，缺少 sub_sink_for_field/sub_sink_for_item/finish_subsink 的行为。虽然可从上下文推断（返回新 PyDictSink::empty()），但设计文档应补充完整。
- ⚠️ **S-COMP-2（建议）**：**GIL 可重入性应明确说明**。
  - PyDictSink/PyCallback 的方法中反复用 `Python::with_gil`，parse_bytes_py 入口已持有 GIL。需在设计中说明：parse_bytes_py 的 GIL 在整个 exec_parse 递归期间持有，内层 `with_gil` 是廉价的可重入获取（非重新获取 GIL 锁），避免 DEV 误以为有性能问题或死锁风险。
- ✅ **8 个子任务覆盖性**：13.1-13.8 覆盖了所有主要工作（协议扩展/External variant/PyDictSink/PyInput/PyContextView/PyCallback/api 重写/PyLazyProxy），依赖关系图清晰。
- ✅ **conversions.rs 保留的标量转换**：§6.2 明确保留 value_to_py/py_to_value（单值转换），删除 context_to_py_container。value_to_py 对 Container/List 的递归分支保留（单字段的 Container，非整棵树）。合理。
- ✅ **expr_bridge.rs 简化方案**：§6.3 将 5 个 func 桥接改为 PyExprCallback（ExprExtension），无 context_to_py_container 全量转换。方案完整。
- ✅ **错误路径（REV #9）**：§8 方案 A（丢弃部分 PyDict）与 Python 原版一致，实现简单（Err 路径 sink 被 drop）。ConstructError.path 提供字段级定位。合理。
- ✅ **Lazy 分期（REV #7）**：§5.6 PyLazyProxy 完整设计，Phase 13 初始退化为立即解析（try_set_lazy 总返回 false），正确性保证。分期理由充分。

### 结论：驳回至 DESIGNING

**驳回理由**：存在 2 个阻塞级问题（B-FEAS-1、B-FEAS-2），涉及核心 trait（Input / CompiledExtension）的定义不完整和签名矛盾，必须在 CODING 前解决。

**ARCH 修正要求**：

1. **[B-FEAS-1]** 补充 Input trait 的 `as_value()` 方法（或等效的标量值获取方法），并明确所有"内部构造临时 Value 传给子节点"的 exec_build 适配模式（约 15 处 `self.inner.exec_build(&some_value, ...)` → `self.inner.exec_build(&ValueInput::new(&some_value), ...)`）。特别覆盖叶子节点（17 个 `impl_leaf_exec!`）和 CompiledDynamic。

2. **[B-FEAS-2]** 统一 CompiledExtension::ext_build 的 input 类型与 CompiledExec::exec_build 的新签名（`&dyn Input`），或明确 CompiledExternal::exec_build 如何从 `&dyn Input` 提取 Value 传给 ext_build。

3. **[I-INT-1]** 补充 Sequence（及 FocusedSeq）named entry 在 finish_field/finish_item 协议下的整合方案（引入 finish_item_named 或等效方法，确保 PyDictSink 场景下写入 PyList 而非 PyDict）。

4. **[I-FEAS-1]** 统一 parse_bytes_py/build_from_py 的定义载体（建议 CompiledSchemaHolder wrapper），消除 §2.3 与 §7.3 的不一致。

5. **[I-COMP-1]** 给出 PyContextView 的 use-after-free 防护方案（epoch 机制或等效安全方案），不能仅依赖"文档化约束"。

6. **[建议]** 补充 S-CONT-1（wrapper 变更清单）、S-COMP-1（sub_sink 行为表）、S-COMP-2（GIL 可重入说明）、S-PERF-1（Phase 14 标记）。

修正后需重新提交 DESIGN_REVIEW，REV 将重点复查上述 6 项。

#### 二、v2 新发现问题

##### I-INT-2（重要，新发现）：FocusedSeq 与 Select 的 finish 方法归类错误

**问题位置**：§2.1.4（line 338-341）影响范围列表：

> `CompiledStruct`（finish_field）、`CompiledSequence`（finish_named_item）、
> `CompiledUnion`（finish_field）、`CompiledFocusedSeq`（finish_field）、
> `CompiledArray`/`CompiledArrayExpr`/`CompiledGreedyRange`/`CompiledRepeatUntil`
> （finish_item）、`CompiledSelect`（finish_item）。

**问题**：`CompiledFocusedSeq` 和 `CompiledSelect` 被错误归入整合式 finish 方法（finish_field / finish_item），但这两个节点的 exec_parse 实际使用的是**"解析 child 到临时 sub sink → into_value 提取 → set_scalar 输出"**的非整合模式，不应使用任何 finish_* 方法。

**源码事实**：

1. **CompiledFocusedSeq**（`mod.rs:2402-2452`）：
   ```rust
   // named child: exec_parse_named_child（sub_sink_for_field + into_value，不写入 parent sink）
   let value = exec_parse_named_child(&field.subcon, stream, &mut child_ctx, sink, name)?;
   child_ctx.insert(name.clone(), value.clone());  // 只进 context
   // 最终：只输出 focused value 作为标量
   sink.set_scalar(focused_value)?;  // ← set_scalar，非 set_field/push_item
   ```
   FocusedSeq 解析所有 named child 到 context（用于后续字段表达式），但**输出**只通过 `set_scalar` 输出 focused field 的值（标量语义，非 Container）。

2. **CompiledSelect**（`mod.rs:2147-2180`）：
   ```rust
   let mut sub_sink = sink.sub_sink_for_item()?;
   sc.exec_parse(stream, ctx, sub_sink.as_mut())?;
   let value = sub_sink.into_value()?;
   sink.set_scalar(value)?;  // ← set_scalar，非 push_item
   return Ok(());
   ```
   Select 尝试每个 case，第一个成功的 case 的值通过 `set_scalar` 输出（标量语义，非 List）。

**若照 §2.1.4 归类实现会产生什么错误**：

- **FocusedSeq 改用 finish_field**（默认实现 = `into_value + set_field`）：每个 named child 的 Value 会被 `set_field(name, value)` 写入 parent sink。
  - **ValueSink 路径**：set_field 进入 fields map，之后 set_scalar 写入 pending。`into_value` 优先级 `pending > fields`，最终返回 scalar——**行为侥幸不变**，但 sink 内有无用的冗余 fields 数据。
  - **PyDictSink 路径（灾难性）**：`set_field` 使 PyDictSink 进入 `Struct` 模式（持有 PyDict）。随后 `set_scalar(focused_value)` 在 §2.2 行为表中明确为 **`Struct → Err`**（mode 互斥）。**FocusedSeq 在 direct-to-Python 路径下直接报错**。

- **Select 改用 finish_item**（默认实现 = `finish_subsink = into_value + push_item`）：匹配的 value 会被 `push_item` 追加到 list。
  - **ValueSink 路径**：`push_item` 进入 items，`into_value` 返回 `Value::List(vec![value])` 而非标量——**输出类型改变**（标量变 List），破坏 parse/build 对称性和所有 Select 测试。
  - **PyDictSink 路径**：`push_item` 进入 `Array` 模式（持有 PyList），而非应有的 `Leaf` 模式——**输出类型错误**。

**严重性**：重要级。Select 是较常用的构造器（try/except 式多选一），FocusedSeq 虽不常用但语义必须正确。照当前设计实现会破坏 S-FUNC-1（原版测试通过率 ≥85%），且 PyDictSink 路径下 FocusedSeq 直接 panic/error。

**建议修正方向**：

1. **从 §2.1.4 影响范围列表中移除 FocusedSeq 和 Select**（或单独标注"非整合节点，保留 sub_sink+into_value+set_scalar 模式"）。
2. 这两个节点的 exec_parse 改造**不涉及** finish_* 协议——它们保持当前的"临时 sub sink 提取 Value，set_scalar 输出"模式。finish_field/finish_named_item/finish_item 仅适用于"输出结构 = child 输出整合"的节点（Struct/Sequence/Array/Union）。
3. 不需要新增 trait 方法——exec_parse_named_child（FocusedSeq）和 sub_sink_for_item+into_value+set_scalar（Select）的现有模式直接保留即可。
4. 建议在 §2.1.4 新增一段"**非整合节点说明**"，明确列出 FocusedSeq/Select 不走 finish 协议的原因（标量输出语义），避免 DEV 误改。

**影响范围**：仅文档修正，**不涉及任何 trait 定义变更**（Input/OutputSink/CompiledExtension 均不受影响）。

##### S-CACHE-1（建议）：PyContextView `__getitem__` 的 cache 实现细节未定

**问题位置**：§4.3（line 1078-1103）`__getitem__` 代码示例。

**问题**：方法签名是 `fn __getitem__(&self, py: Python<'_>, key: &str)`（不可变借用），但 `cache` 字段（`IndexMap<String, PyObject>`）的写入需要 interior mutability。代码示例中 `self.cache.get(key)`（读）可行，但无法 `self.cache.insert(key, py_obj)`（写）。注释（line 1094-1098）讨论了这个问题（RefCell vs `&mut self` vs 放弃缓存），但未给出最终方案。

### 设计质疑

**[设计质疑 - 小]** CompiledExternal::exec_parse 的 ProducedOutput::Object(_) 分支在纯 Rust 路径（ValueSink）中无法存储 opaque boxed object。当前实现用 `Value::None` 作为占位符。这是合理的——纯 Rust 路径不会产生 External variant（SchemaCompiler 不产出 External），External 仅在 construct-py 的 PyDictSink 路径中可达，那里 finish_field 会正确处理 Object 分支。但设计文档 §5.3 未明确说明此退化行为。

**D1（重要观察） CompiledExtension::ext_parse 签名偏离设计文档**

- **设计文档 §5.2**：`fn ext_parse(&self, stream, ctx, sink: &mut dyn OutputSink) -> Result<()>`（接收 sink，写入 sink）

**D2（次要观察） CompiledExtension::ext_sizeof 丢弃 ctx 参数**

- **设计文档 §5.2**：`fn ext_sizeof(&self, ctx: &Context) -> Result<usize>`

**D3（次要观察） ExprExtension::ext_eval 丢弃 obj 参数**

- **设计文档 §5.5**：`fn ext_eval(&self, ctx: &Context, obj: Option<&Value>) -> Result<Value>`

**D4（次要观察） 复合节点 exec_build 使用 as_value()+clone 而非 get_field/sub_input_field**

- **设计文档 §3.3.1 模式 C**：复合节点应使用 `input.get_field(name)` / `input.sub_input_field(name)?` 逐字段惰性读取

#### 十三、预存测试失败追溯

**结论**：预存失败，不阻塞 Phase 13 验收。建议在独立子任务中修复 conversions.rs 的 Int/UInt 映射一致性。

### 非阻塞观察项（O1-O4）

以下 4 项为本次审查发现的实现细节，**不影响 Phase 13 功能正确性**，建议在后续阶段关注：

**O1（重要观察）CompiledExternal::exec_parse 的 Object 分支数据丢失隐患**

- CompiledExternal::exec_parse（mod.rs:4150）对 `ProducedOutput::Object(_)` 用 `sink.set_scalar(Value::None)`。
- **当前安全**：PyCallback::ext_parse 总是返回 ProducedOutput::Value（py_to_value 转换），从不返回 Object。
- **未来风险**：如果新的 CompiledExtension 实现返回 Object，数据会在 exec_parse 层丢失。
- **建议**：在扩展 CompiledExtension 生态时，需解决 Object 路径的 sink 整合问题（回归 ext_parse 接收 sink 的设计，或扩展 sink 协议支持 Object 透传）。

**O2（次要观察）parse_bytes_py 强制 Struct 模式的根 sink**

- parse_bytes_py 使用 PyDictSink::new_root（Struct 模式），叶子根构造器（如单独 Int8ub）会导致 `set_scalar on composite sink` 错误。
- **影响**：与 Python construct 典型用法一致（根几乎总是 Struct），但应在用户文档中标注。

**O3（次要观察）build_from_py 的 context "_" 嵌入使用 as_value() 全量转换**

- build_from_py（compiled_ext.rs:170-172）设置 `context._ = obj` 时调用 `input.as_value()`，触发 PyObject → Value 全量转换。
- **矛盾**：与 PyInput 惰性读取设计部分矛盾——即使 build 路径只读少数字段，as_value 也会转换整个对象。
- **必要性**：Optional/IfThenElse 等构造器需要检查 `context._`，Python 原版也在 build 前设置 `context._ = obj`。
- **建议**：Phase 14 可考虑延迟转换（首次访问 `context._` 时才转换）。

**O4（次要观察）PyCallback Construct kind 的 BytesIO read-all 策略**

- ext_parse 的 Construct kind 使用 `stream.read_remaining()?` 读取所有剩余字节。对大流可能效率低下。
- **一致性**：与现有 PyConstructAdapter 策略一致，Python construct 的 parse_stream 本身是 BytesIO-based。
