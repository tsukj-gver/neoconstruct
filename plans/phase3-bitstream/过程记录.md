### ARCH 设计说明

**设计文档**：`docs/design/模块设计/模块设计-BitStream.md`

**核心架构决策（5 项）**：
- **B1**：不采用 Python 的 8 倍膨胀 bit 串机制，直接在原始字节上位运算
  （Stream 是纯 Rust 内部抽象，无需膨胀来"复用字节接口"，一次 FFI 已满足）
- **B2**：ParseStream/BuildStream 增加 bit 游标（bit_pos 0-7），bit 节点和字节节点
  用不同 API 分流，不破坏现有 Construct trait 签名
- **B3**：bit 域 sizeof 单位是 bit，由 BitwiseNode（/8）/BytewiseNode（*8）做单位换算
- **B4**：Padding 单位由编译期 bitwise 上下文决定（Bitwise 子树内 → BitPaddingNode）
- **B5**：BitsSwapped/ByteSwapped 共用 TransformNode + ByteTransform 枚举（仅两种变换）

**节点设计（6 个新 Node 变体）**：
- `BitsIntegerNode`：bit 原子整数（含 signed/swapped）
- `BitPaddingNode`：bit 级填充
- `BitwiseNode`：bit 域边界包装器（含对齐校验），持有 `Box<Node>` 子树（首个递归变体）
- `BytewiseNode`：bit→byte 适配器（对齐快路径 + 未对齐慢路径）
- `TransformNode`：字节级变换（BitSwap/ByteSwap）
- `PaddingNode`：字节级填充（补全 Phase 1 遗留）

**Python API 映射**：9 个构造器 + 1 个基类（BitStructMixin）全部覆盖。

**边界条件**：35 个场景分 7 类列出（§9）。

**性能假设**：5 个瓶颈识别（8 倍膨胀、Python 循环、查表 join、缓冲管理、bits2integer），
预测 ≥10x，基线 6288 ns/op，验证方法明确（§10）。

**需要 PM 决策的事项（3 项）**：
1. BitsInteger 表达式 length 是否纳入 3.1（推荐：仅常量，表达式作 3.2）
2. 字节级 PaddingNode 是否纳入 3.1（推荐：纳入）
3. Bytewise 未对齐慢路径优先级（推荐：3.1 实现完整）

**与架构设计文档的兼容性**：不修改核心约定，唯一补充点是 Node enum 的递归变体
（Box<Node>），建议在架构设计 §C.2 补注，不构成冲突。

### 备注
- Python BitStruct 的 size//8 截断 quirk 已在设计 BW-2 边界条件中体现：
  construct-rs 的 BitwiseNode.sizeof 在非 8 倍数时直接报错（比 Python 的晦涩

#### 严重问题（驳回依据）

**P1. BitPaddingNode pattern 映射错误（§4.2）**

设计定义 `pattern_bit = pattern >> 7`（取 pattern 字节的最高有效位 MSB）。这与
Python 行为不一致：

| pattern 字节 | Python bit 域行为 | 设计 `>>7` 结果 | 是否一致 |
|-------------|------------------|----------------|---------|
| 0x00（默认） | 填 0 bit | 0 | ✅ |
| 0x01 | 填 1 bit（bits2bytes 把 0x01 当 bit 1） | 0 | ❌ |
| 0x80 | KeyError（bits2bytes 查表失败） | 1 | ❌（设计更宽松） |
| 0xff | KeyError | 1 | ❌（设计更宽松） |

依据：Python `Padded._build`（core.py L4239）写 `self.pattern * pad`。在 bit 域
（Bitwise 内），stream 是 8 倍膨胀的 bit 串，每"bit 字节"为 0x00 或 0x01。
`bits2bytes`（binary.py L109）用 `BITS2BYTES_CACHE` 查表，cache 键仅含 0x00/0x01
序列（由 `bytes2bits(int2byte(i))` 生成）。因此：
- pattern=0x00 → 写 0x00 字节 → bit 0
- pattern=0x01 → 写 0x01 字节 → bit 1
- pattern=其他 → 写非 0x00/0x01 字节 → bits2bytes KeyError

设计 §4.2 注释称"若 pattern=b'\xff'，写 length 个 0x01 字节（length 个 1 bit）"
是对 Python 机制的**误解**（Python 实际写 0xff 字节，会触发 KeyError）。

**影响**：`Padding(N, pattern=b"\x01")`（bit 域内填充 1 bit 的常见用法）在
construct-rs 会错误地填充 0 bit，build 产出与 Python 不一致。

**建议修改方向**：`pattern_bit = pattern & 1`（LSB），匹配 Python 的 0x00→0、
0x01→1 两个有效 case；或严格校验 `pattern ∈ {0x00, 0x01}`，其他值报
PaddingError（对齐 Python 的 KeyError 行为）。同时修正 §4.2 注释中关于
pattern=0xff 的错误描述。

---

**P2. BitwiseNode 嵌套对齐校验自相矛盾（§4.3 vs §9.3 BW-4）**

§4.3 parse/build 退出时检查 `stream.bit_pos() == 0`。但 §9.3 BW-4 声明：
"嵌套 Bitwise（Bitwise(Bitwise(...))）内层 Bitwise 退出时回到入口 bit_pos"。
两者矛盾。

场景：`Bitwise(Bitwise(BitsInteger(8)))`
- 外层 Bitwise 进入，bit_pos=0
- 内层 Bitwise 进入，bit_pos=0
- 内层 BitsInteger(8) 消耗 8 bit，bit_pos 回到 0
- 内层 Bitwise 退出，检查 bit_pos==0 → 通过（此 case 碰巧 OK）

场景：`Bitwise(Struct('a'/Nibble, 'b'/Bitwise(BitsInteger(8))))`
- 外层进入，bit_pos=0
- Nibble 消耗 4 bit，bit_pos=4
- 内层 Bitwise 进入，bit_pos=4
- 内层 BitsInteger(8) 消耗 8 bit，bit_pos 回到 4
- 内层 Bitwise 退出，检查 bit_pos==0 → **失败**（bit_pos=4），误报 BitFieldError

设计 §13.4 明确讨论嵌套 Bitwise 语义并声称"与 Python 行为一致"，但 §4.3 的
硬编码 `bit_pos==0` 检查在入口 bit_pos!=0 时错误。

**依据**：Python `RestreamedBytesIO.close()`（bitstream.py L50）校验的是**缓冲
清空**（消耗量为 encoderunit 倍数），等价于"消耗 bit 数为 8 倍数"，即
`exit_bit_pos == entry_bit_pos`，而非绝对 `bit_pos == 0`。

**建议修改方向**：BitwiseNode.parse/build 记录入口 `(entry_pos, entry_bit_pos)`，
退出时检查 `stream.bit_pos() == entry_bit_pos`（等价于内层消耗 8 倍数 bit）。
顶层 Bitwise 入口 bit_pos=0，退化为现行检查，行为不变。

#### 中度问题（建议修正，不单独阻塞）

**P3. BitsSwapped 变长 subcon 支持缺失（§4.5 / §9.5 TR-1）**

Python `BitsSwapped`（core.py L4855-4859）对变长 subcon 有 Restreamed 回退
（SizeofError 路径，encoderunit=1 逐字节变换），docstring L4838 明确
"Does NOT require a fixed sized subcon"。设计的 TransformNode 统一要求定长
（§4.5 step 1、§9.5 TR-1 归因于"ByteSwapped 需定长"）。

`BitsSwapped(变长 subcon)` 在 construct-rs 会报错，Python 成功。

§1.2 已排除"通用 Restreamed"，但 §4.5/§9.5 应明确标注 BitsSwapped 的变长
不支持为 Phase 3.1 已知限制（而非错误地归因于 ByteSwapped 的定长要求）。

**P4. 表达式 length 错误路径未闭环（§7.2 vs §8.2）**

§8.2 的 `BitsIntegerDescriptor` / `PaddingDescriptor` 通过 `_expr_params` 报告
表达式 length（当 length 是 FieldRef/ExprRef 时），但 §7.2 的
`build_node_from_descriptor` 仅调用 `new_const`（常量路径）。

用户传 `BitsInteger(count)`（count 为 FieldRef）时：描述符会触发表达式编译管线
（_expr_params 非空），但 build_node_from_descriptor 不处理表达式 length。

§8.2 注释称"Phase 3.1 仅支持常量 length，表达式 length 标记为后续子任务"，但
未明确：检测到表达式 length 时应返回什么错误？

**建议**：§7.2 显式处理——若 desc.length 是表达式且 Phase 3.1 不支持，返回
`ConstructError::Compilation`（"expression length not supported in Phase 3.1"）；
或在 §8.2 描述符层不设置 _expr_params（Phase 3.1 期间）。

#### 轻度问题（建议修正，不阻塞）

**P5.** §9.1 BI-3 length>64 的错误类型模糊（"Stream/BitField 错误"）。Python
无此限制（大整数）。建议明确为 `IntegerError`（"length exceeds 64-bit limit"），
属 construct-rs 文档化范围限定。

**P6.** §9.1 BI-2 负 length 称"编译期 Compilation 错误"，但 §7.2 未描述 Python
int → usize 转换时负数检测。建议 build_node_from_descriptor 显式校验
`length >= 0`（i64 提取后检查），避免 usize 回绕。

**P7.** §9.4 BY-4 称 Bytewise 在 Bitwise 外"等价直接 subcon，无意义但不报错"，
但 Python Bytewise 外用会在 bits2bytes 阶段 KeyError（core.py L1106 Transformed
读 size*8 字节后 bits2bytes 查表失败）。两者都异常但方式不同。建议文档化为
已知差异（非语义对齐点）。

## ARCH 修正说明（v2）

**修正时间**：2026-06-27
**修正人**：ARCH
**修正文档**：`docs/design/模块设计/模块设计-BitStream.md`
**修正依据**：REV 检视报告 + Python 源码逐行验证

### 严重问题修正（必须）

#### P1. BitPaddingNode pattern 映射错误（§4.2）— 已修正

**REV 指出**：`pattern_bit = pattern >> 7`（取 MSB）对最常见的非零 pattern `0x01`
给出错误结果（0x01 >> 7 = 0，而 Python 实际填充 bit 1）。

**ARCH 验证**（基于 Python 源码）：
- `binary.py` L108：`BITS2BYTES_CACHE = {bytes2bits(int2byte(i)): i for i in range(256)}`
  — cache 键由 `bytes2bits` 生成，`bytes2bits`（L96）用 `BYTES2BITS_CACHE`，
  `BYTES2BITS_CACHE`（L95）由 `integer2bits(i, 8)` 生成，每 bit 为 0x00/0x01。
  **因此 BITS2BYTES_CACHE 的键仅含 0x00/0x01 序列**。
- `core.py` L4239：`Padded._build` 写 `stream_write(stream, self.pattern * pad, ...)`。
  在 bit 域（Bitwise 内），stream 是 8 倍膨胀 bit 串，每"bit 字节"为 pattern[0]。
- 结论：pattern=0x00 → bit 0；pattern=0x01 → bit 1；pattern=其他 → bits2bytes KeyError。
- 设计 §4.2 原"pattern=0xff 写 length 个 0x01 字节"的注释是**误解**
  （Python 实际写 0xff 字节，触发 KeyError）。

**修正内容**：
1. `pattern_bit = pattern & 1`（LSB），匹配 0x00→0、0x01→1 两个合法 case。
2. **严格校验**：`BitPaddingNode::new` 要求 `pattern ∈ {0x00, 0x01}`，否则返回
   `ConstructError::Padding`（fail-fast，优于 Python 延迟 KeyError）。
3. `new()` 签名改为返回 `Result<Self, ConstructError>`。

### 发现的问题（均不阻塞）

**P1 [低-中] 错误类型映射差异：IntegerError vs FormatFieldError**

- **现象**：Python BitsInteger 的所有错误（length<=0、非 int、超范围、swapped+%8!=0）
  均抛 `IntegerError`（core.py L49、L1367/L1374/L1378/L1387）。
  construct-rs 的 BitsIntegerNode 返回 `ConstructError::FormatField`，
  映射到 Python `FormatFieldError`（_errors.py L63）。
- **影响**：用户代码 `except IntegerError` 在 construct-rs 中无法捕获
  BitsInteger 的错误（会捕获到 FormatFieldError）。
- **根因**：`_errors.py` / `error.rs` 在 Phase 1 未定义 `IntegerError` 变体
  （Phase 1 错误类型体系遗留）。DEV 在无 IntegerError 变体的情况下选择
  FormatField 是合理折中（bits_integer.rs 文档注释 L75-82 已说明）。
- **建议**：记录为已知差异。后续完善错误类型体系时（建议 Phase 3.2 或独立子任务），
  新增 `ConstructError::Integer` 变体 + `_errors.IntegerError` 类，
  将 BitsInteger 的错误改映射到 IntegerError。**不阻塞 Phase 3.1 验收**。
- **DEV 已在过程记录 §"偏离设计文档"明确说明此选择**（L699-703），透明可追溯。

**P2 [低] BI-6 检查顺序差异（设计决策，Rust 做法更优）**

- **现象**：Python `_parse` 先 `stream_read`（消耗游标），再在 `swapbytesinbits`
  内部检查 length%8（报错时游标已前进）。Rust 先检查 swapped+%8 再 `read_bits`
  （报错时不消耗游标）。
- **评估**：符合设计 §4.1 步骤 2（"若 swapped：校验 length%8==0"）先于步骤 3
  （"raw = stream.read_bits"）。Rust 提前校验是设计明确决策，且更优（fail-fast、
  不污染流状态）。Python 的"先读后报错"是其膨胀机制的历史包袱。
- **影响**：仅在错误恢复场景有差异（错误后流游标状态不同），正常路径无影响。
- **建议**：无需修改。记录为已知差异（设计层面接受）。

**P3 [低] read_bits/skip_bits 的 remaining_bits 计算防御性不足**

- **位置**：`stream.rs` L196、L266
  ```rust
  let remaining_bytes = self.data.len().saturating_sub(self.pos);
  let remaining_bits = remaining_bytes * 8 - self.bit_pos as usize;
  ```
- **潜在问题**：若 `remaining_bytes == 0` 且 `bit_pos > 0`，`0 - bit_pos`
  会下溢（debug panic / release 回绕为巨大值）。
- **不变量保证**：当前由 read_bits/skip_bits 自身保证 `pos == data.len()` 时
  `bit_pos == 0`（预检查在推进游标前拦截越界读取）。初始状态也满足。
  故**正常使用中不会触发**。
- **建议**：改用 `saturating_sub` 增强防御性，避免未来代码修改破坏不变量时
  出现 panic/回绕：
  ```rust
  let remaining_bits = remaining_bytes.saturating_mul(8).saturating_sub(self.bit_pos as usize);
  ```
  **非阻塞**，可作为后续防御性增强提交。

**P4 [极低] build_bits_integer_node 的 path 参数未使用**

- **位置**：`compile.rs` L407-495
- **现象**：`path: String` 参数传入但 `let _ = (py, &path);` 显式丢弃，
  错误信息用 `field_index` 替代。
- **影响**：无功能影响（错误信息仍含 field_index 定位）。代码气味。
- **建议**：后续可统一用 path 或移除 path 参数。**非阻塞**。

- **Bitwise 完整路径无法直接测**：Python construct 2.10.70 的 Bitwise 在 Python 3.14 下
  存在已知兼容性问题（RestreamedBytesIO 的 stream_read 路径异常）。引用 ARCH 在 Python 3.13
  上的实测作为基线（6288 ns/op 对 3 字段 BitStruct）。

### 底层 `BuildStream::write_bits` 数据（辅助分析）

| length(bit) | new() + write (ns/op) | with_capacity(16) + write (ns/op) | 说明 |
|---|---|---|---|
| 1 | 2.08 | 21.91 | length<8 时不 push 字节，new() 零分配 |

| 64 | 25.87 | 24.20 | 同上 |

**解释**：`new()` 在 length<8 时不分配 Vec（buf 保持空），所以最快；`with_capacity(16)`
强制分配 16 字节（Windows HeapAlloc ~20-30 ns）。length>=8 时两者接近，因 `new()` 也要
reallocate。生产中 BitwiseNode 入口预分配一次后多个字段复用，第二次起免分配。

### 关键观察

1. **底层 `read_bits` 极快**：2-4 ns/op（小常数），加速比 **27x（1-bit）~ 736x（64-bit）**。
   length 越大加速越明显，因为 Python `for b in data` 是 O(n) Python 字节循环。

2. **`BitsIntegerNode.parse` (unsigned) 加速 3-61x**：
   - length=1/4 时只 ~3-5x，PyLong 构造开销占主导（短 bit 序列下相对开销大）。
   - length>=8 后加速比线性增长到 61x（64-bit）。

3. **`BitsIntegerNode.parse` (signed) 加速 1.8-42x，几何平均 7.1x**：
   - signed 比 unsigned 慢一倍以上（60 vs 25 ns）。根因：i128 → PyLong 转换路径较长
     （pyo3 i128 不在 CPython 小整数 fast path）。
   - **[优化机会]** length<=63 时 signed 可走 i64 fast path（最高位单独处理），
     仅 length=64+signed 用 i128 兜底。预计 parse_s 可降到 ~30 ns，1-bit 加速比从 1.8x → 3.5x。
   - 此为已知优化点，**不阻塞 Phase 3.1 验收**（≥4x 目标除短位 signed 外全部达成）。

4. **`BitsIntegerNode.build` 加速 7-74x，几何平均 ~22x**：
   - length<8 时不触发 Vec push（仅写 `current_byte`），最快（19-24 ns）。
   - length>=8 时 push 触发 Vec reallocate，跳到 43-51 ns（含 ~20ns 分配）。
   - 生产中 BitwiseNode 入口预分配 stream 后，多个字段复用，第二次起免分配（摊销成本接近裸操作）。

5. **Bitwise 完整路径基线**：ARCH Phase 3 设计阶段实测（Python 3.13）
   `Bitwise(BitStruct(3 字段)).parse` = **6288 ns/op**（每字段摊 ~2000 ns）。
   Rust 端 `BitsIntegerNode.parse` 平均 ~30-40 ns，含 BitwiseNode 包装估算 ~100-200 ns/字段，
   预计完整 BitStruct 加速可达 **30-60x**（待 Phase 3.2 BitwiseNode 实现后验证）。

### 结论

Phase 3.1 bit-level 操作性能**远超 ≥4x 目标**：

| 操作类别 | 几何平均加速比 | 最差单点 | 最优单点 |
|---------|--------------|---------|---------|
| 底层 read_bits (unsigned) | **122.3x** | 27.0x (1-bit) | 736.5x (64-bit) |
| BitsIntegerNode.parse (unsigned) | **11.7x** | 2.9x (1-bit) | 61.2x (64-bit) |
| BitsIntegerNode.parse (signed) | **7.1x** | 1.8x (1-bit)* | 41.7x (64-bit) |
| BitsIntegerNode.build (unsigned) | **22.8x** | 11.7x (1-bit) | 74.2x (64-bit) |
| BitsIntegerNode.build (signed) | **21.6x** | 7.1x (1-bit) | 70.4x (64-bit) |

*signed parse 1-bit 仅 1.8x 是唯一接近门禁的边缘 case，由 i128 转换开销导致，
有明确优化路径（i64 fast path）。

### 已知优化机会（不阻塞 Phase 3.1 验收，可作 Phase 3.2+ 改进项）

- **[OPT-1] parse_s i64 fast path**：当前实现统一用 `i128` 中间值处理二补码（为对齐
  length=64+signed 边界 BI-4）。可在 length<64 时分支走 `i64`，仅 length==64 + signed 用 i128 兜底。
  预计 parse_s 整体下降 ~30 ns（60→30），signed 1-bit 加速比从 1.8x → ~3.5x。
- **[OPT-2] build u64 fast path**：当前 build 统一用 i128 提取（覆盖极大数报错路径）。
  可在 `value >= 0 && value <= u64::MAX` 时直接走 u64 提取 fast path。预计 build_u 整体下降 ~5-10 ns。

### 发现的问题（均不阻塞）

**P1 [低] sizeof 错误路径为空字符串**

- **位置**：`bitwise.rs` L162
  ```rust
  return Err(ConstructError::BitField {
      message: format!(...),
      path: String::new(),  // ← 空字符串
  });
  ```
- **现象**：sizeof 不接收 path 参数（`fn sizeof(&self, ctx)`），无法填充路径。
  BitField 错误规范要求携带 path 字段（error.rs L173-178），但 sizeof 上下文无 path 可用。
- **影响**：用户看到 sizeof 错误时缺少字段定位信息（仅 inner bit 数描述）。
  实际影响小——sizeof 错误通常在编译/调试阶段触发，且 message 已含 "Bitwise inner sizeof N" 定位信息。
- **根因**：sizeof 签名设计层面不含 path 参数（与 FormatField/Bytes 等节点 sizeof 错误一致）。
- **建议**：记录为设计限制。后续若引入 path 到 sizeof 签名（独立子任务），同步修正。
  **不阻塞 Phase 3.2 验收**。

**P2 [低] parse 与 build 的 BitField 错误信息不对称**

- **位置**：`bitwise.rs` L107-112（parse）vs L138-140（build）
- **现象**：
  - parse：`"bit stream not byte-aligned after Bitwise parse (entry bit_pos={}, exit bit_pos={}, consumed {} bits mod 8)"`
  - build：`"bit stream not byte-aligned after Bitwise build (entry bit_pos={}, exit bit_pos={})"`
- **差异**：parse 多了 `"consumed {} bits mod 8"` 诊断信息，build 没有。
- **影响**：仅诊断信息详尽度差异，不影响功能。
- **建议**：build 错误信息也加上 `"consumed {} bits mod 8"` 以对称。**非阻塞**。

**P3 [极低] compile.rs build_node_from_descriptor 中 `let _ = bitwise;`**

- **位置**：`compile.rs` L257-258
- **现象**：函数顶部 `let _ = bitwise;` 显式 consume 参数避免 unused 警告。
  BitwiseDescriptor 分支递归调用传 `true` 字面量而非外层 `bitwise` 变量。
- **评估**：合规。DEV 在过程记录明确说明此为 Phase 3.3 PaddingDescriptor 分支预留接口。
  当前所有调用路径正确：BitwiseDescriptor 递归传 true，其他分支不需要。
- **建议**：Phase 3.3 实现 PaddingDescriptor 后移除 `let _ = bitwise;`。

**P4 [极低] BitStructMixin 缺独立的 sizeof 方法**

- **现象**：Python construct 的 `BitStruct.sizeof()` 返回字节数。

- **影响**：用户无法直接 `Header.sizeof()`。需通过 build/parse 间接推断。
- **根因**：Phase 1-2 的 StructMixin 也未暴露 sizeof（CompiledSchema 持有 sizeof 但 Mixin 未委托）。
  这是项目整体的 API 覆盖度问题，非 BitStructMixin 特有。
- **建议**：作为独立子任务补充 StructMixin.sizeof() / BitStructMixin.sizeof()（后续阶段）。
  **不阻塞 Phase 3.2 验收**。

**P5 [观察] BitStructMixin 文档注释提到 Phase 3.3 的 BitPaddingNode**

- **位置**：`_mixin.py` L990

### 关键观察

1. **S-PERF ≥10x 目标全部达成**：parse 几何平均 27.9x，build 几何平均 26.6x。
   最低单点为 ByteSwapped build 10.0x（恰好达到门禁）。

2. **Bytewise 对齐快路径几乎零开销**：Bitwise(Bytewise(Bytes(4))) parse 36.5 ns，
   比 Bitwise(BitsInteger(16)) 的 53.5 ns 还快——因为 Bytewise 对齐时直接委托 Bytes(4)
   读 4 字节 + 创建 PyBytes，比 BitsInteger 的 PyLong 构造路径更快。
   Bytewise(Int8ub) parse 30.2 ns 是全部场景最快。

3. **Bytewise 未对齐慢路径仍高效**：BitStruct(Nibble, Bytewise(Int16ub), Nibble)
   parse 260.6 ns（含 3 个字段完整 StructNode.parse + 实例 dict 填充），
   vs Python 5300 ns = 20.3x。未对齐慢路径的逐 bit 提取（16 bit）相比对齐快路径
   仅多 ~50-80 ns（260 vs 30+30+30 ≈ 90 ns 的纯 Bytewise 对齐估算）。

4. **BitsSwapped/ByteSwapped 查表极快**：
   - BitsSwapped(Bytes(4)) parse 58.1 ns / build 98.0 ns
   - ByteSwapped(Int32ub) parse 58.4 ns / build 98.2 ns
   Rust 端 BIT_REVERSE_TABLE 是编译期 const 表（无运行时初始化），ByteSwap 用 Vec::reverse。

5. **BitPadding/字节级 Padding 摊销成本接近零**：
   - BitStruct(Nibble, BitPadding(4)) parse 164.9 ns，相比单纯 Nibble parse
     （~30 ns 估）+ BitPadding skip（~10 ns 估）+ StructNode 包装（~100 ns 估）合理。
   - Struct(Bytes(1), Padding(4), Bytes(2)) parse 165.6 ns，Padding 4 字节 read 几乎零开销。

6. **端到端 BitStruct 远超 ARCH 设计目标**：
   BitStruct(Nibble, BitsInteger(10), BitPadding(2)) parse = 221.1 ns，build = 151.7 ns，
   vs Python 4700/4905 ns，加速比 **21.3x / 32.3x**。
   ARCH 在 Python 3.13 实测的 6288 ns/op 基线目标（< 629 ns/op）已**远超达成**：
   - 实际 Rust parse 221 ns vs 目标 629 ns，**比目标还快 2.8x**
   - 即使按本次 Python 3.14 实测基线 4700 ns，加速比仍 21.3x

7. **ByteSwapped build 是最接近门禁的 case（10.0x）**：
   Python construct 的 ByteSwapped build 路径本身已经很轻量（980 ns，
   仅是字节反序 + 一次 FormatField struct.pack 写入），Rust 端 98 ns 主要是
   PyLong → i32 提取 + Vec 字节交换 + 写入。这是 TransformNode 包装的固有开销下限，
   实际 BitStruct 端到端场景下 Padding/Transform 的开销被多字段摊薄到接近零。

### 结论

Phase 3.3 新增的 Bytewise / BitsSwapped / ByteSwapped / BitPadding / 字节级 Padding
全部性能达标（S-PERF ≥10x）。Phase 3 S-PERF 主目标"BitStruct parse/build ≥10x"
在端到端 BitStruct 场景下达到 **21.2x parse / 32.0x build** 的几何平均加速比，
远超设计预期。

2. **BW3 (ByteSwapped(Int32ub)) parse 单点门禁失败（3.59x < 4.0x）⚠**：
   - 根因：ByteSwapped 是"包装器"节点，inner 字段少（仅 Int32ub 1 个），Python 端
     极简实现（字节反序 + Int32ub），仅 1171 ns；Rust 端 327 ns 中 FFI + Python 分发
     开销占 ~230 ns（绝大头），实际 Rust 处理仅 ~100 ns。
   - 这是包装器类型节点的固有性能特征：FFI 开销不随 inner 复杂度增长，简单 inner 时
     FFI 占比高，加速比降低。
   - **需要 PM 决策**：是否要求 ByteSwapped 等包装器节点也满足 ≥10x（理论极值 ~10x），
     还是接受包装器类型 4-10x 区间作为 Phase 3 验收（BitStruct 端到端场景已 ≥10x）。

3. **BitStruct 端到端场景全部 ≥10x（实际达成 ≥12.5x）**：
   - BS1 12.78x、BS2 12.50x、BW1 14.48x、BW4 10.20x
   - 多字段（3-4 个）摊薄了 FFI 开销，加速比回归到设计预期
   - ARCH 设计阶段目标"BitStruct parse/build ≥10x"在端到端 BitStruct 场景**全部达成**

4. **BitsInteger 系列加速比 5-9x（B1-B4）**：
   - 单字段 BitStruct（仅 1 个 BitsInteger）下，FFI 开销占主导
   - B3 (BitsInteger(32)) parse 8.59x 最优（Python 端 32-bit 慢于 8-bit 比例更大）
   - B4 (signed) 加速比 4.99x 最低（Rust 端 i128 二补码 + Python i128→PyLong 转换较慢）
   - **建议**：实际用户场景中 BitsInteger 通常在 BitStruct 内与其他字段组合，
     单字段场景加速比意义有限

5. **build 方向普遍优于 parse 方向**（12.55x vs 7.67x）：
   - build 路径：实例化已 cached，`obj.build()` 内 Rust 通过 C API 读 attr → write bytes，
     返回 PyBytes（单次构造）
   - parse 路径：Rust 内部需 force_setattr 多次 + PyDict 维护，开销略高
   - 符合架构设计预测（§0 一次 FFI 在两个方向上开销分布不对称）

| 检查项 | 标准 | 实际 | 判定 |
|--------|------|------|------|

**结论**：Phase 3 S-PERF **未通过**严格门禁（≥10x）。build 方向通过，parse 方向未通过，
单点 BW3 parse 失败。端到端 BitStruct 场景全部 ≥10x。

### 已知优化方向（不阻塞 Phase 3 验收的潜在 PM/ARCH 决策点）

- **[OPT-A] parse 方向 force_setattr 优化**：当前 parse 内部通过 `force_setattr` 写实例
  字段（绕过 dataclass `__setattr__`）。可探索 batch setattr 或预构建 `__slots__`
  instance 减少 C API 调用次数。预计可降低 parse 路径 30-50 ns，把 B1 parse 从 5.87x
  提到 ~7x，BW3 从 3.59x 提到 ~4.2x。
- **[OPT-B] FFI 入口 fast path**：对极简单字段场景（如 BitsInteger 单字段），
  可在 Python 包装层添加 fast path（避免 `schema._parse_raw(data)` 间接调用）。
  收益估计 20-40 ns。
- **[OPT-C] i128 → PyLong 转换优化**（B4 signed）：当前用 pyo3 默认 i128 转换路径，
  不在 CPython 小整数 fast path。可改用 i64 + 单独最高位处理，使 B4 加速比从 4.99x → ~8x。

```

A = StructNode 固有不对称 = 32 ns（tp_new + getattr_dict - PyBytes - BuildStream）
```

### 1. OPT-1 实施（`construct-rs/src/nodes/bits_integer.rs`）

**修改**：parse 路径根据 `signed` 与 `length` 选择 PyLong 创建路径：

```rust
if self.signed || self.length < 64 {
    // 值总在 i64 范围内：
    // - signed: -2^(length-1) .. 2^(length-1)-1，length<=64 时 fits in i64
    // - unsigned length<64: 0 .. 2^length-1，length<64 时 fits in i64 正范围
    let value: i128 = if self.signed && (raw >> (self.length - 1)) & 1 == 1 {
        (raw as i128) - (1i128 << self.length)
    } else {
        raw as i128
    };
    Ok((value as i64).into_py(py))   // i64 fast path（~1.7 ns）
} else {
    // unsigned + length == 64：raw 可能 > i64::MAX，用 u64 直接转换
    Ok(raw.into_py(py))              // u64 fast path（~1.9 ns）
}
```

**安全性论证**：
- signed + length ≤ 64：值域 `[-2^(length-1), 2^(length-1)-1]` ⊆ `[-2^63, 2^63-1]` = i64 范围 ✓
- unsigned + length < 64：值域 `[0, 2^length-1]` ⊆ `[0, 2^63-1]` ⊆ i64 正范围 ✓
- unsigned + length == 64：值域 `[0, 2^64-1]`，超出 i64::MAX 时需要 u64 路径 ✓
- i128 仅作为 length==64 + signed 的二补码计算中间值（避免 `1i64 << 64` 溢出，BI-4 不变），最终值仍在 i64 范围内

**保持不变**：
- 对外行为完全一致（44 个单元测试全 PASS，含 `parse_64_bits_max_unsigned`、`parse_signed_64_bits_min/max`、`round_trip_*` 边界）
- build 路径未改动
- length=64 + signed 的 i128 边界处理保留

### 发现的问题（均不阻塞）

**O1 [低] BytewiseNode 慢路径 partial byte 分支为死代码**

- **位置**：`bytewise.rs` L122-132
- **现象**：未对齐慢路径的"剩余不足 8 bit"分支（`if remaining_bits > 0`）在当前使用场景下永远不会触发。
- **分析**：`size = inner.sizeof(ctx)?` 返回**字节数**（usize），`remaining_bits = size.saturating_mul(8)` 起始即为 8 的倍数。64-bit chunk 循环（`while remaining_bits >= 64`）减去 64 仍为 8 倍数；8-bit chunk 分支（`if remaining_bits >= 8`）中 `bits_to_read = full_bytes * 8` 减去后 `remaining_bits` 必为 0。故最后的 `if remaining_bits > 0` 块不可达。
- **影响**：无功能影响（dead code），仅为过度防御性编码。若未来 inner 类型报告非字节倍数的 sizeof（目前不存在），此分支会生效。
- **建议**：可保留作为防御性代码，或添加 `debug_assert!(remaining_bits == 0)` 明确不变量。**非阻塞**。

**O2 [低] TransformNode build/parse 对变长 subcon 的非对称行为**

- **位置**：`transform.rs` L207（build）vs L174-184（parse）
- **现象**：
  - parse：`inner.sizeof(ctx).map_err(...)?` —— 变长 subcon 返回 Generic 错误（TR-1）
  - build：`self.inner.sizeof(ctx).unwrap_or(0)` —— 变长 subcon 静默吞掉错误，仅作为容量提示
- **影响**：`BitsSwapped(GreedyBytes).build(...)` 会成功（不报错），但 `.parse(...)` 失败。这与 Python construct 行为不一致（Python 两方向均通过 Restreamed 回退成功）。
- **根因**：设计 §13.5 文档化为 Phase 3.1 已知限制（变长 subcon 走 Restreamed encoderunit=1 逐字节变换，construct-rs 未实现）。
- **评估**：DEV 在偏离设计说明中已明确记录此限制（过程记录 L1511-1519）。常见用例（`BitsSwapped(Bytes(N))` / `ByteSwapped(Int*ub)`）subcon 均为定长，覆盖主要场景。**非阻塞**，可作为 Phase 3.4+ 扩展点。

**O3 [极低] TransformNode build 容量提示用 unwrap_or(0) 吞错误**

- **位置**：`transform.rs` L207
- **现象**：`let capacity = self.inner.sizeof(ctx).unwrap_or(0);` 将 sizeof 错误静默转为 0（Vec 自动扩容兜底）。
- **影响**：无功能影响（Vec 自动扩容）。但与 parse 路径的 fail-fast 不对称（见 O2）。
- **建议**：与 O2 一并处理（变长 subcon 支持时统一两方向行为）。**非阻塞**。

**O4 [极低] has_expressions 对根级 PaddingNode(expr length) 返回 false**

- **位置**：`nodes/mod.rs` L202-210
- **现象**：PaddingNode 暴露 `new_expr` 但 has_expressions 不递归检查 length 是否为表达式变体。
- **分析**：与 3.2 REV 已识别的小问题一致——Phase 3.1 编译管线对所有 Padding 表达式 length 编译期拒绝（build_padding_node L628-639），所以实际不存在根级 PaddingNode(expr)。Padding 多作为 Struct 字段使用，由 StructNode.has_expressions 覆盖。
- **影响**：无功能影响。
- **建议**：Phase 3.4+ 引入表达式 length 时同步扩展。**非阻塞**。

### 发现的问题

**[INFO-1] `_geomean` 潜在边界 bug**（`benchmark_bitstream.py` L503-507）

```python
def _geomean(values):
    if not values:
        return 0.0
    log_sum = sum(math.log(v) for v in values if v > 0)
    return math.exp(log_sum / len(values))
```

如果 `values` 含 v≤0 的元素（理论上 speedup=0 时，由 `py / rs if rs > 0 else 0`
产生），`log_sum` 跳过这些值（只累加 v>0），但 `len(values)` 包含它们，导致
geomean 偏低。

**实际影响**：无。`rs > 0` 在所有现实场景中成立（Rust 调用至少消耗几纳秒）。
仅当 Rust 完全失败（rs=0）时才会触发，此时其他错误检查会先报错。

**建议修复**（非阻塞，可在后续清理时一并处理）：
```python
def _geomean(values):
    positive = [v for v in values if v > 0]
    if not positive:
        return 0.0
    log_sum = sum(math.log(v) for v in positive)
    return math.exp(log_sum / len(positive))
```

**[INFO-2] Rust 侧 `extract` 为显式 lambda，可能掩盖字段遗漏**

parity 测试中 Rust 侧用 `lambda o: {'a': o.a, ...}` 显式提取字段，Python 侧用
`dict(parsed_obj)`（自动包含全部字段）。如果 Rust 解析后实例有多余字段，
extract 不会抓到。

**实际影响**：无。已逐 case 对照过显式 extract 与 Python dict 输出，
字段集合一致（wfield 在 Rust 侧默认 None，Python 侧 Padding 返回 None，
normalize 后均过滤下划线开头键）。

## PM 验收分析记录（子任务 3.4，S-PERF）

### Benchmark 口径修订独立判断

DEV 自主修订了 benchmark 口径：Python 侧 B1-B4/BW2/BW3 从裸 Bitwise/Transform 改为 BitStruct/Struct 包裹。

PM 独立判断：**修订正确。** 之前 Rust 侧用 BitStructMixin（创建实例 + tp_new + 填字段），Python 侧用裸 Bitwise 返回 int（无 Struct 开销），这是不对等比较。修订后两边都创建容器/实例，开销对等。BW3 parse 从 3.75x → 8.23x 的翻盘不是性能改善，是修正了不公平比较——之前 Rust 在做更多工作却被惩罚。

### 对称性检查

6 个 bit 域场景（B1-B4, BS1, BS2）parse/build 方向仍反转：Rust build < parse，Python build > parse。调查已确认根因是架构差异（Rust build 读属性+写 Vec 快，Python build 需 Container 迭代+bit 重组慢）。所有场景两侧加速比均 ≥11x。

4 个字节域场景（BW1-BW4）方向一致：两边都是 build ≤ parse。

### 跨场景一致性

加速比按复杂度递增：BW3(9.2x) < BW2(10.4x) < BW4(12.0x) < B1(14.5x) < BS2(16.5x) < B3(19.0x)。趋势符合预期——操作越复杂，Python 的 8 倍膨胀和慢循环被放大的越多。

### 技术基本面

全部场景 ≥8x，几何平均 14.41x。BitStruct 端到端 12-14x。Python 的 8 倍内存膨胀在 bit 域场景中被 Rust 的直接位操作完全消除，优势体现充分。

### 异常项

| # | 异常 | 阻塞? | 理由 |
|---|------|:---:|------|
| 1 | BW3 parse 8.23x 最低 | 否 | 薄包装器 + Python 基线极低（2576ns）。≥4x 门禁，≥8x |
| 2 | 6 bit 域场景方向反转 | 否 | 调查确认为架构差异，两侧加速比均 ≥11x |

### 验收结论

S-PERF 全部达标：parse 几何平均 12.14x，build 17.09x，整体 14.41x。无 <4x 场景。口径公平。3.4 验收通过。
