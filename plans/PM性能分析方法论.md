# PM 性能分析方法论

> PM 专属。其他角色（ARCH/DEV/REV/VET）有各自的职责，不需要也不应该遵循此方法论。

## 核心原则

PM 在性能分析中不碰实现细节，不碰开销拆解。PM 的唯一职责是：**判断性能数据在逻辑上是否自洽。**

数据不是用来算加法的，是用来验证逻辑关系的。发现不自洽就是信号，PM 的行动是分派调查，不是自己钻代码。

## 检验维度

"是否自洽"的判断来源不限于以下维度——任何能提供逻辑约束的知识都可以用：

- **技术基本面**：所选技术栈的典型性能表现是什么量级？业界同类方案的加速比在什么范围？当前数据是否与这些基本面冲突？
- **数据内部关系**：相关数据之间的比率、差值、增长模式是否符合预期？对称操作的成本是否对称？跨场景的数据在数学模型上是否一致？
- **复杂度一致性**：成本随输入规模的增长是否符合预期的复杂度类别（常数/线性/超线性）？不该随规模变化的成本是否确实不变？
- **跨阶段/跨版本递进**：新版本的计算量相比旧版本是增加还是减少？性能极限应该随之上升还是下降？实际数据是否符合这个方向？
- **横向对比**：与同类系统、同类任务、参考实现的数据相比，是否在合理的范围内？

以上不是穷举。核心问题是：**我已知的任何事实、逻辑、约束，是否与当前数据矛盾？** 有矛盾就是信号。

## 发现不自洽时的行动

1. **不分派优化任务**——你还不知道问题在哪
2. **分派调查任务**——要求查明数据为何与逻辑矛盾，提供所需的新数据维度
3. **拿到调查结果后**，判断根因是否在预期之内，再决定是否分派优化

## 已应用案例（本项目）

以下案例说明方法论如何应用，不是 checklist：

| 案例 | 已知约束（逻辑） | 观察数据 | 矛盾 | 结论 |
|------|-----------------|---------|------|------|
| Phase 1: 2x | Rust 计算性能远超 Python；同类 Rust-core 库达 10x+ | rs 仅 2x py | 与技术基本面冲突 | 不是极限，是架构问题 |
| Phase 2: 性能极限 | Phase 2 计算量 > Phase 1，Rust 优势被放大 | Phase 2 性能 < Phase 1 | 与递进逻辑矛盾 | 实现有结构性开销 |
| Phase 2.5: parse/build 比 | Python parse ≈ build（逻辑对称） | rs parse >> build | 对称性被破坏 | parse 路径有多余开销 |
| Phase 2.5: 差值 vs 字段数 | 固定开销不随字段数变化 | E1(2字段)与E3(6字段)差距相同 | 差值恒定 | 瓶颈是固定成本，非字段级 |

每个案例用的逻辑约束不同。下一个问题会有新的约束来源。关键是：**先想清楚什么必须成立，再看数据是否满足。**
