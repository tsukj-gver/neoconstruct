##### [B1 阻塞] CompiledNode 直接引用 pyo3 类型，construct-rs 无 pyo3 依赖

**文档位置**：§2.2 enum 定义 `PyCallback(PyCallbackNode)`；§2.5 `PyCallbackNode { callable: pyo3::Py<pyo3::types::PyAny>, ... }`；§6.2 `CompiledExpr::PyCallback(pyo3::Py<pyo3::PyAny>)`。

**问题**：经核实 `construct-rs/Cargo.toml`，Rust 内核 crate **不依赖 pyo3**（这是顶层设计 §1.1/§1.2 的架构边界：Rust 内核层与 Python 用户层隔离）。文档中所有 `pyo3::Py<pyo3::PyAny>` 引用在 construct-rs 中**无法解析，编译会失败**。

文档 §2.2 注释称"Phase 12 仅定义结构并允许编译产出"——但"定义结构"就已经引入了 pyo3 类型，无法编译通过。

**违反**：
- 顶层设计 §1.1 架构分层（Rust 内核层不依赖 pyo3）
- 顶层设计 §1.2 模块清单（PyCallback 是"construct-rs 新增"，但运行时 FFI 是 Phase 13）

**建议修改方向（三选一）**：
- **方案 A（推荐）**：PyCallback variant 和 PyCallbackNode 整体推迟到 Phase 13 定义。Phase 12 的 CompiledNode 不含 PyCallback variant；遇到 Python callable 来源时编译为 CompiledDynamic（文档 §4.3 已有此降级方案）。Phase 13 再在 construct-rs（增加 pyo3 可选依赖，feature gate `python`）或 construct-py 中扩展 CompiledNode。
- **方案 B**：PyCallback variant 用 `#[cfg(feature = "python")]` 门控，callable 字段用 `Box<dyn std::any::Any + Send + Sync>` 间接持有（Phase 13 downcast）。需在 Cargo.toml 增加 `[features] python = ["pyo3"]`。
- **方案 C**：CompiledExpr::PyCallback 同理处理（或直接删除该 variant，Phase 12 不产生它）。

##### [B2 阻塞] CombinedExpr 不实现 Clone，表达式编译方案与源码事实矛盾

**文档位置**：§6.3 `compile_expr` 代码 `Ok(CompiledExpr::Native(expr.clone_ref()))`；§6.4 "CombinedExpr 的所有 variant 都实现了 `Clone`（`#[derive(Clone, Debug)]`，见 `expr.rs:105`）"。

**问题**：经逐行核实源码，上述声称**全部错误**：
- `CombinedExpr` enum（`expr.rs:1082`）：`#[derive(Debug)]`——**无 Clone**。
- `BinExpr`（`expr.rs:316`）、`UniExpr`（`679`）、`FuncPath`（`761`）、`CondExpr`（`914`）、`ListPath`（`983`）：均只有 `#[derive(Debug)]`——**无 Clone**。
- `Path`（`105`）和 `ConstExpr`（`193`）有 Clone，但不能代表全部 variant。
- `clone_ref()` 方法在 CombinedExpr 上**不存在**（grep 确认无此方法）。

因此 §6.3 的 `compile_expr` 实现无法编译，§6.4 "运行时零拷贝（编译时 clone 一次）"的前提不成立。

**影响范围**：所有持有 `CompiledExpr` 的 CompiledNode variant（§2.4 列出 BytesExpr/ArrayExpr/SeekExpr/PointerExpr/IfThenElse/Switch/Computed 等）的表达式编译都会受影响。

**建议修改方向（二选一）**：
- **方案 A（推荐）**：`CompiledExpr::Native(Arc<CombinedExpr>)`。编译时 `Arc::new(expr_clone_or_move)`，clone 廉价（一次原子计数）。但前提是 `compile_expr` 接收 `&CombinedExpr` 时仍需 clone 整棵树——除非能消费（move）表达式。由于 `BuildConstruct::compile(&self, ...)` 只有 `&self`，表达式字段也是 `&`，无法 move。因此仍需 CombinedExpr 可 Clone。
- **方案 B**：为 CombinedExpr 及 BinExpr/UniExpr/FuncPath/CondExpr/ListPath 添加 `#[derive(Clone)]`。Value 已是 Clone（`value.rs:39`），Box<CombinedExpr> 在 CombinedExpr derive Clone 后可递归 clone。此方案需 ARCH 在设计文档中明确"Phase 12 需为 CombinedExpr 补充 Clone derive"作为前置改动，并纳入子任务 12.3。

> 无论哪个方案，§6.3 的 `clone_ref()` 必须改为 `expr.clone()`（方案 B）或 `Arc::new(expr.clone())`（方案 A+B）。

##### [B3 阻塞] CompiledNode variant 计数错误（71 vs 实际 72）

**文档位置**：§2.2 注释"variant 数量：71 个（70 个镜像 CombinedConstruct + 1 个 PyCallback）"；§10.4 出口标准"CompiledNode 定义完整（71 variant）"。

**问题**：实际 CombinedConstruct 有 **71 个 variant**（70 内置 + `Dynamic(Box<dyn Construct>)` escape-hatch，见 `combined.rs:182`）。CompiledNode enum 定义（§2.2 列表）包含：70 个内置镜像 + `Dynamic(CompiledDynamic)` + `PyCallback(PyCallbackNode)` = **72 个 variant**。文档反复说 71，自相矛盾。

若采纳 B1 方案 A（删除 PyCallback），则为 71；否则为 72。计数必须修正一致，否则出口标准无法核验。

##### [B4 阻塞] Adapter 闭包迁移的 Send+Sync 类型不匹配

**文档位置**：§5.4 方案 1："DecodeFunc/EncodeFunc 从 Box 改为 Arc（Send + Sync）；编译时 Arc::clone" + "Adapter::new 保持接受 Box，内部转 Arc: `decode: Arc::from(decode)`"。

**问题**：当前闭包类型是 `Box<dyn Fn(&Value, &Context) -> Result<Value>>`（`adapters.rs:45`，**无 Send+Sync bound**）。目标类型 `Arc<dyn Fn(...) + Send + Sync>`。文档称"Adapter::new 保持接受 Box（无 Send+Sync），内部转 Arc（有 Send+Sync）"——这在 Rust 类型系统中**不可行**：无法将 `Box<dyn Fn>`（无 Send+Sync 保证）转为 `Arc<dyn Fn + Send + Sync>`，编译器会拒绝。

`Arc::from(Box<dyn Fn>)` 最多得到 `Arc<dyn Fn>`（无 Send+Sync），而非文档要求的 `Arc<dyn Fn + Send + Sync>`。

**建议修改方向**：
- 明确 `DecodeFunc`/`EncodeFunc`/`SymmetricFunc`/`CheckFunc` 类型别名**全部**改为含 `Send + Sync` bound：
  ```rust
  pub type DecodeFunc = Arc<dyn Fn(&Value, &Context) -> Result<Value> + Send + Sync>;
  ```
- `Adapter::new` 的参数类型也相应改为 `Arc<...>`（或 `Box<dyn Fn + Send + Sync>` 再转 Arc）。
- 在子任务 12.6 中明确：需全局搜索所有闭包构造点，验证其捕获值满足 `Send + Sync`（非捕获闭包天然满足；捕获 i64/&str 等满足；捕获 Rc/RefCell 等不满足——需确认无此类用法）。
- 文档 §5.4 的代码示例 `Arc::from(decode)` 必须修正为类型匹配的转换。

#### 性能：⚠️ 有条件通过（2 个重要）

##### [I1 重要] 叶子节点 exec_parse 的 sink 写入路径低效且协议不清

**文档位置**：§2.3.1"叶子构造器的 exec_parse 直接委托给内嵌的 CombinedConstruct 具体类型"；§7.5 CompiledStruct::exec_parse 示例。

**问题**：CompiledExec trait 的 `exec_parse` 签名为 `-> Result<()>`（写入 sink，不返回 Value）。但：
1. 叶子节点（如 CompiledFormatField）调用 `inner.parse(stream, ctx)` 得到 `Value` 后，需要写入 sink。OutputSink trait 的方法是面向复合节点的（`set_field` 需要字段名，`push_item` 面向数组）——**叶子节点不知道自己的字段名/位置**，无法直接选择 sink 方法。
2. §7.5 的解决方案是对每个字段创建 `sub_sink = sink.sub_sink_for_field(name)` → 叶子写入 sub_sink → `sub_sink.into_value()` → `sink.set_field(name, value)`。这为**每个叶子字段**引入了一次 ValueSink 分配 + IndexMap 构建 + into_value 序列化 + 再写入父 sink 的 IndexMap。对于 100 字段 Struct，这是 100 次额外分配 + clone。

**评估**：文档 §7.7 承认"Phase 12 的 sink 价值主要是架构准备"，接受性能不优于旧路径。但**协议本身**（叶子如何写入）的设计需要更明确，否则 DEV 实现时会产生歧义。

**建议**：ARCH 应在文档中明确选择以下之一，并补充到 §7.3/§7.5：
- **方案 A**：OutputSink 增加 `set_leaf_value(Value)` 方法。复合节点在调用叶子 `exec_parse` 前设置"当前字段上下文"，叶子直接 `sink.set_leaf_value(value)`。ValueSink 用一个 `pending: Option<Value>` 字段暂存，复合节点取出后写入正确位置。避免每叶子创建 sub_sink。
- **方案 B**：CompiledExec 区分标量/容器——叶子节点的 exec_parse 返回 `Result<Option<Value>>`（Some 表示标量值），复合节点收集后写入 sink。但这改变 trait 签名。
- **方案 C（最小改动）**：保持当前设计，但在文档中明确标注"Phase 12 每叶子字段有一次额外 ValueSink 分配（已知开销，Phase 14 优化）"，并在出口标准中移除"编译执行树 ≥ 旧路径速度"的隐含要求（§8.4 已部分提及，但应更明确）。

##### [I2 重要] CompiledStruct::exec_parse 的 sink+Context 双写 clone

**文档位置**：§7.5 `sink.set_field(name, value.clone())` + `child_ctx.insert(name, value)`；§7.5 末尾"Phase 12 先用双写（正确性优先），Phase 14 优化为共享"。

**问题**：每个字段值 clone 一次。对大 Bytes/Container 有开销。

**评估**：文档已识别此问题并标注为阶段性权衡。**可接受**，但建议在出口标准中明确"Phase 12 不要求性能 ≥ 旧路径"（与 I1 方案 C 一致）。

##### 性能问题其余项：✅ 通过

- `&mut dyn OutputSink` 每字段一次虚分发：文档论证"字段写入远少于字节操作"，合理。100 字段 Struct = 100 次虚分发（~ns 级），相对字节解析可忽略。
- CompiledNode enum 大小（§10.3 风险点 1）：文档要求 DEV 实测 `size_of::<CompiledNode>()`，>128 字节则对大 variant 加 Box。参考 Phase 11 §6.1（CombinedConstruct ~80 字节）的评估方法正确。
- enum_dispatch 分发本身零开销，与 Phase 11 一致。

##### [I3 重要] CompiledDynamic 与 CombinedConstruct::Dynamic 的 BuildConstruct 分发问题

**文档位置**：§2.5 `CompiledDynamic { inner: Box<dyn crate::core::Construct> }`；§4.3"遇到上述来源时，编译为 CompiledDynamic"。

**问题**：CombinedConstruct 已有 `Dynamic(Box<dyn Construct>)` variant（`combined.rs:182`）。当 SchemaCompiler 通过 `BuildConstruct::compile` 分发到 Dynamic variant 时，enum_dispatch 会要求 `Box<dyn Construct>` 实现 `BuildConstruct`。但 `Box<dyn Construct>` 是 trait object，enum_dispatch 无法对它生成 match 分发（它不是 CombinedConstruct 的"内部具体类型"）。

文档 §5.2 说"enum_dispatch 宏会为 CombinedConstruct 生成 compile 方法的 match 分发"——但对 Dynamic variant，enum_dispatch 会尝试调用 `inner.compile()`，而 `Box<dyn Construct>` 不实现 BuildConstruct。

**建议**：ARCH 应明确 Dynamic variant 的特殊处理：
- 方案：在 CombinedConstruct 上为 BuildConstruct **手写** impl（不依赖 enum_dispatch 自动生成），对 Dynamic 分支直接返回 `CompiledNode::Dynamic(CompiledDynamic { inner: self.0.clone() })`。其余 variant 仍可走 enum_dispatch。
- 或：BuildConstruct trait 不用 enum_dispatch，改为 SchemaCompiler 内部手写 match（文档 §4.1 提到"直接 match CombinedConstruct variant"，与 §5.2 的 enum_dispatch 方案矛盾——应统一）。

##### [I4 重要] LazyBound 延迟编译机制未定义

**文档位置**：§8.5"LazyBound 的 compile 不能立即递归...需产出 CompiledLazyBound（持有延迟绑定引用），运行时首次访问时才编译子节点"；§10.3 风险点 4。

**问题**："运行时首次访问时才编译子节点"——这需要 CompiledLazyBound 在运行时能触发编译，即持有 SchemaCompiler 引用或等价能力。但 CompiledSchema 是编译产物，持有编译器会导致生命周期/所有权问题（CompiledSchema 应是 `'static` 的，编译器不应长存）。

文档未定义 CompiledLazyBound 的具体结构。

**建议**：ARCH 应明确选择：
- **方案 A（推荐，简单）**：CompiledLazyBound 持有原始的 `LazyBound` 声明树节点（含 `Box<CombinedConstruct>` 子构造器引用），运行时降级为旧路径执行（`inner.parse(stream, ctx)`），不走编译执行树。这与 §4.3 的"降级为 CompiledDynamic"思路一致。
- **方案 B**：CompiledLazyBound 持有 `OnceLock<CompiledNode>` + 编译所需的 `Box<dyn Fn() -> Result<CompiledNode>>`（闭包捕获绑定信息）。复杂度高，不推荐 Phase 12。

##### 完备性其余项：✅ 基本通过

- 11 个子任务覆盖了所有构造器类别（叶子/包装器/复合/枚举计算/流操作惰性/控制流/escape-hatch/测试）。**无遗漏类别**。
- Sink 场景覆盖：叶子/复合/嵌套/数组/条件分支均有提及（§7.5-7.6），虽协议需细化（见 I1），但场景识别完整。
- 错误路径：parse 中途失败时，`exec_parse` 返回 `Err`，`CompiledSchema::parse_bytes` 通过 `map_err(e.with_path_prefix)` 传播。sink 状态在 Err 时被丢弃（ValueSink 未 into_value）。这在纯 Rust 路径下是正确的（Err 即整体失败）。
- 边界条件：循环引用（max_depth=256）、空 Struct、空输入在 §8.2 测试矩阵中覆盖。

```rust
pub struct LazyBound {

}
```

### 设计决策（实现层面）

1. **enum_dispatch → 手写 match**：设计文档 §5.2 使用 `#[enum_dispatch(BuildConstruct)]` 为 CombinedConstruct 自动生成 match 分发。实测发现 enum_dispatch 宏对 Dynamic variant（`Box<dyn Construct>`）生成代码时 panic（"This macro does not support unsized types"）。改为手写 match，功能等价。设计文档 §5.2/§4.1 已预留此方案（S2 统一表述："普通 variant 走 enum_dispatch 自动分发；Dynamic variant 手写降级分支"）。Phase 12.3 中 Dynamic Box→Arc 迁移后可恢复 enum_dispatch。

2. **CompiledNode 71 variant 均为单元结构体**：Phase 12.1 只定义 enum 结构和 trait，所有 compiled node struct（如 CompiledFormatField、CompiledStruct 等）暂为单元结构体 `pub struct CompiledFormatField;`。真实字段（inner construct、pre-compiled expression、mapping table 等）在 12.2-12.8 子任务中逐步添加。enum 定义和 variant 列表在后续阶段不变。

3. **CompiledExec stub 返回 ConstructError::Generic**：所有 71 个 compiled node 的 exec_parse/exec_build/exec_sizeof 均返回 `Err(ConstructError::Generic { path, message })`，message 含 "not yet implemented"。这确保编译可过且测试可断言，同时不使用 `unreachable!()` 或 `todo!()`。

4. **try_fold_static_size stub 返回 None**：所有 compiled node 的 try_fold_static_size 返回 None（大小未知），sizeof 走 exec_sizeof 路径（也是 stub Err）。真实实现从 12.4 开始填充。

5. **ValueSink.into_value 优先级**：pending scalar > fields (Container) > items (List)。与设计文档 §7.4 Line 1538-1547 一致。

6. **OutputSink 7 方法签名**：完全遵循设计文档 §7.3（v2 版本），包括 `set_scalar(Value)` 方法（I1 修正）。所有方法返回 `Result<()>`，into_value 返回 `Result<Value>`。
