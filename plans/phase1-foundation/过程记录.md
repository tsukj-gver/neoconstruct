**嵌套结构 Display** ❌ 不一致：

以 `Container({b: Container({c: 3})})` 为例（value.rs 测试 `display_nested_container_indents`）：

| 行 | Python 缩进 | Rust 缩进 | 一致性 |
|----|-----------|----------|--------|
| `Container:` | 0 | 0 | ✅ |
| `b = Container:` | 4 | 4 | ✅ |
| `c = 3` | **8** | **12** | ❌ |

**根因分析**：

Rust `format_container` 中 `value_to_display(val, inner)` 以 `inner`（= `indent + 1`）级别渲染内部值，导致内部 Container 的子条目已有 `inner + 1` 级缩进。然后 `indent_lines` 又给后续行添加当前级 `pad`，导致缩进**双重计算**。

Python 的做法：`value_to_string(v)` → `str(v)` 将内部值渲染在**基准级别**（4 空格），然后 `indentation.join(value_to_string(v).split("\n"))` 只在外层加一次缩进。

当前 Rust 代码（value.rs L593）：
```rust
let rendered = value_to_display(val, inner);  // 传 inner 给内层
```

应改为：
```rust
let rendered = value_to_display(val, 0);  // 内层从基准级别开始
```

同理 `format_list`（L609）也需修改。

**影响范围**：所有嵌套 Container/List 的 Display 输出（非标量子值）。由于 Display 仅用于调试输出，不影响 parse/build 功能正确性。

**现有测试的断言不够严格**：`display_nested_container_indents` 使用 `s.contains("        c = 3")`（8 空格），由于 12 空格的字符串也包含 8 空格子串，测试虽通过但未检测到此 bug。建议修复后将断言改为精确匹配。

### 综合结论：❌ 驳回

**驳回理由**：Display 实现中嵌套 Container/List 的缩进计算存在 bug（双重缩进），导致嵌套结构的输出与 Python 版本不一致。代码注释明确声称"Matches the Python original's 4-space indentation"（L29），但实际缩进行为不符。

**具体问题**：

1. **[BUG-必须修复] Display 嵌套缩进双重计算**：
   - **位置**：`value.rs` L593（`format_container`）和 L609（`format_list`）
   - **根因**：`value_to_display(val, inner)` 将 `inner` 传给内层渲染，内层已有缩进。`indent_lines` 再加一次缩进。
   - **Python 行为**：内层从基准级别（4 空格）开始，外层 `indentation.join` 只加一次缩进。双层嵌套 c=8 空格。
   - **Rust 行为**：内层从 `inner+1` 级别开始（8 空格），`indent_lines` 再加 4 空格。双层嵌套 c=12 空格。
   - **修复方案**：将 `value_to_display(val, inner)` 改为 `value_to_display(val, 0)`，让 `indent_lines` 负责所有额外缩进。`format_list` 同理。
   - **影响**：所有嵌套 Container/List 的 Display 输出。不影响 parse/build 功能。

2. **[测试-建议修复] `display_nested_container_indents` 断言不够严格**：
   - `s.contains("        c = 3")`（8 空格）在 12 空格字符串中仍能匹配
   - 建议改为精确匹配（如检查整行内容或使用 `assert_eq!`）

3. **[非阻塞] Bool/NaN Display 大小写差异**：
   - Python `True`/`False`/`nan` vs Rust `true`/`false`/`NaN`
   - 属语言惯例差异，Display 仅供人类阅读，不参与数据交换

4. **[非阻塞] 设计质疑 `is_int`/`is_uint` 语义**：
   - DEV 已提出。当前 `is_int` 仅匹配 `Int(i64)`，不覆盖 UInt/BigInt
   - 语义清晰可预测，`to_i64` 提供跨类型转换
   - 建议 PM/ARCH 确认并更新设计文档

### [设计质疑] 偏离说明

**`with_path_prefix` 签名：`&self` → `self`**

- 设计文档：`pub fn with_path_prefix(&self, prefix: &str) -> Self`
- 实际实现：`pub fn with_path_prefix(self, prefix: &str) -> Self`
- 原因：`Stream` 变体的 `io::Error` 与 `StringEncoding` 变体的 `FromUtf8Error` 均未实现 `Clone`。设计提示的 `source.kind().into()` 仅适用于 `io::Error`（且会丢失原始错误详情），对 `FromUtf8Error` 完全无法在 `&self` 下重建。按值消费可原样移动 source 字段，完整保留底层错误。该方法语义为"错误传播时丰富"，调用方不会再使用原错误，按值消费符合惯用 Rust 模式。
- 影响：属小问题（参数传递方式微调），不影响错误类型本身。等待 PM/ARCH 确认。
