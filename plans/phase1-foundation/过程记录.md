**嵌套结构 Display** ❌ 不一致：

以 `Container({b: Container({c: 3})})` 为例（value.rs 测试 `display_nested_container_indents`）：

| 行 | Python 缩进 | Rust 缩进 | 一致性 |
|----|-----------|----------|--------|
| `Container:` | 0 | 0 | ✅ |
| `b = Container:` | 4 | 4 | ✅ |
| `c = 3` | **8** | **12** | ❌ |

**根因分析**：

Rust `format_container` 中 `value_to_display(val, inner)` 以 `inner`（= `indent + 1`）级别渲染内部值，导致内部 Container 的子条目已有 `inner + 1` 级缩进。然后 `indent_lines` 又给后续行添加当前级 `pad`，导致缩进**双重计算**。

Python 的做法：`value_to_string(v)` → `str(v)` 将内部值渲染在**基准级别**（4 空格），然后 `indentation.join(value_to_string(v).split("\n"))` 只在外层加一次缩进。

当前 Rust 代码（value.rs L593）：
```rust
let rendered = value_to_display(val, inner);  // 传 inner 给内层
```

应改为：
```rust
let rendered = value_to_display(val, 0);  // 内层从基准级别开始
```

同理 `format_list`（L609）也需修改。

**影响范围**：所有嵌套 Container/List 的 Display 输出（非标量子值）。由于 Display 仅用于调试输出，不影响 parse/build 功能正确性。

**现有测试的断言不够严格**：`display_nested_container_indents` 使用 `s.contains("        c = 3")`（8 空格），由于 12 空格的字符串也包含 8 空格子串，测试虽通过但未检测到此 bug。建议修复后将断言改为精确匹配。

### 综合结论：❌ 驳回

**驳回理由**：Display 实现中嵌套 Container/List 的缩进计算存在 bug（双重缩进），导致嵌套结构的输出与 Python 版本不一致。代码注释明确声称"Matches the Python original's 4-space indentation"（L29），但实际缩进行为不符。

**具体问题**：

1. **[BUG-必须修复] Display 嵌套缩进双重计算**：
   - **位置**：`value.rs` L593（`format_container`）和 L609（`format_list`）
   - **根因**：`value_to_display(val, inner)` 将 `inner` 传给内层渲染，内层已有缩进。`indent_lines` 再加一次缩进。
   - **Python 行为**：内层从基准级别（4 空格）开始，外层 `indentation.join` 只加一次缩进。双层嵌套 c=8 空格。
   - **Rust 行为**：内层从 `inner+1` 级别开始（8 空格），`indent_lines` 再加 4 空格。双层嵌套 c=12 空格。
   - **修复方案**：将 `value_to_display(val, inner)` 改为 `value_to_display(val, 0)`，让 `indent_lines` 负责所有额外缩进。`format_list` 同理。
   - **影响**：所有嵌套 Container/List 的 Display 输出。不影响 parse/build 功能。

2. **[测试-建议修复] `display_nested_container_indents` 断言不够严格**：
   - `s.contains("        c = 3")`（8 空格）在 12 空格字符串中仍能匹配
   - 建议改为精确匹配（如检查整行内容或使用 `assert_eq!`）

3. **[非阻塞] Bool/NaN Display 大小写差异**：
   - Python `True`/`False`/`nan` vs Rust `true`/`false`/`NaN`
   - 属语言惯例差异，Display 仅供人类阅读，不参与数据交换

4. **[非阻塞] 设计质疑 `is_int`/`is_uint` 语义**：
   - DEV 已提出。当前 `is_int` 仅匹配 `Int(i64)`，不覆盖 UInt/BigInt
   - 语义清晰可预测，`to_i64` 提供跨类型转换
   - 建议 PM/ARCH 确认并更新设计文档

### [设计质疑] 偏离说明

**`with_path_prefix` 签名：`&self` → `self`**

- 设计文档：`pub fn with_path_prefix(&self, prefix: &str) -> Self`
- 实际实现：`pub fn with_path_prefix(self, prefix: &str) -> Self`
- 原因：`Stream` 变体的 `io::Error` 与 `StringEncoding` 变体的 `FromUtf8Error` 均未实现 `Clone`。设计提示的 `source.kind().into()` 仅适用于 `io::Error`（且会丢失原始错误详情），对 `FromUtf8Error` 完全无法在 `&self` 下重建。按值消费可原样移动 source 字段，完整保留底层错误。该方法语义为"错误传播时丰富"，调用方不会再使用原错误，按值消费符合惯用 Rust 模式。
- 影响：属小问题（参数传递方式微调），不影响错误类型本身。等待 PM/ARCH 确认。

### [设计质疑] `get_path` 首键使用 `get_recursive` 向上查找父级

**位置**：设计文档 `docs/模块设计-Context容器.md` "路径查找逻辑" 第3条；实现 `context.rs` L191-196

**Python 行为**：
- `this.field` 表达式（expr.py L184-188）仅在当前 context 层级查找 `field`
- 父级字段需通过 `context._.field` 显式访问
- 例如在嵌套 Struct 中，`this.field` 不会自动穿透到父级 Struct 的 context

**设计文档**：
> 查找规则：
> 3. 如果当前层级找不到，向上查找 parent

**Rust 实现**：
```rust
let mut current = self.get_recursive(first_key).ok_or_else(|| ...)?;
```

**影响**：Rust 的 `get_path` 比 Python 的 `this` 表达式更具穿透性——能自动找到父级 context 中的字段。例如：
- Python：`this.field` 在子 Struct 中找不到父级 `field` → `KeyError`
- Rust：`ctx.get_path(&["field"])` 能通过 parent 链找到父级的 `field` → 成功

**REF 评估**：这可能是**有意的设计简化**——Rust 用一个统一的 `get_path` + `get_recursive` 替代 Python 中 `this.field`（当前层）和 `context._.field`（父级层）两种模式。在实际使用中，`get_recursive` 的穿透行为在大多数场景下更方便（减少了显式父级访问的需要）。

**建议**：PM/ARCH 确认此行为是否为有意设计。如果期望严格匹配 Python 的 `this` 行为（不穿透父级），应将 `get_path` 中首键查找从 `get_recursive` 改为 `get`。

**风险等级**：低。此差异使得 Rust 查找范围更广，不会导致"找不到"的问题，只可能导致"意外找到"——但字段名冲突在实践中有规范的命名约定，风险可控。

### [设计质疑] 偏离说明（均为小问题，按自认为合理方式实现）

1. **`ByteStream::seek` 使用 `set_position` 而非 `cursor.seek(SeekFrom::Start(pos))`**：两者语义等价（Cursor 对 SeekFrom::Start 不可能返回错误），`set_position` 更简洁高效（避免不必要的错误检查）。对外行为完全一致。

2. **`ByteStream::size/tell/is_eof` 使用 `cursor.get_ref().len()` / `cursor.position()` 而非 seek-based 实现**：Python `stream_size` 通过 seek-to-end-then-seek-back 实现。Rust 版本直接访问内部 Vec 长度，更高效且不需要 seek 恢复位置。`size()` 天然不改变位置（直接读 len），`is_eof` 通过 `position >= len` 判断。对外行为一致。

3. **`stream_seek` 的 `i64` 偏移**：设计文档签名为 `offset: i64`，但 `Stream::seek` 为 `pos: u64`（绝对定位）。`stream_seek` 对负偏移返回 `InvalidInput` 错误，对非负偏移转为 `u64` 调用 `Stream::seek`。Python `stream_seek` 支持 `whence` 参数（SEEK_SET/SEEK_CUR/SEEK_END），设计文档移除了 `whence` 简化为仅绝对定位，Phase 6 Pointer 等构造器可能需要扩展。

4. **`ByteStream` 额外实现 `Default` trait**：设计文档未列出，但 `Default` 等价于 `new_write()`，是 Rust 惯例。所有构造函数已有对应 doctest 验证。

1. **便捷方法定义在 `impl dyn Construct` 而非 trait 默认方法**：设计文档将 `parse_bytes`/`build_bytes` 等列为 trait 的一部分，但 Rust 不允许在 trait 定义中提供方法体（除非是默认实现）。将便捷方法放在 `impl dyn Construct` 上使得所有 `&dyn Construct` 引用可以调用这些方法，且具体类型可通过 `(&concrete as &dyn Construct).parse_bytes(...)` 调用。这与 Python 中 `Construct.parse(data)` 在基类上定义、子类继承使用的模式对应。

2. **`parse_file`/`build_file` 使用 `std::fs::read/write` 而非流式读取**：设计文档说明"从文件解析"和"构建到文件"。Python 版本使用 `open(filename, 'rb')` 传递文件对象给 `parse_stream`。Rust 版本先将整个文件读入内存再解析，简化了实现（避免实现 `Stream` for `std::fs::File`）。对于 construct 库的典型使用场景（解析二进制格式），文件通常不大，全量读取合理。

3. **`Subconstruct` 和 `Renamed` 不实现 `name`/`docs`/`flagbuildnone` 等 Python 属性**：Python 的 Construct 基类有 `name`、`docs`、`flagbuildnone`、`parsed` 等属性。Rust 版本将这些推迟到需要时再添加（Phase 2/3 的 Struct 等复合构造器会使用 Renamed 的 name 字段）。

**已知设计质疑（确认，不阻塞）**：

1. **`impl dyn Construct` vs trait 默认方法**（DEV 已提出，REF 已确认）：
   - Rust 不允许在 trait 定义中提供方法体（除非是默认实现，但 `dyn Construct` 不支持默认方法调用）
   - `impl dyn Construct` 是 Rust 对象安全限制下的合理替代方案
   - 调用方式需通过 `&dyn Construct` 引用，具体类型可通过强转调用
   - 建议设计文档明确标注此实现方式

2. **`parse_file`/`build_file` 全量读写**（DEV 已提出，REF 已确认）：
   - Python 使用流式 I/O，Rust 全量读入内存
   - 对 construct 典型使用场景合理（二进制格式文件通常不大）
   - Phase 6 如需流式解析超大文件可扩展 Stream trait

3. **Python name/docs/flagbuildnone 等属性未实现**（DEV 已提出）：
   - 这些是 Python 特有的内省/钩子机制
   - Rust 推迟到实际需要时再添加，Phase 1 无功能影响
