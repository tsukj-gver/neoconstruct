### 设计决策说明

#### 1. StructNode.parse 返回 PyDict（非用户类实例）

设计文档 §C.3.4 明确 StructNode.parse 产出 `PyDict`（字段名→值的映射），
用户类实例化由 Python 侧 `cls(**dict)` 完成。
StructRefNode 负责将 StructNode 产出的 dict 通过 Rust→Python 回调实例化为用户类。

#### 2. StructRefNode 存储 `Py<PyType>` 而非 schema 引用

设计文档 §B.7 描述编译产物存储在用户类的 `_construct_compiled` 属性上。
StructRefNode 持有类引用 `Py<PyType>`（而非直接持有 schema），原因：
- 支持互相引用（NodeA 引用 NodeB，NodeB 引用 NodeA）—— 若直接持有 schema 引用，
  构造 NodeA 时 NodeB 的 schema 尚未存在。
- `resolve_schema` 在首次 parse 时从 `cls._construct_compiled` 属性读取，
  缓存到 `OnceLock<Py<CompiledSchema>>`，后续调用零查找。

#### 3. StructRefNode.sizeof 返回 Err（[设计质疑]）

Construct trait 的 `sizeof` 签名 `fn sizeof(&self, ctx: &Context<'_>) -> Result<usize, ConstructError>`
不含 `Python<'py>` GIL token，因此 StructRefNode 无法在 sizeof 中调用 `resolve_schema`
（需要 GIL 访问 Python 对象属性）。

当前返回 `ConstructError::Generic`，path 为空字符串。
后续若需要 sizeof 支持，需修改 Construct trait 的 sizeof 签名增加 `py: Python<'_>` 参数。
**等待 PM/ARCH 决策**。

#### 4. enum_dispatch 关键修复

`#[enum_dispatch(Construct)]` 标注在 Node enum 上时，enum_dispatch 0.3.13 要求
被分派的 trait **也**标注 `#[enum_dispatch]`。否则 enum_dispatch 在编译期查找 trait 信息失败，
**静默不生成 impl**（不报错）。

1.3 的原子节点（FormatField/Bytes/GreedyBytes）的 parse/build/sizeof 不递归调用
其他 Node 方法，因此即使没有 enum_dispatch 生成的 `Node::parse`（通过 `Construct` trait），
`node.parse(...)` 仍通过 `match` 手动分派到具体变体的方法。

1.4 的 StructNode.parse 中 `field.1.parse(py, ...)` 需要对任意 Node 变体调用 parse，
此时需要 enum_dispatch 生成的 `Node: Construct` impl。缺少 trait 标注导致编译失败，
暴露了此潜伏 bug。

修复：在 `Construct` trait 定义上添加 `#[enum_dispatch]`。

#### 5. Context 嵌套未使用

设计文档 §C.5 提供了 `Context::new_child` 用于嵌套 context。
Phase 1 的 StructNode.parse 直接在传入的 ctx 上 `set_field`，不创建 child context。
原因：Phase 1 无表达式系统（this/obj_ 引用），不需要 context 层级查找。
Phase 2 添加表达式系统时可启用 child context。

#### 8. useless_conversion allow 评估：✅ 合理（不掩盖真实问题）

**质疑内容**：DEV 在 compile.rs:31 和 schema.rs:23 添加模块级
`#![allow(clippy::useless_conversion)]`，理由是 pyo3 0.22 的 #[pyfunction]/
#[pymethods] 宏展开在返回 PyResult<T> 的包装代码时生成 `PyErr.into()` 冗余转换。

**VET 评估方法**：分析 pyo3 0.22 宏展开行为 + 检查用户代码中是否存在真实的
useless_conversion。

**用户代码分析**：
- compile.rs 用户代码中 `.into()` 调用：
  - 行 79-86 `Err(ConstructError::Compilation { ... }.into())`：从 `ConstructError` 到 `PyErr`
    的转换，**必要的 `.into()`**（非 useless）。
  - 行 102 `Ok(CompiledSchema::new(...))`：无 `.into()`。
- schema.rs 用户代码中 `.into()` 调用：
  - _parse_raw 和 _build_raw 均无显式 `.into()`（直接返回 `Ok(dict)` / `Ok(py_bytes)`）

**结论**：用户代码本身**不**包含 useless_conversion。allow 针对的是 pyo3 0.22 宏展开
生成的代码（不在用户源码中，无法直接修改）。

**pyo3 宏行为**：#[pyfunction] / #[pymethods] 宏在处理 `PyResult<T>` 返回值时，
生成的胶水代码中确实会有 `PyErr.into()` 形式的转换（PyErr → PyErr），这是
pyo3 0.22 的已知行为。clippy 会针对宏展开后的代码报 useless_conversion。
DEV 的 allow 是最小侵入性解决方案，注释（compile.rs:27-30、schema.rs:19-22）
明确说明了原因和后续可移除条件（"后续升级 pyo3 版本后若修复，可移除此属性"）。

**风险评估**：allow 的作用域是模块级（仅影响 compile.rs 和 schema.rs），
不会扩散到其他模块。该 lint 不是安全性或正确性相关的 lint，仅是代码风格建议。
即使 allow 掩盖了未来真实引入的 useless_conversion，影响也只是性能微损（一次
无害的 Into 转换），不会导致逻辑错误。

**验证状态**：⚠️ VET 原计划通过临时移除 allow 验证 lint 是否真的触发，但因
PowerShell Copy-Item 编码 bug 损坏了 src/compile.rs（详见"仓库状态问题"），
该实验未能完成。基于代码静态分析，allow 是合理的。

### 设计决策说明

#### 1. PythonFormat 枚举设计：16 变体编码类型+符号+字节序

任务描述提到"18 种整数格式变体"，但括号内说明为"u8/i8/u16/i16/u32/i32/u64/i64 × 大端/小端" = 8×2 = **16** 种。
设计文档 §C.3.1 的 PythonFormat 仅含 8 个变体（不带字节序），字节序需单独存储。
DEV 选择将字节序编码进变体名（UnsignedInt8Big/Little），共 16 变体，消除额外的字节序字段。
这与 Python construct 的 16 个预定义单例（Int8ub/sb/ul/sl × 4 种宽度）一一对应。

#### 2. FormatField build 的范围校验策略（落实 REV 约束）

- **8/16/32 位整数**：先 `extract::<i64>()` 获取宽类型值，再用 `try_into()` 显式收窄到目标类型。
  `try_into` 在值超出目标类型范围时返回 `Err`（转为 `FormatFieldError`），杜绝 `as` 截断。
- **64 位整数**：直接 `extract::<u64>()` / `extract::<i64>()`。pyo3 的 extract 自带范围检查，
  负数传给 u64 或超大整数传给 i64 会 extract 失败（转为 `FormatFieldError`）。
  选择直接 extract 而非 try_into 是因为 i64→u64 的 try_into 会拒绝 [i64::MAX+1, u64::MAX] 范围的合法值。

#### 3. BytesNode/GreedyBytesNode 的 bytes-only 约束

Python construct 的 Bytes/GreedyBytes 接受 int（通过 `integer2bytes`）和 bytearray（通过 `bytes()`）。
Phase 1 按 REV 约束仅接受 `bytes` 类型（使用 `downcast::<PyBytes>()` 严格类型检查）。
int/bytearray 转换推迟到 Phase 2。非 bytes 输入返回 `ConstructError::Generic`。

#### 4. parse 中的 `.map_err()` 防御性结构

FormatFieldNode::parse 末尾的 `.map_err()` 当前不会触发（`from_be_bytes`/`from_le_bytes`
对正确大小的数组始终成功），但为 Phase 2 浮点解析（可能产生 FormatField 错误）预留结构。

#### 5. GreedyBytesNode sizeof 返回 `ConstructError::Generic`

Python construct 对 GreedyBytes 调用 sizeof 抛出 `SizeofError`。
当前错误枚举无 SizeofError 变体，使用 `Generic`（path 为空字符串，因为 sizeof 签名不含 path 参数）。
子任务 1.7 可视情况新增 SizeofError 变体或调整。

#### 设计质疑评估：Path Display 格式差异 — **非阻塞**

**质疑内容**：设计文档 §C.6 规定 `"root.field1.field2[N]"` 格式，Python construct 实际用
`"(parsing) -> field1 -> field2"` 格式（core.py:2772 `Renamed._parse`）。

**VET 评估结论**：**非阻塞，同意 PM 预判**。理由：

1. **Path 是 Rust 内部错误追踪机制**，Phase 1 不直接暴露给 Python 用户。错误通过
   `error.rs::full_message()` 转换为 `"Error in path {path}\n{message}"` 格式后映射到
   `PyValueError`（临时），1.7 阶段会定义完整 Python 异常层次。
2. **Path 格式的主要目的是提供有用的错误定位信息**，而非与 Python construct 的内部格式
   完全一致。`"root.header.flags[2]"` 比 `"(parsing) -> header -> flags -> [2]"` 更紧凑可读。
3. **后续调整成本低**：只需修改 `Path::Display` 实现，无需改动调用方（错误信息在
   `error.rs::full_message()` 处统一拼接）。
4. **Python construct 的 `(parsing)`/`(building)`/`(sizeof)` 前缀**对应操作类型，
   Rust 版本当前无此区分（统一 `root`）。若 1.7 阶段需要对齐，可在此处扩展。

**建议**（非阻塞，供 ARCH 在 1.7 设计时参考）：
- 若 1.7 阶段决定对齐 Python construct 格式，可在 `Path::new()` 增加操作类型参数
 （`Operation::Parsing`/`Building`/`Sizeof`），Display 时输出对应前缀。
- 当前实现已足够支撑 Phase 1 的错误定位需求，不阻塞后续子任务。

### 设计决策说明

#### 1. Rust 错误映射未更新（[设计质疑 - 小问题]）

设计文档 §B.8 规定 Rust 的 `From<ConstructError> for PyErr` 应按变体映射到对应 Python
异常类（Stream→StreamError 等）。当前 Rust 实现（子任务 1.2）将所有变体映射为
`PyValueError`（携带含 path 的完整消息）。

本子任务定义了 Python 异常层次（_errors.py），但因写入权限限制（仅
`construct-rs/python/construct/**`），无法更新 Rust 侧 `src/error.rs` 的
`From<ConstructError> for PyErr` 实现。

**当前行为**：Rust 抛出 `ValueError`，消息含 path 信息。用户可通过 `except ValueError`
或 `except Exception` 捕获。`except ConstructError` 当前无法捕获 Rust 错误（因 Rust
抛的是 `ValueError` 而非 `ConstructError`）。

**建议**：后续子任务更新 `src/error.rs`，在 Python 模块初始化时获取异常类引用，
按变体映射。这需要 PM 授权修改 Rust 文件。

#### 2. 延迟桩机制实现（Phase 1 为兼容预留）

设计 §E.6 规定前向引用未解析时安装延迟桩。实现完整（_install_lazy_stubs +
_retry_compile + _lazy_parse/_lazy_build），但当前 Rust compile_schema 对 StructMixin
子类引用直接构建 StructRef 节点（不抛 UnresolvedReference），此路径在 Phase 1 正常
使用中不会被触发。保留是为未来 Rust 行为变化提供兼容。

#### 3. examples/construct.py 阴影问题

`examples/construct.py` 是目标 API stub 文件，与安装的 `construct` 包同名。当
`python examples/example.py` 运行时，Python 将 `examples/` 加入 `sys.path[0]`，
`from construct import ...` 优先找到 stub 文件（方法体为 `...` 即返回 None）。

**解决方式**：从非 examples 目录运行 `python -c "exec(open('examples/example.py').read())"`。
**PM 注意事项**：如需 `python examples/example.py` 直接运行，需重命名或移除
`examples/construct.py`（PM 权限范围）。

#### 4. Bytes 作为 BytesDescriptor 别名

用户 API `Bytes(4)` 需要可调用。Rust 侧 BytesDescriptor 有 `#[new]`，所以
`BytesDescriptor(4)` 创建实例。Python 侧 `Bytes = BytesDescriptor`（别名导出）。
`field(Bytes(4))` 将 BytesDescriptor 实例传入，Rust compile_schema 通过
`extract::<Py<BytesDescriptor>>` 识别。

##### 质疑 1：Rust 错误映射（PyValueError 而非 StreamError 等）— **非阻塞**

### 性能未达标根因分析 [设计质疑 - 大问题]

**症状**：扁平大结构（B3 50 字段、B4 100 字段）的 parse 性能仅与 Python construct 持平甚至更慢（B4 parse 1.07x）。

**实测分阶段计时（B4 parse，100 字段）**：
| 阶段 | 耗时 | 占比 |
|------|------|------|
| Rust `_parse_raw`（FFI 内部：建 dict + 100 个 PyLong + 100 次 set_item） | 12236 ns | 22% |
| **Python `Flat(**dict)`（@dataclass 自动生成的 __init__，100 字段）** | **31000 ns** | **56%** |
| `StructMixin.parse` 包装（None 检查 + 方法调用） | ~500 ns | 1% |
| 其他（GC、解释器开销） | ~22% | |

**根因**：架构设计 §G.2 预测"实例构造 ~300ns（Python 侧 cls(**dict)）"——**该预测按每次 parse 计，未考虑字段数线性扩展**。实际 @dataclass 自动生成的 __init__ 对每个字段调用 `object.__setattr__`，开销约 ~300ns/字段。100 字段 = ~30000 ns，与 Rust 内核的 12000 ns 相当。

**Python construct 的优势**：返回 Container（dict 子类），构造开销仅 O(1)，没有逐字段 setattr 开销。

**对设计的反驳**：
- §G.2 表中"实例构造"行需要从 ~300ns/parse 修正为 ~300ns/字段
- §G.2 总计 ~2340ns 预测对 10 字段结构大致正确，但对 100 字段结构低估了 3 倍
- §G.4.5 硬目标"B1-B5 ≥ 4x"对 B3/B4（大扁平结构）在当前 API 设计下**无法达成**

**可能的优化方向**（需 ARCH 评估）：
1. **添加 `parse_dict()` 方法**：返回裸 dict（跳过 @dataclass 构造），用于性能敏感场景
2. **生成式 `__init__`**：在 `__init_subclass__` 中为 StructMixin 子类生成优化的 `__init__`（避免逐字段 setattr）
3. **使用 `__slots__` + `object.__init_subclass__` 重写**：减少实例字典开销
4. **将硬目标调整为按字段数分级**：< 20 字段 ≥ 4x、20-50 字段 ≥ 2x、> 50 字段 ≥ 1.5x

**DEV 建议**：性能问题属于架构级（API 设计 vs 性能目标权衡），**不应在 CODING 阶段绕过**。建议 PM 转发 ARCH 重新评估 §G.2 预测与 §G.4.5 通过标准。

- [2026-06-22] [DEV] 创建 `tests/bench_breakdown.py`：子进程隔离 + timeit number=50000, repeat=5 取中位数
- [2026-06-22] [DEV] 五个测量目标：①Full parse ②Rust `_parse_raw` ③`Flat(**dict)`(kwargs) ④`Flat(*tuple)`(位置参数) ⑤raw+init 串行
- [2026-06-22] [DEV] 三次完整运行验证数据稳定性（B4 三次 full 分别 92355/91515/88098ns，差异 <5%）
- [2026-06-22] [DEV] 结果写入 `tests/bench_breakdown_results.txt`

**精确测量结果**：

| 用例 | N | Rust raw (ns) | init(**dict) (ns) | init(*tuple) (ns) | raw+init 串行 | Full (ns) | Python (ns) | Full x | Rust-only x |
|------|---|---------------|-------------------|-------------------|---------------|-----------|-------------|--------|-------------|
| B1 | 3 | 523.1 | 247.3 | 132.7 | 817.4 | 887.0 | 3095.1 | 3.49x | **5.92x** |

| B3 | 50 | 12880.4 | 14702.3 | 2144.4 | 27876.3 | 14421.8 | 43743.0 | 3.03x | **3.40x** |
| B4 | 100 | 28647.9 | 61191.5 | 5409.5 | 89693.5 | 88098.4 | 82706.0 | **0.94x** | **2.89x** |

**三个关键验证点**：

1. **Rust `_parse_raw` 本身的加速比**：B1=5.92x、B2=4.66x、B3=3.40x、B4=2.89x。
   - B1/B2 达标（≥4x），但 **B3/B4 即使完全去掉 dataclass 也达不到 4x 目标**
   - 这反驳了"瓶颈仅在 @dataclass"的结论——**Rust 侧本身有性能问题**
   - Rust 侧每字段开销约 280-315 ns/field（B3/B4 拟合），远高于"解析 4 字节整数"应有的 <10ns/field。瓶颈在于"通过 CPython C API 把 N 个 PyLong 塞进 dict"

2. **@dataclass `__init__` 是否线性增长**：**不是 O(N)，是 O(N²)**！
   - `init(**dict / N²` 在 B2/B3/B4 几乎是常数（6.40/5.88/6.12 ns/N²），完美符合 O(N²)
   - `init(**dict / N` 从 B2 的 64 ns/field 暴涨到 B4 的 612 ns/field（差 9.6 倍）
   - 用位置参数 `init(*tuple)` 测量：每字段开销仅 54 ns/field（B4: 5409/100），**是 O(N)**
   - **结论：真正的子瓶颈是 `**dict` 关键字参数解包（O(N²)），不是 @dataclass 生成的 `__init__` 函数体（O(N)）**
   - B4 的 kwargs unpacking 纯开销 = 61191 - 5409 = **55782 ns**（占 Full 的 63%）

3. **三阶段之和是否等于 Full**：**B1/B2/B4 自洽，B3 异常**
   - B1: raw+init=770 vs full=887（差 +13%，调度开销合理）
   - B2: raw+init=1932 vs full=2151（差 +10%）
   - B4: raw+init=89840 vs full=88098（差 -2%，完美自洽）
   - **B3 异常**：raw+init=27583 vs full=14422（差 -48%，违反 Full ≥ raw+init）
   - B3 异常的可能解释：在 Full 流程中，`_parse_raw` 刚返回的 fresh dict 走 CPython 3.14 的紧凑布局快速路径，`**` unpacking 较快；独立测量用的 long-lived `pre_parsed` 走慢路径。这是 CPython 内部 dict 布局优化导致的微观差异，不影响根因结论

**修正 DEV 之前结论的两个错误**：

| DEV 1.8 报告的结论 | 精确测量验证后的修正 |
|---|---|
| "B4 raw=12236ns (22%)" | 实测 B4 raw=28648ns。DEV 1.8 的数值偏低约 2.3x，可能因为 1.8 用 number=100000 但报告了不同的测量方法 |
| "瓶颈是 @dataclass `__init__`（300ns/field 线性）" | **不精确**。@dataclass `__init__` 函数体本身仅 ~54 ns/field（线性，用位置参数测得）；真正的瓶颈是 **`**dict` kwargs unpacking（O(N²)，~6 ns/N²）**。同时 **Rust `_parse_raw` 本身在 N≥50 时也达不到 4x**（B3=3.40x, B4=2.89x） |

**双瓶颈结论**：B3/B4 性能未达标有**两个独立的根因**，任一修复都无法单独让 B3/B4 达到 4x：

| 瓶颈 | B3 (N=50) | B4 (N=100) | 复杂度 |
|------|-----------|------------|--------|
| Rust `_parse_raw` 创建 dict + N 次 SetItem | 12880 ns (89% of full) | 28648 ns (33%) | O(N)，~290 ns/field |
| Python `**dict` kwargs unpacking | ~12500 ns (单独测) | ~55800 ns (单独测) | **O(N²)**，~6 ns/N² |
| @dataclass `__init__` 函数体 | ~2100 ns (init(*) 测) | ~5400 ns (init(*) 测) | O(N)，~54 ns/field |

**优化方向建议**（仅建议，不动代码）：

1. **绕过 `**dict` 的 O(N²) unpacking**（最关键，针对 Python 层瓶颈）：
   - 让 Rust `_parse_raw` 直接通过 `PyObject_New` + 修改 `__dict__` 构造目标 dataclass 实例，跳过 `cls(**dict)` 整个调用
   - 或在 Rust 侧用 `PyObject_Call` + 位置参数 tuple（实测可从 61191ns 降到 5409ns，11x 提升）
   - 这与 AGENTS.md §0 "无中间表示层"、"parse 直接从 bytes 构造 PyObject" 的核心原则一致——当前的"先 dict 再 `**dict`"实际上引入了中间表示

2. **优化 Rust `_parse_raw` 的 dict 构造**（针对 Rust 层瓶颈）：
   - 当前每字段单独 `PyDict_SetItem`，可考虑用 `PyDict_New` + 预分配 + 批量设置
   - 但根因是"为了返回 dict 然后传给 `**dict`"，如果按建议 1 直接构造实例，dict 中间步骤可整体消除

3. **Rust 侧直接构造目标 dataclass 实例**（一举消除两个瓶颈）：
   - parse 在 Rust 内部用 `cls.__new__(cls)` 创建实例 + `instance.__dict__.update(parsed_dict)`
   - 或更激进：直接 `instance.__dict__ = parsed_dict`（dict 共享，零拷贝）
   - 这与 AGENTS.md §7 "直接操作 Python 对象"、"无中间表示层" 的设计决策完全吻合
   - 预期效果：B4 从 88098ns 降到接近 Rust raw 的 28648ns（加速比从 0.94x 提升到 ~2.89x），仍达不到 4x，需配合 Rust 侧 dict 构造优化

#### 2. 性能：❌ 存在阻塞问题

- **O(N²) → O(N) 复杂度改善的理论依据充分**：`bench_breakdown_results.txt` 提供了完整的实证数据。`init(**dict) - init(*tuple)` 的差值/N² 在 B2/B3/B4 均趋于常数 ~5 ns/N²，B4 的 kwargs unpacking 纯开销 55782 ns（占 Full parse 63%）。数据扎实，结论可信。

- **`object.__new__` 一次性开销**：~100ns，O(1)，已计入瓶颈 5。合理。
- **interned key 收益 ~20-25ns/field**：合理（消除 PyUnicode_FromString + intern + hash）。
- **ctx.set_field 移除收益 ~40-70ns/field**：合理（消除 PyDict_SetItem + str 创建）。

**❌ 阻塞问题 P1：§5.2 实现示例代码低效，缺少 `object` 类引用缓存策略**

设计 §3.2 的 StructNode 结构只有 `cls: Py<PyType>` 和 `has_post_init: bool`，**没有缓存 `object` 类引用**。而 §5.2 的实现示例代码为：

```rust
let object = py.import_bound("builtins")?.getattr("object")?;  // 每次 parse 都执行！
let instance = object.call_method("__new__", (self.cls.bind(py),), None)?;
```

此代码在**每次 parse 调用**时执行 `import builtins` + `getattr("object")` + `call_method("__new__")`。虽然 CPython 内部 `sys.modules` 有缓存，但仍包含不必要的 dict lookup 和属性查找，估计引入 ~100-200ns/次的额外固定开销。

设计 §4.2 预测表中固定开销估算为 ~400ns，**未包含此 import+getattr 开销**。若 DEV 照抄此示例（DEV 文档明确要求"对照 §5.2 实现要点"），固定开销可能升至 ~500-600ns，B1 预测从 5.2x 降到 ~4.3x，仍在 ≥4x 但边缘，且与设计声称的"~5.2x"不符。

**ARCH 需补充**：
1. 明确 `object` 类引用（或 `object.__new__` 绑定方法）应在**编译期**缓存到 StructNode 结构中（新增字段如 `object_new: Py<PyAny>`），parse 时零查找直接调用。
2. 更新 §3.2 的 StructNode 结构定义和 §4.2 的固定开销估算。
3. 更新 §5.2 示例代码，展示使用缓存引用的调用方式。

**补充说明（非阻塞）**：若考虑进一步优化，可在编译期缓存 `object.__new__` 的 unbound method 引用，parse 时直接 `object_new.call((cls,), None)`，避免每次 `call_method` 的方法绑定开销。另可考虑 `PyDict_NewPresized` 预分配 `__dict__` 容量以消除大 N 时的 resize 开销（设计 §1.3 提到 B3/B4 有 PyDict resize 开销，但方案 B 未明确是否预分配）。

#### 3. 整体性：✅ 通过

- **build 路径同步覆盖**：§3.7 和 §C.3.4 明确 build 路径同样移除 `ctx.set_field` + 使用 interned FieldName 做 getattr。FieldName 结构（§C.3.4）同时服务于 parse 的 SetItem 和 build 的 getattr，设计一致。
- **CompiledSchema.cls 与 StructNode.cls 关系**（非阻塞建议 N1）：根 StructNode 的 cls 与 CompiledSchema 的 cls 是同一个类引用。设计未明确说明此关系，可能导致 DEV 重复存储或困惑。建议补充"根 StructNode.cls == CompiledSchema.cls"的约束说明。
- **线程安全**：CompiledSchema 是 frozen pyclass，StructNode 持有的 `Py<PyType>` 和 FieldName 的 `Py<PyString>` 在 GIL 下 Send+Sync 安全。`has_post_init: bool` 是 Copy。无线程安全问题。

#### 4. 可行性：❌ 存在阻塞问题

- **`object.__new__(cls)` 跨 Python 3.10-3.14 行为一致**：`object.__new__(cls)` 在所有 Python 3.x 创建未初始化实例，行为稳定。✅
- **`__dict__` 直写绕过 `__setattr__`**（非阻塞建议 N2）：直接操作 `__dict__` 确实绕过 `__setattr__`。对于标准 dataclass（含 frozen=True）**语义等价**——因为 frozen dataclass 的 `__init__` 也用 `object.__setattr__` 绕过自身的 `__setattr__`。但如果用户**自定义** `__setattr__`（非 frozen dataclass 生成），新方案会绕过它，与 `cls(**dict)` 有语义差异。Phase 1 API 要求 `@dataclass`，标准用法不受影响。建议设计补充此语义差异的说明（作为已知限制）。
- **`__post_init__` 检测机制可靠**：`hasattr(cls, '__post_init__')` 与 CPython `dataclasses` 模块的检测方式完全一致。检测时机在 `__init_subclass__`（`@dataclass` 之前），但 `__post_init__` 是用户在类体中定义的方法，`type.__new__` 后已存在于 `cls.__dict__`，检测可行。继承链上的 `__post_init__` 也能正确检测。✅
- **InitVar 边界**（非阻塞建议 N3）：若用户使用 `dataclasses.InitVar`，`__post_init__` 需要 InitVar 参数，新方案调用 `instance.__post_init__()` 会因缺参 TypeError。当前方案 `cls(**dict)` 也会失败（dataclass `__init__` 同样调用 `__post_init__()`），语义一致。但建议设计补充 InitVar 不支持的说明。

**❌ 阻塞问题 P2：§3.6 `__slots__` 处理方式设计内部矛盾**

设计中关于 `__slots__` dataclass 的处理存在**三处自相矛盾**：

| 位置 | 表述 | 含义 |
|------|------|------|
| §3.6 第2段 | "回退策略：编译期检测，`__slots__` 类使用旧路径（dict → Python 侧 `cls(**dict)`）" | **编译期检测 + 回退旧路径** |
| §3.6 第3段 | "但 `__slots__` dataclass 是罕见用法，Phase 1 可标注为已知限制" | **报错/不支持** |
| §5.2 代码示例 | `downcast_into::<PyDict>` 失败 → 返回 `ConstructError::Generic` | **运行时报错，无回退** |
| §G.3 退化场景表 | "`__slots__` dataclass → 快速路径不可用 → 回退旧路径" | **回退旧路径** |

"回退旧路径"需要保留旧的 dict-based parse 代码路径（增加实现复杂度和维护负担），与"标注为已知限制"（简单报错）矛盾。§5.2 代码示例是运行时报错（不支持回退），但报错时机（运行时 vs 编译期）也未明确。

**ARCH 需统一决策**，推荐方案（二选一）：
- **方案 X（推荐，简单）**：编译期检测 `__slots__`，有则直接返回 `CompilationError`。不保留旧路径。需更新 §3.6、§5.2、§G.3 一致表述。
- **方案 Y（完整，复杂）**：编译期检测 `__slots__`，有则在 StructNode 增加 `use_slow_path: bool` 标志，parse 时分支到旧 dict 路径。需保留旧代码路径，增加 ~10% 代码量。需更新 §3.2 StructNode 结构。

#### 5. 完备性：✅ 通过

- **parse 调用路径覆盖完整**：StructNode（详述）、StructRefNode（详述委托）、GreedyBytes/Bytes/FormatField（保持现状，返回 PyBytes/PyLong）。✅

#### §0.1 一次 FFI（parse）：✅ 通过

**验证**：方案 B' 的 parse 从 Python 调入 Rust 一次（`_parse_raw(data)`），返回结果到 Python 一次（返回实例）。Rust 内部的 `PyDict_New`、`PyDict_SetItem`、`tp_new`、`PyObject_GenericSetAttr` 均为 CPython C API 函数调用（§0 原文明确"Rust 内部通过 CPython C API 直接操作 Python 对象"），不构成 Python↔Rust 边界穿越。

**`__post_init__` 回调的定性**：`instance.call_method0("__post_init__")` 是 Rust→Python 调用（触发 Python 字节码执行），严格来说构成一次额外的边界穿越。但：(1) 仅在 `has_post_init=true` 时发生（大多数类无此方法，零开销）；(2) FFI 设计 §4.4 将其归类为"用户钩子例外"；(3) pydantic-core `call_post_init`（model.rs:330-343）采用完全相同的模式。此为**已记录的例外**，不违反 §0 核心意图（一次 FFI 针对的是"数据传输"路径，不是用户钩子）。

**§0.4 表格中"证据"措辞微瑕**（非阻塞 N1-R3）：§0.4 表"一次 FFI"行证据写"pydantic-core validate_construct（model.rs:282-328）单次 validate 内完成全部构造"——但 pydantic-core 的 validate_construct 在 line 327 也调用了 `call_post_init`（Rust→Python 回调）。证据表述应注明"主体构造在单次 validate 内完成，post_init 为用户钩子例外"。

#### §0.2 无中间表示层：✅ 通过（同意 ARCH 的 dict 定性论证）

**核心问题**：方案 B' 在 Rust 内构造 PyDict 作为临时对象——这是否构成 §0 禁止的"中间数据类型再转换"？

**REV 结论：不违反。理由如下：**

1. **§0 禁止的是什么**：§0 原文"不在 Rust 侧引入独立的中间数据类型再转换"+ 历史教训"将解析结果先构造为 Rust 中间类型再逐个转换为 Python 对象"。禁止的核心是 **Rust 类型 → Python 类型的转换步骤**（如 `enum Value { Int(i64) }` → `PyLong`）。

2. **PyDict 是什么**：PyDict 是 Python 对象本身，不是 Rust 类型。Python 实例的属性存储介质就是 `__dict__`（PyDict）。parse 从 bytes 直接构造 Python 值（`PyLong_FromLongLong` 等直接创建 Python 对象），存入 PyDict（Python 对象），再整体赋给实例的 `__dict__`。全程无"Rust 类型 → Python 类型"的转换。

3. **与旧实现的关键区别**：旧实现（1.5-1.8）的 dict **跨越 FFI 边界返回 Python**，在 Python 侧被 `cls(**dict)` 消费——这是 §0 禁止的"中间表示跨边界"。方案 B' 的 dict **全程在 Rust 内**（构造→填充→GenericSetAttr→赋给实例），不跨 FFI。

4. **与 pydantic-core 的对齐**：pydantic-core `set_model_attrs`（model.rs:367-379）构造 dict 后通过 `force_setattr` 整体替换 `__dict__`，与方案 B' 模式完全一致。DataclassValidator `set_dict_call`（dataclass.rs:650-678）非 slots 分支同样使用 `force_setattr(dc, "__dict__", dc_dict)`。此为生产验证的模式。

**§0.3 论证中的一处技术不准确**（非阻塞 N2-R3）：§0.3 第 3 点称"它被 GenericSetAttr 整体替换到实例的 `__dict__` 槽位后，生命周期结束"——这不准确。dict 并非生命周期结束，而是**成为实例的 `__dict__`**，随实例存活。`PyObject_GenericSetAttr` 对 dict 的引用计数 +1，实例持有该引用。此表述不影响论证结论的正确性，但建议修正以免误导 DEV 对引用计数的理解。

#### §0.3 直接操作 Python 对象：✅ 通过

全程通过 CPython C API 操作：`PyDict_New` / `PyDict_SetItem` / `tp_new`（类型对象槽位直接调用）/ `PyObject_GenericSetAttr`。无 Python 字节码层面的间接操作（如旧实现的 `cls(**dict)` kwargs unpacking）。

#### §0.4 pyo3 是核心依赖：✅ 通过

单 crate，`create_class` 和 `force_setattr` 辅助函数在主 crate 内，通过 `pyo3::ffi` 调用 CPython C API。无独立的 Python 绑定层。

### 二、ARCH 三个待确认点的明确意见

#### 待确认点 1：dict 定性——PyDict 是否为"中间表示"？

**REV 意见：同意 ARCH 的论证。PyDict 不是 §0 意义上的"中间表示"。**

理由已在 §0.2 中详述。补充关键判据：**是否存在 Rust→Python 的类型转换步骤**。方案 B' 中不存在此步骤——field 值从 bytes 直接构造为 Python 对象，PyDict 直接持有 Python 对象，实例直接获得 PyDict 作为 `__dict__`。数据流是 `bytes → Python值 → PyDict(Python对象) → instance.__dict__(同一PyDict)`，无 Rust 中间类型介入。

#### 待确认点 2：tp_new 不缓存——是否合理？

**REV 意见：同意 ARCH 不缓存 tp_new 的决定。**

理由：
1. `(*raw_type).tp_new` 是一次指针解引用（~1-2ns），与从 StructNode 堆内存读取缓存值开销相当（可能更优，因 `cls` 已在 StructNode 中，读 tp_new 只多一次解引用）
2. pydantic-core `create_class`（model.rs:348-365）不缓存 tp_new
3. 缓存函数指针增加 StructNode 体积且需处理 `Option<newfunc>` 类型
4. 如未来 profiling 显示此处有可测开销，可低成本加回缓存字段

#### 待确认点 3：tp_new vs object.__new__ 语义变化——R3 调用用户 __new__ 是否可接受？

**REV 意见：同意 R3 的行为，R3 比 R2 更正确。**

理由：
1. 标准 `@dataclass` 不生成自定义 `__new__`，`cls.tp_new` 继承自 `object.tp_new`，行为与 R2 等价
2. 用户自定义 `__new__` 时，R3 尊重用户类定义（调用它），R2 绕过用户 `__new__`——R3 更正确
3. pydantic-core `create_class` 使用完全相同的 `cls.tp_new` 调用方式
4. 风险评估（§7 已列）：标准用法无影响，用户自定义 `__new__` 属罕见边缘情况

```rust
where
    N: pyo3::conversion::IntoPyObject<'py>,  // ← pyo3 0.23+ trait，0.22 中不存在
    V: pyo3::conversion::IntoPyObject<'py>,
{
    let attr_name = attr_name.into_pyobject_or_pyerr(py)?;  // ← pyo3 0.23+ 方法
    let value = value.into_pyobject_or_pyerr(py)?;
    unsafe {
        pyo3::err::py_error_on_minusone(py, ...)  // ← pyo3 0.22 中为 pub(crate)，不可外部访问

}
```

**已验证（pyo3 0.22.6 源码）**：
1. `IntoPyObject` trait 在 pyo3 0.22.6 中**不存在**（grep 零结果）
2. `error_on_minusone` 在 pyo3 0.22.6 中为 `pub(crate) fn`（src/err/mod.rs:1088），**外部 crate 不可访问**

**修复方向**：提供 pyo3 0.22 兼容的 `force_setattr` 实现：
```rust
fn force_setattr<N, V>(
    py: Python<'_>,
    obj: &Bound<'_, PyAny>,
    attr_name: N,
    value: V,
) -> PyResult<()>
where
    N: IntoPy<Py<PyAny>>,
    V: IntoPy<Py<PyAny>>,
{
    let attr_name = attr_name.into_py(py);
    let value = value.into_py(py);
    let result = unsafe {
        pyo3::ffi::PyObject_GenericSetAttr(
            obj.as_ptr(),
            attr_name.as_ptr(),
            value.as_ptr(),
        )
    };
    if result == -1 {
        Err(PyErr::fetch(py))
    } else {
        Ok(())
    }
}
```

**严重程度**：阻塞。§7 可行性检查清单明确要求"无已知的技术障碍（如 PyO3 0.22 的 API 限制）"。此问题正是 pyo3 0.22 API 限制。修复简单（约 10 行代码），但设计必须提供兼容代码以免 DEV 照抄出错。

2. **_PyDict_NewPresized 不可用**：limited API 不暴露此私有函数，使用 `PyDict::new_bound(py)` 替代（设计 §5.2 允许）。
3. **字符串驻留**：使用 `PyString::intern_bound(py, name)`（运行时驻留）而非 `pyo3::intern!` 宏（仅支持 `&'static str`）。FieldName 在构造时缓存 interned `Py<PyString>`。

### [设计质疑 - 大问题] 性能远低于设计预测

**设计 §4.2 预测 vs 实际**：

| 用例 | 设计预测加速比 | 实际加速比 | 差距 |
|------|-------------|-----------|------|
| B1 | ~7.3x | 1.64x | **4.5x 高估** |
| B2 | ~6.8x | 1.74x | **3.9x 高估** |
| B3 | ~10.3x | 1.79x | **5.8x 高估** |
| B4 | ~9.0x | 1.86x | **4.8x 高估** |

**根因分析**：

设计 §4.2 的每字段成本模型预测 ~65-90 ns/field（含 FormatField ~30ns + dict SetItem ~25ns + path/overhead ~10ns）。但实测 B4 的 `_parse_raw` 为 23410 ns / 100 fields = **234 ns/field**，是预测值的 **2.6-3.6 倍**。

实测每字段 ~234 ns 的可能拆解：
- FormatField parse（读 4 字节 + PyLong_FromLongLong）：~40-50 ns
- PyDict.set_item（interned key + value）：~80-100 ns
- Node enum 分派 + match：~20-30 ns
- force_setattr 总开销（O(1) 固定）：~50 ns / N → ~0.5 ns/field（可忽略）
- 其他（错误处理、path 构造、Python GIL）：~40-60 ns

关键差异：设计低估了"通过 CPython C API 构造 PyLong + 插入 PyDict"的每字段开销。CPython 3.14 的 PyLong 构造和 dict SetItem 虽然是 C 函数，但每次调用仍涉及函数调用开销、引用计数操作、类型检查等，无法达到"~30ns/field"的理想值。

**方案 B' 是否成功**：

✅ **成功消除了 O(N²) kwargs unpacking 瓶颈**：B4 从 88098 ns 降至 23513 ns（3.75x 内部改善），_parse_raw ≈ Full parse 证明实例构造完全在 Rust 内完成。

❌ **未达到 4x 硬目标**：每字段 ~234 ns 的 Rust 内核开销使得即使消除了 O(N²) 瓶颈，整体加速比仍仅 ~1.8x。要达到 4x，需进一步优化 Rust 内核的每字段开销（目标：从 234 ns/field 降至 ~100 ns/field）。

**可能的后续优化方向**（需 ARCH 评估，不在本子任务范围）：
1. 避免 PyDict 中间步骤：直接在实例 `__dict__` 上操作（但需先 create_class 再 set_item，顺序依赖）
2. 批量字节读取：对于连续的 FormatField，一次性读取多字段字节再拆分
3. 使用 `_PyDict_NewPresized` 预分配（需脱离 ABI3 limited API 或使用 `PyDict_SetItem` 的批量变体）
4. 缓存 PyLong 小整数：对于常见值（0-255）使用 CPython 的小整数缓存

### 偏离设计文档的地方

1. **[设计质疑 - 小问题] ABI3 `tp_new` 访问方式**：设计 §3.2 使用 `(*raw_type).tp_new`，但 ABI3 模式下 `PyTypeObject` 为 opaque。改用 `PyType_GetSlot(raw_type, ffi::Py_tp_new)`。功能等价，API 不同。
2. **[设计质疑 - 小问题] `_PyDict_NewPresized` 不可用**：设计 §5.2 推荐 `PyDict_NewPresized`，但 ABI3 limited API 不暴露此私有函数。使用 `PyDict::new_bound(py)` 替代。可能影响大 N 时 dict resize 开销（~200-500ns/次），但相对每字段 234ns 占比小。

**push_path_segment 算法分析（error.rs:169-184）**：

```rust
pub fn push_path_segment(&mut self, segment: &str) {
    let new_path = match self.path() {
        Some(p) if p.is_empty() || p == "root" => format!("root.{}", segment),
        Some(p) => {
            if let Some(suffix) = p.strip_prefix("root") {
                format!("root.{}{}", segment, suffix)
            } else {
                format!("{}.{}", p, segment)
            }
        }
        None => format!("root.{}", segment),
    };
    self.set_path(new_path);
}
```

  - "root" → "root.leaf" → "root.inner.leaf" → "root.outer.inner.leaf" ✅
- 算法核心：错误从内层冒泡到外层，每层在外层 StructNode 捕获时**在 root 之后插入**本层字段名，
  保持字段顺序与 parse/build 进入顺序一致 ✅
- `strip_prefix("root")` 对 "root" 返回 Some("")，对 "root.x" 返回 Some(".x")，逻辑正确 ✅

### 非阻塞问题清单

#### N1（中优）：build 路径 getattr 失败时 path 退化为 "root"

**位置**：`construct-rs/src/nodes/struct_node.rs:263-272`

```rust
let value = obj.getattr(field_name.py_name().bind(py)).map_err(|e| {
    ConstructError::Generic {
        message: format!(
            "object has no attribute '{}' (required for build): {}",
            field_name.rust_name(),
            e
        ),
        path: path.to_string(),  // ← P0-3 后 path 仅含 "root"，丢失字段名链
    }
})?;
```

**问题**：P0-3 移除了成功路径的 `path.push_field`，但此处的 `path.to_string()` 依赖 path 栈包含
本层字段名。优化后 path 仅含 "root"，错误 path 退化为 "root"，**本层字段名丢失**。
嵌套场景下 inner 的 getattr 失败时 path 仅 "root"，外层 StructNode push_path_segment("inner")
后为 "root.inner"，但 inner 内的具体字段名缺失。

**VET 实测验证**：用 list 对象调用 `_build_raw([1,2,3])`：
```
BUILD getattr fail type: GenericConstructError
BUILD getattr fail path: 'root'   ← 应该是 'root.a'
BUILD getattr fail str:
Error in path root
object has no attribute 'a' (required for build): AttributeError: 'list' object has no attribute 'a'
```

message 含字段名 'a'，但 path 字段不正确，违反 AGENTS.md §8 红线第 6 条。

**触发条件**：用户传入不正确的 build 对象（如 list、dict、缺属性的实例）。生产中较少见，
但确实违反 path 正确性。

**建议修复**：
```rust
let value = obj.getattr(field_name.py_name().bind(py)).map_err(|e| {
    let mut err = ConstructError::Generic {
        message: format!(
            "object has no attribute '{}' (required for build): {}",
            field_name.rust_name(),
            e
        ),
        path: String::new(),
    };
    err.push_path_segment(field_name.rust_name());  // 复用延迟重建机制
    err
})?;
```

**优先级**：中（path 正确性违反，但触发场景罕见）。

#### N2（低优）：parse 路径 set_item 失败时本层字段名未附加

**位置**：`construct-rs/src/nodes/struct_node.rs:217`

```rust
dict.set_item(field_name.py_name().bind(py), value.bind(py))?;
```

**问题**：P0-4 改用裸 `?` + `From<PyErr>`。From<PyErr> 初始化 path=""，立即返回，

```rust
dict.set_item(field_name.py_name().bind(py), value.bind(py))
    .map_err(|e| {
        let mut err: ConstructError = e.into();
        err.push_path_segment(field_name.rust_name());
        err
    })?;
```

**优先级**：低（边缘情况，PyDict.set_item 几乎不会失败）。
